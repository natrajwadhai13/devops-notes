# Module 23: Best Practices

Writing a script that **works** is important, but writing a script that is **readable, secure, reusable, and maintainable** is even more important.

Best practices are followed in:

* Linux Administration
* DevOps
* Cloud Engineering
* Production Environments
* CI/CD Pipelines

---

# Why Follow Best Practices?

Good scripts are:

* Easy to understand
* Easy to maintain
* Less error-prone
* Secure
* Faster
* Reusable

---

# 1. Coding Standards

Follow consistent coding conventions.

---

## Use Meaningful Variable Names

❌ Bad

```bash id="d4n7c1"
a=10

b=20
```

✅ Good

```bash id="j7x3m2"
backup_dir="/backup"

server_name="web01"
```

---

## Use Uppercase for Constants

```bash id="x5q1v9"
BACKUP_DIR="/backup"

LOG_FILE="/var/log/backup.log"
```

---

## Use Lowercase for Variables

```bash id="n2w8k4"
username="natraj"

hostname="server01"
```

---

## Indentation

Use consistent indentation (2 or 4 spaces).

```bash id="g6p3z8"
if [ -f file.txt ]
then
    echo "Found"
fi
```

---

## Add Comments

```bash id="m9t4b7"
# Backup Application Data

cp -r /data /backup
```

Avoid unnecessary comments.

❌

```bash id="r8k2j5"
# This command prints Hello

echo "Hello"
```

---

# 2. Script Structure

A professional Bash script follows a standard structure.

```bash id="v4h9s6"
#!/bin/bash

set -euo pipefail

# Variables

# Functions

# Main Script
```

---

## Example

```bash id="f3q7u2"
#!/bin/bash

set -euo pipefail

LOG_FILE="/tmp/script.log"

backup() {

    echo "Backup Started"

}

backup
```

---

## Recommended Order

```text id="h8n1x4"
1. Shebang

2. Shell Options

3. Variables

4. Functions

5. Main Logic
```

# 3. Error Handling

Never ignore command failures.

---

## Good

```bash id="k5d8r1"
cp source destination || exit 1
```

---

## Better

```bash id="p7m4w9"
if cp source destination
then
    echo "Success"
else
    echo "Failed"
    exit 1
fi
```

---

## Use Functions

```bash id="w1z6n3"
error_exit() {

    echo "ERROR: $1"

    exit 1

}
```

Usage

```bash id="c9x5t7"
cp file backup || error_exit "Backup Failed"
```

Avoid repeating code.

---

---

## Good

```bash id="d1m6r9"
}
```

Usage

```bash id="j4t8p2"

```

# 6. Secure Scripting

Security is critical in production.

---

## Quote Variables

❌

```bash id="a2p8f5"
rm $file
```

✅

```bash id="n5w1c8"
rm "$file"
```

---

## Validate User Input

```bash id="g3v7x2"
if [ -z "$username" ]
then
    echo "Username Required"
    exit 1
fi
```

---

## Check File Exists

```bash id="l8d4m9"
if [ ! -f config.txt ]
then
    exit 1
fi
```

---

## Avoid Hardcoded Passwords

❌

```bash id="r1z6q4"
PASSWORD="admin123"
```

✅

```bash id="p9x2k7"
read -s PASSWORD
```

or

```bash id="t6w5n1"
PASSWORD="$DB_PASSWORD"
```

---

## Least Privilege

Run scripts with the minimum permissions required.

Avoid running everything as `root`.

---

# 7. Performance Optimization

Efficient scripts run faster and use fewer resources.

---

## Use Built-in Features

Instead of

```bash id="k2m9d8"
expr 5 + 10
```

Use

```bash id="c5t4q1"
echo $((5+10))
```

---

## Avoid Unnecessary cat

❌

```bash id="z8v6p3"
cat file.txt | grep ERROR
```

✅

```bash id="f7r2w9"
grep ERROR file.txt
```

---

## Read Files Efficiently

```bash id="m1q8k5"
while read line
do
    echo "$line"
done < file.txt
```

---

## Use Local Variables

```bash id="n4x7v2"
function demo() {

    local name="Linux"

}
```

---

## Use Arrays

Instead of

```bash id="b3k6m1"
server1

server2

server3
```

Use

```bash id="y5p9r4"
servers=("web01" "web02" "db01")
```

# Complete Script Template

```bash id="u6n3k8"
#!/bin/bash

set -euo pipefail

LOG_FILE="/tmp/backup.log"

log() {

    echo "$(date) : $1" | tee -a "$LOG_FILE"

}

backup() {

    cp -r "$1" "$2" || exit 1

}

main() {

    log "Backup Started"

    backup "/etc" "/backup"

    log "Backup Completed"

}

main
```

# Best Practices for DevOps Scripts

* Always start scripts with:

```bash id="k1n7w4"
#!/bin/bash

set -euo pipefail
```

* Use functions to organize code into logical units.
* Store configuration values in variables at the top of the script.
* Quote every variable expansion unless unquoted behavior is explicitly required.
* Check prerequisites (commands, files, permissions) before performing work.
* Log important actions and failures with timestamps.
* Use exit codes consistently:

  * `0` = Success
  * Non-zero = Error
* Clean up temporary files using `trap`.
* Test scripts in a development or staging environment before running them in production.

# Interview Questions

### 1. Why should you use `set -euo pipefail`?

It makes scripts safer by:

* `-e` → Exits on errors.
* `-u` → Treats undefined variables as errors.
* `pipefail` → Fails a pipeline if any command fails.

---

### 2. Why should variables always be quoted?

To prevent issues caused by spaces, wildcard expansion, and word splitting.

Example:

```bash id="g8v2m6"
cp "$SOURCE" "$DEST"
```

---

### 3. Why are functions important?

Functions improve code reusability, readability, and maintenance by avoiding duplicated code.

---

### 4. Why should scripts use logging?

Logging records execution details, making it easier to troubleshoot failures and audit script activity.

---

### 5. What is the purpose of `trap`?

To perform cleanup or execute specific actions when a script exits or receives signals.

---

### 6. Why should you avoid hardcoded passwords?

Hardcoded passwords expose sensitive information and create security risks. Use environment variables, secret management systems, or prompt securely with `read -s`.

---

### 7. Why are absolute paths recommended in scripts?

Because scripts may run in environments where the current working directory or `PATH` is different (for example, cron jobs or CI/CD pipelines).

---

### 8. Why should input be validated?

To prevent invalid data, unexpected behavior, security issues, and accidental misuse.

---

### 9. What is the recommended structure of a Bash script?

```text id="c7q9m5"
1. Shebang
2. Shell options
3. Variables
4. Functions
5. Main logic
```

---

### 10. What is the biggest mistake beginners make in Bash scripts?

Common mistakes include:

* Not quoting variables
* Ignoring command failures
* Hardcoding values
* Repeating code instead of using functions
* Running scripts without testing them
* Skipping logging and input validation

> **Interview Tip:** Many interviewers focus less on syntax and more on **how you write production-quality scripts**. Demonstrating good practices such as `set -euo pipefail`, proper error handling, reusable functions, logging, input validation, and secure scripting often leaves a stronger impression than writing a complex script.
