# 29. DNS & Name Resolution Troubleshooting

> DNS troubleshooting is about determining whether a problem is caused by **name resolution, DNS configuration, DNS servers, network connectivity, search domains, `/etc/hosts`, systemd-resolved, caching, or the remote application itself**. A key interview skill is separating a **DNS problem** from a **network connectivity problem**.

# Q296. What is DNS and how does name resolution work in Linux?

## Answer

**DNS (Domain Name System)** converts human-readable hostnames into IP addresses.

Example:

```text id="2q8m4x"
www.example.com
       |
       v
     DNS
       |
       v
  93.184.216.34
```

Applications normally need an IP address to establish network communication.

### Basic Linux Name Resolution Flow

A simplified flow is:

```text id="x7m3q8"
Application
     |
     v
Name Service Switch
     |
     v
/etc/nsswitch.conf
     |
     +----------------+
     |                |
     v                v
/etc/hosts          DNS
                      |
                      v
                DNS Server
                      |
                      v
                  IP Address
```

### Check NSS Configuration

```bash id="p5m8x2"
cat /etc/nsswitch.conf
```

Look for:

```text id="q3m7x1"
hosts: files dns
```

This commonly means:

```text id="8x2m5q"
1. Check /etc/hosts
2. Then query DNS
```

The exact configuration can differ by distribution and environment.

### Check Hostname

```bash id="m7x3q2"
hostname
```

```bash id="x4m8q1"
hostname -f
```

### Important

DNS is not the same as network connectivity.

```text id="5m8x2q"
DNS
  ↓
Name → IP

Network
  ↓
IP → Destination
```

### Example

If:

```bash id="j2q7m4"
ping 10.10.10.20
```

works but:

```bash id="p8m3x5"
ping app.example.com
```

fails with name-resolution errors, DNS/name resolution is a strong suspect.

### Interview Tip

> "DNS resolves names to IP addresses. On Linux, name resolution can involve NSS, `/etc/hosts`, DNS servers, and local resolver services. I check the name-resolution configuration before assuming the problem is networking."

# Q297. How do you check DNS configuration on a Linux server?

## Answer

Start with the resolver configuration.

### Step 1: Check `/etc/resolv.conf`

```bash id="m8q3x7"
cat /etc/resolv.conf
```

Example:

```text id="q5m2x8"
search example.com
nameserver 10.10.10.10
nameserver 10.10.10.11
```

Important fields:

```text id="7x3m9q"
nameserver
search
options
```

### Step 2: Check NSS

```bash id="p4m8x2"
cat /etc/nsswitch.conf
```

Look for:

```text id="x7m2q5"
hosts:
```

### Step 3: Check DNS Resolution

```bash id="q8m3x1"
getent hosts example.com
```

### Step 4: Use `dig`

```bash id="m5x7q2"
dig example.com
```

Check command:

```bash id="p2m8x4"
command -v dig
```

### Step 5: Check Network Configuration

On NetworkManager systems:

```bash id="x3q7m1"
nmcli device show
```

Search DNS information:

```bash id="m8x2q5"
nmcli device show | grep -i dns
```

### Step 6: Check Resolver Service

Depending on the system:

```bash id="q4m7x2"
systemctl status systemd-resolved
```

or:

```bash id="y8m3q5"
systemctl status NetworkManager
```

Do not assume `systemd-resolved` is used on every Linux distribution.

### Step 7: Check Routing

```bash id="p5x8m2"
ip route
```

DNS queries still require network connectivity to the configured DNS server.

### Interview Tip

> "I check `/etc/resolv.conf`, `/etc/nsswitch.conf`, resolver service configuration, `getent`, `dig`, NetworkManager DNS information, and routing to the DNS server."

# Q298. How do you troubleshoot "Could not resolve host" errors?

## Answer

This usually means the application could not resolve the hostname to an IP address.

Example:

```text id="8m2x5q"
curl: Could not resolve host: example.com
```

### Step 1: Test With `getent`

```bash id="q5m8x2"
getent hosts example.com
```

If this fails, continue investigating name resolution.

### Step 2: Check `/etc/resolv.conf`

```bash id="m7x3q1"
cat /etc/resolv.conf
```

Check:

```text id="4x8m2q"
nameserver
search
```

### Step 3: Test DNS Directly

```bash id="p2m8x5"
dig example.com
```

### Step 4: Test Specific DNS Server

```bash id="x7m4q2"
dig @10.10.10.10 example.com
```

This helps distinguish:

```text id="m5x8q2"
Local resolver configuration
```

from:

```text id="q3m7x1"
DNS server problem
```

### Step 5: Check DNS Server Reachability

```bash id="v8m2x4"
ping -c 4 10.10.10.10
```

Ping may be blocked, so also consider testing DNS itself:

```bash id="k4m7x2"
dig @10.10.10.10 example.com
```

### Step 6: Check Routing

```bash id="x2m8q5"
ip route get 10.10.10.10
```

### Step 7: Check Firewall

Verify that DNS traffic is not being blocked.

DNS commonly uses:

```text id="9m3x7q"
UDP 53
TCP 53
```

TCP may be needed for certain DNS responses and DNS operations.

### Step 8: Check `/etc/hosts`

```bash id="p7m2x8"
cat /etc/hosts
```

A wrong static entry can override DNS depending on NSS configuration.

### Possible Causes

```text id="4x7m2q"
Wrong nameserver
DNS server unavailable
Network problem
Firewall blocking DNS
Incorrect /etc/resolv.conf
Wrong /etc/hosts entry
NSS configuration
Search domain issue
DNS server-side problem
```

### Interview Tip

> "For a 'Could not resolve host' error, I first reproduce it with `getent` and `dig`, inspect `/etc/resolv.conf` and NSS configuration, test the configured DNS server directly, verify routing and DNS traffic, and check `/etc/hosts`."

# Q299. How do you test DNS resolution using dig, nslookup, and getent?

## Answer

These tools test different parts of the resolution process.

### 1. `getent`

```bash id="q3m7x2"
getent hosts example.com
```

This uses the system's configured name-service mechanisms.

Therefore, it is useful for checking:

```text id="m8x2q5"
What the application/system resolver may see
```

### 2. `dig`

```bash id="x5m8q2"
dig example.com
```

It directly queries DNS and provides detailed DNS information.

Useful for:

```text id="p7m3x8"
A/AAAA records
CNAME
TTL
DNS server
Response status
Query time
```

Check a specific DNS server:

```bash id="m2x7q4"
dig @10.10.10.10 example.com
```

### 3. `nslookup`

```bash id="q8m3x5"
nslookup example.com
```

Check availability:

```bash id="x4m7q2"
command -v nslookup
```

### Comparison

| Command        | Main Use                            |
| -------------- | ----------------------------------- |
| `getent hosts` | Test system name-service resolution |
| `dig`          | Detailed DNS query/testing          |
| `nslookup`     | Basic DNS query/testing             |

### Important Difference

Suppose:

```bash id="y3m8q2"
dig example.com
```

works but:

```bash id="p7x2m5"
getent hosts example.com
```

fails.

This suggests the problem may be in:

```text id="5m8q3x"
NSS
/etc/hosts
Resolver integration
Local configuration
```

rather than the DNS server itself.

### Reverse DNS

To query a PTR record:

```bash id="q4m7x2"
dig -x 10.10.10.20
```

### Interview Tip

> "`dig` is my preferred detailed DNS troubleshooting tool, while `getent hosts` is especially useful because it tests the system's configured name-service resolution path."

# Q300. How do you troubleshoot DNS when IP connectivity works but hostname connectivity fails?

## Answer

This is a classic DNS troubleshooting scenario.

```text
IP works
   |
   v
10.10.10.20
   |
   X
app.example.com
```

### Step 1: Test IP Directly

```bash id="m3x7q2"
ping -c 4 10.10.10.20
```

Or test the application port:

```bash id="q8m2x5"
nc -vz 10.10.10.20 443
```

### Step 2: Test Hostname

```bash id="p5m8x2"
getent hosts app.example.com
```

### Step 3: Use `dig`

```bash id="x7m3q1"
dig app.example.com
```

### Step 4: Check Resolver Configuration

```bash id="m2q8x4"
cat /etc/resolv.conf
```

### Step 5: Check NSS

```bash id="p4x7m2"
grep '^hosts:' /etc/nsswitch.conf
```

### Step 6: Check `/etc/hosts`

```bash id="x8m3q5"
grep -w "app.example.com" /etc/hosts
```

### Step 7: Query DNS Server Directly

```bash id="q5m7x2"
dig @<dns-server-ip> app.example.com
```

### Possible Causes

```text id="7m3x8q"
Wrong DNS server
Missing DNS record
Wrong /etc/hosts
NSS configuration
Search domain
DNS timeout
Split DNS
DNS firewall issue
```

### Important

If:

```text id="x2m8q5"
IP connectivity works
```

but:

```text id="p7m3x1"
hostname resolution fails
```

do not immediately troubleshoot routes or NICs.

Start with name resolution.

### Interview Tip

> "If the IP works but the hostname doesn't, I focus first on DNS and NSS: `getent`, `dig`, `/etc/resolv.conf`, `/etc/nsswitch.conf`, `/etc/hosts`, and the configured DNS server."

# Q301. How do you troubleshoot DNS when hostname resolution is slow?

## Answer

Slow DNS resolution can cause applications to appear slow even when the network itself is healthy.

### Step 1: Measure DNS Query Time

```bash id="x5m8q2"
dig example.com
```

Look for:

```text id="p8m3x7"
Query time
```

### Step 2: Test Each DNS Server

Suppose `/etc/resolv.conf` contains:

```text id="q2m7x4"
nameserver 10.10.10.10
nameserver 10.10.10.11
```

Test separately:

```bash id="m8x3q5"
dig @10.10.10.10 example.com
```

```bash id="x7m2q4"
dig @10.10.10.11 example.com
```

Compare response time.

### Step 3: Check DNS Server Reachability

```bash id="p4m8x2"
ip route get 10.10.10.10
```

### Step 4: Check Packet Loss

```bash id="q5m3x8"
ping -c 20 10.10.10.10
```

Again, ping is only one signal because ICMP may be filtered.

### Step 5: Check Resolver Configuration

```bash id="x8m2q5"
cat /etc/resolv.conf
```

### Step 6: Check Search Domains

A poorly designed search list can result in multiple DNS queries.

Example:

```text id="7m3x9q"
search example.com internal.example.com another.example.com
```

A short hostname can cause multiple lookup attempts.

### Step 7: Check Application Behavior

Some applications perform:

```text id="m5x8q2"
A lookup
AAAA lookup
Reverse lookup
Multiple retries
```

### Step 8: Check DNS Server Health

If possible, check:

```text id="q7m2x5"
DNS server load
Response latency
DNS logs
Network connectivity
Upstream DNS
```

### Possible Causes

```text id="4x8m2q"
Slow DNS server
Unreachable primary DNS
Slow secondary DNS
Network latency
Packet loss
Search-domain expansion
DNS timeout/retry
Application behavior
```

### Interview Tip

> "I measure DNS query latency with `dig`, test each configured nameserver independently, check routing and packet loss, review search domains and resolver behavior, and compare DNS latency with application latency."

# Q302. How do you troubleshoot `/etc/hosts` and `/etc/resolv.conf` problems?

## Answer

These two files are commonly involved in Linux name resolution.

## `/etc/hosts`

It provides local static hostname-to-IP mappings.

Example:

```text id="7m3x8q"
10.10.10.20  app.example.com
```

Check:

```bash id="m5x8q2"
cat /etc/hosts
```

Test:

```bash id="p4m7x1"
getent hosts app.example.com
```

### Common `/etc/hosts` Problems

```text id="q8m2x5"
Wrong IP
Duplicate entry
Incorrect hostname
Unexpected override of DNS
```

---

## `/etc/resolv.conf`

It contains resolver configuration.

Check:

```bash id="x7m3q2"
cat /etc/resolv.conf
```

Example:

```text id="2m8x5q"
search example.com
nameserver 10.10.10.10
```

### Check Whether It Is a Symlink

```bash id="p5m7x2"
ls -l /etc/resolv.conf
```

On some systems it may be managed by:

```text id="8m3q7x"
systemd-resolved
NetworkManager
DHCP client
Other network-management software
```

### Important

Do not manually edit `/etc/resolv.conf` without understanding what manages it.

Your manual change may be overwritten after:

```text id="m2x8q5"
Network restart
DHCP renewal
Reboot
NetworkManager reload
```

### Check NetworkManager DNS

```bash id="q7m3x1"
nmcli device show | grep -i dns
```

### Check Resolver Service

If applicable:

```bash id="x4m8q2"
systemctl status systemd-resolved
```

### Troubleshooting Model

```text id="8q2m5x"
Application
    |
    v
NSS
    |
    +--> /etc/hosts
    |
    +--> Resolver
            |
            v
       /etc/resolv.conf
            |
            v
        DNS Server
```

### Interview Tip

> "`/etc/hosts` provides local static resolution, while `/etc/resolv.conf` defines resolver settings such as nameservers. Before editing either file, I determine whether it is managed by NetworkManager, systemd-resolved, DHCP, or another service."

# Q303. How do you troubleshoot systemd-resolved or local DNS caching problems?

## Answer

Some Linux systems use **systemd-resolved** as a local DNS resolver.

First check whether it is actually running.

### Step 1: Check Service

```bash id="x5m8q2"
systemctl status systemd-resolved
```

### Step 2: Check Resolver State

```bash id="p7m3x8"
resolvectl status
```

Check availability:

```bash id="q4m8x2"
command -v resolvectl
```

### Step 3: Check DNS Configuration

```bash id="m2x7q5"
resolvectl dns
```

### Step 4: Test Resolution

```bash id="x8m3q1"
resolvectl query example.com
```

### Step 5: Check `/etc/resolv.conf`

```bash id="p5m7x2"
ls -l /etc/resolv.conf
```

It may point to a local resolver address such as:

```text id="7m2x4q"
127.0.0.53
```

when systemd-resolved is configured that way.

### Step 6: Check Logs

```bash id="q3m8x5"
journalctl -u systemd-resolved
```

### Step 7: Check Upstream DNS

```bash id="x7m2q4"
resolvectl status
```

Verify the configured upstream DNS servers.

### Possible Causes

```text id="m5x8q2"
Resolver service stopped
Incorrect DNS server
Broken /etc/resolv.conf link
Network problem
DNS server unavailable
Resolver configuration
Caching/stale data
```

### Important

Not every Linux system uses `systemd-resolved`.

Before troubleshooting it:

```bash id="p8m3x7"
systemctl is-active systemd-resolved
```

### Interview Tip

> "I first confirm whether `systemd-resolved` is actually being used. If it is, I check `resolvectl status`, `resolvectl query`, `/etc/resolv.conf`, and the service logs before making changes."

# Q304. How do you troubleshoot DNS problems involving multiple DNS servers, search domains, or split DNS?

## Answer

Complex environments may use:

```text id="q8m3x2"
Multiple DNS servers
Search domains
Internal DNS
External DNS
Split DNS
VPN DNS
Cloud DNS
```

### Step 1: Check Resolver Configuration

```bash id="m5x7q2"
cat /etc/resolv.conf
```

Look for:

```text id="7x3m8q"
nameserver
search
options
```

### Step 2: Test Each DNS Server

```bash id="p4m8x2"
dig @10.10.10.10 app.internal.example.com
```

```bash id="x7m3q5"
dig @10.10.10.11 app.internal.example.com
```

Compare:

```text id="8m2x4q"
Response
Response time
Server
Record
```

### Step 3: Check Search Domains

Example:

```text id="q5m8x2"
search internal.example.com example.com
```

Then:

```bash id="m7x3q1"
getent hosts app
```

may try search-domain combinations.

### Step 4: Check Split DNS

Example:

```text id="3x8m2q"
internal.example.com
        |
        v
Internal DNS

google.com
    |
    v
External DNS
```

A system may intentionally send different domains to different DNS servers.

### Step 5: Check Resolver Configuration

On systems using systemd-resolved:

```bash id="x4m7q2"
resolvectl status
```

### Step 6: Check NetworkManager

```bash id="p8m3x5"
nmcli device show
```

### Step 7: Check VPN

VPN software may change:

```text id="6m2q8x"
DNS servers
Search domains
Routing
Resolver behavior
```

### Possible Causes

```text id="q7m3x1"
Wrong DNS server order
Internal DNS unavailable
Search-domain problem
Split DNS misconfiguration
VPN DNS override
Cloud DNS configuration
NetworkManager configuration
```

### Important

The first nameserver listed is not simply "the only DNS server used."

Resolver behavior can include:

```text id="4x8m2q"
Timeouts
Retries
Server selection
Search-domain processing
Local resolver logic
```

### Interview Tip

> "For multiple DNS servers or split DNS, I test each nameserver directly with `dig`, inspect search domains and resolver configuration, and verify which DNS server should answer internal versus external names."

# Q305. How do you troubleshoot a production server with a DNS/name-resolution issue?

## Answer

I separate **DNS resolution** from **network connectivity** and troubleshoot from the client outward.

### Step 1: Define the Failure

Ask:

```text id="m7x3q2"
Which hostname?
Which application?
Which server?
All hostnames or one?
Internal or external name?
Intermittent or permanent?
When did it start?
```

### Step 2: Test System Resolution

```bash id="p5m8x2"
getent hosts <hostname>
```

### Step 3: Test DNS Directly

```bash id="x7m3q1"
dig <hostname>
```

### Step 4: Check Resolver Configuration

```bash id="m8x2q5"
cat /etc/resolv.conf
```

### Step 5: Check NSS

```bash id="q4m7x2"
grep '^hosts:' /etc/nsswitch.conf
```

### Step 6: Check `/etc/hosts`

```bash id="p8m3x5"
cat /etc/hosts
```

### Step 7: Test Specific DNS Server

If the DNS server is known:

```bash id="x5m7q2"
dig @<dns-server-ip> <hostname>
```

This helps determine whether the issue is:

```text id="7m3x8q"
Local resolver
        or
DNS server
```

### Step 8: Check DNS Server Reachability

```bash id="m2x8q4"
ip route get <dns-server-ip>
```

Then:

```bash id="p4m7x2"
ping -c 4 <dns-server-ip>
```

and preferably test DNS itself:

```bash id="x8m3q5"
dig @<dns-server-ip> <hostname>
```

### Step 9: Check Firewall

Verify DNS traffic is permitted.

```text id="q5m8x2"
UDP 53
TCP 53
```

### Step 10: Check Resolver Service

If applicable:

```bash id="m7x3q1"
systemctl status systemd-resolved
```

or:

```bash id="x4m8q2"
systemctl status NetworkManager
```

### Step 11: Check DNS Logs/Server Side

If you manage the DNS server, check:

```text id="8m2x5q"
DNS server logs
Zone configuration
Authoritative server health
Forwarders
Recursion
Upstream DNS
```

### Step 12: Check Application Behavior

An application may use:

```text id="q7m3x1"
Its own DNS resolver
DNS cache
Connection pool
Proxy
Container-specific DNS
```

For containers/Kubernetes, also inspect the platform's DNS configuration.

### Step 13: Use Packet Capture if Necessary

```bash id="p5x8m2"
sudo tcpdump -ni any port 53
```

This can help determine:

```text id="4m7x2q"
DNS query sent?
DNS response received?
Which server responded?
Timeout?
Repeated queries?
```

Use a targeted capture in production.

### Step 14: Apply the Smallest Safe Fix

Possible fixes:

```text id="x8m3q5"
Correct nameserver
Fix DNS record
Correct /etc/hosts
Fix resolver service
Fix DNS routing/firewall
Correct search domain
Fix internal DNS
Correct VPN/cloud DNS configuration
```

### Step 15: Verify

Verify:

```text id="m2q7x4"
Hostname resolves
       ↓
Correct IP returned
       ↓
IP reachable
       ↓
Required port reachable
       ↓
Application works
```

### Production Scenario

**Interviewer:**

> "A production application suddenly reports `Could not resolve host`. What will you do?"

**Strong Answer:**

> "First I would identify the hostname and determine whether the problem affects one hostname or all DNS lookups. I would test the system resolver with `getent hosts` and DNS directly with `dig`. Then I would inspect `/etc/resolv.conf`, `/etc/nsswitch.conf`, `/etc/hosts`, and the configured DNS servers. I would test the DNS server directly with `dig @server hostname` and verify routing and DNS traffic. If systemd-resolved or NetworkManager is involved, I would check its status and logs. I would also check whether the application is running in a container or using its own DNS configuration. If needed, I would use targeted `tcpdump` to determine whether DNS queries and responses are actually reaching the server. I would identify the failing layer, make the smallest safe correction, and verify DNS resolution, IP connectivity, the required application port, and application health."

# 🎤 DNS Interview Golden Rules

```text id="m5x8q2"
DNS failure ≠ Network failure
IP works ≠ Hostname works
Ping failure ≠ DNS failure
DNS server reachable ≠ DNS query working
dig works ≠ getent necessarily works
DNS record exists ≠ Application reachable
/etc/resolv.conf ≠ Always manually managed
/etc/hosts can override DNS
systemd-resolved ≠ Used on every Linux system
Multiple DNS servers ≠ Automatically load balanced
Traceroute ≠ DNS troubleshooting tool
DNS response ≠ Application health
```

### ⚠️ Production Safety Rules

Before changing DNS configuration:

```text id="q8m3x2"
1. Identify the exact hostname
2. Determine whether one or many names are affected
3. Test with getent
4. Test with dig
5. Check /etc/resolv.conf
6. Check /etc/nsswitch.conf
7. Check /etc/hosts
8. Identify DNS server(s)
9. Test each DNS server where appropriate
10. Check routing to DNS servers
11. Check firewall/DNS traffic
12. Determine whether systemd-resolved or NetworkManager manages DNS
13. Check application/container DNS configuration
14. Avoid blindly editing /etc/resolv.conf
15. Avoid blindly restarting network services
16. Make the smallest safe change
17. Verify hostname resolution
18. Verify IP connectivity
19. Verify application port
20. Verify application health
21. Monitor after the change
22. Document the root cause
```

> **Interview mindset:** Do not say, "The hostname is not working, so I will change `/etc/resolv.conf`." Say, **"I will verify system-level resolution with `getent`, test DNS directly with `dig`, inspect NSS, `/etc/hosts`, and resolver configuration, test the configured DNS servers, verify network reachability and DNS traffic, identify whether the issue is client-side or DNS-server-side, and then apply the smallest safe fix."**
