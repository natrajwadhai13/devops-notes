# 32. HTTP/HTTPS & Web Server Troubleshooting

> HTTP/HTTPS troubleshooting focuses on the complete web request path: **DNS → TCP → TLS → Web Server → Reverse Proxy → Application → Backend Dependencies**. Common problems include connection refused, timeout, HTTP 4xx/5xx errors, TLS failures, incorrect virtual hosts, configuration errors, permissions, and resource exhaustion.

# Q326. What is HTTP/HTTPS and how does a web request work?

## Answer

**HTTP (Hypertext Transfer Protocol)** is an application-layer protocol used for communication between clients and web servers.

**HTTPS** is HTTP protected using **TLS encryption**.

### Basic HTTP Request Flow

```text id="5g0f7v"
Client
   |
   | DNS
   v
Hostname → IP
   |
   | TCP
   v
Server:80/443
   |
   | HTTP/HTTPS
   v
Web Server
   |
   v
Reverse Proxy
   |
   v
Application
   |
   v
Database / Backend
```

### HTTP

Commonly uses:

```text id="y9m2e4"
TCP 80
```

### HTTPS

Commonly uses:

```text id="2y8x4q"
TCP 443
```

### HTTPS Flow

Simplified:

```text id="k7p3m2"
Client
   |
   | TCP connection
   v
Server
   |
   | TLS handshake
   v
Certificate validation
   |
   v
Encrypted HTTP
```

### Example

```bash id="g1x8m4"
curl -v https://example.com
```

This can show:

```text id="j5q2x8"
DNS resolution
TCP connection
TLS handshake
Certificate information
HTTP request
HTTP response
```

### Important

A web request has multiple layers.

```text id="7m4x2p"
DNS
 ↓
Network
 ↓
TCP
 ↓
TLS
 ↓
HTTP
 ↓
Web Server
 ↓
Application
```

A failure at one layer can look like a web-server problem even when the web server itself is healthy.

### Interview Tip

> "For HTTP/HTTPS troubleshooting, I separate DNS, TCP, TLS, HTTP, web-server, application, and backend dependency problems instead of treating everything as a web-server issue."

# Q327. How do you check whether a web server is running?

## Answer

Common Linux web servers include:

```text id="8m3q7x"
Nginx
Apache HTTP Server
HAProxy
```

### Step 1: Check Service

For Nginx:

```bash id="x5m8q2"
systemctl status nginx
```

For Apache:

```bash id="p7m3x4"
systemctl status httpd
```

On Debian/Ubuntu, Apache may use:

```bash id="q2x8m5"
systemctl status apache2
```

### Step 2: Check Process

```bash id="m8q3x1"
pgrep -a nginx
```

or:

```bash id="x4m7q2"
ps -ef | grep nginx
```

### Step 3: Check Listening Port

```bash id="p5x8m2"
ss -lntp | grep -E ':80|:443'
```

Example:

```text id="7m3q8x"
LISTEN 0 511 0.0.0.0:80
LISTEN 0 511 0.0.0.0:443
```

### Step 4: Test Locally

```bash id="q8m2x5"
curl -v http://127.0.0.1
```

For HTTPS:

```bash id="x3m7q2"
curl -vk https://127.0.0.1
```

`-k` disables certificate verification and should be used only for troubleshooting.

### Step 5: Check Configuration

Nginx:

```bash id="m5x8q3"
nginx -t
```

Apache:

```bash id="p7m2x4"
apachectl -t
```

Check availability:

```bash id="x8m3q1"
command -v nginx
command -v apachectl
```

### Step 6: Check Logs

Nginx commonly:

```bash id="q4m7x2"
tail -f /var/log/nginx/error.log
```

Apache commonly:

```bash id="m8x2q5"
tail -f /var/log/httpd/error_log
```

Exact paths depend on configuration and distribution.

### Important

A running process does not guarantee a healthy web service.

```text id="7x3m8q"
Process running
      ≠
HTTP request working
```

### Interview Tip

> "I verify the service, process, listening ports, local HTTP response, configuration syntax, and logs. I don't consider the service healthy just because systemd reports it as active."

# Q328. How do you troubleshoot connection refused and connection timeout errors?

## Answer

These two errors provide different clues.

## Connection Refused

Example:

```text id="m4x8q2"
Connection refused
```

Usually means the destination was reachable but no service accepted the connection, or an active device rejected it.

### Check Listener

```bash id="p7m3x5"
ss -lntp | grep :80
```

### Check Service

```bash id="x2m8q4"
systemctl status nginx
```

### Check Firewall

```bash id="q5x7m2"
firewall-cmd --list-all
```

or:

```bash id="m8q3x1"
nft list ruleset
```

### Check Bind Address

An application listening on:

```text id="4m7x2q"
127.0.0.1:80
```

cannot normally accept remote connections.

---

## Connection Timeout

Example:

```text id="8x3m5q"
Connection timed out
```

Possible causes:

```text id="q7m2x4"
Firewall drop
Security Group
NACL
Routing problem
Network failure
Server unavailable
Wrong IP
```

### Test TCP

```bash id="p5m8x2"
nc -vz <server-ip> 80
```

### Check Route

```bash id="x8m3q5"
ip route get <server-ip>
```

### Check Packet Flow

On server:

```bash id="m2q7x4"
sudo tcpdump -ni any port 80
```

### Comparison

| Error              | Common Direction                       |
| ------------------ | -------------------------------------- |
| Connection refused | Service/listener/firewall reject       |
| Connection timeout | Network/firewall/routing/security path |

These are clues, not absolute rules.

### Interview Tip

> "For connection refused I first check whether the application is listening. For timeout I investigate routing, firewall, security controls, and packet flow."

# Q329. How do you troubleshoot HTTP 400, 401, 403, and 404 errors?

## Answer

These are client/request/access-related HTTP responses, but their exact meaning depends on the application.

## HTTP 400 — Bad Request

Usually indicates the server cannot process the request as sent.

Check:

```text id="1s6r8m"
URL
Headers
Request syntax
Parameters
Payload
HTTP method
Proxy behavior
```

Test:

```bash id="f8m3x2"
curl -v https://example.com/path
```

---

## HTTP 401 — Unauthorized

Usually indicates authentication is required or failed.

Check:

```text id="7q2m8x"
Authentication header
Token
Credentials
Session
Identity provider
Application logs
```

Example:

```bash id="p5x8m2"
curl -v -H "Authorization: Bearer <token>" https://example.com/api
```

Do not expose real production tokens in shell history, tickets, screenshots, or logs.

---

## HTTP 403 — Forbidden

Usually means the request was understood but access was denied.

Possible causes:

```text id="m7x3q2"
File permissions
Application authorization
Web-server access rules
SELinux
WAF
IP restrictions
Directory restrictions
```

Check Linux permissions:

```bash id="x4m8q5"
ls -l /path/to/file
```

Check SELinux:

```bash id="q8m3x2"
getenforce
```

---

## HTTP 404 — Not Found

Possible causes:

```text id="p2m7x4"
Wrong URL
Missing file
Wrong document root
Wrong server block
Wrong application route
Reverse-proxy routing
Deployment problem
```

Check web-server configuration.

### Nginx

```bash id="m5x8q2"
nginx -T
```

### Apache

```bash id="x7m3q4"
apachectl -S
```

### Important

Do not automatically assume:

```text id="8m2x5q"
404 = file does not exist
```

A web application can generate its own 404 response.

### Interview Tip

> "For 4xx errors I identify whether the response is generated by the web server, reverse proxy, WAF, or application, then check the request, authentication, authorization, routing, and resource configuration."

# Q330. How do you troubleshoot HTTP 500, 502, 503, and 504 errors?

## Answer

These are commonly associated with server-side or upstream problems.

### 500 — Internal Server Error

Usually indicates an unexpected server/application error.

Check:

```text id="x8m3q2"
Application logs
Web-server logs
Configuration
Permissions
Dependencies
Recent deployment
```

Example:

```bash id="p5m7x4"
journalctl -u <application-service>
```

---

## 502 — Bad Gateway

Usually indicates a gateway/reverse proxy received an invalid or unusable response from an upstream.

Check:

```text id="q7x2m5"
Backend IP
Backend port
Backend listener
Proxy configuration
Backend logs
TLS between proxy and backend
```

Test backend:

```bash id="m4x8q2"
curl -v http://<backend-ip>:8080
```

---

## 503 — Service Unavailable

Often means the service/backend is temporarily unavailable.

Check:

```text id="x3m7q5"
Backend health
Application service
Load-balancer target health
Resource exhaustion
Maintenance
Connection limits
```

---

## 504 — Gateway Timeout

Usually means the proxy/gateway did not receive a timely upstream response.

Check:

```text id="p8m2x4"
Backend response time
Database latency
External API
Network
Proxy timeout
Application timeout
```

### Quick Comparison

| Status | Typical Area                |
| ------ | --------------------------- |
| 500    | Application/server error    |
| 502    | Proxy → upstream problem    |
| 503    | Service/backend unavailable |
| 504    | Upstream response timeout   |

### Important

These meanings are not universal.

The component generating the response matters.

### Interview Tip

> "For 5xx errors I identify which component generated the response, then trace the request from web server to upstream application and its dependencies."

# Q331. How do you troubleshoot HTTPS/TLS certificate errors?

## Answer

HTTPS adds TLS to the normal HTTP flow.

### Step 1: Test With Curl

```bash id="8m3q2x"
curl -v https://example.com
```

### Step 2: Inspect TLS Handshake

```bash id="m5x8q7"
openssl s_client -connect example.com:443 -servername example.com
```

### Step 3: Check Certificate Dates

```bash id="p7m2x4"
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates
```

Look for:

```text id="x4m8q2"
notBefore
notAfter
```

### Step 4: Check Subject and SAN

```bash id="q8m3x5"
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
```

The hostname must be covered by the certificate's SAN.

### Step 5: Check Certificate Chain

Look at the `openssl s_client` output for:

```text id="m7x3q2"
Verify return code
Certificate chain
Issuer
```

### Step 6: Check SNI

SNI allows a server to select the appropriate certificate based on hostname.

Use:

```bash id="p4m8x2"
openssl s_client -connect <IP>:443 -servername example.com
```

Without the correct SNI, a server hosting multiple HTTPS sites may return the wrong certificate.

### Step 7: Check TLS Policy

Possible problems:

```text id="x5m8q3"
Unsupported TLS version
Cipher mismatch
Protocol mismatch
Security policy
Old client
```

### Step 8: Check System Time

```bash id="q2m7x4"
timedatectl
```

Incorrect time can cause certificate validation failures.

### Common Causes

```text id="7m3x8q"
Expired certificate
Wrong certificate
Hostname mismatch
Missing intermediate CA
Incorrect SNI
TLS version mismatch
Cipher mismatch
Incorrect system time
```

### Important

Do not immediately renew or replace a certificate.

First determine the actual TLS failure.

### Interview Tip

> "I use `curl -v` and `openssl s_client` to identify whether the problem is certificate expiry, SAN mismatch, chain validation, SNI, TLS version, cipher compatibility, or system time."

# Q332. How do you troubleshoot an Nginx or Apache configuration problem?

## Answer

Always validate configuration **before restarting**.

## Nginx

Test configuration:

```bash id="m8x3q2"
nginx -t
```

Dump effective configuration:

```bash id="p5m7x4"
nginx -T
```

Check service:

```bash id="x2q8m5"
systemctl status nginx
```

Check logs:

```bash id="q7m3x2"
journalctl -u nginx
```

Common log:

```bash id="m4x8q7"
tail -f /var/log/nginx/error.log
```

---

## Apache

Test configuration:

```bash id="x8m2q4"
apachectl -t
```

Show virtual hosts:

```bash id="p3m7x5"
apachectl -S
```

Check service:

```bash id="q5x8m2"
systemctl status httpd
```

On Debian/Ubuntu:

```bash id="m7x3q4"
systemctl status apache2
```

### Common Configuration Problems

```text id="8m2x5q"
Syntax error
Wrong port
Wrong document root
Wrong upstream
Wrong certificate path
Missing module
Wrong permissions
Incorrect virtual host
Proxy configuration
```

### Safe Troubleshooting Flow

```text id="x7m3q2"
Edit configuration
       |
       v
Test configuration
       |
       +---- FAIL ----> Fix configuration
       |
       +---- PASS
              |
              v
         Reload/restart
              |
              v
            Verify
```

### Reload vs Restart

When supported:

```text id="m5x8q2"
Reload
  ↓
Apply configuration with less disruption
```

A restart may terminate existing processes/connections depending on the service.

### Interview Tip

> "I always run the web server's configuration test before applying a configuration change. For Nginx I use `nginx -t`; for Apache I use `apachectl -t`."

# Q333. How do you troubleshoot virtual host/server block problems?

## Answer

A web server can host multiple websites on the same IP.

Example:

```text id="j3m8x2"
             Nginx
               |
      +--------+--------+
      |                 |
      v                 v
example.com       app.example.com
      |                 |
      v                 v
 /var/www/site1    /var/www/site2
```

### Nginx

Inspect effective configuration:

```bash id="p7m2x4"
nginx -T
```

Look for:

```text id="5x8m3q"
server_name
listen
root
proxy_pass
ssl_certificate
```

### Apache

```bash id="x4m8q2"
apachectl -S
```

This shows virtual-host configuration and helps identify which configuration is handling a request.

### Step 1: Check DNS

```bash id="q8m3x5"
dig example.com
```

### Step 2: Test Host Header

```bash id="m5x7q2"
curl -v -H "Host: example.com" http://<server-ip>
```

For HTTPS, SNI also matters:

```bash id="p2x8m4"
curl -vk --resolve example.com:443:<server-ip> https://example.com/
```

### Step 3: Check `server_name` / Virtual Host

Verify that the requested hostname matches the configured site.

### Step 4: Check Document Root

```bash id="x7m3q2"
ls -ld /var/www/site
```

### Step 5: Check Permissions

```bash id="m8x2q5"
namei -l /var/www/site/index.html
```

### Step 6: Check SELinux

```bash id="q4m7x2"
ls -Z /var/www/site/index.html
```

If relevant:

```bash id="p5x8m3"
ausearch -m AVC -ts recent
```

### Common Causes

```text id="7m3x8q"
Wrong DNS
Wrong server_name
Wrong virtual host
Wrong default server
Wrong document root
Incorrect Host header
Incorrect SNI
Permission problem
SELinux context
```

### Interview Tip

> "For virtual-host problems I verify DNS, hostname matching, `server_name` or Apache virtual-host configuration, Host header, SNI for HTTPS, document root, permissions, and SELinux."

# Q334. How do you troubleshoot a slow web application?

## Answer

A slow website does not necessarily mean the web server is slow.

The bottleneck can be anywhere:

```text id="v7x2m8"
Client
  |
  v
DNS
  |
  v
Network
  |
  v
Load Balancer
  |
  v
Web Server
  |
  v
Application
  |
  +----> Database
  |
  +----> External API
  |
  +----> Cache
```

### Step 1: Measure Request Time

```bash id="m5x8q2"
curl -o /dev/null -s -w 'DNS: %{time_namelookup}\nConnect: %{time_connect}\nTLS: %{time_appconnect}\nTTFB: %{time_starttransfer}\nTotal: %{time_total}\n' https://example.com
```

This helps separate:

```text id="q7m3x4"
DNS time
TCP connection time
TLS time
Time to first byte
Total request time
```

### Step 2: Check Web-Server Logs

Look for:

```text id="x8m2q5"
Request duration
5xx errors
Upstream time
Connection errors
```

### Step 3: Check Application

Investigate:

```text id="m4x7q2"
CPU
Memory
Thread pools
Connection pools
Application latency
Garbage collection
```

### Step 4: Check Database

Possible causes:

```text id="p5m8x2"
Slow queries
Connection exhaustion
Locks
High CPU
Storage latency
```

### Step 5: Check External Dependencies

For example:

```text id="q2x7m4"
External API
DNS
Authentication service
Redis
Message queue
```

### Step 6: Check Linux Resources

```bash id="x7m3q2"
top
```

```bash id="m8x2q5"
free -h
```

```bash id="p4m7x2"
iostat -xz 1
```

### Step 7: Compare Healthy vs Slow Requests

Look for:

```text id="8m3x7q"
Same endpoint?
Same backend?
Same database query?
Same user?
Same region?
Same time?
```

### Step 8: Check Recent Changes

```text id="q5m8x2"
Application deployment
Web-server configuration
Database change
Certificate change
Infrastructure change
Traffic increase
```

### Important

Do not immediately:

```text id="m7x2q4"
restart the server
increase timeouts
increase CPU
restart the database
```

First identify the bottleneck.

### Interview Tip

> "I measure where the latency occurs first—DNS, TCP, TLS, web server, application, or dependency—and then correlate it with logs and system metrics."

# Q335. How do you troubleshoot a complete production HTTP/HTTPS issue?

## Answer

I troubleshoot the complete request path layer by layer.

```text id="8m3q7x"
Client
  |
  v
DNS
  |
  v
TCP
  |
  v
TLS
  |
  v
Load Balancer / Reverse Proxy
  |
  v
Web Server
  |
  v
Application
  |
  v
Database / Dependencies
```

### Step 1: Define the Failure

Ask:

```text id="m5x8q2"
Which URL?
Which hostname?
HTTP or HTTPS?
Which client?
All users or some users?
Which HTTP status?
When did it start?
Permanent or intermittent?
```

### Step 2: Check DNS

```bash id="q7m3x4"
getent hosts app.example.com
```

```bash id="x2m8q5"
dig app.example.com
```

### Step 3: Check TCP

```bash id="p5m7x2"
nc -vz app.example.com 443
```

### Step 4: Check Routing

```bash id="m8x3q4"
ip route get <destination-ip>
```

### Step 5: Check TLS

```bash id="q4m7x2"
openssl s_client -connect app.example.com:443 -servername app.example.com
```

### Step 6: Check HTTP

```bash id="x7m2q5"
curl -v https://app.example.com
```

Record:

```text id="m5x8q3"
HTTP status
Response headers
Response time
Redirects
Server information
```

### Step 7: Check Load Balancer/Reverse Proxy

Verify:

```text id="p8m2x4"
Listener
Backend health
Routing rules
Certificates
Timeouts
Proxy configuration
```

### Step 8: Check Web Server

Nginx:

```bash id="x3m7q2"
systemctl status nginx
nginx -t
```

Apache:

```bash id="q8m2x5"
systemctl status httpd
apachectl -t
```

### Step 9: Check Listening Ports

```bash id="m4x8q2"
ss -lntp
```

### Step 10: Check Logs

```bash id="p7m3x5"
journalctl -u nginx
```

or:

```bash id="x5m8q2"
journalctl -u httpd
```

Also inspect:

```text id="q2m7x4"
Access logs
Error logs
Application logs
Load-balancer logs
```

### Step 11: Test Backend Directly

If the web server proxies to an application:

```bash id="m8x3q2"
curl -v http://<backend-ip>:8080
```

### Step 12: Check Firewall/Security

```bash id="p4m7x2"
firewall-cmd --list-all
```

or:

```bash id="x7m2q5"
nft list ruleset
```

Also verify cloud/network controls where applicable.

### Step 13: Check Application and Dependencies

```text id="m5x8q2"
Application
   |
   +---- Database
   |
   +---- Redis
   |
   +---- External API
   |
   +---- DNS
   |
   +---- Storage
```

### Step 14: Check System Resources

```bash id="q8m3x5"
top
```

```bash id="x3m7q2"
free -h
```

```bash id="p5m8x2"
df -h
```

### Step 15: Use Packet Capture if Necessary

```bash id="m7x2q4"
sudo tcpdump -ni any port 443
```

Use targeted captures rather than collecting unnecessary traffic.

### Step 16: Check Recent Changes

```text id="8m3x7q"
DNS changes
Certificate renewal
Firewall changes
Load-balancer changes
Web-server configuration
Application deployment
OS/package update
Database changes
```

### Step 17: Apply the Smallest Safe Fix

Examples:

```text id="q5m8x2"
Correct DNS
Fix certificate
Correct listener
Fix web-server configuration
Fix backend port
Fix firewall rule
Rollback application deployment
Fix application dependency
```

### Step 18: Verify End-to-End

```text id="m2x7q4"
DNS
 ↓
TCP
 ↓
TLS
 ↓
HTTP
 ↓
Load Balancer
 ↓
Web Server
 ↓
Application
 ↓
Dependencies
```

### Production Scenario

**Interviewer:**

> "Users report that the production website is down. What will you check?"

**Strong Answer:**

> "First I would define the scope and identify the URL, hostname, protocol, affected users, HTTP status, and start time. I would check DNS with `getent` and `dig`, then TCP connectivity and routing. For HTTPS I would validate the TLS handshake and certificate with `openssl s_client`. I would test the application using `curl -v` and identify the HTTP status. Then I would check the load balancer or reverse proxy, web-server status and configuration, listening ports, access/error logs, backend health, application logs, and downstream dependencies. I would also check firewall/security controls and system resources. If necessary, I would use targeted packet capture to determine where traffic stops. Finally, I would identify the failing layer, apply the smallest safe and reversible fix, verify the complete request path, monitor the service, and document the root cause."

# ⚠️ Production Safety Rules

Before making HTTP/HTTPS or web-server changes:

```text id="q5m8x2"
1. Identify the exact URL
2. Identify the hostname
3. Check DNS
4. Check TCP connectivity
5. Check routing
6. Check TLS if HTTPS
7. Record the HTTP status
8. Identify which component generated the response
9. Check Load Balancer/Reverse Proxy
10. Check backend health
11. Check web-server listener
12. Validate configuration before reload/restart
13. Check access/error logs
14. Check application logs
15. Check firewall/security controls
16. Check SELinux where relevant
17. Check system resources
18. Check database and external dependencies
19. Check recent deployments/configuration changes
20. Avoid blindly restarting the server
21. Avoid blindly increasing timeouts
22. Avoid disabling TLS/security controls
23. Make the smallest reversible change
24. Verify end-to-end
25. Monitor after the change
26. Document the root cause
```

> **Interview mindset:** Don't say **"Website is down, so I will restart Nginx."** Say: **"I will trace the request from DNS through TCP, TLS, HTTP, load balancer/reverse proxy, web server, application, and dependencies. I will identify the failing layer using `dig`, `curl`, `openssl`, `ss`, logs, and packet capture where necessary, then apply the smallest safe fix and verify the complete request path."**
