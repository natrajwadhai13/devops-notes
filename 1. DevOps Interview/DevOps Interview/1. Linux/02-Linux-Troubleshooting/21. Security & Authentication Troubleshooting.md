# 21. Security & Authentication Troubleshooting

> Linux security and authentication issues can affect **SSH access, sudo, user login, service authentication, file access, SELinux, PAM, passwords, SSH keys, and centralized authentication systems**. The safest approach is to identify the exact authentication layer before changing permissions or security settings.

# Q216. What is the difference between authentication and authorization in Linux?

## Answer

These are two different security concepts.

### Authentication

Authentication answers:

> **"Who are you?"**

Examples:

```text
Username + Password
SSH Key
MFA
Certificate
Kerberos
LDAP
```

### Authorization

Authorization answers:

> **"What are you allowed to do?"**

Examples:

```text
File permissions
sudo privileges
ACLs
SELinux policy
Group membership
Application permissions
```

### Example

A user successfully logs in:

```text id="8u2y0s"
Authentication
      |
      v
User identity verified
```

But then:

```bash id="3j3yq1"
cat /etc/shadow
```

may fail because the user does not have authorization.

### Simple Model

```text id="x5f7nq"
User
 |
 v
Authentication
"Who are you?"
 |
 v
Identity
 |
 v
Authorization
"What can you access?"
 |
 v
Resource
```

### Interview Tip

> "Authentication verifies the user's identity, while authorization determines what that authenticated user is allowed to access or perform."

# Q217. How do you troubleshoot a user who cannot log in to Linux?

## Answer

First identify **how the user is trying to log in**:

```text id="y8z0e3"
Console
SSH
Application
LDAP/AD
```

### Step 1: Check the User

```bash id="c5h5am"
id username
```

Check account information:

```bash id="4w4p6n"
getent passwd username
```

### Step 2: Check Account Status

```bash id="sqc1fm"
sudo passwd -S username
```

On systems using shadow utilities:

```bash id="6s7a2g"
sudo chage -l username
```

Check:

```text id="y0m8a7"
Password status
Password expiry
Account expiry
```

### Step 3: Check Login Shell

```bash id="a4c0ny"
getent passwd username
```

Example:

```text id="8w9h6f"
username:x:1001:1001::/home/username:/bin/bash
```

If the shell is:

```text id="1q0v7w"
/sbin/nologin
```

interactive login may be intentionally disabled.

### Step 4: Check Home Directory

```bash id="z1i8j5"
ls -ld /home/username
```

Check ownership:

```bash id="p9j7x8"
ls -ld /home/username
```

### Step 5: Check Authentication Logs

Systemd:

```bash id="8b4k1x"
journalctl
```

SSH-specific:

```bash id="3e2w7p"
journalctl -u sshd
```

Depending on distribution, authentication logs may also be under:

```text id="e2c4q7"
/var/log/secure
/var/log/auth.log
```

### Step 6: Check SSH Configuration

If the issue is SSH:

```bash id="5v3f8t"
sshd -t
```

Then inspect:

```bash id="k4x9m1"
grep -Ei "PasswordAuthentication|PubkeyAuthentication|AllowUsers|AllowGroups|DenyUsers|DenyGroups" /etc/ssh/sshd_config
```

### Step 7: Check Security Controls

```bash id="9t4y6n"
getenforce
```

Check firewall/network if SSH itself is unreachable.

### Possible Causes

```text id="l0b7c8"
Wrong password
Account locked
Account expired
Password expired
Wrong shell
Home directory problem
SSH configuration
SSH key permissions
PAM problem
SELinux
Firewall/network
LDAP/AD problem
```

### Interview Tip

> "For a login failure, I first identify the access method, then check the account, password/expiry status, login shell, home directory, authentication logs, SSH configuration if applicable, and security controls such as PAM and SELinux."

# Q218. How do you troubleshoot password authentication failures?

## Answer

### Step 1: Verify the Username

```bash id="v8e1f3"
id username
```

### Step 2: Check Password Status

```bash id="m4c1w2"
sudo passwd -S username
```

### Step 3: Check Password Expiry

```bash id="c9d3q5"
sudo chage -l username
```

Look for:

```text
Password expires
Account expires
```

### Step 4: Check Account Lock

On systems supporting it:

```bash id="9p0u2e"
sudo faillock --user username
```

The exact account-locking mechanism depends on the distribution and PAM configuration.

### Step 5: Check Authentication Logs

```bash id="9i0f2g"
journalctl
```

For SSH:

```bash id="0j8k3m"
journalctl -u sshd
```

On some systems:

```bash id="d8x0v1"
grep -i "failed" /var/log/secure
```

or:

```bash id="0w8m6k"
grep -i "failed" /var/log/auth.log
```

### Step 6: Check PAM Configuration

Review:

```text id="b2p8s4"
/etc/pam.d/
```

Do not modify PAM configuration without understanding the authentication flow.

### Step 7: Check Account Restrictions

```bash id="7x5z2k"
getent passwd username
```

Look for the configured shell.

### Important

Do not repeatedly attempt passwords on a production account because this may trigger account lockout.

### Common Causes

```text id="2m3g7q"
Wrong password
Password expired
Account locked
Account expired
PAM configuration
LDAP/AD failure
Authentication policy
Keyboard/layout issue
Wrong authentication method
```

### Interview Tip

> "For password authentication failures, I check account status, password and account expiry, lockout state, authentication logs, PAM configuration, and centralized authentication dependencies."

# Q219. How do you troubleshoot SSH key authentication failures?

## Answer

If password authentication works but SSH key authentication fails, focus on:

```text id="z8y2k6"
Client key
Server authorized_keys
Permissions
Ownership
sshd configuration
SELinux
```

### Step 1: Run SSH in Verbose Mode

From the client:

```bash id="b4f5t7"
ssh -vvv user@server
```

This provides detailed authentication information.

### Step 2: Check Client Key

```bash id="q3s7j1"
ls -l ~/.ssh/
```

Check available keys:

```bash id="v9w3e4"
ssh-add -l
```

if using an SSH agent.

### Step 3: Check Server Authorized Keys

```bash id="j7x5c2"
ls -l ~/.ssh/authorized_keys
```

For another user:

```bash id="3v5n9q"
sudo ls -l /home/username/.ssh/authorized_keys
```

### Step 4: Check Ownership

```bash id="6q1z0p"
sudo ls -ld /home/username/.ssh
sudo ls -l /home/username/.ssh/authorized_keys
```

The files should have appropriate ownership and permissions.

### Typical Permissions

A common secure setup is:

```text id="2u6p8f"
~/.ssh              700
authorized_keys     600
```

But always consider the actual account and SSH configuration.

### Step 5: Check sshd Configuration

```bash id="9k0x4r"
sshd -T | grep -Ei "pubkeyauthentication|authorizedkeysfile"
```

Test configuration syntax:

```bash id="3f6c8n"
sshd -t
```

### Step 6: Check SSH Logs

```bash id="2s7g5v"
journalctl -u sshd
```

### Step 7: Check SELinux

```bash id="8z1p5k"
getenforce
```

Check SSH file contexts:

```bash id="r4v8c2"
ls -Z ~/.ssh/
```

### Common Causes

```text id="q5f2n9"
Wrong private key
Public key missing
Wrong authorized_keys
Wrong ownership
Wrong permissions
sshd configuration
SELinux context
SSH agent issue
Wrong username
```

### Important

Do not make `.ssh` or `authorized_keys` world-writable.

Avoid:

```bash id="q8f5z1"
chmod 777 ~/.ssh
```

### Interview Tip

> "For SSH key failures, I use `ssh -vvv` on the client, verify the server's `authorized_keys`, ownership and permissions, inspect effective sshd configuration with `sshd -T`, check logs, and verify SELinux context if applicable."

# Q220. How do you troubleshoot sudo access problems?

## Answer

If a user can log in but cannot run a command with sudo, check:

```text id="2y7k0x"
User
Group
sudoers
Policy
Command
```

### Step 1: Check Identity

```bash id="c5y7p4"
id username
```

### Step 2: Check Current Sudo Privileges

For the current user:

```bash id="4d8s2j"
sudo -l
```

For another user, with appropriate administrative privileges:

```bash id="3r8x1v"
sudo -l -U username
```

### Step 3: Check Group Membership

```bash id="f7p2k5"
id username
```

Common administrative groups include:

```text
sudo
wheel
```

depending on the distribution.

### Step 4: Check Sudo Configuration

Use:

```bash id="x1v9r3"
visudo
```

`visudo` safely validates sudoers syntax before saving.

Also inspect included configuration:

```bash id="j4m8q6"
ls -lah /etc/sudoers.d/
```

### Step 5: Check Logs

```bash id="r5z7u2"
journalctl | grep -i sudo
```

Some systems may also log authentication/security events in:

```text id="f8c2w0"
/var/log/secure
/var/log/auth.log
```

### Common Errors

```text id="v5x2m8"
user is not in the sudoers file
Sorry, try again
permission denied
command not allowed
```

### Important

Do not directly edit:

```text id="x0p8k4"
/etc/sudoers
```

with a normal text editor.

Prefer:

```bash id="q2y5r6"
visudo
```

### Interview Tip

> "For sudo issues, I verify the user's identity and groups, run `sudo -l`, inspect `/etc/sudoers` and `/etc/sudoers.d` using `visudo`, and check the authentication/security logs."

# Q221. How do you troubleshoot account locked, expired, or disabled issues?

## Answer

Linux accounts can be affected by:

```text id="7c9v2s"
Password expiration
Account expiration
Lockout
Administrative lock
Disabled login shell
```

### Step 1: Check Password Status

```bash id="3h6q0w"
sudo passwd -S username
```

### Step 2: Check Expiration

```bash id="6n8y1k"
sudo chage -l username
```

### Step 3: Check Account Information

```bash id="0z7r2x"
getent passwd username
```

### Step 4: Check Lockout

On systems using `faillock`:

```bash id="9c2x6v"
sudo faillock --user username
```

### Step 5: Check Login Shell

```bash id="5x4m1q"
getent passwd username
```

Example:

```text id="q8w3e2"
/sbin/nologin
```

may indicate that interactive login is intentionally disabled.

### Unlock Account

The exact command depends on the locking mechanism.

For example, on systems using `faillock`:

```bash id="3p6k8j"
sudo faillock --user username --reset
```

Use this only after confirming the lockout is legitimate to clear.

### Administrative Password Lock

```bash id="6h2z9w"
sudo passwd -S username
```

Some systems may use:

```bash id="2k8y5f"
sudo passwd -u username
```

to unlock a password lock.

### Important

Do not unlock accounts blindly.

First determine:

```text id="v3w7c1"
Why was it locked?
Was the activity legitimate?
Is there suspicious authentication activity?
Is centralized identity management involved?
```

### Interview Tip

> "I distinguish password expiry, account expiry, PAM lockout, administrative password locking, and a disabled login shell. I check `passwd -S`, `chage -l`, `faillock`, account information, and authentication logs before changing the account."

# Q222. How do you troubleshoot PAM authentication problems?

## Answer

**PAM (Pluggable Authentication Modules)** provides a framework used by Linux applications for authentication and related account/session controls.

Common PAM configuration is under:

```text id="2h8s6k"
/etc/pam.d/
```

### Common PAM Functions

```text id="1w5f7z"
Authentication
Account checks
Password management
Session management
```

### Step 1: Identify the Application

For example:

```text id="z5r2y8"
SSH
sudo
login
su
```

Each may have relevant PAM configuration.

### Step 2: Check Configuration

```bash id="a3j9s6"
ls -lah /etc/pam.d/
```

For SSH:

```bash id="4h7c2m"
cat /etc/pam.d/sshd
```

### Step 3: Check Logs

```bash id="7p1k4f"
journalctl
```

For SSH:

```bash id="c8y2m6"
journalctl -u sshd
```

### Step 4: Check Account State

```bash id="d6n3q8"
passwd -S username
```

```bash id="h9k4v1"
chage -l username
```

### Step 5: Check Centralized Authentication

If using:

```text id="8z2q5x"
LDAP
Active Directory
SSSD
Kerberos
```

check the relevant service and configuration.

For example:

```bash id="w4m7p9"
systemctl status sssd
```

### Important Production Warning

A broken PAM configuration can prevent **all users**, including administrators, from logging in.

Do not make untested PAM changes on a production server.

Always maintain a recovery/console path before modifying authentication configuration.

### Interview Tip

> "For PAM problems, I identify the affected application, inspect the relevant `/etc/pam.d` configuration, check authentication logs and account state, and investigate centralized authentication dependencies. I treat PAM changes as high-risk because a configuration mistake can lock out administrators."

# Q223. How do you troubleshoot permission/security issues involving SELinux?

## Answer

SELinux can deny an operation even when normal Linux permissions appear correct.

### Step 1: Check SELinux Status

```bash id="t1n5c8"
getenforce
```

### Step 2: Check File Context

```bash id="x3q7v2"
ls -Z /path/to/file
```

### Step 3: Check Process Context

```bash id="q5m8z4"
ps -eZ
```

### Step 4: Search for AVC Denials

```bash id="k9f2w6"
ausearch -m AVC -ts recent
```

### Step 5: Check Audit Log

```bash id="0x4v7c"
grep -i denied /var/log/audit/audit.log
```

### Step 6: Check File Context Mapping

```bash id="y6s1n9"
matchpathcon /path/to/file
```

### Step 7: Restore Correct Context

If the file should have the default SELinux context:

```bash id="r8p3j5"
restorecon -v /path/to/file
```

For custom persistent file labeling:

```bash id="m2z5c7"
semanage fcontext -a -t <type> "/path(/.*)?"
restorecon -Rv /path
```

### Important

Do not immediately disable SELinux:

```bash id="6x9p2q"
setenforce 0
```

Permissive mode can be useful as a controlled diagnostic in some situations, but it should not be used as a permanent production fix.

### Interview Tip

> "If normal permissions look correct but access is still denied, I check SELinux mode, file/process contexts, and AVC denials. I fix the specific SELinux policy/context issue rather than disabling SELinux."

# Q224. How do you investigate suspicious authentication attempts and security logs?

## Answer

Authentication logs can provide evidence of:

```text id="9f4j3k"
Failed logins
Successful logins
Invalid users
sudo activity
SSH activity
Account lockouts
Authentication source IPs
```

### Step 1: Check SSH Logs

```bash id="0m3n7v"
journalctl -u sshd
```

### Step 2: Search for Failed Authentication

```bash id="4r8y1k"
journalctl | grep -Ei "failed|authentication failure|invalid user"
```

On some systems:

```bash id="2s5q8j"
grep -Ei "failed|invalid user" /var/log/secure
```

### Step 3: Check Successful Logins

```bash id="5h7m9p"
last
```

### Step 4: Check Failed Login History

```bash id="1c8v6z"
lastb
```

Availability of `lastb` depends on the system and permissions.

### Step 5: Check Current Sessions

```bash id="w4x2j9"
who
```

or:

```bash id="5d7q3m"
w
```

### Step 6: Check Sudo Activity

```bash id="n6k1p8"
journalctl | grep -i sudo
```

### Step 7: Correlate Source Information

Look for:

```text id="f2q7v9"
Username
Source IP
Timestamp
Authentication method
Success/failure
Command
```

### Example

```text id="b8x5n1"
21:00 → Failed SSH login
21:01 → Failed SSH login
21:02 → Successful login
21:03 → sudo command
```

This timeline deserves investigation.

### Important

Do not assume every failed login is an attack.

Servers exposed to the internet may receive automated scanning and password-guessing attempts.

Investigate:

```text id="y4c9m2"
Frequency
Source
Account targeted
Successful access
Commands executed
Expected vs unexpected activity
```

### Interview Tip

> "I use authentication and audit logs to establish who attempted access, from where, when, whether it succeeded, and what happened afterward. I correlate failed and successful authentication with sessions and privileged activity."

# Q225. How do you troubleshoot a production authentication/security issue?

## Answer

Security incidents require **evidence-first troubleshooting** and careful changes.

### Step 1: Define the Impact

Determine:

```text id="v8q2z5"
One user affected?
Multiple users?
All SSH users?
Sudo only?
Application authentication?
Centralized authentication?
```

### Step 2: Identify the Authentication Layer

```text id="0c7w4n"
Client
  |
  v
Network
  |
  v
SSH / Application
  |
  v
PAM
  |
  v
Local Account / LDAP / AD
  |
  v
Authorization
  |
  v
SELinux / sudo / permissions
```

### Step 3: Check Account State

```bash id="j7v4k8"
id username
```

```bash id="0x8q2s"
passwd -S username
```

```bash id="w5c1m9"
chage -l username
```

### Step 4: Check Authentication Logs

```bash id="8r4k2p"
journalctl
```

For SSH:

```bash id="z6q1w8"
journalctl -u sshd
```

### Step 5: Check PAM

```bash id="3v9n5k"
ls -lah /etc/pam.d/
```

Review only the relevant configuration.

### Step 6: Check Authorization

For sudo:

```bash id="2f7m4q"
sudo -l
```

Check groups:

```bash id="9k1x5c"
id username
```

### Step 7: Check SELinux

```bash id="w8d3j6"
getenforce
```

If required:

```bash id="r2m7v4"
ausearch -m AVC -ts recent
```

### Step 8: Check Security Activity

```bash id="4n6q9x"
last
```

```bash id="1z5c8v"
lastb
```

Check current sessions:

```bash id="6y2p4k"
w
```

### Step 9: Check Centralized Authentication

If applicable:

```text id="7v8m1x"
SSSD
LDAP
Active Directory
Kerberos
```

Check the relevant service, for example:

```bash id="9q4w6c"
systemctl status sssd
```

### Step 10: Apply the Smallest Safe Fix

Examples:

```text id="0t5r8j"
Correct account expiry
Correct SSH key
Correct file ownership
Correct sudo policy
Correct SELinux context
Restore authentication dependency
```

Avoid broad security changes such as:

```text id="x2k7p1"
Disable SELinux
Disable firewall
Allow password login everywhere
chmod 777
Give unrestricted sudo
```

### Step 11: Verify

Verify:

```text id="h4j9q2"
Authentication
     |
     v
Authorization
     |
     v
Required resource access
     |
     v
Security controls still enabled
```

### Production Scenario

**Interviewer:**

> "Suddenly all users are unable to SSH into a production server. What will you do?"

**Strong Answer:**

> "First I would confirm whether the issue affects all users or a subset and whether the server is reachable on SSH. I would use console or out-of-band access if available. Then I would check `sshd` status and logs, validate the SSH configuration with `sshd -t`, check PAM and centralized authentication such as SSSD if used, and verify that accounts are not expired or locked. I would also check recent configuration changes, SELinux, firewall/network controls, and system resources. Because authentication configuration is high-risk, I would avoid broad changes and apply the smallest reversible fix, then verify access with multiple test accounts."

# 🎤 Security Interview Golden Rules

```text id="6q2k7w"
Authentication ≠ Authorization
Login failure ≠ automatically wrong password
SSH failure ≠ automatically network problem
SSH key failure ≠ automatically wrong key
Sudo failure ≠ automatically missing group
Permission denied ≠ chmod 777
Account locked ≠ automatically unlock it
PAM issue ≠ safely edit PAM immediately
SELinux denial ≠ disable SELinux
Failed login ≠ automatically successful attack
Firewall issue ≠ automatically disable firewall
```

Always investigate:

```text id="1z7p3k"
User
 +
Authentication Method
 +
Account State
 +
Password / Key
 +
SSH / Application
 +
PAM
 +
LDAP / AD / SSSD
 +
sudo
 +
File Permissions
 +
SELinux
 +
Firewall / Network
 +
Authentication Logs
 +
Recent Changes
```

### ⚠️ Production Security Rules

```text id="y8m4q2"
1. Preserve access to a console/recovery path
2. Confirm the scope of the problem
3. Check logs before changing configuration
4. Never blindly modify PAM
5. Never blindly modify sudoers
6. Use visudo for sudoers changes
7. Validate sshd configuration before reload/restart
8. Do not disable SELinux as a permanent fix
9. Do not disable the firewall as a troubleshooting shortcut
10. Do not use chmod 777 to solve access problems
11. Do not unlock accounts without understanding the cause
12. Apply least privilege
13. Make reversible changes
14. Verify authentication and authorization separately
15. Investigate suspicious access attempts
16. Document the root cause and security impact
```

> **Interview mindset:** Do not say, "The user cannot log in, so I will reset the password." Say, "I will first determine the authentication method and scope, then check account status, logs, SSH/PAM or centralized authentication, authorization, SELinux, and network controls. I will identify the failed layer and apply the smallest safe fix."
