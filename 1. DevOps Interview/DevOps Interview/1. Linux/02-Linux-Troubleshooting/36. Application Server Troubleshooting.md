# 36. Application Server Troubleshooting

> Application server issues can occur between the **client, load balancer, web server, application process, JVM/runtime, database, filesystem, network, and external dependencies**. The key is to identify the failing layer before taking action.

# Q366. What is an application server and how do you troubleshoot it?

## Answer

An **application server** is a server/runtime where an application executes business logic and handles requests.

Examples include:

```text
Java       → Tomcat, JBoss/WildFly
.NET       → ASP.NET / IIS
Node.js    → Node.js runtime
Python     → Gunicorn, uWSGI
PHP        → PHP-FPM
```

A typical production flow is:

```text
User
  |
  v
DNS
  |
  v
Load Balancer
  |
  v
Web Server / Reverse Proxy
  |
  v
Application Server
  |
  +------> Database
  |
  +------> Cache
  |
  +------> External API
  |
  +------> Files / Storage
```

### Application Server Troubleshooting Areas

```text
1. Process
2. Service
3. Port
4. Network
5. CPU
6. Memory
7. Disk
8. Logs
9. Configuration
10. Database
11. External dependencies
12. Deployment changes
13. Application runtime
14. File permissions
15. TLS/certificates
```

### First Commands

```bash
systemctl status <application-service>
```

```bash
ps -ef | grep <application>
```

```bash
ss -lntp
```

```bash
top
```

```bash
free -h
```

```bash
df -h
```

```bash
journalctl -u <application-service>
```

### Interview Tip

> "I troubleshoot an application server layer by layer: service/process, listener, network, resources, logs, configuration, database, dependencies, and recent changes."

# Q367. How do you troubleshoot an application server that is not running?

## Answer

First determine whether the application process or service is actually running.

### Step 1: Check Service

```bash
systemctl status <application-service>
```

Example:

```bash
systemctl status tomcat
```

### Step 2: Check Process

```bash
pgrep -a java
```

or:

```bash
ps -ef | grep java
```

### Step 3: Check Logs

```bash
journalctl -u <application-service> -n 100
```

For the current boot:

```bash
journalctl -u <application-service> -b
```

### Step 4: Check Configuration

For Java/Tomcat, verify:

```text
JAVA_HOME
Application configuration
Environment variables
Application files
JVM options
```

### Step 5: Check Port

```bash
ss -lntp
```

If the application should listen on port `8080`:

```bash
ss -lntp | grep :8080
```

### Step 6: Check Port Conflict

Another process may already be using the required port.

```bash
ss -lntp | grep :8080
```

### Step 7: Check Resources

```bash
free -h
```

```bash
df -h
```

```bash
df -i
```

A full filesystem can prevent an application from starting.

### Step 8: Check Permissions

```bash
namei -l /opt/myapp
```

Check:

```text
Application files
Log directory
Temporary directory
Configuration files
Certificate files
```

### Step 9: Check Security Controls

If SELinux is enabled:

```bash
getenforce
```

Check recent AVC denials:

```bash
ausearch -m AVC -ts recent
```

### Step 10: Check Recent Changes

Investigate:

```text
Application deployment
Configuration change
Package update
JDK/runtime update
Certificate change
Permission change
Database change
OS patch
```

### Important

Do not repeatedly execute:

```bash
systemctl restart <application-service>
```

without checking why it is failing.

### Interview Tip

> "If the application is not running, I check service status, process state, startup logs, configuration, port conflicts, disk/memory, permissions, SELinux, dependencies, and recent changes before restarting it."

# Q368. How do you troubleshoot an application server that is running but not reachable?

## Answer

A running process does not guarantee that users can reach the application.

Example:

```text
Application Process
       |
       v
Listening Port
       |
       v
Network
       |
       v
Firewall / Security Group
       |
       v
Load Balancer
       |
       v
User
```

### Step 1: Check Process

```bash
pgrep -a <application>
```

### Step 2: Check Listening Port

```bash
ss -lntp | grep :8080
```

### Step 3: Check Bind Address

Example:

```text
127.0.0.1:8080
```

means the application may only accept local connections.

Compare with:

```text
0.0.0.0:8080
```

or an appropriate server IP.

### Step 4: Test Locally

```bash
curl -v http://127.0.0.1:8080/
```

If HTTPS:

```bash
curl -vk https://127.0.0.1:8443/
```

### Step 5: Test Using Server IP

```bash
curl -v http://<server-ip>:8080/
```

### Step 6: Check Firewall

```bash
firewall-cmd --list-all
```

Also check:

```bash
nft list ruleset
```

### Step 7: Check Route

```bash
ip route
```

### Step 8: Test From Remote Server

```bash
nc -vz <server-ip> 8080
```

### Step 9: Check Load Balancer

If a load balancer exists:

```text
LB listener
Target health
Health-check path
Health-check port
Security rules
Backend registration
```

### Step 10: Check Logs

```bash
journalctl -u <application-service>
```

Also inspect application-specific logs.

### Important

```text
Application running
      ≠
Port reachable
```

And:

```text
Port reachable
      ≠
Application healthy
```

### Interview Tip

> "I test locally first and then remotely. This helps me separate an application/bind problem from a firewall, routing, load-balancer, or network problem."

# Q369. How do you troubleshoot high CPU usage in an application server?

## Answer

First identify whether the CPU is being consumed by the application or another process.

### Step 1: Check Overall CPU

```bash
top
```

Look at:

```text
us → user CPU
sy → system CPU
wa → I/O wait
id → idle
st → steal time
```

### Step 2: Find High-CPU Processes

```bash
ps aux --sort=-%cpu | head
```

For a specific application:

```bash
pgrep -a java
```

```bash
ps -p <PID> -o pid,ppid,%cpu,%mem,etime,cmd
```

### Step 3: Check Per-CPU Usage

```bash
mpstat -P ALL 1
```

If `mpstat` is unavailable, check whether the `sysstat` package is installed.

### Step 4: Check Application Logs

Look for:

```text
Repeated errors
Request spikes
Infinite loops
Retry storms
Slow dependencies
Thread problems
Unexpected workload
```

### Step 5: Check Traffic

A sudden increase in requests can cause high CPU.

Check:

```text
Load balancer metrics
Web server access logs
Application metrics
Request rate
```

### Step 6: Check Database/External Dependencies

Sometimes the application repeatedly retries a slow dependency.

```text
Application
    |
    +----> Database
    |
    +----> External API
    |
    +----> Cache
```

### Step 7: Check Runtime-Specific Metrics

For Java applications, investigate:

```text
Threads
Garbage collection
Heap
Thread dumps
CPU-consuming threads
```

The exact tools depend on the JVM/application environment.

### Step 8: Check System CPU

If:

```text
sy high
```

investigate:

```text
Network
Disk I/O
System calls
Drivers
Kernel activity
```

### Step 9: Compare With Baseline

Ask:

```text
Was CPU always high?
Did it start after deployment?
Is traffic higher?
Is only one instance affected?
```

### Important

Do not immediately kill the high-CPU process.

It may be the production application itself.

### Interview Tip

> "I identify the process first, then determine whether CPU is application, system, I/O wait, or steal time. I correlate CPU usage with traffic, logs, runtime metrics, dependencies, and recent deployments."

# Q370. How do you troubleshoot high memory usage or an Out-of-Memory issue?

## Answer

Memory problems can cause:

```text
Application slowdown
Swap usage
Process termination
OOM killer
Application restart
Connection failures
```

### Step 1: Check Memory

```bash
free -h
```

Important fields:

```text
used
available
swap
```

Do not judge memory only by the `used` column.

### Step 2: Find Memory-Heavy Processes

```bash
ps aux --sort=-%mem | head
```

### Step 3: Check Application Process

```bash
ps -p <PID> -o pid,%mem,rss,vsz,etime,cmd
```

### Step 4: Check OOM Messages

```bash
dmesg -T | grep -i -E 'out of memory|oom|killed process'
```

Or:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

### Step 5: Check Swap

```bash
swapon --show
```

```bash
free -h
```

Heavy swap activity can increase latency.

### Step 6: Check Application Runtime

For Java:

```text
Heap
Metaspace
Garbage collection
Threads
Native memory
```

Do not assume high RSS automatically means Java heap leak.

### Step 7: Check Container Limits

If the application runs inside a container:

```text
Container memory limit
Container memory usage
OOM events
Kubernetes memory requests/limits
```

The container can be killed even when the host still has free memory.

### Step 8: Check Logs

Search for:

```text
OutOfMemoryError
OOMKilled
heap exhaustion
allocation failure
GC overhead
```

### Common Causes

```text
Memory leak
Large workload
Incorrect JVM/container limits
Too many threads
Large cache
Connection accumulation
Traffic increase
Application bug
```

### Important

Increasing memory is not always the permanent solution.

First determine:

```text
Why is memory increasing?
```

### Interview Tip

> "I check system memory, swap, the application's RSS, kernel OOM logs, runtime-specific memory metrics, and container limits. Then I determine whether the problem is workload, configuration, a leak, or an infrastructure limit."

# Q371. How do you troubleshoot an application server that is responding slowly?

## Answer

Slow response can come from many layers.

```text
Client
  |
  v
DNS
  |
  v
Load Balancer
  |
  v
Web Server
  |
  v
Application
  |
  +----> Database
  |
  +----> Cache
  |
  +----> External API
```

### Step 1: Confirm the Problem

Determine:

```text
Which URL?
Which users?
Which server?
Which application instance?
When did it start?
Always slow or intermittent?
```

### Step 2: Test Locally

```bash
curl -v http://127.0.0.1:8080/
```

For timing:

```bash
curl -s -o /dev/null -w \
'DNS:%{time_namelookup} CONNECT:%{time_connect} START:%{time_starttransfer} TOTAL:%{time_total}\n' \
http://127.0.0.1:8080/
```

### Step 3: Check CPU

```bash
top
```

### Step 4: Check Memory

```bash
free -h
```

### Step 5: Check Disk I/O

```bash
iostat -xz 1
```

### Step 6: Check Application Logs

Look for:

```text
Slow requests
Exceptions
Timeouts
Retries
Thread pool exhaustion
Connection pool exhaustion
```

### Step 7: Check Database

Investigate:

```text
Slow queries
Locks
Connection pool
Database CPU
Database I/O
Connection count
```

### Step 8: Check External Dependencies

An external API may be slow:

```text
Application → External API → Slow
```

The application may appear slow even though its own CPU is normal.

### Step 9: Check Threads/Workers

Application servers may have limits such as:

```text
Thread pool
Worker processes
Request queue
Connection pool
```

### Step 10: Compare Instances

If there are multiple application servers:

```text
Server A → Fast
Server B → Slow
Server C → Fast
```

Focus on Server B.

Possible differences:

```text
Configuration
Resource usage
Deployment
Network
JVM/runtime
Connection pool
```

### Important

Do not immediately increase:

```text
Thread count
Connection pool
Timeout
Memory
```

These may hide the actual problem or increase system pressure.

### Interview Tip

> "I measure where the latency occurs, then correlate application metrics with CPU, memory, I/O, thread pools, database performance, external dependencies, and load-balancer behavior."

# Q372. How do you troubleshoot application connection failures to a database?

## Answer

First determine whether the failure is:

```text
DNS
Network
Port
Authentication
Connection pool
Database
Application configuration
```

### Step 1: Check Application Configuration

Verify:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USER
```

Do not expose passwords.

### Step 2: Test DNS

```bash
getent hosts <db-host>
```

### Step 3: Test Route

```bash
ip route get <db-ip>
```

### Step 4: Test TCP Port

```bash
nc -vz <db-host> <db-port>
```

### Step 5: Test Native Client

PostgreSQL:

```bash
psql -h <db-host> -p 5432 -U <user> -d <database>
```

MySQL:

```bash
mysql -h <db-host> -P 3306 -u <user> -p
```

### Step 6: Check Application Logs

Search for:

```text
Connection refused
Connection timeout
Authentication failure
Too many connections
Pool exhausted
SSL error
Unknown host
```

### Step 7: Check Database Server

```bash
systemctl status <database-service>
```

```bash
ss -lntp | grep :<db-port>
```

### Step 8: Check Firewall/Security

```text
Application server firewall
Database server firewall
Security Group
NACL
Network Firewall
Kubernetes NetworkPolicy
```

### Step 9: Check Connection Pool

Look for:

```text
Maximum pool size
Active connections
Idle connections
Connection wait time
Connection timeout
```

### Step 10: Check Database Health

```bash
top
```

```bash
free -h
```

```bash
iostat -xz 1
```

### Important

If:

```text
nc → SUCCESS
```

but:

```text
psql/mysql → FAILURE
```

the network is probably not the primary problem.

Move to:

```text
Authentication
Database permissions
SSL
Database state
Application configuration
```

### Interview Tip

> "I reproduce the connectivity test from the application server using the same hostname and port, then move from DNS and TCP connectivity to database authentication, connection pooling, database health, and application configuration."

# Q373. How do you troubleshoot application logs and errors?

## Answer

Logs are one of the most important sources of evidence.

### Step 1: Find Application Logs

Possible locations:

```text
/var/log/
/opt/<application>/logs/
/var/log/<application>/
systemd journal
Container logs
Kubernetes logs
```

### Step 2: Check Systemd Logs

```bash
journalctl -u <application-service>
```

Recent logs:

```bash
journalctl -u <application-service> -n 100
```

Follow logs:

```bash
journalctl -u <application-service> -f
```

### Step 3: Filter by Time

```bash
journalctl -u <application-service> --since "1 hour ago"
```

### Step 4: Search for Errors

```bash
grep -i "error" /path/to/application.log
```

Multiple keywords:

```bash
grep -Ei 'error|exception|failed|timeout|refused' /path/to/application.log
```

### Step 5: Check Log Rotation

```bash
ls -lh /var/log/
```

```bash
du -sh /var/log/*
```

Check:

```text
logrotate configuration
disk space
inode usage
application log configuration
```

### Step 6: Check Disk

```bash
df -h
```

```bash
df -i
```

A full filesystem can stop applications from writing logs.

### Step 7: Correlate Logs

Do not look at one error in isolation.

Build a timeline:

```text
10:01 Deployment
10:03 Database connection errors
10:04 Application latency increased
10:05 Load balancer health checks failed
```

This may reveal the relationship between events.

### Step 8: Check Log Levels

Applications may use:

```text
DEBUG
INFO
WARN
ERROR
FATAL
```

Increasing logging in production should be done carefully because it can generate large volumes of data.

### Important

```text
First error
    ≠
Root cause
```

An error may be a symptom of an earlier failure.

### Interview Tip

> "I use application and system logs to establish a timeline, identify the affected component, correlate errors with resources and recent changes, and distinguish symptoms from the actual root cause."

# Q374. How do you troubleshoot an application after a deployment?

## Answer

A production issue immediately after deployment strongly suggests a possible deployment-related change, but it should still be verified with evidence.

### Step 1: Confirm Deployment Time

Determine:

```text
Deployment started
Deployment completed
Issue started
```

### Step 2: Compare Before and After

Check:

```text
Application version
Configuration
Environment variables
Dependencies
Runtime/JDK version
Database schema
Certificates
Permissions
```

### Step 3: Check Service

```bash
systemctl status <application-service>
```

### Step 4: Check Logs

```bash
journalctl -u <application-service> -b
```

Search application logs for:

```text
Exception
ERROR
Connection failure
Configuration error
Class/module errors
Timeout
```

### Step 5: Check Port

```bash
ss -lntp
```

### Step 6: Test Locally

```bash
curl -v http://127.0.0.1:<port>/
```

### Step 7: Check Dependencies

Verify:

```text
Database
Cache
Message queue
External APIs
Storage
DNS
Certificates
```

### Step 8: Check Resource Usage

```bash
top
```

```bash
free -h
```

```bash
df -h
```

### Step 9: Compare With Healthy Instance

If only one server was deployed:

```text
Healthy instance
       vs
Problem instance
```

Compare:

```text
Version
Config
Environment
Packages
Runtime
Network
Resources
```

### Step 10: Consider Rollback

If the deployment is confirmed as the cause and rollback is part of the approved incident procedure:

```text
Rollback
   ↓
Verify service
   ↓
Verify application
   ↓
Monitor
```

Do not rollback blindly if database schema or data changes are involved.

### Common Causes

```text
Bad configuration
Missing environment variable
Wrong secret
Dependency incompatibility
Runtime/JDK change
Database schema mismatch
Wrong file permissions
Certificate issue
Port/configuration change
Application bug
```

### Interview Tip

> "I correlate the deployment timeline with the incident, compare the new and previous versions/configuration, inspect logs and dependencies, test the application locally, and use a controlled rollback when the deployment is confirmed as the cause."

# Q375. How do you troubleshoot a complete production application server issue?

## Answer

I follow a structured, evidence-based approach.

```text
                USER
                  |
                  v
                 DNS
                  |
                  v
          Load Balancer
                  |
                  v
          Web Server/Proxy
                  |
                  v
        APPLICATION SERVER
                  |
       +----------+----------+
       |          |          |
       v          v          v
   Database     Cache    External API
       |
       v
    Storage
```

## Step 1: Define the Incident

Identify:

```text
What is failing?
Which application?
Which URL/API?
Which environment?
Which users?
Which server/instance?
When did it start?
Is it intermittent?
What is the exact error?
```

## Step 2: Check Application Service

```bash
systemctl status <application-service>
```

## Step 3: Check Process

```bash
pgrep -a <application>
```

```bash
ps -ef | grep <application>
```

## Step 4: Check Listener

```bash
ss -lntp
```

Verify:

```text
Expected port
Expected IP
Expected process
```

## Step 5: Test Locally

```bash
curl -v http://127.0.0.1:<port>/
```

If local request fails:

```text
Application
Configuration
Process
Runtime
Dependency
```

become primary suspects.

If local request succeeds but remote request fails:

```text
Firewall
Routing
Security Group
Load Balancer
Network
Bind address
```

become stronger suspects.

## Step 6: Check Application Logs

```bash
journalctl -u <application-service> -n 100
```

Also check application-specific logs.

## Step 7: Check CPU

```bash
top
```

```bash
ps aux --sort=-%cpu | head
```

## Step 8: Check Memory

```bash
free -h
```

```bash
ps aux --sort=-%mem | head
```

Check OOM:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

## Step 9: Check Disk

```bash
df -h
```

```bash
df -i
```

```bash
du -xhd1 /var
```

## Step 10: Check Network

```bash
ip addr
```

```bash
ip route
```

```bash
ip route get <destination-ip>
```

## Step 11: Check Database Connectivity

```bash
getent hosts <db-host>
```

```bash
nc -vz <db-host> <db-port>
```

Then use the appropriate native database client when required.

## Step 12: Check External Dependencies

Investigate:

```text
Database
Redis/cache
Message queue
External APIs
DNS
Storage
Authentication service
```

## Step 13: Check Security Controls

```bash
firewall-cmd --list-all
```

```bash
getenforce
```

If necessary:

```bash
ausearch -m AVC -ts recent
```

Also check cloud/network security controls.

## Step 14: Check Recent Changes

Look for:

```text
Application deployment
Configuration changes
OS patches
Runtime/JDK update
Database changes
Certificate rotation
Firewall changes
Network changes
Secret rotation
```

## Step 15: Compare With Healthy Instances

If only one application server is affected:

```text
Problem Server
      vs
Healthy Server
```

Compare:

```text
Application version
Configuration
Environment
Packages
Runtime
Resources
Network
Dependencies
```

## Step 16: Use Packet Capture if Required

```bash
sudo tcpdump -ni any port <port>
```

Use targeted captures instead of capturing unnecessary traffic.

## Step 17: Apply the Smallest Safe Fix

Possible fixes:

```text
Correct configuration
Restore missing dependency
Fix permission
Correct firewall rule
Fix DNS
Recover database connectivity
Rollback deployment
Restart application
Scale application
```

The fix depends on the identified root cause.

## Step 18: Verify End-to-End

```text
DNS
 ↓
Load Balancer
 ↓
Web Server
 ↓
Application
 ↓
Database/Dependencies
 ↓
Response
```

Then monitor:

```text
CPU
Memory
Errors
Latency
Traffic
Database connections
Application health
```

## Production Scenario

**Interviewer:**

> "The production application is down. How will you troubleshoot it?"

**Strong Answer:**

> "First I would determine the scope and capture the exact error rather than immediately restarting the server. I would check the application service and process, verify the expected listening port, and test the application locally with curl. If the local request fails, I would inspect application logs, configuration, runtime, dependencies, CPU, memory, disk, and recent deployment changes. If the local request works but remote access fails, I would investigate DNS, routing, firewall, security groups, load balancer health, and bind addresses. I would verify database and external dependency connectivity from the application server. I would also check OOM events, disk/inode exhaustion, SELinux, and recent infrastructure or application changes. If necessary, I would use targeted packet capture to identify where traffic is failing. Once the failing layer is identified, I would apply the smallest safe and reversible fix, verify the application end-to-end, monitor the system, and document the root cause."

# 📌 Application Troubleshooting Decision Tree

```text
              APPLICATION ISSUE
                     |
                     v
              Is service running?
```

# 🎤 Application Server Interview Golden Rules

```text
Application running ≠ Application healthy
Process running ≠ Port reachable
Port listening ≠ Remote connectivity
Local curl works ≠ Remote access works
Remote access works ≠ Application is healthy
High CPU ≠ Automatically application bug
High memory ≠ Automatically memory leak
OOM ≠ Automatically application code problem
Slow application ≠ Automatically database problem
Database failure ≠ Automatically application failure
Service failure ≠ Automatically restart
Deployment timing ≠ Automatically deployment root cause
Log error ≠ Automatically root cause
Free memory ≠ No memory problem
Free disk ≠ Application can always write
Firewall disabled ≠ No network security control
```

# ⚠️ Production Safety Rules

```text
1. Do not restart blindly
2. Capture the exact error first
3. Identify the affected application
4. Determine the scope
5. Check service and process
6. Verify listening port
7. Test locally before testing remotely
8. Check logs before changing configuration
9. Check CPU/memory/disk
10. Check DNS/network/firewall
11. Check database/dependencies
12. Protect production secrets
13. Do not expose passwords or tokens
14. Do not blindly kill processes
15. Do not blindly increase memory/thread/connection limits
16. Do not blindly change firewall rules
17. Use controlled rollback for confirmed bad deployments
18. Prefer reversible changes
19. Verify application health after changes
20. Monitor after recovery
21. Document root cause and prevention
```

> **Interview mindset:** Don't say **"Application is down, so I will restart the application."** Say: **"I will first identify the scope and exact error, check the service, process, listener, local endpoint, logs, resources, network, dependencies, and recent changes. I will identify the failing layer and then apply the smallest safe fix, followed by end-to-end verification."**
