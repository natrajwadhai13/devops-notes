# 27. Network Bonding, Teaming & VLAN Troubleshooting

> Network bonding, teaming, and VLANs are commonly used in Linux production environments for **high availability, redundancy, load distribution, network segmentation, and improved network design**. # Q276. What is network bonding and why is it used?

## Answer

**Network bonding** combines multiple physical or virtual network interfaces into a single logical interface.

Example:

```text
              bond0
             /     \
          eth0     eth1
```

Applications can use:

```text
bond0
```

instead of directly using `eth0` or `eth1`.

### Why Use Bonding?

Common reasons:

```text
High availability
NIC redundancy
Failover
Load distribution
Higher throughput in supported modes
```

### Example

Without bonding:

```text
Server
  |
 eth0
  |
Switch
```

If `eth0` fails:

```text
Network unavailable
```

With bonding:

```text
             bond0
            /     \
         eth0     eth1
           |       |
        Switch   Switch
```

If one link fails, the other may continue providing connectivity depending on the configuration.

### Common Bonding Modes

```text
Mode 0 → balance-rr
Mode 1 → active-backup
Mode 2 → balance-xor
Mode 3 → broadcast
Mode 4 → 802.3ad / LACP
Mode 5 → balance-tlb
Mode 6 → balance-alb
```

### Most Common Production Examples

#### Active-Backup

```text
bond0
 |
 +-- eth0 → ACTIVE
 |
 +-- eth1 → BACKUP
```

If `eth0` fails:

```text
eth1 → ACTIVE
```

#### LACP

```text
bond0
 |
 +-- eth0
 |
 +-- eth1
       |
       v
    Switch
```

LACP uses **802.3ad** to negotiate link aggregation with the network infrastructure.

### Important

Bonding mode must match the intended network architecture.

You cannot assume that simply creating a bond will automatically provide redundancy or load balancing.

### Interview Tip

> "Network bonding combines multiple interfaces into one logical interface. It is commonly used for redundancy, failover, and in some modes load distribution or increased aggregate throughput."

# Q277. How do you check the status of a Linux bond?

## Answer

For the Linux bonding driver, check:

```bash id="5m8q2x"
cat /proc/net/bonding/bond0
```

Example:

```text id="q7m3x9"
Ethernet Channel Bonding Driver

Bonding Mode: fault-tolerance (active-backup)

Currently Active Slave: eth0

Slave Interface: eth0
MII Status: up

Slave Interface: eth1
MII Status: up
```

### Important Fields

Look for:

```text
Bonding Mode
Currently Active Slave
MII Status
Slave Interface
Link Failure Count
```

### Step 2: Check Interfaces

```bash id="p4x7m2"
ip link
```

### Step 3: Check IP Address

```bash id="n8m2q5"
ip addr show bond0
```

### Step 4: Check Routing

```bash id="v6q3m8"
ip route
```

### Step 5: Check NetworkManager

On systems using NetworkManager:

```bash id="j5m8x2"
nmcli device status
```

```bash id="r3q7m1"
nmcli connection show
```

### Step 6: Check Each Slave

```bash id="w4m9p2"
ethtool eth0
```

```bash id="y7x3m8"
ethtool eth1
```

### Step 7: Check Kernel Logs

```bash id="q2m8x4"
journalctl -k | grep -Ei "bond|eth0|eth1|link|fail"
```

### Troubleshooting Model

```text
bond0
 |
 +-- Mode?
 |
 +-- Active slave?
 |
 +-- Slave eth0?
 |
 +-- Slave eth1?
 |
 +-- Link?
 |
 +-- IP?
 |
 +-- Route?
 |
 +-- Traffic?
```

### Interview Tip

> "I check `/proc/net/bonding/bond0` for bonding state, then verify the individual interfaces with `ip link` and `ethtool`, IP and routing with `ip addr` and `ip route`, and NetworkManager configuration if applicable."

# Q278. How do you troubleshoot a bond when one slave interface is DOWN?

## Answer

First determine whether the bond is still providing connectivity through the other slave.

### Step 1: Check Bond

```bash id="g4x8m2"
cat /proc/net/bonding/bond0
```

Look for:

```text
MII Status: up/down
Currently Active Slave
```

### Step 2: Check Individual Interface

```bash id="t7m2q5"
ip link show eth0
```

```bash id="p8x4m1"
ip link show eth1
```

### Step 3: Check Physical/Virtual Link

```bash id="m5q9x2"
ethtool eth0
```

```bash id="w3m7p8"
ethtool eth1
```

Look for:

```text
Link detected: yes/no
```

### Step 4: Check Driver

```bash id="c6x2m9"
ethtool -i eth0
```

### Step 5: Check Kernel Logs

```bash id="z4m8q1"
journalctl -k | grep -Ei "eth0|eth1|bond|link|reset|error"
```

### Possible Causes

```text
Cable disconnected
Switch port failure
NIC failure
NIC driver problem
Firmware problem
Interface administratively down
NetworkManager configuration
Virtual NIC problem
```

### Example

```text
bond0
 |
 +-- eth0 → DOWN
 |
 +-- eth1 → UP
```

If:

```text
Bond mode = active-backup
eth1 = active
```

then the server may continue operating normally.

### Important

A single failed slave does not necessarily mean the bond is failed.

```text
One slave DOWN
      ≠
Bond DOWN
```

However, redundancy has been reduced.

### Production Action

If the remaining slave is healthy:

```text
1. Confirm traffic is using healthy slave
2. Investigate failed slave
3. Restore redundancy
4. Verify both members
```

### Interview Tip

> "If one bond member is down, I first confirm whether the bond is still healthy and whether traffic has failed over. Then I troubleshoot the affected NIC, link, driver, switch port, and configuration without unnecessarily disrupting the healthy member."

```bash id="m6q4x1"

```

```bash id="y8p2m7"

```

### Step 5: Check Switch Configuration

Depending on bonding mode, verify:

```text

```

### Step 6: Check ARP/Neighbor Information

```bash id="8x4m2q"

```

If necessary:

```bash id="p3x7m2"

```

```text

LACP mismatch
Switch port-channel issue
VLAN mismatch
Wrong IP
Wrong route
ARP/neighbor issue
MTU mismatch
Switch configuration
```

<a id="q280"></a>

# Q280. What is the difference between bonding modes and LACP?

## Answer

Bonding supports different modes for different requirements.

### Mode 1: Active-Backup

```text
bond0
 |
 +-- eth0 → ACTIVE
 |
 +-- eth1 → BACKUP
```

Only one interface normally carries traffic at a time.

Main purpose:

```text
High availability
Failover
```

### Mode 4: 802.3ad / LACP

LACP dynamically negotiates link aggregation with the switch.

```text
              bond0
             /     \
          eth0     eth1
            \       /
             \     /
              Switch
            Port-Channel
```

Main benefits:

```text
Link aggregation
Redundancy
Aggregate throughput
```

The actual throughput of an individual flow may still be limited by the hashing/load-balancing algorithm.

### Comparison

| Feature               | Active-Backup  | LACP                     |
| --------------------- | -------------- | ------------------------ |
| Redundancy            | Yes            | Yes                      |
| Multiple links active | Usually no     | Yes                      |
| Switch configuration  | Usually simple | Required                 |
| LACP required         | No             | Yes                      |
| Main purpose          | Failover       | Aggregation + redundancy |

### Important

Do not assume:

```text
2 × 1 Gbps NIC
=
1 single TCP connection at 2 Gbps
```

Traffic distribution depends on the bonding/LACP hashing and network architecture.

### Interview Tip

> "Active-backup primarily provides failover, while 802.3ad/LACP provides negotiated link aggregation with the switch. LACP requires compatible switch-side configuration."

# Q281. How do you troubleshoot LACP or switch-side bonding problems?

## Answer

LACP problems require checking **both Linux and the switch**.

### Step 1: Check Linux Bond

```bash id="x6m3q8"
cat /proc/net/bonding/bond0
```

Look for:

```text
Bonding Mode
MII Status
Slave interfaces
Actor information
Partner information
```

The exact fields depend on the bonding implementation and driver.

### Step 2: Check Interface State

```bash id="q8m2x5"
ip link
```

### Step 3: Check Link

```bash id="p4m7q2"
ethtool eth0
```

```bash id="r9x3m8"
ethtool eth1
```

### Step 4: Check Switch Port-Channel

On the network side, verify:

```text
Both ports belong to the same aggregation group
LACP enabled
Correct VLAN configuration
Correct trunk/access mode
Compatible speed/duplex
No port errors
```

The exact commands depend on the switch vendor.

### Step 5: Check VLAN

```bash id="j7m2q4"
ip -d link
```

### Step 6: Check Logs

```bash id="w5x8m1"
journalctl -k | grep -Ei "bond|lacp|link|eth0|eth1"
```

### Common LACP Problems

```text
LACP enabled on one side only
Wrong ports in port-channel
VLAN mismatch
One link connected to incorrect switch
Switch configuration mismatch
NIC link failure
Driver problem
MTU mismatch
```

### Important

Do not assume that:

```text
Both NICs UP
+
Bond exists
=
LACP working
```

The switch must also recognize and correctly aggregate the links.

### Interview Tip

> "For LACP problems, I validate the Linux bond configuration and each NIC, then correlate it with the switch port-channel and LACP state. I specifically check VLAN, port membership, link settings, and switch-side errors."

# Q282. What is a VLAN and how do you troubleshoot a VLAN interface?

## Answer

A **VLAN (Virtual Local Area Network)** logically separates network traffic on the same physical network infrastructure.

Example:

```text
Physical NIC: eth0
       |
       +-- VLAN 10 → Management
       |
       +-- VLAN 20 → Application
       |
       +-- VLAN 30 → Database
```

### Step 1: Check VLAN Interfaces

```bash id="m4x7q2"
ip -d link
```

You may see:

```text
eth0.10
eth0.20
```

### Step 2: Check Interface

```bash id="x8m2q5"
ip link show eth0.10
```

### Step 3: Check IP

```bash id="q3m7x1"
ip addr show eth0.10
```

### Step 4: Check Routing

```bash id="p6x2m8"
ip route
```

### Step 5: Check Parent NIC

```bash id="y5m8q3"
ip link show eth0
```

### Step 6: Check Link

```bash id="8x4m2p"
ethtool eth0
```

### Step 7: Check NetworkManager

```bash id="k7m3x9"
nmcli connection show
```

### Possible Causes

```text
Wrong VLAN ID
Parent interface down
Incorrect IP configuration
Switch trunk problem
VLAN not allowed
Wrong switch port mode
Routing issue
MTU mismatch
```

### Interview Tip

> "For a VLAN interface, I verify the VLAN ID and interface with `ip -d link`, check IP and routing, verify the parent NIC, and then confirm the switch trunk and VLAN configuration."

# Q283. How do you troubleshoot VLAN connectivity problems?

## Answer

A VLAN can be correctly configured on Linux but still fail because of the switch configuration.

### Step 1: Verify VLAN ID

```bash id="x2m8q5"
ip -d link
```

Example:

```text
eth0.20
vlan id 20
```

### Step 2: Check Parent Interface

```bash id="v7m3x1"
ip link show eth0
```

### Step 3: Check IP

```bash id="p4q8m2"
ip addr show eth0.20
```

### Step 4: Check Route

```bash id="j6x2m9"
ip route
```

### Step 5: Check Gateway

```bash id="q5m8x3"
ping -c 4 <gateway-ip>
```

### Step 6: Check ARP/Neighbor

```bash id="n7m2x4"
ip neigh
```

### Step 7: Check Switch

Verify:

```text
Port is trunk where required
Correct VLAN is allowed
Correct native VLAN
Correct access/trunk mode
Correct switch port
```

### Step 8: Check MTU

```bash id="y3q7m2"
ip link show
```

If jumbo frames are expected, verify MTU consistently across the path.

### Step 9: Capture Traffic

```bash id="m8x4q1"
sudo tcpdump -ni eth0
```

### Troubleshooting Model

```text
Linux VLAN
    |
    v
Parent NIC
    |
    v
Switch Port
    |
    v
Trunk
    |
    v
VLAN
    |
    v
Gateway
    |
    v
Destination
```

### Important

If the VLAN is not allowed on the switch trunk, Linux may look completely healthy while traffic still fails.

### Interview Tip

> "For VLAN connectivity, I validate the VLAN ID, parent NIC, IP, routing, gateway, ARP state, and MTU on Linux, then verify that the switch trunk allows the VLAN and uses the correct port configuration."

# Q284. How do you troubleshoot bonding with VLANs?

## Answer

Bonding and VLANs can be combined.

A common architecture is:

```text
             bond0
            /     \
         eth0     eth1
             |
             v
           VLAN
             |
     +-------+-------+
     |       |       |
   VLAN10  VLAN20  VLAN30
```

For example:

```text
bond0.10
bond0.20
bond0.30
```

### Step 1: Check Bond

```bash id="t8m3q7"
cat /proc/net/bonding/bond0
```

### Step 2: Check VLAN Interfaces

```bash id="x5q8m2"
ip -d link
```

### Step 3: Check IP Addresses

```bash id="p7m4x1"
ip addr
```

### Step 4: Check Routes

```bash id="j2x8q5"
ip route
```

### Step 5: Check Parent Interfaces

```bash id="q6m3x9"
ip link
```

### Step 6: Check Each NIC

```bash id="w4m8x2"
ethtool eth0
```

```bash id="c7x2m5"
ethtool eth1
```

### Step 7: Check LACP if Used

```text
Linux Bond
     ↕
LACP
     ↕
Switch Port-Channel
```

Verify the switch-side configuration.

### Step 8: Check VLAN Trunk

The switch ports connected to the bond may need compatible trunk/VLAN configuration depending on the design.

### Step 9: Test Each Layer

```text
Bond healthy?
      ↓
VLAN interface exists?
      ↓
Correct VLAN ID?
      ↓
Correct IP?
      ↓
Correct route?
      ↓
Gateway reachable?
      ↓
Destination reachable?
```

### Common Problems

```text
Wrong bond mode
LACP mismatch
Wrong VLAN ID
VLAN not allowed on trunk
Incorrect parent interface
Wrong IP/route
MTU mismatch
Switch port-channel problem
```

### Important

The configuration must be consistent across:

```text
Linux NICs
    ↓
Linux bond
    ↓
Linux VLAN
    ↓
Switch port-channel
    ↓
Switch VLAN/trunk
```

### Interview Tip

> "When bonding and VLANs are combined, I troubleshoot from the bottom up: physical NICs, bond state, VLAN interface, IP, routing, gateway, and then switch-side LACP and trunk configuration."

# Q285. How do you troubleshoot a production server with bonding, teaming, and VLAN problems?

## Answer

I use a **layer-by-layer approach** and avoid making disruptive network changes without a recovery path.

### Step 1: Understand the Architecture

First identify:

```text
Physical NICs
      ↓
Bond / Team
      ↓
VLAN
      ↓
IP Address
      ↓
Routing
      ↓
Switch
```

### Step 2: Check Bond/Team

For Linux bonding:

```bash id="y7m3q8"
cat /proc/net/bonding/bond0
```

For NetworkManager:

```bash id="p5x8m2"
nmcli device status
```

```bash id="q4m7x1"
nmcli connection show
```

### Step 3: Check NICs

```bash id="x2m8q5"
ip link
```

```bash id="j6q3m9"
ethtool eth0
```

```bash id="w5m2x8"
ethtool eth1
```

### Step 4: Check VLAN

```bash id="r7x3m2"
ip -d link
```

Verify:

```text
VLAN ID
Parent interface
Interface state
```

### Step 5: Check IP and Routing

```bash id="p8m4q1"
ip addr
```

```bash id="y3x7m2"
ip route
```

### Step 6: Check Gateway

```bash id="m5q8x4"
ping -c 4 <gateway-ip>
```

### Step 7: Check ARP/Neighbor

```bash id="k2m7x5"
ip neigh
```

### Step 8: Check Kernel Logs

```bash id="x8q3m1"
journalctl -k | grep -Ei "bond|team|vlan|eth|link|error|reset"
```

### Step 9: Check Switch Side

Verify:

```text
Correct switch ports
Correct port-channel
LACP state
Correct VLAN
Trunk configuration
Allowed VLANs
Speed/duplex
Port errors
```

### Step 10: Check Packet Flow

If needed:

```bash id="v4m8q2"
sudo tcpdump -ni bond0
```

For a VLAN interface:

```bash id="x6q2m7"
sudo tcpdump -ni bond0.20
```

Use narrow filters where possible on production systems.

### Step 11: Identify the Failure Layer

```text
Physical NIC
     ↓
Driver
     ↓
Interface
     ↓
Bond/Team
     ↓
VLAN
     ↓
IP
     ↓
Route
     ↓
Gateway
     ↓
Switch
     ↓
Destination
```

### Step 12: Protect Production

If redundant networking exists:

```text
Healthy NIC
     ↓
Keep production traffic
     ↓
Troubleshoot failed member
     ↓
Restore redundancy
```

Avoid unnecessarily restarting the entire network stack when only one component is failing.

### Step 13: Apply the Smallest Safe Fix

Possible actions:

```text
Correct VLAN configuration
Restore failed bond member
Fix switch port
Correct LACP configuration
Correct network profile
Replace failed NIC
Fix driver/firmware
Correct MTU
```

### Step 14: Verify

Check:

```text
Bond healthy
+
All expected NICs healthy
+
VLAN operational
+
Correct IP
+
Correct route
+
Gateway reachable
+
Destination reachable
+
Application reachable
```

### Production Scenario

**Interviewer:**

> "A production Linux server has two NICs in an LACP bond and multiple VLANs. One application VLAN suddenly becomes unreachable. How will you troubleshoot it?"

**Strong Answer:**

> "First I would identify whether the problem is limited to one VLAN or affects the entire bond. I would check the bond state with `/proc/net/bonding/bond0`, verify both NICs and their link status with `ip link` and `ethtool`, and check the VLAN configuration with `ip -d link`. I would verify the VLAN IP and routing using `ip addr` and `ip route`, then test the gateway and inspect neighbor information. Since this is LACP, I would also check the switch port-channel and confirm that the affected VLAN is allowed on the trunk. I would review kernel logs and use targeted packet capture if necessary. Because it is production, I would avoid restarting the entire network stack or changing LACP/VLAN configuration blindly. I would apply the smallest safe fix and verify the VLAN, gateway, destination, and application connectivity afterward."

# 🎤 Bonding & VLAN Interview Golden Rules

```text
Bond exists ≠ Bond healthy
One slave DOWN ≠ Bond DOWN
Both slaves UP ≠ LACP working
LACP ≠ Automatically higher single-flow speed
Bonding ≠ VLAN
VLAN configured ≠ VLAN reachable
VLAN interface UP ≠ Network working
IP configured ≠ Correct routing
Correct Linux config ≠ Correct switch config
LACP requires compatible switch configuration
Trunk ≠ Automatically all VLANs allowed
Gateway reachable ≠ Application reachable
```

### ⚠️ Production Safety Rules

Before changing bonding, teaming, or VLAN configuration:

```text
1. Understand the complete network architecture
2. Identify all NICs and their roles
3. Check whether redundant connectivity exists
4. Confirm the active bond member
5. Check bond/team mode
6. Check LACP configuration if used
7. Check VLAN IDs
8. Check IP and routing
9. Check switch port/port-channel configuration
10. Check whether the VLAN is allowed on the trunk
11. Keep console/out-of-band access available
12. Avoid restarting the entire network stack blindly
13. Avoid changing LACP on only one side
14. Avoid changing VLAN configuration without a rollback plan
15. Make the smallest required change
16. Verify gateway connectivity
17. Verify destination connectivity
18. Verify application health
19. Confirm redundancy is restored
20. Document the root cause
```

> **Interview mindset:** Do not say, "The VLAN is down, so I will restart NetworkManager." Say, **"I will determine whether the failure is at the NIC, bond/team, LACP, VLAN, IP, routing, or switch layer, verify both Linux and network-side configuration, protect the production traffic using available redundancy, apply the smallest safe correction, and verify end-to-end application connectivity."**
