# Q376. How do you troubleshoot a web application that is not accessible?

## Answer

First identify **where the request is failing**.

Typical architecture:

```text
User
  |
  v
DNS
  |
  v
Load Balancer
  |
  v
Web Server / Reverse Proxy
  |
  v
Application
  |
  +----> Database
  |
  +----> Cache
  |
  +----> External API
```

### Step 1: Check DNS

```bash
getent hosts app.example.com
```

```bash
dig app.example.com
```

### Step 2: Test HTTP/HTTPS

```bash
curl -v http://app.example.com
```

For HTTPS:

```bash
curl -vk https://app.example.com
```

### Step 3: Check TCP Port

```bash
nc -vz app.example.com 80
```

```bash
nc -vz app.example.com 443
```

### Step 4: Check Application/Web Server

```bash
systemctl status nginx
```

or:

```bash
systemctl status httpd
```

### Step 5: Check Listening Ports

```bash
ss -lntp
```

### Step 6: Check Logs

Nginx:

```bash
journalctl -u nginx -n 100
```

Apache:

```bash
journalctl -u httpd -n 100
```

Application:

```bash
journalctl -u <application-service> -n 100
```

### Step 7: Check Resources

```bash
top
```

```bash
free -h
```

```bash
df -h
```

### Step 8: Check Firewall

```bash
firewall-cmd --list-all
```

Also check cloud/network security controls where applicable.

### Step 9: Check Backend Dependencies

Verify:

```text
Database
Cache
Message queue
External API
Storage
Authentication service
```

### Interview Tip

> "I start from the client side and move through DNS, TCP, load balancer, web server, application, and backend dependencies until I identify the failing layer."

# Q377. How do you troubleshoot HTTP 4xx errors?

## Answer

4xx errors generally indicate a problem with the **client request or access to the requested resource**, although the exact cause depends on the component generating the response.

Common codes:

| Code | Meaning            |
| ---- | ------------------ |
| 400  | Bad Request        |
| 401  | Unauthorized       |
| 403  | Forbidden          |
| 404  | Not Found          |
| 405  | Method Not Allowed |
| 408  | Request Timeout    |
| 429  | Too Many Requests  |

### Step 1: Identify the Exact Status Code

```bash
curl -I https://app.example.com/path
```

For detailed output:

```bash
curl -v https://app.example.com/path
```

### Step 2: Identify Which Component Returned It

The response could come from:

```text
Load Balancer
WAF
Nginx
Apache
Application
API Gateway
```

Check:

```text
Server headers
Request IDs
Load balancer logs
Web server logs
Application logs
```

### 400 — Bad Request

Possible causes:

```text
Invalid request syntax
Invalid parameters
Malformed JSON
Invalid headers
```

### 401 — Unauthorized

Possible causes:

```text
Missing credentials
Invalid token
Expired token
Authentication failure
```

### 403 — Forbidden

Possible causes:

```text
File permissions
Web server access rules
Application authorization
WAF/security policy
SELinux
IP restrictions
```

### 404 — Not Found

Possible causes:

```text
Wrong URL
Missing file
Wrong DocumentRoot
Incorrect application route
Wrong VirtualHost/server block
Rewrite configuration
```

### 405 — Method Not Allowed

Example:

```text
GET allowed
POST not allowed
```

Check application routing and web-server configuration.

### 429 — Too Many Requests

Possible causes:

```text
Rate limiting
API throttling
Traffic spike
WAF policy
Application limits
```

### Important

Do not assume every 4xx error is an application bug.

### Interview Tip

> "I identify the exact 4xx status, determine which component generated it, inspect the request and corresponding logs, and then investigate authentication, authorization, routing, access rules, or rate limiting as appropriate."

# Q378. How do you troubleshoot HTTP 5xx errors?

## Answer

5xx errors generally indicate a problem while processing the request on the server side or an upstream dependency.

Common codes:

| Code | Meaning               |
| ---- | --------------------- |
| 500  | Internal Server Error |
| 501  | Not Implemented       |
| 502  | Bad Gateway           |
| 503  | Service Unavailable   |
| 504  | Gateway Timeout       |

### 500 — Internal Server Error

Check:

```text
Application logs
Web server logs
Stack traces
Configuration
Permissions
Dependencies
Recent deployment
```

### 502 — Bad Gateway

Common with reverse proxies/load balancers.

Check:

```text
Backend listener
Backend service
proxy configuration
DNS
Firewall
TLS between proxy and backend
```

Test backend directly:

```bash
curl -v http://<backend-ip>:<port>/
```

### 503 — Service Unavailable

Possible causes:

```text
Application unavailable
No healthy backend
Overloaded server
Maintenance
Connection pool exhaustion
Resource exhaustion
```

### 504 — Gateway Timeout

Possible causes:

```text
Slow application
Slow database
Slow external API
Network latency
Backend timeout
Connection pool wait
```

### Step 1: Check Web Server Logs

```bash
journalctl -u nginx -n 100
```

or:

```bash
journalctl -u httpd -n 100
```

### Step 2: Check Application Logs

```bash
journalctl -u <application-service> -n 100
```

### Step 3: Check Backend

```bash
ss -lntp
```

### Step 4: Check Resources

```bash
top
free -h
df -h
```

### Step 5: Check Database/Dependencies

Test connectivity:

```bash
nc -vz <db-host> <db-port>
```

### Important

```text
502 ≠ Automatically restart backend
503 ≠ Automatically application is down
504 ≠ Automatically increase timeout
```

### Interview Tip

> "For a 5xx error, I first identify which layer generated the response, then correlate web-server logs, application logs, backend health, resource usage, and dependency failures."

# Q379. How do you troubleshoot a web application that is slow?

## Answer

First determine **where the latency is occurring**.

```text
Client
  |
  v
DNS
  |
  v
Load Balancer
  |
  v
Web Server
  |
  v
Application
  |
  +----> Database
  |
  +----> Cache
  |
  +----> External API
```

### Step 1: Measure Request Time

```bash
curl -s -o /dev/null -w \
'DNS:%{time_namelookup} CONNECT:%{time_connect} START:%{time_starttransfer} TOTAL:%{time_total}\n' \
https://app.example.com/
```

### Step 2: Check CPU

```bash
top
```

```bash
ps aux --sort=-%cpu | head
```

### Step 3: Check Memory

```bash
free -h
```

### Step 4: Check Disk I/O

```bash
iostat -xz 1
```

### Step 5: Check Web Server

Look for:

```text
High request rate
Connection limits
Worker exhaustion
Upstream latency
Errors
```

### Step 6: Check Application

Investigate:

```text
Thread pools
Worker processes
Connection pools
Slow code paths
Garbage collection
Application errors
```

### Step 7: Check Database

Investigate:

```text
Slow queries
Locks
High connections
CPU
Memory
I/O
```

### Step 8: Check External APIs

An application may be slow because an external service is slow.

### Step 9: Compare Instances

Example:

```text
Server A → 200 ms
Server B → 8 seconds
Server C → 220 ms
```

Focus on Server B.

### Step 10: Check Recent Changes

```text
Deployment
Configuration
Database changes
Network changes
Traffic increase
Certificate changes
```

### Important

Do not blindly:

```text
Increase timeout
Increase worker count
Increase connection pool
Restart application
```

These actions can hide the actual problem.

### Interview Tip

> "I measure latency first, then identify whether the delay is in DNS, network, web server, application processing, database, or an external dependency."

# Q380. How do you troubleshoot a web application that works locally but not remotely?

## Answer

This is a common networking problem.

Example:

```text
On Server:
curl localhost:8080 → SUCCESS

Remote Client:
curl server-ip:8080 → FAILURE
```

This indicates that the application itself may be working, but remote access is failing.

### Step 1: Check Listening Address

```bash
ss -lntp | grep :8080
```

If:

```text
127.0.0.1:8080
```

the application may only accept local connections.

If:

```text
0.0.0.0:8080
```

it is listening on all IPv4 interfaces, subject to other controls.

### Step 2: Test Server IP Locally

```bash
curl -v http://<server-ip>:8080/
```

### Step 3: Check Firewall

```bash
firewall-cmd --list-all
```

### Step 4: Check Routing

```bash
ip route
```

### Step 5: Test From Remote Host

```bash
nc -vz <server-ip> 8080
```

### Step 6: Check Cloud Security

If hosted in cloud, inspect:

```text
Security Group
Network Security Rules
NACL
Load Balancer
Cloud Firewall
```

### Step 7: Use Packet Capture

On the application server:

```bash
sudo tcpdump -ni any port 8080
```

If the remote request does not arrive:

```text
Network
Firewall
Security Group
Routing
```

become stronger suspects.

If it arrives but is rejected:

```text
Application
Listener
Firewall
```

need investigation.

### Interview Tip

> "If localhost works but remote access fails, I check the bind address, host firewall, routing, cloud security controls, and packet arrival before changing the application."

# Q381. How do you troubleshoot a web application that works by IP but not by hostname?

## Answer

If:

```text
http://10.20.10.50 → SUCCESS
```

but:

```text
http://app.example.com → FAILURE
```

DNS or hostname-based configuration becomes a primary suspect.

### Step 1: Check DNS

```bash
getent hosts app.example.com
```

```bash
dig app.example.com
```

### Step 2: Compare IP Address

Verify that DNS points to the expected:

```text
Load Balancer
Web Server
Application endpoint
```

### Step 3: Check Virtual Host/Server Block

Nginx:

```bash
nginx -T
```

Apache:

```bash
apachectl -S
```

Check:

```text
server_name
ServerName
ServerAlias
VirtualHost
```

### Step 4: Test Host Header

HTTP:

```bash
curl -v -H 'Host: app.example.com' http://10.20.10.50/
```

### Step 5: Test HTTPS/SNI

```bash
curl -vk --resolve app.example.com:443:10.20.10.50 https://app.example.com/
```

This is useful when testing a specific backend IP while preserving the hostname/SNI.

### Step 6: Check Certificates

For HTTPS:

```bash
openssl s_client -connect app.example.com:443 -servername app.example.com
```

Check:

```text
Certificate
SAN
Expiry
Chain
SNI
```

### Important

A web application may use hostname-based routing.

Therefore:

```text
IP works
```

does not always prove:

```text
Hostname configuration is correct
```

### Interview Tip

> "I verify DNS first, then test the expected Host header and SNI behavior, and inspect Nginx/Apache VirtualHost or server-block configuration and TLS certificates."

# Q382. How do you troubleshoot intermittent web application failures?

## Answer

Intermittent failures require **pattern identification**.

### Step 1: Identify the Pattern

Ask:

```text
When does it fail?
Which users?
Which region?
Which server?
Which URL?
Which status code?
How frequently?
```

### Step 2: Check Load Balancer Distribution

Example:

```text
Server A → Healthy
Server B → Errors
Server C → Healthy
```

The load balancer may send traffic to Server B intermittently.

### Step 3: Compare Application Instances

Check:

```text
Version
Configuration
Resources
Dependencies
Network
Logs
```

### Step 4: Check Application Logs

Search around the exact failure time:

```bash
journalctl -u <application-service> --since "10 minutes ago"
```

### Step 5: Check Resource Spikes

```bash
top
```

```bash
free -h
```

```bash
iostat -xz 1
```

### Step 6: Check Network Errors

```bash
ip -s link
```

```bash
ss -s
```

### Step 7: Check Backend Dependencies

Investigate:

```text
Database
Cache
External APIs
DNS
Message queues
```

### Step 8: Check Timeouts

Look at:

```text
Load balancer timeout
Web server timeout
Application timeout
Database timeout
External API timeout
```

### Step 9: Check Packet Flow

```bash
sudo tcpdump -ni any host <client-ip>
```

Use a targeted capture appropriate to the incident.

### Step 10: Check Recent Changes

```text
Deployment
Scaling
Network changes
Firewall changes
DNS changes
Configuration changes
Certificate changes
```

### Common Causes

```text
One unhealthy backend
Connection pool exhaustion
Resource spikes
Network packet loss
DNS instability
Database overload
External API failures
Timeouts
Race conditions
Application bugs
```

### Interview Tip

> "For intermittent failures, I look for a pattern and compare successful and failed requests. I correlate load-balancer target selection, application logs, resource metrics, network errors, dependencies, and timing."

## Answer

Backend services can include:

```text
Database
Redis
Message Queue
REST API
Storage
Authentication Service
```

### Step 1: Identify the Backend

Determine:

```text
Hostname/IP
Port
Protocol
Expected response
```

### Step 2: Check DNS

```bash
getent hosts <backend-host>
```

### Step 3: Check Route

```bash
ip route get <backend-ip>
```

### Step 4: Check TCP Connectivity

```bash
nc -vz <backend-host> <port>
```

### Step 5: Test Protocol

For HTTP:

```bash
curl -v http://<backend-host>:<port>/
```

For HTTPS:

```bash
curl -vk https://<backend-host>:<port>/
```

For PostgreSQL:

```bash
psql -h <backend-host> -p 5432 -U <user> -d <database>
```

### Step 6: Check Application Logs

Look for:

```text
Connection refused
Timeout
Unknown host
Authentication failure
SSL error
Connection pool exhausted
Too many connections
```

### Step 7: Check Backend Listener

On the backend:

```bash
ss -lntp
```

### Step 8: Check Firewall/Security Controls

```text
Application server firewall
Backend firewall
Cloud Security Group
NACL
Network Firewall
Kubernetes NetworkPolicy
```

### Step 9: Check Backend Health

The backend can be reachable but unhealthy.

Check:

```text
CPU
Memory
Disk
Connections
Application health
Database health
```

### Step 10: Check Application Configuration

Verify:

```text
Backend hostname
Port
Credentials
TLS configuration
Timeouts
Connection pool
```

### Important

```text
TCP connection successful
       ≠
Backend service healthy
```

### Interview Tip

> "I reproduce the backend connection from the application server and move through DNS, routing, TCP, protocol-level testing, authentication, application configuration, security controls, and backend health."

# Q384. How do you troubleshoot a web application after a deployment?

## Answer

If an issue starts immediately after deployment, compare the **previous working state with the new state**.

### Step 1: Check Deployment Timeline

```text
Deployment started
       ↓
Deployment completed
       ↓
Application issue started
```

### Step 2: Check Application Version

Verify the deployed version/build.

### Step 3: Check Logs

```bash
journalctl -u <application-service> -b
```

Search for:

```text
ERROR
Exception
Timeout
Connection failure
Configuration error
```

### Step 4: Check Service and Process

```bash
systemctl status <application-service>
```

```bash
pgrep -a <application>
```

### Step 5: Check Port

```bash
ss -lntp
```

### Step 6: Test Locally

```bash
curl -v http://127.0.0.1:<port>/
```

### Step 7: Check Configuration

Compare:

```text
Environment variables
Configuration files
Secrets
Database URL
API endpoints
TLS certificates
Runtime options
```

### Step 8: Check Dependencies

```text
Database
Cache
Message queue
External APIs
DNS
Authentication
```

### Step 9: Check Runtime Compatibility

Examples:

```text
JDK version
Python version
Node.js version
Library versions
OS packages
```

### Step 10: Compare With Previous Version

Look for:

```text
Code changes
Configuration changes
Dependency changes
Database schema changes
Runtime changes
```

### Step 11: Rollback if Confirmed

If the deployment is confirmed as the cause and rollback is approved:

```text
Rollback
   ↓
Verify application
   ↓
Monitor
```

Be especially careful if the deployment changed database schema or data.

### Important

```text
Issue after deployment
      ≠
Automatically bad code
```

Infrastructure, configuration, secrets, dependencies, and database changes can also cause the issue.

### Interview Tip

> "I correlate the incident with the deployment, compare the previous and current application state, inspect logs and dependencies, test locally, and perform a controlled rollback when the deployment is confirmed as the cause."

# 📌 HTTP Status Code Quick Reference

| Code    | Category | Common Meaning                 |
| ------- | -------- | ------------------------------ |
| 200     | Success  | Request successful             |
| 301/302 | Redirect | Client redirected              |
| 400     | 4xx      | Bad request                    |
| 401     | 4xx      | Authentication required/failed |
| 403     | 4xx      | Access forbidden               |
| 404     | 4xx      | Resource/route not found       |
| 405     | 4xx      | HTTP method not allowed        |
| 408     | 4xx      | Request timeout                |
| 429     | 4xx      | Too many requests              |
| 500     | 5xx      | Internal server error          |
| 502     | 5xx      | Bad gateway/upstream failure   |
| 503     | 5xx      | Service unavailable            |
| 504     | 5xx      | Gateway timeout                |

> The component generating the response matters. A 403 or 503 may be generated by a WAF, load balancer, web server, or application—not necessarily by the application itself.


# ⚠️ Production Safety Rules

```text
1. Capture the exact URL and error
2. Determine the incident scope
3. Check whether the issue is reproducible
4. Do not restart blindly
5. Check DNS before changing DNS
6. Check TCP before changing firewall rules
7. Check local connectivity before changing network configuration
8. Identify which component generated the HTTP response
9. Check logs before making configuration changes
10. Protect production credentials and secrets
11. Do not expose tokens/passwords in logs or commands
12. Avoid blindly increasing timeouts
13. Avoid blindly increasing worker/thread/connection limits
14. Avoid chmod 777 as a web-application fix
15. Avoid flushing firewall rules
16. Use targeted packet captures
17. Compare healthy and unhealthy instances
18. Use controlled rollback for confirmed bad deployments
19. Prefer reversible changes
20. Verify the application end-to-end after recovery
21. Monitor after the fix
22. Document root cause and preventive action
```

> **Interview mindset:** When a web application fails, don't immediately say **"restart Nginx"** or **"restart the application."** A strong answer is: **"I will identify the scope and exact HTTP/network error, then troubleshoot DNS, TCP, TLS, load balancer, web server, application, resources, backend dependencies, security controls, and recent changes layer by layer. Once I identify the failing layer, I will apply the smallest safe fix and verify the complete request path."**
