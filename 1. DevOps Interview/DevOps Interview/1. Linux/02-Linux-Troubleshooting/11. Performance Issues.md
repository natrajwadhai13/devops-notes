# Q106. How do you troubleshoot a slow Linux server?

## Answer

First identify whether the slowness is caused by **CPU, memory, disk I/O, network, or the application**.

### Step 1: Check Load

```bash
uptime
```

### Step 2: Check CPU

```bash
top
```

### Step 3: Check Memory

```bash
free -h
```

### Step 4: Check I/O

```bash
iostat -xz 1
```

### Step 5: Check Processes

```bash
ps aux --sort=-%cpu | head
```

```bash
ps aux --sort=-%mem | head
```

### Step 6: Check Network

```bash
ss -s
```

### Step 7: Check System Logs

```bash
journalctl --since "30 minutes ago"
```

### Common Causes

* High CPU
* Memory pressure
* Heavy swap activity
* Disk latency
* High I/O wait
* Network problems
* Too many processes
* Application issue
* Database issue
* Scheduled backup/batch job

### Interview Tip

> "For a slow Linux server, I don't immediately restart it. I collect CPU, memory, disk I/O, network, process, and application information to identify the bottleneck."

# Q108. How do you identify whether CPU is causing a performance problem?

## Answer

Check:

```bash
top
```

Look at:

```text
us
sy
id
wa
st
```

Also check:

```bash
mpstat -P ALL 1
```

This helps identify whether a particular CPU is heavily utilized.

Find CPU-heavy processes:

```bash
ps aux --sort=-%cpu | head -20
```

### Example

```text
CPU Usage = 98%
Load     = 12
CPU Count = 8
```

This indicates significant CPU pressure.

But:

```text
CPU Usage = 40%
Load     = 12
```

may indicate that tasks are waiting on I/O or another resource.

### Important

Do not look only at:

```text
%CPU
```

Also correlate:

```text
CPU utilization
+
Load average
+
CPU count
+
I/O wait
+
Process activity
```

### Interview Tip

> "I confirm CPU saturation by checking overall utilization, per-CPU statistics, load average, and the processes consuming CPU."

<a id="q109"></a>

# Q109. How do you identify whether memory is causing a performance problem?

## Answer

Check:

```bash
free -h
```

Look at:

```text
available
swap
```

Then:

```bash
vmstat 1
```

Check active swap:

```bash
swapon --show
```

Find memory-heavy processes:

```bash
ps aux --sort=-%mem | head
```

### Warning Signs

```text
Low available memory
+
Continuous swap activity
+
High I/O
+
Slow applications
```

This can indicate memory pressure.

### Check OOM Events

```bash
journalctl -k | grep -i oom
```

### Interview Tip

> "I don't consider low free memory alone to be a performance problem. I look at available memory, swap activity, OOM events, and application behavior."

# Q110. How do you identify whether disk I/O is causing a performance problem?

## Answer

Start with:

```bash
iostat -xz 1
```

Important metrics include:

```text
%util
await
r/s
w/s
rkB/s
wkB/s
```

Check which devices are busy:

```bash
lsblk
```

Check processes generating I/O:

```bash
iotop
```

if available.

### Check I/O Wait

```bash
vmstat 1
```

Look at:

```text
wa
```

### Common Causes

* Database workload
* Backup jobs
* Large file operations
* Log processing
* Slow disks
* SAN/NFS latency
* Cloud storage performance limits

### Important

High disk utilization alone does not always mean the disk is faulty. You need to correlate:

```text
I/O workload
+
Latency
+
Queueing
+
Application response time
```

### Interview Tip

> "I use `iostat` to identify device-level latency and utilization, then correlate it with the processes and applications generating the I/O."

# Q111. How do you troubleshoot high load average?

## Answer

Check:

```bash
uptime
```

Example:

```text
load average: 16.0, 14.0, 10.0
```

Then check CPU count:

```bash
nproc
```

Suppose:

```text
CPU = 8
Load = 16
```

The load is significantly higher than the available logical CPU capacity.

### Check CPU

```bash
top
```

### Check I/O

```bash
vmstat 1
```

If required:

```bash
iostat -xz 1
```

### Important

High load can be caused by:

```text
CPU-bound tasks
       OR
I/O-bound tasks
       OR
Tasks stuck waiting on resources
```

Therefore:

```text
High Load
   |
   +-- High CPU → CPU bottleneck
   |
   +-- High wa → I/O bottleneck
   |
   +-- Both normal → Investigate processes/dependencies
```

### Interview Tip

> "I compare load average with the number of logical CPUs and then determine whether the load is CPU-driven or caused by tasks waiting on I/O."

# Q112. How do you troubleshoot a server that becomes slow at a specific time?

## Answer

This is usually a **time-based performance issue**.

First identify when the problem occurs.

Example:

```text
Every day:
02:00 AM → Server becomes slow
02:30 AM → Performance returns to normal
```

Check historical CPU:

```bash
sar -u
```

Memory:

```bash
sar -r
```

I/O:

```bash
sar -d
```

Check scheduled jobs:

```bash
crontab -l
```

System cron:

```bash
ls -l /etc/cron.*
```

Also check:

```bash
systemctl list-timers
```

### Common Causes

* Backup job
* Database maintenance
* Log rotation
* Batch processing
* Security scan
* Cron job
* Data processing
* Monitoring/scan workload

### Troubleshooting Approach

```text
Identify Time
      ↓
Check Historical Metrics
      ↓
CPU / Memory / I/O / Network
      ↓
Check Cron & Timers
      ↓
Identify Scheduled Workload
      ↓
Correlate With Application Logs
      ↓
Fix / Reschedule / Optimize
```

### Interview Tip

> "If performance degradation occurs at the same time every day, I compare historical metrics with cron jobs, systemd timers, backups, batch jobs, and application schedules."

# Q113. How do you troubleshoot application slowness on Linux?

## Answer

First determine whether the application itself is slow or whether the Linux host is causing the problem.

### Step 1: Check Application Status

```bash
systemctl status myapp
```

### Step 2: Check Application Logs

```bash
journalctl -u myapp
```

### Step 3: Check CPU

```bash
top
```

### Step 4: Check Memory

```bash
free -h
```

### Step 5: Check I/O

```bash
iostat -xz 1
```

### Step 6: Check Network Connections

```bash
ss -s
```

### Step 7: Check Dependencies

Investigate:

```text
Application
    |
    +-- Database
    |
    +-- API
    |
    +-- DNS
    |
    +-- Storage
    |
    +-- Network
```

### Example

If the application response time increases but:

```text
CPU    → normal
Memory → normal
Disk   → normal
```

investigate:

* Database latency
* External API
* Network latency
* DNS
* Application thread pool
* Connection pool
* Dependency failures

### Interview Tip

> "Application slowness is not always a Linux resource problem. I verify host health first and then investigate application logs, dependencies, network, database, and connection/thread pools."

# Q114. How do you troubleshoot performance degradation after a deployment?

## Answer

First establish whether the problem started immediately after the deployment.

Compare:

```text
Before Deployment
        ↓
Deployment
        ↓
After Deployment
```

Check:

```bash
top
free -h
iostat -xz 1
```

Check application logs:

```bash
journalctl -u myapp --since "1 hour ago"
```

### Compare Metrics

Look for changes in:

* CPU usage
* Memory usage
* Disk I/O
* Network traffic
* Request rate
* Response time
* Error rate
* Process/thread count

### Possible Causes

* Application code change
* Configuration change
* Memory leak
* Increased logging
* Database query change
* Increased thread count
* Dependency change
* Incorrect resource limits

### Rollback

If the deployment is confirmed as the cause and rollback is approved:

```text
Stop/mitigate impact
       ↓
Confirm deployment correlation
       ↓
Rollback according to change procedure
       ↓
Verify application
       ↓
Collect evidence
       ↓
Perform RCA
```

### Interview Tip

> "If performance degradation begins immediately after deployment, I compare before-and-after metrics, application logs, configuration, and dependencies. If the deployment is confirmed as the cause, I follow the approved rollback or mitigation procedure."

# Q115. How do you perform end-to-end Linux performance troubleshooting in production?

## Answer

I use a structured **top-down approach**.

### Step 1: Confirm the Impact

Determine:

```text
What is slow?
Who is affected?
When did it start?
Is it intermittent or continuous?
```

### Step 2: Check System Load

```bash
uptime
```

### Step 3: Check CPU

```bash
top
```

```bash
mpstat -P ALL 1
```

### Step 4: Check Memory

```bash
free -h
```

```bash
vmstat 1
```

### Step 5: Check Disk I/O

```bash
iostat -xz 1
```

### Step 6: Check Network

```bash
ss -s
```

```bash
ip -s link
```

### Step 7: Find Resource-Heavy Processes

```bash
ps aux --sort=-%cpu | head -20
```

```bash
ps aux --sort=-%mem | head -20
```

### Step 8: Check Application

```bash
systemctl status myapp
```

```bash
journalctl -u myapp
```

### Step 9: Check Historical Data

```bash
sar -u
sar -r
sar -d
```

### Step 10: Identify the Bottleneck

```text
                    Performance Issue
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
         CPU            Memory             Disk
          |                |                |
          v                v                v
       Process           Swap             I/O
          |                |                |
          +----------------+----------------+
                           |
                           v
                        Network
                           |
                           v
                      Application
                           |
                           v
                       Dependency
                           |
                           v
                      Root Cause
```

### Step 11: Mitigate

Depending on the issue:

* Stop or reschedule non-critical workload
* Scale application resources
* Resolve storage bottleneck
* Fix application configuration
* Restart a failed service when appropriate
* Roll back a problematic deployment
* Increase resources if capacity is genuinely insufficient

### Step 12: Verify

After mitigation:

```text
CPU
Memory
I/O
Network
Application Response
Error Rate
```

should be checked again.

### Step 13: RCA

Document:

```text
Problem
Impact
Timeline
Root Cause
Immediate Fix
Permanent Fix
Prevention
```

### Production Interview Scenario

**Interviewer:**

> "Users report that the production application is very slow. What will you check?"

**Strong Answer:**

> "First I will confirm the scope and start time of the issue. On the Linux server I will check load average, CPU, memory, swap, disk I/O, and network statistics using commands such as `uptime`, `top`, `free`, `vmstat`, `iostat`, and `ss`. I will identify resource-heavy processes and check application logs and dependencies such as the database or external APIs. I will compare current metrics with historical data to identify what changed. Once I identify the bottleneck, I will apply the appropriate mitigation, verify recovery, and document the root cause and preventive action."

# 📌 Command Prerequisites & Limitations

> Linux troubleshooting commands do not all have the same availability or permission requirements. In interviews and production environments, mention the prerequisite when a command depends on an installed package, elevated privileges, or a specific environment.

## 1. Commands That May Require Additional Packages

Some useful troubleshooting commands may not be installed on a minimal Linux installation.

| Command    | Usually Provided By | May Require Installation? | Purpose                        |
| ---------- | ------------------- | ------------------------: | ------------------------------ |
| `iostat`   | `sysstat`           |                       Yes | Disk/CPU I/O                   |
| `sar`      | `sysstat`           |                       Yes | Historical system statistics   |
| `mpstat`   | `sysstat`           |                       Yes | Per-CPU statistics             |
| `iotop`    | `iotop`             |                       Yes | Process-level I/O              |
| `htop`     | `htop`              |                       Yes | Interactive process monitoring |
| `lsof`     | `lsof`              |                       Yes | Open files/processes           |
| `lsscsi`   | `lsscsi`            |                       Yes | SCSI device information        |
| `smartctl` | `smartmontools`     |                       Yes | Disk health information        |
| `pstree`   | `psmisc`            |                       Yes | Process hierarchy              |

### Check Whether a Command Exists

```bash
command -v iostat
```

or:

```bash
which iostat
```

Preferred:

```bash
command -v iostat
```

If there is no output, the command may not be installed or may not be in the current `PATH`.

---

# 2. `sysstat` Commands

Commands such as:

```bash
iostat
sar
mpstat
```

are commonly provided by the **`sysstat`** package.

Check:

```bash
rpm -q sysstat
```

On RHEL-based systems:

```bash
dnf install sysstat
```

### Important Limitation

Installing `sysstat` does not automatically mean historical data is already available.

For example:

```bash
sar -u
```

may have limited or no historical information if data collection was not previously configured/running.

Therefore:

```text
sar = historical data only if collection exists
```

### Interview Tip

> "I use `sar` for historical analysis, but I first verify that `sysstat` is installed and that historical collection was enabled."

---

# 3. `iotop` Prerequisites

`iotop` provides process-level I/O information.

Example:

```bash
iotop
```

It may require:

* Installation of the `iotop` package
* Root/sudo privileges for complete information
* Kernel support for the required accounting information

Run with appropriate privileges when necessary:

```bash
sudo iotop
```

### Limitation

`iotop` is useful for identifying processes generating I/O, but it should be correlated with:

```bash
iostat
vmstat
application metrics
```

Do not use `iotop` alone to conclude that a disk is faulty.

---

# 4. `lsof` Prerequisites

`lsof` is useful for identifying files opened by processes.

Example:

```bash
lsof +L1
```

It is especially useful for finding:

```text
Deleted file
      ↓
Still open by process
      ↓
Disk space not released
```

### Installation

```bash
dnf install lsof
```

### Permission

Some process/file information may require:

```bash
sudo lsof
```

### Limitation

`lsof` output can be large on busy systems.

Use targeted commands when possible:

```bash
lsof -p PID
```

or:

```bash
lsof +L1
```

---

# 5. `smartctl` Prerequisites

`smartctl` is provided by:

```text
smartmontools
```

Install:

```bash
dnf install smartmontools
```

Check disk information:

```bash
smartctl -a /dev/sda
```

### Important Limitations

SMART information depends on the storage environment.

It may be limited or unavailable for:

* Some virtual disks
* Certain RAID controllers
* SAN storage
* Cloud block storage

Therefore, if the server uses cloud/SAN/virtual storage, also check the underlying storage platform.

### Interview Tip

> "I use `smartctl` when the storage device exposes SMART information. For virtual, SAN, or cloud storage, I also investigate the underlying storage layer."

---

# 6. `lsscsi` Prerequisites

`lsscsi` is useful for SCSI troubleshooting:

```bash
lsscsi
```

It may require:

```bash
dnf install lsscsi
```

### Limitation

Not every storage device will appear as a simple physical SCSI disk. Virtualized and cloud environments may abstract the underlying storage.

Therefore also check:

```bash
lsblk
fdisk -l
dmesg
```

---

# 7. `top` Does Not Usually Require Installation

`top` is normally available on Linux systems.

```bash
top
```

Useful shortcuts:

```text
P → Sort by CPU
M → Sort by memory
H → Threads
1 → Individual CPU statistics
```

### Important CPU Limitation

Process CPU percentage can exceed `100%` on multi-core systems.

Example:

```text
%CPU = 400%
```

approximately means the process is using:

```text
4 logical CPUs
```

Use:

```bash
nproc
```

to check the number of available logical CPUs.

---

# 8. `free` Does Not Show the Complete Memory Picture

```bash
free -h
```

is normally available and does not require a special package.

However, do not judge memory health using only:

```text
free
```

Also check:

```text
available
swap
vmstat
OOM events
```

Example:

```bash
free -h
vmstat 1
```

### Important

Low `free` memory can be normal because Linux uses RAM for cache.

---

# 9. `vmstat` Limitations

```bash
vmstat 1
```

is useful for a quick system overview.

It shows:

* Processes
* Memory
* Swap
* I/O
* CPU

### Important

`vmstat` provides system-level information. It does not directly identify the exact application responsible for the problem.

Use:

```bash
ps
top
iotop
```

for process-level investigation.

---

# 10. `journalctl` Prerequisite

`journalctl` is used with systems running **systemd**.

Example:

```bash
journalctl -u nginx
```

Kernel logs:

```bash
journalctl -k
```

### Limitation

If the required logs are not available or have already been rotated/removed, `journalctl` may not provide historical information.

Also, not every application logs exclusively to `journald`.

Check application-specific logs when required.

---

# 11. `systemctl` Prerequisite

`systemctl` is used to manage and inspect systemd services.

Example:

```bash
systemctl status nginx
```

### Limitation

It is not applicable to every Linux environment.

For example, a container may not run systemd as PID 1.

Inside containers, use the container runtime or orchestration platform:

```bash
docker ps
docker logs <container>
```

or:

```bash
kubectl get pods
kubectl logs <pod>
```

---

# 12. Commands Requiring Root/Sudo

Some commands may require elevated privileges depending on the operation and system configuration.

Examples:

```bash
sudo iotop
sudo lsof
sudo smartctl -a /dev/sda
sudo dmesg
sudo mount
sudo lvextend
sudo pvcreate
```

### Important

Do not automatically run every troubleshooting command with `sudo`.

Use the minimum required privilege.

---

# 13. Commands That Depend on the Environment

Some troubleshooting commands depend on whether you are working on:

```text
Physical Server
VMware/KVM/Xen VM
Cloud VM
Docker Container
Kubernetes Pod
Bare-metal Server
SAN/NFS Storage
```

For example:

```text
CPU steal time
```

is particularly relevant to virtual machines.

Similarly:

```text
smartctl
```

may not provide useful physical-disk information from inside a VM.

And:

```text
systemctl
```

may not work as expected inside a container.

---

# 🎯 Interview Rule: Mention the Limitation

Instead of saying:

> "`iostat` checks disk performance."

A stronger interview answer is:

> "`iostat` checks disk and CPU I/O statistics. If it is not installed, it is normally provided by the `sysstat` package. I also correlate its output with `vmstat`, process-level I/O, and application metrics."

Instead of:

> "`smartctl` checks disk health."

Say:

> "`smartctl` can check SMART information when the underlying storage exposes it. In VMs, SANs, RAID environments, or cloud storage, I may need to use the infrastructure/storage platform's monitoring instead."

# ⭐ Production Rule

Before using a troubleshooting command, ask:

```text
1. Is the command installed?
2. Do I have permission?
3. Does it apply to this OS/environment?
4. Does it require a specific package/service?
5. Does it provide current or historical data?
6. Could the command modify production?
7. Do I need to correlate it with another metric?
```

This prevents a common production mistake:

```text
Command Output
      ↓
Immediate Conclusion
      ↓
Wrong Diagnosis
```

The correct approach is:

```text
Command Output
      ↓
Validate Context
      ↓
Correlate Metrics
      ↓
Identify Root Cause
      ↓
```
