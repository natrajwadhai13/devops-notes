# 22. Systemd & Service Management Troubleshooting

> **systemd** is the service and system manager used by many modern Linux distributions. It manages services, startup targets, dependencies, timers, sockets, mounts, and other units. In production, `systemctl` and `journalctl` are two of the most important tools for troubleshooting service failures.

# Q226. What is systemd and what is a systemd unit?

## Answer

**systemd** is a system and service manager used by many modern Linux distributions.

It is responsible for managing:

```text id="8f7m2x"
Services
Processes
Boot targets
Dependencies
Timers
Sockets
Mounts
Devices
```

### Common systemd Command

```bash
systemctl
```

### What is a Unit?

A **unit** is a resource managed by systemd.

Common unit types:

| Unit         | Purpose                       |
| ------------ | ----------------------------- |
| `.service`   | Service/process               |
| `.target`    | Group of units / system state |
| `.timer`     | Scheduled task                |
| `.socket`    | Socket activation             |
| `.mount`     | Filesystem mount              |
| `.automount` | Automatic mount               |
| `.path`      | Path-based activation         |
| `.device`    | Device                        |
| `.swap`      | Swap device/file              |

### Example

A service unit:

```text id="z5n2j7"
nginx.service
```

A timer:

```text id="q7v9m4"
backup.timer
```

### Service Relationship

```text id="0d4s9c"
systemd
   |
   +-- nginx.service
   +-- sshd.service
   +-- chronyd.service
   +-- docker.service
   +-- backup.timer
```

### Check Running Units

```bash id="9n8x5w"
systemctl list-units
```

### Check Service Units

```bash id="2j6p8z"
systemctl list-units --type=service
```

### Interview Tip

> "systemd is the system and service manager on many modern Linux systems. It manages units such as services, targets, timers, sockets, mounts, and devices."

# Q227. How do you check the status of a systemd service?

## Answer

Use:

```bash id="6x9q3v"
systemctl status nginx
```

Example:

```text id="4r8k2m"
● nginx.service
   Loaded: loaded
   Active: active (running)
   Main PID: 1234
```

### Important Status Values

```text id="k7m1x4"
active (running)
active (exited)
inactive
failed
activating
deactivating
```

### Check Whether Service Is Active

```bash id="8w3p5n"
systemctl is-active nginx
```

### Check Whether Service Starts at Boot

```bash id="m4z7q2"
systemctl is-enabled nginx
```

### Check Service Unit File

```bash id="c8v2y6"
systemctl cat nginx
```

### Show Service Properties

```bash id="f5n9r3"
systemctl show nginx
```

For example:

```bash id="j2k8x1"
systemctl show nginx -p ActiveState -p SubState -p MainPID
```

### Check Failed Services

```bash id="3q7w5m"
systemctl --failed
```

### Interview Tip

> "I normally start with `systemctl status <service>`. Then I check `is-active`, `is-enabled`, the unit definition, and `systemctl --failed` when investigating broader system issues."

# Q228. How do you troubleshoot a service that fails to start?

## Answer

Do not repeatedly restart the service.

First identify the exact failure.

### Step 1: Check Status

```bash id="5c8y2k"
systemctl status myapp
```

### Step 2: Check Logs

```bash id="3j7n5v"
journalctl -u myapp
```

Recent logs:

```bash id="q6m2w9"
journalctl -u myapp -n 100
```

### Step 3: Check Configuration

Inspect the unit:

```bash id="8x1p4r"
systemctl cat myapp
```

Check effective properties:

```bash id="7k5m2q"
systemctl show myapp
```

### Step 4: Validate Application Configuration

If the application provides a configuration test, use it.

For example, an application may provide:

```bash
application --test-config
```

The exact command depends on the service.

### Step 5: Check Port Conflicts

```bash id="1n8q6x"
ss -lntup
```

If another process already owns the required port, the service may fail.

### Step 6: Check Files and Permissions

```bash id="9p3v7k"
ls -l /path/to/config
```

Check path permissions:

```bash
namei -l /path/to/config
```

### Step 7: Check Resources

```bash id="2w6m8c"
df -h
```

```bash id="5y1q9z"
free -h
```

### Step 8: Check Dependencies

```bash id="7c4x2m"
systemctl list-dependencies myapp
```

### Step 9: Check Recent Changes

Investigate:

```text id="r6n8v1"
Configuration
Package update
Certificate
Permissions
Network
Dependency service
Kernel
Deployment
```

### Common Causes

```text id="j5p2w7"
Configuration error
Port already in use
Missing file
Permission denied
Dependency unavailable
Certificate problem
Disk full
Memory shortage
Wrong environment variable
SELinux denial
```

### Interview Tip

> "For a failed service, I check `systemctl status`, service-specific journal logs, configuration, dependencies, ports, permissions, resources, and recent changes. I avoid repeated restarts before identifying the cause."

# Q229. How do you troubleshoot a service that keeps restarting?

## Answer

A restart loop usually means the service starts and then exits or crashes.

### Step 1: Check Status

```bash id="8y3m1v"
systemctl status myapp
```

Look for:

```text id="r9k4x7"
activating
failed
restart counter
```

### Step 2: Check Logs

```bash id="9p7c2x"
journalctl -u myapp -n 200
```

Follow:

```bash id="f3k6m8"
journalctl -u myapp -f
```

### Step 3: Check Restart Policy

```bash id="j5n8q4"
systemctl show myapp -p Restart -p RestartSec -p NRestarts
```

### Step 4: Check Unit Configuration

```bash id="m8v2c5"
systemctl cat myapp
```

Look for:

```text id="x7p4q1"
ExecStart
Restart
RestartSec
User
Environment
WorkingDirectory
```

### Step 5: Check Process

```bash id="k6q9w3"
pgrep -af myapp
```

### Step 6: Check Port

```bash id="5w8r2n"
ss -lntp
```

### Step 7: Check Resources

```bash id="z4x7m2"
free -h
df -h
```

Check OOM messages:

```bash id="n3q5v8"
journalctl -k | grep -Ei "oom|out of memory|killed process"
```

### Common Causes

```text id="m9k2c7"
Application crash
Bad configuration
Missing dependency
Port conflict
Permission issue
Environment variable missing
Certificate problem
Out-of-memory kill
SELinux denial
Incorrect ExecStart
```

### Important

A restart loop can make an incident worse by:

```text id="q8y1w5"
Repeated process creation
CPU consumption
Log growth
Connection attempts
Dependency load
```

### Interview Tip

> "For a restart loop, I check the service logs, restart policy, exit behavior, configuration, dependencies, ports, resources, and OOM/SELinux evidence. I don't treat repeated restarts as the fix."

# Q230. How do you check systemd service logs?

## Answer

The primary command is:

```bash id="6v8x3m"
journalctl -u nginx
```

### Last 100 Entries

```bash id="j4n7p2"
journalctl -u nginx -n 100
```

### Follow Logs

```bash id="2x6m9q"
journalctl -u nginx -f
```

### Current Boot

```bash id="4p8w1z"
journalctl -u nginx -b
```

### Previous Boot

```bash id="7k3v5n"
journalctl -u nginx -b -1
```

### Specific Time

```bash id="9m2q6x"
journalctl -u nginx --since "30 minutes ago"
```

### Errors

```bash id="5x7p4c"
journalctl -u nginx -p err
```

### Search Logs

```bash id="8q1n6v"
journalctl -u nginx | grep -Ei "error|failed|denied|timeout"
```

### Check Journal Disk Usage

```bash id="3z5m8r"
journalctl --disk-usage
```

### Important

A service may also write logs outside journald:

```text id="n4x7p2"
/var/log/
/opt/application/logs/
stdout/stderr
Remote logging system
```

Therefore:

```text id="x8q2m5"
journalctl
    +
Application logs
```

may both be required.

### Interview Tip

> "For systemd-managed services, I use `journalctl -u <service>`, filtering by boot, time, severity, and keywords. If the application has its own log files, I correlate those with the journal."

# Q231. What is the difference between start, stop, restart, reload, enable, and disable?

## Answer

These commands perform different operations.

### `start`

Starts a stopped service:

```bash id="6p2w8n"
systemctl start nginx
```

### `stop`

Stops a running service:

```bash id="7k4x9m"
systemctl stop nginx
```

### `restart`

Stops and starts the service:

```bash id="8n3q6v"
systemctl restart nginx
```

This can interrupt active connections depending on the application.

### `reload`

Asks the service to reload configuration without fully stopping the service:

```bash id="5m9x2k"
systemctl reload nginx
```

This only works if the service supports reload.

### `enable`

Configures the service to start automatically according to its systemd installation/dependency setup:

```bash id="2q7w5p"
systemctl enable nginx
```

### `disable`

Prevents the service from being automatically enabled for boot:

```bash id="4x8n1m"
systemctl disable nginx
```

### Enable and Start

```bash id="9v3k6q"
systemctl enable --now nginx
```

### Disable and Stop

```bash id="7m2p5x"
systemctl disable --now nginx
```

### Simple Comparison

| Command         | Purpose                           |
| --------------- | --------------------------------- |
| `start`         | Start now                         |
| `stop`          | Stop now                          |
| `restart`       | Stop + start now                  |
| `reload`        | Reload configuration if supported |
| `enable`        | Configure automatic startup       |
| `disable`       | Disable automatic startup         |
| `enable --now`  | Enable + start                    |
| `disable --now` | Disable + stop                    |

### Important

```text id="0c6v9x"
enable ≠ start
disable ≠ stop
reload ≠ restart
```

### Interview Tip

> "`start` and `stop` affect the current service state. `enable` and `disable` affect automatic startup. `reload` applies configuration without a full restart when supported, while `restart` actually restarts the service."

# Q232. How do you troubleshoot systemd service dependencies and startup order?

## Answer

Services often depend on other services, mounts, network availability, or targets.

Example:

```text id="j8w4p1"
Application
    |
    +-- Database
    +-- Network
    +-- Filesystem
```

If the dependency is unavailable, the application may fail.

### Step 1: Check Dependencies

```bash id="4z6m2x"
systemctl list-dependencies myapp
```

### Reverse Dependencies

```bash id="7q3n8v"
systemctl list-dependencies --reverse myapp
```

### Step 2: Inspect Unit

```bash id="5p8x1m"
systemctl cat myapp
```

Look for:

```text id="3m7v9q"
Requires=
Wants=
After=
Before=
```

### Difference

`After=` controls ordering.

It does **not by itself mean** the other unit must be successfully running.

For example:

```text id="2q8k5v"
After=network-online.target
```

means the service should start after that target in the dependency ordering.

### `Requires=`

This creates a stronger dependency relationship.

Example:

```text id="5n1x7p"
Requires=database.service
```

### `Wants=`

A weaker dependency relationship:

```text id="8m4q2z"
Wants=database.service
```

### Step 3: Check Failed Dependencies

```bash id="1v6p8k"
systemctl --failed
```

### Step 4: Check Target

```bash id="3x7n2m"
systemctl get-default
```

### Step 5: Check Boot Order

```bash id="9q5m4v"
systemd-analyze
```

For a detailed critical path:

```bash id="7k1x8p"
systemd-analyze critical-chain
```

### Interview Tip

> "For systemd dependency problems, I use `systemctl list-dependencies`, inspect `Requires=`, `Wants=`, `After=`, and `Before=`, check failed units, and use `systemd-analyze critical-chain` to understand boot ordering."

# Q233. How do you troubleshoot a service that starts manually but not after reboot?

## Answer

This usually indicates a startup configuration, dependency, environment, or ordering issue.

### Step 1: Check Enable Status

```bash id="1r5x7m"
systemctl is-enabled myapp
```

If appropriate:

```bash id="5q8v2n"
systemctl enable myapp
```

### Step 2: Check Previous Boot Logs

After the system comes up:

```bash id="7m4x1p"
journalctl -u myapp -b -1
```

### Step 3: Check Service Status

```bash id="8n2q6v"
systemctl status myapp
```

### Step 4: Check Dependencies

```bash id="3k7p9m"
systemctl list-dependencies myapp
```

### Step 5: Check Ordering

Inspect:

```bash id="4x1m8q"
systemctl cat myapp
```

Look for:

```text id="q7v3n5"
After=
Before=
Requires=
Wants=
```

### Step 6: Check Environment

A service started by systemd does not necessarily have the same environment as your interactive shell.

Check:

```bash id="6p8x2m"
systemctl show myapp -p Environment -p User -p WorkingDirectory
```

### Step 7: Check Mounts

If the application requires a filesystem:

```bash id="0m5q7x"
findmnt
```

The mount may not be available when the service starts.

### Step 8: Check Network Dependencies

Some applications need network connectivity or DNS before starting.

### Common Causes

```text id="v6k1p9"
Service not enabled
Dependency unavailable
Wrong startup order
Mount unavailable
Network unavailable
Environment missing
Permissions
Configuration issue
Race condition
```

### Interview Tip

> "If a service works manually but fails after reboot, I check whether it is enabled, inspect the previous boot logs, verify dependencies and ordering, check required mounts/network, and compare the systemd environment with the interactive environment."

# Q234. How do you troubleshoot systemd targets, boot problems, and failed units?

## Answer

A **target** represents a system state or grouping of units.

Examples include:

```text id="8q4m1x"
multi-user.target
graphical.target
rescue.target
emergency.target
```

### Check Default Target

```bash id="3m7p8v"
systemctl get-default
```

### List Targets

```bash id="5x2n9q"
systemctl list-units --type=target
```

### Check Target Status

```bash id="7k4p1m"
systemctl status multi-user.target
```

### Check Failed Units

```bash id="2q8v6x"
systemctl --failed
```

### Check Boot Time

```bash id="9m3p5k"
systemd-analyze
```

Example:

```text id="6x1q8v"
Startup finished in ...
```

### Check Critical Chain

```bash id="4p7n2m"
systemd-analyze critical-chain
```

This helps identify units delaying boot.

### Check Specific Unit

```bash id="8v5m1q"
systemctl status myapp
```

### Check Unit Dependencies

```bash id="0q6x9p"
systemctl list-dependencies myapp
```

### Check Previous Boot

```bash id="7n4m2x"
journalctl -b -1
```

Kernel:

```bash id="3p8v5k"
journalctl -k -b -1
```

### Emergency/Rescue Modes

Linux can boot into recovery-oriented targets such as:

```text id="q9m2x6"
rescue.target
emergency.target
```

These should be used carefully, especially on production systems.

### Interview Tip

> "For systemd boot problems, I check the default target, failed units, boot journal, and `systemd-analyze critical-chain`. This helps identify whether a service or dependency is delaying or preventing the expected system state."

# Q235. How do you troubleshoot a production service failure using systemd?

## Answer

I use an **evidence-first** approach.

### Step 1: Confirm the Impact

Determine:

```text id="2w8q4m"
One service?
Multiple services?
All users?
One server?
Multiple servers?
```

### Step 2: Check Service Status

```bash id="7m3p9x"
systemctl status myapp
```

### Step 3: Check Service Logs

```bash id="5x8q2n"
journalctl -u myapp -n 200
```

If the issue is time-specific:

```bash id="9p4m7v"
journalctl -u myapp --since "30 minutes ago"
```

### Step 4: Check Failed Units

```bash id="6q1x5m"
systemctl --failed
```

### Step 5: Check Dependencies

```bash id="8v3n2p"
systemctl list-dependencies myapp
```

### Step 6: Check Application Resources

```bash id="4m7q9x"
df -h
```

```bash id="2n5v8k"
free -h
```

```bash id="1x6p3m"
uptime
```

### Step 7: Check Network/Port

```bash id="5q9m2v"
ss -lntup
```

### Step 8: Check Configuration

```bash id="7x4p1n"
systemctl cat myapp
```

If supported by the application, validate its configuration.

### Step 9: Check Security

```bash id="9m6q3x"
getenforce
```

Check SELinux AVCs if applicable:

```bash id="4v8p2k"
ausearch -m AVC -ts recent
```

### Step 10: Check Recent Changes

Investigate:

```text id="6p2x9m"
Deployment
Configuration
Package update
Certificate
Permissions
Dependency
Kernel
Network
```

### Step 11: Apply the Minimum Safe Fix

Possible actions:

```text id="1q7m4x"
Correct configuration
Restore dependency
Correct permissions
Free required disk space
Fix certificate
Correct environment
Restart service
Rollback recent change
```

Do not automatically restart repeatedly.

### Step 12: Verify

```bash id="8m5x2q"
systemctl is-active myapp
```

Then verify:

```text id="5v9p1n"
Process
   |
   v
Port
   |
   v
Dependency
   |
   v
Application
   |
   v
User functionality
```

### Production Scenario

**Interviewer:**

> "A critical production service is down. How will you troubleshoot it?"

**Strong Answer:**

> "First I will confirm the impact and check `systemctl status` for the service. Then I will inspect `journalctl -u <service>` around the failure time and check whether other units have failed. I will verify dependencies, configuration, ports, disk and memory, network connectivity, SELinux, and recent changes. I will identify the root cause before making a change. If a restart is required, I will perform it in a controlled way and then verify the process, port, dependencies, and application functionality."

# 🎤 Systemd Interview Golden Rules

```text id="4m8q2x"

Service active ≠ application healthy
enable ≠ start
disable ≠ stop
reload ≠ restart
After= ≠ dependency requirement
Requires= ≠ simple ordering
Journal logs ≠ all application logs
Manual start works ≠ boot startup will work
Restart loop ≠ problem solved
```

### ⚠️ Production Safety Rules

Before changing a production systemd service:

```text id="5q8m1x"
1. Confirm the affected service
2. Check systemctl status
3. Read service-specific journal logs
4. Check failed dependencies
5. Check the unit configuration
6. Check ports and processes
7. Check disk and memory
8. Check security controls
9. Check recent changes
10. Avoid repeated blind restarts
11. Prefer reload when supported and appropriate
12. Make controlled and reversible changes
13. Consider application impact before restart
14. Verify service and application health
15. Check for recurrence
16. Document the root cause
```

> **Interview mindset:** Do not say, "The service is down, so I will restart it." Say, "I will first check `systemctl status` and `journalctl -u`, identify the exact failure, verify dependencies, configuration, resources, ports, and recent changes, then apply the smallest safe fix and verify the complete application path."
