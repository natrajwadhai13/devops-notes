# Q346. What is Apache HTTP Server and how do you check whether it is running?

## Answer

**Apache HTTP Server** is an open-source web server used to serve HTTP/HTTPS traffic.

It can also provide:

```text id="3u5q7m"
Web Server
Reverse Proxy
SSL/TLS Termination
Virtual Hosting
Static File Serving
Application Gateway
```

### Common Architecture

```text id="8m2x5q"
Client
   |
   | HTTP/HTTPS
   v
 Apache
   |
   +---- Static Files
   |
   +---- Reverse Proxy
             |
             v
        Application
```

### Apache Service Names

On many RHEL-based systems:

```bash id="x7m3q2"
systemctl status httpd
```

On Debian/Ubuntu:

```bash id="p5m8x4"
systemctl status apache2
```

### Step 1: Check Service

RHEL-based:

```bash id="m4x7q2"
systemctl is-active httpd
```

Debian/Ubuntu:

```bash id="q8m2x5"
systemctl is-active apache2
```

### Step 2: Check Process

```bash id="x3m7q2"
pgrep -a httpd
```

or:

```bash id="p7m2x4"
pgrep -a apache2
```

### Step 3: Check Listening Ports

```bash id="m8x2q5"
ss -lntp | grep -E ':80|:443'
```

### Step 4: Test Locally

```bash id="x5m7q2"
curl -v http://127.0.0.1
```

For HTTPS:

```bash id="q3m8x4"
curl -vk https://127.0.0.1
```

### Step 5: Check Configuration

RHEL-style:

```bash id="m7x2q5"
apachectl -t
```

Debian/Ubuntu may also provide:

```bash id="p4m8x2"
apache2ctl -t
```

### Step 6: Check Logs

RHEL-style locations commonly include:

```bash id="x8m3q2"
tail -f /var/log/httpd/error_log
```

Debian/Ubuntu commonly:

```bash id="q5m7x2"
tail -f /var/log/apache2/error.log
```

Systemd:

```bash id="m2x8q4"
journalctl -u httpd
```

or:

```bash id="p7m3x5"
journalctl -u apache2
```

### Important

```text id="8m3q7x"
Apache process running
       ≠
Website healthy
```

### Interview Tip

> "I check the Apache service, processes, listening ports, configuration syntax, local HTTP response, and access/error logs."

# Q347. How do you troubleshoot when Apache fails to start?

## Answer

Do not repeatedly restart Apache.

First identify the exact error.

### Step 1: Check Service Status

RHEL-based:

```bash id="x5m8q2"
systemctl status httpd
```

Debian/Ubuntu:

```bash id="p7m3x4"
systemctl status apache2
```

### Step 2: Check Systemd Logs

```bash id="m4x7q2"
journalctl -u httpd -n 100
```

or:

```bash id="q8m2x5"
journalctl -u apache2 -n 100
```

### Step 3: Test Configuration

```bash id="x3m8q2"
apachectl -t
```

or:

```bash id="p5m7x4"
apache2ctl -t
```

Possible output:

```text id="7m2x5q"
Syntax OK
```

or an error showing the configuration file and line.

### Step 4: Check Port Conflicts

```bash id="m8x3q2"
ss -lntp | grep -E ':80|:443'
```

Another service may already be using the required port.

### Step 5: Check Included Configuration

Apache can load configuration from multiple files.

Check effective configuration:

```bash id="x7m2q5"
apachectl -S
```

On some systems:

```bash id="p4m8x2"
apachectl -t -D DUMP_RUN_CFG
```

### Step 6: Check Certificate Files

If HTTPS is configured:

```bash id="m5x8q2"
ls -l /path/to/certificate
```

```bash id="q7m3x4"
ls -l /path/to/private-key
```

### Step 7: Check Permissions

```bash id="x8m2q5"
namei -l /path/to/certificate
```

### Step 8: Check Disk Space

```bash id="p5m7x2"
df -h
```

```bash id="m3x8q4"
df -i
```

### Common Causes

```text id="7q2m5x"
Configuration syntax error
Port already in use
Missing configuration file
Missing certificate
Incorrect certificate path
Permission problem
Missing Apache module
Disk full
SELinux restriction
Incorrect VirtualHost configuration
```

### Safe Flow

```text id="x8m3q2"
Apache failed
     |
     v
systemctl status
     |
     v
journalctl
     |
     v
apachectl -t
     |
     +---- FAIL ----> Fix configuration
     |
     +---- PASS
            |
            v
     Check ports/files/
     permissions/resources
            |
            v
       Start Apache
            |
            v
          Verify
```

### Interview Tip

> "I first check `systemctl status`, `journalctl`, and `apachectl -t`. Then I investigate port conflicts, certificates, modules, permissions, disk space, SELinux, and VirtualHost configuration."

# Q348. How do you troubleshoot Apache configuration errors?

## Answer

Apache configuration can be split across many files.

### Step 1: Test Syntax

```bash id="p4x7m2"
apachectl -t
```

Possible output:

```text id="7m3x8q"
Syntax OK
```

### Step 2: Check Virtual Hosts

```bash id="m8x2q5"
apachectl -S
```

This helps identify:

```text id="x5m7q2"
VirtualHost
ServerName
ServerAlias
Listening address
Configuration file
```

### Step 3: Inspect Loaded Modules

```bash id="q3m8x2"
apachectl -M
```

A missing module can cause configuration or application problems.

### Step 4: Check Configuration Files

Common locations include:

RHEL-based:

```text id="7m2x5q"
/etc/httpd/conf/httpd.conf
/etc/httpd/conf.d/
```

Debian/Ubuntu:

```text id="m8x3q2"
/etc/apache2/apache2.conf
/etc/apache2/sites-enabled/
/etc/apache2/sites-available/
```

Exact layout depends on distribution and installation.

### Step 5: Check Common Errors

```text id="x4m7q2"
Syntax error
Invalid directive
Missing module
Wrong path
Duplicate VirtualHost
Wrong ServerName
Wrong DocumentRoot
Incorrect proxy configuration
Incorrect SSL configuration
```

### Step 6: Validate After Change

```bash id="p5m8x2"
apachectl -t
```

Only apply the change after the configuration test succeeds.

### Step 7: Reload When Appropriate

```bash id="m7x3q4"
systemctl reload httpd
```

or:

```bash id="x8m2q5"
systemctl reload apache2
```

Then verify:

```bash id="q4x7m2"
systemctl status httpd
```

### Important

Do not edit generated/runtime configuration blindly.

Always identify the actual configuration source that controls the behavior.

### Interview Tip

> "I use `apachectl -t` for syntax validation, `apachectl -S` to understand VirtualHosts, and `apachectl -M` to verify required modules."

# Q349. How do you troubleshoot Apache 403 Forbidden errors?

## Answer

A 403 means access is being denied, but the exact cause can be at multiple layers.

### Step 1: Check Apache Error Log

RHEL:

```bash id="m3x7q2"
tail -f /var/log/httpd/error_log
```

Debian/Ubuntu:

```bash id="p8m2x4"
tail -f /var/log/apache2/error.log
```

### Step 2: Check File Permissions

```bash id="x5m8q2"
ls -l /var/www/html/index.html
```

### Step 3: Check Directory Traversal

```bash id="q7m3x4"
namei -l /var/www/html/index.html
```

Apache needs appropriate permissions to traverse parent directories and read the resource.

### Step 4: Check Apache Access Rules

Inspect:

```bash id="m8x2q5"
apachectl -S
```

Then review the relevant VirtualHost/directory configuration.

Look for directives such as:

```text id="x3m7q2"
Require all denied
Require ip
Require all granted
```

### Step 5: Check Directory Listing

If requesting a directory without an index file, Apache may return 403 when directory listing is disabled.

Check:

```text id="p5m8x2"
DirectoryIndex
Options Indexes
```

### Step 6: Check SELinux

```bash id="m4x7q2"
getenforce
```

Check file context:

```bash id="x8m3q5"
ls -Z /var/www/html/index.html
```

If relevant:

```bash id="q5m7x2"
ausearch -m AVC -ts recent
```

### Step 7: Check DocumentRoot

```bash id="p4m8x2"
apachectl -S
```

Verify the request is reaching the expected VirtualHost and document root.

### Common Causes

```text id="7m3x8q"
File permissions
Directory permissions
Apache Require rules
SELinux
Wrong DocumentRoot
Missing DirectoryIndex
IP restrictions
Application authorization
```

### Important

Do not immediately:

```bash id="x2m8q5"
chmod -R 777 /var/www/html
```

This can create a security problem without fixing the root cause.

### Interview Tip

> "For 403 I check Apache access rules, file and directory permissions, VirtualHost configuration, SELinux context, and whether the requested resource requires directory indexing or authorization."

# Q350. How do you troubleshoot Apache 404 Not Found errors?

## Answer

A 404 means the requested resource was not found, but the response can come from Apache or the application.

### Step 1: Reproduce

```bash id="m7x2q4"
curl -v http://example.com/test
```

### Step 2: Check Access Log

```bash id="x5m8q2"
tail -f /var/log/httpd/access_log
```

or:

```bash id="p7m3x4"
tail -f /var/log/apache2/access.log
```

### Step 3: Check DocumentRoot

```bash id="m3x8q2"
apachectl -S
```

### Step 4: Check the Requested File

```bash id="q8m2x5"
ls -l /var/www/html/test
```

### Step 5: Check VirtualHost

Verify:

```text id="x7m3q2"
ServerName
ServerAlias
DocumentRoot
Directory
RewriteRule
```

### Step 6: Check URL Rewriting

Applications commonly use rewrite rules.

Check loaded rewrite module:

```bash id="p5m8x2"
apachectl -M | grep rewrite
```

### Step 7: Check `.htaccess`

If the application uses `.htaccess`:

```bash id="m4x7q2"
find /var/www/html -name .htaccess -ls
```

Review rules carefully.

### Step 8: Determine Who Generated the 404

A 404 may come from:

```text id="8m3x7q"
Apache
Reverse Proxy
Application
Framework
```

Look at:

```text id="x5q2m7"
Response headers
Access logs
Application logs
```

### Common Causes

```text id="p8m3x2"
Wrong URL
Wrong VirtualHost
Wrong DocumentRoot
Missing file
Rewrite rule
Application route
Deployment problem
```

### Interview Tip

> "For 404 I verify the requested URL, VirtualHost, DocumentRoot, rewrite rules, file existence, and whether Apache or the application generated the response."

# Q351. How do you troubleshoot Apache 500, 502, 503, and 504 errors?

## Answer

First identify which component generated the response.

## HTTP 500

Usually indicates an internal server/application error.

Check:

```bash id="m5x8q2"
tail -f /var/log/httpd/error_log
```

or:

```bash id="p7m3x4"
tail -f /var/log/apache2/error.log
```

Investigate:

```text id="x8m2q5"
Application
PHP/CGI
Permissions
Modules
Configuration
Dependencies
```

---

## HTTP 502

Common when Apache is acting as a reverse proxy and cannot communicate correctly with the upstream.

Check:

```text id="m3x7q2"
Backend IP
Backend port
Backend listener
Proxy configuration
Network
Firewall
TLS to upstream
```

Test:

```bash id="q5m8x2"
curl -v http://<backend-ip>:8080
```

---

## HTTP 503

Often indicates the service/backend is unavailable.

Check:

```text id="x7m3q2"
Backend health
Application service
Connection limits
Application overload
Maintenance
Proxy configuration
```

---

## HTTP 504

Usually indicates an upstream timeout.

Check:

```text id="p4m8x2"
Backend response time
Application
Database
External API
Proxy timeout
Network
```

### Check Apache Proxy Configuration

```bash id="m8x3q2"
apachectl -S
```

Also inspect the relevant configuration for directives such as:

```text id="q7m2x5"
ProxyPass
ProxyPassReverse
ProxyTimeout
```

### Common Model

```text id="x3m8q2"
Client
  |
  v
Apache
  |
  +---- 500 → Apache/Application
  |
  +---- 502 → Upstream communication
  |
  +---- 503 → Service unavailable
  |
  +---- 504 → Upstream timeout
```

These are general troubleshooting directions, not absolute meanings.

### Interview Tip

> "For Apache 5xx errors, I identify the component generating the response, then inspect Apache error logs, upstream connectivity, application health, resources, and timeout configuration."

# Q352. How do you troubleshoot Apache SSL/TLS certificate problems?

## Answer

Apache commonly terminates HTTPS on port 443.

### Step 1: Test HTTPS

```bash id="7m2x5q"
curl -v https://example.com
```

### Step 2: Inspect TLS

```bash id="m8x3q2"
openssl s_client -connect example.com:443 -servername example.com
```

### Step 3: Check Certificate Dates

```bash id="p5m7x4"
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates
```

### Step 4: Check SAN

```bash id="x4m8q2"
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
```

### Step 5: Check Apache SSL Configuration

Search effective configuration:

```bash id="q7m3x5"
apachectl -S
```

Then inspect the relevant VirtualHost for directives such as:

```text id="m2x8q4"
SSLEngine on
SSLCertificateFile
SSLCertificateKeyFile
SSLCertificateChainFile
```

The exact certificate-chain configuration depends on Apache version and deployment method.

### Step 6: Check Certificate Files

```bash id="p8m3x2"
ls -l /path/to/certificate
```

```bash id="x5m7q2"
ls -l /path/to/private-key
```

### Step 7: Check Key/Certificate Match

You can compare public-key information from the certificate and private key using appropriate OpenSSL commands.

### Step 8: Check SNI

For multiple HTTPS VirtualHosts:

```bash id="m7x3q4"
openssl s_client -connect <server-ip>:443 -servername example.com
```

### Step 9: Check Time

```bash id="q4m8x2"
timedatectl
```

### Step 10: Validate Apache Configuration

```bash id="x8m2q5"
apachectl -t
```

### Common Causes

```text id="m5x7q2"
Expired certificate
Wrong certificate
Hostname mismatch
Missing chain/intermediate
Wrong VirtualHost
SNI issue
Wrong private key
Incorrect file permissions
TLS policy mismatch
Incorrect system time
```

### Interview Tip

> "For Apache TLS issues I use `curl` and `openssl s_client`, then inspect the correct SSL VirtualHost, certificate, key, SAN, chain, SNI, permissions, and Apache configuration."

# Q353. How do you troubleshoot Apache VirtualHost and reverse-proxy problems?

## Answer

Apache can host multiple websites and can proxy requests to backend applications.

### VirtualHost Example

```apache id="j1r3d2"
<VirtualHost *:80>
    ServerName app.example.com
    DocumentRoot /var/www/app
</VirtualHost>
```

### Reverse Proxy Example

```apache id="m4x7q2"
<VirtualHost *:80>
    ServerName app.example.com

    ProxyPass        /api/ http://127.0.0.1:8080/
    ProxyPassReverse /api/ http://127.0.0.1:8080/
</VirtualHost>
```

### Step 1: Show VirtualHosts

```bash id="p8m2x5"
apachectl -S
```

This is one of the most useful Apache troubleshooting commands.

### Step 2: Check ServerName/ServerAlias

Verify:

```text id="x7m3q2"
Hostname
ServerName
ServerAlias
```

### Step 3: Check DNS

```bash id="m5x8q2"
dig app.example.com
```

### Step 4: Test Host Header

```bash id="q3m7x4"
curl -v -H "Host: app.example.com" http://<server-ip>
```

For HTTPS, SNI must also be considered.

### Step 5: Check DocumentRoot

```bash id="x8m2q5"
ls -ld /var/www/app
```

### Step 6: Check Reverse Proxy Modules

```bash id="p4m8x2"
apachectl -M | grep proxy
```

Common modules may include:

```text id="m7x3q2"
proxy_module
proxy_http_module
```

The exact modules required depend on the proxy protocol.

### Step 7: Check Backend Listener

```bash id="x5m8q2"
ss -lntp | grep :8080
```

### Step 8: Test Backend Directly

```bash id="q7m3x4"
curl -v http://127.0.0.1:8080
```

### Step 9: Check Proxy Configuration

Look for:

```text id="m2x8q5"
ProxyPass
ProxyPassReverse
ProxyTimeout
```

### Step 10: Check Logs

```bash id="x8m3q2"
tail -f /var/log/httpd/error_log
```

or:

```bash id="p5m7x4"
tail -f /var/log/apache2/error.log
```

### Common Causes

```text id="7m3x8q"
Wrong VirtualHost
Wrong ServerName
DNS problem
Wrong DocumentRoot
Missing proxy module
Wrong backend port
Backend unavailable
Firewall
SELinux
Proxy configuration
```

### Interview Tip

> "For VirtualHost issues I use `apachectl -S` to identify which configuration handles the request. For reverse-proxy issues I then verify proxy modules, `ProxyPass`, backend listener, direct backend connectivity, firewall, SELinux, and logs."

# Q354. How do you troubleshoot high CPU, memory, or connection usage in Apache?

## Answer

Apache resource usage depends on its **Multi-Processing Module (MPM)** and workload.

Common MPMs include:

```text id="4m8x2q"
event
worker
prefork
```

### Step 1: Check CPU/Memory

```bash id="m5x7q2"
top
```

Detailed process view:

```bash id="p8m3x4"
ps -eo pid,ppid,%cpu,%mem,cmd --sort=-%cpu | head
```

### Step 2: Check Apache Processes

```bash id="x7m2q5"
pgrep -a httpd
```

or:

```bash id="q4m8x2"
pgrep -a apache2
```

### Step 3: Check Connections

```bash id="m3x7q2"
ss -s
```

Apache-related connections:

```bash id="p5m8x4"
ss -antp | grep -E 'httpd|apache2'
```

### Step 4: Check Apache MPM

```bash id="x8m2q5"
apachectl -M
```

Look for:

```text id="q7m3x2"
mpm_event_module
mpm_worker_module
mpm_prefork_module
```

### Step 5: Check Configuration

```bash id="m5x8q2"
apachectl -t -D DUMP_RUN_CFG
```

Depending on Apache version/build, this can provide useful runtime configuration details.

### Step 6: Check Access Logs

```bash id="p7m3x4"
tail -f /var/log/httpd/access_log
```

or:

```bash id="x4m8q2"
tail -f /var/log/apache2/access.log
```

Look for:

```text id="m8x3q5"
Traffic spike
Repeated requests
Slow endpoints
Large downloads
Specific clients
Bot traffic
5xx responses
```

### Step 7: Check Error Logs

```bash id="q5m7x2"
tail -f /var/log/httpd/error_log
```

### Step 8: Check File Descriptors

```bash id="x7m2q4"
ulimit -n
```

For a specific process:

```bash id="p4m8x2"
ls /proc/<PID>/fd | wc -l
```

### Step 9: Check Backend Performance

Apache may be waiting on:

```text id="m8x3q2"
Application
Database
External API
PHP/CGI
Storage
```

Check:

```bash id="x5m7q4"
top
```

```bash id="q8m2x5"
free -h
```

```bash id="m4x7q2"
iostat -xz 1
```

### Step 10: Check MPM Limits

Inspect the active MPM configuration and understand directives such as:

```text id="7m3x8q"
MaxRequestWorkers
ServerLimit
ThreadsPerChild
StartServers
```

Do not blindly increase these values.

Higher concurrency can increase:

```text id="x2m8q5"
Memory usage
CPU usage
Backend connections
Database load
```

### Important

High Apache CPU does not automatically mean Apache is the root cause.

The real bottleneck may be:

```text id="p5m8x2"
Application
Database
External API
Traffic spike
Slow clients
```

### Interview Tip

> "For high Apache resource usage, I correlate process usage, MPM configuration, active connections, access/error logs, traffic patterns, and backend latency before changing worker limits."

### Production Scenario

**Interviewer:**

> "The production application behind Apache is returning 502 errors. What will you check?"

**Strong Answer:**

> "First I would confirm the 502 and identify the affected URL, users, and timeframe. I would verify DNS, TCP, and TLS if applicable, then check the Apache service and run `apachectl -t`. I would inspect `apachectl -S` to confirm the correct VirtualHost and review the Apache error log. Since 502 commonly points toward an upstream problem when Apache is acting as a reverse proxy, I would verify `ProxyPass`, the backend IP and port, check the backend listener with `ss`, and test the backend directly with `curl`. I would then investigate firewall, SELinux, DNS, routing, application logs, resources, and backend dependencies based on the evidence. If necessary, I would use targeted packet capture. I would identify the exact failing layer, make the smallest reversible change, verify the full request path, monitor the service, and document the root cause."

# ⚠️ Production Safety Rules

Before changing Apache in production:

```text id="p5m8x2"
1. Identify the exact URL
2. Identify the hostname
3. Check DNS
4. Check TCP connectivity
5. Check TLS if HTTPS
6. Record the HTTP status
7. Check Apache service
8. Run apachectl -t before applying configuration
9. Check apachectl -S for VirtualHost problems
10. Check apachectl -M for module problems
11. Check access/error logs
12. Check listening ports
13. Verify DocumentRoot
14. Verify ProxyPass if reverse proxy is used
15. Test backend directly
16. Check firewall/security controls
17. Check SELinux where relevant
18. Check CPU/memory/disk
19. Check application logs
20. Check database/external dependencies
21. Check recent configuration/deployment changes
22. Avoid blind restarts
23. Avoid blindly increasing worker limits
24. Avoid blindly increasing timeouts
25. Protect TLS private keys
26. Make the smallest reversible change
27. Prefer reload when appropriate
28. Verify end-to-end
29. Monitor after the change
30. Document the root cause
```

> **Interview mindset:** Don't say **"Apache is giving 502, so I will restart Apache."** Say: **"I will confirm the 502, inspect Apache's error log, validate the configuration and VirtualHost, verify the reverse-proxy/upstream configuration, test the backend directly, and then investigate network, firewall, SELinux, TLS, application, and dependency issues based on the evidence."**
