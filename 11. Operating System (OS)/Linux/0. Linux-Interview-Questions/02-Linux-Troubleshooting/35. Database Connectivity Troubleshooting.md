> Database connectivity issues are common in production DevOps environments. The problem can exist at multiple layers: **DNS → Network → Firewall → Port → Database Listener → Authentication → Connection Pool → Database Health → Application**.

# Q356. How do you troubleshoot a database connection problem?

## Answer

Database connectivity should be investigated layer by layer.

### Typical Flow

```text id="4x7m2q"
Application
     |
     v
DNS
     |
     v
IP Address
     |
     v
Network Route
     |
     v
Firewall / Security Group
     |
     v
Database Port
     |
     v
Database Listener
     |
     v
Authentication
     |
     v
Database
```

### Step 1: Identify the Database

Determine:

```text id="m8x3q5"
Database type
Hostname/IP
Port
Database name
Username
Environment
```

Common database ports:

| Database             | Common Port |
| -------------------- | ----------: |
| MySQL                |        3306 |
| MariaDB              |        3306 |
| PostgreSQL           |        5432 |
| Microsoft SQL Server |        1433 |
| Oracle               |        1521 |
| MongoDB              |       27017 |
| Redis                |        6379 |

These are defaults, not requirements.

### Step 2: Check DNS

```bash id="p5m8x2"
getent hosts db.example.com
```

```bash id="x7m3q4"
dig db.example.com
```

### Step 3: Check Route

```bash id="m4x8q2"
ip route get <database-ip>
```

### Step 4: Test Database Port

```bash id="q8m2x5"
nc -vz db.example.com 5432
```

### Step 5: Check Database Listener

On the database server:

```bash id="x5m7q2"
ss -lntp | grep :5432
```

### Step 6: Check Firewall

```bash id="m8x3q2"
firewall-cmd --list-all
```

or:

```bash id="p4m7x5"
nft list ruleset
```

### Step 7: Check Database Service

For PostgreSQL:

```bash id="x7m2q4"
systemctl status postgresql
```

For MySQL:

```bash id="q5m8x2"
systemctl status mysqld
```

Service names vary by distribution/version.

### Step 8: Test With Database Client

PostgreSQL:

```bash id="m3x7q2"
psql -h db.example.com -U appuser -d appdb
```

MySQL:

```bash id="p8m2x4"
mysql -h db.example.com -u appuser -p
```

### Step 9: Check Database Logs

Use the database's configured log location or systemd journal.

Example:

```bash id="x4m7q2"
journalctl -u postgresql
```

### Important

Do not immediately restart the database.

First determine whether the problem is:

```text id="m8x2q5"
DNS
Network
Firewall
Listener
Authentication
Database health
Application
```

### Interview Tip

> "I troubleshoot database connectivity from the application outward: DNS, route, security controls, port, database listener, authentication, database health, and application connection behavior."

# Q357. How do you check whether a database server and port are reachable?

## Answer

Suppose PostgreSQL is expected on:

```text id="8m3q7x"
db.example.com:5432
```

### Step 1: Resolve Hostname

```bash id="x5m8q2"
getent hosts db.example.com
```

### Step 2: Check Route

```bash id="p7m3x4"
ip route get <database-ip>
```

### Step 3: Test TCP Port

```bash id="m4x8q2"
nc -vz db.example.com 5432
```

Example:

```text id="q8m3x5"
Connection to db.example.com 5432 port [tcp/postgresql] succeeded!
```

### Step 4: Test With Database Client

For PostgreSQL:

```bash id="x7m2q4"
psql -h db.example.com -p 5432 -U appuser -d appdb
```

For MySQL:

```bash id="m5x8q2"
mysql -h db.example.com -P 3306 -u appuser -p
```

### Why Use Both?

`nc` proves approximately:

```text id="4m7x2q"
TCP connectivity
```

A database client proves more:

```text id="p8m3x5"
TCP
+
Database protocol
+
Authentication
+
Database access
```

### Step 5: Check Application Server Firewall

```bash id="x3m8q2"
firewall-cmd --list-all
```

### Step 6: Check Database Server Firewall

Also inspect the database server's firewall/security rules.

### Step 7: Check Listener

On database server:

```bash id="q5m7x2"
ss -lntp | grep -E ':3306|:5432|:1433|:1521'
```

### Important

This:

```text id="m8x2q4"
nc → success
```

does not mean:

```text id="p5m7x2"
Database login → success
```

Authentication or database-level access can still fail.

### Interview Tip

> "`nc` checks TCP reachability, while a native database client verifies the actual database protocol and authentication."

# Q358. How do you troubleshoot "Connection refused" and "Connection timed out" for a database?

## Answer

These errors provide useful clues.

## Connection Refused

Example:

```text id="x7m3q2"
Connection refused
```

Possible causes:

```text id="m5x8q4"
Database service stopped
Wrong port
No listener
Database bound only to localhost
Active reject
Incorrect endpoint
```

### Check Listener

```bash id="p8m2x5"
ss -lntp | grep :5432
```

### Check Service

```bash id="q4x7m2"
systemctl status postgresql
```

### Check Bind Configuration

For PostgreSQL, inspect the effective configuration for the listening address and port.

For example:

```text id="m8x3q2"
listen_addresses
port
```

---

## Connection Timeout

Example:

```text id="x5m7q2"
Connection timed out
```

Possible causes:

```text id="p4m8x2"
Firewall drop
Security Group
NACL
Routing problem
Network problem
Wrong IP
Database unreachable
```

### Check Route

```bash id="q7m3x5"
ip route get <database-ip>
```

### Check Port

```bash id="m2x8q4"
nc -vz -w 3 <database-ip> 5432
```

### Check Packet Flow

On database server:

```bash id="x8m3q2"
sudo tcpdump -ni any port 5432
```

### Interpretation

If no packets reach the database server:

```text id="5m7x2q"
Client
   |
   X
Network / SG / NACL / Firewall / Route
   |
Database
```

If packets arrive but no connection is established:

```text id="p8m3x2"
Investigate listener/firewall/database
```

### Important

```text id="q7m3x2"
Connection refused
    ≠ Always firewall

Connection timeout
    ≠ Always database down
```

### Interview Tip

> "For refused connections I check the database listener and service. For timeouts I focus on routing, firewall, security groups, NACLs, and packet flow."

# Q359. How do you troubleshoot database DNS/name-resolution problems?

## Answer

Applications often connect using a database hostname instead of an IP.

Example:

```text id="8m3q7x"
db-prod.internal.example.com
```

### Step 1: Test System Resolution

```bash id="x5m8q2"
getent hosts db-prod.internal.example.com
```

### Step 2: Test DNS Directly

```bash id="p7m3x4"
dig db-prod.internal.example.com
```

### Step 3: Check Resolver Configuration

```bash id="m4x8q2"
cat /etc/resolv.conf
```

### Step 4: Check `/etc/hosts`

```bash id="q8m2x5"
grep -w "db-prod.internal.example.com" /etc/hosts
```

### Step 5: Test the DNS Server

```bash id="x7m3q2"
dig @<dns-server-ip> db-prod.internal.example.com
```

### Step 6: Compare Hostname vs IP

Hostname:

```bash id="m5x8q2"
nc -vz db-prod.internal.example.com 5432
```

IP:

```bash id="p4m7x5"
nc -vz 10.20.10.50 5432
```

If:

```text id="x8m2q3"
IP works
Hostname fails
```

focus on DNS/name resolution.

### Step 7: Check Application Environment

Applications may use:

```text id="m7x3q2"
Environment variables
Configuration files
Secrets
Container DNS
Kubernetes DNS
Service discovery
```

### Important

Do not change the application's database hostname to an IP as a permanent fix unless that is part of the approved architecture.

Using an IP can break:

```text id="p5m8x2"
Failover
Database endpoint changes
DNS-based service discovery
High availability
```

### Interview Tip

> "If the database IP works but the database hostname fails, I focus on DNS, `/etc/hosts`, resolver configuration, service discovery, and the application's runtime environment."

# Q360. How do you troubleshoot database authentication failures?

## Answer

A database server can be reachable while authentication still fails.

Example:

```text id="m8x3q2"
TCP connection → SUCCESS
Database login → FAIL
```

### Step 1: Check Username

Verify the application is using the expected account.

### Step 2: Check Password/Secret

Verify the configured secret without exposing it.

Common sources:

```text id="p5m7x2"
Environment variables
Secret manager
Configuration file
Kubernetes Secret
Cloud secret service
```

### Step 3: Check Database Authentication Rules

For PostgreSQL, review:

```text id="x7m3q4"
pg_hba.conf
```

This controls client authentication rules.

### Step 4: Check Database User

PostgreSQL:

```sql id="q8m2x5"
\du
```

MySQL:

```sql id="m4x7q2"
SELECT user, host FROM mysql.user;
```

Use appropriate privileged access.

### Step 5: Check Database Name

A valid user may still fail if the requested database does not exist or the user cannot connect to it.

### Step 6: Check Source IP

Authentication rules may depend on:

```text id="p7m3x2"
Client IP
Subnet
Hostname
SSL requirements
Authentication method
```

### Step 7: Check Database Logs

Look for:

```text id="x5m8q2"
Authentication failure
Invalid user
Access denied
No matching authentication rule
SSL requirement
Connection rejection
```

### Step 8: Test Manually

PostgreSQL:

```bash id="m8x2q5"
psql -h <host> -U <user> -d <database>
```

MySQL:

```bash id="q4m7x2"
mysql -h <host> -u <user> -p
```

### Important

Do not repeatedly change passwords without first determining the cause.

Authentication failure can result from:

```text id="x7m3q2"
Wrong username
Wrong password
Expired credential
Wrong database
Host restriction
Authentication policy
SSL requirement
Secret/configuration mismatch
```

### Security Rule

Never print production passwords or secrets into:

```text id="p5m8x2"
Terminal history
Logs
Tickets
Screenshots
Git repositories
```

### Interview Tip

> "If TCP connectivity works but authentication fails, I move to the database authentication layer: credentials, database/user permissions, source restrictions, authentication rules, SSL requirements, and database logs."

# Q361. How do you troubleshoot database connection pool exhaustion?

## Answer

Applications commonly use a **connection pool** instead of opening a new database connection for every request.

Example:

```text id="8m3q7x"
Application
     |
     v
Connection Pool
 +---+---+---+---+
 |   |   |   |   |
 v   v   v   v   v
 DB Connections
```

If all connections are busy:

```text id="m5x8q2"
Application Request
       |
       X
No available DB connection
```

### Symptoms

```text id="p7m3x4"
Connection timeout
Pool exhausted
Requests waiting
Application latency
Database connection errors
```

### Step 1: Check Application Logs

Search for:

```text id="x4m8q2"
pool exhausted
connection timeout
unable to acquire connection
too many connections
```

### Step 2: Check Pool Configuration

Common parameters:

```text id="q8m3x5"
Maximum pool size
Minimum idle
Connection timeout
Idle timeout
Maximum lifetime
```

Names vary by application/framework.

### Step 3: Check Database Connections

PostgreSQL example:

```sql id="m5x7q2"
SELECT count(*) FROM pg_stat_activity;
```

MySQL example:

```sql id="x7m2q4"
SHOW STATUS LIKE 'Threads_connected';
```

### Step 4: Check Connection State

For PostgreSQL:

```sql id="p4m8x2"
SELECT state, count(*)
FROM pg_stat_activity
GROUP BY state;
```

### Step 5: Check Long-Running Queries

PostgreSQL:

```sql id="m8x3q5"
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY duration DESC;
```

Use appropriate access and caution with query visibility.

### Step 6: Check Application Traffic

A sudden traffic increase can consume the pool.

### Step 7: Check Database Performance

Slow queries keep connections busy for longer.

Investigate:

```text id="q5m7x2"
CPU
Memory
I/O
Locks
Slow queries
Indexes
```

### Common Causes

```text id="x7m3q2"
Pool too small
Pool too large
Connection leak
Slow queries
Long transactions
Database overload
Traffic spike
Downstream dependency causing requests to wait
```

### Important

Increasing the pool size is not automatically the solution.

If the database is already overloaded:

```text id="m8x2q5"
Bigger pool
   ↓
More DB connections
   ↓
More database pressure
   ↓
Potentially worse performance
```

### Interview Tip

> "For connection pool exhaustion, I check application pool metrics and configuration, database active connections, long-running queries, traffic, and database capacity before increasing the pool size."

# Q362. How do you troubleshoot "Too many connections" errors?

## Answer

This means the database has reached or is approaching its connection limit.

### Step 1: Check Current Connections

PostgreSQL:

```sql id="p5m8x2"
SELECT count(*) FROM pg_stat_activity;
```

MySQL:

```sql id="x7m3q4"
SHOW STATUS LIKE 'Threads_connected';
```

### Step 2: Check Connection Limit

PostgreSQL:

```sql id="m4x8q2"
SHOW max_connections;
```

MySQL:

```sql id="q8m3x5"
SHOW VARIABLES LIKE 'max_connections';
```

### Step 3: Identify Connection Sources

PostgreSQL:

```sql id="x5m7q2"
SELECT client_addr, usename, application_name, state, count(*)
FROM pg_stat_activity
GROUP BY client_addr, usename, application_name, state
ORDER BY count(*) DESC;
```

This can identify which application/client is consuming connections.

### Step 4: Check Idle Connections

Large numbers of idle connections may indicate:

```text id="m8x2q4"
Pool configuration
Connection leaks
Application behavior
Long-lived connections
```

### Step 5: Check Long-Running Sessions

Investigate:

```text id="p7m3x2"
Long transactions
Blocked queries
Idle-in-transaction sessions
```

### Step 6: Check Application Pools

Multiple application instances can multiply total connections.

Example:

```text id="x4m8q2"
10 application pods
×
20 DB connections each
=
200 potential connections
```

### Step 7: Check Database Capacity

Increasing connection limits consumes more resources.

```text id="q5m8x2"
More connections
      ↓
More memory/context switching
      ↓
Potential performance degradation
```

### Step 8: Apply Safe Fix

Possible solutions:

```text id="m7x3q2"
Fix connection leak
Reduce oversized pools
Terminate approved stale sessions
Reduce unnecessary application instances
Optimize slow queries
Use connection pooling infrastructure
Increase DB connection limit only after capacity analysis
```

### Important

Do not blindly execute commands that terminate all database sessions.

That can cause a major production outage.

### Interview Tip

> "I identify who is consuming the connections, distinguish active from idle sessions, check application pool sizing across all instances, investigate leaks and long-running queries, and only then consider changing the database connection limit."

# Q363. How do you troubleshoot slow database connectivity or slow queries?

## Answer

First distinguish:

```text id="8m3q7x"
Connection establishment is slow
          vs
Query execution is slow
```

These are different problems.

### Step 1: Measure Connection Time

Test the database client and compare timing.

For HTTP applications, application metrics can help identify whether time is spent acquiring a DB connection.

### Step 2: Check Network

```bash id="m5x8q2"
ip route get <database-ip>
```

```bash id="p7m3x4"
nc -vz <database-ip> 5432
```

### Step 3: Check DNS

```bash id="x4m8q2"
dig db.example.com
```

### Step 4: Check Database Health

On Linux:

```bash id="m8x3q5"
top
```

```bash id="q5m7x2"
free -h
```

```bash id="x7m3q4"
iostat -xz 1
```

### Step 5: Check Active Queries

PostgreSQL:

```sql id="p4m8x2"
SELECT pid, now() - query_start AS duration, state, query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY duration DESC;
```

### Step 6: Check Locks

Database-specific lock inspection can reveal queries waiting for other transactions.

### Step 7: Check Query Plans

For PostgreSQL:

```sql id="m5x8q2"
EXPLAIN ANALYZE SELECT ...;
```

Use carefully in production because `EXPLAIN ANALYZE` executes the query.

### Step 8: Check Storage

Database performance may be affected by:

```text id="x7m3q2"
High disk latency
Low IOPS
Filesystem pressure
Storage errors
```

### Step 9: Check Connection Pool

If queries are fast but requests are waiting for a connection:

```text id="p8m2x4"
Pool exhaustion
```

may be the actual bottleneck.

### Step 10: Check Network Latency

For remote databases, network latency can affect:

```text id="q4m7x2"
Connection establishment
Many small queries
Chatty applications
Cross-region traffic
```

### Important

```text id="m8x3q2"
Slow application
   ≠
Automatically slow database
```

The delay may be:

```text id="p5m7x4"
DNS
Network
Connection pool
Query
Lock
Database I/O
External dependency
```

### Interview Tip

> "I first determine whether the delay is DNS, TCP connection establishment, connection-pool wait, query execution, lock wait, or database I/O before optimizing the database."

## Answer

This is a very common DevOps production scenario.

Example:

```text id="8m3q7x"
Application Server
       |
       | TCP/5432
       v
Database Server
```

### Step 1: Check Database Configuration

Find the configured:

```text id="m5x8q2"
DB_HOST
DB_PORT
DB_NAME
DB_USER
```

Do not expose passwords.

### Step 2: Test DNS

```bash id="p7m3x4"
getent hosts <db-hostname>
```

### Step 3: Test Route

```bash id="x4m8q2"
ip route get <db-ip>
```

### Step 4: Test Port

```bash id="m8x3q5"
nc -vz <db-hostname> <db-port>
```

### Step 5: Test Database Client

PostgreSQL:

```bash id="q5m7x2"
psql -h <db-hostname> -p <db-port> -U <user> -d <database>
```

MySQL:

```bash id="x7m3q4"
mysql -h <db-hostname> -P <db-port> -u <user> -p
```

### Step 6: Check Application Logs

```bash id="p4m8x2"

```

Look for:

```text id="m5x8q2"
Connection refused
Connection timeout
Authentication failure
Pool exhausted
SSL error
Unknown host
Too many connections
```

### Step 7: Check Application Environment

The application may have different configuration from your interactive shell.

Check:

```bash id="x8m3q5"
systemctl show <application-service> -p Environment
```

Be careful not to expose secrets.

### Step 8: Check Firewall

Application server:

```bash id="q7m2x4"
firewall-cmd --list-all
```

Database server:

```bash id="m4x8q2"
firewall-cmd --list-all
```

### Step 9: Check Database Listener

On database server:

```bash id="x5m7q2"
ss -lntp | grep :5432
```

### Step 10: Check Database Authentication

If TCP works but login fails, investigate:

```text id="p8m3x4"
Username
Password/secret
Database
Source IP
Authentication rules
SSL requirements
```

### Step 11: Check Packet Flow if Necessary

On database server:

```bash id="m8x2q5"
sudo tcpdump -ni any port 5432
```

### Troubleshooting Decision Tree

```text id="x7m3q2"
Application
    |
    v
DB hostname resolves?
    |
  +---+---+
  |       |
 NO      YES
  |       |
 DNS      v
       Route?
         |
         v
       Port?
         |
         v
      Listener?
         |
         v
    Authentication?
         |
         v
     DB access?
```

### Interview Tip

> "From the application server, I reproduce the problem using the same hostname and port, then test DNS, route, TCP connectivity, native database authentication, application configuration, firewall/security controls, and database-side logs."

### Production Scenario

**Interviewer:**

> "The production application suddenly cannot connect to PostgreSQL. What will you do?"

**Strong Answer:**

> "First I would capture the exact application error and determine whether all application instances are affected. I would verify the configured database hostname and port without exposing credentials. Then I would test DNS using `getent` and `dig`, check the route with `ip route get`, and test TCP connectivity with `nc`. On the database server I would check the PostgreSQL service and listener using `systemctl` and `ss`. I would verify host and cloud firewall controls, then test authentication using `psql` from an appropriate application-side host. If TCP works but authentication fails, I would investigate credentials, PostgreSQL authentication rules, source restrictions, and SSL requirements. If the error indicates pool exhaustion or too many connections, I would inspect application pool metrics and database sessions rather than blindly increasing connection limits. I would also check database resource usage, logs, recent changes, and use targeted packet capture if required. After identifying the failing layer, I would make the smallest safe change, verify the database connection and application health, and document the root cause."
