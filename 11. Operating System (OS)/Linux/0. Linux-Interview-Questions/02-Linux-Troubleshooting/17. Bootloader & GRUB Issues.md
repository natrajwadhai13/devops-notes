# 17. Bootloader & GRUB Issues

> The **bootloader** is responsible for loading the Linux kernel and starting the operating system. On many Linux systems, **GRUB2** is the bootloader. Boot problems can occur because of incorrect GRUB configuration, damaged boot files, incorrect kernel/initramfs entries, filesystem problems, or changes to the boot disk/partition.

# Q176. What is GRUB and what is its role in the Linux boot process?

## Answer

**GRUB2 (GRand Unified Bootloader)** is commonly used to boot Linux systems.

It sits between the system firmware and the Linux kernel.

### Simplified Boot Process

```text id="d1u8p6"
Power On
   |
   v
BIOS / UEFI
   |
   v
GRUB
   |
   v
Linux Kernel
   |
   v
initramfs
   |
   v
systemd
   |
   v
Services
```

### GRUB Responsibilities

GRUB can:

* Display the boot menu
* Select the kernel
* Pass kernel parameters
* Load the kernel
* Load the initramfs
* Support booting different kernels
* Provide recovery options

### Example

A GRUB menu may contain:

```text id="5gq7nq"
Linux 5.14.0-427
Linux 5.14.0-400
Advanced options
```

If the newest kernel has a problem, an administrator may select the previous known-good kernel.

### Kernel Parameters

GRUB can pass parameters to the kernel.

Example:

```text id="n5n5ih"
root=/dev/mapper/rhel-root
ro
quiet
```

These parameters influence how the kernel starts.

### Important

GRUB is not the Linux kernel.

```text id="6w7l0h"
GRUB
 ↓
Loads kernel

Kernel
 ↓
Manages operating system
```

### Interview Tip

> "GRUB2 is the bootloader commonly used on Linux systems. It loads the selected kernel and initramfs and passes kernel parameters before handing control to the Linux kernel."

# Q177. How do you check the current GRUB and kernel configuration?

## Answer

First check the running kernel:

```bash id="j4l5sy"
uname -r
```

### Check Installed Kernels

On RPM-based systems:

```bash id="8s2tqy"
rpm -q kernel
```

### Check GRUB Configuration

A generated GRUB configuration is commonly found at:

```text id="x6atj1"
/boot/grub2/grub.cfg
```

On some UEFI systems/distributions, the exact path can differ.

Check:

```bash id="5q72kq"
ls -l /boot/grub2/
```

### Check Kernel and Initramfs Files

```bash id="qf58um"
ls -lh /boot
```

Look for files similar to:

```text id="89y6w5"
vmlinuz-...
initramfs-...
```

### Check Kernel Command Line

```bash id="t7m2k4"
cat /proc/cmdline
```

This shows the parameters passed to the currently running kernel.

### Check GRUB Defaults

Common configuration:

```bash id="x4qv9p"
cat /etc/default/grub
```

### Important

Do not manually edit:

```text id="v1q2h4"
/boot/grub2/grub.cfg
```

as a normal configuration method.

It is generally generated from configuration and should be rebuilt using the appropriate distribution procedure.

### Interview Tip

> "I check `uname -r` for the running kernel, `/boot` for installed kernel and initramfs files, `/proc/cmdline` for the current kernel parameters, and `/etc/default/grub` for GRUB defaults."

# Q178. How do you troubleshoot a server that stops at the GRUB menu?

## Answer

If the server reaches the GRUB menu but does not continue booting, the problem may involve:

```text id="5iqd0u"
GRUB configuration
Kernel
initramfs
Root filesystem
Kernel parameters
Storage
```

### Step 1: Try a Previous Kernel

If multiple kernels are available:

```text id="6f2h9q"
GRUB
 |
 +-- New Kernel
 |
 +-- Previous Kernel
```

Select the previous known-good kernel.

If it boots successfully, investigate the newer kernel.

### Step 2: Check Kernel and initramfs

After booting:

```bash id="9b9w1f"
ls -lh /boot
```

Look for matching:

```text id="k1f8uk"
vmlinuz
initramfs
```

### Step 3: Check Boot Logs

```bash id="8qf4u3"
journalctl -b
```

Kernel messages:

```bash id="n6o6p8"
journalctl -k -b
```

### Step 4: Check Root Filesystem

```bash id="y0d5h2"
findmnt /
```

Check storage:

```bash id="w7k7pg"
lsblk -f
```

### Step 5: Check Recent Changes

Investigate:

```text id="2s6rj0"
Kernel update
GRUB change
Storage change
Filesystem change
Boot disk change
LVM change
Driver update
```

### Troubleshooting Flow

```text id="d1h5av"
GRUB Menu Appears
       |
       v
Try Previous Kernel
       |
       +-- Boots → Investigate New Kernel
       |
       v
Check /boot
       |
       v
Check Kernel + initramfs
       |
       v
Check Root Device
       |
       v
Check Logs
       |
       v
Fix / Rebuild Boot Configuration
```

### Interview Tip

> "If the server stops at GRUB, I first try the previous known-good kernel if available. Then I check kernel/initramfs files, root-device configuration, boot logs, storage, and recent changes."

# Q179. How do you troubleshoot "GRUB rescue" mode?

## Answer

`grub rescue>` generally indicates that GRUB cannot find or properly load the files it needs to continue booting.

You may see:

```text id="2os0u4"
grub rescue>
```

### Possible Causes

* GRUB configuration problem
* Boot partition problem
* Incorrect disk/partition configuration
* Boot files missing
* Filesystem problem
* Disk replacement
* Incorrect bootloader installation

### Step 1: Inspect GRUB Disks

At the GRUB rescue prompt:

```text id="7j2r7x"
ls
```

You may see devices/partitions such as:

```text id="9z5y3k"
(hd0)
(hd0,gpt1)
(hd0,gpt2)
```

### Step 2: Identify the Boot Partition

You may inspect partitions:

```text id="q5v3t8"
ls (hd0,gpt1)/
```

Try relevant partitions until you identify the one containing boot files.

### Step 3: Recover Carefully

The exact GRUB rescue commands depend on:

```text id="3c9l4n"
BIOS vs UEFI
Partition layout
Filesystem
GRUB installation
Distribution
```

Therefore, do not blindly copy commands from another system.

### Production Recovery Approach

A common recovery pattern is:

```text id="w0r7pz"
Boot Rescue Environment
       |
       v
Identify Root / Boot Partitions
       |
       v
Mount Filesystems
       |
       v
Chroot if Required
       |
       v
Repair GRUB
       |
       v
Regenerate Configuration
       |
       v
Reboot
```

### Important

Before repairing GRUB, identify:

```bash id="8jqm7w"
lsblk -f
```

and understand the partition layout.

### Interview Tip

> "For GRUB rescue, I first identify the available disks and partitions and determine whether the boot partition or GRUB configuration is missing or inaccessible. For complex recovery, I use an appropriate rescue environment rather than guessing commands."

# Q180. How do you troubleshoot a server that shows GRUB but does not boot Linux?

## Answer

If GRUB appears, the bootloader has started successfully enough to display its menu.

The failure may occur while loading:

```text id="m4z0tb"
Kernel
initramfs
Root filesystem
Drivers
```

### Step 1: Select Previous Kernel

If available:

```text id="3z2aqb"
GRUB
 |
 +-- Current Kernel
 |
 +-- Previous Kernel
```

Try the previous kernel.

### Step 2: Check Boot Messages

If the system boots with the previous kernel:

```bash id="c2v4kd"
journalctl -b
```

Kernel:

```bash id="8ozvdy"
journalctl -k -b
```

### Step 3: Check `/boot`

```bash id="4q4wif"
ls -lh /boot
```

Confirm that:

```text id="v3k7j5"
Kernel
+
Matching initramfs
```

exist.

### Step 4: Check Root Device

```bash id="db3t3s"
lsblk -f
```

Check:

```bash id="v24d9b"
UUID
Filesystem
LVM
Mount point
```

### Step 5: Check Kernel Command Line

```bash id="e9p3nq"
cat /proc/cmdline
```

Compare the root-device information with the actual storage configuration.

### Possible Causes

* Incorrect root device
* Missing initramfs
* Missing storage driver
* Filesystem issue
* LVM activation issue
* Incorrect kernel parameter
* Kernel problem

### Interview Tip

> "If GRUB loads but Linux does not, I focus on the kernel, initramfs, root filesystem, storage drivers, kernel parameters, and recent changes rather than assuming GRUB itself is broken."

# Q181. How do you troubleshoot a server that cannot find the kernel or initramfs?

## Answer

The kernel is normally stored under:

```text id="u1t2ce"
/boot
```

Typical files include:

```text id="3f7i1x"
vmlinuz-<version>
initramfs-<version>.img
```

### Step 1: Check `/boot`

```bash id="3t1f6d"
ls -lh /boot
```

### Step 2: Check Installed Kernels

RPM-based:

```bash id="c0q4cl"
rpm -q kernel
```

### Step 3: Check initramfs

Look for a matching image:

```bash id="9z2e9x"
ls -lh /boot/initramfs*
```

### Important

The kernel and initramfs should correspond to the kernel version being booted.

Example:

```text id="d3o4h1"
vmlinuz-5.14.0-427
initramfs-5.14.0-427.img
```

### Step 4: Check Bootloader Configuration

```bash id="0j8pgn"
grep -E "linux|linuxefi|initrd|initrdefi" /boot/grub2/grub.cfg
```

The exact generated configuration and syntax can vary by distribution and boot mode.

### Step 5: Check `/boot` Space

```bash id="a7i2we"
df -h /boot
```

A full `/boot` filesystem can prevent new kernels or initramfs images from being installed correctly.

### Step 6: Rebuild initramfs if Required

On systems using `dracut`, an appropriate command may be:

```bash id="j8m0qi"
sudo dracut -f
```

For a specific kernel:

```bash id="x1v5c7"
sudo dracut -f /boot/initramfs-<kernel-version>.img <kernel-version>
```

Use the procedure appropriate to the distribution and kernel package management.

### Important

Do not rebuild or overwrite boot files blindly in production.

First confirm:

```text id="6m5o8f"
Kernel version
Boot mode
Existing initramfs
Root filesystem
Storage drivers
```

### Interview Tip

> "If the kernel or initramfs cannot be found, I check `/boot`, installed kernel packages, matching initramfs images, `/boot` capacity, and GRUB configuration. If required, I rebuild the initramfs using the distribution's supported tooling."

# Q182. How do you troubleshoot boot problems after modifying GRUB configuration?

## Answer

If boot failure starts immediately after a GRUB configuration change, first suspect the change.

### Step 1: Try a Known-Good GRUB Entry

If the GRUB menu provides another working entry, select it.

### Step 2: Check Current Configuration

After booting:

```bash id="7q1f2w"
cat /etc/default/grub
```

### Step 3: Check Kernel Command Line

```bash id="o2k7zi"
cat /proc/cmdline
```

Review parameters related to:

```text id="a0v9th"
root=
rd.*
resume=
rd.lvm.*
rd.luks.*
quiet
```

depending on the system.

### Step 4: Check Generated GRUB Configuration

```bash id="3k9w8f"
grep -E "linux|linuxefi|initrd|initrdefi" /boot/grub2/grub.cfg
```

### Step 5: Compare With Previous Configuration

If configuration was backed up, compare the old and new versions.

### Step 6: Regenerate GRUB Configuration

Use the distribution's supported GRUB configuration generation method.

For many BIOS-based RHEL-family installations, a command such as:

```bash id="j5r0pd"
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
```

may be appropriate.

However, **UEFI systems and different distributions can use different paths and procedures**.

### Important

Do not blindly overwrite:

```text id="9o6w1a"
/boot/grub2/grub.cfg
```

on every Linux system.

First determine:

```text id="7m0d7c"
Distribution
BIOS / UEFI
Boot partition
GRUB layout
```

### Interview Tip

> "If a GRUB change causes a boot failure, I use a known-good boot entry if available, compare the changed kernel parameters and configuration, and regenerate the configuration using the distribution's supported procedure."

```text id="1z8a6f"
initramfs
Drivers
GRUB entries
Storage
Networking
Third-party modules
```

### Step 1: Boot Previous Kernel

From GRUB:

```text id="r3n7qo"
Advanced Options
        |
        v
Previous Kernel
```

If the previous kernel works, the new kernel becomes a strong suspect.

### Step 2: Check Running Kernel

```bash id="2v2l3k"
uname -r
```

### Step 3: Check Installed Kernels

```bash id="a5d7n9"
rpm -q kernel
```

### Step 4: Check `/boot`

```bash id="1h5xk2"
ls -lh /boot
```

Check:

```text id="8b6qf5"
vmlinuz
initramfs
```

### Step 5: Check Kernel Logs

```bash id="2f6n1j"
journalctl -k -b
```

### Step 6: Check Drivers/Modules

```bash id="8n5xq5"
lsmod
```

For a specific module:

```bash id="f9w4j2"
modinfo module_name
```

### Step 7: Check Package History

```bash id="r3l0q2"
dnf history
```

### Common Causes

* Kernel bug
* Missing driver
* Incompatible third-party module
* Incorrect initramfs

```text id="u0zqkn"
Kernel Upgrade
```

# Q184. How do you safely rebuild GRUB configuration or boot files?

## Answer

Before rebuilding GRUB, identify:

```text id="l0h4qt"
Distribution
BIOS or UEFI
Boot disk
Boot partition
Current kernel
```

### Step 1: Check Boot Mode

```bash id="d5l8t3"
test -d /sys/firmware/efi && echo UEFI || echo BIOS
```

### Step 2: Check Disks and Mounts

```bash id="m7c6f8"
lsblk -f
```

```bash id="s2l8m4"
findmnt /boot
```

If UEFI:

```bash id="x8j4s0"
findmnt /boot/efi
```

### Step 3: Check Current Kernel

```bash id="0r5j1h"
uname -r
```

### Step 4: Back Up Relevant Configuration

Before making changes, preserve the current configuration where appropriate.

For example:

```bash id="q7s8d0"
cp /etc/default/grub /etc/default/grub.backup
```

### Step 5: Regenerate Configuration

On many BIOS-based RHEL-family systems:

```bash id="t3d8h4"
sudo grub2-mkconfig -o /boot/grub2/grub.cfg
```

But the exact procedure can differ for:

```text id="c5v4x9"
UEFI
RHEL-family versions
Debian/Ubuntu
Cloud images
Vendor-specific layouts
```

### Step 6: Verify

Check the generated file:

```bash id="n2f4g5"
grep -E "menuentry|linux|linuxefi|initrd|initrdefi" /boot/grub2/grub.cfg
```

### Step 7: Reboot Only After Validation

```bash id="j7n1q0"
sudo reboot
```

Only reboot after confirming the configuration and having an appropriate recovery plan.

### Important

**Regenerating GRUB configuration is different from reinstalling GRUB to the boot disk.**

These are separate operations:

```text id="6s8g4p"
Regenerate Configuration
        |
        v
Update GRUB menu/config

Reinstall Bootloader
        |
        v
Repair GRUB installation on disk/EFI
```

Do not reinstall the bootloader unless the evidence indicates that the bootloader installation itself is damaged.

### Interview Tip

> "I first identify BIOS versus UEFI and the boot layout, back up the relevant configuration, regenerate the GRUB configuration using the distribution-supported method, verify the generated entries, and only then plan a reboot. I distinguish configuration regeneration from reinstalling GRUB itself."

# Q185. How do you troubleshoot a production server with a suspected bootloader/GRUB issue?

## Answer

Bootloader issues are high-impact because the server may become completely unavailable.

I use a **recovery-first and evidence-based approach**.

### Step 1: Confirm the Failure Stage

Determine whether the server stops at:

```text id="r0qf8k"
BIOS / UEFI
   |
   v
GRUB
   |
   v
Kernel
   |
   v
initramfs
   |
   v
systemd
   |
   v
Services
```

This immediately narrows the troubleshooting area.

### Step 2: Check Console Output

If remote console or out-of-band management is available, inspect the exact boot message.

Look for:

```text id="j3t0v9"
GRUB error
Kernel not found
initramfs not found
Root device not found
Filesystem error
Kernel panic
```

### Step 3: Try Previous Kernel

If the GRUB menu is available:

```text id="q8u2m0"
Previous Known-Good Kernel
```

Boot it if appropriate.

### Step 4: Check Boot Files

After recovery:

```bash id="5g6x2r"
ls -lh /boot
```

Check:

```text id="f0u6z7"
Kernel
initramfs
Boot configuration
```

### Step 5: Check Boot Configuration

```bash id="4c2p5x"
cat /etc/default/grub
```

```bash id="m8x3c1"
cat /proc/cmdline
```

### Step 6: Check Storage and Mounts

```bash id="q4m6k1"
lsblk -f
```

```bash id="5x2g9j"
findmnt
```

### Step 7: Check Logs

```bash id="h2q9v0"
journalctl -b
```

Kernel:

```bash id="5h7z4c"
journalctl -k -b
```

Previous boot:

```bash id="v7j4d1"
journalctl -k -b -1
```

### Step 8: Check Recent Changes

Investigate:

```text id="y3q8k6"
Kernel upgrade
GRUB configuration change
Boot disk replacement
Partition changes
LVM changes
Filesystem changes
Driver updates
```

### Step 9: Recover Using an Appropriate Method

Depending on the failure:

```text id="v6w0x1"
Previous Kernel
       OR
Rescue Environment
       OR
Restore Boot Configuration
       OR
Rebuild initramfs
       OR
Repair GRUB
       OR
Restore Boot Disk
```

### Step 10: Verify

After recovery:

```text id="k9j0m3"
System boots
   |
   v
Correct kernel
   |
   v
Root filesystem mounted
   |
   v
Network available
   |
   v
Required services running
   |
   v
Application healthy
```

### Production Interview Scenario

**Interviewer:**

> "A production server is not booting after a kernel update. What will you do?"

**Strong Answer:**

> "First I will use the available console to determine exactly where the boot process stops. If GRUB is available, I will select the previous known-good kernel to restore service. Once the system is available, I will verify the running and installed kernels, inspect `/boot` for matching kernel and initramfs files, review GRUB configuration and kernel parameters, and check kernel and boot logs. I will also investigate recent changes, storage, drivers, and filesystem issues. If required, I will use a rescue environment to repair the boot configuration or rebuild the initramfs. After recovery, I will verify the complete system and application stack and document the root cause."

# 🎤 GRUB Interview Golden Rules

```text
GRUB issue ≠ automatically reinstall GRUB
Boot failure ≠ automatically kernel problem
GRUB menu appears ≠ Linux kernel is healthy
New kernel installed ≠ new kernel must be used
Missing kernel ≠ automatically damaged GRUB
initramfs issue ≠ automatically filesystem issue
Regenerate GRUB config ≠ reinstall GRUB
BIOS ≠ UEFI
```

Always investigate:

```text
Boot Stage
 +
BIOS / UEFI
 +
GRUB Configuration
 +
Kernel
 +
initramfs
 +
Kernel Parameters
 +
Root Device
 +
/boot
 +
Storage
 +
Drivers
 +
Recent Changes
```

### ⚠️ Production Safety Rules

Before changing bootloader configuration:

```text
1. Confirm exactly where boot is failing
2. Use console/out-of-band access when possible
3. Identify BIOS vs UEFI
4. Check current kernel and installed kernels
5. Check /boot and EFI partitions
6. Preserve the current configuration
7. Prefer a previous known-good kernel for recovery
8. Validate GRUB configuration before rebooting
9. Do not blindly reinstall GRUB
10. Do not blindly run filesystem repair commands
11. Ensure a recovery/rescue path exists
12. Reboot only after validation
13. Verify services and applications after recovery
14. Document the root cause and recovery steps
```

> **Interview mindset:** Do not say, "The server is not booting, so I will reinstall GRUB." Say, "I will first identify the exact boot stage, use the previous known-good kernel if available, inspect GRUB, kernel, initramfs, storage, and boot configuration, then perform the minimum required recovery using the appropriate BIOS/UEFI procedure."
