# 24. Kernel Module & Driver Troubleshooting

> Kernel modules and drivers allow Linux to communicate with hardware and provide additional kernel functionality. A driver problem can cause devices to be missing, unavailable, unstable, or generate kernel errors.

# Q246. What is a kernel module and what is a driver?

## Answer

A **kernel module** is code that can be loaded into the Linux kernel when needed.

A **device driver** is software that allows the operating system/kernel to communicate with a particular hardware device.

### Simple Example

```text
Application
     |
     v
Linux Kernel
     |
     v
Device Driver
     |
     v
Hardware
```

For example:

```text
Application
     |
     v
Linux Kernel
     |
     v
Network Driver
     |
     v
Network Card
```

### Kernel Module

A module is commonly stored as:

```text
/lib/modules/<kernel-version>/
```

Check:

```bash
uname -r
```

```bash
ls /lib/modules/$(uname -r)/
```

### Common Module Types

Examples:

```text
Network drivers
Storage drivers
USB drivers
Filesystem modules
Virtualization modules
```

### Important Difference

Not every kernel module is a hardware driver.

For example:

```text
Filesystem module
Security module
Virtualization module
Hardware driver
```

can all be kernel modules.

### Interview Tip

> "A kernel module is code that can be dynamically loaded into the kernel. A driver is software that allows Linux to communicate with hardware, and many hardware drivers are implemented as kernel modules."

# Q247. How do you check loaded kernel modules?

## Answer

Use:

```bash
lsmod
```

Example:

```text
Module                  Size  Used by
nf_conntrack           ...
xfs                     ...
virtio_net              ...
```

### Check a Specific Module

```bash
lsmod | grep virtio
```

### Get Detailed Module Information

```bash
modinfo virtio_net
```

### Check Module Files

```bash
find /lib/modules/$(uname -r) -type f | grep virtio
```

### Check Current Kernel

```bash
uname -r
```

This is important because modules are normally associated with a particular kernel version.

```text
Running Kernel
      |
      v
uname -r
      |
      v
/lib/modules/<same-kernel-version>/
```

### Check Module Parameters

```bash
modinfo module_name
```

Look for:

```text
filename
description
author
license
depends
parm
```

### Check Kernel Logs

```bash
journalctl -k | grep -i module_name
```

### Interview Tip

> "I use `lsmod` to see loaded modules, `modinfo` for detailed information, and `uname -r` to make sure I'm checking modules for the currently running kernel."

# Q248. How do you check which driver a hardware device is using?

## Answer

For PCI devices, use:

```bash
lspci -k
```

Example:

```text
Ethernet controller
    Kernel driver in use: ixgbe
    Kernel modules: ixgbe
```

### Search for a Specific Device

```bash
lspci -k | grep -A 3 -i ethernet
```

### Find Network Interface Driver

```bash
ethtool -i eth0
```

Example:

```text
driver: ixgbe
version: ...
firmware-version: ...
bus-info: ...
```

Check availability:

```bash
command -v ethtool
```

### Check Storage/Other Devices

```bash
lspci -k
```

This helps identify:

```text
Kernel driver in use
Kernel modules
```

### Check Loaded Driver

```bash
lsmod | grep driver_name
```

### Check Driver Details

```bash
modinfo driver_name
```

### Troubleshooting Flow

```text
Hardware
   |
   v
lspci -k
   |
   v
Driver identified
   |
   +----> lsmod
   |
   +----> modinfo
   |
   +----> journalctl -k
```

### Interview Tip

> "I start with `lspci -k` to identify the driver in use. For network interfaces I can use `ethtool -i <interface>`, then use `lsmod`, `modinfo`, and kernel logs for deeper troubleshooting."

# Q249. How do you troubleshoot a missing kernel module?

## Answer

First confirm that the device actually requires that module.

### Step 1: Identify the Device

```bash
lspci -k
```

or:

```bash
lsusb
```

### Step 2: Check Available Modules

```bash
find /lib/modules/$(uname -r) -type f
```

Search:

```bash
find /lib/modules/$(uname -r) -type f | grep driver_name
```

### Step 3: Check Module Information

```bash
modinfo driver_name
```

If you get an error such as:

```text
modinfo: ERROR: Module driver_name not found
```

the module may not be installed for the running kernel.

### Step 4: Check Kernel Version

```bash
uname -r
```

### Step 5: Check Module Directory

```bash
ls /lib/modules/$(uname -r)/
```

### Step 6: Check Kernel Logs

```bash
journalctl -k | grep -Ei "module|driver|firmware|failed"
```

### Possible Causes

```text
Module not installed
Wrong kernel version
Driver package missing
Kernel module not built
Third-party module incompatibility
Firmware missing
Unsupported hardware
```

### Important

Do not immediately download and compile a random driver.

First determine:

```text
Hardware
+
Kernel version
+
Distribution
+
Required driver
+
Supported package/source
```

### Interview Tip

> "For a missing module, I identify the hardware, check `lspci -k`, verify the running kernel with `uname -r`, check `/lib/modules/$(uname -r)`, use `modinfo`, and review kernel logs. Then I install or rebuild the driver using the supported package or vendor method."

# Q250. How do you load and unload a kernel module?

## Answer

### Load a Module

Use:

```bash
sudo modprobe module_name
```

Example:

```bash
sudo modprobe dummy
```

Check:

```bash
lsmod | grep dummy
```

### Remove a Module

```bash
sudo modprobe -r module_name
```

### Check Module Information

```bash
modinfo module_name
```

### Why Use `modprobe`?

`modprobe` understands module dependencies and normally handles required dependent modules automatically.

### `insmod` vs `modprobe`

```text
insmod
  |
  +-- Directly inserts a module
  +-- Does not handle dependencies as conveniently

modprobe
  |
  +-- Loads module
  +-- Handles dependencies
  +-- Preferred for normal module management
```

### Verify After Loading

```bash
lsmod | grep module_name
```

Then check:

```bash
journalctl -k | tail -n 50
```

### Important Production Warning

Do not unload a module blindly.

A module may be actively used by:

```text
Network interface
Storage device
Filesystem
Running application
Virtualization subsystem
```

Removing the wrong module can cause service or system failure.

### Interview Tip

> "I normally use `modprobe` to load or remove modules because it handles dependencies. Before unloading a module on production, I verify whether it is actively being used."

<a id="q251"></a>

# Q251. How do you troubleshoot a driver that fails to load?

## Answer

Start with the exact error instead of repeatedly trying to load the driver.

### Step 1: Check Module

```bash
modinfo driver_name
```

### Step 2: Try Loading

```bash
sudo modprobe driver_name
```

If it fails, capture the exact error.

### Step 3: Check Kernel Logs

```bash
journalctl -k | tail -n 100
```

Search:

```bash
journalctl -k | grep -Ei "driver_name|firmware|failed|error"
```

### Step 4: Check Hardware

```bash
lspci -k
```

### Step 5: Check Module Dependencies

```bash
modinfo driver_name
```

Look at:

```text
depends
```

### Step 6: Check Kernel Version

```bash
uname -r
```

### Step 7: Check Module File

```bash
modinfo -n driver_name
```

This can show the module file path.

### Step 8: Check Firmware

Some drivers require firmware.

Search:

```bash
journalctl -k | grep -i firmware
```

You may see:

```text
firmware: failed to load ...
```

### Common Causes

```text
Missing firmware
Wrong/incompatible driver
Kernel ABI compatibility issue
Missing dependency
Unsupported hardware
Module signature/security restriction
Third-party module problem
Hardware failure
```

### Important

A module existing on disk does not mean it will successfully load.

```text
Module exists
     ≠
Module loads successfully
```

### Interview Tip

> "If a driver fails to load, I capture the exact `modprobe` error, check `modinfo`, kernel version, dependencies, hardware detection, firmware messages, and kernel logs. I don't repeatedly retry without understanding the failure."

# Q252. How do you check kernel module dependencies?

## Answer

Use:

```bash
modinfo module_name
```

Look for:

```text
depends:
```

Example:

```bash
modinfo some_module | grep depends
```

### Check Loaded Modules

```bash
lsmod
```

The output includes a `Used by` field.

Example:

```text
Module       Size    Used by
module_a     ...     module_b,module_c
```

### Check Module Dependency Database

Linux maintains module dependency information under:

```bash
/lib/modules/$(uname -r)/
```

You may see files such as:

```text
modules.dep
modules.alias
modules.symbols
```

### Useful Command

```bash
grep "module_name" /lib/modules/$(uname -r)/modules.dep
```

### Why Dependencies Matter

Suppose:

```text
Module A
   |
   +--> Module B
          |
          +--> Module C
```

Removing Module C while Module B depends on it may fail.

### Interview Tip

> "I use `modinfo` to check module metadata and dependencies, `lsmod` to see currently loaded modules and usage, and the `/lib/modules/<kernel-version>` dependency database for deeper investigation."

# Q253. How do you make a kernel module load automatically after reboot?

## Answer

There are multiple approaches depending on the distribution and requirement.

### Step 1: Confirm the Module

```bash
modinfo module_name
```

### Step 2: Test Loading

```bash
sudo modprobe module_name
```

Verify:

```bash
lsmod | grep module_name
```

### Step 3: Configure Automatic Loading

On many Linux systems, a configuration file under:

```text
/etc/modules-load.d/
```

can be used.

Example:

```bash
sudo vi /etc/modules-load.d/my-module.conf
```

Content:

```text
module_name
```

### Step 4: Verify

```bash
cat /etc/modules-load.d/my-module.conf
```

### Step 5: Reboot Verification

After reboot:

```bash
lsmod | grep module_name
```

and:

```bash
journalctl -k | grep -i module_name
```

### Important

Before making a module persistent, confirm:

```text
Module is required
Driver is supported
Module is compatible with kernel
Loading it does not create conflicts
```

Some drivers are loaded automatically through device detection, initramfs, systemd, or other mechanisms, so manually forcing module loading is not always necessary.

### Interview Tip

> "If a module must be loaded at boot, I can configure it through `/etc/modules-load.d/`, after first testing that the module loads correctly and is compatible with the running kernel."

# Q254. How do you troubleshoot driver problems after a kernel upgrade?

## Answer

This is a common production issue.

Example:

```text
Before kernel upgrade
        |
        v
Network works
        |
        v
Kernel upgraded
        |
        v
Reboot
        |
        v
Network unavailable
```

### Step 1: Check Running Kernel

```bash
uname -r
```

### Step 2: Check Installed Kernels

On RPM-based systems:

```bash
rpm -q kernel
```

On Debian-based systems:

```bash
dpkg -l | grep linux-image
```

### Step 3: Check Driver

```bash
lspci -k
```

For network:

```bash
ethtool -i eth0
```

### Step 4: Check Module

```bash
lsmod
```

```bash
modinfo driver_name
```

### Step 5: Check Kernel Logs

```bash
journalctl -k -b
```

Search:

```bash
journalctl -k -b | grep -Ei "driver|module|firmware|failed|error"
```

### Step 6: Check Previous Kernel

If the previous kernel is available, booting it can help determine whether the issue is kernel-related.

```text
Old Kernel
   |
   +--> Hardware works
   |
New Kernel
   |
   +--> Hardware fails
```

This is strong evidence of a kernel/driver compatibility problem.

### Step 7: Check Third-Party Modules

Third-party drivers may need rebuilding for the new kernel.

Examples include:

```text
DKMS modules
Vendor drivers
Special storage drivers
Special network drivers
```

### Step 8: Check Initramfs

If the required driver is needed during early boot:

```bash
ls -lh /boot/initramfs*
```

On systems using `dracut`, inspect or rebuild using the distribution-supported procedure.

Example:

```bash
sudo dracut -f
```

Do not run this blindly on production; confirm the correct kernel/initramfs and change procedure first.

### Possible Causes

```text
Driver incompatible with new kernel
Third-party module not rebuilt
Missing firmware
Module missing from initramfs
DKMS failure
Kernel configuration difference
Driver regression
```

### Interview Tip

> "If a driver fails after a kernel upgrade, I compare the working and failed kernels, check `uname -r`, `lspci -k`, `modinfo`, kernel logs, third-party/DKMS modules, firmware, and initramfs. If necessary and approved, I use the previous known-good kernel as a recovery path."

# Q255. How do you troubleshoot a production server with a suspected kernel module or driver issue?

## Answer

I follow an **evidence-first approach**.

### Step 1: Understand the Impact

Determine:

```text
Network unavailable?
Storage unavailable?
USB device unavailable?
Performance problem?
Application outage?
Boot failure?
```

### Step 2: Identify the Hardware

```bash
lspci
```

```bash
lsusb
```

```bash
lsblk
```

### Step 3: Identify the Driver

```bash
lspci -k
```

For NICs:

```bash
ethtool -i eth0
```

### Step 4: Check Running Kernel

```bash
uname -r
```

### Step 5: Check Module

```bash
lsmod
```

```bash
modinfo driver_name
```

### Step 6: Check Kernel Logs

```bash
journalctl -k
```

For the current boot:

```bash
journalctl -k -b
```

For the previous boot:

```bash
journalctl -k -b -1
```

Search for errors:

```bash
journalctl -k | grep -Ei "error|fail|driver|module|firmware"
```

### Step 7: Check Recent Changes

Ask:

```text
Was the kernel upgraded?
Was a driver installed?
Was firmware changed?
Was hardware replaced?
Was the server rebooted?
Was configuration changed?
```

### Step 8: Compare With Known-Good State

For example:

```text
Working Kernel
     |
     +--> Driver version
     +--> Module
     +--> Firmware
     +--> Device state

Failing Kernel
     |
     +--> Driver version
     +--> Module
     +--> Firmware
     +--> Device state
```

### Step 9: Choose the Safest Recovery

Depending on the issue:

```text
Restart service
Reload module
Restore supported driver
Rebuild module
Boot previous kernel
Fail over workload
Replace hardware
Contact vendor/cloud provider
```

Do not unload or reload a production storage/network driver without understanding the impact.

### Step 10: Verify

After remediation:

```bash
lspci -k
```

```bash
lsmod
```

```bash
ip link
```

or:

```bash
lsblk
```

Then verify:

```text
Device
   ↓
Driver
   ↓
Kernel
   ↓
OS
   ↓
Service
   ↓
Application
```

### Production Scenario

**Interviewer:**

> "After a kernel upgrade, the production server has lost network connectivity. What will you do?"

**Strong Answer:**

> "First I would assess the impact and use the console or another approved access method if SSH is unavailable. I would check the running kernel with `uname -r`, identify the NIC with `lspci -k`, verify the driver and firmware with `ethtool -i`, inspect `lsmod`, and review `journalctl -k -b` for driver or firmware errors. I would compare the current kernel with the previous known-good kernel. If the evidence points to a kernel/driver compatibility issue, and the recovery procedure allows it, I would boot the previous known-good kernel or use the approved driver remediation. After recovery I would verify the interface, routing, connectivity, and application health before documenting the root cause."

# 🎤 Kernel Module & Driver Interview Golden Rules

```text
Module ≠ always a hardware driver
Device detected ≠ driver working
Driver installed ≠ driver loaded
Module exists ≠ module loads
Module loaded ≠ device healthy
Driver loaded ≠ device operational
Kernel upgrade ≠ driver automatically compatible
Old kernel available ≠ currently running old kernel
Firmware ≠ driver
Removing a module ≠ harmless
```

### ⚠️ Production Safety Rules

Before changing a kernel module or driver:

```text
1. Identify the exact hardware
2. Identify the running kernel
3. Identify the driver and module
4. Check current module usage
5. Review kernel logs
6. Check firmware requirements
7. Check recent kernel/driver changes
8. Confirm production impact
9. Use supported packages/vendor drivers
10. Avoid random third-party drivers
11. Do not unload critical storage/network modules blindly
12. Keep a known-good recovery path
13. Prefer reversible changes
14. Verify hardware after remediation
15. Verify services and application health
16. Document the root cause and fix
```

> **Interview mindset:** Do not say, "The driver is broken, so I will reinstall it." Say, "I will identify the hardware and driver, verify the running kernel, inspect module and firmware status, review kernel logs, correlate the issue with recent changes, and then apply the smallest supported and reversible recovery."
