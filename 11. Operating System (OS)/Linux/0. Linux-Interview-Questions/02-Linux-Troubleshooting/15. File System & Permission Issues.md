# 15. File System & Permission Issues

> File system and permission problems are common Linux production issues. Troubleshooting requires checking **filesystem health, disk space, inodes, mount points, ownership, permissions, ACLs, SELinux contexts, read-only filesystems, and open file handles**.

# Q156. How do you troubleshoot a file or directory that cannot be accessed?

## Answer

First identify the exact error.

Common errors include:

```text
Permission denied
No such file or directory
Read-only file system
Input/output error
Stale file handle
```

### Step 1: Check Whether the Path Exists

```bash
ls -ld /path/to/file
```

For a directory:

```bash
ls -ld /path/to/directory
```

### Step 2: Check Parent Directory Permissions

A user needs appropriate **execute (`x`) permission on directories** in the path to access an object inside them.

Check:

```bash
namei -l /path/to/file
```

This is very useful for finding which directory in the path is causing the problem.

### Step 3: Check Ownership and Permissions

```bash
ls -l /path/to/file
```

Example:

```text
-rw-r----- 1 appuser appgroup 1024 Sep 2 file.txt
```

Check:

```text
Owner
Group
Permissions
```

### Step 4: Check ACLs

```bash
getfacl /path/to/file
```

### Step 5: Check SELinux Context

```bash
ls -Z /path/to/file
```

### Step 6: Check Filesystem

```bash
df -h /path/to/file
```

Check mount:

```bash
findmnt /path/to/file
```

### Troubleshooting Flow

```text
File/Directory Access Problem
          |
          v
      Check Error
          |
          v
       Path Exists?
          |
          v
   Ownership / Permissions
          |
          v
       Parent Directories
          |
          v
          ACL
          |
          v
       SELinux Context
          |
          v
      Filesystem / Mount
```

### Interview Tip

> "I first identify the exact error, then check the path, parent-directory permissions, ownership, ACLs, SELinux context, and filesystem state instead of changing permissions blindly."

# Q157. How do you troubleshoot "Permission denied" errors in Linux?

## Answer

Do not immediately run:

```bash
chmod 777 file
```

First determine **which security layer is denying access**.

### Step 1: Check Current User

```bash
whoami
```

Check groups:

```bash
id
```

### Step 2: Check File Permissions

```bash
ls -l /path/to/file
```

Example:

```text
-rw------- 1 root root file.txt
```

If another user tries to read it, access may be denied.

### Step 3: Check Parent Directories

```bash
namei -l /path/to/file
```

### Step 4: Check ACL

```bash
getfacl /path/to/file
```

An ACL may grant or restrict access beyond traditional owner/group/other permissions.

### Step 5: Check SELinux

```bash
getenforce
```

Check the context:

```bash
ls -Z /path/to/file
```

Check denials:

```bash
ausearch -m AVC -ts recent
```

### Step 6: Check Mount Options

```bash
findmnt /path/to/file
```

Look for relevant mount options such as:

```text
ro
noexec
nosuid
nodev
```

### Example

```text
User
 |
 v
Linux Permissions
 |
 +-- Denied
 |
 v
ACL
 |
 v
SELinux
 |
 v
Filesystem / Mount
```

### Important

`Permission denied` can be caused by more than normal Unix permissions.

Possible causes:

* Incorrect ownership
* Incorrect mode bits
* Parent directory permissions
* ACL
* SELinux
* Mount options
* Filesystem restrictions

### Interview Tip

> "For a permission denied error, I check the user identity, file ownership, mode bits, parent directories, ACLs, SELinux context, and mount options. I never use `chmod 777` as a first troubleshooting step."

# Q158. How do you troubleshoot a disk or filesystem that is full?

## Answer

First determine whether the problem is:

```text
Disk space exhaustion
OR
Inode exhaustion
```

### Step 1: Check Filesystem Usage

```bash
df -h
```

Example:

```text
Filesystem      Size  Used Avail Use%
/dev/sda2        50G   49G  1G   98%
```

This indicates the filesystem is almost full.

### Step 2: Find Large Directories

Start from the affected filesystem:

```bash
du -xhd1 / | sort -h
```

For a specific directory:

```bash
du -xhd1 /var | sort -h
```

### Step 3: Find Large Files

Example:

```bash
find /var -xdev -type f -size +1G -ls
```

### Step 4: Check Inodes

```bash
df -i
```

Example:

```text
Filesystem      Inodes  IUsed  IFree IUse%
/dev/sda2       3.2M    3.2M      0  100%
```

The filesystem may have free disk space but no available inodes.

### Step 5: Check Deleted but Open Files

A deleted file can continue consuming disk space while a process still has it open.

```bash
lsof +L1
```

### Example

```text
Disk Usage = 95%
       |
       v
df -h
       |
       +-- Large Files
       |
       +-- Deleted Open Files
       |
       +-- Logs
       |
       +-- Application Data
```

### Common Causes

* Large application logs
* Backup files
* Temporary files
* Core dumps
* Database files
* Container images/logs
* Deleted but open files
* Too many small files

### Production Warning

Do not blindly delete files from:

```text
/var
/opt
database directories
application directories
```

First identify what created them and whether they are safe to remove.

### Interview Tip

> "I first check `df -h` and `df -i` to distinguish space exhaustion from inode exhaustion. Then I investigate large files, application logs, temporary data, and deleted-but-open files."

# Q159. What is the difference between disk space and inode exhaustion?

## Answer

Linux filesystems have two important resources:

```text
Disk Blocks
Inodes
```

### Disk Space

Disk space stores the actual file data.

Check:

```bash
df -h
```

Example:

```text
Use% = 98%
```

This indicates the filesystem is almost out of storage capacity.

### Inodes

An inode stores filesystem metadata about a file, such as:

```text
Owner
Permissions
File type
Timestamps
Pointers to data
```

Check:

```bash
df -i
```

### Example: Disk Full

```text
Disk:
100 GB
Used:
99 GB

Inodes:
50%
```

The problem is mainly disk space.

### Example: Inode Full

```text
Disk:
100 GB
Used:
40 GB

Inodes:
100%
```

The filesystem can have significant free space but cannot create new files.

### Common Cause of Inode Exhaustion

Millions of small files:

```text
/tmp
cache directories
application temporary files
mail queues
session files
```

### Troubleshooting

Check:

```bash
df -h
```

and:

```bash
df -i
```

Find directories containing large numbers of files:

```bash
find /var -xdev -type f | cut -d/ -f1-4 | sort | uniq -c | sort -n | tail
```

For large directory trees, use more targeted investigation rather than running expensive commands across the entire filesystem.

### Interview Tip

> "Disk space tracks storage capacity, while inodes track the number of filesystem objects. A filesystem can have free disk space but still fail to create files when all inodes are exhausted."

# Q160. How do you troubleshoot a filesystem that becomes read-only?

## Answer

A filesystem mounted as read-only can cause:

```text
Application failures
Unable to create files
Unable to write logs
Database errors
Service failures
```

### Step 1: Confirm Mount Status

```bash
findmnt /mount/point
```

or:

```bash
mount | grep /mount/point
```

Look for:

```text
ro
```

### Step 2: Check Kernel Logs

```bash
journalctl -k --since "30 minutes ago"
```

Also:

```bash
dmesg -T | grep -iE "error|I/O|filesystem|read-only"
```

### Step 3: Check Disk Health

```bash
lsblk
```

Check filesystem space:

```bash
df -h
```

### Step 4: Check for I/O Errors

Look for messages such as:

```text
I/O error
Buffer I/O error
Filesystem error
Device error
```

### Common Causes

* Filesystem errors
* Storage failure
* Disk I/O errors
* Underlying SAN/cloud storage problems
* Kernel detecting filesystem corruption
* Filesystem intentionally mounted read-only

### Important

Do not immediately run a filesystem repair command on a mounted production filesystem.

For filesystem checks such as:

```bash
fsck
```

the filesystem usually needs to be **unmounted or checked in an appropriate maintenance/recovery environment**, depending on filesystem type and operational procedure.

### Troubleshooting Flow

```text
Filesystem Read-Only
        |
        v
Check findmnt
        |
        v
Check Kernel Logs
        |
        v
Check I/O Errors
        |
        v
Check Storage
        |
        v
Plan Maintenance
        |
        v
Filesystem Repair if Required
        |
        v
Remount / Restore Service
        |
        v
Verify
```

### Interview Tip

> "If a filesystem unexpectedly becomes read-only, I check the mount state and kernel logs for filesystem or I/O errors. I do not blindly run `fsck` on a mounted production filesystem; I follow the appropriate recovery procedure."

# Q161. How do you troubleshoot mount and unmount issues?

## Answer

### Check Existing Mounts

```bash
findmnt
```

For a specific mount point:

```bash
findmnt /data
```

### Check Disk and Filesystem

```bash
lsblk -f
```

This shows:

```text
Device
Filesystem
UUID
Mount Point
```

### Check `/etc/fstab`

```bash
cat /etc/fstab
```

A wrong entry can cause mount problems during boot.

### Test a Mount

```bash
mount /data
```

or, when using an `fstab` entry:

```bash
mount /data
```

Check the error message carefully.

### Common Mount Errors

```text
wrong filesystem type
bad option
missing device
invalid UUID
permission denied
network unavailable
filesystem corrupted
```

### Unmount

```bash
umount /data
```

If you get:

```text
target is busy
```

find which processes are using it:

```bash
lsof +D /data
```

or:

```bash
fuser -vm /data
```

### Common Reasons for "Target is Busy"

* Shell's current directory is inside the mount
* Application has files open
* Process is accessing the filesystem
* Another mount exists below it

Check:

```bash
pwd
```

in relevant shells and inspect processes.

### NFS Example

For NFS mounts, also check:

```bash
findmnt -t nfs,nfs4
```

and network/reachability to the NFS server.

### Important

Avoid forceful unmounting in production unless you understand the impact.

```text
Application
    |
    v
Files Open
    |
    v
Unmount Request
    |
    X
Target is Busy
```

First identify and safely stop or move the workload using the mount.

### Interview Tip

> "For mount issues I check `findmnt`, `lsblk -f`, `/etc/fstab`, filesystem type and options. For an unmount failure, I identify processes holding the filesystem with `lsof` or `fuser` before taking action."

# Q162. How do you troubleshoot incorrect file ownership and permissions?

## Answer

First inspect:

```bash
ls -l /path/to/file
```

Example:

```text
-rw-r----- 1 root appgroup file.txt
```

This tells us:

```text
Owner = root
Group = appgroup
```

### Check User

```bash
id username
```

This shows the user's groups.

### Change Ownership

If the ownership is genuinely incorrect:

```bash
sudo chown appuser:appgroup /path/to/file
```

For a directory tree:

```bash
sudo chown -R appuser:appgroup /path/to/directory
```

### ⚠️ Be Careful With `-R`

Recursive ownership changes can affect thousands of files and potentially break system applications.

Always verify the target path first.

### Change Permissions

Example:

```bash
chmod 640 /path/to/file
```

This means:

```text
Owner  → read/write
Group  → read
Other  → no access
```

### Directory Permissions

For a directory:

```bash
chmod 750 /path/to/directory
```

Remember:

```text
r = list/read directory entries
w = create/delete/rename entries
x = access/traverse directory
```

### Check the Complete Path

```bash
namei -l /path/to/file
```

### Important

Do not automatically use:

```bash
chmod 777
```

This gives broad access and may create a security problem.

### Interview Tip

> "I first identify the required application user and access level, then correct ownership and permissions using the minimum required privileges. I avoid recursive or `777` changes unless there is a specific, justified requirement."

# Q163. How do you troubleshoot ACL and SELinux permission issues?

## Answer

Linux access can involve multiple security layers.

```text
Traditional Permissions
        +
ACL
        +
SELinux
        |
        v
Access Decision
```

### Check Standard Permissions

```bash
ls -l /path/to/file
```

### Check ACL

```bash
getfacl /path/to/file
```

Example:

```text
user::rw-
user:alice:r--
group::r--
mask::r--
other::---
```

### Set an ACL

If the requirement is to give a specific user access without changing the normal owner/group model:

```bash
sudo setfacl -m u:alice:r /path/to/file
```

Verify:

```bash
getfacl /path/to/file
```

### Remove an ACL

```bash
sudo setfacl -x u:alice /path/to/file
```

### Check SELinux

```bash
getenforce
```

Check context:

```bash
ls -Z /path/to/file
```

Check denials:

```bash
ausearch -m AVC -ts recent
```

### Example

```text
ls -l
   |
   v
Permissions look correct
   |
   v
getfacl
   |
   v
ACL looks correct
   |
   v
SELinux AVC denial
   |
   v
Incorrect SELinux context/policy
```

### Important ACL Concept

The ACL **mask** can limit the effective permissions of named users and groups.

Therefore, do not look only at:

```text
user:alice:rwx
```

Also check:

```text
mask
```

### Interview Tip

> "When normal permissions look correct but access is still denied, I check ACLs with `getfacl` and SELinux contexts and AVC logs. I also check the ACL mask because it can limit effective permissions."

# Q164. How do you find which process is using or holding a file?

## Answer

Use:

```bash
lsof /path/to/file
```

Example:

```bash
lsof /var/log/myapp.log
```

This can show:

```text
COMMAND
PID
USER
FD
TYPE
FILE
```

### Find Processes Using a Directory

```bash
lsof +D /data
```

For large directories, this can be expensive.

An alternative is:

```bash
fuser -vm /data
```

### Deleted but Open Files

A common production scenario is:

```text
Application writes large log
       |
       v
Log file deleted
       |
       v
Application still has file open
       |
       v
Disk space is still consumed
```

Find such files:

```bash
lsof +L1
```

### Example

```text
COMMAND   PID   USER   FD   NAME
java      2450  app    1w   /var/log/app.log (deleted)
```

The file was deleted from the directory but remains open by the Java process.

### Why This Matters

`df -h` may show:

```text
Filesystem = 95% full
```

while:

```bash
du -sh /var/log
```

does not appear large enough.

One possible reason is deleted-but-open files.

### Troubleshooting Flow

```text
Filesystem Full
      |
      v
df -h
      |
      v
du
      |
      v
Size Doesn't Match?
      |
      v
lsof +L1
      |
      v
Deleted Open File
      |
      v
Identify Process
      |
      v
Gracefully Restart / Reopen Logs
```

### Important

Do not manually delete `/proc/<PID>/fd/*` or kill a critical production process just to reclaim space.

Determine the correct application-specific method to close or rotate the file.

### Interview Tip

> "I use `lsof` or `fuser` to identify processes holding files. For disk usage discrepancies, `lsof +L1` is particularly useful for finding deleted files that are still open."

# Q165. How do you troubleshoot a production filesystem and permission issue end-to-end?

## Answer

I use a structured approach and first determine whether the issue is related to **space, filesystem state, mount configuration, permissions, ACLs, or SELinux**.

### Step 1: Confirm the Problem

Determine:

```text
What application is affected?
Which path is affected?
What exact error is reported?
When did it start?
Are all users affected?
```

### Step 2: Check Filesystem Space

```bash
df -h
```

### Step 3: Check Inodes

```bash
df -i
```

### Step 4: Check Mount

```bash
findmnt /path/to/file
```

### Step 5: Check Filesystem and Device

```bash
lsblk -f
```

### Step 6: Check Permissions

```bash
ls -l /path/to/file
```

### Step 7: Check Complete Path

```bash
namei -l /path/to/file
```

### Step 8: Check ACL

```bash
getfacl /path/to/file
```

### Step 9: Check SELinux

```bash
getenforce
```

```bash
ls -Z /path/to/file
```

If required:

```bash
ausearch -m AVC -ts recent
```

### Step 10: Check Open Files

```bash
lsof /path/to/file
```

If disk usage is unexpected:

```bash
lsof +L1
```

### Step 11: Check Kernel Logs

```bash
journalctl -k --since "30 minutes ago"
```

Look for:

```text
I/O errors
Filesystem errors
Device errors
Read-only filesystem
```

### Step 12: Identify Root Cause

```text
                    FILESYSTEM ISSUE
                           |
          +----------------+----------------+
          |                |                |
          v                v                v
       Space            Inodes           Mount
          |                |                |
          +----------------+----------------+
                           |
                           v
                     Permissions
                           |
                 +---------+---------+
                 |         |         |
                 v         v         v
              Owner      ACL      SELinux
                 |         |         |
                 +---------+---------+
                           |
                           v
                    Process / Files
                           |
                           v
                     Kernel / I/O
                           |
                           v
                       Root Cause
```

### Step 13: Apply the Minimum Fix

Possible fixes:

```text
Remove confirmed unnecessary data
        OR
Fix log rotation
        OR
Correct ownership
        OR
Correct permissions
        OR
Fix ACL
        OR
Restore SELinux context
        OR
Correct mount configuration
        OR
Resolve storage problem
```

### Step 14: Verify

Check:

```text
Filesystem space
Inodes
Mount status
Permissions
Application
Logs
User access
```

### Production Interview Scenario

**Interviewer:**

> "A production application suddenly cannot write to `/data`. What will you check?"

**Strong Answer:**

> "First I will confirm the exact application error and affected path. I will check filesystem space with `df -h` and inode usage with `df -i`, then verify the mount using `findmnt` and the filesystem/device with `lsblk -f`. If the filesystem is available, I will check ownership and permissions with `ls -l` and `namei`, followed by ACLs using `getfacl` and SELinux context and denials if applicable. I will also check whether another process is holding the file and review kernel logs for I/O or filesystem errors. Once I identify the root cause, I will apply the smallest safe fix, verify application functionality, and document the incident."

# 🎤 File System & Permission Interview Golden Rules

```text
Permission denied ≠ automatically chmod 777
Disk full ≠ automatically large files
Free disk space ≠ files can always be created
Correct owner ≠ access is guaranteed
Correct permissions ≠ SELinux allows access
Unmount failed ≠ automatically force unmount
Read-only filesystem ≠ automatically run fsck
Deleted file ≠ disk space immediately reclaimed
High disk usage ≠ automatically filesystem failure
```

Always check:

```text
Filesystem Space
 +
Inodes
 +
Mount Status
 +
Filesystem Type
 +
Ownership
 +
Permissions
 +
Parent Directories
 +
ACL
 +
SELinux
 +
Open Files
 +
Kernel / I/O Errors
```

### ⚠️ Production Safety Rules

Before changing filesystem or permission configuration:

```text
1. Confirm the exact affected path
2. Identify the application and user
3. Check filesystem and inode usage
4. Check mount status
5. Check ownership and permissions
6. Check ACL and SELinux where applicable
7. Collect logs before making destructive changes
8. Avoid chmod 777 as a workaround
9. Avoid blind recursive chown/chmod
10. Do not run fsck blindly on a mounted production filesystem
11. Avoid forceful unmount unless operationally justified
12. Verify application functionality after the fix
13. Document the root cause and permanent fix
```

> **Interview mindset:** Do not say, "The application cannot write, so I will change the permissions." Say, "I will first identify the exact error, verify filesystem space, mount status, ownership, permissions, ACLs, and SELinux, identify the actual root cause, and apply the minimum required fix."
