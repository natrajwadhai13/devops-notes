# 33. Nginx Troubleshooting

> Nginx is commonly used as a **web server, reverse proxy, load balancer, and TLS termination point**. Production troubleshooting should follow the request path: **DNS → TCP → TLS → Nginx → Upstream → Application → Dependencies**.

# Q336. What is Nginx and how do you check whether it is running?

## Answer

**Nginx** is a high-performance web server that can also work as:

```text
Web Server
Reverse Proxy
Load Balancer
TLS Termination Point
Static File Server
```

### Common Architecture

```text
Client
   |
   | HTTP/HTTPS
   v
 Nginx
   |
   | proxy_pass
   v
Application
   |
   v
Database
```

### Step 1: Check Nginx Service

```bash
systemctl status nginx
```

Quick check:

```bash
systemctl is-active nginx
```

Check whether it starts automatically:

```bash
systemctl is-enabled nginx
```

### Step 2: Check Nginx Process

```bash
pgrep -a nginx
```

Or:

```bash
ps -ef | grep nginx
```

Typical architecture:

```text
nginx master process
nginx worker processes
```

### Step 3: Check Listening Ports

```bash
ss -lntp | grep -E ':80|:443'
```

Example:

```text
LISTEN 0 511 0.0.0.0:80
LISTEN 0 511 0.0.0.0:443
```

### Step 4: Test Locally

```bash
curl -v http://127.0.0.1
```

For HTTPS:

```bash
curl -vk https://127.0.0.1
```

`-k` skips certificate verification and should be used only for troubleshooting.

### Step 5: Check Configuration

```bash
nginx -t
```

### Step 6: Check Logs

```bash
journalctl -u nginx
```

Common Nginx logs:

```bash
tail -f /var/log/nginx/access.log
```

```bash
tail -f /var/log/nginx/error.log
```

Actual log locations can be changed in Nginx configuration.

### Important

```text
Nginx process running
       ≠
Nginx application working correctly
```

### Interview Tip

> "I check the systemd service, Nginx processes, listening ports, configuration syntax, local HTTP response, and access/error logs."

# Q337. How do you troubleshoot when Nginx fails to start?

## Answer

Do not repeatedly restart Nginx.

First identify the exact error.

### Step 1: Check Service Status

```bash
systemctl status nginx
```

### Step 2: Check Systemd Logs

```bash
journalctl -u nginx -n 100
```

For the current boot:

```bash
journalctl -u nginx -b
```

### Step 3: Test Configuration

```bash
nginx -t
```

Example:

```text
nginx: [emerg] unexpected "}" in /etc/nginx/nginx.conf:25
```

This immediately identifies a configuration problem.

### Step 4: Check Port Conflicts

```bash
ss -lntp | grep -E ':80|:443'
```

Example:

```text
Another service is already listening on port 80.
```

Identify the process:

```bash
ss -lntp
```

### Step 5: Check Configuration Files

```bash
nginx -T
```

This displays the effective configuration.

Look for:

```text
listen
server_name
root
proxy_pass
ssl_certificate
ssl_certificate_key
include
```

### Step 6: Check Certificate Files

If HTTPS is configured:

```bash
ls -l /path/to/certificate
```

```bash
ls -l /path/to/private-key
```

Verify that Nginx can access them.

### Step 7: Check Permissions

```bash
namei -l /path/to/certificate
```

### Step 8: Check Disk

```bash
df -h
```

```bash
df -i
```

A full filesystem can prevent Nginx from starting or writing logs.

### Common Causes

```text
Configuration syntax error
Port already in use
Missing certificate
Incorrect certificate path
Permission problem
Missing included file
Invalid upstream configuration
Disk full
SELinux restriction
Package/module problem
```

### Safe Flow

```text
Nginx failed
    |
    v
systemctl status
    |
    v
journalctl
    |
    v
nginx -t
    |
    +---- FAIL ----> Fix configuration
    |
    +---- PASS
           |
           v
     Check ports/files/
     permissions/resources
           |
           v
        Start Nginx
           |
           v
         Verify
```

### Interview Tip

> "If Nginx fails to start, I check `systemctl status`, `journalctl`, and especially `nginx -t` before restarting it. Then I check port conflicts, certificates, included files, permissions, disk space, and SELinux if relevant."

# Q338. How do you troubleshoot Nginx configuration errors?

## Answer

Nginx configuration is hierarchical and can include multiple files.

### Step 1: Test Configuration

```bash
nginx -t
```

This is the first command I would use after a configuration change.

### Step 2: View Effective Configuration

```bash
nginx -T
```

This is useful when configuration is split across:

```text
/etc/nginx/nginx.conf
/etc/nginx/conf.d/
/etc/nginx/sites-enabled/
```

The exact directory structure depends on the distribution and installation.

### Step 3: Check Main Configuration

```bash
less /etc/nginx/nginx.conf
```

Look for:

```text
include
events
http
server
location
upstream
```

### Step 4: Check Common Syntax Problems

Examples:

```text
Missing ;
Missing }
Invalid directive
Incorrect nesting
Wrong file path
Duplicate/conflicting configuration
```

### Step 5: Check File References

If Nginx reports:

```text
No such file or directory
```

check:

```bash
ls -l /path/to/file
```

### Step 6: Check Permissions

```bash
namei -l /path/to/file
```

### Step 7: Validate Again

```bash
nginx -t
```

Only after it succeeds should you apply the change.

### Step 8: Reload When Appropriate

```bash
systemctl reload nginx
```

Then verify:

```bash
systemctl status nginx
```

### Important

Do not manually edit:

```text
/var/run/
/run/
```

generated/runtime files to fix a persistent Nginx configuration problem.

Fix the actual configuration source.

### Interview Tip

> "`nginx -t` validates the configuration syntax and referenced configuration structure. `nginx -T` helps me inspect the complete effective configuration when multiple files are involved."

# Q339. How do you troubleshoot Nginx 502 Bad Gateway errors?

## Answer

A 502 from Nginx usually indicates a problem communicating with the **upstream backend**.

Example:

```text
Client
  |
  v
Nginx
  |
  X
Upstream Application
```

### Step 1: Confirm the Error

```bash
curl -v https://app.example.com
```

### Step 2: Check Nginx Error Log

```bash
tail -f /var/log/nginx/error.log
```

Look for messages such as:

```text
connect() failed
connection refused
upstream timed out
no route to host
upstream prematurely closed connection
```

### Step 3: Check Upstream Configuration

```bash
nginx -T | grep -n "proxy_pass"
```

Example:

```nginx
proxy_pass http://127.0.0.1:8080;
```

Verify:

```text
IP
Port
Protocol
```

### Step 4: Check Backend Listener

```bash
ss -lntp | grep :8080
```

### Step 5: Test Backend Directly

```bash
curl -v http://127.0.0.1:8080
```

If this fails, investigate the backend application.

### Step 6: Check Backend Service

```bash
systemctl status <application-service>
```

### Step 7: Check Firewall

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 8: Check SELinux

```bash
getenforce
```

If Nginx is prevented from making network connections, inspect AVC denials:

```bash
ausearch -m AVC -ts recent
```

### Step 9: Check DNS

If `proxy_pass` uses a hostname:

```nginx
proxy_pass http://backend.example.com:8080;
```

test:

```bash
getent hosts backend.example.com
```

```bash
dig backend.example.com
```

### Common Causes

```text
Backend stopped
Wrong backend port
Wrong backend IP
Connection refused
DNS failure
Firewall
SELinux
Backend crash
Invalid upstream response
TLS problem to upstream
```

### Interview Tip

> "For Nginx 502, I focus on the Nginx-to-upstream path. I inspect the error log, verify `proxy_pass`, check the backend listener, test the backend directly, and then investigate firewall, DNS, SELinux, and TLS if applicable."

# Q340. How do you troubleshoot Nginx 504 Gateway Timeout errors?

## Answer

A 504 generally means Nginx did not receive a timely response from the upstream.

### Step 1: Confirm

```bash
curl -v https://app.example.com
```

### Step 2: Check Nginx Error Log

```bash
tail -f /var/log/nginx/error.log
```

Look for:

```text
upstream timed out
```

### Step 3: Test Backend Directly

```bash
time curl -v http://127.0.0.1:8080
```

If the backend itself is slow, Nginx may only be reporting the symptom.

### Step 4: Check Application Logs

```bash
journalctl -u <application-service>
```

Look for:

```text
Slow request
Database timeout
External API timeout
Thread exhaustion
Connection pool exhaustion
```

### Step 5: Check Nginx Timeout Configuration

Inspect:

```bash
nginx -T | grep -E 'proxy_connect_timeout|proxy_read_timeout|proxy_send_timeout'
```

Common directives:

```text
proxy_connect_timeout
proxy_read_timeout
proxy_send_timeout
```

### Step 6: Check Database/Dependencies

The application may be waiting for:

```text
Database
Redis
External API
DNS
Message queue
Storage
```

### Step 7: Check Resources

```bash
top
```

```bash
free -h
```

```bash
iostat -xz 1
```

### Important

Do not simply increase:

```nginx
proxy_read_timeout
```

without understanding why the backend is slow.

Example:

```text
Backend response = 120 seconds
Nginx timeout = 60 seconds
```

Nginx returns 504.

Increasing the timeout may hide a slow database query or application bottleneck.

### Interview Tip

> "For a 504, I compare Nginx timeout values with actual upstream response time and investigate the application and downstream dependencies before changing timeout values."

# Q341. How do you troubleshoot Nginx 403 Forbidden and 404 Not Found errors?

## Answer

These errors commonly involve:

```text
Permissions
Document root
Location rules
Server block
URL
SELinux
Application routing
```

## 403 Forbidden

### Step 1: Check Nginx Error Log

```bash
tail -f /var/log/nginx/error.log
```

### Step 2: Check File Permissions

```bash
ls -l /var/www/html/index.html
```

### Step 3: Check Directory Permissions

```bash
namei -l /var/www/html/index.html
```

Nginx needs appropriate traversal permissions on parent directories.

### Step 4: Check SELinux

```bash
ls -Z /var/www/html/index.html
```

```bash
getenforce
```

If relevant:

```bash
ausearch -m AVC -ts recent
```

### Step 5: Check Nginx Configuration

```bash
nginx -T
```

Look for:

```text
root
location
deny
allow
internal
```

---

## 404 Not Found

### Step 1: Check Requested URL

```bash
curl -v http://example.com/test
```

### Step 2: Check Document Root

```bash
nginx -T | grep -n "root "
```

### Step 3: Check File

```bash
ls -l /var/www/html/test
```

### Step 4: Check Server Block

Verify:

```text
server_name
listen
root
location
```

### Step 5: Check Application Routing

A 404 can be generated by the application rather than Nginx.

### Important

Do not immediately use:

```bash
chmod 777
```

or:

```bash
chown -R
```

Understand the actual permission problem first.

### Interview Tip

> "For 403 I check permissions, directory traversal, Nginx access rules, SELinux, and the effective configuration. For 404 I check URL, server block, document root, location rules, and whether the response actually comes from the application."

# Q342. How do you troubleshoot Nginx SSL/TLS certificate problems?

## Answer

Nginx commonly terminates HTTPS on port 443.

### Step 1: Test HTTPS

```bash
curl -v https://example.com
```

### Step 2: Inspect Certificate

```bash
openssl s_client -connect example.com:443 -servername example.com
```

### Step 3: Check Certificate Dates

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -dates
```

### Step 4: Check SAN

```bash
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
```

The requested hostname must be covered by the certificate SAN.

### Step 5: Check Nginx Configuration

```bash
nginx -T | grep -n -E 'ssl_certificate|ssl_certificate_key'
```

Example:

```nginx
ssl_certificate /etc/nginx/ssl/server.crt;
ssl_certificate_key /etc/nginx/ssl/server.key;
```

### Step 6: Check Files

```bash
ls -l /etc/nginx/ssl/
```

### Step 7: Check Private-Key Permissions

The Nginx master process needs appropriate access to the private key.

Do not make the private key world-readable.

### Step 8: Validate Configuration

```bash
nginx -t
```

### Step 9: Check SNI/Server Blocks

Multiple HTTPS websites may have:

```text
example.com
api.example.com
admin.example.com
```

Nginx selects the appropriate server block based partly on the requested hostname/SNI.

Test:

```bash
openssl s_client -connect <server-ip>:443 -servername example.com
```

### Common Causes

```text
Expired certificate
Wrong certificate
Hostname mismatch
Missing intermediate certificate
Wrong certificate path
Wrong private key
Incorrect permissions
Incorrect server block
SNI issue
TLS policy mismatch
```

### Interview Tip

> "For Nginx TLS problems, I verify the certificate externally with `openssl`, then inspect the certificate and key configuration, SAN, expiry, SNI, permissions, and `nginx -t`."

# Q343. How do you troubleshoot Nginx upstream, proxy_pass, and connection problems?

## Answer

Nginx often acts as a reverse proxy.

Example:

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
```

Request flow:

```text
Client
  |
  | HTTPS :443
  v
Nginx
  |
  | HTTP :8080
  v
Application
```

### Step 1: Inspect Effective Configuration

```bash
nginx -T
```

Look for:

```text
proxy_pass
upstream
proxy_set_header
proxy_connect_timeout
proxy_read_timeout
```

### Step 2: Check Backend Listener

```bash
ss -lntp | grep :8080
```

### Step 3: Test Backend

```bash
curl -v http://127.0.0.1:8080
```

### Step 4: Check DNS

If hostname is used:

```bash
getent hosts backend.example.com
```

### Step 5: Check Routing

```bash
ip route get <backend-ip>
```

### Step 6: Check Firewall

```bash
firewall-cmd --list-all
```

### Step 7: Check SELinux

```bash
getenforce
```

For relevant AVC denials:

```bash
ausearch -m AVC -ts recent
```

### Step 8: Check Nginx Error Logs

```bash
tail -f /var/log/nginx/error.log
```

### Common Errors

```text
Connection refused
Connection timed out
No route to host
Host not found
Upstream prematurely closed connection
SSL handshake failure
```

### Important `proxy_pass` Detail

The URI behavior of `proxy_pass` can change depending on whether it includes a URI component.

For example:

```nginx
location /api/ {
    proxy_pass http://backend;
}
```

and:

```nginx
location /api/ {
    proxy_pass http://backend/;
}
```

can produce different upstream request paths.

Therefore, when troubleshooting routing problems, inspect the exact `location` and `proxy_pass` configuration rather than assuming they behave identically.

### Interview Tip

> "For upstream problems, I verify the exact `proxy_pass` behavior, backend IP and port, listener, DNS, routing, firewall, SELinux, and Nginx error logs."

# Q344. How do you troubleshoot high CPU, memory, or connection usage in Nginx?

## Answer

Nginx uses a master/worker architecture.

High resource usage can be caused by:

```text
High traffic
Too many connections
Slow clients
Large responses
Application/backend latency
Configuration
Abnormal requests
Resource leaks
```

### Step 1: Check CPU and Memory

```bash
top
```

Find Nginx processes:

```bash
ps -eo pid,ppid,%cpu,%mem,cmd --sort=-%cpu | head
```

### Step 2: Check Nginx Processes

```bash
pgrep -a nginx
```

### Step 3: Check Connections

```bash
ss -s
```

For Nginx-related connections:

```bash
ss -antp | grep nginx
```

### Step 4: Check Listening Configuration

```bash
nginx -T
```

### Step 5: Check Access Logs

Look for:

```text
High request rate
Repeated requests
Large response downloads
Specific endpoint
Specific client
5xx responses
```

Example:

```bash
tail -f /var/log/nginx/access.log
```

### Step 6: Check Error Logs

```bash
tail -f /var/log/nginx/error.log
```

### Step 7: Check Backend Performance

Nginx may appear busy because upstream applications are slow.

Check:

```bash
top
free -h
iostat -xz 1
```

### Step 8: Check File Descriptors

```bash
ulimit -n
```

Check current open files:

```bash
ls /proc/$(pgrep -o nginx)/fd | wc -l
```

For detailed inspection:

```bash
lsof -p <nginx-pid>
```

### Step 9: Check Connection Limits

Inspect configuration:

```bash
nginx -T | grep -E 'worker_connections|worker_processes'
```

### Step 10: Check Traffic Pattern

Determine whether the issue is:

```text
Normal traffic increase
Traffic spike
Bot/scanner activity
Abnormal client
Application slowdown
Backend failure
```

### Important

Do not automatically increase:

```text
worker_processes
worker_connections
worker_rlimit_nofile
```

without understanding CPU, memory, file-descriptor, and operating-system limits.

Increasing limits does not automatically solve a backend bottleneck.

### Interview Tip

> "For high Nginx resource usage, I identify whether the pressure comes from traffic, connections, slow upstreams, file descriptors, or abnormal requests, then correlate Nginx logs with system metrics."

# Q345. How do you troubleshoot a complete production Nginx issue?

## Answer

I use a layer-by-layer approach.

```text
Client
  |
  v
DNS
  |
  v
TCP
  |
  v
TLS
  |
  v
Nginx
  |
  v
Upstream
  |
  v
Application
  |
  v
Database / Dependencies
```

### Step 1: Define the Problem

Identify:

```text
Hostname
URL
HTTP/HTTPS
Source
Time of failure
HTTP status
All users or some users?
All endpoints or one endpoint?
Permanent or intermittent?
```

### Step 2: Check DNS

```bash
getent hosts app.example.com
```

```bash
dig app.example.com
```

### Step 3: Check TCP

```bash
nc -vz app.example.com 443
```

### Step 4: Check TLS

```bash
openssl s_client -connect app.example.com:443 -servername app.example.com
```

### Step 5: Check HTTP

```bash
curl -v https://app.example.com
```

Record:

```text
HTTP status
Response headers
Response time
Redirects
```

### Step 6: Check Nginx Service

```bash
systemctl status nginx
```

### Step 7: Validate Configuration

```bash
nginx -t
```

### Step 8: Inspect Effective Configuration

```bash
nginx -T
```

### Step 9: Check Listening Ports

```bash
ss -lntp | grep -E ':80|:443'
```

### Step 10: Check Nginx Logs

Access log:

```bash
tail -f /var/log/nginx/access.log
```

Error log:

```bash
tail -f /var/log/nginx/error.log
```

Systemd:

```bash
journalctl -u nginx
```

### Step 11: Identify the HTTP Error

```text
4xx
  ↓
Request/access/routing investigation

5xx
  ↓
Server/upstream/application investigation
```

For example:

```text
502 → upstream communication
503 → service/backend availability
504 → upstream timeout
```

### Step 12: Check Upstream

```bash
ss -lntp | grep :8080
```

Then:

```bash
curl -v http://127.0.0.1:8080
```

### Step 13: Check Firewall/Security

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

Check SELinux if relevant:

```bash
getenforce
```

### Step 14: Check Resources

```bash
top
```

```bash
free -h
```

```bash
df -h
```

```bash
iostat -xz 1
```

### Step 15: Check Application and Dependencies

```text
Nginx
  |
  v
Application
  |
  +---- Database
  |
  +---- Redis
  |
  +---- External API
  |
  +---- DNS
  |
  +---- Storage
```

### Step 16: Check Recent Changes

Look for:

```text
Nginx configuration
Certificate renewal
DNS changes
Firewall changes
Application deployment
Backend port changes
OS/package update
Load-balancer changes
```

### Step 17: Compare Healthy vs Unhealthy Backend

If only one backend is failing:

```text
Backend-1 → Healthy
Backend-2 → Failing
Backend-3 → Healthy
```

Compare:

```text
Nginx configuration
Application version
Network
Firewall
Resources
Logs
Health endpoint
Dependencies
```

### Step 18: Use Packet Capture if Necessary

```bash
sudo tcpdump -ni any port 443
```

For Nginx-to-backend traffic:

```bash
sudo tcpdump -ni any port 8080
```

Use targeted captures in production.

### Step 19: Apply the Smallest Safe Fix

Examples:

```text
Fix Nginx configuration
Correct upstream port
Fix backend service
Correct certificate
Fix permissions
Fix firewall rule
Fix SELinux context/policy
Rollback bad deployment
Remove unhealthy backend
```

### Step 20: Verify End-to-End

```text
DNS
 ↓
TCP
 ↓
TLS
 ↓
Nginx
 ↓
Upstream
 ↓
Application
 ↓
Dependencies
```

### Production Scenario

**Interviewer:**

> "The production website is returning 502 errors through Nginx. How will you troubleshoot it?"

**Strong Answer:**

> "First I would confirm the scope and reproduce the 502 using `curl -v`. I would check DNS and TCP connectivity, then verify the Nginx service and run `nginx -t`. I would inspect the Nginx error log because it usually provides the reason for an upstream failure. Then I would inspect the effective configuration with `nginx -T`, verify the `proxy_pass` target and backend port, check whether the backend is listening with `ss`, and test the backend directly with `curl`. If that fails, I would troubleshoot the application, firewall, routing, SELinux, or DNS depending on the error. I would also check system resources and recent changes. If necessary, I would use targeted packet capture to confirm the Nginx-to-backend traffic flow. After identifying the failing layer, I would make the smallest reversible change, verify the complete request path, monitor the service, and document the root cause."

# 🎤 Nginx Interview Golden Rules


# ⚠️ Production Safety Rules

Before changing Nginx in production:

```text
1. Identify the exact URL
2. Identify the hostname
3. Check DNS
4. Check TCP connectivity
5. Check TLS if HTTPS
6. Record the HTTP status
7. Check Nginx service
8. Run nginx -t before applying configuration
9. Inspect nginx -T when configuration is complex
10. Check access and error logs
11. Check listening ports
12. Verify upstream configuration
13. Test backend directly
14. Check firewall/security controls
15. Check SELinux where relevant
16. Check CPU/memory/disk
17. Check application logs
18. Check database/external dependencies
19. Check recent changes
20. Avoid blind restarts
21. Avoid blindly increasing timeouts
22. Protect TLS private keys
23. Make the smallest reversible change
24. Prefer reload when appropriate
25. Verify end-to-end
26. Monitor after the change
27. Document the root cause
```

> **Interview mindset:** Don't say **"Nginx is giving 502, so I will restart Nginx."** Say: **"I will confirm the 502, inspect the Nginx error log, validate the configuration, verify the upstream target and port, test the backend directly, and then investigate network, firewall, SELinux, TLS, application, and dependency issues based on the evidence."**
