# 09. Memory Issues

# Q81. How do you troubleshoot high memory usage?

## Answer

First check overall memory usage:

```bash
free -h
```

Example:

```text
              total   used   free   shared  buff/cache  available
Mem:            16G    14G    500M    200M        1.5G       1.2G
Swap:            4G     2G      2G
```

Then identify memory-consuming processes:

```bash
top
```

or:

```bash
ps aux --sort=-%mem | head
```

Check memory statistics:

```bash
vmstat 1 5
```

Check swap:

```bash
swapon --show
```

### Troubleshooting Flow

```text
High Memory Usage
       |
       v
    free -h
       |
       v
Check available memory
       |
       v
    top / ps
       |
       v
Find top memory process
       |
       v
Check swap
       |
       v
Check application logs
       |
       v
Identify root cause
```

### Common Causes

* Memory-intensive application
* Application memory leak
* Too many processes
* Large JVM heap
* Database workload
* Cache usage
* Insufficient RAM
* Memory pressure

### Interview Tip

> "I first check `free -h` and `vmstat`, then identify the top memory-consuming processes with `top` or `ps`. I also check swap activity and application logs before deciding whether the issue is an application problem or actual memory pressure."

# Q82. What is the difference between free memory and available memory?

## Answer

In Linux, **free memory** means memory that is currently completely unused.

**Available memory** is an estimate of how much memory can be given to new applications without significant swapping.

Check:

```bash
free -h
```

Example:

```text
              total   used   free   buff/cache   available
Mem:            16G    12G    500M       3.5G        4G
```

Here:

```text
Free       = 500 MB
Available  = 4 GB
```

Although free memory is low, the system still has approximately 4 GB that can be made available to applications.

### Why?

Linux uses unused RAM for:

* Page cache
* Filesystem cache
* Buffers
* Other reclaimable memory

This improves performance.

### Interview Tip

> "Low free memory alone does not indicate a problem. On Linux, I pay more attention to available memory, swap activity, and memory pressure."

# Q83. How do you identify which process is consuming the most memory?

## Answer

### Using `top`

```bash
top
```

Inside `top`, press:

```text
M
```

This sorts processes by memory usage.

### Using `ps`

```bash
ps aux --sort=-%mem | head
```

Example:

```text
USER   PID   %CPU  %MEM   COMMAND
root   1234   5.2  35.4   java
app    4567   2.1  15.8   nginx
```

### Check a Specific Process

```bash
ps -p 1234 -o pid,ppid,%mem,rss,vsz,cmd
```

### Check Process Memory Details

```bash
cat /proc/1234/status
```

Useful fields include:

```text
VmSize
VmRSS
VmSwap
```

### Interview Tip

> "I normally use `top` with `M` or `ps aux --sort=-%mem` to quickly identify the process consuming the most memory, then investigate that application's behavior."

<a id="q84"></a>

# Q84. What is swap and how do you troubleshoot high swap usage?

## Answer

**Swap** is disk space used as additional virtual memory when RAM is under pressure.

Check swap:

```bash
swapon --show
```

or:

```bash
free -h
```

Check swap activity:

```bash
vmstat 1
```

Important columns:

```text
si = swap in
so = swap out
```

If `si` and `so` continuously increase, the system may be under memory pressure.

### Identify Memory Consumers

```bash
ps aux --sort=-%mem | head
```

### Check Swappiness

```bash
sysctl vm.swappiness
```

### Common Causes

* Insufficient RAM
* Memory-intensive applications
* Too many processes
* Application memory leak
* Large database/JVM workload

### Important

**Swap usage alone does not necessarily mean a problem.**

A system can have some used swap without currently experiencing severe memory pressure.

### Interview Tip

> "I don't treat any swap usage as an incident automatically. I check whether the system is actively swapping using `vmstat`, along with available memory and application behavior."

<a id="q85"></a>

# Q85. What is the difference between RAM and swap?

## Answer

| RAM                           | Swap                                        |
| ----------------------------- | ------------------------------------------- |
| Physical memory               | Disk-backed virtual memory                  |
| Very fast                     | Much slower than RAM                        |
| Used directly by applications | Used when memory needs exceed available RAM |
| Limited by physical memory    | Allocated from disk/storage                 |
| Preferred by the kernel       | Used under memory pressure                  |

Example:

```text
Application
     |
     v
    RAM
     |
     | Memory pressure
     v
   Swap
     |
     v
   Disk
```

### Important

Swap should **not** normally be treated as a replacement for adequate RAM.

Heavy swapping can cause:

* High I/O
* Slow applications
* Increased latency
* Poor system responsiveness

### Interview Tip

> "RAM is physical high-speed memory, while swap uses storage as a slower backing area for memory pages. Continuous heavy swapping usually indicates memory pressure."

<a id="q86"></a>

# Q86. Why does Linux show very little free memory?

## Answer

This is often normal.

Linux uses available RAM for filesystem cache and buffers to improve performance.

Check:

```bash
free -h
```

Example:

```text
Mem:
total       16G
used        12G
free       500M
buff/cache  3.5G
available    4G
```

The important value is often:

```text
available
```

rather than simply:

```text
free
```

When applications need memory, Linux can reclaim appropriate cache.

### Do Not Immediately Clear Cache

Commands such as:

```bash
sync
echo 3 > /proc/sys/vm/drop_caches
```

should **not** be used routinely to "free memory."

Linux normally manages cache automatically.

### Interview Tip

> "Low free memory is not necessarily a problem because Linux intentionally uses RAM for cache. I check available memory and memory pressure rather than judging the server by the free column alone."

<a id="q87"></a>

# Q87. How do you troubleshoot an application killed due to Out Of Memory (OOM)?

## Answer

Linux has an **OOM killer** that can terminate processes when the kernel cannot satisfy memory allocation requirements.

First check kernel messages:

```bash
dmesg | grep -i -E 'oom|out of memory|killed process'
```

On systems using systemd journal:

```bash
journalctl -k | grep -i -E 'oom|out of memory|killed process'
```

You may see information indicating that a process was killed because of memory exhaustion.

### Check Current Memory

```bash
free -h
```

### Check Swap

```bash
swapon --show
```

### Identify Memory Consumers

```bash
ps aux --sort=-%mem | head
```

### Check Application Logs

For example:

```bash
journalctl -u myapp
```

### Common Causes

* Application memory leak
* Insufficient RAM
* Incorrect JVM/container memory configuration
* Too many processes
* Large workload
* Container memory limit

### Correct Approach

Do not simply restart the application and close the incident.

Investigate:

```text
OOM Event
   ↓
Check kernel logs
   ↓
Identify killed process
   ↓
Check memory usage
   ↓
Check application configuration
   ↓
Check memory leak / workload
   ↓
Apply permanent fix
```

### Interview Tip

> "If an application is killed by OOM, I confirm the OOM event in kernel logs, identify the affected process, check memory and swap usage, and investigate whether the root cause is a leak, workload, configuration, or insufficient resources."

# Q88. How do you check memory usage in real time?

## Answer

### `top`

```bash
top
```

Shows:

* Total memory
* Used memory
* Free memory
* Load
* CPU
* Process memory usage

### `free`

```bash
watch -n 2 free -h
```

### `vmstat`

```bash
vmstat 2
```

This provides information about:

* Memory
* Processes
* Swap
* CPU
* I/O

### `sar`

If the `sysstat` package is installed:

```bash
sar -r 2 5
```

### `htop`

If installed:

```bash
htop
```

### Interview Tip

> "`top` is useful for process-level monitoring, `free` for a quick memory overview, and `vmstat`/`sar` for analyzing memory pressure and system behavior over time."

# Q89. How do you check whether a process is leaking memory?

## Answer

A memory leak can occur when an application continuously allocates memory but does not release it properly.

First monitor the process over time:

```bash
ps -p 1234 -o pid,%mem,rss,vsz,cmd
```

Run it repeatedly:

```bash
watch -n 5 'ps -p 1234 -o pid,%mem,rss,vsz,cmd'
```

If RSS continuously grows without returning to a normal level, investigate further.

### Check Process Details

```bash
cat /proc/1234/status
```

Look at:

```text
VmRSS
VmSize
VmSwap
```

### Monitor Over Time

```text
Time     RSS
10:00    500 MB
10:10    700 MB
10:20    950 MB
10:30    1.3 GB
```

A continuous increase can indicate a possible memory leak, although increasing memory usage alone does not prove a leak.

### Application-Level Investigation

Depending on the application:

* JVM → heap analysis
* Python → memory profiling
* C/C++ → tools such as Valgrind
* Database → application/database-specific diagnostics

### Interview Tip

> "I monitor RSS over time rather than taking a single memory snapshot. Continuous unexplained growth is a strong indication to investigate a possible memory leak at the application level."

# Q90. How do you troubleshoot a production server with continuously increasing memory usage?

## Answer

I would follow a structured approach.

### Step 1: Check Overall Memory

```bash
free -h
```

### Step 2: Check Memory Pressure

```bash
vmstat 1 10
```

Look at:

```text
si
so
```

Continuous swap activity can indicate memory pressure.

### Step 3: Find Top Consumers

```bash
ps aux --sort=-%mem | head -20
```

### Step 4: Monitor the Suspected Process

```bash
watch -n 5 'ps -p PID -o pid,%mem,rss,vsz,cmd'
```

### Step 5: Check Application Logs

```bash
journalctl -u application-name
```

or application-specific log files.

### Step 6: Check OOM Events

```bash
journalctl -k | grep -i oom
```

### Step 7: Determine the Root Cause

Possible causes:

```text
Memory Leak
    ↓
Application Configuration
    ↓
Increasing Workload
    ↓
Too Many Processes
    ↓
Insufficient RAM
    ↓
Container/Service Memory Limit
```

### Step 8: Apply the Correct Fix

Depending on the root cause:

* Fix application memory leak
* Tune application memory settings
* Increase available RAM
* Adjust workload
* Fix process accumulation
* Configure appropriate service/container limits
* Restart service only as a temporary mitigation when appropriate

### Production Interview Scenario

**Interviewer:**
"Production server memory is continuously increasing. What will you do?"

**Strong Answer:**

> "First I will verify the memory condition using `free -h` and `vmstat`. Then I will identify the top memory-consuming processes using `top` or `ps`. I will monitor the suspected process over time to determine whether RSS is continuously increasing. I will also check swap activity, OOM events, and application logs. After identifying whether the cause is a memory leak, workload, configuration, or insufficient resources, I will apply the appropriate permanent fix. I would avoid blindly restarting the server."

# 09. Container Memory Troubleshooting

> Container memory problems are different from normal Linux memory problems because a container can have its own **memory limit**, even when the host still has plenty of RAM.

---

<a id="q91"></a>

# Q91. How do you check memory usage of Docker containers?

## Answer

Check running containers:

```bash
docker ps
```

Check container resource usage:

```bash
docker stats
```

Example:

```text
CONTAINER ID   NAME       CPU %   MEM USAGE / LIMIT
abc123         web        2.5%    450MiB / 512MiB
def456         app        8.2%    1.2GiB / 2GiB
```

For a specific container:

```bash
docker stats <container_name>
```

Inspect configured memory limits:

```bash
docker inspect <container_name> | grep -i -A 10 memory
```

### Interview Tip

> "I use `docker stats` for real-time container memory usage and `docker inspect` to verify the configured memory limit."

---

<a id="q92"></a>

# Q92. What happens when a Docker container reaches its memory limit?

## Answer

If a container exceeds its configured memory limit, the container or one of its processes may be terminated by the kernel's OOM mechanism.

Check:

```bash
docker inspect <container_name>
```

Check container status:

```bash
docker ps -a
```

Check logs:

```bash
docker logs <container_name>
```

Check host kernel logs:

```bash
dmesg | grep -i -E 'oom|out of memory|killed process'
```

or:

```bash
journalctl -k | grep -i oom
```

### Example

Container limit:

```text
512 MB
```

Application usage:

```text
500 MB → 510 MB → 520 MB
```

The container may eventually experience an OOM event.

### Common Causes

* Memory limit too low
* Application memory leak
* Increasing workload
* Incorrect JVM/Python/application configuration
* Too many processes inside the container

### Interview Tip

> "A container can run out of memory even when the host has free RAM because the container may have a lower memory cgroup limit."

<a id="q93"></a>

# Q93. How do you troubleshoot a Kubernetes pod getting OOMKilled?

## Answer

First check the pod:

```bash
kubectl get pod <pod-name>
```

Check detailed information:

```bash
kubectl describe pod <pod-name>
```

Look for:

```text
Reason: OOMKilled
```

Check previous container logs:

```bash
kubectl logs <pod-name> --previous
```

Check current resource usage:

```bash
kubectl top pod <pod-name>
```

Check the deployment configuration:

```bash
kubectl get deployment <deployment-name> -o yaml
```

Look for:

```yaml
resources:
  requests:
    memory: "256Mi"
  limits:
    memory: "512Mi"
```

### Important Difference

```text
request = memory Kubernetes expects/reserves for scheduling
limit   = maximum memory the container is allowed to use
```

If the application requires more memory than the configured limit, it can be terminated with:

```text
OOMKilled
```

### Troubleshooting Flow

```text
Pod OOMKilled
     |
     v
kubectl describe pod
     |
     v
Confirm OOMKilled
     |
     v
kubectl top pod
     |
     v
Check memory request/limit
     |
     v
Check application logs
     |
     v
Check application memory usage
     |
     v
Tune application or resources
```

### Interview Tip

> "For `OOMKilled`, I check the pod events and container status, compare actual memory usage with the configured limit, review previous logs, and determine whether the limit is too low or the application has abnormal memory growth."

<a id="q94"></a>

# Q94. What is the difference between container memory usage and host memory usage?

## Answer

A container runs on the host but can have resource restrictions.

Example:

```text
Linux Host
   |
   |-- Total RAM: 32 GB
   |
   |-- Docker
   |     |
   |     |-- Container A → Limit 512 MB
   |     |
   |     |-- Container B → Limit 2 GB
   |
   |-- Other Host Processes
```

The host may have:

```text
Available RAM = 10 GB
```

while Container A may still be limited to:

```text
512 MB
```

Therefore:

```text
Host has free RAM
        ≠
Container can automatically use unlimited RAM
```

### Docker

Check:

```bash
docker stats
```

### Kubernetes

Check:

```bash
kubectl top pod
```

Check configured limits:

```bash
kubectl describe pod <pod-name>
```

### Interview Tip

> "I always distinguish between host-level memory and container-level memory. A container can hit its cgroup limit while the host still has available RAM."

<a id="q95"></a>

# Q95. How do you troubleshoot continuously increasing memory usage inside a container?

## Answer

First identify the container:

```bash
docker stats
```

For Kubernetes:

```bash
kubectl top pods
```

Monitor the container over time.

### Docker

```bash
docker stats <container_name>
```

Check application processes inside the container:

```bash
docker exec -it <container_name> ps aux
```

Check application logs:

```bash
docker logs <container_name>
```

### Kubernetes

```bash
kubectl top pod <pod-name>
```

Check container processes:

```bash
kubectl exec -it <pod-name> -- ps aux
```

Check previous logs if the container restarted:

```bash
kubectl logs <pod-name> --previous
```

Check pod configuration:

```bash
kubectl describe pod <pod-name>
```

### Possible Causes

```text
Memory Increasing
       |
       +-- Application memory leak
       |
       +-- Increasing workload
       |
       +-- Incorrect application configuration
       |
       +-- JVM heap configuration
       |
       +-- Container memory limit too low
       |
       +-- Too many child processes
```

### Correct Approach

Do not simply increase the memory limit.

First determine:

1. Is the application actually leaking memory?
2. Is workload increasing?
3. Is the configured limit appropriate?
4. Is the application correctly configured?
5. Is the container repeatedly restarting because of OOM?

### Interview Scenario

**Interviewer:**

> "A Kubernetes application is restarting every few hours with `OOMKilled`. What will you check?"

**Strong Answer:**

> "I will first confirm the OOM event using `kubectl describe pod` and check the previous container logs. Then I will compare the pod's memory usage from `kubectl top` with its configured memory limit. I will monitor memory growth over time to determine whether it is a memory leak or simply an insufficient limit. I will also review application configuration and workload before deciding whether to tune the application or increase the memory limit."
