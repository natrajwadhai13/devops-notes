# 30. Network Security & Firewall Connectivity Troubleshooting

> Network connectivity problems in production are often caused by **firewalls, security groups, ACLs, network policies, NAT, ports, or incorrect access rules**. The key interview skill is to identify **where traffic is blocked** instead of immediately changing firewall rules.

# Q306. What is network security and what components can block network traffic?

## Answer

Network security controls determine **which traffic is allowed or denied** between systems.

Traffic can be blocked at multiple layers.

### Common Components

```text
Client
  |
  v
Linux Firewall
  |
  v
Network Firewall
  |
  v
Cloud Security Group
  |
  v
Cloud NACL / ACL
  |
  v
Load Balancer
  |
  v
Server Firewall
  |
  v
Application
```

Common controls include:

| Component            | Example                |
| -------------------- | ---------------------- |
| Linux firewall       | firewalld, nftables    |
| Legacy firewall      | iptables               |
| Cloud firewall       | Security Group         |
| Network ACL          | NACL / router ACL      |
| Load balancer        | Listener/backend rules |
| Kubernetes           | NetworkPolicy          |
| Application firewall | WAF                    |
| Proxy                | HTTP/HTTPS proxy       |
| NAT                  | SNAT/DNAT              |
| Host security        | SELinux                |

### Important

A connection failure does **not automatically mean Linux firewall**.

For example:

```text
Client
  |
  X
Cloud Security Group
```

The Linux server may never receive the packet.

### Example

Application:

```text
10.10.10.20:8080
```

Client:

```text
10.10.10.50
```

Possible blocking points:

```text
Client routing
      ↓
Network ACL
      ↓
Security Group
      ↓
Load Balancer
      ↓
Linux firewall
      ↓
SELinux
      ↓
Application
```

### Interview Tip

> "I identify the traffic path and check each security control along that path. I don't assume that a connection failure is caused by the host firewall."

# Q307. How do you check whether a Linux firewall is blocking traffic?

## Answer

First identify which firewall framework is active.

### Step 1: Check firewalld

```bash
systemctl status firewalld
```

```bash
firewall-cmd --state
```

Check active zones:

```bash
firewall-cmd --get-active-zones
```

### Step 2: Check Rules

```bash
firewall-cmd --list-all
```

For a specific zone:

```bash
firewall-cmd --zone=public --list-all
```

Check allowed ports:

```bash
firewall-cmd --list-ports
```

Check services:

```bash
firewall-cmd --list-services
```

### Step 3: Check nftables

```bash
nft list ruleset
```

Check availability:

```bash
command -v nft
```

### Step 4: Check iptables

```bash
iptables -L -n -v
```

Check NAT:

```bash
iptables -t nat -L -n -v
```

### Important

Do not assume:

```text
firewalld stopped = no firewall
```

Another firewall framework or external security control may still exist.

### Step 5: Check Whether Application Is Listening

```bash
ss -lntup
```

Example:

```text
LISTEN 0 128 0.0.0.0:8080
```

### Step 6: Test Locally

```bash
nc -vz 127.0.0.1 8080
```

Or:

```bash
curl -v http://127.0.0.1:8080
```

### Step 7: Test Remotely

From the client:

```bash
nc -vz 10.10.10.20 8080
```

This comparison is important:

```text
Local works
Remote fails
       ↓
Investigate firewall/network path
```

### Interview Tip

> "I check whether the application is listening first, then inspect the active firewall framework and rules, and finally compare local and remote connectivity."

# Q308. How do you troubleshoot a port that is not reachable remotely?

## Answer

Suppose:

```text
Client → Server:8080
```

fails.

Do not immediately open port `8080`.

### Step 1: Check Server IP

```bash
ip addr
```

### Step 2: Check Application

```bash
ss -lntp | grep :8080
```

Possible result:

```text
LISTEN 0 128 0.0.0.0:8080
```

If nothing is listening:

```text
Firewall troubleshooting is not the first problem.
```

Investigate the application/service.

### Step 3: Test Locally

```bash
nc -vz 127.0.0.1 8080
```

### Step 4: Test Using Server IP

```bash
nc -vz 10.10.10.20 8080
```

### Step 5: Check Firewall

```bash
firewall-cmd --get-active-zones
```

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 6: Check Routing

On the client:

```bash
ip route get 10.10.10.20
```

On the server:

```bash
ip route
```

### Step 7: Check Security Groups / NACLs

For cloud environments verify:

```text
Source
Destination
Protocol
Port
Security Group
NACL
Route table
Load balancer
```

### Step 8: Use Packet Capture

On the server:

```bash
sudo tcpdump -ni any port 8080
```

This is extremely useful.

#### Scenario A

No packets arrive:

```text
Client
  |
  X
Network / SG / NACL / routing
  |
Server
```

The Linux firewall may not even see the traffic.

#### Scenario B

Packets arrive but no response:

```text
Server receives SYN
       |
       X
Firewall / application / local issue
```

#### Scenario C

SYN and SYN-ACK are visible but connection fails:

```text
Possible return-path / firewall / NAT issue
```

### Interview Tip

> "I verify the listener first, then local connectivity, firewall rules, routing, external security controls, and finally packet capture to determine whether traffic reaches the server."

# Q309. How do you troubleshoot when the application is listening but the port is still unreachable?

## Answer

This is a common production scenario.

Example:

```bash
ss -lntp | grep :8080
```

shows:

```text
LISTEN 0 128 0.0.0.0:8080
```

But remote clients cannot connect.

### Step 1: Check Bind Address

Compare:

```text
127.0.0.1:8080
```

with:

```text
0.0.0.0:8080
```

If the application listens only on:

```text
127.0.0.1
```

remote systems cannot directly connect.

### Step 2: Check Server IP

```bash
ip addr
```

### Step 3: Check Local Connectivity

```bash
nc -vz 127.0.0.1 8080
```

```bash
nc -vz <server-ip> 8080
```

### Step 4: Check Firewall

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 5: Check SELinux

SELinux can affect application behavior.

```bash
getenforce
```

Check denials if relevant:

```bash
ausearch -m AVC -ts recent
```

### Step 6: Check Routing

```bash
ip route
```

```bash
ip route get <client-ip>
```

### Step 7: Check Packet Arrival

```bash
sudo tcpdump -ni any port 8080
```

### Step 8: Check External Controls

Depending on environment:

```text
Security Group
NACL
Network Firewall
Load Balancer
Proxy
Kubernetes NetworkPolicy
```

### Troubleshooting Model

```text
Listening?
   |
   +-- NO --> Application/service
   |
   +-- YES
        |
        v
Correct bind address?
        |
        v
Local connection?
        |
        v
Host firewall?
        |
        v
Packet reaches server?
        |
        v
Cloud/network security?
        |
        v
Return path?
```

### Interview Tip

> "A listening socket only proves that the application has opened the port. It does not prove that remote traffic can reach it."

# Q310. How do you troubleshoot firewall rules using firewalld, nftables, and iptables?

## Answer

First identify the active firewall framework.

### firewalld

Check:

```bash
systemctl status firewalld
```

```bash
firewall-cmd --state
```

Active zones:

```bash
firewall-cmd --get-active-zones
```

Rules:

```bash
firewall-cmd --list-all
```

Specific zone:

```bash
firewall-cmd --zone=public --list-all
```

### nftables

Check:

```bash
nft list ruleset
```

Counters can help identify whether packets are hitting a rule.

### iptables

Check:

```bash
iptables -L -n -v
```

NAT:

```bash
iptables -t nat -L -n -v
```

### Important

Do not blindly execute:

```bash
iptables -F
```

or:

```bash
nft flush ruleset
```

on production systems.

These can remove security rules and potentially expose the server or break connectivity.

### Check Rule Ordering

Firewall rules can be order-dependent.

Conceptually:

```text
Packet
  |
  v
Rule 1
  |
  v
Rule 2
  |
  v
Rule 3
```

An earlier rule may accept or drop traffic before a later rule is reached.

### Check Zone Assignment

With firewalld:

```bash
firewall-cmd --get-active-zones
```

A common mistake is modifying the wrong zone.

### Interview Tip

> "I identify the active firewall framework, inspect the effective rules and counters, verify the interface/zone, and avoid flushing firewall rules on production."

# Q311. How do you troubleshoot network connectivity involving cloud Security Groups and NACLs?

## Answer

In cloud environments, Linux firewall rules are only one part of network security.

Typical path:

```text
Client
  |
  v
Route Table
  |
  v
NACL
  |
  v
Security Group
  |
  v
Server
  |
  v
Linux Firewall
  |
  v
Application
```

The exact order depends on the cloud architecture.

### Step 1: Confirm Source

Identify:

```text
Source IP
Source subnet
Source security group
```

### Step 2: Confirm Destination

Identify:

```text
Destination IP
Destination subnet
Destination port
Protocol
```

### Step 3: Check Route

Verify routing between source and destination.

On Linux:

```bash
ip route get <destination-ip>
```

### Step 4: Check Security Group

Verify:

```text
Inbound rule
Protocol
Port
Source
```

For example:

```text
TCP 443
Source: Application subnet
```

### Step 5: Check NACL

NACLs may be stateless depending on the cloud implementation, so return traffic may require explicit consideration.

Check:

```text
Inbound rules
Outbound rules
Rule ordering
Ephemeral return ports
```

### Step 6: Check Linux Firewall

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 7: Check Application

```bash
ss -lntp
```

### Step 8: Use Packet Capture

```bash
sudo tcpdump -ni any port 443
```

### Important

A correct Linux firewall rule does not help if:

```text
Cloud Security Group
        |
        X
     DENY
```

The packet may never reach Linux.

### Interview Tip

> "In cloud troubleshooting I check the complete path: route table, NACL, security group, load balancer if present, host firewall, and application. I also verify the return path."

# Q312. How do you troubleshoot NAT-related connectivity problems?

## Answer

**NAT (Network Address Translation)** changes source or destination addresses, and sometimes ports.

Common types:

```text
SNAT
DNAT
Port forwarding
Masquerading
```

### Example: SNAT

Private server:

```text
10.0.1.10
```

connects to the internet.

NAT gateway/firewall may translate:

```text
10.0.1.10
      ↓
Public IP
```

### Example: DNAT

External traffic:

```text
Public-IP:443
      ↓
Private-IP:8443
```

### Step 1: Check Routing

```bash
ip route
```

### Step 2: Check NAT Rules

For iptables:

```bash
iptables -t nat -L -n -v
```

For nftables:

```bash
nft list ruleset
```

### Step 3: Check Firewall Rules

NAT alone does not guarantee that traffic is permitted.

### Step 4: Check Packet Capture

Capture traffic on the relevant interfaces:

```bash
sudo tcpdump -ni any host <destination-ip>
```

### Step 5: Check Return Path

NAT problems often involve asymmetric or incorrect return traffic.

Conceptually:

```text
Client
  |
  v
NAT
  |
  v
Server
  |
  v
Return traffic
  |
  X
Wrong route / NAT / firewall
```

### Step 6: Check Port Translation

Verify whether:

```text
Public-IP:443
```

is actually translated to:

```text
Private-IP:8443
```

### Common Causes

```text
Wrong NAT rule
Missing SNAT
Missing DNAT
Wrong destination port
Wrong return route
Firewall blocking translated traffic
Security Group/NACL
Asymmetric routing
```

### Interview Tip

> "For NAT issues, I verify routing, NAT rules, firewall rules, translated addresses and ports, and especially the return path."

# Q313. How do you troubleshoot intermittent firewall/network connectivity?

## Answer

Intermittent failures require identifying **when, where, and under what conditions** the connection fails.

### Step 1: Define the Pattern

Ask:

```text
Does it happen randomly?
Every few minutes?
Only during high traffic?
Only from one subnet?
Only one server?
Only one port?
Only one availability zone?
```

### Step 2: Test Repeatedly

```bash
ping -c 50 <destination>
```

For TCP:

```bash
for i in {1..20}; do nc -vz -w 2 <host> 443; done
```

### Step 3: Check Interface Errors

```bash
ip -s link
```

```bash
ethtool -S eth0
```

### Step 4: Check Routing

```bash
ip route get <destination-ip>
```

If policy routing is involved:

```bash
ip rule
```

### Step 5: Check Firewall Counters

```bash
nft list ruleset
```

or:

```bash
iptables -L -n -v
```

Look for counters increasing unexpectedly.

### Step 6: Check Packet Capture

```bash
sudo tcpdump -ni any host <destination-ip>
```

Look for:

```text
SYN
SYN-ACK
RST
Retransmissions
Missing packets
```

### Step 7: Check External Controls

Investigate:

```text
Network firewall
Security Group
NACL
Load balancer
Proxy
Switch
Router
NAT gateway
```

### Step 8: Check Resource Pressure

```bash
ss -s
```

```bash
ss -ant
```

Also check:

```bash
top
free -h
iostat
```

Connection failures may occur because of resource exhaustion rather than a firewall rule.

### Possible Causes

```text
Packet loss
Connection tracking limits
NAT exhaustion
Firewall rate limiting
Load balancer behavior
Network congestion
NIC errors
Asymmetric routing
Resource exhaustion
Security-rule changes
```

### Interview Tip

> "For intermittent connectivity, I don't just test once. I correlate repeated connection tests, packet captures, interface counters, firewall counters, routing, NAT, and infrastructure-side logs."

# Q314. How do you safely change firewall rules in production?

## Answer

Firewall changes can immediately affect production connectivity and security.

### Step 1: Understand the Requirement

Define:

```text
Source
Destination
Protocol
Port
Direction
Purpose
Duration
```

Example:

```text
Source: 10.10.10.0/24
Destination: 10.20.10.50
Protocol: TCP
Port: 443
Direction: inbound
```

### Step 2: Check Existing Rules

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 3: Confirm Application

```bash
ss -lntp | grep :443
```

### Step 4: Make the Smallest Change

Avoid:

```text
Allow from 0.0.0.0/0
```

when only one trusted network is required.

Prefer:

```text
Specific source
Specific destination
Specific protocol
Specific port
```

### Step 5: Understand Runtime vs Permanent

For firewalld:

Runtime:

```bash
firewall-cmd --add-port=8080/tcp
```

Permanent:

```bash
firewall-cmd --permanent --add-port=8080/tcp
```

After permanent changes, reload as appropriate:

```bash
firewall-cmd --reload
```

### Step 6: Validate

From the client:

```bash
nc -vz <server-ip> 8080
```

For HTTP:

```bash
curl -v http://<server-ip>:8080
```

### Step 7: Monitor

Check:

```bash
ss -s
```

Application logs:

```bash
journalctl -u <service>
```

Firewall counters/logs where configured.

### Step 8: Have a Rollback

Know exactly how to remove the rule.

Example:

```bash
firewall-cmd --remove-port=8080/tcp
```

### Critical Production Warning

If connected through SSH, an incorrect firewall change can lock you out.

Before modifying firewall rules, confirm:

```text
Out-of-band console available?
Existing SSH access protected?
Rollback ready?
Correct zone?
Correct interface?
```

### Interview Tip

> "I use the least-permissive rule required, verify the existing configuration, make a controlled and reversible change, validate connectivity, and keep a rollback path—especially for SSH-accessed production servers."

# Q315. How do you troubleshoot a complete production network-security connectivity issue?

## Answer

I use a **layer-by-layer approach** instead of immediately changing firewall rules.

### Step 1: Define the Connection

Identify:

```text
Source IP/hostname
Destination IP/hostname
Protocol
Port
Direction
Time of failure
Intermittent or permanent
```

Example:

```text
10.10.10.50
     |
     | TCP/443
     v
10.20.10.100
```

### Step 2: Check DNS if Hostname Is Used

```bash
getent hosts app.example.com
```

```bash
dig app.example.com
```

### Step 3: Check Local Interface

```bash
ip link
```

```bash
ip addr
```

### Step 4: Check Route

```bash
ip route get <destination-ip>
```

If policy routing may be involved:

```bash
ip rule
```

### Step 5: Check Destination Listener

On destination server:

```bash
ss -lntp | grep :443
```

### Step 6: Test Locally

```bash
nc -vz 127.0.0.1 443
```

Then:

```bash
nc -vz <server-ip> 443
```

### Step 7: Check Host Firewall

```bash
firewall-cmd --get-active-zones
```

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 8: Check Cloud/Network Security

Depending on architecture:

```text
Security Group
NACL
Network Firewall
Load Balancer
Proxy
Kubernetes NetworkPolicy
Router ACL
```

### Step 9: Check NAT

If NAT is involved:

```bash
iptables -t nat -L -n -v
```

or:

```bash
nft list ruleset
```

Verify:

```text
Source translation
Destination translation
Port translation
Return path
```

### Step 10: Check Packet Flow

Use targeted packet capture:

```bash
sudo tcpdump -ni any host <destination-ip> and port 443
```

Determine:

```text
Packet arrives?
SYN sent?
SYN-ACK returned?
RST?
Retransmissions?
No response?
```

### Step 11: Check Interface Errors

```bash
ip -s link
```

```bash
ethtool -S eth0
```

### Step 12: Check Application and System Logs

```bash
journalctl -u <service>
```

```bash
journalctl -k
```

### Step 13: Identify the Failing Layer

```text
DNS
 ↓
Interface
 ↓
Routing
 ↓
Cloud/network security
 ↓
NAT
 ↓
Host firewall
 ↓
Listener
 ↓
Application
```

### Step 14: Apply the Smallest Safe Fix

Examples:

```text
Correct firewall rule
Correct Security Group
Correct NACL
Correct route
Correct NAT rule
Correct bind address
Correct load-balancer rule
Fix application
```

### Step 15: Verify End-to-End

Verify:

```text
DNS
 ↓
IP connectivity
 ↓
TCP port
 ↓
TLS/HTTP if applicable
 ↓
Application health
```

### Production Scenario

**Interviewer:**

> "The application is running and port 443 is listening, but users cannot access it. How will you troubleshoot?"

**Strong Answer:**

> "First I would define the source, destination, protocol, port, and whether the issue is permanent or intermittent. I would verify DNS if a hostname is involved, then check the destination interface, route, and listening socket with `ss`. I would test locally and from the client. Next I would inspect the host firewall and then external controls such as Security Groups, NACLs, network firewalls, load balancers, or proxies depending on the architecture. If NAT is involved, I would verify translation and the return path. Finally, I would use targeted `tcpdump` to determine whether packets reach the server and whether SYN/SYN-ACK traffic is returning. I would identify the exact failing layer, make the smallest reversible change, and verify connectivity and application health."

# 🎤 Network Security Interview Golden Rules

```text
Connection failure ≠ Firewall failure
Listening port ≠ Remote accessibility
Firewall allows traffic ≠ Application is healthy
firewalld stopped ≠ No firewall exists
Linux firewall ≠ Cloud Security Group
Security Group ≠ NACL
NACL behavior ≠ Stateful firewall behavior
NAT ≠ Firewall
Correct inbound rule ≠ Correct return path
Packet reaches server ≠ Application accepts it
Ping works ≠ TCP port works
Ping fails ≠ TCP port is blocked
Port open ≠ Application healthy
DNS failure ≠ Firewall failure
No packet on server ≠ Automatically Linux firewall
```

# ⚠️ Production Safety Rules

Before modifying network-security configuration:

```text
1. Identify source and destination
2. Identify protocol and port
3. Identify direction
4. Check DNS if hostname is involved
5. Check interface/IP
6. Check routing
7. Check application listener
8. Test local connectivity
9. Test remote connectivity
10. Identify every security control in the path
11. Check host firewall
12. Check cloud Security Groups/NACLs
13. Check NAT if applicable
14. Check load balancer/proxy if applicable
15. Use packet capture when necessary
16. Make the smallest possible change
17. Avoid 0.0.0.0/0 unless explicitly required
18. Never blindly flush firewall rules
19. Protect SSH access
20. Have a rollback plan
21. Verify end-to-end
22. Monitor after the change
23. Document the root cause
```

> **Interview mindset:** Don't say **"Port is not reachable, so I will open the firewall."** Say: **"I will verify the listener, local connectivity, routing, host firewall, external security controls, NAT and return path, and use packet capture if necessary to identify exactly where the traffic is being dropped."**
