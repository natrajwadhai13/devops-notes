# Q266. How do you check network interfaces in Linux?

## Answer

Start by identifying the available network interfaces.

### Step 1: List Interfaces

```bash id="f3h8sa"
ip link
```

Example:

```text id="8f6m2v"
1: lo: <LOOPBACK,UP,LOWER_UP>
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP>
3: eth1: <BROADCAST,MULTICAST,DOWN>
```

### Step 2: Check IP Addresses

```bash id="z1x7c4"
ip addr
```

For one interface:

```bash id="91v9y8"
ip addr show eth0
```

### Step 3: Check Routing

```bash id="x7f4m2k"
ip route
```

### Step 4: Check Link Details

If `ethtool` is installed:

```bash id="c7n2q5"
ethtool eth0
```

Check availability:

```bash id="k1z6mw"
command -v ethtool
```

Important fields:

```text id="g5q9s2"
Link detected
Speed
Duplex
Auto-negotiation
```

### Step 5: Identify NIC Hardware

```bash id="a8m3q7"
lspci | grep -Ei "ethernet|network"
```

### Step 6: Identify Driver

```bash id="v6k1p4"
lspci -k
```

### Step 7: Check Interface Statistics

```bash id="n8w3r2"
ip -s link show eth0
```

This can show:

```text id="5x2m7q"
RX packets
RX errors
RX dropped
TX packets
TX errors
TX dropped
```

### Interview Tip

> "I start with `ip link` and `ip addr`, then check routing with `ip route`, link details with `ethtool`, hardware and driver information with `lspci -k`, and interface statistics with `ip -s link`."

# Q267. How do you troubleshoot a network interface that is DOWN?

## Answer

First determine whether the interface is administratively down or whether the physical/virtual link is unavailable.

### Step 1: Check Interface

```bash id="h2c8x5"
ip link show eth0
```

You may see:

```text id="9p5m2x"
state DOWN
```

### Step 2: Bring Interface UP

If appropriate and authorized:

```bash id="s8q4n1"
sudo ip link set eth0 up
```

Verify:

```bash id="r7k3m6"
ip link show eth0
```

### Important

This is a runtime change and may not persist after reboot.

The persistent configuration depends on the distribution/network stack.

### Step 3: Check Link

```bash id="v4p8z2"
ethtool eth0
```

Look for:

```text id="0n5x7m"
Link detected: yes
```

### Step 4: Check Network Manager

On systems using NetworkManager:

```bash id="j8q3s6"
nmcli device status
```

```bash id="5d7m2x"
nmcli device show eth0
```

### Step 5: Check Driver

```bash id="0x8p4m"
ethtool -i eth0
```

### Step 6: Check Kernel Logs

```bash id="m3k7q1"
journalctl -k | grep -Ei "eth0|link|network|driver|firmware"
```

### Possible Causes

```text id="w5n8q2"
Interface administratively down
Network configuration issue
Cable disconnected
Switch port problem
NIC driver problem
Firmware problem
Hardware failure
Virtual NIC issue
```

### Interview Tip

> "I first check `ip link`, determine whether the interface is administratively down or has no physical link, then check `ethtool`, NetworkManager, driver information, and kernel logs."

# Q268. How do you troubleshoot a NIC with no IP address?

## Answer

A working NIC does not necessarily have an IP address.

### Step 1: Check Interface

```bash id="z3n7x4"
ip link show eth0
```

### Step 2: Check IP

```bash id="w5m8q1"
ip addr show eth0
```

If no expected address exists, investigate configuration.

### Step 3: Check NetworkManager

```bash id="c6p2v9"
nmcli device status
```

```bash id="a4q8m1"
nmcli connection show
```

### Step 4: Check DHCP

If the interface should receive an address through DHCP, check:

```text id="2x7n5q"
DHCP configuration
DHCP server
VLAN
Network connectivity
NetworkManager logs
```

### Step 5: Check Routing

```bash id="y8m4p2"
ip route
```

### Step 6: Check DNS Separately

Do not confuse:

```text id="3q7x9m"
No IP
```

with:

```text id="6p2k8v"
DNS problem
```

First confirm the interface has the correct IP configuration.

### Step 7: Check Logs

```bash id="h6m1q9"
journalctl -u NetworkManager
```

If applicable:

```bash id="f5x8c2"
journalctl -k | grep -Ei "network|eth0|dhcp"
```

### Possible Causes

```text id="j4p7m2"
DHCP failure
Static IP missing
Wrong network profile
Interface disabled
VLAN problem
NetworkManager issue
Cloud NIC configuration
```

### Interview Tip

> "I check `ip addr` first, then verify the network profile with `nmcli`, DHCP or static configuration, routing, and relevant logs. I keep IP configuration separate from DNS troubleshooting."

# Q269. How do you check NIC driver and firmware information?

## Answer

### Step 1: Check Hardware

```bash id="p8m2q5"
lspci | grep -Ei "ethernet|network"
```

### Step 2: Check Driver

```bash id="x7n4m1"
lspci -k
```

Look for:

```text id="8q3m6v"
Kernel driver in use
Kernel modules
```

### Step 3: Use ethtool

```bash id="m5x8p2"
ethtool -i eth0
```

Example information:

```text id="4n7q1m"
driver
version
firmware-version
bus-info
```

Check command:

```bash id="y2k6p8"
command -v ethtool
```

### Step 4: Check Loaded Module

```bash id="q9m3x7"
lsmod | grep driver_name
```

### Step 5: Check Module Details

```bash id="v5p8m2"
modinfo driver_name
```

### Step 6: Check Kernel Logs

```bash id="a7x2q4"
journalctl -k | grep -Ei "driver|firmware|eth0|network"
```

### Example Troubleshooting

```text id="2m7q9x"
NIC detected
    ↓
lspci -k
    ↓
Driver identified
    ↓
ethtool -i
    ↓
Firmware checked
    ↓
journalctl -k
```

### Important

A driver being loaded does not guarantee the NIC is operating correctly.

```text id="5x8m2q"
Driver loaded
     ≠
Network working
```

### Interview Tip

> "I use `lspci -k` to identify the NIC driver and `ethtool -i` to check driver and firmware information. I then correlate this with `lsmod` and kernel logs."

# Q270. How do you troubleshoot packet drops and network errors?

## Answer

Packet drops and errors can indicate problems at the NIC, driver, cable, switch, VLAN, congestion, or higher network layers.

### Step 1: Check Interface Statistics

```bash id="t6q3m8"
ip -s link show eth0
```

Look at:

```text id="x4p7m2"
RX errors
RX dropped
TX errors
TX dropped
```

### Step 2: Check Detailed NIC Statistics

```bash id="v8m2q5"
ethtool -S eth0
```

Depending on the driver, you may see:

```text id="2x6m9q"
CRC errors
Frame errors
Receive errors
Transmit errors
Dropped packets
Queue errors
```

Not every driver exposes the same counters.

### Step 3: Check Link

```bash id="p4n7x1"
ethtool eth0
```

Check:

```text id="q8m3v5"
Speed
Duplex
Link detected
```

### Step 4: Check Driver/Kernel Errors

```bash id="k2x7m4"
journalctl -k | grep -Ei "eth0|link|error|reset|timeout"
```

### Step 5: Check Network Path

Test the gateway:

```bash id="7p3m8x"
ping -c 4 <gateway-ip>
```

Test another known endpoint:

```bash id="1x5q9m"
ping -c 4 <destination-ip>
```

### Step 6: Check Interface Traffic

If available:

```bash id="w8m2q4"
sar -n DEV 1
```

### Step 7: Use Packet Capture When Necessary

```bash id="r4x7m2"
sudo tcpdump -ni eth0
```

Use a narrow capture/filter in production rather than collecting unnecessary traffic.

### Possible Causes

```text id="n5q8m2"
Bad cable
Switch port issue
Speed/duplex mismatch
NIC hardware problem
Driver problem
VLAN issue
Network congestion
MTU mismatch
Virtual NIC issue
```

### Important

Packet drops do not automatically mean the NIC is faulty.

Correlate:

```text id="6m2q9x"
NIC Counters
+
Driver Logs
+
Switch Port
+
Network Path
+
Application Behavior
```

### Interview Tip

> "I check `ip -s link` and `ethtool -S` for interface errors and drops, verify link settings, inspect driver/kernel logs, and correlate the counters with switch and network-path information."

# Q271. How do you troubleshoot speed and duplex problems?

## Answer

Speed and duplex determine how the NIC communicates with the connected network device.

### Step 1: Check Current Settings

```bash id="x5m8q2"
ethtool eth0
```

Example:

```text id="q4n7m1"
Speed: 1000Mb/s
Duplex: Full
Auto-negotiation: on
Link detected: yes
```

### Step 2: Check NIC Capabilities

```bash id="p8x3m5"
ethtool eth0 | grep -Ei "Speed|Duplex|Auto-negotiation|Supported link modes"
```

### Step 3: Check Errors

```bash id="m2q7x9"
ip -s link show eth0
```

Also:

```bash id="7n4p8m"
ethtool -S eth0
```

### Step 4: Compare With Switch

Check whether the switch port has compatible:

```text id="x6m2q8"
Speed
Duplex
Auto-negotiation
Port errors
```

### Symptoms

A speed/duplex problem can cause:

```text id="q8p4m1"
Poor throughput
Packet errors
Retransmissions
High latency
Intermittent connectivity
```

### Important

Do not manually force speed or duplex without understanding the connected switch configuration.

For example, blindly using:

```bash id="8m3q6x"
ethtool -s eth0 ...
```

can cause connectivity problems.

### Interview Tip

> "I check `ethtool` for negotiated speed, duplex, and auto-negotiation, then compare those values with the switch port and interface error counters. I avoid forcing settings unless the network design specifically requires it."

# Q272. How do you troubleshoot bonding or NIC teaming problems?

## Answer

NIC bonding combines multiple network interfaces to provide redundancy, load distribution, or both.

Example:

```text id="w7m3q9"
        Bond0
       /     \
    eth0     eth1
```

### Step 1: Check Bonding Status

On systems using Linux bonding:

```bash id="2x8m4p"
cat /proc/net/bonding/bond0
```

This may show:

```text id="p5q7m2"
Bonding Mode
Currently Active Slave
MII Status
Slave Interface
Link Failure Count
```

### Step 2: Check Interfaces

```bash id="j4m8x2"
ip link
```

### Step 3: Check NetworkManager

```bash id="y6q3m9"
nmcli connection show
```

```bash id="t8m2p4"
nmcli device status
```

### Step 4: Check Each NIC

```bash id="c7x4m1"
ethtool eth0
```

```bash id="9m5q8x"
ethtool eth1
```

### Step 5: Check Kernel Logs

```bash id="p2m7q4"
journalctl -k | grep -Ei "bond|eth0|eth1|link|fail"
```

### Common Problems

```text id="3x8m5q"
Slave interface down
Cable problem
Switch configuration mismatch
Wrong bonding mode
LACP configuration issue
NetworkManager profile problem
Driver issue
```

### Important

Bonding mode must match the network architecture.

For example, LACP-based configurations require appropriate switch-side configuration.

### Interview Tip

> "I check `/proc/net/bonding/bond0`, verify each slave interface, check link and driver status with `ethtool`, inspect NetworkManager configuration, and correlate the Linux configuration with the switch-side configuration."

# Q273. How do you troubleshoot VLAN-related network problems?

## Answer

A VLAN problem can make a NIC appear healthy while the application remains unreachable.

### Architecture

```text id="8m2q6x"
Application
    |
    v
VLAN Interface
    |
    v
Physical NIC
    |
    v
Switch
    |
    v
VLAN
```

### Step 1: Check Interfaces

```bash id="v4x7m2"
ip link
```

### Step 2: Check VLAN Interfaces

```bash id="m8q3p5"
ip -d link
```

You may see VLAN information such as:

```text id="1n6x9q"
vlan id
```

### Step 3: Check IP Configuration

```bash id="z2m7q4"
ip addr
```

### Step 4: Check Routing

```bash id="p5x8m1"
ip route
```

### Step 5: Check NetworkManager

```bash id="7q3m9x"
nmcli connection show
```

### Step 6: Check Parent Interface

If VLAN is built on `eth0`, verify:

```bash id="f8m2q5"
ip link show eth0
```

and:

```bash id="n4x7m1"
ethtool eth0
```

### Step 7: Check Switch Configuration

Verify:

```text id="q6m8p2"
Correct VLAN ID
Trunk/access mode
Allowed VLANs
Native VLAN
LACP/bonding configuration
```

### Possible Causes

```text id="2x5m9q"
Wrong VLAN ID
VLAN not allowed on trunk
Wrong switch port mode
Incorrect Linux VLAN configuration
Missing IP configuration
Routing problem
Bonding/LACP mismatch
```

### Important

```text id="6m3q8x"
NIC healthy
+
Link UP
+
IP configured
≠
VLAN connectivity guaranteed
```

### Interview Tip

> "For VLAN problems, I verify the VLAN interface and ID in Linux, confirm IP and routing, check the parent NIC, and then verify the switch port and trunk configuration."

# Q274. How do you troubleshoot a NIC that disappears or repeatedly resets?

## Answer

A NIC that disappears or repeatedly resets can indicate a hardware, driver, firmware, PCIe, power, or virtualization problem.

### Step 1: Check Whether the Device Exists

```bash id="k7m2q5"
ip link
```

Then:

```bash id="x4p8m1"
lspci | grep -Ei "ethernet|network"
```

### Step 2: Check Driver

```bash id="9q3m6x"
lspci -k
```

### Step 3: Check Kernel Logs

```bash id="p7x2m8"
journalctl -k | grep -Ei "reset|timeout|firmware|error|eth|network"
```

Look for messages such as:

```text id="5m8q1x"
NIC reset
TX timeout
firmware error
device removed
PCI error
link down
```

### Step 4: Check Interface Statistics

```bash id="x2q7m4"
ip -s link show eth0
```

### Step 5: Check Driver/Firmware

```bash id="m5x8q2"
ethtool -i eth0
```

### Step 6: Check PCIe Errors

Search:

```bash id="q8m3x6"
journalctl -k | grep -Ei "PCIe|AER|PCI error"
```

### Step 7: Determine Environment

Check:

```bash id="p4m7x2"
systemd-detect-virt
```

A virtual NIC disappearing may require hypervisor/cloud investigation rather than physical hardware replacement.

### Possible Causes

```text id="9x5m2q"
NIC hardware failure
Driver bug
Firmware problem
PCIe problem
Power issue
Kernel compatibility
Virtual NIC/hypervisor issue
```

### Important

Repeated resets are more significant than a single link-down event.

Check the timeline:

```text id="8m2q5x"
NIC Reset
   ↓
Driver Recovery
   ↓
Link Down
   ↓
Link Up
   ↓
NIC Reset Again
```

### Interview Tip

> "For a NIC that repeatedly resets, I correlate `lspci`, driver and firmware information, interface statistics, and kernel logs. I also check PCIe errors and determine whether the server is physical or virtual before deciding whether the problem is hardware, driver, firmware, or platform related."

# Q275. How do you troubleshoot a production server with a suspected NIC failure?

## Answer

I follow a layered troubleshooting approach.

### Step 1: Confirm the Impact

Determine:

```text id="0q7m4x"
SSH unavailable?
Application unavailable?
Packet loss?
High latency?
Interface completely missing?
Intermittent connectivity?
```

### Step 2: Check Interface

```bash id="5m8q2p"
ip link
```

```bash id="r4x7m1"
ip addr
```

### Step 3: Check Link

```bash id="x2m9q5"
ethtool eth0
```

### Step 4: Check Driver/Firmware

```bash id="k7p3m8"
ethtool -i eth0
```

```bash id="6m4x8q"
lspci -k
```

### Step 5: Check Errors

```bash id="y5q2m7"
ip -s link show eth0
```

```bash id="p8x3m6"
ethtool -S eth0
```

### Step 6: Check Kernel Logs

```bash id="n4m7q2"
journalctl -k | grep -Ei "error|fail|reset|timeout|firmware|link"
```

### Step 7: Check Routing

```bash id="8x2m5q"
ip route
```

### Step 8: Check Connectivity

Test the nearest known point first:

```bash id="q7m3x9"
ping -c 4 <gateway-ip>
```

Then test the required destination.

For TCP connectivity:

```bash id="m2x8q4"
nc -vz <destination-ip> <port>
```

### Step 9: Check VLAN/Bonding

If applicable:

```bash id="p5q8m2"
cat /proc/net/bonding/bond0
```

and:

```bash id="j3m7x1"
ip -d link
```

### Step 10: Determine Failure Layer

```text id="x8m4q2"
Application
    |
TCP/UDP
    |
Routing
    |
VLAN
    |
NIC Interface
    |
Driver
    |
Firmware
    |
PCIe
    |
Physical Hardware
    |
Switch
```

### Step 11: Protect Production

Depending on the architecture:

```text id="7m2q5x"
Failover
Move workload
Use redundant NIC
Switch to healthy bond member
Migrate VM
Replace NIC
Provider escalation
```

Do not reset or reload a production NIC blindly if it is the only network path.

### Step 12: Verify

After remediation:

```text id="4q8m2x"
NIC detected
    ↓
Driver loaded
    ↓
Link UP
    ↓
Correct IP
    ↓
Correct route
    ↓
VLAN/bond healthy
    ↓
Connectivity works
    ↓
Application works
```

### Production Scenario

**Interviewer:**

> "A production server suddenly loses network connectivity. How will you troubleshoot it?"

**Strong Answer:**

> "First I would confirm the impact and whether the interface is visible. I would check `ip link` and `ip addr`, then verify physical or virtual link status with `ethtool`. I would check the NIC driver and firmware with `ethtool -i` and `lspci -k`, inspect interface error counters with `ip -s link` and `ethtool -S`, and review kernel logs for resets, timeouts, firmware, or PCIe errors. I would also verify routing, VLAN or bonding configuration, and test connectivity from the server outward. If the server has redundant networking, I would use the approved failover procedure before making disruptive changes. Finally, I would verify connectivity and application health and document the root cause."

# 🎤 NIC Interview Golden Rules

```text
Interface UP ≠ Network reachable
Link UP ≠ IP configured
IP configured ≠ Correct routing
Correct routing ≠ Application reachable
Driver loaded ≠ NIC healthy
NIC detected ≠ NIC operational
No ping ≠ Automatically NIC failure
Packet drops ≠ Automatically NIC hardware failure
Speed problem ≠ Automatically cable failure
NIC reset ≠ Automatically hardware failure
Bond healthy ≠ Every slave healthy
VLAN configured ≠ VLAN connectivity guaranteed
```

### ⚠️ Production Safety Rules

Before changing NIC configuration:

```text
1. Confirm the affected interface
2. Check whether it is the only network path
3. Assess production impact
4. Check link and interface state
5. Check IP and routing
6. Check driver and firmware
7. Review kernel logs
8. Check VLAN/bonding if applicable
9. Check interface error counters
10. Correlate with switch/network-side evidence
11. Avoid blindly restarting NetworkManager
12. Avoid blindly changing speed/duplex
13. Do not reload a critical NIC driver without a recovery path
14. Use redundant networking/failover where available
15. Prefer console/out-of-band access before disruptive changes
16. Verify connectivity after remediation
17. Verify application health
18. Document the root cause
```

> **Interview mindset:** Do not say, "The network is down, so I will restart NetworkManager." Say, **"I will identify whether the failure is at the interface, link, IP, routing, VLAN, bonding, driver, firmware, hardware, or network-path layer, collect evidence from Linux and the network side, use the safest recovery path, and verify application connectivity afterward."**
