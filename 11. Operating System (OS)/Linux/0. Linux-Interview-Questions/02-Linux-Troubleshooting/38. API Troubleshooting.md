# Q386. What is an API and how do you troubleshoot an API issue?

## Answer

An **API (Application Programming Interface)** allows applications or services to communicate with each other.

Example:

```text
Frontend
   |
   | HTTPS Request
   v
API / Backend
   |
   +----> Database
   |
   +----> Cache
   |
   +----> External API
```

Example API request:

```bash
curl -v https://api.example.com/users/123
```

A typical API request flow is:

```text
Client
  |
  v
DNS
  |
  v
Load Balancer / API Gateway
  |
  v
Web Server / Reverse Proxy
  |
  v
API Application
  |
  +----> Authentication
  |
  +----> Database
  |
  +----> Cache
  |
  +----> External Service
```

### Main Troubleshooting Areas

```text
DNS
Network
TCP
TLS
Load Balancer
API Gateway
Web Server
Application
Authentication
Authorization
Database
Cache
External APIs
CPU
Memory
Disk
Configuration
Deployment
```

### Basic API Test

```bash
curl -v https://api.example.com/health
```

Check:

```text
HTTP status
Response headers
Response body
TLS
Connection time
Response time
```

### Check DNS

```bash
getent hosts api.example.com
```

```bash
dig api.example.com
```

### Check TCP

```bash
nc -vz api.example.com 443
```

### Interview Tip

> "I troubleshoot an API layer by layer, starting with DNS and connectivity, then TLS, gateway/load balancer, API application, authentication, backend dependencies, resources, logs, and recent changes."

# Q387. How do you troubleshoot an API that is not reachable?

## Answer

First determine whether the failure is at the **DNS, network, TLS, gateway, web server, or application layer**.

### Step 1: Test DNS

```bash
getent hosts api.example.com
```

```bash
dig api.example.com
```

### Step 2: Test TCP Port

Most HTTPS APIs use TCP `443`.

```bash
nc -vz api.example.com 443
```

### Step 3: Test HTTPS

```bash
curl -v https://api.example.com/health
```

### Step 4: Check TLS

```bash
openssl s_client -connect api.example.com:443 -servername api.example.com
```

Check:

```text
Certificate
SAN
Expiry
Certificate chain
SNI
TLS version/policy
```

### Step 5: Check API Gateway/Load Balancer

Verify:

```text
Listener
Route
Backend target
Health check
TLS configuration
Security rules
```

### Step 6: Check Web Server

Nginx:

```bash
systemctl status nginx
```

Apache:

```bash
systemctl status httpd
```

### Step 7: Check API Process

```bash
pgrep -a <application>
```

```bash
ss -lntp
```

Verify the expected API port.

### Step 8: Test API Locally

```bash
curl -v http://127.0.0.1:<api-port>/health
```

If local access works but remote access fails, investigate:

```text
Firewall
Routing
Load Balancer
API Gateway
Security Group
Network
```

### Step 9: Check Logs

```bash
journalctl -u <api-service> -n 100
```

Also check:

```text
API application logs
Gateway logs
Load-balancer logs
Web-server logs
```

### Step 10: Check Backend Dependencies

```text
Database
Cache
Message Queue
External API
Authentication service
```

### Interview Tip

> "I first reproduce the API failure with curl, then verify DNS, TCP, TLS, gateway/load-balancer health, API listener, local health endpoint, logs, and backend dependencies."

# Q388. How do you troubleshoot HTTP 4xx errors in an API?

## Answer

4xx errors generally indicate a problem with the request or access to the requested resource.

Common API errors:

| Code | Meaning               | Common Cause                    |
| ---- | --------------------- | ------------------------------- |
| 400  | Bad Request           | Invalid request/JSON/parameters |
| 401  | Unauthorized          | Missing/invalid authentication  |
| 403  | Forbidden             | Insufficient permission         |
| 404  | Not Found             | Wrong endpoint/resource         |
| 405  | Method Not Allowed    | Wrong HTTP method               |
| 409  | Conflict              | Resource/state conflict         |
| 422  | Unprocessable Content | Validation failure              |
| 429  | Too Many Requests     | Rate limiting                   |

### Step 1: Check Request

```bash
curl -v https://api.example.com/users
```

For POST/JSON:

```bash
curl -v \
-H "Content-Type: application/json" \
-d '{"name":"test"}' \
https://api.example.com/users
```

### Step 2: Check HTTP Method

Example:

```text
GET
POST
PUT
PATCH
DELETE
```

The API may reject an incorrect method with `405`.

### Step 3: Check Request Parameters

Check:

```text
Path parameters
Query parameters
Headers
JSON body
Content-Type
```

### Step 4: Check Authentication

Example:

```bash
curl -v \
-H "Authorization: Bearer <token>" \
https://api.example.com/users
```

Do not expose real production tokens.

### Step 5: Check Authorization

A valid user/token may still not have permission.

### Step 6: Check API Gateway/WAF

A 4xx may be generated by:

```text
API Gateway
WAF
Load Balancer
Reverse Proxy
Application
```

### Step 7: Check Logs

Correlate:

```text
Request ID
Timestamp
Client
Endpoint
HTTP method
Status code
```

### Example

```text
GET /api/users/100
       |
       v
404
```

Possible causes:

```text
Wrong URL
Resource does not exist
Incorrect API route
Gateway routing
Application routing
```

### 429 — Rate Limiting

Check:

```text
API rate limit
Client traffic
Gateway limits
WAF policy
Application throttling
```

### Interview Tip

> "For API 4xx errors, I validate the method, URL, headers, parameters, authentication, authorization, request body, and identify whether the response was generated by the gateway or the application."

# Q389. How do you troubleshoot HTTP 5xx errors in an API?

## Answer

Common API 5xx errors:

```text
500 → Internal Server Error
502 → Bad Gateway
503 → Service Unavailable
504 → Gateway Timeout
```

### 500

Check:

```text
Application logs
Stack traces
Configuration
Code errors
Database failures
Dependency failures
Recent deployment
```

### 502

Usually indicates a problem communicating with an upstream/backend.

Check:

```bash
ss -lntp
```

Test backend:

```bash
curl -v http://<backend-ip>:<port>/health
```

Investigate:

```text
Backend service
Port
DNS
Firewall
TLS
Proxy configuration
```

### 503

Possible causes:

```text
No healthy backend
API service unavailable
Overloaded application
Maintenance
Resource exhaustion
Connection pool exhaustion
```

### 504

Usually indicates a timeout while waiting for an upstream response.

Investigate:

```text
API application
Database
External API
Network
Load balancer
Gateway
Timeout settings
```

### Step 1: Identify Response Source

Check:

```text
Gateway logs
Load-balancer logs
Web-server logs
API logs
Response headers
Request ID
```

### Step 2: Check Application

```bash
systemctl status <api-service>
```

```bash
pgrep -a <api-process>
```

### Step 3: Check Resources

```bash
top
```

```bash
free -h
```

```bash
df -h
```

### Step 4: Check Backend

```bash
nc -vz <backend-host> <port>
```

### Step 5: Check Logs

```bash
journalctl -u <api-service> -n 100
```

### Important

```text
500 ≠ Automatically code bug
502 ≠ Automatically proxy bug
503 ≠ Automatically API process stopped
504 ≠ Automatically increase timeout
```

### Interview Tip

> "For 5xx errors, I identify which component generated the response and then trace the request to the API application and its dependencies."

# Q390. How do you troubleshoot API authentication and authorization failures?

## Answer

First distinguish:

```text
Authentication → Who are you?
Authorization  → What are you allowed to do?
```

### 401 — Authentication Problem

Possible causes:

```text
Missing token
Invalid token
Expired token
Wrong credentials
Invalid API key
Incorrect authentication scheme
```

Test carefully:

```bash
curl -v \
-H "Authorization: Bearer <token>" \
https://api.example.com/users
```

Do not expose real tokens.

### 403 — Authorization Problem

Possible causes:

```text
User lacks permission
Role missing
Scope missing
Resource access denied
IP restriction
Policy restriction
```

### Step 1: Check Token/Key Configuration

Verify:

```text
Token source
API key
Secret
Issuer
Audience
Expiration
Scopes
```

### Step 2: Check Server Time

Authentication tokens can fail when system time is incorrect.

```bash
timedatectl
```

### Step 3: Check Authentication Service

If the API depends on:

```text
OAuth provider
Identity provider
LDAP
Active Directory
SSO
```

verify that dependency.

### Step 4: Check API Gateway

Authentication may be performed before traffic reaches the API application.

### Step 5: Check Application Logs

Look for:

```text
Invalid token
Expired token
Invalid signature
Missing scope
Access denied
Authentication provider unavailable
```

### Important

A valid token does not necessarily mean the user is authorized for every endpoint.

### Security Rule

Never troubleshoot production authentication by printing:

```text
Passwords
API keys
Bearer tokens
Client secrets
Private keys
```

### Interview Tip

> "I separate authentication from authorization. For 401 I investigate credentials, tokens, expiry, issuer and authentication configuration. For 403 I investigate roles, scopes, policies, and resource permissions."

# Q391. How do you troubleshoot a slow API?

## Answer

First determine whether the latency is caused by:

```text
Network
Gateway
API application
Database
Cache
External API
```

### Step 1: Measure API Response Time

```bash
curl -s -o /dev/null -w \
'DNS:%{time_namelookup} CONNECT:%{time_connect} START:%{time_starttransfer} TOTAL:%{time_total}\n' \
https://api.example.com/health
```

### Step 2: Check API Logs/Metrics

Look for:

```text
Request duration
Endpoint
Request rate
Error rate
Concurrent requests
```

### Step 3: Check CPU

```bash
top
```

```bash
ps aux --sort=-%cpu | head
```

### Step 4: Check Memory

```bash
free -h
```

### Step 5: Check Disk I/O

```bash
iostat -xz 1
```

### Step 6: Check Database

Investigate:

```text
Slow queries
Locks
Connection pool
Database CPU
Database I/O
```

### Step 7: Check External APIs

Example:

```text
API
 |
 +----> Payment API → 5 seconds
```

The API may appear slow because it is waiting for the external service.

### Step 8: Check Connection Pools

Investigate:

```text
Database pool
HTTP client pool
Thread pool
Worker pool
```

### Step 9: Compare Endpoints

Example:

```text
GET /health → 50 ms
GET /users  → 5 seconds
GET /orders → 200 ms
```

Focus on `/users`.

### Step 10: Compare Instances

```text
API-01 → 200 ms
API-02 → 5 sec
API-03 → 180 ms
```

Focus on API-02.

### Important

Do not immediately increase:

```text
Timeout
Threads
Connection pool
Workers
```

First determine the bottleneck.

### Interview Tip

> "I measure latency at each layer and compare fast and slow requests or instances. Then I investigate application processing, database queries, connection pools, external APIs, and infrastructure resources."

# Q392. How do you troubleshoot API timeout errors?

## Answer

Timeouts occur when one component waits longer than its configured limit for another component.

Example:

```text
Client
  |
  v
API Gateway
  |
  v
API
  |
  v
Database
```

### Step 1: Identify Which Timeout

Possible timeout:

```text
DNS timeout
TCP connection timeout
TLS timeout
Gateway timeout
Application timeout
Database timeout
External API timeout
```

### Step 2: Test API

```bash
curl -v https://api.example.com/resource
```

### Step 3: Check Backend Connectivity

```bash
nc -vz <backend-host> <port>
```

### Step 4: Check Application Logs

Search for:

```text
timeout
connection timeout
read timeout
upstream timeout
database timeout
```

### Step 5: Check Database

Investigate:

```text
Slow query
Lock
Connection pool
Database resource usage
```

### Step 6: Check External API

Measure the external service separately if possible.

### Step 7: Check Network

```bash
ip route get <destination-ip>
```

Check packet loss and latency where required.

### Step 8: Check Timeout Configuration

There may be multiple timeout layers:

```text
Client timeout
Load balancer timeout
API gateway timeout
Reverse proxy timeout
Application timeout
Database timeout
External API timeout
```

### Important

Increasing a timeout can make resource exhaustion worse.

Example:

```text
Slow backend
   ↓
Requests wait longer
   ↓
More threads/connections occupied
   ↓
Pool exhaustion
   ↓
More requests timeout
```

### Interview Tip

> "I identify which layer is timing out and measure the actual backend latency before changing timeout values."

# Q393. How do you troubleshoot API connection failures to database or backend services?

## Answer

First identify the backend dependency.

```text
API
 |
 +----> PostgreSQL
 |
 +----> Redis
 |
 +----> Kafka
 |
 +----> External REST API
 |
 +----> Storage
```

### Step 1: Check Configuration

Verify:

```text
Hostname
Port
Protocol
Credentials
TLS configuration
Timeouts
```

Do not expose secrets.

### Step 2: Test DNS

```bash
getent hosts <backend-host>
```

### Step 3: Check Route

```bash
ip route get <backend-ip>
```

### Step 4: Test Port

```bash
nc -vz <backend-host> <port>
```

### Step 5: Test Protocol

HTTP:

```bash
curl -v http://<backend-host>:<port>/health
```

Database:

```bash
psql -h <db-host> -p 5432 -U <user> -d <database>
```

### Step 6: Check Firewall

```bash
firewall-cmd --list-all
```

Also investigate cloud/network security controls.

### Step 7: Check Backend Listener

On backend server:

```bash
ss -lntp
```

### Step 8: Check API Logs

```bash
journalctl -u <api-service> -n 100
```

Look for:

```text
Connection refused
Connection timeout
Unknown host
Authentication failure
SSL error
Pool exhausted
Too many connections
```

### Step 9: Check Backend Health

```text
CPU
Memory
Disk
Connections
Application status
Database health
```

### Step 10: Check Packet Flow

If required:

```bash
sudo tcpdump -ni any port <backend-port>
```

### Important

```text
TCP success
   ≠
Backend healthy
```

### Interview Tip

> "I reproduce the backend connection from the API server, then check DNS, route, TCP, protocol, authentication, security controls, API configuration, and backend health."

# Q394. How do you troubleshoot an API after deployment?

## Answer

A deployment can change:

```text
Code
Configuration
Dependencies
Environment variables
Secrets
Database schema
Runtime
API routes
Authentication
TLS
```

### Step 1: Correlate Timeline

```text
Deployment
    ↓
Issue started
```

Check whether the timing matches.

### Step 2: Check API Process

```bash
systemctl status <api-service>
```

```bash
pgrep -a <api-process>
```

### Step 3: Check Port

```bash
ss -lntp
```

### Step 4: Test Health Endpoint

```bash
curl -v http://127.0.0.1:<port>/health
```

### Step 5: Check API Logs

```bash
journalctl -u <api-service> -b
```

Look for:

```text
Startup failure
Configuration error
Exception
Database connection failure
Authentication error
Missing dependency
Port conflict
```

### Step 6: Compare Configuration

Check:

```text
Environment variables
Secrets
Database URL
External API URL
API keys
TLS certificates
Runtime settings
```

### Step 7: Check API Contract

A deployment may change:

```text
Endpoint
HTTP method
Request format
Response format
Authentication
Status codes
```

This can break clients even if the API process is healthy.

### Step 8: Check Dependencies

```text
Database
Cache
Message queue
Authentication service
External APIs
```

### Step 9: Compare Previous Version

Compare:

```text
Code
Configuration
Dependencies
Runtime
Database changes
```

### Step 10: Consider Controlled Rollback

If the deployment is confirmed as the cause:

```text
Rollback
   ↓
Test API
   ↓
Verify dependencies
   ↓
Monitor
```

Be careful when database schema/data changes are involved.

### Important

```text
Deployment issue
    ≠
Automatically code issue
```

### Interview Tip

> "I correlate the deployment with the incident, compare the previous and current application state, inspect logs and dependencies, test the API locally and externally, and use a controlled rollback if the deployment is confirmed as the cause."

# Q395. How do you troubleshoot a complete production API issue?

## Answer

I use an **end-to-end request flow**.

```text
                         CLIENT
                           |
                           v
                          DNS
                           |
                           v
                  API Gateway / LB
                           |
                           v
                    Web Server
                           |
                           v
                      API APP
                       /  |  \
                      /   |   \
                     v    v    v
                   DB   Cache  External API
```

## Step 1: Define the Incident

Identify:

```text
API
Environment
Endpoint
HTTP method
Affected users
Region
Start time
HTTP status
Exact error
Intermittent or permanent
```

## Step 2: Test the API

```bash
curl -v https://api.example.com/health
```

Test the affected endpoint separately:

```bash
curl -v https://api.example.com/api/users
```

## Step 3: Check DNS

```bash
getent hosts api.example.com
```

```bash
dig api.example.com
```

## Step 4: Check TCP

```bash
nc -vz api.example.com 443
```

## Step 5: Check TLS

```bash
openssl s_client \
-connect api.example.com:443 \
-servername api.example.com
```

## Step 6: Check API Gateway/Load Balancer

Verify:

```text
Listener
Routing rule
Target health
Health check
TLS
Security policy
Rate limits
Backend registration
```

## Step 7: Check Web Server/Reverse Proxy

Nginx:

```bash
nginx -t
```

Apache:

```bash
apachectl -t
```

Check service:

```bash
systemctl status nginx
```

or:

```bash
systemctl status httpd
```

## Step 8: Check API Application

```bash
systemctl status <api-service>
```

```bash
pgrep -a <api-process>
```

```bash
ss -lntp
```

## Step 9: Test API Locally

```bash
curl -v http://127.0.0.1:<port>/health
```

Interpretation:

```text
Local fails
   ↓
API/application/config/dependency issue

Local works
   ↓
Investigate external network/LB/firewall/gateway
```

## Step 10: Check API Logs

```bash
journalctl -u <api-service> -n 100
```

Also inspect:

```text
Application logs
Gateway logs
Load-balancer logs
Web-server logs
```

Use request IDs/correlation IDs when available.

## Step 11: Check Resources

```bash
top
```

```bash
free -h
```

```bash
df -h
```

```bash
df -i
```

```bash
iostat -xz 1
```

## Step 12: Check Database/Backend

DNS:

```bash
getent hosts <backend-host>
```

Port:

```bash
nc -vz <backend-host> <port>
```

Then use the appropriate protocol/database client.

## Step 13: Check Authentication

Investigate:

```text
Token
API key
OAuth/SSO
Issuer
Audience
Expiry
Scopes
Roles
Authentication service
```

## Step 14: Check Network/Security

```bash
ip addr
```

```bash
ip route
```

```bash
ip route get <destination-ip>
```

```bash
firewall-cmd --list-all
```

Also check:

```text
Security Group
NACL
WAF
Network Firewall
Kubernetes NetworkPolicy
API Gateway policy
```

## Step 15: Check Recent Changes

```text
API deployment
Configuration
Secret rotation
Certificate rotation
Database change
DNS change
Firewall change
Gateway/LB change
OS/runtime update
```

## Step 16: Compare Healthy vs Unhealthy Instance

```text
API-01 → Healthy
API-02 → Failing
API-03 → Healthy
```

Compare:

```text
Version
Configuration
Environment
Runtime
Packages
Resources
Network
Dependencies
```

## Step 17: Use Packet Capture if Required

```bash
sudo tcpdump -ni any port <port>
```

Use a targeted capture to answer a specific network question.

## Step 18: Identify the Failing Layer

```text
DNS fails
   ↓
DNS problem

DNS works + TCP fails
   ↓
Network/Security problem

TCP works + TLS fails
   ↓
Certificate/TLS problem

TLS works + HTTP 4xx
   ↓
Request/Auth/Authorization/Routing

HTTP 5xx
   ↓
Gateway/Application/Backend

HTTP succeeds + slow
   ↓
Application/Database/Dependency/Resource
```

## Step 19: Apply the Smallest Safe Fix

Possible fixes:

```text
Correct DNS
Fix routing
Correct firewall/security rule
Fix gateway route
Fix API configuration
Fix authentication configuration
Restore backend connectivity
Rollback deployment
Restart API only when justified
```

## Step 20: Verify End-to-End

```text
DNS
 ↓
TCP
 ↓
TLS
 ↓
Gateway/LB
 ↓
Web Server
 ↓
API
 ↓
Authentication
 ↓
Database/Backend
 ↓
HTTP Response
```

Then monitor:

```text
Availability
Latency
4xx
5xx
Request rate
CPU
Memory
Database connections
Backend errors
```

# ⚠️ Production Safety Rules

```text
1. Capture the exact API endpoint
2. Record HTTP method and status code
3. Identify affected users/instances
4. Check DNS before changing DNS
5. Check TCP before changing firewall rules
6. Check TLS before changing certificates
7. Identify which component generated the response
8. Check logs before changing configuration
9. Protect API keys and tokens
10. Never expose passwords/secrets
11. Do not blindly increase timeouts
12. Do not blindly increase worker/thread/connection limits
13. Do not blindly restart the API
14. Do not blindly flush firewall rules
15. Use targeted packet captures
16. Compare healthy and unhealthy instances
17. Validate deployment-related changes
18. Use controlled rollback when justified
19. Prefer the smallest reversible change
20. Verify the complete request path
21. Monitor after recovery
22. Document RCA and preventive action
```

> **Interview mindset:** Don't say **"API is returning 500, so I will restart the application."** Say: **"I will identify the endpoint, method, status code, scope, and component generating the response. Then I will trace DNS, TCP, TLS, gateway/load balancer, web server, API application, authentication, backend dependencies, resources, security controls, and recent changes. After identifying the failing layer, I will apply the smallest safe fix and verify the API end-to-end."**
