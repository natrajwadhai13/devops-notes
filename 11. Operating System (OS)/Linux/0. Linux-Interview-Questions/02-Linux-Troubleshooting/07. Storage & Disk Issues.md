# Q61. How do you troubleshoot a filesystem that is 100% full?

## Answer

First identify which filesystem is full.

```bash
df -h
```

Example:

```text
Filesystem      Size  Used Avail Use%
/dev/sda3        50G   50G     0 100% /
```

Then identify which directory is consuming the space.

```bash
du -xsh /* 2>/dev/null
```

For a specific directory:

```bash
du -xsh /var/*
```

Find large files:

```bash
find /var -type f -size +1G -ls
```

Also check for deleted files that are still held open:

```bash
lsof +L1
```

### Common Causes

* Large application logs
* Old backup files
* Temporary files
* Core dumps
* Deleted files still open by a process
* Large database files
* Package cache
* Container images/logs

### Important

Do **not** immediately delete random files from a production server.

First identify:

1. What consumed the space?
2. Is the file required?
3. Which application owns it?
4. Is there a cleanup or retention policy?

### Interview Tip

> "I first use `df -h` to identify the full filesystem, then `du` to locate large directories and `find` for large files. I also check `lsof` for deleted-but-open files before taking cleanup action."

# Q62. Why does `df -h` show free space but applications report "No space left on device"?

## Answer

`df -h` checks filesystem **block usage**, but an application may fail because of another resource limit.

First check inode usage:

```bash
df -i
```

If you see:

```text
Filesystem      Inodes IUsed IFree IUse%
/dev/sda3       3.0M  3.0M     0  100%
```

the filesystem has run out of **inodes**, even though disk blocks may still be available.

### Check deleted-but-open files

```bash
lsof +L1
```

A process may still hold a deleted large file open.

### Other Possible Causes

* Inode exhaustion
* User/group quota reached
* Project quota reached
* Reserved filesystem blocks
* Application-specific storage limits
* Container storage limits

### Troubleshooting

```bash
df -h
df -i
quota -s username
lsof +L1
```

### Interview Tip

> "`No space left on device` does not always mean disk capacity is full. I check both `df -h` and `df -i`, followed by quotas and deleted-open files."

# Q63. How do you troubleshoot inode exhaustion?

## Answer

Check inode usage:

```bash
df -i
```

If `IUse%` is close to or equal to `100%`, inode exhaustion is the problem.

Find directories containing a huge number of files:

```bash
find /var -xdev -type f | cut -d/ -f1-4 | sort | uniq -c | sort -nr | head
```

You can also inspect directory contents:

```bash
find /var -xdev -type f | wc -l
```

Common locations:

```text
/var/log
/tmp
/var/tmp
/cache
/application directories
```

### Common Causes

* Millions of small files
* Application-generated temporary files
* Mail queues
* Cache files
* Session files
* Poor application cleanup

### Solution

Remove unnecessary files according to the application's retention policy.

For example:

```bash
find /tmp -type f -mtime +7 -delete
```

**Do not run cleanup commands blindly in production.**

### Interview Tip

> "If disk space is available but inode usage is 100%, I identify directories containing millions of small files and clean them according to the application's retention policy."

# Q64. How do you troubleshoot a full `/boot` filesystem?

## Answer

Check `/boot`:

```bash
df -h /boot
```

List installed kernels:

```bash
rpm -q kernel
```

On RHEL-based systems, remove **old unused kernels** using the package manager rather than manually deleting kernel files.

Check:

```bash
dnf list installed kernel
```

On systems where `dnf` provides the kernel cleanup functionality, review:

```bash
dnf repoquery --installonly --latest-limit=3 -q
```

### Common Causes

* Multiple old kernels
* Kernel package accumulation
* Large files in `/boot`
* Incorrect manual file copying

### Important

Never manually delete the currently running kernel.

Check:

```bash
uname -r
```

### Interview Tip

> "For a full `/boot`, I first check the running kernel with `uname -r`, list installed kernels, and safely remove old unused kernel packages while keeping the active and required fallback kernels."

# Q65. How do you troubleshoot a full `/var` filesystem?

## Answer

First check usage:

```bash
df -h /var
```

Then identify large directories:

```bash
du -xsh /var/*
```

Common locations:

```text
/var/log
/var/cache
/var/lib
/var/tmp
```

Check logs:

```bash
du -sh /var/log/*
```

Check deleted files:

```bash
lsof +L1
```

### Common Causes

* Large system logs
* Application logs
* Package cache
* Database files
* Container data
* Temporary files

### Safe Approach

For logs managed by `systemd-journald`:

```bash
journalctl --disk-usage
```

Review journal retention before cleanup.

For package cache:

```bash
dnf clean all
```

### Interview Tip

> "I don't delete files directly from `/var/lib` because many applications store critical data there. I first identify the owner and purpose of the files."

# Q66. What do you do when a filesystem becomes read-only?

## Answer

Check mount status:

```bash
mount | grep ' ro[,)]'
```

or:

```bash
findmnt -o TARGET,SOURCE,FSTYPE,OPTIONS
```

Check kernel messages:

```bash
dmesg | tail -50
```

Look for errors such as:

```text
I/O error
EXT4-fs error
XFS error
Filesystem shutdown
```

### Common Causes

* Filesystem corruption
* Disk failure
* Storage I/O errors
* Hardware problems
* Filesystem protection mechanisms

Check disk health where supported:

```bash
smartctl -a /dev/sda
```

### Important

Do not simply force the filesystem back to read-write mode without understanding why it became read-only.

For example:

```bash
mount -o remount,rw /
```

may work in some situations, but if the underlying disk/filesystem has errors, the problem can return or become worse.

### Correct Approach

1. Check kernel logs.
2. Check disk/storage health.
3. Identify filesystem type.
4. Schedule filesystem repair if required.
5. Check underlying hardware/storage.

### Interview Tip

> "A read-only filesystem can be a protection mechanism caused by filesystem or I/O errors. I investigate the root cause before remounting it as read-write."

# Q67. How do you troubleshoot a mount failure?

## Answer

First check the mount command and error:

```bash
mount /data
```

Check available block devices:

```bash
lsblk
```

Check filesystem information:

```bash
blkid
```

Check existing mounts:

```bash
findmnt
```

Check `/etc/fstab`:

```bash
cat /etc/fstab
```

### Common Causes

* Incorrect device name
* Wrong UUID
* Incorrect filesystem type
* Missing mount point
* Invalid `/etc/fstab`
* Filesystem corruption
* Missing filesystem support
* Permission/security restrictions

Verify the mount point:

```bash
ls -ld /data
```

Test `/etc/fstab` entries:

```bash
mount -a
```

### Interview Tip

> "I check `lsblk`, `blkid`, `findmnt`, and `/etc/fstab`, then run `mount -a` carefully to identify configuration errors."

# Q68. How do you troubleshoot an `/etc/fstab` or UUID-related mount issue?

## Answer

First check the UUID:

```bash
blkid
```

Example:

```text
/dev/sdb1: UUID="abc123..." TYPE="xfs"
```

Then compare it with `/etc/fstab`:

```bash
cat /etc/fstab
```

Example:

```text
UUID=abc123...  /data  xfs  defaults  0 0
```

If the UUID in `/etc/fstab` does not match the actual disk UUID, the mount can fail.

### Test the configuration

```bash
mount -a
```

If there is an error, correct `/etc/fstab`.

### Important

Always make a backup before modifying:

```bash
cp /etc/fstab /etc/fstab.bak
```

### Common Causes

* Disk replaced
* Partition recreated
* UUID changed
* Typographical error
* Wrong filesystem type
* Incorrect mount point

### Interview Tip

> "`/etc/fstab` should normally use UUIDs or other stable identifiers rather than relying on device names such as `/dev/sdb1`, because device names can change."

# Q69. How do you troubleshoot a newly added disk that is not visible?

## Answer

First check whether Linux detects the disk:

```bash
lsblk
```

```bash
fdisk -l
```

Check kernel messages:

```bash
dmesg | tail -50
```

For SCSI-based disks:

```bash
lsscsi
```

If the disk is still not visible, investigate the virtualization platform, cloud platform, storage system, controller, or physical hardware.

### Possible Causes

* Disk not attached to VM
* Storage presentation problem
* SCSI bus not rescanned
* Controller issue
* Hardware problem
* Cloud volume attachment issue

### After Disk Detection

Once the disk appears, check:

```bash
lsblk
blkid
```

Then decide whether it needs:

* Partitioning
* Filesystem creation
* Mounting
* `/etc/fstab` configuration
* LVM configuration

### Interview Tip

> "I first determine whether the operating system can see the disk. If `lsblk` and `fdisk -l` don't show it, I investigate storage presentation or perform the appropriate device rescan."

# Q70. How do you rescan SCSI disks in Linux?

## Answer

First check existing SCSI devices:

```bash
lsscsi
```

You can inspect SCSI hosts:

```bash
ls /sys/class/scsi_host/
```

A common rescan method is:

```bash
for host in /sys/class/scsi_host/host*; do
    echo "- - -" > "$host/scan"
done
```

Then verify:

```bash
lsblk
```

```bash
fdisk -l
```

### For a Specific SCSI Host

Example:

```bash
echo "- - -" > /sys/class/scsi_host/host0/scan
```

### In Virtualized/Cloud Environments

If a new disk has been attached from the hypervisor or cloud platform, the storage must first be correctly presented to the VM. An OS rescan cannot detect a disk that has not actually been attached/presented.

### Interview Tip

> "For a newly presented SCSI disk, I verify the disk at the infrastructure layer, rescan the appropriate SCSI host, and then confirm the device using `lsblk`."

# 📌 Important Storage Troubleshooting Commands

| Command    | Purpose                                 |
| ---------- | --------------------------------------- |
| `df -h`    | Check filesystem capacity               |
| `df -i`    | Check inode usage                       |
| `du -sh`   | Check directory size                    |
| `find`     | Find large/old files                    |
| `lsblk`    | List block devices                      |
| `blkid`    | Display UUID and filesystem type        |
| `fdisk -l` | List disks and partitions               |
| `findmnt`  | Display mounted filesystems             |
| `mount`    | Mount filesystems                       |
| `mount -a` | Mount `/etc/fstab` entries              |
| `lsscsi`   | Display SCSI devices                    |
| `dmesg`    | Check kernel/device messages            |
| `lsof +L1` | Find deleted files still open           |
| `smartctl` | Check supported disk health information |
| `uname -r` | Check running kernel                    |

# 🎤 Strong Interview Answer

> "When troubleshooting a Linux storage issue, I start with `df -h` and `df -i` to determine whether the problem is disk capacity or inode exhaustion. Then I use `du`, `find`, and `lsof` to identify the cause. For mount or disk-detection issues, I check `lsblk`, `blkid`, `findmnt`, `/etc/fstab`, kernel logs, and SCSI devices. I always identify the root cause before deleting data or modifying production storage."
