# 31. Load Balancer & Reverse Proxy Troubleshooting

> A **Load Balancer** distributes client traffic across backend servers, while a **Reverse Proxy** receives client requests and forwards them to backend applications. Troubleshooting requires checking the complete request path: **Client → DNS → Load Balancer/Reverse Proxy → Backend → Application → Database/Dependency**.

# Q316. What is a Load Balancer and Reverse Proxy?

## Answer

A **Load Balancer** distributes incoming traffic across multiple backend servers.

A **Reverse Proxy** receives client requests and forwards them to backend applications.

### Basic Architecture

```text
                    Client
                       |
                       v
                     DNS
                       |
                       v
              Load Balancer
                       |
          +------------+------------+
          |            |            |
          v            v            v
       Server-1     Server-2     Server-3
          |            |            |
          +------------+------------+
                       |
                       v
                  Application
```

### Reverse Proxy Example

```text
Client
  |
  | HTTPS :443
  v
Nginx
  |
  | HTTP :8080
  v
Application
```

The client may only know:

```text
https://app.example.com
```

while the backend application may run on:

```text
10.10.10.20:8080
```

### Common Load Balancers

Examples:

```text
AWS ALB
AWS NLB
Azure Load Balancer
Azure Application Gateway
HAProxy
Nginx
F5
```

### Common Reverse Proxies

```text
Nginx
HAProxy
Apache HTTP Server
Envoy
Traefik
```

### Important Difference

A load balancer can distribute traffic across multiple backend servers.

A reverse proxy can provide:

```text
TLS termination
Routing
Header modification
Caching
Compression
Authentication
Access control
```

A single product can perform both roles.

### Interview Tip

> "A load balancer distributes traffic among backend servers, while a reverse proxy accepts client requests and forwards them to backend services. In modern environments, the same component can perform both functions."

# Q317. How do you troubleshoot when a Load Balancer is not reachable?

## Answer

Start from the client and move toward the load balancer.

### Step 1: Check DNS

```bash
getent hosts app.example.com
```

```bash
dig app.example.com
```

Verify that DNS points to the expected load-balancer address.

### Step 2: Test the Port

For HTTPS:

```bash
nc -vz app.example.com 443
```

For HTTP:

```bash
nc -vz app.example.com 80
```

### Step 3: Test HTTP/HTTPS

```bash
curl -v https://app.example.com
```

### Step 4: Check Routing

```bash
ip route get <load-balancer-ip>
```

### Step 5: Check Firewall/Security Controls

Depending on architecture:

```text
Client firewall
Network firewall
Cloud Security Group
NACL
Load Balancer listener
WAF
```

### Step 6: Check Load Balancer Listener

Verify:

```text
Listener port
Protocol
Frontend IP
Certificate
Listener rule
Backend target group
```

For example:

```text
HTTPS :443
      |
      v
Target Group
      |
      v
Backend :8080
```

### Step 7: Check Network Path

If the LB is reachable but connections are failing intermittently, investigate:

```text
Routing
NAT
Firewall
Security Group
NACL
Network ACLs
```

### Step 8: Packet Capture

If you control the client/backend host:

```bash
sudo tcpdump -ni any port 443
```

### Important

A load balancer may be:

```text
Public
Private/Internal
```

A private load balancer cannot necessarily be accessed from the public internet.

### Interview Tip

> "I first verify DNS and the frontend listener, then test TCP/HTTPS connectivity, routing and security controls. I don't start troubleshooting backend servers until I know the request is reaching the load balancer."

# Q318. How do you troubleshoot a backend server marked unhealthy?

## Answer

Load balancers normally perform **health checks** against backend servers.

Example:

```text
Load Balancer
     |
     +----> Server-1  Healthy
     |
     +----> Server-2  Unhealthy
     |
     +----> Server-3  Healthy
```

### Step 1: Check Health-Check Configuration

Verify:

```text
Protocol
Port
Path
Expected response
Timeout
Interval
Healthy threshold
Unhealthy threshold
```

Example:

```text
GET /health
Port: 8080
Expected: HTTP 200
```

### Step 2: Check Application Listener

On backend:

```bash
ss -lntp | grep :8080
```

### Step 3: Test Locally

```bash
curl -v http://127.0.0.1:8080/health
```

### Step 4: Test Using Backend IP

```bash
curl -v http://10.10.10.20:8080/health
```

This helps identify binding problems.

### Step 5: Check Application Logs

```bash
journalctl -u <service>
```

Also check application-specific logs.

### Step 6: Check Firewall

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

The backend firewall must allow traffic from the load balancer/health-check source.

### Step 7: Check Security Group/NACL

Verify:

```text
LB → Backend
```

is permitted.

### Step 8: Check SELinux

```bash
getenforce
```

If the application is being blocked:

```bash
ausearch -m AVC -ts recent
```

### Step 9: Check Resources

```bash
free -h
```

```bash
df -h
```

```bash
top
```

A resource-exhausted backend may fail health checks.

### Common Causes

```text
Application stopped
Wrong health-check port
Wrong health-check path
Application listening only on localhost
Firewall blocking LB
Security Group blocking LB
TLS mismatch
Health endpoint returns 4xx/5xx
Application dependency failure
High CPU/memory
Disk full
```

### Interview Tip

> "I compare the exact health-check configuration with what the application actually exposes. I test the health endpoint locally and through the backend network path before changing the load balancer configuration."

# Q319. How do you troubleshoot when the Load Balancer is reachable but the application is not working?

## Answer

Example:

```text
Client
  |
  | HTTPS
  v
Load Balancer
  |
  X
Backend
```

The frontend is reachable, but the application fails.

### Step 1: Check DNS

```bash
dig app.example.com
```

### Step 2: Check LB Response

```bash
curl -v https://app.example.com
```

Identify the HTTP status:

```text
200
301
302
400
401
403
404
500
502
503
504
```

### Step 3: Check Backend Health

Verify target/backend status in the LB.

### Step 4: Check Backend Listener

```bash
ss -lntp
```

### Step 5: Test Backend Locally

```bash
curl -v http://127.0.0.1:8080
```

### Step 6: Test Backend From the LB Network

If possible, test:

```bash
curl -v http://<backend-ip>:8080
```

from an appropriate host in the same network path.

### Step 7: Check Firewall

```bash
firewall-cmd --list-all
```

### Step 8: Check Application Logs

```bash
journalctl -u <service>
```

### Step 9: Check Dependencies

The application may depend on:

```text
Database
Redis
External API
DNS
Authentication service
Storage
Message queue
```

The backend may be "up" but unable to serve requests.

### Step 10: Check Load Balancer Logs/Metrics

Look for:

```text
Request count
Backend errors
Latency
Connection errors
Health-check failures
HTTP status codes
```

### Important

A healthy load balancer does not guarantee a healthy application.

```text
LB healthy
   ≠
Application healthy
```

### Interview Tip

> "I separate frontend health from backend health. I check the HTTP status, backend target health, backend listener, local application response, firewall/security controls, application logs, and downstream dependencies."

# Q320. How do you troubleshoot HTTP 502 Bad Gateway errors?

## Answer

A **502 Bad Gateway** generally means a gateway or reverse proxy received an invalid or unusable response from the upstream/backend.

Example:

```text
Client
  |
  v
Nginx / Load Balancer
  |
  X
Backend
```

### Step 1: Confirm the 502

```bash
curl -v https://app.example.com
```

Check:

```text
HTTP/1.1 502
```

### Step 2: Identify the Proxy/LB

Determine whether the response comes from:

```text
Nginx
HAProxy
Cloud Load Balancer
API Gateway
Other proxy
```

### Step 3: Check Backend Health

```bash
ss -lntp | grep :8080
```

### Step 4: Test Backend Directly

```bash
curl -v http://<backend-ip>:8080
```

If direct backend access fails, focus on:

```text
Application
Port
Firewall
Routing
Backend configuration
```

### Step 5: Check Reverse Proxy Logs

For Nginx, commonly:

```bash
tail -f /var/log/nginx/error.log
```

Actual log location depends on configuration.

### Step 6: Check Backend Logs

```bash
journalctl -u <service>
```

### Step 7: Check Configuration

For Nginx:

```bash
nginx -t
```

Check availability:

```bash
command -v nginx
```

For HAProxy:

```bash
haproxy -c -f /etc/haproxy/haproxy.cfg
```

### Common Causes

```text
Backend service stopped
Wrong backend port
Wrong backend IP
Connection refused
Backend reset connection
Invalid upstream response
Proxy configuration error
TLS mismatch
Backend resource exhaustion
Network/firewall issue
```

### Important

Do not automatically restart Nginx/load balancer.

First determine why the upstream connection failed.

### Interview Tip

> "For a 502, I focus on the proxy-to-backend connection. I verify the upstream address and port, backend listener, direct backend connectivity, proxy logs, backend logs, and TLS/configuration if applicable."

# Q321. How do you troubleshoot HTTP 503 Service Unavailable errors?

## Answer

A **503 Service Unavailable** often means the service cannot currently handle the request.

In a load-balancer environment, common causes include:

```text
No healthy backends
Backend unavailable
Maintenance
Connection limits
Application overload
Load balancer configuration
```

### Step 1: Confirm Response

```bash
curl -v https://app.example.com
```

### Step 2: Check Backend Health

Verify whether the target group contains healthy servers.

Example:

```text
Server-1 Healthy
Server-2 Healthy
Server-3 Unhealthy
```

If all are unhealthy:

```text
LB → No usable backend
```

### Step 3: Check Backend Service

```bash
systemctl status <service>
```

### Step 4: Check Port

```bash
ss -lntp
```

### Step 5: Test Health Endpoint

```bash
curl -v http://127.0.0.1:8080/health
```

### Step 6: Check Resources

```bash
top
```

```bash
free -h
```

```bash
df -h
```

### Step 7: Check Logs

```bash
journalctl -u <service>
```

### Step 8: Check LB Metrics

Look for:

```text
Healthy hosts
Unhealthy hosts
Request count
Backend connection errors
Latency
HTTP 5xx
```

### Important Difference

A 503 does not always mean the application process is completely down.

The application may be:

```text
Running
but overloaded
```

or:

```text
Running
but failing health checks
```

### Interview Tip

> "For 503, I first check whether healthy backends are available. Then I verify the backend service, health endpoint, resources, application logs, and load-balancer health metrics."

# Q322. How do you troubleshoot HTTP 504 Gateway Timeout errors?

## Answer

A **504 Gateway Timeout** generally means a gateway/proxy did not receive a timely response from the upstream service.

Example:

```text
Client
  |
  v
Load Balancer
  |
  | request
  v
Backend
  |
  |---- Database
  |
  |---- External API
  |
  X
Timeout
```

### Step 1: Confirm the 504

```bash
curl -v https://app.example.com
```

### Step 2: Check Backend Health

Verify:

```text
Backend healthy?
Backend reachable?
Backend accepting connections?
```

### Step 3: Test Backend Directly

```bash
curl -v http://<backend-ip>:8080
```

### Step 4: Measure Response Time

```bash
time curl -v http://<backend-ip>:8080
```

### Step 5: Check Application Logs

Look for:

```text
Slow requests
Database timeout
External API timeout
Thread pool exhaustion
Connection pool exhaustion
```

### Step 6: Check Resources

```bash
top
```

```bash
free -h
```

```bash
iostat -xz 1
```

### Step 7: Check Dependencies

The backend may be waiting for:

```text
Database
DNS
External API
Redis
Message queue
Storage
```

### Step 8: Compare Timeout Settings

There may be multiple timeout layers:

```text
Client timeout
        ↓
Load Balancer timeout
        ↓
Reverse Proxy timeout
        ↓
Application timeout
        ↓
Database timeout
```

### Important

Increasing the timeout is not automatically the correct fix.

If a database query takes:

```text
120 seconds
```

simply changing the LB timeout to:

```text
180 seconds
```

may hide the real performance problem.

### Interview Tip

> "For 504, I identify which hop is timing out. I compare proxy/LB timeouts with backend response time and investigate application and downstream dependency latency instead of simply increasing the timeout."

# Q323. How do you troubleshoot SSL/TLS issues on a Load Balancer or Reverse Proxy?

## Answer

TLS can terminate at different points.

### Architecture 1: TLS Termination at LB

```text
Client
  |
 HTTPS
  v
Load Balancer
  |
 HTTP
  v
Backend
```

### Architecture 2: TLS Pass-through

```text
Client
  |
 HTTPS
  v
Load Balancer
  |
 HTTPS
  v
Backend
```

### Step 1: Check Certificate

Use:

```bash
openssl s_client -connect app.example.com:443 -servername app.example.com
```

Check availability:

```bash
command -v openssl
```

### Step 2: Check Certificate Dates

```bash
echo | openssl s_client -connect app.example.com:443 -servername app.example.com 2>/dev/null | openssl x509 -noout -dates
```

### Step 3: Check Certificate Subject/SAN

```bash
echo | openssl s_client -connect app.example.com:443 -servername app.example.com 2>/dev/null | openssl x509 -noout -subject -issuer -ext subjectAltName
```

The hostname should be covered by the certificate's SAN.

### Step 4: Check TLS Version/Cipher Compatibility

Possible problems:

```text
Unsupported TLS version
Unsupported cipher
Client/server incompatibility
Security policy mismatch
```

### Step 5: Check LB Certificate Configuration

Verify:

```text
Correct certificate
Correct hostname
Certificate chain
Listener
TLS policy
Certificate expiry
```

### Step 6: If TLS Also Exists Between LB and Backend

Test backend TLS:

```bash
openssl s_client -connect <backend-ip>:443 -servername backend.example.com
```

### Step 7: Check Time

Incorrect system time can affect TLS validation.

```bash
timedatectl
```

### Common Causes

```text
Expired certificate
Wrong certificate
Missing intermediate certificate
Hostname mismatch
TLS version mismatch
Cipher mismatch
Incorrect SNI
Backend certificate problem
Wrong certificate attached to listener
```

### Interview Tip

> "I first determine where TLS terminates, then verify the certificate, SAN, expiry, SNI, certificate chain, TLS policy, and—if TLS continues to the backend—the backend certificate and connectivity."

# Q324. How do you troubleshoot Load Balancer traffic distribution and sticky-session issues?

## Answer

A load balancer may distribute requests across multiple backend servers.

Example:

```text
             Load Balancer
             /     |     \
            /      |      \
           v       v       v
        App-1    App-2    App-3
```

### Step 1: Check Backend Health

An unhealthy server should generally not receive normal traffic.

Verify:

```text
Healthy targets
Unhealthy targets
Draining targets
```

### Step 2: Check Distribution

Look at LB metrics/logs.

Example:

```text
App-1 → 80% traffic
App-2 → 15%
App-3 → 5%
```

Uneven traffic may be expected depending on:

```text
Algorithm
Connection count
Request duration
Weights
Sticky sessions
Long-lived connections
```

### Step 3: Check Sticky Sessions

Sticky sessions may keep a client associated with one backend.

Common mechanisms include:

```text
Cookies
Source-IP affinity
Load-balancer session persistence
```

### Step 4: Check Application Session Storage

If the application stores sessions locally:

```text
Client
  |
  v
App-1
  |
  | Session exists here
  X
App-2
```

A request sent to App-2 may not find the session.

Solutions may include:

```text
Shared session store
Redis
Database-backed sessions
Stateless application
Appropriate session affinity
```

### Step 5: Check Long-Lived Connections

Traffic may appear uneven because of:

```text
WebSockets
Long HTTP connections
Keep-alive
Streaming
```

### Step 6: Check DNS Load Balancing

If DNS itself distributes traffic, verify:

```bash
dig app.example.com
```

Multiple IPs may be returned.

### Important

Uneven traffic does not automatically mean the load balancer is broken.

### Interview Tip

> "I check target health, load-balancing algorithm, weights, sticky-session behavior, connection duration, and application session design before concluding that traffic distribution is incorrect."

# Q325. How do you troubleshoot a complete production Load Balancer/Reverse Proxy issue?

## Answer

I troubleshoot the complete request path.

```text
Client
  |
  v
DNS
  |
  v
Load Balancer / Reverse Proxy
  |
  v
Backend
  |
  v
Application
  |
  v
Dependencies
```

### Step 1: Define the Problem

Identify:

```text
Hostname
URL
Source
Time of failure
HTTP status
One user or all users?
One backend or all backends?
Intermittent or permanent?
```

### Step 2: Check DNS

```bash
getent hosts app.example.com
```

```bash
dig app.example.com
```

### Step 3: Test Frontend

```bash
curl -v https://app.example.com
```

Check:

```text
DNS
TCP connection
TLS handshake
HTTP status
Response headers
Response time
```

### Step 4: Identify HTTP Status

```text
200 → Request succeeded
3xx → Redirect
4xx → Client/request/auth issue
502 → Upstream/proxy problem
503 → Service/backend availability
504 → Upstream timeout
```

Do not treat these as absolute rules; the exact meaning depends on the component generating the response.

### Step 5: Check Load Balancer

Verify:

```text
Listener
Target group
Backend health
Routing rules
Certificates
Security controls
Timeouts
Connection limits
```

### Step 6: Check Backend

```bash
ss -lntp
```

Test:

```bash
curl -v http://127.0.0.1:8080/health
```

### Step 7: Test Backend From Network Path

If possible:

```bash
curl -v http://<backend-ip>:8080/health
```

### Step 8: Check Firewall

```bash
firewall-cmd --list-all
```

or:

```bash
nft list ruleset
```

### Step 9: Check Application Logs

```bash
journalctl -u <service>
```

Also inspect application-specific logs.

### Step 10: Check Resources

```bash
top
```

```bash
free -h
```

```bash
df -h
```

```bash
iostat -xz 1
```

### Step 11: Check Dependencies

Investigate:

```text
Database
DNS
Redis
External APIs
Message queues
Storage
Authentication
```

### Step 12: Check TLS

If HTTPS is involved:

```bash
openssl s_client -connect app.example.com:443 -servername app.example.com
```

### Step 13: Check Network Path

```bash
ip route get <destination-ip>
```

If necessary:

```bash
sudo tcpdump -ni any port 443
```

### Step 14: Compare Healthy vs Unhealthy Backend

If only one backend is failing:

```text
App-1 → Healthy
App-2 → Unhealthy
App-3 → Healthy
```

Compare:

```text
Configuration
Application version
Resources
Network
Firewall
Logs
Health endpoint
Dependencies
```

This is often faster than changing the load balancer itself.

### Step 15: Check Recent Changes

Look for:

```text
Application deployment
Load balancer configuration
Certificate renewal
Firewall changes
DNS changes
Security Group changes
Backend configuration
OS/package updates
```

### Step 16: Apply the Smallest Safe Fix

Examples:

```text
Remove unhealthy backend from rotation
Fix health-check configuration
Correct backend port
Fix firewall rule
Fix application
Correct certificate
Rollback bad deployment
Correct proxy configuration
```

### Step 17: Verify End-to-End

```text
DNS
 ↓
TCP
 ↓
TLS
 ↓
Load Balancer
 ↓
Backend
 ↓
Application
 ↓
Dependencies
```

### Production Scenario

**Interviewer:**

> "Users are getting 502/503 errors from the production application. What will you check?"

**Strong Answer:**

> "First I would determine whether the errors are 502 or 503, whether they affect all users or only some requests, and whether all or only some backends are affected. I would verify DNS and test the frontend with `curl -v`. Then I would check the load balancer listener, target health, routing rules, and recent configuration changes. On the backend I would verify the listening port with `ss`, test the health endpoint and application directly, and inspect application and service logs. I would also check firewall/security controls, resources, TLS if applicable, and downstream dependencies such as databases or external APIs. If the behavior is unclear, I would use targeted packet capture and load-balancer logs/metrics to identify the failing hop. I would make the smallest safe change, verify the complete request path, and document the root cause."

# 🎤 Load Balancer Interview Golden Rules

```text
Load Balancer reachable ≠ Backend healthy
Backend healthy ≠ Application healthy
Listening port ≠ Health-check success
Health-check success ≠ Full application health
502 ≠ Automatically application down
503 ≠ Automatically server down
504 ≠ Automatically network failure
DNS works ≠ Load Balancer works
TCP works ≠ HTTP works
HTTP works ≠ Application business logic works
TLS succeeds ≠ Backend is healthy
One unhealthy backend ≠ Entire application is down
Uneven traffic ≠ Automatically load-balancer failure
Sticky sessions ≠ Automatically the best solution
Increasing timeout ≠ Fixing root cause
Restarting proxy ≠ Troubleshooting
```

# ⚠️ Production Safety Rules

Before changing a Load Balancer or Reverse Proxy:

```text
1. Identify the exact URL
2. Identify source and destination
3. Check DNS
4. Check frontend listener
5. Check TCP connectivity
6. Check TLS if applicable
7. Identify HTTP status
8. Check backend health
9. Check backend listener
10. Test backend directly
11. Check firewall/security controls
12. Check application logs
13. Check resources
14. Check dependencies
15. Check LB/proxy logs and metrics
16. Check recent changes
17. Compare healthy vs unhealthy backends
18. Avoid blindly restarting the LB/proxy
19. Avoid blindly increasing timeouts
20. Avoid removing all backends from production
21. Make the smallest reversible change
22. Verify end-to-end
23. Monitor after the change
24. Document the root cause
```

> **Interview mindset:** Don't say **"502 means restart Nginx"** or **"503 means restart the server."** Say: **"I identify which component generated the response, check backend health and connectivity, verify listeners and health checks, inspect proxy/LB and application logs, check security controls and dependencies, identify the failing hop, and then apply the smallest safe fix."**
