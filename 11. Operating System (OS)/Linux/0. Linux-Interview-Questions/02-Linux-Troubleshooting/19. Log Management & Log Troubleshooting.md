# 19. Log Management & Log Troubleshooting

> Linux logs provide evidence about what happened on a system. Effective troubleshooting means knowing **where logs are stored, how to search them, how to filter them by time/service/severity, and how to identify whether logs are missing because of an application, logging service, disk, permissions, or configuration issue**.

# Q196. What are Linux logs and why are they important?

## Answer

Linux logs are records of system, application, security, kernel, and service events.

They help answer:

```text
What happened?
When did it happen?
Which service/process was involved?
What error occurred?
What changed before the failure?
```

### Common Log Sources

```text
Linux System
    |
    +-- systemd journal
    +-- Authentication
    +-- Kernel
    +-- Applications
    +-- Services
    +-- Cron / Scheduled jobs
    +-- Security / Audit
```

### Examples

A service fails:

```text
systemctl status nginx
```

Then check:

```bash
journalctl -u nginx
```

Authentication problem:

```bash
journalctl
```

or distribution-specific authentication logs under:

```text
/var/log/
```

Kernel problem:

```bash
journalctl -k
```

### Why Logs Matter in Production

Without logs, troubleshooting becomes guesswork.

For example:

```text
Application Down
       |
       v
Check Logs
       |
       +-- Port already in use
       +-- Permission denied
       +-- Configuration error
       +-- Database unavailable
       +-- Certificate expired
```

### Interview Tip

> "Logs provide evidence about system and application behavior. I use them to establish the timeline, identify the failing component, correlate errors with recent changes, and confirm whether a fix worked."

# Q197. Where are Linux log files commonly stored?

## Answer

Traditional Linux log files are commonly stored under:

```bash
/var/log/
```

Check:

```bash
ls -lah /var/log/
```

### Common Log Files

| Log                        | Typical Purpose                                     |
| -------------------------- | --------------------------------------------------- |
| `/var/log/messages`        | General system messages on some distributions       |
| `/var/log/syslog`          | General system messages on Debian/Ubuntu systems    |
| `/var/log/auth.log`        | Authentication logs on Debian/Ubuntu                |
| `/var/log/secure`          | Authentication/security logs on RHEL-family systems |
| `/var/log/kern.log`        | Kernel logs on some distributions                   |
| `/var/log/boot.log`        | Boot-related logs on some systems                   |
| `/var/log/cron`            | Cron-related logs on some systems                   |
| `/var/log/dmesg`           | Kernel boot/message information on some systems     |
| `/var/log/audit/`          | SELinux/Linux audit logs when auditd is configured  |
| Application-specific files | Application logs                                    |

### Important

Not every Linux distribution uses exactly the same log files.

For example:

```text
RHEL-family
    → /var/log/messages
    → /var/log/secure

Debian/Ubuntu
    → /var/log/syslog
    → /var/log/auth.log
```

Modern systems may rely heavily on **systemd-journald** instead of traditional text log files.

### Check Journald

```bash
journalctl
```

### Check Journal Disk Usage

```bash
journalctl --disk-usage
```

### Interview Tip

> "I normally start with `/var/log`, but I don't assume a particular file exists because log locations differ by distribution and service. On systemd-based systems, I also check the journal with `journalctl`."

# Q198. How do you view and search Linux log files?

## Answer

For normal text logs:

### View Entire File

```bash
cat /var/log/messages
```

For large files, prefer:

```bash
less /var/log/messages
```

### View Last Lines

```bash
tail /var/log/messages
```

### Follow New Log Entries

```bash
tail -f /var/log/messages
```

### Follow More Lines

```bash
tail -n 100 -f /var/log/messages
```

### Search for an Error

```bash
grep -i "error" /var/log/messages
```

Multiple patterns:

```bash
grep -Ei "error|failed|critical|denied" /var/log/messages
```

### Search With Line Numbers

```bash
grep -in "error" /var/log/messages
```

### Search Compressed Logs

Rotated logs may be compressed:

```text
messages.1
messages.2.gz
```

Use:

```bash
zgrep -i "error" /var/log/messages*.gz
```

### Check Log File Size

```bash
du -sh /var/log/*
```

### Useful Combination

```bash
tail -n 200 /var/log/messages | grep -Ei "error|fail|warning"
```

### Important

Do not automatically use:

```bash
cat huge-log-file
```

for very large production logs.

Prefer:

```bash
less
tail
grep
awk
```

to reduce output and focus on the relevant timeframe.

### Interview Tip

> "For log analysis, I usually use `less` for browsing, `tail -f` for real-time monitoring, and `grep` for searching. For rotated compressed logs, I use `zgrep`."

# Q199. How do you troubleshoot an issue using journalctl?

## Answer

`journalctl` is used to query logs collected by **systemd-journald**.

### View All Journal Entries

```bash
journalctl
```

### View Recent Logs

```bash
journalctl -n 100
```

### Follow Logs in Real Time

```bash
journalctl -f
```

### Logs for a Service

```bash
journalctl -u nginx
```

Follow service logs:

```bash
journalctl -u nginx -f
```

### Logs for Current Boot

```bash
journalctl -b
```

Kernel logs:

```bash
journalctl -k -b
```

Previous boot:

```bash
journalctl -b -1
```

### Logs Since a Time

```bash
journalctl --since "1 hour ago"
```

Example:

```bash
journalctl --since "2026-09-02 10:00:00"
```

### Logs Between Two Times

```bash
journalctl --since "10:00:00" --until "11:00:00"
```

### Show Errors

```bash
journalctl -p err
```

For current boot:

```bash
journalctl -b -p err
```

### Search Text

```bash
journalctl | grep -i "error"
```

### Example Troubleshooting

```text
Application Failed
       |
       v
systemctl status app
       |
       v
journalctl -u app
       |
       v
Find Exact Error
       |
       v
Investigate Root Cause
```

### Important

`journalctl` only shows logs available in the systemd journal.

An application may instead write to:

```text
/var/log/
Application-specific directory
Container logs
Remote logging system
```

### Interview Tip

> "For a systemd service, I usually combine `systemctl status <service>` with `journalctl -u <service>`. I then filter by boot, time, and severity to isolate the failure."

# Q200. How do you troubleshoot when logs are not being generated?

## Answer

First determine whether:

```text
The application is not generating logs
OR
The logging service is not collecting them
OR
The logs are being written somewhere else
```

### Step 1: Check the Application/Service

```bash
systemctl status myservice
```

### Step 2: Check Journal

```bash
journalctl -u myservice
```

### Step 3: Check `/var/log`

```bash
ls -lah /var/log/
```

### Step 4: Check Configuration

Determine where the application is configured to write logs.

For example:

```text
/var/log/myapp/
```

or:

```text
stdout / stderr
```

### Step 5: Check Permissions

```bash
ls -ld /var/log/myapp
ls -l /var/log/myapp/
```

Check the service user:

```bash
ps -ef | grep myservice
```

### Step 6: Check Disk Space

```bash
df -h
```

Also check inodes:

```bash
df -i
```

### Step 7: Check SELinux

```bash
getenforce
```

Check contexts:

```bash
ls -Z /var/log/myapp/
```

If SELinux denials are suspected:

```bash
ausearch -m AVC -ts recent
```

### Step 8: Check Journald

```bash
systemctl status systemd-journald
```

### Possible Causes

```text
Wrong log path
Permission problem
Disk full
Inodes exhausted
SELinux denial
Service not running
Logging configuration error
journald issue
Application logging disabled
Logs sent to remote system
Containerized application
```

### Interview Tip

> "If logs are missing, I don't immediately blame journald. I verify the application's configured log destination, service status, permissions, disk/inodes, SELinux, journald, and whether the application sends logs to stdout or a remote logging platform."

# Q201. How do you troubleshoot a service using its logs?

## Answer

Suppose a service named `myapp` is failing.

### Step 1: Check Service Status

```bash
systemctl status myapp
```

### Step 2: Check Recent Logs

```bash
journalctl -u myapp -n 100
```

### Step 3: Follow Logs

```bash
journalctl -u myapp -f
```

### Step 4: Search for Important Errors

```bash
journalctl -u myapp | grep -Ei "error|failed|fatal|denied"
```

### Step 5: Check the Time of Failure

```bash
journalctl -u myapp --since "30 minutes ago"
```

### Step 6: Correlate With Other Components

For example:

```text
myapp
  |
  +-- Database
  +-- Network
  +-- DNS
  +-- Filesystem
  +-- Authentication
  +-- Certificates
```

If the application reports:

```text
Connection refused
```

do not assume the application itself is broken.

Check the dependency:

```bash
ss -lntp
```

and network connectivity.

### Step 7: Check Recent Changes

Look for:

```text
Deployment
Configuration change
Package update
Certificate change
Permission change
Server restart
Network change
```

### Troubleshooting Model

```text
Service Failure
      |
      v
systemctl status
      |
      v
journalctl -u service
      |
      v
Exact Error
      |
      v
Dependency / Resource / Configuration
      |
      v
Fix
      |
      v
Verify Logs
      |
      v
Verify Service
```

### Interview Tip

> "I use logs to identify the exact failure rather than repeatedly restarting the service. I correlate the error with dependencies, resources, configuration, and recent changes."

# Q202. How do you check logs for a specific time period or severity?

## Answer

Filtering logs by time is extremely useful during production incidents.

### Last 30 Minutes

```bash
journalctl --since "30 minutes ago"
```

### Specific Start Time

```bash
journalctl --since "2026-09-02 10:00:00"
```

### Time Range

```bash
journalctl \
  --since "2026-09-02 10:00:00" \
  --until "2026-09-02 11:00:00"
```

### Service + Time

```bash
journalctl -u nginx \
  --since "2026-09-02 10:00:00" \
  --until "2026-09-02 11:00:00"
```

### Errors

```bash
journalctl -p err
```

### Warning and Above

```bash
journalctl -p warning
```

### Current Boot Errors

```bash
journalctl -b -p err
```

### Important

Severity filtering is useful, but do not assume every important application failure is logged at `err`.

Some applications may log critical information as:

```text
info
warning
notice
```

Therefore, combine:

```text
Time
+
Service
+
Severity
+
Relevant keywords
```

### Example

```bash
journalctl -u myapp \
  --since "1 hour ago" | \
  grep -Ei "error|failed|timeout|denied|connection"
```

### Interview Tip

> "During an incident, I narrow logs by service and time first, then use severity and keywords. This reduces noise and helps establish an accurate failure timeline."

# Q203. What is logrotate and how do you troubleshoot log rotation issues?

## Answer

**logrotate** automatically manages and rotates log files so they do not grow indefinitely.

### Why Log Rotation Is Needed

Without rotation:

```text
application.log
     |
     v
10 MB
     |
     v
1 GB
     |
     v
50 GB
     |
     v
Disk Full
```

With rotation:

```text
application.log
application.log.1
application.log.2
application.log.3.gz
```

### Check logrotate

```bash
command -v logrotate
```

Check version:

```bash
logrotate --version
```

### Main Configuration

Common locations include:

```text
/etc/logrotate.conf
/etc/logrotate.d/
```

Check:

```bash
cat /etc/logrotate.conf
ls -lah /etc/logrotate.d/
```

### Check Logrotate Timer

On systemd systems:

```bash
systemctl list-timers | grep logrotate
```

Depending on the distribution, logrotate may instead be triggered by another scheduling mechanism.

### Test Configuration

A common diagnostic option is:

```bash
sudo logrotate -d /etc/logrotate.conf
```

`-d` performs a debug/dry-run style check without making the normal rotation changes.

### Force Rotation

For testing/controlled operations:

```bash
sudo logrotate -f /etc/logrotate.conf
```

Use carefully on production systems.

### Common Problems

```text
Incorrect configuration
Wrong file path
Permission problem
Missing directory
Incorrect ownership
Scheduler/timer problem
Application does not reopen log file
Disk full
SELinux restrictions
```

### Interview Tip

> "Logrotate prevents logs from consuming unlimited disk space. I check `/etc/logrotate.conf`, `/etc/logrotate.d/`, the scheduler, configuration with `logrotate -d`, permissions, and whether the application properly handles rotated log files."

# Q204. How do you troubleshoot high disk usage caused by logs?

## Answer

First identify whether logs are actually consuming the disk.

### Step 1: Check Filesystem Usage

```bash
df -h
```

### Step 2: Check `/var`

```bash
du -xhd1 /var
```

### Step 3: Check `/var/log`

```bash
du -xhd1 /var/log
```

### Step 4: Find Large Log Files

```bash
find /var/log -type f -size +500M -ls
```

### Step 5: Check Journal Size

```bash
journalctl --disk-usage
```

### Step 6: Check Deleted but Open Files

This is an important production case:

```bash
lsof +L1
```

A process may still hold a deleted log file open.

Example:

```text
logfile.log
     |
     v
Deleted
     |
     v
Process still has file open
     |
     v
Disk space NOT released
```

### Step 7: Check Logrotate

```bash
ls -lah /etc/logrotate.d/
```

Review the relevant configuration.

### Common Causes

```text
Application logging too much
Debug logging enabled
Logrotate not working
Large retained logs
Journal growing
Deleted-open files
Disk/inode exhaustion
Application log loop
```

### Important

Do **not** blindly run:

```bash
rm -rf /var/log/*
```

on a production system.

This can:

* Remove important evidence
* Break applications
* Remove required log files
* Make incident investigation harder

### Safer Approach

```text
Identify large logs
        |
        v
Identify why they grew
        |
        v
Check logrotate
        |
        v
Check application logging
        |
        v
Free space safely
        |
        v
Prevent recurrence
```

### Interview Tip

> "If `/var` is full because of logs, I identify the largest consumers, check logrotate and application logging, look for deleted-open files with `lsof +L1`, and free space using a controlled approach rather than deleting logs blindly."

# Q205. How do you troubleshoot a production issue using Linux logs?

## Answer

I use logs as **evidence**, not as the only source of information.

### Step 1: Define the Incident

Identify:

```text
What is failing?
When did it start?
Which server?
Which service?
Which users are affected?
```

### Step 2: Establish the Timeline

Check:

```bash
date
```

Then inspect the relevant period:

```bash
journalctl --since "30 minutes ago"
```

### Step 3: Check the Service

```bash
systemctl status myapp
```

### Step 4: Check Service Logs

```bash
journalctl -u myapp --since "30 minutes ago"
```

### Step 5: Check Kernel/System Logs

```bash
journalctl -k --since "30 minutes ago"
```

### Step 6: Check Resources

```bash
df -h
```

```bash
df -i
```

```bash
free -h
```

```bash
uptime
```

### Step 7: Correlate Logs

For example:

```text
10:00  Deployment started
10:02  Application restarted
10:03  Connection errors
10:04  Database timeout
10:05  Users report failure
```

This timeline is much more useful than looking at one error in isolation.

### Step 8: Check Recent Changes

Investigate:

```text
Deployment
Package update
Configuration change
Certificate renewal
Permission change
Network change
Kernel update
```

### Step 9: Fix the Root Cause

Do not simply suppress the error.

For example:

```text
Disk full
   |
   +-- Delete logs
```

is incomplete.

Instead investigate:

```text
Why did logs grow?
   |
   +-- Debug logging?
   +-- Application loop?
   +-- Logrotate broken?
   +-- Retention too high?
```

### Step 10: Verify

After the fix:

```bash
systemctl status myapp
```

```bash
journalctl -u myapp --since "5 minutes ago"
```

Then verify the application from the user/service perspective.

### Production Scenario

**Interviewer:**

> "The application suddenly went down at 2:00 PM. How will you use Linux logs to troubleshoot it?"

**Strong Answer:**

> "First I would confirm the affected server, service, and exact incident time. I would check `systemctl status` and then use `journalctl -u <service>` filtered around the incident window. I would also check kernel logs and system resources such as disk, memory, and CPU. Then I would correlate the application logs with dependencies and recent deployments or configuration changes. After identifying the root cause, I would apply the smallest safe fix, verify the service and application, and document the timeline and root cause."

# 🎤 Log Interview Golden Rules

```text
Log missing ≠ automatically journald problem
Service failure ≠ automatically application bug
Large /var ≠ automatically logs
Disk full ≠ automatically large log files
Logrotate configured ≠ logrotate working
Journal exists ≠ all application logs are there
Error message ≠ automatically root cause
Recent error ≠ automatically first cause
```

Always investigate:

```text
Time
 +
Service
 +
Log Source
 +
Severity
 +
Exact Error
 +
Resources
 +
Dependencies
 +
Recent Changes
 +
Configuration
```

### ⚠️ Production Safety Rules

Before modifying or deleting logs:

```text
1. Preserve important incident evidence
2. Identify why logs are growing
3. Check disk and inode usage
4. Check logrotate
5. Check application logging level
6. Check journal usage
7. Check deleted-open files
8. Avoid blindly deleting /var/log/*
9. Avoid disabling logging to hide disk problems
10. Make controlled cleanup changes
11. Verify applications after cleanup
12. Prevent recurrence
13. Document the root cause
```

> **Interview mindset:** Do not say, "The application is down, so I will check `/var/log/messages`." Say, "I will first establish the incident timeline and affected service, then check service-specific logs, journal/kernel logs, resources, dependencies, and recent changes. I will use the logs to build evidence and identify the root cause before making a controlled fix."
