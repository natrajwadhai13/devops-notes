# Q396. What are microservices and how do you troubleshoot a microservices application?

## Answer

**Microservices architecture** divides an application into multiple small, independently deployable services.

Example:

```text id="7h2k9m"
                    Client
                      |
                      v
               API Gateway / LB
                      |
        +-------------+-------------+
        |             |             |
        v             v             v
     User          Order         Payment
    Service       Service        Service
        |             |             |
        v             v             v
      User DB      Order DB     Payment DB
                      |
                      v
                 Message Queue
```

Each service may have its own:

```text id="6m4p8q"
Process
Port
Configuration
Database
Logs
Resources
Deployment
Dependencies
```

### Common Microservices Problems

```text id="q5x8m2"
Service unavailable
DNS/service discovery failure
Network connectivity
Authentication failure
Timeout
High latency
Database failure
Message queue failure
Resource exhaustion
Configuration mismatch
Deployment problem
Certificate/TLS issue
Cascading failure
```

### Basic Troubleshooting Flow

```text id="8k3m7p"
Client
  |
  v
Gateway
  |
  v
Service A
  |
  v
Service B
  |
  v
Service C
  |
  +----> Database
  |
  +----> Queue
```

Identify **which service first fails**, rather than troubleshooting every service at the same time.

### Useful Linux Commands

```bash id="m4x7q2"
ps -ef
```

```bash id="x8m3p5"
ss -lntp
```

```bash id="q5m2x8"
curl -v <service-url>
```

```bash id="p7x4m2"
getent hosts <service-host>
```

```bash id="m8q3x5"
nc -vz <service-host> <port>
```

```bash id="x4m7q2"
top
```

```bash id="p5x8m3"
free -h
```

```bash id="q7m2x4"
journalctl -u <service>
```

### Interview Tip

> "In microservices, I identify the failing service and dependency first, then trace the request path through service discovery, network, authentication, application health, and backend dependencies."

# Q397. How do you troubleshoot when one microservice is down?

## Answer

Suppose:

```text id="4x7m2p"
Order Service → DOWN
```

while other services are healthy.

### Step 1: Check Service

```bash id="m8q3x5"
systemctl status order-service
```

### Step 2: Check Process

```bash id="p5x7m2"
pgrep -a <order-process>
```

### Step 3: Check Port

```bash id="x4m8q3"
ss -lntp | grep :8081
```

### Step 4: Check Logs

```bash id="q7m2x5"
journalctl -u order-service -n 100
```

Look for:

```text id="m5x8q2"
Startup failure
Configuration error
Database connection failure
Port conflict
Authentication failure
Out-of-memory
Dependency failure
Certificate error
```

### Step 5: Check Resources

```bash id="x8m3q4"
top
```

```bash id="p4m7x2"
free -h
```

```bash id="m7x2q5"
df -h
```

### Step 6: Test Locally

```bash id="q8m3x2"
curl -v http://127.0.0.1:8081/health
```

### Step 7: Check Dependencies

The service may be down because it cannot connect to:

```text id="x5m8q3"
Database
Redis
Message queue
Authentication service
Another microservice
External API
```

### Step 8: Check Recent Changes

```text id="m3x7q2"
Deployment
Configuration
Secret rotation
Certificate change
OS update
Database change
```

### Important

Do not immediately restart the service repeatedly.

Find out **why it stopped**.

### Interview Tip

> "I check service state, process, port, startup logs, resources, health endpoint, dependencies, and recent changes before deciding whether a restart or rollback is appropriate."

# Q398. How do you troubleshoot communication failure between microservices?

## Answer

Example:

```text id="7m3x8q"
Order Service
      |
      X
      |
Payment Service
```

### Step 1: Identify Source and Destination

Determine:

```text id="m5q8x2"
Source service
Destination service
Hostname
Port
Protocol
Endpoint
```

### Step 2: Check DNS/Service Name

```bash id="x7m3p4"
getent hosts payment-service
```

### Step 3: Check Route

```bash id="q4m8x2"
ip route get <payment-ip>
```

### Step 4: Test TCP

```bash id="m7x2q5"
nc -vz payment-service 8082
```

### Step 5: Test HTTP/API

```bash id="x5m8q3"
curl -v http://payment-service:8082/health
```

### Step 6: Check Destination Listener

On the destination server:

```bash id="p8m3q2"
ss -lntp | grep :8082
```

### Step 7: Check Firewall/Security

Investigate:

```text id="q7m2x4"
Host firewall
Cloud Security Group
Network ACL
Service mesh policy
Kubernetes NetworkPolicy
API Gateway policy
```

### Step 8: Check Application Logs

Source service:

```text id="m4x8q2"
Connection refused
Timeout
DNS failure
TLS failure
Authentication error
```

Destination service:

```text id="p5m7x3"
Request received?
Request rejected?
Application error?
```

### Step 9: Check TLS if HTTPS

```bash id="x8m2q4"
openssl s_client \
-connect payment-service:8443 \
-servername payment-service
```

### Step 10: Check Packet Flow if Required

```bash id="q3m7x2"
sudo tcpdump -ni any port 8082
```

### Important

```text id="m8x2q5"
Service A cannot reach Service B
        ≠
Automatically Service B is down
```

The problem can be on:

```text id="p7m3x2"
DNS
Routing
Firewall
Security policy
TLS
Source service
Destination service
```

### Interview Tip

> "I test communication from the source service itself, using the same hostname, port, and protocol, then check destination listener, network/security controls, TLS, and logs on both sides."

# Q399. How do you troubleshoot service discovery problems in microservices?

## Answer

**Service discovery** allows one service to locate another service dynamically.

Instead of:

```text id="5x8m2q"
10.20.10.50:8080
```

a service may use:

```text id="m7q3x5"
payment-service
```

Common mechanisms include:

```text id="x4m8q2"
DNS
Service registry
Kubernetes Services
Cloud service discovery
Consul
Eureka
```

### Step 1: Test Name Resolution

```bash id="p8m3x2"
getent hosts payment-service
```

### Step 2: Test DNS

```bash id="q5m7x4"
dig payment-service
```

### Step 3: Check Resolver Configuration

```bash id="x8m2q3"
cat /etc/resolv.conf
```

### Step 4: Check Service Discovery System

Depending on the environment, inspect:

```text id="m4x7q2"
Service registry
DNS records
Kubernetes Service
Service endpoints
Cloud discovery configuration
```

### Step 5: Test Connectivity

```bash id="p7m3x2"
nc -vz payment-service 8080
```

### Step 6: Check Application Configuration

Verify the service is using the correct:

```text id="x5m8q3"
Service name
Port
Protocol
Namespace/environment
```

### Step 7: Check Registration

A service may be running but not registered correctly.

Check:

```text id="q8m3x2"
Service registration
Health status
Instance address
Instance port
TTL/heartbeat
```

### Step 8: Check Stale Registration

Possible situation:

```text id="m7x2q5"
Service registry
      |
      +----> Old instance
      |
      +----> New instance
```

The caller may receive an unavailable endpoint.

### Important

```text id="x4m8q2"
Service running
    ≠
Service discoverable
```

And:

```text id="p5m7x3"
DNS resolves
    ≠
Service healthy
```

### Interview Tip

> "I verify service-name resolution, discovery registration, returned endpoints, ports, health status, and connectivity from the calling service."

# Q400. How do you troubleshoot cascading failures between microservices?

## Answer

A **cascading failure** occurs when failure in one service causes problems in dependent services.

Example:

```text id="7x3m8q"
Database Slow
     |
     v
Order Service Slow
     |
     v
Payment Service Requests Wait
     |
     v
Connection Pools Exhaust
     |
     v
API Gateway Errors
     |
     v
Application Outage
```

### Step 1: Find the First Failure

Do not start with the final error.

Build a timeline:

```text id="m5q8x2"
10:00 Database latency increased
10:02 Order Service latency increased
10:03 Connection pools increased
10:05 Payment Service timeouts
10:06 API 503 errors
```

The first event may be the actual starting point.

### Step 2: Check Error Rates

Look at:

```text id="x7m3q4"
HTTP 5xx
Timeouts
Connection failures
Retries
Queue depth
```

### Step 3: Check Connection Pools

Investigate:

```text id="p4m8x2"
Database connections
HTTP connections
Thread pools
Worker pools
```

### Step 4: Check Retries

Poor retry configuration can amplify failures.

Example:

```text id="m8x2q5"
Service A
  |
  +---- retry × 3
       |
       v
Service B
  |
  +---- retry × 3
       |
       v
Database
```

A small failure can generate a large number of requests.

### Step 5: Check Timeouts

Long timeouts can cause:

```text id="q5m7x2"
Threads waiting
Connections occupied
Queues growing
Memory increasing
```

### Step 6: Check Resource Usage

```bash id="x4m8q3"
top
```

```bash id="p7m2x5"
free -h
```

### Step 7: Check Dependency Health

Investigate:

```text id="m8q3x2"
Database
Cache
Queue
External API
Authentication
Service discovery
```

### Step 8: Check Circuit Breakers

If implemented, verify whether the application is correctly preventing requests from continuously reaching a failing dependency.

### Common Causes

```text id="x5m7q2"
Database overload
Connection pool exhaustion
Retry storm
Long timeouts
Slow external API
Service dependency failure
Resource exhaustion
Traffic spike
```

### Important

The service producing the final `503` may not be the original cause.

### Interview Tip

> "For cascading failures, I establish the timeline and identify the first failing dependency. Then I investigate retries, timeouts, connection pools, queues, resource usage, and dependency health."

# Q401. How do you troubleshoot high latency in a microservices application?

## Answer

Microservices latency can accumulate across multiple service calls.

Example:

```text id="8m3q7x"
API Gateway       20 ms
      +
User Service      30 ms
      +
Order Service    100 ms
      +
Payment Service  500 ms
      +
Database         300 ms
      =
Request latency
```

### Step 1: Identify the Slow Endpoint

```bash id="m5x8q2"
curl -v https://api.example.com/orders
```

### Step 2: Check Application Metrics

Look for:

```text id="x7m3q4"
Request latency
p50
p95
p99
Error rate
Request rate
```

### Step 3: Trace the Request

If distributed tracing is available, follow:

```text id="p4m8x2"
Gateway
 ↓
Service A
 ↓
Service B
 ↓
Service C
 ↓
Database
```

A correlation/trace ID is extremely useful.

### Step 4: Check Individual Services

```bash id="m8q3x2"
top
```

```bash id="x5m7q4"
free -h
```

Check:

```text id="q7m2x3"
CPU
Memory
Threads
Workers
Connection pools
```

### Step 5: Check Network

```bash id="p8m3x2"
ip route get <destination-ip>
```

Test connectivity:

```bash id="x4m7q2"
nc -vz <service-host> <port>
```

### Step 6: Check Database

Investigate:

```text id="m5q8x2"
Slow queries
Locks
Connections
CPU
I/O
```

### Step 7: Check External Services

An external API can add significant latency.

### Step 8: Compare Healthy and Slow Requests

Example:

```text id="q7m3x2"
Successful request → 200 ms
Slow request       → 5 seconds
```

Identify which service call differs.

### Important

```text id="x8m2q4"
Slow API
   ≠
Slow first service
```

The delay may occur several services downstream.

### Interview Tip

> "I use metrics and distributed tracing to break total latency into individual service calls and identify the slowest component before making changes."

# Q402. How do you troubleshoot timeout and retry problems between microservices?

## Answer

Timeouts and retries must be analyzed together.

Example:

```text id="m4x8q2"
Service A
   |
   | timeout = 5 sec
   v
Service B
   |
   | retry × 3
   v
Database
```

### Step 1: Identify the Timeout Layer

Possible layers:

```text id="x7m3q5"
Client
API Gateway
Service A
Service B
Database
External API
```

### Step 2: Check Logs

Search for:

```text id="p5m8x2"
timeout
connection timeout
read timeout
upstream timeout
retry
circuit breaker
```

### Step 3: Check Retry Count

Determine:

```text id="m8q3x2"
Maximum retries
Retry interval
Backoff
Which errors trigger retries
```

### Step 4: Check Exponential Backoff

A safer retry strategy often uses:

```text id="x4m7q2"
Retry 1 → short delay
Retry 2 → longer delay
Retry 3 → longer delay
```

Instead of immediately retrying continuously.

### Step 5: Check Connection Pools

Retries can consume additional connections.

### Step 6: Check Backend Health

```bash id="p7m2x5"
nc -vz <backend> <port>
```

For HTTP:

```bash id="q8m3x2"
curl -v http://<backend>:<port>/health
```

### Step 7: Check Resource Usage

```bash id="m5q7x2"
top
```

```bash id="x8m3q4"
free -h
```

### Step 8: Check Network

```bash id="p4m8x2"
ip route get <backend-ip>
```

### Common Failure Pattern

```text id="q7m3x2"
Backend becomes slow
       ↓
Requests timeout
       ↓
Clients retry
       ↓
More traffic
       ↓
Backend becomes slower
       ↓
More timeouts
       ↓
Cascading failure
```

### Important

Do not simply increase timeout and retries.

That can increase the load on an already unhealthy service.

### Interview Tip

> "I identify the timeout layer, inspect retry behavior and backoff, check connection pools and backend health, and make sure retries are not amplifying the original failure."

# Q403. How do you troubleshoot database or backend dependency failures in microservices?

## Answer

A microservice may depend on several backend systems.

```text id="8m3q7x"
Order Service
   |
   +----> PostgreSQL
   |
   +----> Redis
   |
   +----> Kafka
   |
   +----> Payment API
```

### Step 1: Identify the Failed Dependency

Check application logs for:

```text id="m5q8x2"
Database connection failure
Redis timeout
Kafka connection failure
HTTP 503
DNS failure
TLS failure
Authentication failure
```

### Step 2: Check DNS

```bash id="x7m3q4"
getent hosts <dependency-host>
```

### Step 3: Check TCP

```bash id="p4m8x2"
nc -vz <dependency-host> <port>
```

### Step 4: Test Protocol

HTTP:

```bash id="m8q3x2"
curl -v http://<dependency-host>:<port>/health
```

PostgreSQL:

```bash id="x5m7q2"
psql -h <db-host> -p 5432 -U <user> -d <database>
```

### Step 5: Check Dependency Service

On the dependency server:

```bash id="p7m2x4"
systemctl status <service>
```

### Step 6: Check Listener

```bash id="m4x8q2"
ss -lntp
```

### Step 7: Check Resources

```bash id="x8m3q5"
top
```

```bash id="q5m7x2"
free -h
```

```bash id="p4m8x2"
df -h
```

### Step 8: Check Connection Pools

Investigate:

```text id="m7x3q2"
Database pool
HTTP client pool
Message broker connections
```

### Step 9: Check Security

```text id="x5m8q2"
Firewall
Security Group
NetworkPolicy
TLS
Authentication
```

### Step 10: Check Dependency Logs

Correlate the timestamp between:

```text id="p8m3x2"
Microservice logs
        +
Dependency logs
```

### Important

A dependency may be:

```text id="q7m2x5"
Reachable
```

but still:

```text id="m4x8q2"
Unhealthy
Overloaded
Rejecting connections
Slow
```

### Interview Tip

> "I identify the exact dependency, test it from the calling microservice, check DNS, TCP, protocol, authentication, security controls, connection pools, dependency health, and correlate logs between both systems."

# Q404. How do you troubleshoot a microservice after deployment?

## Answer

First correlate the deployment with the incident.

### Step 1: Check Deployment Timeline

```text id="8m3q7x"
Deployment
    ↓
New version starts
    ↓
Errors increase
```

### Step 2: Check Service

```bash id="m5q8x2"
systemctl status <service>
```

### Step 3: Check Logs

```bash id="x7m3q4"
journalctl -u <service> -b
```

Look for:

```text id="p4m8x2"
Startup errors
Configuration errors
Dependency failures
Authentication failures
TLS errors
Database errors
```

### Step 4: Check Health Endpoint

```bash id="m8q3x2"
curl -v http://127.0.0.1:<port>/health
```

### Step 5: Check Configuration

Compare:

```text id="x5m7q2"
Environment variables
Service URLs
Ports
Secrets
Certificates
Database configuration
Feature flags
```

### Step 6: Check Service Discovery

Verify the new instance is registered with:

```text id="p7m2x4"
Correct hostname
Correct IP
Correct port
Healthy status
Correct environment
```

### Step 7: Check API Contract

A deployment may change:

```text id="m4x8q2"
Endpoint
Request format
Response format
Authentication
HTTP method
```

This can break dependent services.

### Step 8: Check Database Compatibility

Verify:

```text id="x8m3q5"
Schema version
Migration
Application compatibility
Database permissions
```

### Step 9: Compare With Previous Version

```text id="q5m7x2"
Old version → Healthy
New version → Failing
```

Compare:

```text id="m7x3q2"
Code
Config
Dependencies
Runtime
Database
```

### Step 10: Rollback if Required

If the deployment is confirmed as the cause:

```text id="p4m8x2"
Rollback
   ↓
Health check
   ↓
Service discovery
   ↓
End-to-end test
   ↓
Monitor
```

Be careful with database schema/data changes.

### Interview Tip

> "After deployment, I compare the old and new service state, check health, logs, configuration, service discovery, API compatibility, dependencies, and database compatibility before deciding on a controlled rollback."

## Answer

```text id="7m3x8q"
                         CLIENT
                           |
                           v
                  API Gateway / LB
                           |
                           v
                       Service A
                      /    |    \
                     /     |     \
                    v      v      v
               Service B Service C Cache
                   |
                   v
                Database
                   |
                   v
              External API
```

## Step 1: Define the Incident

Identify:

```text id="m5q8x2"
Affected application
Affected services
Affected users
Affected region
Endpoint
HTTP status
Exact error
Start time
Intermittent/permanent
```

## Step 2: Check Gateway/Load Balancer

Verify:

```text id="x7m3q4"
Listener
Routing
Target health
Health checks
TLS
Security rules
```

Do not assume the gateway is the root cause.

Find:

```text id="p4m8x2"
Which service is failing first?
```

```bash id="m8q3x2"

```


## Step 5: Check Listening Ports

## Step 7: Check Service-to-Service Connectivity

Verify:


# ⚠️ Production Safety Rules

```text id="x7m3q4"
1. Identify the affected service first
2. Capture the exact error
3. Establish the timeline
4. Identify the first failure
5. Do not restart every service
6. Do not blindly increase retries
7. Do not blindly increase timeouts
8. Do not blindly increase connection pools
9. Check service discovery before changing network configuration
10. Protect production credentials and tokens
11. Do not expose secrets in logs
12. Use targeted packet captures
13. Compare healthy and unhealthy instances
14. Check dependency health
15. Consider cascading-failure effects
16. Protect databases from additional load
17. Use controlled rollback for confirmed bad deployments
18. Remove unhealthy instances only when appropriate
19. Prefer the smallest reversible change
20. Verify service-to-service communication
21. Verify the complete request path
22. Monitor after recovery
23. Document RCA and preventive actions
```

> **Interview mindset:** Don't say **"One microservice is down, so I will restart it."** Say: **"I will identify the affected service and establish whether it is the first failure or a downstream symptom. I will check the service/process, listener, health endpoint, service discovery, DNS, network, authentication, logs, resources, and dependencies. I will also check timeouts, retries, connection pools, and recent changes. Once I identify the failing layer, I will apply the smallest safe fix and verify the complete request flow."**
