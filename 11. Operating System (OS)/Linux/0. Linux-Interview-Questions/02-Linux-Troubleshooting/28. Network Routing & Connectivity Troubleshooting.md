# Q286. How do you check the routing table in Linux?

## Answer

The routing table tells Linux where to send packets.

### Step 1: Display Routes

```bash id="zqj1x2"
ip route
```

Example:

```text id="w3f8k2"
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10
```

This means:

```text id="k6m2q9"
Destination             Gateway          Interface
default                 192.168.1.1     eth0
192.168.1.0/24          directly        eth0
```

### Step 2: Show All Routes

```bash id="q8m3x5"
ip route show
```

### Step 3: Show IPv6 Routes

```bash id="p4x7m1"
ip -6 route
```

### Step 4: Check Interface Addresses

```bash id="m2q8x4"
ip addr
```

This is important because routes and IP addresses must make sense together.

### Step 5: Check Routing to a Specific Destination

```bash id="x7m3q9"
ip route get 8.8.8.8
```

Example:

```text id="v5p2m8"
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10
```

This tells you:

```text id="8q3m6x"
Gateway → 192.168.1.1
Interface → eth0
Source IP → 192.168.1.10
```

### Interview Tip

> "I use `ip route` to inspect the routing table and `ip route get <destination>` to determine exactly which gateway, interface, and source address Linux will use."

# Q287. How do you troubleshoot a missing default gateway?

## Answer

The default route is used when no more specific route exists.

Example:

```text id="q2m7x4"
default via 192.168.1.1 dev eth0
```

### Step 1: Check Routes

```bash id="n8x3m5"
ip route
```

If there is no:

```text id="q6m2p9"
default via ...
```

the server may not know where to send external traffic.

### Step 2: Check IP Address

```bash id="y4m8x2"
ip addr
```

### Step 3: Check Gateway Reachability

```bash id="p7x3m9"
ping -c 4 <gateway-ip>
```

### Step 4: Check NetworkManager

On systems using NetworkManager:

```bash id="m5q8x1"
nmcli connection show
```

Detailed information:

```bash id="r3x7m2"
nmcli device show eth0
```

Look for:

```text id="4q8m2x"
IP4.ADDRESS
IP4.GATEWAY
IP4.ROUTE
```

### Step 5: Check DHCP or Static Configuration

Determine whether the address and gateway are obtained through:

```text id="8m3q7x"
DHCP
Static configuration
Cloud network configuration
```

### Possible Causes

```text id="x5m2q8"
DHCP failure
Incorrect static configuration
Wrong network profile
Gateway missing
NetworkManager issue
Cloud network configuration
```

### Important

Do not manually add a gateway without first understanding the network design.

A server with multiple interfaces may intentionally have:

```text id="m7x3q2"
Multiple routes
Multiple gateways
Policy routing
```

### Interview Tip

> "I first check `ip route` for the default route, then verify the interface IP and gateway configuration with `ip addr` and `nmcli`. I also test gateway reachability before changing the route."

# Q288. How do you determine which route Linux will use for a destination?

## Answer

The best command is:

```bash id="s2m8x5"
ip route get <destination-ip>
```

Example:

```bash id="f7x3m1"
ip route get 10.10.20.50
```

Possible output:

```text id="j5m2q8"
10.10.20.50 via 192.168.1.1 dev eth0 src 192.168.1.10
```

This tells us:

```text id="4x8m2q"
Destination → 10.10.20.50
Gateway     → 192.168.1.1
Interface   → eth0
Source IP   → 192.168.1.10
```

### Why This Is Better Than Only Looking at `ip route`

When a server has many routes:

```text id="3m7x9q"
10.0.0.0/8
10.10.0.0/16
10.10.20.0/24
default
```

it can be difficult to manually determine which one applies.

`ip route get` asks the kernel directly.

### Check Source Address

```bash id="p8m4x2"
ip route get 10.10.20.50
```

Pay attention to:

```text id="w6q2m8"
dev
via
src
```

### Advanced: Policy Routing

Check:

```bash id="v4m7x2"
ip rule
```

Then:

```bash id="x8q3m5"
ip route show table main
```

There may be additional routing tables.

### Troubleshooting Flow

```text id="q5m8x2"
Destination
     |
     v
ip route get
     |
     +--> Interface
     +--> Gateway
     +--> Source IP
     |
     v
Check next network layer
```

### Interview Tip

> "For a specific destination, I prefer `ip route get <destination>` because it shows the route Linux will actually select, including the interface, gateway, and source address."

# Q289. How do you troubleshoot a server that can reach the gateway but not the destination?

## Answer

This is a common production troubleshooting scenario.

```text id="q7m3x8"
Server
  |
  | Works
  v
Gateway
  |
  | Fails
  v
Destination
```

This indicates that the problem may be beyond the local server's first-hop connectivity.

### Step 1: Verify Server IP

```bash id="k4m8x2"
ip addr
```

### Step 2: Verify Route

```bash id="x7q3m5"
ip route get <destination-ip>
```

### Step 3: Test Gateway

```bash id="p5m8x1"
ping -c 4 <gateway-ip>
```

### Step 4: Test Destination

```bash id="n2x7m4"
ping -c 4 <destination-ip>
```

Remember that ICMP may be blocked, so ping failure does not always prove the destination is unavailable.

### Step 5: Test Required TCP Port

For example:

```bash id="q8m3x5"
nc -vz <destination-ip> 443
```

### Step 6: Trace the Path

If available:

```bash id="m4x7q2"
traceroute <destination-ip>
```

or:

```bash id="p8m2x5"
tracepath <destination-ip>
```

### Step 7: Check Firewall

Local firewall:

```bash id="z5m8x2"
sudo firewall-cmd --list-all
```

If applicable:

```bash id="w3q7m1"
sudo nft list ruleset
```

### Step 8: Check Destination Side

The problem could be:

```text id="6x2m8q"
Destination firewall
Destination service
Remote route
Load balancer
Network ACL
Cloud security group
```

### Step 9: Check Packet Capture

```bash id="r7m3x5"
sudo tcpdump -ni eth0 host <destination-ip>
```

You can determine whether:

```text id="8q2m6x"
Packets leave
Packets return
Only SYN leaves
No response returns
```

### Important

```text id="q4m8x2"
Gateway reachable
      ≠
Destination reachable
```

### Interview Tip

> "If the gateway is reachable but the destination is not, I verify the selected route, test the destination port, trace the network path, check local and remote firewall controls, and use packet capture when necessary."

# Q290. How do you troubleshoot asymmetric routing?

## Answer

**Asymmetric routing** occurs when packets travel through different paths in opposite directions.

Example:

```text id="3m8q2x"
Client
   |
   v
Router A
   |
   v
Server

Return:
Server
   |
   v
Router B
   |
   v
Client
```

This can cause problems with:

```text id="x5m7q2"
Stateful firewalls
NAT
Load balancers
Applications
Security devices
```

### Step 1: Check Routing

```bash id="p8m3x7"
ip route
```

### Step 2: Check Route to Client

```bash id="m4q7x2"
ip route get <client-ip>
```

### Step 3: Check Routing Rules

```bash id="y8m2q5"
ip rule
```

### Step 4: Check Multiple Interfaces

```bash id="k3x7m1"
ip addr
```

### Step 5: Check Packet Flow

Use packet capture:

```bash id="q5m8x2"
sudo tcpdump -ni any host <client-ip>
```

You can observe:

```text id="7m3x9q"
Incoming packet
Outgoing response
```

### Step 6: Compare Network Paths

Use:

```bash id="x4q8m2"
traceroute <destination>
```

and from the other side if possible.

### Common Causes

```text id="8m2x5q"
Multiple gateways
Multiple NICs
Policy routing
Incorrect route
Load balancing
Network design
Firewall routing
```

### Important

Asymmetric routing is not automatically wrong.

Some environments intentionally use asymmetric paths.

The problem occurs when a network device or application requires symmetric traffic.

### Interview Tip

> "I identify the source and return paths separately using `ip route get`, `ip rule`, and packet capture. Then I correlate them with firewall, NAT, load balancer, and network architecture."

# Q291. How do you troubleshoot multiple network interfaces and incorrect route selection?

## Answer

Multiple interfaces can cause Linux to select an unexpected interface or source IP.

Example:

```text id="f8m2q5"
        Server
       /      \
    eth0      eth1
     |          |
Network A    Network B
```

### Step 1: List Interfaces

```bash id="x3m7q2"
ip addr
```

### Step 2: Check Routes

```bash id="q8m4x1"
ip route
```

### Step 3: Determine Actual Route

```bash id="m5x2q8"
ip route get <destination-ip>
```

### Step 4: Check Routing Rules

```bash id="p7m3x9"
ip rule
```

### Step 5: Check All Routing Tables

```bash id="w2x8m4"
ip route show table main
```

Additional tables may exist.

### Step 6: Check Source IP

Look at:

```text id="6m4q8x"
src <source-ip>
```

in:

```bash id="3x7m2q"
ip route get <destination-ip>
```

The wrong source IP can cause:

```text id="q5m8x1"
Return path problems
Firewall drops
Application connection failures
Asymmetric routing
```

### Step 7: Check NetworkManager

```bash id="v8m2q4"
nmcli device status
```

```bash id="x6q3m9"
nmcli connection show
```

### Possible Causes

```text id="4m7x2q"
Incorrect default route
Multiple gateways
Incorrect metric
Policy routing
Wrong source IP
NetworkManager configuration
Bond/VLAN configuration
```

### Important

Don't simply delete a route because it looks unusual.

A route may be required for:

```text id="5x8m2q"
Management
Application traffic
Replication
Backup
Storage
```

### Interview Tip

> "With multiple NICs, I check interfaces, routes, routing rules, and the selected source IP using `ip route get`. I also verify whether policy routing or NetworkManager configuration is influencing route selection."

# Q292. How do you troubleshoot packet loss and intermittent connectivity?

## Answer

Intermittent connectivity is more difficult than a complete outage because the problem may occur only under certain conditions.

### Step 1: Test the Gateway

```bash id="x7m3q8"
ping -c 20 <gateway-ip>
```

### Step 2: Test the Destination

```bash id="p4m8x2"
ping -c 20 <destination-ip>
```

### Step 3: Check Interface Errors

```bash id="q5x7m3"
ip -s link show eth0
```

### Step 4: Check NIC Statistics

```bash id="m8q2x4"
ethtool -S eth0
```

### Step 5: Check Route

```bash id="j3m7x1"
ip route get <destination-ip>
```

### Step 6: Trace Path

```bash id="w6x2m8"
tracepath <destination-ip>
```

### Step 7: Check MTU

```bash id="v4m8q2"
ip link show eth0
```

If required, test path MTU using appropriate tools and packet sizes.

### Step 8: Check Kernel Logs

```bash id="x2m7q5"
journalctl -k | grep -Ei "link|reset|error|timeout|network"
```

### Step 9: Capture Traffic

```bash id="p8x3m6"
sudo tcpdump -ni eth0 host <destination-ip>
```

### Step 10: Check Network Infrastructure

Possible sources:

```text id="7m2q8x"
Switch port
Cable
NIC
Firewall
Load balancer
Router
Cloud networking
Congestion
```

### Common Causes

```text id="4x8m2q"
NIC errors
Bad cable
Switch errors
MTU mismatch
Congestion
Routing changes
Firewall state
Application overload
Virtual network issue
```

### Important

Packet loss to a destination does not automatically mean packet loss exists everywhere.

Compare:

```text id="5m8x2q"
Server → Gateway
Server → Destination
```

### Interview Tip

> "For intermittent connectivity, I compare packet loss to the local gateway and destination, inspect NIC counters, routes, MTU, kernel logs, and network infrastructure, and use packet capture to determine where packets are being lost."

# Q293. How do you use traceroute or tracepath for connectivity troubleshooting?

## Answer

`traceroute` and `tracepath` help identify the network path toward a destination.

### traceroute

```bash id="v7m2q8"
traceroute <destination-ip>
```

Check availability:

```bash id="x3m8q2"
command -v traceroute
```

### tracepath

```bash id="m4q7x2"
tracepath <destination-ip>
```

Check:

```bash id="p8x2m5"
command -v tracepath
```

### Example

```text id="q6m3x8"
1  192.168.1.1
2  10.10.0.1
3  10.20.0.1
4  destination
```

This gives an indication of the path.

### What It Can Help Identify

```text id="4m8x2q"
First-hop problem
Routing path
Unexpected router
Path changes
Possible MTU issue
Where responses stop
```

### Important Limitation

A `* * *` hop does not automatically mean that router is broken.

Some routers/firewalls:

```text id="7x2m5q"
Block traceroute responses
Rate-limit responses
Hide themselves
```

### Use Along With

```bash id="p5m8x2"
ip route get <destination-ip>
```

and:

```bash id="w3x7m1"
ping <destination-ip>
```

and, when necessary:

```bash id="q8m2x5"
tcpdump
```

### Interview Tip

> "I use `traceroute` or `tracepath` to understand the path and identify where responses stop, but I don't assume a `*` hop means failure because intermediate devices may intentionally not respond."

# Q294. How do you troubleshoot routing problems involving firewall, NAT, or cloud networking?

## Answer

Routing problems can involve multiple layers.

```text id="4x7m2q"
Linux Server
     |
     v
Local Route
     |
     v
Firewall
     |
     v
NAT
     |
     v
Router
     |
     v
Cloud Network
     |
     v
Destination
```

### Step 1: Check Linux Route

```bash id="m8q3x2"
ip route
```

### Step 2: Check Specific Route

```bash id="p5x7m1"
ip route get <destination-ip>
```

### Step 3: Check Firewall

For firewalld:

```bash id="q2m8x4"
sudo firewall-cmd --list-all
```

For nftables:

```bash id="x7m3q5"
sudo nft list ruleset
```

### Step 4: Check NAT

For nftables environments:

```bash id="v4m8x2"
sudo nft list ruleset
```

Look for relevant NAT rules.

For legacy iptables environments:

```bash id="m3x7q1"
sudo iptables -t nat -L -n -v
```

### Step 5: Check Cloud Network Controls

Depending on the platform, verify:

```text id="8q2m5x"
Route tables
Security groups
Network ACLs
Subnet configuration
Internet/NAT gateway
Load balancer
VPC/VNet configuration
```

### Step 6: Check Return Path

A request may leave successfully but the response may take a wrong path.

```text id="y7m2q4"
Request
Server ─────────→ Destination

Response
Server ←──────X── Destination
```

### Step 7: Use Packet Capture

```bash id="p4x8m2"
sudo tcpdump -ni any host <destination-ip>
```

### Important

A Linux route can be correct while the cloud route table is wrong.

Similarly:

```text id="x5m8q2"
Linux firewall OK
      ≠
Cloud firewall OK
```

### Interview Tip

> "For complex connectivity problems, I troubleshoot from the Linux route outward: route selection, local firewall/NAT, network path, cloud route tables and security controls, and finally the destination and return path."

# Q295. How do you troubleshoot a production server with a network connectivity issue?

## Answer

I use a **layer-by-layer approach** instead of immediately restarting networking.

### Step 1: Define the Failure

Ask:

```text id="3m8q2x"
What destination?
What protocol?
What port?
All users or one user?
All destinations or one destination?
Intermittent or permanent?
When did it start?
```

### Step 2: Check Interface

```bash id="x7m3q5"
ip link
```

### Step 3: Check IP

```bash id="p4m8x2"
ip addr
```

### Step 4: Check Routing

```bash id="q5m2x8"
ip route
```

Specific destination:

```bash id="m8x3q1"
ip route get <destination-ip>
```

### Step 5: Check Gateway

```bash id="v7m2q4"
ping -c 4 <gateway-ip>
```

### Step 6: Check Destination

```bash id="x2m8q5"
ping -c 4 <destination-ip>
```

If ICMP is blocked, test the actual application port:

```bash id="p6m3x8"
nc -vz <destination-ip> <port>
```

### Step 7: Check DNS Separately

If a hostname is involved:

```bash id="m4x7q2"
getent hosts <hostname>
```

If DNS fails, distinguish:

```text id="7m2x5q"
DNS problem
```

from:

```text id="8q4m3x"
Routing problem
```

### Step 8: Check Firewall

```bash id="y5m8x2"
sudo firewall-cmd --list-all
```

or:

```bash id="q3x7m1"
sudo nft list ruleset
```

### Step 9: Check NIC Errors

```bash id="p8m2x4"
ip -s link show eth0
```

```bash id="x6q3m7"
ethtool -S eth0
```

### Step 10: Check Kernel Logs

```bash id="m7x2q5"
journalctl -k | grep -Ei "network|link|reset|timeout|error"
```

### Step 11: Trace the Path

```bash id="q4m8x2"
tracepath <destination-ip>
```

or:

```bash id="x7m3q5"
traceroute <destination-ip>
```

### Step 12: Capture Packets if Necessary

```bash id="p5m8x2"
sudo tcpdump -ni any host <destination-ip>
```

Check:

```text id="8m3q7x"
Request sent?
Response received?
TCP handshake complete?
Retransmissions?
RST?
ICMP errors?
```

### Step 13: Check External Controls

Depending on environment:

```text id="q2m7x5"
Switch
Router
Firewall
Load balancer
NAT
Cloud security group
Network ACL
Cloud route table
```

### Step 14: Identify the Failure Layer

```text id="9x4m7q"
Application
    ↓
Port
    ↓
DNS
    ↓
Firewall
    ↓
Routing
    ↓
Gateway
    ↓
VLAN/Bond
    ↓
NIC
    ↓
Driver
    ↓
Network Infrastructure
    ↓
Destination
```

### Step 15: Apply the Smallest Safe Fix

Possible fixes:

```text id="m8q2x5"
Correct route
Correct firewall rule
Correct VLAN
Restore NIC
Fix DNS
Correct cloud route
Fix security rule
Restore failed network path
```

Do not blindly run:

```bash id="x5m8q3"
systemctl restart NetworkManager
```

on a production server, especially if it is remotely accessed and has no out-of-band recovery path.

### Step 16: Verify End-to-End

After the fix:

```text id="7m3q8x"
Interface
   ↓
IP
   ↓
Route
   ↓
Gateway
   ↓
Destination
   ↓
Port
   ↓
Application
```

### Production Scenario

**Interviewer:**

> "A production application cannot connect to a remote database. What will you do?"

**Strong Answer:**

> "First I would confirm the exact database hostname, IP, port, and scope of the failure. I would check the server's interface and IP with `ip link` and `ip addr`, then use `ip route get <database-ip>` to confirm the selected route and source IP. I would test the gateway and the database port rather than relying only on ping. I would check DNS if a hostname is involved, then review local firewall rules, NIC errors, kernel logs, and the network path. If necessary, I would use targeted `tcpdump` to determine whether TCP SYN packets leave and whether responses return. I would also check network-side or cloud controls such as route tables, security groups, ACLs, firewalls, or load balancers. I would identify the failing layer, apply the smallest safe fix, and verify the database connection and application health afterward."

# 🎤 Routing Interview Golden Rules

```text id="q5m8x2"
Route exists ≠ Route is correct
Default route exists ≠ Destination reachable
Gateway reachable ≠ Destination reachable
Ping fails ≠ Application unavailable
Ping works ≠ Application port works
Interface UP ≠ Network connectivity
Correct route ≠ Correct return path
Linux route correct ≠ Cloud route correct
Traceroute * ≠ Router failure
Multiple NICs ≠ Automatically wrong
Multiple gateways ≠ Automatically wrong
Packet loss ≠ Automatically NIC failure
DNS failure ≠ Routing failure
TCP failure ≠ Automatically Firewall failure
```

### ⚠️ Production Safety Rules

Before changing production routing:

```text id="m2x7q4"
1. Identify exact source and destination
2. Identify protocol and port
3. Check interface state
4. Check IP configuration
5. Check current routes
6. Use `ip route get` before changing routes
7. Check policy routing with `ip rule`
8. Check firewall/NAT
9. Check VLAN/bonding
10. Check network/cloud-side routing
11. Check return path
12. Keep console/out-of-band access available
13. Avoid deleting routes blindly
14. Avoid adding a second default gateway blindly
15. Make the smallest reversible change
16. Verify gateway connectivity
17. Verify destination connectivity
18. Verify application functionality
19. Monitor after the change
20. Document the root cause
```

> **Interview mindset:** Do not say, "The application cannot connect, so I will restart the network." Say, **"I will identify the destination, verify the interface and IP, determine the route Linux will actually select, test the gateway and application port, check firewall/VLAN/network controls, trace the path, use packet capture if required, identify the failing layer, and apply the smallest safe fix."**
