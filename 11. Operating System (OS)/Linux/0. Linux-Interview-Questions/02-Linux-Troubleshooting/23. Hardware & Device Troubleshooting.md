# 23. Hardware & Device Troubleshooting

> Hardware and device troubleshooting in Linux involves identifying problems with **CPU, memory, disks, storage controllers, network interfaces, PCI devices, USB devices, drivers, and hardware errors**. In cloud and virtual environments, some physical hardware details may not be directly visible, so troubleshooting often requires coordination with the virtualization or cloud platform.

# Q236. How do you identify hardware devices on a Linux server?

## Answer

Linux provides several commands for identifying hardware.

### Step 1: General Hardware Information

```bash
sudo lshw
```

For a shorter summary:

```bash
sudo lshw -short
```

Check whether it is installed:

```bash
command -v lshw
```

### Step 2: PCI Devices

```bash
lspci
```

Example:

```text id="x2p7m4"
Ethernet controller
Storage controller
VGA controller
USB controller
```

More details:

```bash
lspci -vv
```

### Step 3: USB Devices

```bash
lsusb
```

### Step 4: Block Devices

```bash
lsblk
```

With filesystem information:

```bash
lsblk -f
```

### Step 5: CPU

```bash
lscpu
```

### Step 6: Memory

```bash
free -h
```

Hardware-level information:

```bash
sudo dmidecode -t memory
```

### Step 7: Kernel Hardware Messages

```bash
dmesg -T
```

or:

```bash
journalctl -k
```

### Useful Hardware Map

```text id="8f3qz1"
Linux Server
    |
    +-- CPU       → lscpu
    +-- Memory    → free / dmidecode
    +-- Disk      → lsblk
    +-- PCI       → lspci
    +-- USB       → lsusb
    +-- Network   → ip / lspci
    +-- Kernel    → dmesg / journalctl -k
```

### Important

Not every command is installed by default.

For example:

```bash
command -v lshw
command -v lspci
command -v lsusb
command -v dmidecode
```

### Interview Tip

> "I use `lscpu` for CPU information, `free` and `dmidecode` for memory, `lsblk` for storage, `lspci` for PCI devices, `lsusb` for USB devices, and `dmesg` or `journalctl -k` for kernel-level hardware messages."

# Q237. How do you check CPU and memory hardware information?

## Answer

### CPU Information

Use:

```bash
lscpu
```

Important fields include:

```text id="6m5p9x"
Architecture
CPU(s)
Socket(s)
Core(s) per socket
Thread(s) per core
Model name
```

### Example

```text id="2z7q4v"
CPU(s):              8
Core(s) per socket:  4
Thread(s) per core:  2
```

This means:

```text id="5n8x1m"
4 physical cores
×
2 threads per core
=
8 logical CPUs
```

### Check Memory

```bash
free -h
```

Example:

```text id="7m3p9q"
               total     used     free     available
Mem:             16Gi      8Gi      1Gi       7Gi
Swap:             4Gi      0Gi      4Gi
```

### Check DIMM Information

On physical servers:

```bash
sudo dmidecode -t memory
```

This may show:

```text id="4q8x2m"
Memory size
Memory type
Speed
Manufacturer
Part number
Slot
```

### Check Kernel Memory Messages

```bash
journalctl -k | grep -Ei "memory|mce|hardware"
```

### Memory Error Detection

Hardware memory errors may appear through:

```text id="9k2v6p"
EDAC
Machine Check Exception (MCE)
Hardware Error
```

Search:

```bash
journalctl -k | grep -Ei "mce|edac|hardware error"
```

### Important

`free -h` shows **OS-visible memory**, not detailed physical DIMM information.

Also, virtual machines may expose virtualized CPU and memory information rather than physical hardware.

### Interview Tip

> "I use `lscpu` to understand the CPU topology and `free -h` for OS-visible memory. On physical systems, `dmidecode -t memory` can provide DIMM-level information, while kernel logs can reveal hardware memory errors."

# Q238. How do you troubleshoot a disk or storage device that is not detected?

## Answer

First determine whether Linux can see the device at all.

### Step 1: Check Block Devices

```bash
lsblk
```

### Step 2: Check Partition Information

```bash
sudo fdisk -l
```

### Step 3: Check SCSI Devices

If applicable:

```bash
lsscsi
```

Check installation:

```bash
command -v lsscsi
```

### Step 4: Check PCI Storage Controller

```bash
lspci | grep -Ei "storage|scsi|raid|sata|nvme"
```

### Step 5: Check Kernel Messages

```bash
dmesg -T | grep -Ei "error|fail|scsi|nvme|ata|disk"
```

or:

```bash
journalctl -k | grep -Ei "error|fail|scsi|nvme|ata|disk"
```

### Step 6: Check Device Nodes

```bash
ls -l /dev/
```

For NVMe devices:

```bash
ls -l /dev/nvme*
```

### Step 7: Check Hardware/Platform

If the device is expected but completely absent:

```text id="7n3p8q"
Physical server
    |
    +-- Cable/backplane
    +-- Storage controller
    +-- RAID
    +-- Drive

Virtual server
    |
    +-- Virtual disk attachment
    +-- Hypervisor/cloud configuration
```

### Possible Causes

```text id="2m7x5v"
Disk not attached
Cable/backplane problem
Storage controller problem
RAID issue
Driver problem
Kernel detection issue
Device failure
Virtual disk configuration
```

### Important

If the disk is not visible to the kernel, filesystem commands alone will not solve the problem.

```text id="6q9x3m"
Disk not detected
      ≠
Filesystem problem
```

### Interview Tip

> "If a disk is not detected, I first check `lsblk`, `fdisk -l`, and `lsscsi`, then inspect the storage controller with `lspci` and kernel logs. I also determine whether the server is physical, virtual, or cloud because the troubleshooting path differs."

# Q239. How do you troubleshoot disk I/O errors or hardware errors?

## Answer

Disk errors should be investigated quickly because they can lead to:

```text id="v4q7m2"
Application failures
Filesystem errors
Read-only filesystems
Data corruption
Performance degradation
Server outages
```

### Step 1: Check Kernel Logs

```bash
dmesg -T | grep -Ei "error|fail|I/O|ata|scsi|nvme"
```

Or:

```bash
journalctl -k | grep -Ei "error|fail|I/O|ata|scsi|nvme"
```

### Step 2: Identify the Device

```bash
lsblk
```

### Step 3: Check I/O Performance

If available:

```bash
iostat -xz 1
```

Look for unusually high:

```text id="x7m2p9"
await
util
queue size
```

### Step 4: Check SMART

For supported physical drives:

```bash
sudo smartctl -a /dev/sda
```

Check installation:

```bash
command -v smartctl
```

### Step 5: Check Filesystem State

```bash
findmnt
```

If the filesystem has become read-only, investigate the underlying I/O errors before attempting repair.

### Step 6: Check for Repeated Errors

Example:

```text id="8p3m6x"
I/O error
   ↓
Retry
   ↓
I/O error
   ↓
Filesystem problem
   ↓
Application failure
```

Repeated hardware errors are more concerning than a single transient message.

### Possible Causes

```text id="q5n8x1"
Failing disk
Storage controller problem
Cable/backplane issue
SAN/storage problem
Virtual storage issue
Driver problem
Filesystem corruption
```

### Important

Do not immediately run:

```bash
fsck
```

on a mounted production filesystem.

First determine:

```text id="4m7p2x"
What device?
What filesystem?
Mounted or unmounted?
What exact error?
Is data at risk?
```

### Interview Tip

> "For disk I/O errors, I check kernel logs, identify the device, review I/O performance, inspect SMART where supported, and investigate the storage path. I don't immediately run filesystem repair because the underlying storage problem must be understood first."

# Q240. How do you troubleshoot a network interface that is not detected or not working?

## Answer

Separate the problem into:

```text id="5x8m2q"
Interface Detection
       |
       v
Link
       |
       v
IP Configuration
       |
       v
Routing
       |
       v
Connectivity
```

### Step 1: List Interfaces

```bash
ip link
```

```bash
ip addr
```

### Step 2: Check Interface State

```bash
ip link show eth0
```

The interface may be:

```text id="3q7m9x"
UP
DOWN
```

### Step 3: Check Link Information

If available:

```bash
ethtool eth0
```

Check installation:

```bash
command -v ethtool
```

Look for:

```text id="9p2x6m"
Link detected
Speed
Duplex
```

### Step 4: Check Network Controller

```bash
lspci | grep -Ei "ethernet|network"
```

### Step 5: Check Driver

```bash
ethtool -i eth0
```

or:

```bash
lspci -k
```

### Step 6: Check IP Address

```bash
ip addr show eth0
```

### Step 7: Check Routing

```bash
ip route
```

### Step 8: Check Kernel Logs

```bash
journalctl -k | grep -Ei "eth0|network|link|firmware|driver"
```

### Possible Causes

```text id="6m4q8v"
Interface disabled
No IP address
Cable/link problem
Driver problem
Firmware problem
NetworkManager configuration
Wrong VLAN
Hardware failure
Cloud/virtual NIC issue
```

### Important

A network interface being `UP` does not guarantee network connectivity.

```text id="p3x7m9"
Interface UP
      ≠
Network reachable
```

### Interview Tip

> "For a network interface problem, I check interface detection with `ip link`, IP configuration with `ip addr`, link state with `ethtool`, driver information with `lspci -k` or `ethtool -i`, routing with `ip route`, and kernel logs."

# Q241. How do you identify and troubleshoot driver-related hardware issues?

## Answer

A hardware device may be detected but not function correctly because of a missing, incompatible, or failed driver.

### Step 1: Identify the Device

```bash
lspci
```

### Step 2: Check Kernel Driver

```bash
lspci -k
```

Look for:

```text id="7v2m8q"
Kernel driver in use
Kernel modules
```

### Step 3: Check Module

```bash
lsmod
```

For a specific module:

```bash
modinfo module_name
```

### Step 4: Check Kernel Logs

```bash
journalctl -k
```

Search for driver/firmware problems:

```bash
journalctl -k | grep -Ei "driver|firmware|module|failed|error"
```

### Step 5: Check Device Status

For network:

```bash
ip link
```

For storage:

```bash
lsblk
```

### Step 6: Check Firmware Messages

Look for:

```text id="8q4x1m"
firmware missing
firmware failed
device initialization failed
```

### Possible Causes

```text id="5m7p2q"
Missing driver
Wrong driver
Incompatible kernel
Missing firmware
Kernel module failure
Hardware failure
Third-party module issue
```

### Important

Do not install a random driver from the internet on a production server.

Use:

```text id="2x8n5v"
Approved package source
Vendor documentation
Supported kernel
Change management
```

### Interview Tip

> "I identify the device with `lspci`, determine the driver in use with `lspci -k`, inspect modules with `lsmod` and `modinfo`, and review kernel logs for driver or firmware errors."

# Q242. How do you troubleshoot PCI or USB devices?

## Answer

### PCI Devices

List PCI devices:

```bash
lspci
```

Detailed information:

```bash
lspci -vv
```

Check driver:

```bash
lspci -k
```

### Search for a Specific Device

```bash
lspci | grep -i ethernet
```

### USB Devices

```bash
lsusb
```

Detailed information:

```bash
lsusb -v
```

### Check USB Kernel Messages

```bash
dmesg -T | grep -i usb
```

or:

```bash
journalctl -k | grep -i usb
```

### Check Device Events

For a newly connected device:

```bash
dmesg -T | tail -n 50
```

You may see:

```text id="2k5m8x"
USB device detected
Driver loaded
Device initialization
```

### Possible Causes

```text id="x7q3m1"
Device not connected
Hardware failure
Driver missing
Firmware problem
USB power issue
PCI resource problem
Kernel compatibility
```

### Important

`lsusb` only shows devices visible to the USB subsystem. It does not prove the device is functioning correctly.

Similarly:

```text id="5n8p2q"
Device detected
      ≠
Device operational
```

### Interview Tip

> "For PCI devices I use `lspci` and `lspci -k`; for USB devices I use `lsusb` and kernel logs. I then verify the appropriate driver, firmware, and device functionality."

# Q243. How do you check hardware health and SMART information?

## Answer

For supported physical storage devices, **SMART** can provide information about drive health.

### Step 1: Check smartctl

```bash
command -v smartctl
```

### Step 2: Check Device

```bash
lsblk
```

### Step 3: Read SMART Information

For a supported SATA/SAS drive:

```bash
sudo smartctl -a /dev/sda
```

### Step 4: Run SMART Health Check

```bash
sudo smartctl -H /dev/sda
```

### Important Attributes

Depending on the drive, you may see:

```text id="4x7m9q"
Reallocated sectors
Pending sectors
Uncorrectable errors
Temperature
Power-on hours
Error logs
```

### NVMe

NVMe devices may require an appropriate device path and smartmontools support.

Example:

```bash
sudo smartctl -a /dev/nvme0
```

The exact command depends on the device and smartmontools version.

### Important Limitations

SMART may not provide useful physical-drive health information when storage is:

```text id="6q2m8x"
Virtualized
SAN-backed
RAID-controlled
Cloud-managed
```

In those environments, the underlying platform may own the physical storage.

### Interview Tip

> "I use `smartctl` to inspect SMART health on supported physical drives, but I don't assume SMART is available or authoritative for SAN, RAID, virtual, or cloud storage."

# Q244. How do you troubleshoot hardware problems on a virtual or cloud server?

## Answer

In a virtual or cloud environment, the guest OS may not have access to the actual physical hardware.

### Example

```text id="0x5m8q"
Physical Disk
     |
     v
Storage Platform
     |
     v
Hypervisor / Cloud
     |
     v
Virtual Disk
     |
     v
Linux VM
```

Therefore, guest-level commands may only show virtual devices.

### Step 1: Check OS-visible Devices

```bash
lsblk
```

```bash
lspci
```

```bash
ip link
```

### Step 2: Check Kernel Logs

```bash
journalctl -k
```

Look for:

```text id="4n7p2x"
I/O errors
NIC resets
Driver failures
Device disconnects
Timeouts
```

### Step 3: Identify Virtualization

A useful command is:

```bash
systemd-detect-virt
```

### Step 4: Check Cloud/Hypervisor Layer

Depending on the environment, check:

```text id="7m2q9x"
Virtual disk attachment
Virtual NIC
Instance status
Storage health
Hypervisor events
Cloud platform alerts
Provider maintenance
```

### Step 5: Compare Guest vs Platform

Example:

```text id="6x4p8m"
Linux sees disk
     +
Cloud platform reports storage issue
     =
Investigate platform/storage layer
```

### Important

You may not be able to replace a physical disk from inside the guest OS.

```text id="1q7m5x"
Physical Hardware
      |
      v
Cloud / Hypervisor
      |
      v
Guest OS
```

The failure may need to be handled at the infrastructure-provider level.

### Interview Tip

> "On a VM or cloud server, I first determine what hardware is actually visible to the guest. I inspect guest-level devices and kernel logs, then correlate them with hypervisor or cloud-platform events because physical hardware may be outside the guest's control."

# Q245. How do you troubleshoot a production server with suspected hardware/device failure?

## Answer

Hardware issues can cause serious production impact, so I start with **service impact and evidence**.

### Step 1: Confirm the Impact

Determine whether the issue affects:

```text id="2n8x5q"
Disk
Network
CPU
Memory
Application
Database
Entire server
```

### Step 2: Check System Health

```bash
uptime
```

```bash
free -h
```

```bash
df -h
```

### Step 3: Check Devices

```bash
lsblk
```

```bash
lspci
```

```bash
ip link
```

### Step 4: Check Kernel Hardware Errors

```bash
journalctl -k
```

Search:

```bash
journalctl -k | grep -Ei "error|fail|hardware|I/O|mce|edac|firmware"
```

### Step 5: Check Storage

```bash
lsblk -f
```

If supported:

```bash
sudo smartctl -a /dev/sda
```

### Step 6: Check Network Hardware

```bash
ip link
```

```bash
ethtool eth0
```

If applicable:

```bash
lspci -k
```

### Step 7: Check Driver/Firmware

```bash
lspci -k
```

```bash
lsmod
```

```bash
journalctl -k | grep -Ei "driver|firmware"
```

### Step 8: Determine Environment

```bash
systemd-detect-virt
```

Then determine whether the system is:

```text id="x7m4q2"
Physical
VM
Cloud
```

### Step 9: Correlate With Platform/Vendor Evidence

For physical servers:

```text id="9p2x6m"
RAID controller
BMC/IPMI
Hardware management console
Vendor logs
Disk status
Memory events
```

For cloud:

```text id="5m8q1x"
Instance events
Storage events
Network events
Provider health
```

### Step 10: Protect the Workload

Depending on the failure:

```text id="r4x7m2"
Failover
Move workload
Drain node
Replace device
Restore from backup
Migrate VM
Provider support
```

Do not wait for complete hardware failure if evidence shows the device is degrading.

### Step 11: Verify

After remediation:

```text id="8q3m6x"
Hardware / Device
       |
       v
Kernel Detection
       |
       v
Driver
       |
       v
OS Resource
       |
       v
Application
       |
       v
User Functionality
```

### Production Scenario

**Interviewer:**

> "A production server is reporting repeated disk I/O errors. What will you do?"

**Strong Answer:**

> "First I would assess the application impact and determine which device is generating the errors. I would check `journalctl -k` or `dmesg` for repeated I/O errors, identify the disk with `lsblk`, review I/O performance, and check SMART if the storage type supports it. I would also determine whether the server is physical, virtual, or cloud because the remediation path differs. If the disk appears to be failing, I would protect the workload through the appropriate failover or migration procedure rather than waiting for complete failure. After remediation, I would verify storage, filesystem, services, and application health and document the root cause."

# 🎤 Hardware Interview Golden Rules

```text id="6x2m9q"
Device detected ≠ device healthy
Interface UP ≠ network working
Disk visible ≠ disk healthy
SMART available ≠ SMART always authoritative
I/O error ≠ automatically filesystem problem
Hardware error ≠ automatically replace hardware
Driver loaded ≠ driver working correctly
VM hardware ≠ physical hardware
Cloud disk ≠ directly accessible physical disk
Kernel error ≠ automatically hardware failure
```

Always investigate:

```text id="q7m3x8"
Device
 +
Kernel Detection
 +
Driver
 +
Firmware
 +
Kernel Logs
 +
Performance
 +
Physical / Virtual Environment
 +
Platform / Vendor Evidence
 +
Application Impact
```

### ⚠️ Production Safety Rules

Before making hardware/device changes:

```text id="3n8q5m"
1. Confirm the exact device
2. Assess production impact
3. Collect kernel and system evidence
4. Determine physical vs VM vs cloud
5. Check driver and firmware
6. Check storage/network health
7. Avoid unnecessary device resets
8. Do not run destructive disk commands blindly
9. Do not run fsck on mounted production filesystems
10. Protect the workload before hardware replacement
11. Follow vendor/cloud-provider procedures
12. Use failover/migration where available
13. Verify the device after remediation
14. Verify application health
15. Document the hardware/root cause
```

> **Interview mindset:** Do not say, "The disk has an I/O error, so I will replace the disk." Say, "I will identify the affected device, review kernel and storage evidence, check I/O behavior and SMART where supported, determine whether the server is physical or virtual, assess production impact, and then use the appropriate failover, replacement, migration, or provider-level remediation."
