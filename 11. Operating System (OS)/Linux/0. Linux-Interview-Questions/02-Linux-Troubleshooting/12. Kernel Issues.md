# 12. Kernel Issues

> The Linux kernel is the core component responsible for managing **CPU, memory, processes, devices, networking, filesystems, and hardware interaction**. Kernel-level problems can cause system instability, boot failures, performance issues, hardware errors, and kernel panics.

# Q116. What is the Linux kernel and what does it do?

## Answer

The **Linux kernel** is the core component of the Linux operating system.

It acts as a bridge between:

```text
Applications
     |
     v
System Libraries
     |
     v
Linux Kernel
     |
     +---- CPU
     +---- Memory
     +---- Disk
     +---- Network
     +---- Hardware
     +---- Devices
```

### Main Responsibilities

The kernel manages:

* CPU scheduling
* Memory management
* Process management
* Device drivers
* Disk and filesystem access
* Networking
* Security
* System calls
* Hardware resources

### Example

When an application wants to read a file:

```text
Application
     |
     v
System Call
     |
     v
Kernel
     |
     v
Filesystem
     |
     v
Disk
```

The application normally does not directly control the hardware. The kernel handles that interaction.

### Check Kernel Version

```bash
uname -r
```

### Interview Tip

> "The Linux kernel is the core of the operating system. It manages CPU, memory, processes, devices, networking, filesystems, and provides the interface between applications and hardware."

# Q117. How do you check the running Linux kernel version?

## Answer

The simplest command is:

```bash
uname -r
```

Example:

```text
5.14.0-427.el9.x86_64
```

For more information:

```bash
uname -a
```

Check kernel information:

```bash
cat /proc/version
```

You can also use:

```bash
hostnamectl
```

on systems using systemd.

### Important

`uname -r` shows the **currently running kernel**.

A newer kernel may already be installed but not currently running.

Check installed kernels on RPM-based systems:

```bash
rpm -q kernel
```

### Example

```text
Installed:
5.14.0-300
5.14.0-400
5.14.0-427

Running:
5.14.0-400
```

This means the newest kernel is installed, but the system is currently running an older kernel.

### Interview Tip

> "I use `uname -r` to identify the running kernel. If I need to compare installed and running kernels, I check the installed kernel packages separately."

# Q118. How do you troubleshoot a kernel panic?

## Answer

A **kernel panic** occurs when the kernel encounters a critical condition from which it cannot safely continue.

Typical symptoms:

```text
System freeze
System reboot
Kernel panic message
Application outage
Console unavailable
```

### Step 1: Check Kernel Messages

After the server comes back:

```bash
journalctl -k
```

For the previous boot:

```bash
journalctl -k -b -1
```

### Step 2: Check for Panic Messages

```bash
journalctl -k | grep -i panic
```

Also:

```bash
dmesg -T | grep -iE "panic|oops|fatal"
```

### Step 3: Identify Recent Changes

Check whether the issue started after:

* Kernel upgrade
* Driver installation
* Kernel module change
* Hardware change
* Storage change
* Security configuration change

### Step 4: Check Previous Kernel

If the panic started after a kernel upgrade, boot the previous known-good kernel from the bootloader.

```text
GRUB
 |
 +-- New Kernel
 |
 +-- Previous Kernel
```

If the previous kernel works normally, the new kernel or a related driver/module becomes a strong suspect.

### Step 5: Check Crash Dump

Production systems can use **kdump** to capture kernel crash information.

Check service:

```bash
systemctl status kdump
```

### Common Causes

* Kernel bug
* Faulty driver
* Kernel module issue
* Hardware failure
* Memory corruption
* Filesystem/storage problems
* Incompatible kernel update

### Important

Do not immediately delete the problematic kernel or logs.

First collect:

```text
Kernel version
Kernel logs
Crash dump
Recent changes
Hardware/driver information
```

### Interview Tip

> "For a kernel panic, I collect kernel logs and crash information, identify recent kernel or driver changes, check the previous known-good kernel, and use kdump when configured. In production, I prioritize evidence collection before making changes."

# Q119. How do you troubleshoot a server that fails to boot after a kernel upgrade?

## Answer

If the server stops booting immediately after a kernel upgrade, I first determine whether the new kernel is responsible.

### Step 1: Check Bootloader

At the GRUB menu, check available kernels.

```text
GRUB
 |
 +-- New Kernel
 |
 +-- Previous Kernel
```

Boot the previous known-good kernel.

### Step 2: Verify System

If the system boots successfully:

```bash
uname -r
```

Then check:

```bash
journalctl -b
```

and:

```bash
journalctl -k -b
```

### Step 3: Check Installed Kernels

On RPM-based systems:

```bash
rpm -q kernel
```

### Step 4: Check Kernel Errors

```bash
dmesg -T | less
```

Look for:

```text
error
failed
timeout
panic
filesystem
driver
module
```

### Step 5: Check Recent Changes

Investigate:

* Kernel package update
* Third-party drivers
* DKMS modules
* Storage drivers
* Network drivers
* Bootloader configuration
* initramfs problems

### Example

```text
Kernel Upgrade
      |
      v
Server fails to boot
      |
      v
Boot previous kernel
      |
      v
System works
      |
      v
Compare kernels
      |
      v
Check logs / drivers / initramfs
      |
      v
Fix or rollback
```

### Important

Do not assume every post-upgrade boot failure is caused by the kernel itself. The problem can also be related to:

```text
initramfs
GRUB
drivers
filesystem
storage
configuration
```

### Interview Tip

> "If a server fails to boot after a kernel upgrade, I boot the previous known-good kernel to restore service, then investigate the new kernel, initramfs, drivers, bootloader configuration, and kernel logs."

# Q120. How do you check Linux kernel logs?

## Answer

The primary command on systemd-based systems is:

```bash
journalctl -k
```

This displays kernel messages.

### Current Boot

```bash
journalctl -k -b
```

### Previous Boot

```bash
journalctl -k -b -1
```

### Follow Kernel Messages

```bash
journalctl -k -f
```

### Search for Errors

```bash
journalctl -k | grep -i error
```

```bash
journalctl -k | grep -iE "fail|error|warning|panic|oom"
```

### Using dmesg

```bash
dmesg
```

Human-readable timestamps:

```bash
dmesg -T
```

Search:

```bash
dmesg -T | grep -i error
```

### Important Difference

```text
journalctl -k
    ↓
Kernel messages stored in systemd journal

dmesg
    ↓
Kernel ring-buffer messages
```

Depending on the system and configuration, `journalctl` can provide useful information from previous boots, while `dmesg` focuses on the kernel ring buffer currently available.

### Interview Tip

> "I normally start with `journalctl -k`, especially when investigating previous boots, and use `dmesg -T` for current kernel and hardware-related messages."

# Q121. How do you troubleshoot high kernel/system CPU usage?

## Answer

High **system CPU (`sy`)** means the CPU is spending significant time executing kernel code rather than user-space application code.

First check:

```bash
top
```

Look at:

```text
us → User CPU
sy → System CPU
id → Idle CPU
wa → I/O Wait
```

### Check Per-CPU Usage

```bash
mpstat -P ALL 1
```

### Check Processes

```bash
ps aux --sort=-%cpu | head -20
```

### Check I/O

```bash
iostat -xz 1
```

### Check Kernel Messages

```bash
journalctl -k --since "30 minutes ago"
```

### Possible Causes

High system CPU can be associated with:

* Heavy network traffic
* High disk I/O
* Large number of system calls
* Excessive context switching
* Driver problems
* Kernel modules
* Packet processing
* Very high process/thread activity

### Example

```text
CPU:
us = 20%
sy = 70%
id = 10%
```

This indicates that a large portion of CPU time is being spent in kernel space.

Do not immediately conclude that the kernel itself is defective.

Investigate:

```text
Processes
   ↓
System calls
   ↓
I/O
   ↓
Network
   ↓
Drivers
   ↓
Kernel modules
```

### Interview Tip

> "For high system CPU, I check `sy` in `top` or `mpstat`, then correlate it with I/O, network traffic, process activity, drivers, and kernel logs."

# Q122. What are kernel parameters and how do you check them?

## Answer

**Kernel parameters** are configuration values that control various Linux kernel behaviors.

They can affect areas such as:

* Networking
* Memory management
* Process behavior
* Security
* Filesystem behavior
* Kernel limits

Many runtime parameters are exposed through:

```text
/proc/sys/
```

### Check a Parameter

Example:

```bash
cat /proc/sys/vm/swappiness
```

Using `sysctl`:

```bash
sysctl vm.swappiness
```

### List Parameters

```bash
sysctl -a
```

### Example

```bash
sysctl net.ipv4.ip_forward
```

Output:

```text
net.ipv4.ip_forward = 0
```

### Temporary Change

For example:

```bash
sysctl -w vm.swappiness=10
```

This changes the runtime value.

### Important

A runtime change may not survive a reboot.

For persistent configuration, use an appropriate configuration file under:

```text
/etc/sysctl.conf
/etc/sysctl.d/
```

### Warning

Do not change kernel parameters blindly in production.

A wrong value can cause:

* Performance degradation
* Network problems
* Memory issues
* Application failures
* Security problems

### Interview Tip

> "Kernel parameters control kernel behavior. I use `sysctl` or `/proc/sys` to inspect them, and I validate the impact before changing production values."

# Q123. What is `sysctl` and how do you make kernel parameter changes persistent?

## Answer

`sysctl` is used to **read and modify kernel parameters at runtime**.

### Check a Parameter

```bash
sysctl vm.swappiness
```

### Set a Runtime Value

```bash
sudo sysctl -w vm.swappiness=10
```

Verify:

```bash
sysctl vm.swappiness
```

### Persistent Configuration

Kernel parameter configuration can be stored in:

```text
/etc/sysctl.conf
/etc/sysctl.d/*.conf
```

Example:

```text
/etc/sysctl.d/99-custom.conf
```

Content:

```text
vm.swappiness = 10
```

Apply configuration:

```bash
sudo sysctl --system
```

Verify:

```bash
sysctl vm.swappiness
```

### Configuration Flow

```text
/etc/sysctl.conf
        +
/etc/sysctl.d/*.conf
        |
        v
   sysctl --system
        |
        v
Kernel Runtime Parameter
```

### Important

Always check whether another configuration file defines the same parameter.

```bash
grep -R "vm.swappiness" /etc/sysctl.conf /etc/sysctl.d/
```

This helps avoid confusion caused by duplicate settings.

### Production Best Practice

Before changing a parameter:

```text
Understand Parameter
       ↓
Record Current Value
       ↓
Understand Application Impact
       ↓
Change in Approved Window
       ↓
Validate
       ↓
Make Persistent if Required
       ↓
Document Change
```

### Interview Tip

> "`sysctl` is used to view and modify kernel parameters. For persistence, I use `/etc/sysctl.conf` or a dedicated file under `/etc/sysctl.d/` and apply it with `sysctl --system`."

# Q124. How do you troubleshoot Linux kernel module issues?

## Answer

A **kernel module** is code that can be loaded into the kernel to provide functionality such as device drivers, filesystem support, or other kernel features.

### Step 1: Check Loaded Modules

```bash
lsmod
```

### Step 2: Search for a Module

```bash
lsmod | grep module_name
```

### Step 3: Get Module Information

```bash
modinfo module_name
```

### Step 4: Load a Module

```bash
sudo modprobe module_name
```

### Step 5: Remove a Module

```bash
sudo modprobe -r module_name
```

Only remove a module when it is safe and no required workload depends on it.

### Step 6: Check Kernel Logs

```bash
journalctl -k
```

or:

```bash
dmesg -T
```

Search for module-related errors:

```bash
journalctl -k | grep -i module
```

### Common Problems

```text
Module not found
Module incompatible with kernel
Driver failure
Missing dependency
Module failed to load
Hardware not detected
```

### Example

Suppose a network interface disappears after a kernel upgrade:

```text
Kernel Upgrade
      ↓
Network Interface Missing
      ↓
Check lsmod
      ↓
Check modinfo
      ↓
Check journalctl -k
      ↓
Check Driver Compatibility
```

### Important

Kernel modules are often kernel-version dependent.

A module that worked with one kernel may not work correctly with another kernel.

### Interview Tip

> "For kernel module issues, I check whether the module is loaded with `lsmod`, inspect it using `modinfo`, use `modprobe` when appropriate, and check kernel logs for loading or driver errors."

# Q125. How do you troubleshoot a production server with a suspected kernel-level issue?

## Answer

For a suspected kernel issue in production, I use a **careful evidence-first approach** because kernel-level changes can affect the entire server.

### Step 1: Confirm the Impact

Identify:

```text
What failed?
When did it start?
How many systems are affected?
Is the issue intermittent or continuous?
```

### Step 2: Check Running Kernel

```bash
uname -r
```

### Step 3: Check Kernel Logs

```bash
journalctl -k --since "1 hour ago"
```

```bash
dmesg -T
```

### Step 4: Check System Health

```bash
uptime
```

```bash
top
```

```bash
free -h
```

```bash
iostat -xz 1
```

### Step 5: Look for Kernel Errors

Search for:

```text
panic
oops
BUG
error
failed
segfault
OOM
I/O errors
driver failures
```

Example:

```bash
journalctl -k | grep -iE "panic|oops|bug|error|failed|oom"
```

### Step 6: Check Recent Changes

Investigate:

* Kernel upgrade
* Driver update
* Kernel module change
* Hardware change
* Storage change
* Network configuration
* Security configuration
* System tuning

### Step 7: Check Kernel Modules

```bash
lsmod
```

```bash
modinfo module_name
```

### Step 8: Check Crash Information

If configured:

```bash
systemctl status kdump
```

Check crash dump locations according to the system's kdump configuration.

### Step 9: Mitigate Carefully

Depending on the evidence and approved procedure:

```text
Rollback recent change
        OR
Boot previous kernel
        OR
Restart affected service
        OR
Move workload to healthy server
        OR
Fail over to standby
```

### Step 10: Verify

After mitigation:

```text
System Health
CPU
Memory
Disk
Network
Application
Kernel Logs
```

should be checked again.

### Step 11: Root Cause Analysis

Document:

```text
Incident
   ↓
Impact
   ↓
Timeline
   ↓
Evidence
   ↓
Root Cause
   ↓
Immediate Fix
   ↓
Permanent Fix
   ↓
Prevention
```

### Production Interview Scenario

**Interviewer:**

> "A production server suddenly rebooted and users experienced an outage. You suspect a kernel problem. What will you do?"

**Strong Answer:**

> "First I will confirm the impact and determine when the reboot occurred. I will check the running kernel with `uname -r` and investigate kernel logs using `journalctl -k`, including the previous boot with `journalctl -k -b -1`. I will look for panic, OOPS, driver, hardware, OOM, and I/O errors and check whether there were any recent kernel, driver, or configuration changes. If kdump is configured, I will collect the crash information. If the issue is related to a recent kernel upgrade, I can use the previous known-good kernel as a recovery option according to the change and incident procedures. After recovery, I will verify system and application health and perform RCA before making permanent changes."

# 🎤 Kernel Interview Golden Rules

```text
Kernel issue ≠ automatically kernel bug
Boot failure ≠ automatically kernel failure
High system CPU ≠ automatically kernel defect
Kernel parameter change ≠ automatically permanent
Module issue ≠ automatically hardware failure
New kernel installed ≠ currently running kernel
```

Always correlate:

```text
Kernel Version
 +
Kernel Logs
 +
Recent Changes
 +
Drivers / Modules
 +
Hardware
 +
CPU / Memory / I/O
 +
Application Behavior
```

### ⚠️ Production Safety Rules

Before changing kernel-related configuration:

```text
1. Collect evidence
2. Record current configuration
3. Understand the expected impact
4. Follow change-management procedure
5. Prefer reversible changes
6. Validate after the change
7. Document the result
```

> **Interview mindset:** Never say, "I will change the kernel parameter and see what happens." Say, "I will collect evidence, identify the suspected kernel component, validate the change, apply it through the approved procedure, and verify the impact."
