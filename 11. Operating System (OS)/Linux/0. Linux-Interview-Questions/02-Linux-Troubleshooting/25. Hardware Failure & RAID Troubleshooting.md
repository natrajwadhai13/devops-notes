# 25. Hardware Failure & RAID Troubleshooting

> Hardware failure and RAID troubleshooting is important for production Linux servers because a failed disk, degraded RAID array, controller problem, or filesystem issue can lead to performance degradation, data loss, or service outage. The troubleshooting approach depends on whether RAID is **software RAID, hardware RAID, or storage provided by SAN/cloud platforms**.

# Q256. How do you identify a failed or failing disk?

## Answer

A disk can fail completely or show early warning signs before complete failure.

### Step 1: Check Block Devices

```bash
lsblk
```

Example:

```text
NAME   SIZE TYPE
sda    1T   disk
sdb    1T   disk
sdc    1T   disk
```

If an expected disk is missing, investigate further.

### Step 2: Check Kernel Logs

```bash
journalctl -k
```

Search for storage errors:

```bash
journalctl -k | grep -Ei "error|fail|I/O|ata|scsi|nvme"
```

You may see:

```text
I/O error
device reset
link reset
read error
write error
timeout
```

### Step 3: Check SMART

For supported physical drives:

```bash
sudo smartctl -a /dev/sdb
```

Health check:

```bash
sudo smartctl -H /dev/sdb
```

Check availability:

```bash
command -v smartctl
```

### Step 4: Check I/O Performance

If available:

```bash
iostat -xz 1
```

Look for abnormal:

```text
await
util
queue
```

### Step 5: Check RAID Status

If the disk belongs to software RAID:

```bash
cat /proc/mdstat
```

### Step 6: Check Hardware RAID

For hardware RAID, Linux may only see the logical RAID volume.

You may need:

```text
RAID controller utility
Vendor management tool
BMC/IPMI
Server management console
```

### Common Warning Signs

```text
Repeated I/O errors
SMART errors
High latency
Disk disappearing
Read/write failures
RAID degradation
Filesystem becoming read-only
Controller errors
```

### Important

A single kernel error does not automatically mean the disk has failed.

Correlate:

```text
Kernel Logs
+
SMART
+
RAID Status
+
I/O Behavior
+
Hardware Controller
```

### Interview Tip

> "I identify the affected disk with `lsblk`, check kernel logs for I/O errors, inspect SMART where supported, check RAID status, and correlate the evidence before declaring a disk failure."

# Q257. What is RAID and what are the common RAID levels?

## Answer

**RAID (Redundant Array of Independent Disks)** combines multiple disks to provide some combination of:

```text
Performance
Redundancy
Availability
Capacity
```

### Common RAID Levels

| RAID    | Minimum Disks | Main Concept           | Fault Tolerance         |
| ------- | ------------: | ---------------------- | ----------------------- |
| RAID 0  |             2 | Striping               | None                    |
| RAID 1  |             2 | Mirroring              | 1 disk                  |
| RAID 5  |             3 | Striping + parity      | 1 disk                  |
| RAID 6  |             4 | Striping + dual parity | 2 disks                 |
| RAID 10 |             4 | Mirroring + striping   | Depends on mirror pairs |

### RAID 0

```text
Disk 1 ── Data A ── Data C
Disk 2 ── Data B ── Data D
```

Advantages:

```text
High performance
Full usable capacity
```

Disadvantage:

```text
No redundancy
```

One disk failure can make the array unavailable.

### RAID 1

```text
Disk 1 ── Data A
Disk 2 ── Data A
```

Data is mirrored.

Advantages:

```text
Simple redundancy
Good availability
```

### RAID 5

```text
Disk 1 ── Data
Disk 2 ── Data
Disk 3 ── Parity
```

Can generally tolerate one disk failure.

### RAID 6

Uses dual parity and can generally tolerate two disk failures.

### RAID 10

Combines:

```text
RAID 1 → Mirroring
RAID 0 → Striping
```

Provides good performance and redundancy.

### Important

RAID is **not a backup**.

```text
RAID
  ↓
Availability / redundancy

Backup
  ↓
Recovery from data loss
```

### Interview Tip

> "RAID provides disk-level redundancy or performance depending on the RAID level. RAID 0 has no redundancy, RAID 1 mirrors data, RAID 5 uses single parity, RAID 6 uses dual parity, and RAID 10 combines mirroring and striping."

# Q258. How do you check software RAID status in Linux?

## Answer

Linux software RAID is commonly managed using **mdadm**.

### Step 1: Check `/proc/mdstat`

```bash
cat /proc/mdstat
```

Example healthy array:

```text
Personalities : [raid1]
md0 : active raid1 sda1[0] sdb1[1]
      1048576 blocks [2/2] [UU]
```

### Understanding `[UU]`

```text
[UU]
```

means both expected RAID members are present.

Example:

```text
[U_]
```

means one member is missing.

### Step 2: Detailed RAID Information

```bash
sudo mdadm --detail /dev/md0
```

You may see:

```text
State : clean
Active Devices : 2
Working Devices : 2
Failed Devices : 0
```

### Step 3: Check RAID Devices

```bash
lsblk
```

### Step 4: Check mdadm

```bash
command -v mdadm
```

### Step 5: Check Kernel Logs

```bash
journalctl -k | grep -Ei "md|raid|I/O|error|fail"
```

### Healthy Example

```text
Array
 |
 +-- Disk 1 → Active
 |
 +-- Disk 2 → Active
 |
 +-- State  → Clean
```

### Degraded Example

```text
Array
 |
 +-- Disk 1 → Active
 |
 +-- Disk 2 → Failed/Missing
 |
 +-- State  → Degraded
```

### Interview Tip

> "For Linux software RAID, I start with `/proc/mdstat`, then use `mdadm --detail /dev/mdX` for detailed status and correlate it with `lsblk` and kernel logs."

# Q259. How do you troubleshoot a degraded software RAID array?

## Answer

A degraded array means the RAID is operating with fewer healthy members than expected.

### Step 1: Check RAID Status

```bash
cat /proc/mdstat
```

Example:

```text
md0 : active raid1 sda1[0]
      [2/1] [U_]
```

This indicates one member is missing.

### Step 2: Get Detailed Information

```bash
sudo mdadm --detail /dev/md0
```

Look for:

```text
State
Active Devices
Working Devices
Failed Devices
Spare Devices
```

### Step 3: Identify the Failed Member

```bash
lsblk
```

Then:

```bash
sudo mdadm --detail /dev/md0
```

### Step 4: Check Kernel Logs

```bash
journalctl -k | grep -Ei "raid|md|I/O|error|fail"
```

### Step 5: Determine Why the Disk Failed

Possible causes:

```text
Disk failure
Cable/backplane issue
Controller problem
Temporary device loss
Power issue
Storage connectivity problem
```

### Step 6: Check the Disk Before Replacement

If the device is still visible:

```bash
sudo smartctl -a /dev/sdb
```

Do not assume that every RAID member failure means the physical disk itself is defective.

### Step 7: Protect the Array

If RAID is degraded:

```text
Healthy Members
      ↓
Reduced Redundancy
      ↓
Higher Risk
      ↓
Second Failure May Cause Data Loss
```

Avoid unnecessary heavy workloads during recovery when possible.

### Step 8: Replace/Recover According to the RAID Procedure

For software RAID, the failed member may be removed and a replacement added.

Exact commands depend on:

```text
RAID level
Partition layout
Device naming
Boot configuration
Server design
```

### Important

Do not blindly run:

```bash
mdadm --remove
mdadm --add
```

until the correct member and replacement device have been identified.

### Interview Tip

> "For a degraded RAID array, I first confirm the degraded state with `/proc/mdstat` and `mdadm --detail`, identify the affected member, determine why it failed, and then follow the approved disk replacement and rebuild procedure."

# Q260. How do you replace a failed disk in software RAID?

## Answer

The exact procedure depends on the RAID layout, but the general workflow is:

```text
Identify Failed Disk
       ↓
Confirm Failure
       ↓
Remove Failed Member
       ↓
Replace Physical Disk
       ↓
Partition Replacement
       ↓
Add Replacement to RAID
       ↓
Monitor Rebuild
       ↓
Verify RAID
```

### Step 1: Check RAID

```bash
cat /proc/mdstat
```

```bash
sudo mdadm --detail /dev/md0
```

### Step 2: Identify Failed Member

Example:

```text
/dev/sdb1 → faulty
```

### Step 3: Remove Failed Member

The exact command depends on the situation.

Conceptually:

```bash
sudo mdadm --manage /dev/md0 --fail /dev/sdb1
sudo mdadm --manage /dev/md0 --remove /dev/sdb1
```

Do not run these commands until the correct member is confirmed.

### Step 4: Replace the Disk

On a physical server:

```text
Failed Disk
    ↓
Approved Replacement
    ↓
Physical Installation
```

Hot-swapping is possible only if the hardware/server/storage design supports it.

### Step 5: Partition the Replacement

The new disk normally needs an appropriate partition layout matching the RAID design.

Check:

```bash
lsblk
```

Compare with the existing disk.

### Step 6: Add the New RAID Member

Example:

```bash
sudo mdadm --manage /dev/md0 --add /dev/sdb1
```

### Step 7: Monitor Rebuild

```bash
cat /proc/mdstat
```

You may see:

```text
recovery = 25%
```

### Step 8: Verify

```bash
sudo mdadm --detail /dev/md0
```

Expected:

```text
State : clean
Failed Devices : 0
```

### Step 9: Check Kernel Logs

```bash
journalctl -k | grep -Ei "md|raid|recovery|error"
```

### Important Production Considerations

If the RAID contains the boot disk, additional steps may be required to ensure the system can boot from the replacement disk.

Do not assume:

```text
RAID rebuilt
=
Boot configuration fixed
```

### Interview Tip

> "I first identify and confirm the failed RAID member, replace the disk according to the hardware procedure, recreate the required partition layout, add the replacement member to the RAID, monitor the rebuild, and verify the array. For boot disks, I also verify bootloader redundancy."

# Q261. How do you troubleshoot hardware RAID problems?

## Answer

Hardware RAID is controlled primarily by a RAID controller.

Linux may see:

```text
/dev/sda
```

without seeing each physical disk directly.

### Architecture

```text
Physical Disks
   |  |  |
   v  v  v
RAID Controller
       |
       v
Logical Volume
       |
       v
Linux
```

### Step 1: Check Linux Storage

```bash
lsblk
```

### Step 2: Check PCI RAID Controller

```bash
lspci | grep -Ei "raid|storage|scsi"
```

### Step 3: Check Kernel Logs

```bash
journalctl -k | grep -Ei "raid|scsi|sas|error|fail"
```

### Step 4: Use Controller Management Tools

Depending on the vendor/controller, use the appropriate supported management utility.

It may provide:

```text
Controller status
Physical disk status
Logical volume status
Battery/cache status
Rebuild status
Failed disk
Predictive failure
```

### Step 5: Check Server Management Interface

Physical servers may provide:

```text
BMC
IPMI
Hardware management console
Vendor management software
```

### Step 6: Identify the Layer

```text
Linux filesystem
      ↓
Linux logical device
      ↓
RAID controller
      ↓
Physical disks
```

A problem at one layer may not be visible at another.

### Important

Do not assume `lsblk` showing a healthy logical disk means every physical RAID member is healthy.

### Interview Tip

> "For hardware RAID, I check the RAID controller and its management utility in addition to Linux commands. Linux may only see the logical RAID volume, so physical disk health must often be checked through the controller or server management interface."

# Q262. How do you troubleshoot RAID rebuild problems?

## Answer

A RAID rebuild restores redundancy after a member has been replaced or recovered.

### Step 1: Check Rebuild Status

Software RAID:

```bash
cat /proc/mdstat
```

Hardware RAID:

```text
RAID controller management utility
```

### Step 2: Check Kernel Logs

```bash
journalctl -k | grep -Ei "raid|recovery|resync|I/O|error"
```

### Step 3: Check Failed Devices

```bash
sudo mdadm --detail /dev/md0
```

Look for:

```text
Failed Devices
Active Devices
Spare Devices
State
```

### Step 4: Check Replacement Disk

```bash
lsblk
```

For supported physical drives:

```bash
sudo smartctl -a /dev/sdb
```

### Step 5: Look for I/O Errors

```bash
journalctl -k | grep -Ei "I/O error|read error|write error|timeout"
```

### Step 6: Understand Why Rebuild Is Slow

Possible causes:

```text
Large array
Heavy application I/O
Storage performance limits
Controller configuration
Rebuild throttling
Another disk problem
```

### Step 7: Check for Second Disk Failure

This is critical.

```text
Rebuild
   |
   +-- Disk A
   +-- Disk B
   +-- Disk C
        |
        +-- Another failure?
```

If another disk starts failing during rebuild, the situation becomes much more serious depending on the RAID level.

### Step 8: Do Not Kill the Rebuild Blindly

A rebuild may take hours or longer depending on array size and workload.

### Important

A slow rebuild is not automatically a failed rebuild.

Distinguish:

```text
Slow
vs
Stopped
vs
Repeatedly failing
```

### Interview Tip

> "For a slow or failed RAID rebuild, I check rebuild progress, RAID state, I/O errors, replacement-disk health, workload, and controller status. I also watch for additional disk failures because the array has reduced redundancy during rebuild."

# Q263. How do you troubleshoot a RAID array that is not detected after reboot?

## Answer

First determine whether the problem is:

```text
Hardware
RAID controller
Software RAID assembly
Storage device
Initramfs
Configuration
Boot process
```

### Step 1: Check Devices

```bash
lsblk
```

### Step 2: Check Software RAID

```bash
cat /proc/mdstat
```

### Step 3: Check mdadm Details

If the array device exists:

```bash
sudo mdadm --detail /dev/md0
```

### Step 4: Scan for RAID Metadata

A common diagnostic command is:

```bash
sudo mdadm --examine --scan
```

### Step 5: Examine Individual Members

For known RAID member devices:

```bash
sudo mdadm --examine /dev/sdb1
```

Use the correct device identified from the system's actual layout.

### Step 6: Check Kernel Logs

```bash
journalctl -k -b
```

Search:

```bash
journalctl -k -b | grep -Ei "md|raid|disk|scsi|nvme|error"
```

### Step 7: Check Initramfs

If the RAID is needed during boot:

```bash
ls -lh /boot/initramfs*
```

On systems using `dracut`, initramfs contents and configuration may need to be investigated.

### Step 8: Check Configuration

Depending on the distribution and setup:

```text
/etc/mdadm.conf
/etc/mdadm/mdadm.conf
```

The exact file location is distribution-dependent.

### Step 9: Check Hardware RAID

If hardware RAID is used:

```text
RAID Controller
      ↓
Controller BIOS / Management Utility
      ↓
Physical Disks
      ↓
Logical Volume
```

Check the controller before assuming Linux is the problem.

### Important

Do not blindly recreate an array.

```text
Array not detected
       ≠
Create a new RAID
```

Recreating or initializing an existing array incorrectly can cause data loss.

### Interview Tip

> "After a reboot, I first determine whether the system uses software or hardware RAID. For software RAID I check `lsblk`, `/proc/mdstat`, `mdadm --examine`, configuration, initramfs, and kernel logs. For hardware RAID I also inspect the RAID controller."

# Q264. What is the difference between RAID and backup?

## Answer

RAID and backup solve different problems.

### RAID

RAID primarily provides:

```text
Disk redundancy
Availability
Performance
Fault tolerance
```

Example:

```text
RAID 1

Disk 1 → Data A
Disk 2 → Data A
```

If one disk fails, the other may continue serving the data.

### Backup

Backup provides a separate copy that can be used for recovery.

Example:

```text
Production Data
      |
      +----> Backup Storage
```

### RAID Does Not Protect Against

```text
Accidental deletion
Application corruption
Ransomware
Wrong command
Database corruption
Bad deployment
Logical data corruption
```

Example:

```text
rm -rf important-data
        |
        v
RAID mirrors the deletion
```

The data can be deleted from all mirrored members.

### Simple Comparison

| RAID                                 | Backup                               |
| ------------------------------------ | ------------------------------------ |
| Protects mainly against disk failure | Protects against data loss scenarios |
| Improves availability                | Enables recovery                     |
| Usually local                        | Should preferably be separate        |
| Can improve performance              | Usually focused on recoverability    |
| Not a backup                         | Recovery mechanism                   |

### Best Practice

Production environments commonly use both:

```text
Production
    |
    +--> RAID / Storage Redundancy
    |
    +--> Backup
    |
    +--> Offsite / Separate Recovery Copy
```

### Interview Tip

> "RAID provides redundancy and availability against certain disk failures, while backup provides recovery from deletion, corruption, ransomware, and other logical or operational failures. RAID is not a replacement for backup."

# Q265. How do you troubleshoot a production server with a suspected disk or RAID failure?

## Answer

I follow an **evidence-first and data-protection approach**.

### Step 1: Assess Production Impact

Determine whether the problem affects:

```text
Single disk
RAID array
Filesystem
Database
Application
Entire server
```

### Step 2: Identify Storage Layout

```bash
lsblk
```

```bash
findmnt
```

Determine whether the environment uses:

```text
Software RAID
Hardware RAID
LVM
SAN
Cloud storage
Local disks
```

### Step 3: Check Kernel Errors

```bash
journalctl -k | grep -Ei "error|fail|I/O|disk|scsi|nvme|raid"
```

### Step 4: Check Software RAID

If applicable:

```bash
cat /proc/mdstat
```

```bash
sudo mdadm --detail /dev/md0
```

### Step 5: Check Physical Disk Health

If supported:

```bash
sudo smartctl -a /dev/sdX
```

### Step 6: Check Hardware RAID

If applicable:

```text
RAID controller status
Physical disk status
Logical volume status
Rebuild status
Controller/cache/battery status
```

### Step 7: Check I/O Performance

If available:

```bash
iostat -xz 1
```

### Step 8: Determine Failure Type

```text
Disk failure
     |
     +-- Physical disk
     |
     +-- Controller
     |
     +-- Cable/backplane
     |
     +-- SAN/storage platform
     |
     +-- Cloud storage
```

### Step 9: Protect the Workload

Depending on the architecture:

```text
Failover
Backup
Snapshot
Migration
Application drain
Replace failed disk
Provider escalation
```

Do not immediately reboot or power-cycle a server unless the recovery procedure requires it.

### Step 10: Replace/Rebuild Safely

For software RAID:

```text
Identify failed member
       ↓
Replace disk
       ↓
Partition replacement
       ↓
Add member
       ↓
Monitor rebuild
```

For hardware RAID:

```text
Identify failed physical disk
       ↓
Use controller/vendor procedure
       ↓
Replace disk
       ↓
Monitor rebuild
```

### Step 11: Verify

Check:

```bash
cat /proc/mdstat
```

```bash
lsblk
```

```bash
findmnt
```

```bash
df -h
```

Then verify:

```text
RAID healthy
Filesystem healthy
Services running
Application healthy
Monitoring normal
Backup healthy
```

### Production Scenario

**Interviewer:**

> "A production server has a RAID-1 array in degraded state. What will you do?"

**Strong Answer:**

> "First I would confirm the production impact and identify the RAID implementation. For software RAID, I would check `/proc/mdstat` and `mdadm --detail` to identify the failed member. I would correlate this with `lsblk` and kernel logs and check the disk's health where SMART is supported. I would avoid immediately removing or replacing a disk until I confirm the correct member. After following the approved replacement procedure, I would add the replacement disk and monitor the rebuild. During the rebuild I would watch for I/O errors or another disk failure because redundancy is reduced. Finally, I would verify the RAID state, filesystem, services, application, and backups."

# 🎤 RAID Interview Golden Rules

```text
RAID ≠ Backup
RAID 0 ≠ Redundancy
RAID 1 ≠ Backup
RAID degraded ≠ RAID failed
Disk missing ≠ Disk definitely dead
I/O error ≠ Automatically disk failure
SMART error ≠ Only evidence required
RAID rebuild ≠ Instant recovery
Slow rebuild ≠ Failed rebuild
Linux-visible RAID ≠ Physical RAID layout
Hardware RAID ≠ Software RAID
Logical disk healthy ≠ Every physical disk healthy
```

### ⚠️ Production Safety Rules

Before touching disks or RAID:

```text
1. Confirm the exact disk/RAID array
2. Understand the RAID level
3. Identify software vs hardware RAID
4. Confirm production impact
5. Check backups/recovery options
6. Collect kernel and RAID evidence
7. Confirm the failed member
8. Do not remove the wrong disk
9. Do not recreate an existing RAID blindly
10. Do not initialize a disk containing required data
11. Follow vendor/controller procedures for hardware RAID
12. Use approved replacement hardware
13. Monitor rebuild progress
14. Watch for additional disk failures
15. Verify filesystem after recovery
16. Verify application health
17. Confirm backups are working
18. Document the incident and root cause
```

> **Interview mindset:** Never say, "RAID is degraded, so I will replace `/dev/sdb`." Say, **"I will identify the RAID type and exact failed member, correlate RAID status with kernel and disk-health evidence, confirm the correct physical device, protect the workload, then follow the approved replacement and rebuild procedure and verify the array and application afterward."**
