# Q146. What is a firewall and why is it used in Linux?

## Answer

A **firewall** controls network traffic based on defined security rules.

It can control:

```text
Source IP
Destination IP
Source Port
Destination Port
Protocol
Interface
Connection State
```

### Example

Suppose an application listens on:

```text
TCP 8080
```

The firewall can allow:

```text
10.10.10.0/24 → Server:8080
```

while blocking:

```text
Internet → Server:8080
```

### Basic Flow

```text
Client
   |
   v
Network
   |
   v
Firewall
   |
   +---- Allow ----> Application
   |
   +---- Deny -----> Blocked
```

### Common Linux Firewall Technologies

Depending on the distribution and configuration, you may encounter:

```text
firewalld
nftables
iptables
```

On many modern enterprise Linux systems, `firewalld` provides a management layer for firewall configuration, while the underlying packet filtering may use `nftables`.

### Why Firewall Is Important

Firewalls help:

* Restrict unauthorized access
* Reduce attack surface
* Control application ports
* Restrict source networks
* Protect internal services
* Enforce network security policies

### Important

A firewall is only one part of network security.

```text
Firewall
   +
Application Security
   +
Authentication
   +
Network Segmentation
   +
Host Security
```

### Interview Tip

> "A Linux firewall controls network traffic based on rules such as source, destination, port, protocol, and interface. I use it to restrict unnecessary network access and reduce the server's attack surface."

# Q147. How do you check whether the Linux firewall is running?

## Answer

On systems using `firewalld`, check:

```bash
systemctl status firewalld
```

Check whether it is active:

```bash
systemctl is-active firewalld
```

Check whether it starts automatically:

```bash
systemctl is-enabled firewalld
```

### Check Firewall State

```bash
firewall-cmd --state
```

Expected output:

```text
running
```

### Check Active Zones

```bash
firewall-cmd --get-active-zones
```

### Check Default Zone

```bash
firewall-cmd --get-default-zone
```

### Example

```text
public
  interfaces: eth0
```

This means the `eth0` interface is associated with the `public` zone.

### Important

Do not conclude:

```text
firewalld stopped = no firewall
```

The system may still have rules managed through:

```text
nftables
iptables
```

or another security layer.

### Check nftables

```bash
nft list ruleset
```

### Check iptables

```bash
iptables -L -n -v
```

### Interview Tip

> "I first identify which firewall framework is being used. For firewalld I check `systemctl status firewalld` and `firewall-cmd --state`; if necessary I also inspect nftables or iptables rules."

# Q148. How do you check open ports and firewall rules?

## Answer

First check which applications are actually listening.

```bash
ss -lntup
```

Example:

```text
LISTEN 0 128 0.0.0.0:8080
```

This means an application is listening on TCP port `8080`.

### Check firewalld Rules

List active zones:

```bash
firewall-cmd --get-active-zones
```

List allowed ports:

```bash
firewall-cmd --list-ports
```

List allowed services:

```bash
firewall-cmd --list-services
```

For a specific zone:

```bash
firewall-cmd --zone=public --list-all
```

### Check nftables

```bash
nft list ruleset
```

### Check iptables

```bash
iptables -L -n -v
```

### Important Difference

An application being **listening** does not mean it is **reachable remotely**.

```text
Application
     |
     v
Listening on Port 8080
     |
     v
Firewall Rule
     |
     v
Network Path
     |
     v
Remote Client
```

Every layer needs to allow the connection.

### Example

```text
ss → Port 8080 listening
firewall → Port 8080 blocked
```

The application is healthy, but remote clients cannot connect.

### Interview Tip

> "I first verify whether the application is listening with `ss`, then inspect firewall rules, zones, and the network path. Listening and reachable are two different things."

# Q149. How do you troubleshoot a port that is blocked by the firewall?

## Answer

Suppose users cannot connect to:

```text
TCP 8080
```

### Step 1: Check Whether the Application Is Listening

```bash
ss -lntp | grep :8080
```

If nothing is listening:

```text
Application problem
```

Do not change the firewall yet.

### Step 2: Check Firewall Rules

For firewalld:

```bash
firewall-cmd --get-active-zones
```

```bash
firewall-cmd --list-ports
```

```bash
firewall-cmd --list-services
```

### Step 3: Check the Specific Zone

```bash
firewall-cmd --zone=public --list-all
```

### Step 4: Check From the Client

Test connectivity:

```bash
nc -vz SERVER_IP 8080
```

or:

```bash
curl -v http://SERVER_IP:8080
```

depending on the application protocol.

### Step 5: Check Network Path

Verify:

```text
Client
   |
   v
Routing
   |
   v
Firewall
   |
   v
Server Firewall
   |
   v
Application
```

There may be another firewall before the Linux server.

### Common Causes

* Application not listening
* Wrong port
* Wrong firewall zone
* Missing firewall rule
* Incorrect source network
* Network ACL
* Cloud security group
* External firewall
* Routing problem
* SELinux policy issue

### Important

Do not simply run:

```bash
firewall-cmd --add-port=8080/tcp
```

without understanding whether the port should actually be exposed.

### Interview Tip

> "I first verify that the application is listening, then check the firewall zone and rules, test from the client, and verify the complete network path before opening the port."

# Q150. What are firewalld zones and how do you troubleshoot zone-related issues?

## Answer

A **firewalld zone** represents a level of trust and contains firewall rules that apply to associated interfaces or sources.

Common zones include:

```text
public
internal
external
trusted
dmz
block
drop
```

### Check Available Zones

```bash
firewall-cmd --get-zones
```

### Check Active Zones

```bash
firewall-cmd --get-active-zones
```

Example:

```text
public
  interfaces: eth0
```

This means `eth0` is currently associated with the `public` zone.

### Check Default Zone

```bash
firewall-cmd --get-default-zone
```

### Check a Zone

```bash
firewall-cmd --zone=public --list-all
```

### Troubleshooting Scenario

Suppose you add a port to:

```text
internal
```

but the server interface is actually attached to:

```text
public
```

The expected traffic may still be blocked.

### Troubleshooting Flow

```text
Connection Problem
       |
       v
Check Interface
       |
       v
Check Active Zone
       |
       v
Check Zone Rules
       |
       v
Check Port / Service
       |
       v
Test Connectivity
```

### Check Interface

```bash
ip addr
```

Then:

```bash
firewall-cmd --get-active-zones
```

### Important

Always verify the rule in the **zone actually handling the traffic**.

### Interview Tip

> "A common firewalld mistake is adding a rule to the wrong zone. I check the active interface-to-zone mapping first and then inspect the rules for that specific zone."

<a id="q151"></a>

# Q151. How do you allow or remove a port using firewalld?

## Answer

Suppose the application requires:

```text
TCP 8080
```

### Check Current Rules

```bash
firewall-cmd --list-ports
```

### Add a Port Temporarily

```bash
sudo firewall-cmd --add-port=8080/tcp
```

Verify:

```bash
firewall-cmd --list-ports
```

### Add a Port Permanently

```bash
sudo firewall-cmd --permanent --add-port=8080/tcp
```

Then reload:

```bash
sudo firewall-cmd --reload
```

Verify:

```bash
firewall-cmd --list-ports
```

### Remove a Port

Runtime:

```bash
sudo firewall-cmd --remove-port=8080/tcp
```

Permanent:

```bash
sudo firewall-cmd --permanent --remove-port=8080/tcp
```

Then:

```bash
sudo firewall-cmd --reload
```

### Zone-Specific Rule

```bash
sudo firewall-cmd --zone=public --permanent --add-port=8080/tcp
```

Then:

```bash
sudo firewall-cmd --reload
```

### Service-Based Rule

Instead of opening a raw port, firewalld can allow a predefined service:

```bash
sudo firewall-cmd --permanent --add-service=http
```

Then:

```bash
sudo firewall-cmd --reload
```

### Important

Prefer the narrowest rule required.

For example:

```text
❌ Open unnecessary ports
❌ Use overly broad source ranges
❌ Allow everything
```

Prefer:

```text
✅ Required port only
✅ Required protocol only
✅ Required source only
```

### Runtime vs Permanent

```text
Runtime
   |
   +-- Current firewall state
   |
   +-- May disappear after restart/reboot

Permanent
   |
   +-- Saved configuration
   |
   +-- Applied after reload/restart
```

### Interview Tip

> "I first confirm that the port needs to be exposed. Then I add the minimum required rule to the correct zone, validate it, and make it permanent only when required."

# Q152. How do you troubleshoot a service that is reachable locally but not remotely?

## Answer

This is a common troubleshooting scenario.

Example:

```bash
curl http://localhost:8080
```

works on the server, but:

```bash
curl http://SERVER_IP:8080
```

fails from another machine.

### Step 1: Check Listening Address

```bash
ss -lntp | grep :8080
```

Example:

```text
127.0.0.1:8080
```

This means the application is listening only on localhost.

Remote clients cannot connect directly.

The application may need to listen on an appropriate server interface/address.

### Example

```text
127.0.0.1:8080
      |
      X
Remote Client
```

versus:

```text
0.0.0.0:8080
      |
      v
Remote Client
```

### Step 2: Check Firewall

```bash
firewall-cmd --get-active-zones
```

```bash
firewall-cmd --zone=public --list-all
```

### Step 3: Test From Remote Client

```bash
nc -vz SERVER_IP 8080
```

### Step 4: Check Routing

```bash
ip route
```

### Step 5: Check Network Interface

```bash
ip addr
```

### Step 6: Check Other Security Layers

Depending on the environment:

```text
Linux Firewall
Cloud Security Group
Network ACL
Load Balancer
External Firewall
SELinux
```

### Troubleshooting Model

```text
Local Works
    |
    v
Check Listening Address
    |
    +-- localhost only → Application configuration
    |
    v
Check Linux Firewall
    |
    v
Check Cloud / Network Firewall
    |
    v
Check Routing
    |
    v
Remote Test
```

### Interview Tip

> "If a service works locally but not remotely, I first check whether it is listening only on localhost, then verify the Linux firewall, network path, cloud security controls, routing, and other security layers."

# Q153. How do you troubleshoot firewall issues with iptables or nftables?

## Answer

First identify which firewall framework is actually being used.

### Check nftables

```bash
nft list ruleset
```

### Check iptables

```bash
iptables -L -n -v
```

For NAT rules:

```bash
iptables -t nat -L -n -v
```

### Check Rule Counters

With iptables:

```bash
iptables -L -n -v
```

The packet and byte counters can help determine whether traffic is matching a rule.

### Check nftables Rules

```bash
nft list ruleset
```

Look for:

```text
accept
drop
reject
```

and relevant:

```text
source IP
destination IP
port
protocol
interface
```

### Important

Do not assume:

```text
firewalld
```

and:

```text
iptables
```

are independent firewalls that should both be manually configured.

The actual packet-filtering framework and management layer depend on the operating system and configuration.

### Troubleshooting Flow

```text
Connectivity Problem
       |
       v
Identify Firewall Framework
       |
       +---- firewalld
       |
       +---- nftables
       |
       +---- iptables
       |
       v
Inspect Rules
       |
       v
Check Rule Match
       |
       v
Check Counters
       |
       v
Test Traffic
```

### Important Production Rule

Avoid blindly flushing rules:

```bash
iptables -F
```

or replacing an entire ruleset without understanding the impact.

You can accidentally:

* Expose services
* Break network access
* Disconnect remote administration
* Break application traffic

### Interview Tip

> "For iptables or nftables issues, I first identify the active firewall framework, inspect the relevant rules and counters, trace the expected traffic path, and avoid destructive commands such as blindly flushing production rules."

# Q154. How do you troubleshoot firewall rules without breaking production traffic?

## Answer

Firewall changes can immediately affect production connectivity, so I use a controlled approach.

### Step 1: Understand the Requirement

Determine:

```text
Source
Destination
Protocol
Port
Direction
Expected Traffic
```

Example:

```text
Application Server
      |
      v
Database Server
TCP 5432
```

### Step 2: Check Existing Rules

For firewalld:

```bash
firewall-cmd --zone=public --list-all
```

For nftables:

```bash
nft list ruleset
```

For iptables:

```bash
iptables -L -n -v
```

### Step 3: Confirm Application State

```bash
ss -lntup
```

Make sure the expected application is actually listening.

### Step 4: Test Before Changing

From the client:

```bash
nc -vz SERVER_IP PORT
```

or use an application-specific test.

### Step 5: Make the Smallest Change

Example:

```text
Required:
10.10.10.0/24 → TCP 8080

Avoid:
0.0.0.0/0 → TCP 8080
```

when the broader access is not required.

### Step 6: Validate Immediately

Check:

```text
Application
Connectivity
Logs
Firewall Rules
```

### Step 7: Monitor

Check whether existing traffic remains healthy.

### Step 8: Have a Rollback Plan

Before a production change, know how to remove the exact rule that was added or modified.

### Production Safety Model

```text
Understand Requirement
        ↓
Check Existing Rules
        ↓
Confirm Application
        ↓
Test Connectivity
        ↓
Smallest Change
        ↓
Validate
        ↓
Monitor
        ↓
Rollback if Required
        ↓
Document
```

### Important

When connected remotely over SSH, firewall changes require extra care.

A poorly designed rule can block:

```text
SSH
Management Access
Monitoring
Application Traffic
```

### Interview Tip

> "I never make broad firewall changes just to test connectivity. I identify the exact source, destination, protocol, and port, make the smallest controlled change, validate traffic, and keep a rollback plan."

# Q155. How do you troubleshoot a production connectivity issue end-to-end when a firewall is suspected?

## Answer

I use a **layer-by-layer troubleshooting approach**.

### Step 1: Confirm the Problem

Determine:

```text
Who cannot connect?
From where?
To which server?
Which port?
Which protocol?
When did it start?
```

### Step 2: Check the Destination Application

```bash
ss -lntup
```

Example:

```text
LISTEN 0 128 0.0.0.0:8080
```

If nothing is listening:

```text
Application/service problem
```

not necessarily a firewall problem.

### Step 3: Check Local Firewall

For firewalld:

```bash
firewall-cmd --get-active-zones
```

```bash
firewall-cmd --zone=public --list-all
```

For nftables:

```bash
nft list ruleset
```

For iptables:

```bash
iptables -L -n -v
```

### Step 4: Test From the Client

```bash
nc -vz SERVER_IP 8080
```

For HTTP:

```bash
curl -v http://SERVER_IP:8080
```

### Step 5: Check Routing

On the server:

```bash
ip route
```

On the client, check the route toward the destination.

### Step 6: Check Network Interfaces

```bash
ip -s link
```

Look for:

```text
RX errors
TX errors
Dropped packets
```

### Step 7: Check Other Firewalls

In cloud or enterprise environments, investigate:

```text
Client Firewall
      |
      v
Network Firewall
      |
      v
Load Balancer
      |
      v
Cloud Security Group
      |
      v
Network ACL
      |
      v
Linux Firewall
      |
      v
Application
```

### Step 8: Check SELinux if Relevant

If the service is listening but behavior is unexpected:

```bash
getenforce
```

Check denials:

```bash
ausearch -m AVC -ts recent
```

### Step 9: Use Packet Capture When Required

If the problem remains unclear:

```bash
sudo tcpdump -ni any port 8080
```

This can help determine whether packets:

```text
Reach the server
+
Leave the server
+
Receive a response
```

### Step 10: Identify the Layer

```text
Client
  |
  v
DNS
  |
  v
Routing
  |
  v
Network Firewall
  |
  v
Cloud Firewall / Security Group
  |
  v
Linux Firewall
  |
  v
SELinux
  |
  v
Application Port
  |
  v
Application
```

### Example Scenario

**Problem:**

```text
Application listens on TCP 8080
Local curl works
Remote client cannot connect
```

Investigation:

```text
ss
 ↓
Application is listening
 ↓
firewalld
 ↓
8080 not allowed
 ↓
Correct zone identified
 ↓
Add required rule
 ↓
Test from client
 ↓
Connection successful
```

### But Consider This

If the firewall allows the port and remote access still fails:

```text
Firewall
   ↓
Check routing
   ↓
Cloud security group
   ↓
Network ACL
   ↓
Load balancer
   ↓
Application binding
   ↓
SELinux
```

### Production Interview Scenario

**Interviewer:**

> "Users cannot access your application on port 8080. How will you troubleshoot it?"

**Strong Answer:**

> "First I will identify the source, destination, protocol, and port. On the server I will verify that the application is listening using `ss -lntp`. If it is listening, I will check the active firewalld zone and its rules, or inspect nftables/iptables depending on the firewall framework. I will test connectivity from the client using `nc` or an application-specific command. If the local firewall is not the cause, I will investigate routing, cloud security groups, network ACLs, load balancers, SELinux, and other network controls. If necessary, I will use packet capture to determine whether traffic reaches the server and whether a response is returned. I will make the smallest required firewall change, verify connectivity, and document the root cause."

# 🎤 Firewall Interview Golden Rules

```text
Connection failure ≠ automatically firewall issue
Port open ≠ application is healthy
Port listening ≠ port is remotely reachable
firewalld stopped ≠ no firewall exists
Wrong zone = rule may not affect expected traffic
Opening a port ≠ always the correct solution
iptables ≠ always the active firewall framework
Local connectivity ≠ remote connectivity
```

Always verify:

```text
Source
 +
Destination
 +
Protocol
 +
Port
 +
Application
 +
Listening Address
 +
Firewall Zone
 +
Firewall Rule
 +
Routing
 +
Cloud / Network Controls
 +
SELinux
```

### ⚠️ Production Safety Rules

Before changing firewall rules:

```text
1. Confirm the exact traffic requirement
2. Identify source, destination, protocol and port
3. Verify the application is listening
4. Identify the active firewall framework
5. Identify the correct firewalld zone if applicable
6. Review existing rules
7. Make the smallest required change
8. Avoid broad allow rules
9. Keep a rollback plan
10. Verify existing and new traffic
11. Monitor after the change
12. Document the change
```

> **Interview mindset:** Do not say, "The port is blocked, so I will open it." Say, "I will first verify that the application is listening, identify the active firewall and zone, confirm the required source and destination, inspect the complete network path, apply the minimum required rule, and verify connectivity."
