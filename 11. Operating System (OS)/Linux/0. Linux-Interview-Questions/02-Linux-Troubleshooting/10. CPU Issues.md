# 10. CPU Issues

> CPU troubleshooting is a common Linux production and DevOps interview topic. Always identify whether the CPU is being consumed by **user processes, system/kernel activity, I/O wait, steal time, or a specific application** before taking action.

# Q96. How do you troubleshoot high CPU usage?

## Answer

First check overall CPU usage:

```bash
top
```

Check CPU information:

```bash
lscpu
```

Check system statistics:

```bash
vmstat 1 5
```

Example:

```text
us  sy  id  wa  st
70   15   5   8   2
```

Important CPU fields:

```text
us = User CPU
sy = System/Kernel CPU
id = Idle CPU
wa = I/O Wait
st = Steal Time
```

### Identify Top CPU Processes

```bash
ps aux --sort=-%cpu | head
```

### Troubleshooting Flow

```text
High CPU
   |
   v
  top
   |
   v
Check us / sy / wa / st
   |
   v
Find top CPU process
   |
   v
Check application behavior
   |
   v
Check logs
   |
   v
Identify root cause
```

### Common Causes

* CPU-intensive application
* Infinite loop
* Too many processes
* High request volume
* Database workload
* Java/JVM thread issue
* Compression/encryption workload
* Malware or unexpected process
* Insufficient CPU resources

### Interview Tip

> "I first check CPU utilization with `top` and `vmstat`, identify whether the CPU is spent in user, system, I/O wait, or steal time, and then identify the responsible process."

# Q97. How do you identify which process is consuming high CPU?

## Answer

Use:

```bash
top
```

Inside `top`, press:

```text
P
```

This sorts processes by CPU usage.

You can also use:

```bash
ps aux --sort=-%cpu | head
```

Example:

```text
USER   PID   %CPU   %MEM   COMMAND
app    1234  250.5   10.2  java
root   5678   80.2    2.1  process
```

A process may show more than **100% CPU** on a multi-core system because CPU percentage can be measured relative to a single CPU core.

### Check Specific Process

```bash
ps -p 1234 -o pid,ppid,%cpu,%mem,etime,cmd
```

### Check Threads

For multi-threaded applications:

```bash
top -H -p 1234
```

This is especially useful for Java applications.

### Interview Tip

> "I use `top` or `ps` to identify the process, and if it is a multi-threaded application I use `top -H -p PID` to identify the specific thread consuming CPU."

# Q98. What is the difference between user CPU and system CPU?

## Answer

Linux CPU time is broadly divided into different categories.

### User CPU (`us`)

CPU used by applications running in user space.

Examples:

```text
Java application
Python script
Database workload
Compression
```

### System CPU (`sy`)

CPU used by the kernel on behalf of processes.

Examples:

```text
System calls
Network processing
Disk operations
Kernel operations
```

Check:

```bash
top
```

Example:

```text
%Cpu(s): 70.0 us, 20.0 sy, 5.0 id, 5.0 wa
```

Here:

```text
70% → User space
20% → Kernel/system
5%  → Idle
5%  → I/O wait
```

### High User CPU

Usually investigate:

* Application code
* CPU-intensive workload
* Infinite loops
* Heavy calculations

### High System CPU

Investigate:

* Excessive system calls
* Network workload
* Storage activity
* Kernel-related problems
* Very high process/thread activity

### Interview Tip

> "High user CPU generally points toward application workload, while high system CPU indicates significant kernel activity on behalf of applications."

# Q99. What is CPU load average and how do you troubleshoot high load?

## Answer

Load average represents the amount of work that is runnable or waiting for certain resources, including tasks waiting on CPU and, on Linux, tasks in uninterruptible sleep such as some I/O waits.

Check:

```bash
uptime
```

or:

```bash
top
```

Example:

```text
load average: 8.00, 7.50, 6.80
```

These represent:

```text
1 minute
5 minutes
15 minutes
```

### Important

Load average must be interpreted relative to the number of CPU cores.

Check CPU count:

```bash
nproc
```

Example:

```text
CPU cores = 8
Load average = 2
```

This is generally less concerning than:

```text
CPU cores = 2
Load average = 8
```

### High Load Does Not Always Mean High CPU

For example:

```text
CPU utilization = 40%
Load average    = 10
```

The system may have many tasks waiting on I/O or other uninterruptible work.

Check:

```bash
vmstat 1
```

and:

```bash
top
```

### Interview Tip

> "I never judge load average by the number alone. I compare it with CPU count and investigate whether the load is caused by CPU pressure or tasks waiting on I/O."

# Q100. What is CPU I/O wait and how do you troubleshoot high `%wa`?

## Answer

**I/O wait (`wa`)** represents CPU time during which the CPU is idle because runnable work is waiting for I/O completion.

Check:

```bash
top
```

or:

```bash
vmstat 1
```

Example:

```text
us  sy  id  wa
20  10  10  60
```

A high `wa` can indicate significant I/O pressure.

### Check Disk Performance

```bash
iostat -xz 1
```

If `iostat` is unavailable, install/use the appropriate `sysstat` package for the distribution.

Check disk devices:

```bash
lsblk
```

Check processes:

```bash
iotop
```

if installed and permitted.

### Common Causes

* Slow storage
* Heavy database I/O
* Large file operations
* Backup jobs
* Log processing
* Network storage latency
* Storage hardware problems

### Troubleshooting Flow

```text
High %wa
   |
   v
Check iostat
   |
   v
Identify busy device
   |
   v
Check application/process
   |
   v
Check storage latency
   |
   v
Check SAN/NFS/cloud disk
   |
   v
Fix storage/application issue
```

### Interview Tip

> "High I/O wait does not mean the CPU itself is faulty. I investigate the storage path using `iostat`, process-level I/O tools, application behavior, and the underlying storage system."

# Q101. What is CPU steal time and when is it a problem?

## Answer

**Steal time (`st`)** is mainly relevant to virtual machines.

It represents CPU time where the VM wanted to run but the hypervisor was using the physical CPU for another workload.

Check:

```bash
top
```

Example:

```text
us  sy  id  wa  st
30  10  20  5   35
```

Here:

```text
st = 35%
```

may indicate significant CPU contention at the virtualization layer.

### Common Causes

* Host CPU overcommitment
* Noisy neighbor VMs
* Insufficient physical CPU
* Cloud instance CPU contention

### Troubleshooting

Inside the VM:

```bash
top
```

```bash
vmstat 1
```

Then investigate the hypervisor/cloud platform.

### Important

A guest operating system cannot fully solve high steal time by changing application settings.

The issue may require:

* Moving the VM
* Changing instance size
* Reducing host contention
* Working with the virtualization/cloud team

### Interview Tip

> "High steal time indicates that the VM is waiting for physical CPU from the hypervisor. I would investigate host-level CPU contention rather than treating it as an application CPU problem."

# Q102. How do you troubleshoot a process using 100% CPU?

## Answer

First identify the process:

```bash
top
```

or:

```bash
ps aux --sort=-%cpu | head
```

Get process details:

```bash
ps -p 1234 -o pid,ppid,%cpu,%mem,etime,cmd
```

Check whether the process is multi-threaded:

```bash
top -H -p 1234
```

### Check Process Status

```bash
cat /proc/1234/status
```

Check open files:

```bash
lsof -p 1234
```

### Check Application Logs

```bash
journalctl -u application-name
```

or application-specific logs.

### Possible Causes

* Infinite loop
* Heavy computation
* Thread issue
* High traffic
* Database query
* Application bug
* Unexpected process
* Malware

### Do Not Immediately Kill the Process

First determine:

```text
Is it expected?
       |
       +-- Yes → Investigate workload
       |
       +-- No → Investigate process/application
```

If emergency mitigation is required, follow the production change/incident procedure before terminating a critical process.

### Interview Tip

> "I first identify whether the high CPU is expected workload or abnormal behavior. I inspect the process, threads, logs, and application behavior before restarting or killing it."

# Q103. How do you check CPU usage over time?

## Answer

For real-time monitoring:

```bash
top
```

For periodic statistics:

```bash
vmstat 2
```

For historical CPU statistics:

```bash
sar -u
```

Example:

```bash
sar -u 2 5
```

This collects CPU statistics at intervals.

### Check Specific Time Period

If `sar` historical data is available:

```bash
sar -u -f /var/log/sa/sa02
```

The exact location can vary by distribution and `sysstat` configuration.

### Check CPU Count

```bash
nproc
```

or:

```bash
lscpu
```

### Why Historical Data Is Important

Suppose the application team says:

> "CPU was 100% at 3 AM."

If you check at 10 AM, the CPU may be normal.

Historical monitoring can help determine:

```text
When?
How long?
Which CPU?
Was it recurring?
Was it related to a scheduled job?
```

### Interview Tip

> "For a production incident, historical CPU data is important because a current snapshot may not show the condition that caused the incident."

# Q104. How do you troubleshoot high CPU caused by multiple processes?

## Answer

First identify the processes:

```bash
ps aux --sort=-%cpu | head -20
```

Check overall CPU:

```bash
top
```

Determine whether the processes belong to the same application.

For example:

```text
java       80%
java       70%
java       60%
backup     40%
```

If multiple Java processes are consuming CPU, investigate the application workload rather than treating every process as an independent issue.

### Check Process Tree

```bash
pstree -p
```

For a specific process:

```bash
pstree -p 1234
```

### Check Scheduled Jobs

```bash
crontab -l
```

System-wide cron locations:

```bash
ls -l /etc/cron.*
```

### Possible Causes

* Scheduled backup
* Batch processing
* Multiple application workers
* Cron jobs
* High user traffic
* Runaway processes
* Application deployment issue

### Interview Tip

> "When multiple processes consume CPU, I group them by application/service and check whether they are expected workers, scheduled jobs, or abnormal processes."

# Q105. How do you troubleshoot high CPU in a production server?

## Answer

I would follow a structured approach.

### Step 1: Check Overall CPU

```bash
top
```

### Step 2: Check CPU Statistics

```bash
vmstat 1 10
```

Look at:

```text
us
sy
id
wa
st
```

### Step 3: Check CPU Count

```bash
nproc
```

### Step 4: Find Top Processes

```bash
ps aux --sort=-%cpu | head -20
```

### Step 5: Check Threads

For a suspected process:

```bash
top -H -p PID
```

### Step 6: Check I/O

If `wa` is high:

```bash
iostat -xz 1
```

### Step 7: Check Historical Data

```bash
sar -u
```

### Step 8: Check Application and System Logs

```bash
journalctl --since "30 minutes ago"
```

Application-specific logs should also be checked.

### Step 9: Identify Root Cause

```text
High CPU
   |
   +-- High user CPU
   |       → Application workload
   |
   +-- High system CPU
   |       → Kernel/system activity
   |
   +-- High I/O wait
   |       → Storage/I/O problem
   |
   +-- High steal
   |       → VM/hypervisor contention
   |
   +-- Many processes
           → Workload/scheduled jobs/process issue
```

### Step 10: Apply Correct Fix

Depending on the root cause:

* Fix application code
* Optimize database queries
* Reduce excessive workload
* Tune worker/thread configuration
* Reschedule heavy batch jobs
* Resolve storage issues
* Increase CPU resources
* Resolve VM host contention

### Production Interview Scenario

**Interviewer:**

> "A production Linux server suddenly reaches 100% CPU. What will you do?"

**Strong Answer:**

> "First I will check `top` and `vmstat` to determine where the CPU is being spent. I will identify the top CPU-consuming processes using `ps` or `top`, and for multi-threaded applications I will check individual threads. I will determine whether the CPU is user, system, I/O wait, or steal time. I will also check application logs and historical monitoring data to understand when the issue started. After identifying the root cause, I will apply the appropriate fix rather than blindly killing processes or rebooting the server."

Yes — this is an important interview point. **CPU percentage can be confusing when a server has multiple CPU cores.**

## CPU Percentage and Core Counting

### 1. What does `100% CPU` mean?

In Linux tools such as `top` and `ps`, **100% CPU generally represents one logical CPU/core fully utilized**.

For example, if a server has:

```bash
nproc
```

Output:

```text
4
```

The server has **4 logical CPUs**.

Therefore, approximately:

```text
1 logical CPU = 100%
4 logical CPUs = 400%
```

So a process showing:

```text
%CPU = 100%
```

is using roughly **one full logical CPU**.

---

### 2. Can a process show more than 100%?

**Yes.**

A multi-threaded process can use multiple CPU cores.

Example on a 4-CPU system:

```text
Process CPU usage = 250%
```

This means the process is approximately using:

```text
2.5 logical CPUs
```

Example:

| Process CPU % | Approx. CPU Usage |
| ------------: | ----------------: |
|           25% |          0.25 CPU |
|          100% |             1 CPU |
|          150% |          1.5 CPUs |
|          200% |            2 CPUs |
|          250% |          2.5 CPUs |
|          400% |            4 CPUs |

---

### 3. Example: 8-Core Server

Suppose:

```bash
nproc
```

returns:

```text
8
```

The approximate total CPU capacity represented by `top` is:

```text
8 × 100% = 800%
```

If a process shows:

```text
%CPU = 600%
```

it is using approximately:

```text
6 logical CPUs
```

That is very high.

But if it shows:

```text
%CPU = 100%
```

it is using only:

```text
1 out of 8 logical CPUs
```

So **100% for one process does not necessarily mean the entire server's CPU is 100% utilized.**

---

## 4. `top` Overall CPU vs Process CPU

This distinction is very important.

Suppose the server has **8 logical CPUs**.

`top` may show:

```text
%Cpu(s): 25.0 us, 5.0 sy, 0.0 ni, 65.0 id, 5.0 wa
```

This means approximately:

```text
25% → User CPU
5%  → System CPU
65% → Idle
5%  → I/O wait
```

Overall CPU is therefore roughly:

```text
100% - 65% idle = 35% busy
```

But a process might show:

```text
PID     %CPU
1234    300%
```

That's possible because the process is using approximately **3 logical CPUs**, while the overall server still has significant capacity.

---

## 5. Why does `top` sometimes show 100% overall CPU?

If an 8-CPU server shows:

```text
%Cpu(s): 100.0 us, 0.0 sy, 0.0 id
```

that means **all available CPU capacity is busy**.

Conceptually:

```text
8 CPUs
│
├── CPU 1 → 100%
├── CPU 2 → 100%
├── CPU 3 → 100%
├── CPU 4 → 100%
├── CPU 5 → 100%
├── CPU 6 → 100%
├── CPU 7 → 100%
└── CPU 8 → 100%
```

Total:

```text
800% process-level capacity
```

But `top` normalizes the **overall CPU summary to 100%**, not 800%.

---

## 6. `top` vs `ps` — Interview Point

This is where candidates sometimes get confused.

### `top`

The overall CPU summary is normalized to:

```text
100%
```

regardless of the number of CPUs.

But individual processes can show:

```text
100%
200%
300%
...
```

depending on how many CPUs they are consuming.

### `ps`

```bash
ps aux --sort=-%cpu | head
```

can show a process using:

```text
250%
```

on a multi-core system.

---

## 7. Logical CPU vs Physical Core

Don't automatically equate:

```text
logical CPU = physical core
```

Check:

```bash
lscpu
```

You may see:

```text
CPU(s):                8
Core(s) per socket:    4
Socket(s):             1
Thread(s) per core:    2
```

Meaning:

```text
1 socket
   ↓
4 physical cores
   ↓
2 threads per core
   ↓
8 logical CPUs
```

So Linux sees:

```text
8 logical CPUs
```

while the physical CPU has:

```text
4 physical cores
```

## 🎯 Interview Scenario

**Interviewer:**

> "A process is showing 400% CPU. Is the server's CPU utilization 400%?"

**Answer:**

> "Not necessarily. In Linux, process CPU percentages can exceed 100% on multi-core systems. A process showing 400% is approximately using four logical CPUs. I would check the total number of CPUs with `nproc` or `lscpu` and then check the overall CPU utilization in `top`."

### Another Question

**Interviewer:**

> "Your server has 8 CPUs and one process is using 100% CPU. Is the server overloaded?"

**Answer:**

> "Not necessarily. That process is approximately consuming one logical CPU. On an 8-CPU system, there are still other CPUs available. I would check overall CPU utilization, load average, and other processes before determining whether the server is overloaded."

### ⭐ Remember

```text
1 Logical CPU ≈ 100% process CPU

4 Logical CPUs ≈ 400%
8 Logical CPUs ≈ 800%

But:

Overall system CPU in top → normalized to 100%
Process CPU in top/ps → can exceed 100%
```

**Best interview command:**

```bash
nproc
lscpu
top
ps aux --sort=-%cpu | head
```
