# 14. SELinux Issues

> SELinux (Security-Enhanced Linux) provides **mandatory access control (MAC)** on Linux systems. It can prevent processes from accessing files, ports, or resources even when normal Linux permissions appear correct. SELinux troubleshooting requires checking the **mode, context, policy denials, booleans, ports, and service configuration**.

# Q136. What is SELinux and why is it used?

## Answer

**SELinux (Security-Enhanced Linux)** is a Linux security mechanism that provides **Mandatory Access Control (MAC)**.

Traditional Linux permissions use:

```text
User
Group
Other
```

SELinux adds another security layer based on:

```text
User
Process
File Context
Policy
```

### Example

Suppose a web server runs as:

```text
apache
```

Normal Linux permissions may allow Apache to read:

```text
/var/www/html/index.html
```

But if the SELinux context is incorrect, SELinux can still deny access.

```text
Apache Process
      |
      v
SELinux Policy
      |
      X
Access Denied
```

### Why SELinux Is Used

SELinux helps protect systems from:

* Unauthorized file access
* Compromised processes
* Unauthorized network access
* Privilege escalation
* Incorrect service behavior

### Important Concept

SELinux is an additional security layer.

```text
Linux DAC Permissions
        +
SELinux MAC Policy
        =
Access Decision
```

A process generally needs to satisfy both the normal Linux permissions and the SELinux policy.

### Interview Tip

> "SELinux provides mandatory access control in addition to normal Linux permissions. It restricts what processes can access based on security policies and contexts."

# Q137. How do you check the SELinux status and mode?

## Answer

Use:

```bash
getenforce
```

Possible output:

```text
Enforcing
```

or:

```text
Permissive
```

or:

```text
Disabled
```

### Detailed Status

```bash
sestatus
```

Example:

```text
SELinux status:                 enabled
SELinuxfs mount:                /sys/fs/selinux
SELinux mount:                  /sys/fs/selinux
Current mode:                   enforcing
Mode from config file:          enforcing
Policy version:                 ...
Policy from config file:        targeted
```

### Check Configuration

```bash
cat /etc/selinux/config
```

Example:

```text
SELINUX=enforcing
SELINUXTYPE=targeted
```

### Important

There is a difference between:

```text
Current Mode
```

and:

```text
Configured Mode
```

For example:

```text
getenforce
```

may show:

```text
Permissive
```

while:

```text
/etc/selinux/config
```

may specify:

```text
SELINUX=enforcing
```

### Interview Tip

> "I use `getenforce` for the current mode, `sestatus` for detailed status, and `/etc/selinux/config` to check the configured mode."

# Q138. What is the difference between SELinux Enforcing, Permissive, and Disabled modes?

## Answer

SELinux has three main modes.

### 1. Enforcing

```text
Enforcing
   |
   +-- Policy is active
   +-- Access is checked
   +-- Violations are blocked
   +-- Denials are logged
```

This is the normal recommended mode for systems where SELinux is intended to protect the workload.

Check:

```bash
getenforce
```

Output:

```text
Enforcing
```

### 2. Permissive

In permissive mode:

```text
Policy violations
       |
       +-- Logged
       |
       +-- Not blocked
```

Check:

```bash
getenforce
```

Output:

```text
Permissive
```

This can be useful for troubleshooting because SELinux records denials without enforcing them.

### 3. Disabled

SELinux is completely disabled.

```text
Disabled
   |
   X
No SELinux enforcement
```

### Temporary Mode Change

To temporarily switch to permissive:

```bash
sudo setenforce 0
```

Switch back:

```bash
sudo setenforce 1
```

Verify:

```bash
getenforce
```

### Important

`setenforce` changes the **runtime mode**.

It does not permanently change:

```text
/etc/selinux/config
```

### Production Warning

Do not permanently disable SELinux simply because an application is not working.

Better approach:

```text
Application Failure
       |
       v
Check SELinux Denials
       |
       v
Understand Policy
       |
       v
Fix Context / Boolean / Port / Policy
       |
       v
Keep SELinux Enforcing
```

### Interview Tip

> "Enforcing blocks unauthorized actions and logs them, Permissive logs violations without blocking them, and Disabled turns SELinux off. In production, I prefer fixing the SELinux policy issue instead of disabling SELinux."

# Q139. How do you troubleshoot an application blocked by SELinux?

## Answer

Suppose an application is working correctly according to:

```text
Linux permissions
+
Application configuration
```

but access is still denied.

SELinux may be the reason.

### Step 1: Check SELinux Mode

```bash
getenforce
```

### Step 2: Check Application Status

```bash
systemctl status myapp
```

### Step 3: Check Application Logs

```bash
journalctl -u myapp
```

### Step 4: Check SELinux Denials

```bash
ausearch -m AVC -ts recent
```

If `ausearch` is available.

You can also search the audit log:

```bash
grep -i denied /var/log/audit/audit.log
```

### Step 5: Check File Context

```bash
ls -Z /path/to/file
```

### Step 6: Check Port Context

```bash
sudo semanage port -l
```

### Step 7: Check Booleans

```bash
getsebool -a
```

### Troubleshooting Flow

```text
Application Failure
       |
       v
Check Service
       |
       v
Check Application Logs
       |
       v
Check SELinux Mode
       |
       v
Check AVC Denials
       |
       +---------+---------+
       |         |         |
       v         v         v
    Context   Boolean     Port
       |         |         |
       +---------+---------+
                 |
                 v
             Fix Policy
                 |
                 v
              Verify
```

### Example

A web server cannot read a file:

```text
File exists
Linux permissions look correct
Application configuration looks correct
        |
        v
SELinux denial
        |
        v
Incorrect file context
```

The solution is to correct the SELinux context rather than disabling SELinux.

### Interview Tip

> "If an application appears to have correct Linux permissions but access is denied, I check SELinux mode and AVC denials, then investigate file contexts, booleans, ports, and the applicable policy."

# Q140. How do you check SELinux denial messages?

## Answer

SELinux access denials are commonly recorded as **AVC (Access Vector Cache) denial** messages in the audit logs.

### Using `ausearch`

```bash
ausearch -m AVC -ts recent
```

For a specific service or time range, narrow the search where possible.

### Search Audit Log

```bash
grep -i denied /var/log/audit/audit.log
```

### Search Recent Denials

```bash
ausearch -m AVC -ts recent | less
```

### Example Denial

You may see information similar to:

```text
type=AVC
avc: denied
{ read }
pid=1234
comm="httpd"
name="index.html"
```

Important information includes:

```text
Process
PID
Operation
Source Context
Target Context
Target Object
```

### Use `sealert`

On systems where `setroubleshoot` is installed:

```bash
sealert -a /var/log/audit/audit.log
```

This can provide a more human-readable explanation.

### Important

Do not blindly copy a suggested `audit2allow` command without understanding the denial.

First determine:

```text
Why is the process accessing this resource?
Is the access expected?
Is the context wrong?
Is a boolean required?
Is the port incorrectly labeled?
```

### Interview Tip

> "I check AVC denials using `ausearch` or the audit log, identify the source process and target resource, and then determine whether the denial is caused by an incorrect context, boolean, port labeling, or an actual policy requirement."

# Q141. What is an SELinux context and how do you check it?

## Answer

An **SELinux context** is a security label associated with files, processes, ports, and other resources.

A typical file context looks like:

```text
system_u:object_r:httpd_sys_content_t:s0
```

The major fields represent SELinux security information.

### Check File Context

```bash
ls -Z /var/www/html/
```

Example:

```text
-rw-r--r--. root root system_u:object_r:httpd_sys_content_t:s0 index.html
```

### Check Process Context

```bash
ps -eZ
```

For a specific process:

```bash
ps -eZ | grep httpd
```

### Check Port Context

```bash
sudo semanage port -l
```

Example:

```text
http_port_t
```

may include common web ports.

### Why Context Matters

Suppose:

```text
/var/www/html/index.html
```

has an unexpected SELinux type.

The web server may be prevented from reading it even when:

```bash
ls -l
```

shows correct Unix permissions.

### Compare

```text
Linux Permission
       +
SELinux Context
       +
SELinux Policy
       |
       v
Access Decision
```

### Interview Tip

> "SELinux contexts are security labels used by the SELinux policy. I use `ls -Z` for files, `ps -eZ` for processes, and `semanage` commands for resource-specific SELinux configuration."

# Q142. How do you fix an incorrect SELinux file context?

## Answer

First check the current context:

```bash
ls -Z /var/www/html/index.html
```

If the context is incorrect, first determine the expected context for that path.

### Check Expected Context

```bash
matchpathcon /var/www/html/index.html
```

### Restore Default Context

If the file should have the default SELinux context for its location:

```bash
sudo restorecon -v /var/www/html/index.html
```

For a directory:

```bash
sudo restorecon -Rv /var/www/html/
```

### Verify

```bash
ls -Z /var/www/html/index.html
```

### For a Custom Application Directory

Suppose an application stores web content in:

```text
/opt/myapp/html/
```

You may need a persistent file-context rule.

Example:

```bash
sudo semanage fcontext -a -t httpd_sys_content_t "/opt/myapp/html(/.*)?"
```

Then apply it:

```bash
sudo restorecon -Rv /opt/myapp/html/
```

Verify:

```bash
ls -Z /opt/myapp/html/
```

### Important Difference

`chcon` can change a context directly:

```bash
sudo chcon -t httpd_sys_content_t file
```

But this is generally **not the preferred persistent configuration method**.

For persistent custom labeling, use:

```text
semanage fcontext
        +
restorecon
```

### Interview Tip

> "I first verify the current and expected context. For default paths I normally use `restorecon`; for custom paths I use `semanage fcontext` followed by `restorecon` so the configuration remains persistent."

# Q143. What are SELinux booleans and how do you troubleshoot them?

## Answer

**SELinux booleans** are switches that enable or disable specific SELinux policy behaviors without changing the entire policy.

### List Booleans

```bash
getsebool -a
```

### Check a Specific Boolean

Example:

```bash
getsebool httpd_can_network_connect
```

Output may be:

```text
httpd_can_network_connect --> off
```

### Change Temporarily

```bash
sudo setsebool httpd_can_network_connect on
```

### Make Persistent

```bash
sudo setsebool -P httpd_can_network_connect on
```

The `-P` option updates persistent policy configuration.

### Example Scenario

Suppose:

```text
Web Server
    |
    v
External API
    |
    X
SELinux Denial
```

A relevant SELinux boolean may control whether the web server is allowed to make network connections.

Instead of disabling SELinux:

```text
❌ Disable SELinux
```

investigate whether an appropriate boolean is intended:

```text
✅ Check SELinux Boolean
```

### Important

Do not enable every boolean just to make an application work.

First determine:

```text
What access is required?
Why is SELinux blocking it?
Is there an appropriate existing boolean?
What security impact does enabling it have?
```

### Interview Tip

> "SELinux booleans provide controlled switches for specific policy behaviors. I check the relevant boolean with `getsebool`, change it with `setsebool`, and use `-P` only when the change should persist."

# Q144. How do you troubleshoot an SELinux port-related issue?

## Answer

SELinux also controls which processes can bind to specific ports based on SELinux port types.

Suppose an application normally uses:

```text
8080
```

but you configure it to use:

```text
9090
```

The application may fail because SELinux does not allow the process to bind to that port type.

### Step 1: Check Listening Ports

```bash
ss -lntp
```

### Step 2: Check SELinux Port Labels

```bash
sudo semanage port -l
```

Search for a specific port:

```bash
sudo semanage port -l | grep 9090
```

### Step 3: Add the Port to the Appropriate SELinux Type

For example, if the application is an HTTP service and the policy expects `http_port_t`:

```bash
sudo semanage port -a -t http_port_t -p tcp 9090
```

### Step 4: Verify

```bash
sudo semanage port -l | grep http_port_t
```

### Step 5: Restart/Start the Service

```bash
sudo systemctl restart myapp
```

Then:

```bash
ss -lntp | grep :9090
```

### Important

Do not automatically assign:

```text
http_port_t
```

to every application port.

The correct SELinux type depends on the service and policy.

### If `semanage` Is Missing

On many systems, `semanage` is provided by a package such as:

```text
policycoreutils-python-utils
```

The exact package name can vary by distribution/version.

Check availability:

```bash
command -v semanage
```

### Interview Tip

> "For an SELinux port issue, I verify the application's port, check its SELinux port type with `semanage port -l`, and assign the correct SELinux port label rather than disabling SELinux."

# Q145. How do you troubleshoot SELinux issues in production?

## Answer

In production, I use an **evidence-first approach** rather than immediately changing SELinux mode.

### Step 1: Confirm the Application Problem

```bash
systemctl status myapp
```

Check:

```text
Service status
Application logs
Error messages
User impact
Start time
```

### Step 2: Check SELinux Mode

```bash
getenforce
```

```bash
sestatus
```

### Step 3: Check AVC Denials

```bash
ausearch -m AVC -ts recent
```

or:

```bash
grep -i denied /var/log/audit/audit.log
```

### Step 4: Identify the Resource

Determine whether SELinux is blocking:

```text
File
Directory
Port
Network access
Process
Device
```

### Step 5: Check Context

File:

```bash
ls -Z /path/to/file
```

Process:

```bash
ps -eZ
```

Port:

```bash
semanage port -l
```

### Step 6: Check Booleans

```bash
getsebool -a
```

### Step 7: Check Recent Changes

Investigate:

```text
Application deployment
File movement
Permission changes
Custom directories
Port changes
Policy changes
Boolean changes
OS updates
```

### Step 8: Apply the Smallest Correct Fix

Possible solutions:

```text
Correct file context
        OR
Configure persistent file labeling
        OR
Enable appropriate boolean
        OR
Configure correct SELinux port type
        OR
Review policy requirement
```

### Step 9: Verify

After the fix:

```text
Application
Service
Port
Logs
SELinux denials
User requests
```

should all be checked.

### Step 10: Keep SELinux Secure

Avoid:

```bash
setenforce 0
```

as a permanent solution.

Avoid permanently disabling SELinux just to bypass an application problem.

### Production Troubleshooting Flow

```text
              APPLICATION ISSUE
                      |
                      v
                Confirm Impact
                      |
                      v
               Check Service
                      |
                      v
               Check App Logs
                      |
                      v
              Check SELinux Mode
                      |
                      v
                Check AVC Logs
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Context      Boolean      Port
          |           |           |
          +-----------+-----------+
                      |
                      v
                Apply Correct Fix
                      |
                      v
                    Verify
                      |
                      v
                  Document
```

### Production Interview Scenario

**Interviewer:**

> "The web server has correct Linux permissions, but it cannot access a file. What will you check?"

**Strong Answer:**

> "First I will confirm the application error and verify the normal Linux permissions. Then I will check whether SELinux is enabled and enforcing using `getenforce` or `sestatus`. I will inspect AVC denial messages using `ausearch` or the audit log and check the file's SELinux context with `ls -Z`. If the context is incorrect, I will use the appropriate `restorecon` or persistent `semanage fcontext` configuration. I will verify the application afterward and keep SELinux enforcing rather than disabling it as a workaround."


### ⚠️ Production Safety Rules

Before changing SELinux configuration:

```text
1. Confirm the application problem
2. Check SELinux mode
3. Collect AVC denial evidence
4. Identify the exact resource being blocked
5. Understand why access is required
6. Apply the smallest appropriate policy change
7. Avoid disabling SELinux as a permanent workaround
8. Verify application functionality
9. Verify SELinux denials again
10. Document the change
```

> **Interview mindset:** Do not say, "SELinux is blocking the application, so I will disable it." Say, "I will identify the AVC denial, determine the required access, verify the context, boolean, or port configuration, apply the smallest appropriate fix, and verify the application while keeping SELinux enforcing."

# Q126. What is a Linux process and how do you troubleshoot a problematic process?

## Answer

A **process** is a running instance of a program.

For example:

```text
Application
     |
     v
Program
     |
     v
Running Process
```

Every process has a unique **PID (Process ID)**.

### Check Processes

```bash
ps aux
```

Find a specific process:

```bash
ps aux | grep nginx
```

A better option:

```bash
pgrep -a nginx
```

### Check Process Details

```bash
ps -fp <PID>
```

Example:

```bash
ps -fp 1234
```

### Check Resource Usage

```bash
top
```

Find CPU-heavy processes:

```bash
ps aux --sort=-%cpu | head -20
```

Find memory-heavy processes:

```bash
ps aux --sort=-%mem | head -20
```

### Check Open Files

```bash
lsof -p <PID>
```

### Check Process Status

```bash
cat /proc/<PID>/status
```

### Troubleshooting Flow

```text
Problematic Process
       |
       v
Find PID
       |
       v
Check CPU / Memory
       |
       v
Check Process Status
       |
       v
Check Logs
       |
       v
Check Open Files / Network
       |
       v
Identify Root Cause
```

### Common Problems

* High CPU
* High memory
* Process stuck
* Process repeatedly crashing
* Too many processes
* File descriptor exhaustion
* Network connection problems
* Application deadlock

### Interview Tip

> "I first identify the PID, then check CPU, memory, process state, logs, open files, and network connections before deciding whether the process needs to be restarted or terminated."

# Q127. What is the difference between a process and a service?

## Answer

A **process** is a running instance of a program.

A **service** is usually a long-running background application managed by a service manager such as `systemd`.

### Example

```text
Service
  |
  v
nginx.service
  |
  v
nginx processes
  |
  +-- PID 1001
  +-- PID 1002
```

### Process

Check:

```bash
ps aux
```

### Service

Check:

```bash
systemctl status nginx
```

### Main Difference

| Process                       | Service                          |
| ----------------------------- | -------------------------------- |
| Running instance of a program | Managed background application   |
| Has a PID                     | Usually managed by `systemd`     |
| Can exist independently       | Usually has lifecycle management |
| `ps`, `top`, `pgrep`          | `systemctl`, `journalctl`        |
| Focuses on execution          | Focuses on service lifecycle     |

### Important

A service can be:

```text
Active
Inactive
Failed
Activating
Deactivating
```

A service may also manage one or multiple processes.

### Interview Tip

> "A process is an executing program identified by a PID, while a service is typically a long-running application managed by a service manager such as systemd."

# Q128. How do you check running processes in Linux?

## Answer

There are several commands depending on the information required.

### 1. `ps`

```bash
ps aux
```

Shows currently running processes.

For process hierarchy:

```bash
ps -ef --forest
```

### 2. `top`

```bash
top
```

Useful for real-time monitoring.

### 3. `htop`

```bash
htop
```

Provides an interactive process view if installed.

### 4. `pgrep`

Find a process by name:

```bash
pgrep -a nginx
```

### 5. `pidof`

```bash
pidof nginx
```

### Check a Specific PID

```bash
ps -fp <PID>
```

### Process Tree

```bash
pstree
```

For a specific process:

```bash
pstree -p <PID>
```

### Useful Process Information


# Q134. How do you safely stop or kill a Linux process?

## Answer

First identify the correct process.

```bash
ps -fp <PID>
```

Never kill a process only because its CPU usage is high without understanding its role.

### Step 1: Graceful Termination

Use:

```bash
kill <PID>
```

By default, this sends:

```text
SIGTERM
```

It asks the application to terminate gracefully.

### Step 2: Wait and Verify

```bash
ps -p <PID>
```

If the process exits:

```text
Process stopped
```

### Step 3: Force Kill

Only when necessary:

```bash
kill -9 <PID>
```

This sends:

```text
SIGKILL
```

The process cannot catch or handle `SIGKILL`.

### Important

Prefer:

```text
SIGTERM
   ↓
Graceful shutdown
   ↓
Verify
   ↓
SIGKILL only if necessary
```

### If It Is a Managed Service

Prefer controlling the service instead of directly killing its process:

```bash
systemctl stop myapp
```

This allows the service manager to handle the service lifecycle correctly.

### Find Parent Process

```bash
ps -o pid,ppid,cmd -p <PID>
```

Or:

```bash
pstree -p <PID>
```

### Risks of `kill -9`

Force killing can cause:

* Incomplete transactions
* Temporary files
* Data inconsistency
* Connection termination
* Application cleanup not running

### Interview Tip

> "I first verify the PID and process ownership, then try graceful termination with `SIGTERM`. I use `SIGKILL` only when necessary, and for systemd-managed applications I prefer `systemctl stop`."

```text
   ↓
```
