# 22. Asynchronous Tasks

## Learning Objectives

After completing this chapter, you will be able to:

* Understand Asynchronous Tasks in Ansible.
* Run tasks in the background.
* Use Polling to monitor tasks.
* Execute long-running tasks efficiently.
* Understand Fire and Forget execution.
* Check the status of asynchronous jobs.
* Follow best practices for async tasks.

---

# What are Asynchronous Tasks?

By default, Ansible waits for a task to finish before moving to the next task.

**Asynchronous Tasks** allow Ansible to start a task and continue without waiting for it to complete.

They are useful for tasks that take a long time.

---

# Why Use Asynchronous Tasks?

Examples:

* Operating system updates
* Large package installations
* Database backups
* Database restore operations
* Server reboot
* Software compilation
* Large file downloads

---

# Synchronous vs Asynchronous

## Synchronous (Default)

```
Task 1

↓

Wait

↓

Completed

↓

Task 2
```

Ansible waits until Task 1 finishes.

---

## Asynchronous

```
Task 1

↓

Runs in Background

↓

Task 2
```

Ansible does not wait unless polling is enabled.

---

# Async Keyword

The `async` keyword specifies the maximum time (in seconds) a task is allowed to run.

Syntax

```yaml
async: <seconds>
```

Example

```yaml
- name: Install Package

  package:

    name: docker

    state: present

  async: 600
```

The task can run for up to **600 seconds**.

---

# Poll Keyword

The `poll` keyword controls whether Ansible waits for the task.

Syntax

```yaml
poll: <seconds>
```

---

# Async with Poll

Example

```yaml
- name: Update Packages

  dnf:

    name: "*"

    state: latest

  async: 1800

  poll: 30
```

Meaning:

* Maximum runtime: **1800 seconds**
* Check status every **30 seconds**
* Wait until the task finishes

---

# Background Jobs

Background Jobs allow tasks to continue running on the managed node.

Example

```yaml
- name: Start Backup

  shell: /opt/backup.sh

  async: 3600

  poll: 0
```

The backup starts immediately, and Ansible continues with the next task.

---

# Fire and Forget

`poll: 0` enables **Fire and Forget** mode.

Example

```yaml
- name: Run Script

  shell: /opt/deploy.sh

  async: 1800

  poll: 0
```

Execution

```
Start Task

↓

Background

↓

Next Task
```

Ansible does **not** wait for completion.

---

# Long Running Tasks

Examples:

* Upgrade Linux packages
* Database migration
* Large file transfer
* Application deployment
* Docker image build
* Virtual machine creation

These tasks are ideal for asynchronous execution.

---

# Register Async Job

Store the Job ID for later.

```yaml
- name: Start Backup

  shell: /opt/backup.sh

  async: 3600

  poll: 0

  register: backup_job
```

The registered variable contains the asynchronous job ID.

---

# Check Async Job Status

Use the **async_status** module.

```yaml
- name: Check Backup Status

  async_status:

    jid: "{{ backup_job.ansible_job_id }}"

  register: backup_status
```

---

# Wait Until Job Completes

```yaml
- name: Wait for Backup

  async_status:

    jid: "{{ backup_job.ansible_job_id }}"

  register: backup_status

  until: backup_status.finished

  retries: 30

  delay: 10
```

Meaning:

* Check every **10 seconds**
* Retry **30 times**
* Stop when the job finishes

---

# Async Workflow

```
Start Task

↓

Register Job ID

↓

Background Execution

↓

Check Status

↓

Task Completed
```

---

# Async vs Poll

| Async                      | Poll                  |
| -------------------------- | --------------------- |
| Maximum runtime for a task | Status check interval |
| Required                   | Optional              |
| Measured in seconds        | Measured in seconds   |

---

# Poll Values

| Value    | Behavior               |
| -------- | ---------------------- |
| poll: 0  | Fire and Forget        |
| poll: 5  | Check every 5 seconds  |
| poll: 30 | Check every 30 seconds |

* Server reboot

---

# Best Practices

* Use asynchronous tasks only for long-running operations.
* Use `poll: 0` only when you do not need immediate results.
* Register the Job ID for background tasks.
* Use the `async_status` module to monitor jobs.
* Set realistic `async` timeout values.
* Avoid unnecessary asynchronous execution for short tasks.
