# **Terraform Project :**


## Important Points

1. Goal
   Terraform → AWS Infrastructure
   Ansible → Server Configuration
   Ansible Galaxy → Reusable Roles
   Docker → Container
   Nginx → Web Server

2. Project Flow
   Terraform
      ↓
   AWS EC2
      ↓
   Ansible
      ↓
   Docker + Nginx

3. AWS Region
   us-east-1 (N. Virginia)
   Region can be changed using variable.

4. EC2 Instance
   t2.micro
   1 vCPU + 1 GiB RAM
   Suitable for basic learning/practice.

5. Terraform Files
   terraform.tf       → Required providers
   provider.tf        → AWS provider configuration
   variables.tf       → Input variables
   main.tf            → Infrastructure resources
   outputs.tf         → Output values
   terraform.tfvars   → Variable values (if required)
   terraform.lock.hcl → Automatically generated provider lock file

6. Provider
   provider "aws" {
     region = var.aws_region
   }

7. AWS Provider
   Source:
   hashicorp/aws

   Provider version:
   6.50.0

8. Variables
   aws_region
   instance_type
   key_name
   volume_size
   ssh_key_path
   instances

9. Important
   AMI IDs are region-specific.
   Don't blindly copy AMI IDs from another region.

10. terraform init
    Downloads/initializes required providers.
    Creates terraform.lock.hcl.

11. Learning Approach
    Reference project → Understand → Create own file
    → Test → Fix → Continue

12. Don't copy everything at once.
    Create one file at a time.

13. t2.micro
    Good for basic:
    - Terraform
    - Ansible
    - Docker
    - Nginx

14. Caution
    Multiple EC2 instances + Docker containers
    can require more RAM.

15. Final Architecture
    Terraform → EC2 → Ansible → Docker → Nginx

## ec2.tf File Discritption.

 Ye **`ec2.tf`** aapke project ka main infrastructure file hai. Isme 3 main kaam ho rahe hain:

1. SSH Key Pair create
2. Security Group create
3. Multiple EC2 instances create

Let's understand it block-by-block.

---

## 1. AWS Key Pair

```hcl
resource "aws_key_pair" "ansible" {
  key_name   = var.key_name
  public_key = file("${path.module}/terra-key-ansible.pub")
}
```

### Kya karta hai?

AWS me EC2 ke liye **SSH key pair** register karta hai.

```text
Your local machine
       │
       │ terra-key-ansible.pub
       ▼
     AWS
       │
       ▼
   EC2 Key Pair
```

### `key_name`

```hcl
key_name = var.key_name
```

`variables.tf` se value aayegi:

```hcl
variable "key_name" {
  default = "terra-key-ansible"
}
```

So AWS me key pair ka naam hoga:

```text
terra-key-ansible
```

### `public_key`

```hcl
public_key = file("${path.module}/terra-key-ansible.pub")
```

Yahan Terraform local file read kar raha hai:

```text
terraform/
└── terra-key-ansible.pub
```

`path.module` ka matlab roughly **current Terraform module ka directory**.

So:

```text
${path.module}/terra-key-ansible.pub
```

means:

```text
current terraform directory/terra-key-ansible.pub
```

### Important

`.pub` = **public key**

Private key AWS ko nahi deni chahiye.

---

# 2. Default VPC

```hcl
data "aws_vpc" "default" {
  default = true
}
```

Yeh **new VPC create nahi karta**.

Ye AWS me already existing **default VPC ko find/read** karta hai.

Difference:

```text
resource → create/manage
data     → existing resource read
```

So:

```hcl
data "aws_vpc" "default"
```

means:

> AWS ka default VPC find karo.

Later:

```hcl
vpc_id = data.aws_vpc.default.id
```

se us VPC ki ID use ho rahi hai.

---

# 3. Security Group

```hcl
resource "aws_security_group" "ansible_lab" {
```

Ye EC2 instances ke liye **firewall/security rules** create karta hai.

```hcl
name = "ansible-lab-sg"
```

AWS Security Group ka naam.

```hcl
description = "Security group for Ansible lab instances"
```

Description.

```hcl
vpc_id = data.aws_vpc.default.id
```

Security Group ko default VPC me create karega.

---

# 4. SSH Port 22

```hcl
ingress {
  from_port   = 22
  to_port     = 22
  protocol    = "tcp"
  cidr_blocks = ["0.0.0.0/0"]
  description = "SSH"
}
```

Meaning:

```text
Internet
   ↓
Port 22
   ↓
EC2
```

Ansible ko SSH ke through EC2 se connect karne ke liye port **22** required hai.

### `0.0.0.0/0`

Iska meaning:

> Anywhere on the internet.

Learning lab ke liye convenient hai, **production me SSH ko `0.0.0.0/0` open rakhna security risk hai**. Better is your own IP/allowed network.

---

# 7. Outbound Traffic

```hcl
egress {
  from_port   = 0
  to_port     = 0
  protocol    = "-1"
  cidr_blocks = ["0.0.0.0/0"]
  description = "All outbound traffic"
}
```

EC2 se **outgoing traffic allowed**.

For example EC2 ko:

```text
Internet
  ↑
  │
EC2
  │
  ├── apt update
  ├── Docker download
  ├── Ansible packages
  └── Nginx packages
```

ke liye internet access chahiye.

# 9. EC2 Instance

Ab sabse important part:

```hcl
resource "aws_instance" "my_instance" {
  for_each = var.instances
```

Ye **multiple EC2 instances create kar sakta hai**.

Aapke `variables.tf` me:

```hcl
instances = {
  "control-node-ubuntu" = {...}
  "worker-ubuntu"      = {...}
  "worker-redhat"      = {...}
  "worker-amazon"      = {...}
}
```

To Terraform roughly:

```text
for_each
   │
   ├── control-node-ubuntu → EC2
   ├── worker-ubuntu       → EC2
   ├── worker-redhat       → EC2
   └── worker-amazon       → EC2
```

**Yahi reason hai ki aapke `variables.tf` me complex `instances` variable hai.**

```text

       ↓

```

# 16. `depends_on`

```hcl

  aws_security_group.ansible_lab,
  aws_key_pair.ansible
]
```

> Pehle Security Group aur Key Pair ready karo, uske baad EC2 create karo.

Flow:

```text

                   │
                   ▼
              EC2 Instance
                   ▲
                   │
Security Group ────┘
```

Terraform dependencies usually automatically understand kar leta hai because you reference resources directly, but yahan explicit dependency bhi given hai.

## generate_inventory.tf

 Ye file Terraform se **Ansible inventory automatically generate** karti hai.

Iska main purpose hai:

```text
Terraform creates EC2
        ↓
EC2 IP addresses milte hain
        ↓
Terraform inventory generate karta hai
        ↓
Ansible hosts.ini
        ↓
Ansible connects to EC2
```

## 1. `locals`

```hcl
locals {
  inventory = {
    for name, inst in aws_instance.my_instance : name => {
      public_ip  = inst.public_ip
      private_ip = inst.private_ip
      user       = var.instances[name].user
      os_family  = var.instances[name].os_family
    }
  }
```

Yahan Terraform **EC2 instances ki information ko ek local variable `inventory` me organize** kar raha hai.

Example:

```text
control-node-ubuntu
    public_ip  = 1.2.3.4
    private_ip = 10.0.1.10
    user       = ubuntu
    os_family  = ubuntu
```

Aur worker:

```text
worker-ubuntu
    public_ip  = 5.6.7.8
    private_ip = 10.0.1.11
    user       = ubuntu
    os_family  = ubuntu
```

### Important concepts

Is block se aap seekh rahe ho:

* `locals`
* `for expression`
* `aws_instance.my_instance`
* `each/instance data`
* referencing variables

## 2. Control hosts

```hcl
control_hosts = {
  for name, inst in local.inventory :
  name => inst
  if can(regex("control", name))
}
```

Ye `inventory` me se sirf **control** naam wale instances filter karta hai.

Example:

```text
control-node-ubuntu
worker-ubuntu
worker-redhat
worker-amazon
```

Result:

```text
control-node-ubuntu
```

`regex("control", name)` check karta hai ki instance name me `"control"` hai ya nahi.

---

## 3. Ubuntu workers

```hcl
ubuntu_worker_hosts = {
  for name, inst in local.inventory :
  name => inst
  if inst.os_family == "ubuntu" && can(regex("worker", name))
}
```

Ye 2 conditions check karta hai:

```text
OS = ubuntu
AND
name contains worker
```

So:

```text
worker-ubuntu
```

select hoga.

---

## 4. Red Hat workers

```hcl
redhat_hosts = {
  for name, inst in local.inventory :
  name => inst
  if inst.os_family == "redhat"
}
```

Ye Red Hat instances filter karta hai.

---

## 5. Amazon Linux workers

```hcl
amazon_hosts = {
  for name, inst in local.inventory :
  name => inst
  if inst.os_family == "amazon"
}
```

Ye Amazon Linux instances filter karta hai.

# 6. `local_file` — Ansible Inventory

Ab important part:

```hcl
resource "local_file" "ansible_inventory" {
```

Terraform **local machine par file create** karega.

```hcl
content = templatefile(
  "${path.module}/templates/inventory.tpl",
  {
    control        = local.control_hosts
    ubuntu_workers = local.ubuntu_worker_hosts
    redhat         = local.redhat_hosts
    amazon         = local.amazon_hosts
  }
)
```

Yahan:

```text
templates/inventory.tpl
```

template file use ho rahi hai.

Terraform us template me actual EC2 IPs/details inject karega.

Then:

```hcl
filename = "${path.module}/../inventories/dev/hosts.ini"
```

Generated file:

```text
inventories/
└── dev/
    └── hosts.ini
```

So final flow:

```text
AWS EC2
  ↓
Terraform gets IP
  ↓
local.inventory
  ↓
inventory.tpl
  ↓
hosts.ini
  ↓
Ansible
```

## templates/

bootstrap.tpl

Bilkul. `inventory.tpl` **bootstrap.tpl ke baad actual Ansible inventory template** hai. Iska use Terraform automatically `hosts.ini` generate karne ke liye karta hai.

Sabse important difference:

```text
bootstrap.tpl
Laptop → Control Node → First-time setup

inventory.tpl
Control Node → Workers → Actual Ansible work
```

---

# 1. Header

```text
# Ansible Inventory — Auto-generated by Terraform

# Teaching inventory: run this FROM the control node.

# The control node manages itself locally and reaches workers by PRIVATE IP.
```

Meaning:

* Terraform inventory automatically generate karega.
* Is inventory ko **Control Node se run** karna hai.
* Control Node khud ko local connection se manage karega.
* Workers ko **private IP** se access karega.

Architecture:

```text
Your Laptop
     │
     │ bootstrap
     ▼
Control Node
     │
     │ Ansible
     ├──────────► Ubuntu Worker
     ├──────────► RedHat Worker
     └──────────► Amazon Worker
             Private IP
```

---

# 2. `[all:vars]`

```ini
[all:vars]
ansible_python_interpreter=/usr/bin/python3
```

`all:vars` ka meaning:

> Ye variable inventory ke **sabhi hosts** par apply hoga.

Isliye har host ke liye individually:

```ini
ansible_python_interpreter=/usr/bin/python3
```

likhne ki zarurat nahi.

Ansible remote machines par Python 3 use karega.

---

# 3. `[control]`

```ini
[control]
%{ for name, inst in control ~}
${name} ansible_connection=local ansible_user=${inst.user}
%{ endfor ~}
```

Ye **Control Node group** hai.

Terraform `control` variable me jo instances hain, unke liye loop chalega.

Example generated output:

```ini
[control]
control-node-ubuntu ansible_connection=local ansible_user=ubuntu
```

### Important: `ansible_connection=local`

Ye bahut important hai.

Normally Ansible:

```text
Ansible
   ↓ SSH
Target
```

karta hai.

Lekin Control Node ke case me:

```text
Control Node
     ↓
  local
     ↓
Control Node
```

SSH ki zarurat nahi.

Because **Ansible khud Control Node par run ho raha hai**.

---

# 4. `[ubuntu_workers]`

```ini
[ubuntu_workers]
%{ for name, inst in ubuntu_workers ~}
${name} ansible_host=${inst.private_ip} ansible_user=${inst.user}
%{ endfor ~}
```

Ye Ubuntu worker machines ka group hai.

Important:

```text
${inst.private_ip}
```

Yahan **private IP** use ho raha hai.

Example:

```ini
[ubuntu_workers]
worker-ubuntu ansible_host=10.0.1.20 ansible_user=ubuntu
```

Why private IP?

Because:

```text
Control Node
     │
     │ private network
     ▼
Worker
```

Same VPC/network ke andar communication karna hai.

---

# 5. `[redhat]`

```ini
[redhat]
%{ for name, inst in redhat ~}
${name} ansible_host=${inst.private_ip} ansible_user=${inst.user}
%{ endfor ~}
```

Red Hat worker machines ka group.

Example:

```ini
[redhat]
worker-redhat ansible_host=10.0.1.21 ansible_user=ec2-user
```

---

# 6. `[amazon]`

```ini
[amazon]
%{ for name, inst in amazon ~}
${name} ansible_host=${inst.private_ip} ansible_user=${inst.user}
%{ endfor ~}
```

Amazon Linux instances ka group.

Example:

```ini
[amazon]
worker-amazon ansible_host=10.0.1.22 ansible_user=ec2-user
```

---

# 7. `[workers:children]`

```ini
[workers:children]
ubuntu_workers
redhat
amazon
```

Ye **group of groups** hai.

Instead of:

```text
workers
 ├── worker-ubuntu
 ├── worker-redhat
 └── worker-amazon
```

Aap groups ko combine kar rahe ho:

```text
workers
   │
   ├── ubuntu_workers
   ├── redhat
   └── amazon
```

Ab aap Ansible me simply:

```bash
ansible workers -m ping
```

run kar sakte ho.

Ansible tino groups ke hosts par command execute karega.

---

# 8. `[ubuntu:children]`

```ini
[ubuntu:children]
control
ubuntu_workers
```

Ye bhi group combination hai.

`ubuntu` group ke andar:

```text
ubuntu
 ├── control
 └── ubuntu_workers
```

So agar aap:

```bash
ansible ubuntu -m ping
```

run karoge, to:

```text
Control Node
+
Ubuntu Worker
```

dono target honge.

# Most important concept

Aapke project me **Public IP vs Private IP** intentionally different hai:

### Bootstrap

```text
Laptop
   ↓
Public IP
   ↓
Control Node
```

### Actual Ansible

```text
Control Node
   ↓
Private IP
   ↓
Workers
```

Ye architecture real-world DevOps practice ke liye bhi useful hai.

## Short notes

```text
inventory.tpl

- Template for actual Ansible inventory.
- Generated automatically by Terraform.
- Used FROM the Control Node.
- Control Node uses ansible_connection=local.
- Workers use PRIVATE IPs.
- ubuntu_workers → Ubuntu workers.
- redhat → RHEL workers.
- amazon → Amazon Linux workers.
- workers:children → combines all worker groups.
- ubuntu:children → combines control + Ubuntu workers.
- all:vars → common variables for all hosts.
```

### `bootstrap.tpl` vs `inventory.tpl`

| File            | Used from    | Target       | IP             |
| --------------- | ------------ | ------------ | -------------- |
| `bootstrap.tpl` | Laptop       | Control Node | **Public IP**  |
| `inventory.tpl` | Control Node | Workers      | **Private IP** |

Ye distinction aapke project ka **bahut important concept** hai.
