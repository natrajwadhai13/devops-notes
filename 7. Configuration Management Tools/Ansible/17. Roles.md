# 17. Roles

## Learning Objectives

After completing this chapter, you will be able to:

- Understand what Ansible Roles are.
- Learn the standard Role directory structure.
- Use defaults, vars, tasks, handlers, templates, files, and meta.
- Understand Role dependencies.
- Install and use Galaxy Roles.
- Follow Role best practices.

---

## What is a Role?

A **Role** is a standardized way to organize Playbooks, variables, templates, handlers, and files into reusable components.

Instead of writing one large Playbook, Roles divide automation into smaller, manageable parts.

Example:

```
Web Server Role
↓
Install Package
↓
Copy Configuration
↓
Start Service
↓
Restart if Needed
```

---

## Why Use Roles?

Without Roles

```
playbook.yml

1000+ lines
```

Hard to maintain.

---

With Roles

```bash
roles/

├── nginx/

├── mysql/

├── docker/

└── users/
```

Each Role performs one specific task.

---

## Benefits of Roles

- Reusable
- Organized
- Easy to maintain
- Easy to test
- Team collaboration
- Production-ready
- Scalable

---

# Create a Role

Generate a new Role using Ansible.

```bash
ansible-galaxy role init nginx

ansible-galaxy init role/docker
```

Example Output

```
roles/

└── nginx/

    ├── defaults/

    ├── files/

    ├── handlers/

    ├── meta/

    ├── tasks/

    ├── templates/

    ├── tests/

    ├── vars/
```

---

# tasks/

Contains the main automation tasks.

Example

```yaml
# tasks/main.yml

- name: Install Nginx

  package:
    name: nginx

    state: present
```

---

# handlers/

Contains Handlers triggered by `notify`.

Example

```yaml
# handlers/main.yml

- name: Restart Nginx

  service:
    name: nginx

    state: restarted
```

---

# defaults/

Stores default variable values.

Example

```yaml
# defaults/main.yml

http_port: 80

service_name: nginx
```

These variables have the **lowest precedence**.

---

# vars/

Stores variables that should rarely change.

Example

```yaml
# vars/main.yml

package_name: nginx
```

These variables have **higher precedence** than `defaults`.

---

# templates/

Stores Jinja2 templates.

Example

```
templates/

└── nginx.conf.j2
```

Deploy using:

```yaml
template:
  src: nginx.conf.j2

  dest: /etc/nginx/nginx.conf
```

---

# files/

Stores static files.

Example

```
files/

├── index.html

├── logo.png

└── banner.jpg
```

Copy using:

```yaml
copy:
  src: index.html

  dest: /var/www/html/index.html
```

---

# meta/

Stores Role metadata and dependencies.

Example

```yaml
# meta/main.yml

dependencies:
  - role: common

  - role: firewall
```

---

# Role Dependencies

A Role can automatically execute another Role before it runs.

Example

```
common

↓

firewall

↓

nginx
```

Useful when one Role depends on another.

---

# Using a Role

Playbook

```yaml
---
- hosts: web

  become: true

  roles:
    - nginx
```

Multiple Roles

```yaml
roles:
  - common

  - docker

  - nginx

  - monitoring
```

Roles execute from top to bottom.

---

# Role Execution Order

```
Playbook

↓

Role

↓

Tasks

↓

Handlers

↓

Complete
```

# Best Practices

- One Role should have one responsibility.
- Keep Roles small and reusable.
- Store defaults in `defaults/`.
- Store templates in `templates/`.
- Store static files in `files/`.
- Use Handlers instead of restarting services repeatedly.
- Keep Role names meaningful.
- Reuse community Roles when appropriate.

# Summary

- Roles organize Ansible code into reusable components.
- Each Role has a standard directory structure.
- `tasks/` contains automation tasks.
- `handlers/` contains service restart logic.
- `defaults/` stores default variables.
- `vars/` stores higher-precedence variables.
- `templates/` stores Jinja2 templates.
- `files/` stores static files.
- `meta/` defines Role dependencies.
- Ansible Galaxy provides reusable Roles and Collections.

# Ansible Roles

## 1. What are Ansible Roles?

**Ansible Roles** are a reusable and standardized way to organize Ansible playbooks.

Roles help us create **reusable templates/components** that can be used in multiple playbooks and projects.

### Main advantages

- ♻️ Reusable
- 📁 Well-organized directory structure
- 🧩 Easy to maintain
- 🔄 Can be used by multiple playbooks
- 📦 Can be shared with other users/projects
- 🛠️ Separates tasks, variables, handlers, templates, and files

---

# 2. Ansible Galaxy

**Ansible Galaxy** is used to **create, share, download, and manage Ansible roles and collections**.

The `ansible-galaxy` command can be used to create a role structure.

### Create a Role

```bash
ansible-galaxy init roles/docker
```

This command creates a complete role directory structure.

> **Note:** Ansible Galaxy is not simply a "package manager." It is a hub/ecosystem for Ansible content such as **roles and collections**, and `ansible-galaxy` is the CLI used to manage that content.

---

After running:


# 4. Important Role Directories

| Directory    | Purpose                                  |
| ------------ | ---------------------------------------- |
| `tasks/`     | Main tasks executed by the role          |
| `defaults/`  | Default variables; easy to override      |
| `vars/`      | Role variables with higher precedence    |
| `handlers/`  | Handlers such as restart/reload services |
| `files/`     | Static files copied to managed nodes     |
| `templates/` | Jinja2 templates                         |
| `meta/`      | Role metadata and dependencies           |
| `tests/`     | Basic role testing files                 |
| `README.md`  | Documentation                            |

### Most commonly used

```text
tasks/
defaults/
vars/
handlers/
templates/
files/
```

# 5. Docker Role Example

Suppose we want to create an Ansible role to install Docker.

Create the role:

```bash
ansible-galaxy init roles/docker
```

Our project can look like:

```text
project/
├── hosts.ini
├── playbooks/
│   └── install_docker_with_role.yml
└── roles/
    └── docker/
        ├── defaults/
        │   └── main.yml
        ├── handlers/
        │   └── main.yml
        ├── tasks/
        │   └── main.yml
        └── ...
```

---

# 6. Tasks

The main role tasks are written inside:

```text
roles/docker/tasks/main.yml
```

Example:

```yaml
---
# tasks file for role/docker

- name: Update system
  ansible.builtin.apt:
    name: "*"
    state: latest
    update_cache: true

- name: Install Docker.io
  ansible.builtin.apt:
    name: docker.io
    state: present

- name: Start and enable Docker
  ansible.builtin.service:
    name: docker
    state: started
    enabled: true

- name: Add users to Docker group
  ansible.builtin.user:
    name: "{{ item }}"
    groups: docker
    append: true
  loop: "{{ docker_users }}"
```

> **Important:** `tasks/main.yml` is the default entry point for tasks when the role is called.

---

# 7. Default Variables

Go to:

```bash
vi roles/docker/defaults/main.yml
```

Add:

```yaml
docker_users:
  - johnd
  - john
  - ubuntu
```

These variables can be used inside the role:

```yaml
loop: "{{ docker_users }}"
```

So Ansible will add:

```text
johnd
john
ubuntu
```

to the Docker group.

---

# 8. Handlers

Handlers are generally used for actions that should happen **when notified by a task**.

File:

```bash
vi roles/docker/handlers/main.yml
```

Example:

```yaml
---
# handlers file for role/docker

- name: Restart Docker
  ansible.builtin.service:
    name: docker
    state: restarted
  become: true
```

A task can trigger the handler:

```yaml
- name: Update Docker configuration
  ansible.builtin.template:
    src: docker.conf.j2
    dest: /etc/docker/daemon.json
  notify: Restart Docker
```

The handler runs only when the task reports a change.

---

# 9. Playbook Using the Role

Go to the playbook directory:

```bash
cd playbooks
```

Create:

```bash
vim install_docker_with_role.yml
```

Content:

```yaml
---
- name: Install Docker on Ubuntu
  hosts: servers
  become: true

  roles:
    - docker
```

Here:

```yaml
roles:
  - docker
```

means:

> Execute the `docker` role.

Ansible automatically looks for the role in its configured **roles paths**.

---

# 10. Important Role Location

A common project structure is:

```text
/root/playbooks/
├── hosts.ini
├── install_docker_with_role.yml
└── roles/
    └── docker/
        ├── defaults/
        ├── handlers/
        ├── tasks/
        └── ...
```

Then:

```yaml
roles:
  - docker
```

is sufficient.

### Don't unnecessarily use:

```yaml
roles:
  - ../docker
```

If Ansible says:

```text
ERROR! the role 'docker' was not found
```

check where the role actually exists.

You can check:

```bash
ansible-config dump | grep DEFAULT_ROLES_PATH
```

You can also check:

```bash
ansible-galaxy role list
```

---

# 11. Run the Playbook

From the appropriate directory:

```bash
ansible-playbook -i hosts.ini install_docker_with_role.yml
```

If your inventory is one directory above the playbook:

```bash
ansible-playbook -i ../hosts.ini install_docker_with_role.yml
```

Example project:

```text
/root/project/
├── hosts.ini
├── roles/
│   └── docker/
│       ├── defaults/
│       ├── handlers/
│       └── tasks/
└── playbooks/
    └── install_docker_with_role.yml
```

From `/root/project/playbooks`:

```bash
ansible-playbook -i ../hosts.ini install_docker_with_role.yml
```

# 12. Role Execution Flow

The overall flow is:

```text
ansible-galaxy
      │
      │ create role
      ▼
roles/docker/
      │
      ├── tasks/main.yml
      ├── defaults/main.yml
      ├── handlers/main.yml
      ├── templates/
      ├── files/
      └── vars/main.yml
      │
      ▼
install_docker_with_role.yml
      │
      │ roles:
      │   - docker
      ▼
Ansible executes Docker Role
      │
      ├── Update system
      ├── Install Docker
      ├── Start Docker
      └── Add users to Docker group
```

## Quick Revision

```text
Role
  ↓
Reusable Ansible component
  ↓
ansible-galaxy init
  ↓
roles/docker/
  ├── tasks/
  ├── defaults/
  ├── vars/
  ├── handlers/
  ├── templates/
  ├── files/
  └── meta/
  ↓
Playbook calls the role
  ↓
roles:
  - docker
```

**Key point to remember:**
`tasks/main.yml` = main tasks of the role
`defaults/main.yml` = default variables
`handlers/main.yml` = handlers
`templates/` = Jinja2 templates
`files/` = static files
`roles: - docker` = call the Docker role from a playbook.
