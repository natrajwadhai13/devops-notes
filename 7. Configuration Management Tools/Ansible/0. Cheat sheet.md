# 🚀 Ansible Cheat Sheet — Interview & Production

Ansible ko Kubernetes ki tarah **random commands** ke form me mat padho. Interview ke liye ise **Architecture → Inventory → Playbook → Variables → Tasks → Templates → Roles → Security → Production → Troubleshooting** order me samjho.

---

# 1. Ansible Fundamentals ⭐⭐⭐⭐⭐

| Keyword                    | Simple Interview Explanation                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Ansible** ⭐⭐⭐⭐⭐     | Ansible is an automation and configuration-management tool used to provision, configure, deploy, and manage servers and applications. |
| **Agentless** ⭐⭐⭐⭐⭐   | Ansible does not require an agent on managed Linux servers; it commonly connects using SSH.                                           |
| **Control Node** ⭐⭐⭐⭐  | The machine from which Ansible commands and playbooks are executed.                                                                   |
| **Managed Node** ⭐⭐⭐⭐  | The remote server that Ansible manages or configures.                                                                                 |
| **Automation** ⭐⭐⭐⭐    | Ansible automates repetitive infrastructure and application-management tasks.                                                         |
| **Idempotency** ⭐⭐⭐⭐⭐ | Running the same Ansible task multiple times should produce the same desired state without unnecessary changes.                       |
| **Declarative** ⭐⭐⭐⭐   | You define the desired configuration, and Ansible determines the required changes.                                                    |
| **YAML** ⭐⭐⭐⭐          | Ansible Playbooks are normally written in YAML because it is human-readable and easy to maintain.                                     |
| **Module** ⭐⭐⭐⭐⭐      | A module is a reusable unit of Ansible functionality that performs a specific operation on a managed node.                            |
| **Task** ⭐⭐⭐⭐⭐        | A Task is a single automation action that normally calls an Ansible module.                                                           |
| **Play** ⭐⭐⭐⭐          | A Play maps a group of hosts to a set of tasks.                                                                                       |
| **Playbook** ⭐⭐⭐⭐⭐    | A Playbook is a YAML file containing one or more Plays that define automation workflows.                                              |

# 3. Inventory ⭐⭐⭐⭐⭐

**Inventory defines which servers Ansible manages and how they are grouped.**

Example:

```ini id="0n0g0v"
[web]
web01
web02

[db]
db01

[app]
app01
app02
```

Important concepts:

| Keyword                  | Explanation                                                                |
| ------------------------ | -------------------------------------------------------------------------- |
| **Inventory File**       | Contains hosts and host groups managed by Ansible.                         |
| **Host**                 | Individual managed server.                                                 |
| **Group**                | Collection of hosts logically grouped together.                            |
| **Child Group**          | A group containing other groups.                                           |
| **Host Variables**       | Variables specific to a particular host.                                   |
| **Group Variables**      | Variables shared by all hosts in a group.                                  |
| **Dynamic Inventory** ⭐ | Inventory generated dynamically from cloud platforms such as AWS or Azure. |

---

# 4. Static vs Dynamic Inventory ⭐⭐⭐⭐

### Static Inventory

Manually maintained:

```text id="89hksk"
web01
web02
db01
```

### Dynamic Inventory

Hosts are discovered automatically from cloud/infrastructure sources.

Example:

```text id="7l2xgf"
AWS EC2
   ↓
Dynamic Inventory
   ↓
Ansible
```

Useful when infrastructure changes frequently.

# 5. Ad-Hoc Commands ⭐⭐⭐⭐

**Ad-hoc commands are one-line Ansible commands used for quick operational tasks without creating a Playbook.**

Example:

```bash id="l4jzcm"
ansible all -m ping
```

Check disk:

```bash id="z4a2ve"
ansible all -a "df -h"
```

Restart service:

```bash id="d0x6r1"
ansible web -m service -a "name=nginx state=restarted"
```

### Interview point

```text id="0f8ztr"
Ad-hoc → Quick/simple operation
Playbook → Reusable/structured automation
```

# 6. Modules ⭐⭐⭐⭐⭐

**Modules are the building blocks of Ansible automation.**

Common modules:

| Module                        | Purpose                                             |
| ----------------------------- | --------------------------------------------------- |
| `ansible.builtin.command`     | Executes a command without shell processing.        |
| `ansible.builtin.shell`       | Executes commands through a shell.                  |
| `ansible.builtin.copy`        | Copies files to managed nodes.                      |
| `ansible.builtin.template`    | Generates files using Jinja2 templates.             |
| `ansible.builtin.file`        | Manages files, directories, permissions, and links. |
| `ansible.builtin.package`     | Installs/manages packages in a generic way.         |
| `ansible.builtin.apt`         | Manages Debian/Ubuntu packages.                     |
| `ansible.builtin.yum` / `dnf` | Manages RPM-based packages.                         |
| `ansible.builtin.service`     | Manages services.                                   |
| `ansible.builtin.user`        | Creates/manages users.                              |
| `ansible.builtin.group`       | Creates/manages groups.                             |
| `ansible.builtin.uri`         | Performs HTTP/API requests.                         |
| `ansible.builtin.git`         | Clones and manages Git repositories.                |
| `ansible.builtin.unarchive`   | Extracts archives.                                  |
| `ansible.builtin.debug`       | Displays variables or messages during execution.    |
| `ansible.builtin.stat`        | Gets information about a file/path.                 |

# 7. Command vs Shell ⭐⭐⭐⭐⭐

### command

**Runs a command directly without a shell.**

```yaml id="t9v7v4"
- name: Check uptime
  ansible.builtin.command: uptime
```

### shell

**Runs the command through a shell and supports shell features such as pipes and redirects.**

```yaml id="9v5g1b"
- name: Check logs
  ansible.builtin.shell: cat /var/log/app.log | grep ERROR
```

### Interview answer

> "I prefer the command module when shell features are not required because it is safer and more predictable. I use shell when I specifically need shell functionality."

# 8. Task ⭐⭐⭐⭐⭐

**A Task is one unit of work inside a Play.**

Example:

```yaml id="m8f6xw"
tasks:
  - name: Install Nginx
    ansible.builtin.package:
      name: nginx
      state: present
```

---

# 9. Play ⭐⭐⭐⭐

**A Play connects a group of hosts with the tasks that should run on them.**

Example:

```yaml id="s7y7lq"
- name: Configure Web Servers
  hosts: web
  tasks:
    - name: Install Nginx
      ansible.builtin.package:
        name: nginx
        state: present
```

---

# 10. Playbook ⭐⭐⭐⭐⭐

**A Playbook is a YAML file containing one or more Plays and defines the complete automation workflow.**

Example:

```yaml id="jz4n0b"
- name: Configure web servers
  hosts: web

  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Start nginx
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

---

# 11. Variables ⭐⭐⭐⭐⭐

**Variables store reusable values that can change between hosts, environments, or executions.**

Example:

```yaml id="a4h3xv"
app_port: 8080
app_name: myapp
```

Use:

```yaml id="2kn6uq"
{ { app_port } }
```

---

# 12. Variable Precedence ⭐⭐⭐⭐⭐

Ansible has multiple variable sources, and when the same variable is defined in multiple places, precedence determines which value wins.

Important sources:

```text id="qf6e2p"
Role defaults
Group vars
Host vars
Play vars
Task vars
Extra vars
```

### Most important interview point

**Extra vars (`-e`) have very high precedence.**

Example:

```bash id="x8v5tb"
ansible-playbook deploy.yml -e "env=prod"
```

---

# 13. Facts ⭐⭐⭐⭐

**Facts are system information automatically gathered by Ansible from managed hosts.**

Examples:

```text id="8jv3nz"
OS
IP address
CPU
Memory
Hostname
Disk information
```

Access:

```yaml id="l0xqjz"
{{ ansible_facts['hostname'] }}
```

---

# 14. gather_facts ⭐⭐⭐⭐

By default, Ansible commonly gathers facts at the beginning of a Play.

```yaml id="q8s8cg"
gather_facts: true
```

Disable when unnecessary:

```yaml id="7f9z5p"
gather_facts: false
```

Useful when you want faster execution and do not need system facts.

---

# 15. Registers ⭐⭐⭐⭐

**`register` stores the output of a task in a variable so later tasks can use it.**

```yaml id="m3r8ds"
- name: Check service
  ansible.builtin.command: systemctl is-active nginx
  register: nginx_status
```

Then:

```yaml id="7j6j3e"
- ansible.builtin.debug:
    var: nginx_status
```

---

# 16. Conditionals — when ⭐⭐⭐⭐⭐

**`when` allows a task to execute only when a condition is true.**

```yaml id="x6z2fr"
- name: Install package on Ubuntu
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_facts['os_family'] == "Debian"
```

---

# 17. Loops ⭐⭐⭐⭐⭐

**Loops allow the same task to run for multiple values.**

```yaml id="z2u6c3"
- name: Install packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop:
    - nginx
    - git
    - curl
```

---

# 18. Handlers ⭐⭐⭐⭐⭐

**Handlers are special tasks that run only when notified, usually after a configuration change.**

Example:

```yaml id="s4xv4r"
- name: Update nginx config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx
```

Handler:

```yaml id="v6w7p3"
handlers:
  - name: Restart nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```

### Interview point

> Handler runs only when the notifying task reports a change.

# 22. Roles ⭐⭐⭐⭐⭐

**A Role is a standardized directory structure used to organize reusable Ansible automation.**

Typical structure:

```text id="z8s1cw"
roles/
└── nginx/
    ├── tasks/
    ├── handlers/
    ├── templates/
    ├── files/
    ├── vars/
    ├── defaults/
    ├── meta/
    └── README.md
```

### Why Roles?

```text id="k4j5t2"
Reusable
Maintainable
Modular
Easy to share
Easy to test
```

---

# 23. Role defaults vs vars ⭐⭐⭐⭐

### defaults/

Contains default values that are easier to override.

### vars/

Contains role variables with higher precedence.

Simple interview line:

> "I generally keep configurable defaults in `defaults/main.yml` and use `vars` for values that should have stronger precedence."

# 25. Collections ⭐⭐⭐⭐

# 26. Tags ⭐⭐⭐⭐

**Tags allow you to run only selected tasks from a Playbook.**

Example:

```yaml id="a4h1n8"
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present
  tags:
    - install
```

Run:

```bash id="9r6d3v"
ansible-playbook site.yml --tags install
```

# 27. Vault ⭐⭐⭐⭐⭐

**Ansible Vault encrypts sensitive data such as passwords, API keys, and credentials stored in Ansible files.**

Example:

```bash id="z6k8x0"
ansible-vault create secrets.yml
ansible-vault edit secrets.yml
ansible-vault encrypt secrets.yml
ansible-vault decrypt secrets.yml
```

---

# 28. Vault vs Cloud Secret Manager ⭐⭐⭐⭐

```text id="x3m7j1"
Ansible Vault
→ Encrypts secrets stored in Ansible files.

Azure Key Vault / AWS Secrets Manager
→ Centralized external secret management.
```

For enterprise environments, external secret managers are often preferred depending on architecture and compliance requirements.

# 29. Check Mode ⭐⭐⭐⭐⭐

**Check mode performs a dry run so you can see what Ansible would change without applying those changes.**

Very useful before production changes.

# 30. Diff Mode ⭐⭐⭐⭐

**Diff mode shows differences in files that Ansible plans to modify.**


# 31. Idempotency ⭐⭐⭐⭐⭐

This is one of the **most important Ansible interview concepts**.

Example:

```yaml id="y2n6q8"
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present
```

First run:

```text id="2e8d3j"
Changed
```

Second run:

```text id="9h4f6k"
Ok
```

Because the desired state is already achieved.

---

# 32. changed vs ok ⭐⭐⭐⭐

Ansible task output generally tells you whether:

```text id="u7f4k2"
ok      → No change required
changed → Something was changed
failed  → Task failed
skipped → Condition was false
unreachable → Host could not be contacted
```

# 43. failed_when ⭐⭐⭐⭐

**Allows you to define your own condition for when a task should be considered failed.**

Useful when a command returns a non-standard exit code.

---

# 44. changed_when ⭐⭐⭐⭐

**Controls whether Ansible should consider a task as changed.**

Very useful with `command` or `shell` tasks to maintain idempotent reporting.

---

# 45. ignore_errors ⭐⭐⭐

**Allows the Playbook to continue even if a task fails.**

Use carefully; blindly ignoring errors can hide real production problems.

---

# 46. Delegation ⭐⭐⭐⭐

**`delegate_to` runs a task on another host instead of the current target host.**

Example:

```yaml id="9j5t4c"

```

Useful for:

```text id="7c3v1m"

API calls
DNS changes
Central orchestration
```

---

# 47. run_once ⭐⭐⭐⭐

**Runs a task only once even when the Play targets multiple hosts.**

```yaml id="m5h8r2"
run_once: true
```

Useful for:

```text id="4b7p0v"

Creating shared resources
```

# 48. include vs import ⭐⭐⭐⭐

**Dynamic inclusion; loaded during execution.**


For interviews, understand the difference between **dynamic include vs static import**.


### 🔥 The 5 Ansible concepts you absolutely must be able to explain

**1. Idempotency** → Same playbook multiple times should not unnecessarily change the system.

**2. Inventory** → Defines which servers Ansible manages.

**3. Playbook** → Defines the automation workflow.

**4. Role** → Makes automation reusable and modular.

**5. Variable + Template** → Allows the same automation to work across Dev/QA/Prod with different configuration.

If these five are clear, then add **Vault + Handlers + `when` + loops + `become` + `serial` + troubleshooting + Terraform integration** for the senior-level interview.
