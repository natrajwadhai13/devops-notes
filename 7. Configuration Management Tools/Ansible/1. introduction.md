# Ansible Installation & Basic Setup

## What is Ansible?

Ansible is an **open-source automation tool** used for:

- Configuration Management
- Application Deployment
- Infrastructure Automation
- Cloud Automation (AWS, Azure, GCP)
- Server Provisioning

Ansible is **agentless**, which means no agent needs to be installed on the target servers.

---

# Why Do We Need Ansible?

Imagine you have **100 Linux servers**.

Without Ansible:

- Login to each server manually.
- Run the same commands repeatedly.
- Install software one server at a time.
- High chance of human errors.
- Takes a lot of time.

With Ansible:

- Write the task once.
- Execute it on all servers simultaneously.
- Save time.
- Reduce manual work.
- Keep all servers consistent.

### Benefits of Ansible

- Reduces **Time to Market**
- Faster server configuration
- Easy to manage multiple servers
- Agentless architecture
- Push-based automation
- Simple YAML syntax
- Easy to learn
- Open Source

---

# Push-Based Architecture

Ansible uses a **Push Mechanism**.

The Control Node pushes tasks to all managed servers.

```
              Control Node
                    │
      ┌─────────────┼─────────────┐
      │             │             │
      ▼             ▼             ▼
 Server-1      Server-2      Server-3
```

No agent is required on the target servers.

---

# Prerequisites

Before installing Ansible, make sure the following are available:

- Python 3 installed
- SSH service running
- SSH connectivity between servers
- Root or sudo access

> **Note:** Python must be installed on both the **Control Node** and the **Managed Nodes** because Ansible modules run using Python.

Check Python version:

```bash
python3 --version
```

Example:

```text
Python 3.12.3
```

---

# Jinja2 Template Engine

Ansible uses **Jinja2** for creating dynamic templates.

Jinja2 is commonly used to generate configuration files like:

- nginx.conf
- httpd.conf
- application.properties
- hosts file

Example:

```jinja
ServerName {{ hostname }}
```

---

# Copy Public Key to Managed Nodes

Add the public key to:

```bash
~/.ssh/authorized_keys
```

or use:

```bash
ssh-copy-id -i ansible-master-key.pub root@192.168.16.130
```

Repeat for every managed server.

---

# Test SSH Connectivity

```bash
ssh -i ansible-master-key root@192.168.16.130
```

If login works without a password, SSH is configured correctly.

---

# Inventory File

Create a new inventory file.

```bash
vi hosts.ini
```

Example:

```ini
[servers]
worker-node-1 ansible_host=192.168.16.130 ansible_user=root
worker-node-2 ansible_host=192.168.16.131 ansible_user=root
worker-node-3 ansible_host=192.168.16.132 ansible_user=root

[all:vars]
ansible_ssh_private_key_file=/root/ansible-master-key
ansible_python_interpreter=/usr/bin/python3
```

> **Note:** The correct variable name is `ansible_python_interpreter` (not `ansible_pythone_interpreter`).

# Module 1: Introduction to Ansible

## What is Ansible?

Ansible is an **open-source automation tool** used to automate IT tasks such as:

- Server configuration
- Application deployment
- Software installation
- User management
- Security patching
- Cloud provisioning (AWS, Azure, GCP)
- Infrastructure automation

Unlike many automation tools, Ansible **does not require an agent** to be installed on the target servers. It connects using **SSH** (Linux) or **WinRM** (Windows).

---

## Why Use Ansible?

- reduce the time to market by faster configartions
- We need to have a scalable approach to manage multipal servers
- Push based mechanisam- Agentless

Without Ansible:

- Login to each server manually.
- Run the same commands again and again.
- More chances of human error.
- Time-consuming.

With Ansible:

- Write the task once.
- Run it on hundreds of servers.
- Faster, consistent, and reliable.

---

## Real-Life Example

Imagine you have **100 Linux servers**.

You need to install **Apache** on all servers.

### Without Ansible

```bash
ssh server1
sudo yum install httpd

ssh server2
sudo yum install httpd

ssh server3
sudo yum install httpd
```

Repeat the same steps for all servers.

Time: **2-3 hours**

---

### With Ansible

```bash
ansible web -m yum -a "name=httpd state=present"
```

Time: **Less than 1 minute**

This is the power of automation.

# What is Configuration Management?

Configuration Management is the process of keeping all servers in the desired and consistent state.

It ensures every server has:

- Same software
- Same configuration
- Same users
- Same security settings
- Same packages

---

## Example

Server 1

- Apache Installed
- Java 17
- Docker Installed

Server 2

- Apache Installed
- Java 17
- Docker Installed

Server 3

- Apache Installed
- Java 17
- Docker Installed

All servers are identical.

This is called **Configuration Management**.

| Puppet    | ✅ Yes         | Puppet DSL  |

# Agent vs Agentless

## Agent

An agent is a small software installed on every server.

The management server communicates with this agent.

### Examples

- Puppet
- Chef

```
Management Server
        │
        │
   Agent Installed
        │
   Linux Server
```

---

## Agentless

No software needs to be installed on the target server.

Ansible connects directly using:

- SSH (Linux)
- WinRM (Windows)

```
Ansible Control Node
          │
      SSH / WinRM
          │
     Target Server
```

---

## Advantages of Agentless

- Easy setup
- Less maintenance
- Better security
- Faster deployment
- No extra software

---

## Interview Question

### Why is Ansible called Agentless?

Because Ansible does not require any software (agent) to be installed on the managed servers. It connects using SSH (Linux) or WinRM (Windows).

# Push vs Pull Architecture

## Push Architecture

The control server sends tasks to all target servers.

```
Control Node
      │
      ├────────► Server 1
      ├────────► Server 2
      ├────────► Server 3
```

Examples

- Ansible

---

## Pull Architecture

Servers periodically contact the management server and pull their configuration.

```
Server 1 ──► Management Server

Server 2 ──► Management Server

Server 3 ──► Management Server
```

Examples

- Puppet
- Chef

---

## Difference

| Push                     | Pull                  |
| ------------------------ | --------------------- |
| Control node sends tasks | Server requests tasks |
| Faster execution         | Runs on schedule      |
| Used by Ansible          | Used by Puppet/Chef   |

---

Main Components

```
             Ansible Control Node
                     │
         ┌───────────┴────────────┐
         │                        │
      Inventory               Playbooks
         │                        │
         └───────────┬────────────┘
                     │
              SSH / WinRM

     ┌───────────────┼───────────────┐
     │               │               │
 Linux Server     Linux Server   Windows Server
```

## Components

- Control Node
- Inventory
- Playbooks
- Modules
- Managed Nodes
- SSH
- WinRM

---

# Control Node

The machine where Ansible is installed.

It executes playbooks and sends tasks to target servers.

Examples

- Ubuntu Server
- RHEL Server
- Amazon Linux
- Azure VM

---

## Responsibilities

- Stores playbooks
- Stores inventory
- Runs automation
- Connects using SSH
- Collects results

---

# Managed Nodes

Managed Nodes are the target machines that Ansible controls.

Examples

- Linux Server
- Windows Server
- AWS EC2
- Azure VM
- GCP VM
- VMware VM

No Ansible installation is required on these servers.

---

# Inventory

Inventory is a file containing the list of servers managed by Ansible.

Example:

```ini
[web]
server1
server2

[db]
server3
```

Here:

- **web** is a group containing `server1` and `server2`.
- **db** is a group containing `server3`.

---

## Types of Inventory

### Static Inventory

Servers are manually added.

### Dynamic Inventory

Servers are automatically fetched from:

- AWS
- Azure
- VMware
- GCP

---

# Modules

Modules are small programs that perform specific tasks.

Think of a module as a ready-made command.

Examples:

| Module  | Purpose                   |
| ------- | ------------------------- |
| ping    | Check connectivity        |
| copy    | Copy files                |
| file    | Create/Delete files       |
| yum     | Install packages (RHEL)   |
| apt     | Install packages (Ubuntu) |
| service | Start/Stop services       |
| user    | Create users              |
| group   | Create groups             |
| shell   | Run shell commands        |
| command | Execute Linux commands    |

Example:

```bash
ansible all -m ping
```

---

# Plugins

Plugins extend Ansible's functionality.

Examples:

- Connection Plugin
- Callback Plugin
- Lookup Plugin
- Cache Plugin
- Inventory Plugin

Think of plugins as **extra features** that help Ansible work more efficiently.

---

# Collections

A Collection is a package containing reusable Ansible content.

It may include:

- Modules
- Roles
- Plugins
- Playbooks
- Documentation

Example:

```bash
ansible-galaxy collection install amazon.aws
```

This installs the AWS collection for managing AWS resources.

- Uses **SSH** for Linux and **WinRM** for Windows.

- Plugins add extra functionality.
- Collections group related Ansible content.
