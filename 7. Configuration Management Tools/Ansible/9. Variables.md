# What are Variables?

Variables are named values used to store data that can be reused throughout a Playbook.

Instead of hardcoding values, variables make Playbooks flexible and reusable.

Example:

```yaml
package_name: nginx
```

Instead of writing:

```yaml
name: nginx
```

You can write:

```yaml
name: "{{ package_name }}"
```

---

# Why Use Variables?

Benefits:

- Reusable
- Easy to maintain
- Avoid hardcoding
- Environment-specific configuration
- Dynamic Playbooks

---

# Variable Naming Rules

- Must start with a letter or `_`
- Can contain numbers
- Cannot contain spaces
- Case-sensitive

Valid

```yaml
package_name

http_port

app_version
```

Invalid

```yaml
package-name

1package

package name
```

---

# Playbook Variables

Variables defined inside a Playbook.

```yaml
vars:

  package_name: nginx

  service_name: nginx
```

Usage

```yaml
tasks:

- name: Install Package
  package:
    name: "{{ package_name }}"
```

---

# Inventory Variables

Variables defined in the Inventory.

Host Variable

```ini
web01 ansible_host=192.168.1.10 ansible_user=root
```

Group Variable

```ini
[web:vars]

http_port=80
```

Global Variable

```ini
[all:vars]

ansible_python_interpreter=/usr/bin/python3
```

---

# Variable Files

Store variables in separate YAML files.

Example

```yaml
# vars.yml

package_name: nginx

service_name: nginx
```

Load variables

```yaml
vars_files:

  - vars.yml
```

This keeps Playbooks clean and organized.

# Facts (Introduction)

Facts are automatically collected information about managed nodes.

Examples

```yaml
ansible_hostname

ansible_kernel

```

Display a fact

```yaml
- debug:
    var: ansible_hostname
```

# Magic Variables

Magic Variables are built-in variables created by Ansible.

Examples

```yaml
inventory_hostname

inventory_hostname_short

playbook_dir

groups

hostvars

ansible_play_hosts
```

Example

```yaml
- debug:
    var: inventory_hostname
```

---

# Prompt Variables

Prompt the user for input during Playbook execution.

```yaml
vars_prompt:

  - name: username
    prompt: Enter Username

  - name: password
    prompt: Enter Password
      private: yes
```

Run

```bash
ansible-playbook user.yml
```

The Playbook asks for input before execution.

---

# Extra Variables

Variables passed from the command line.

Example

```bash
ansible-playbook deploy.yml -e "package_name=httpd"
```

Multiple Variables

```bash
ansible-playbook deploy.yml \
-e "package=httpd version=2.4"
```

JSON Format

```bash
ansible-playbook deploy.yml \
-e '{"package":"httpd","version":"2.4"}'
```

---

# Default Variables

Default values can be provided when a variable is not defined.

```yaml
{{ package_name | default("nginx") }}
```

If `package_name` exists

Output

```text
nginx
```

If it does not exist

Output

```text
nginx
```

Change default

```yaml
{{ package_name | default("httpd") }}
```

---

# Registered Variables

Store task output for later use.

Example

```yaml
- name: Check Uptime
  command: uptime
  register: uptime_result
```

Display Output

```yaml
- debug:
    var: uptime_result.stdout
```

---

# Variable Precedence

When the same variable exists in multiple places, Ansible follows a precedence order.

Highest Priority

1. Extra Variables (`-e`)
2. Task Variables
3. Playbook Variables
4. Inventory Host Variables
5. Inventory Group Variables
6. Inventory `all:vars`
7. Role Defaults

Example

If

Inventory

```yaml
package_name: nginx
```

Command Line

```bash
ansible-playbook play.yml \
-e "package_name=httpd"
```

Result

```text
httpd
```

Extra Variables override Inventory Variables.

---

# Variable Filters

Uppercase

```yaml
{{ username | upper }}
```

Lowercase

```yaml
{{ username | lower }}
```

Length

```yaml
{{ users | length }}
```

Default

```yaml
{{ package_name | default("nginx") }}
```

# Best Practices

- Use meaningful variable names.
- Avoid hardcoded values.
- Store reusable variables in files.
- Use Inventory Variables for environment-specific settings.
- Use Extra Variables for temporary overrides.
- Keep secrets in **Ansible Vault**, not plain text.

---

# What are Facts?

**Facts** are pieces of information automatically collected by Ansible about a managed node before executing tasks.

Facts describe the current state of the system, such as:

- Hostname
- IP Address
- Operating System
- Distribution
- CPU Information
- Memory
- Disk Information
- Network Interfaces
- Kernel Version

Ansible gathers these details automatically using the **setup module**.

---

# Why are Facts Important?

Facts allow Playbooks to make intelligent decisions.

Examples:

- Install Apache on RHEL.
- Install Nginx on Ubuntu.
- Restart a service only if enough memory is available.
- Configure files based on hostname.
- Deploy different packages based on CPU architecture.

---

# Gather Facts

By default, Ansible collects Facts before running any tasks.

```yaml
- hosts: all
  gather_facts: true
```

Disable fact collection

```yaml
- hosts: all
  gather_facts: false
```

Disabling Facts makes Playbooks execute faster when system information is not required.

---

# How Gather Facts Works

```
Playbook Starts
       │
       ▼
Gather Facts
       │
       ▼
Facts Stored in Memory
       │
       ▼
Tasks Execute
```

---

# View All Facts

Display every collected Fact.

```bash
ansible all -m setup
```

This command may return hundreds of Facts.

---

# Filter Facts

Display only hostname.

```bash
ansible all -m setup -a "filter=ansible_hostname"
```

Operating System

```bash
ansible all -m setup -a "filter=ansible_distribution"
```

IP Address

```bash
ansible all -m setup -a "filter=ansible_default_ipv4"
```

Memory

```bash
ansible all -m setup -a "filter=ansible_memtotal_mb"
```

---

# Common Facts

| Fact | Description |
|------|-------------|
| ansible_hostname | Hostname |
| ansible_fqdn | Fully Qualified Domain Name |
| ansible_distribution | Operating System |
| ansible_distribution_version | OS Version |
| ansible_os_family | OS Family |
| ansible_kernel | Kernel Version |
| ansible_architecture | CPU Architecture |
| ansible_processor_vcpus | Number of CPUs |
| ansible_memtotal_mb | Total RAM |
| ansible_default_ipv4.address | Primary IP Address |
| ansible_default_ipv4.gateway | Default Gateway |

---

# Using Facts in Playbooks

Display Hostname

```yaml
- hosts: all
  tasks:

    - name: Display Hostname
      debug:
        var: ansible_hostname
```

Display Operating System

```yaml
- debug:
    msg: "{{ ansible_distribution }}"
```

Display IP Address

```yaml
- debug:
    msg: "{{ ansible_default_ipv4.address }}"
```

---

# Facts in Conditions

Install Apache on Red Hat

```yaml
- name: Install Apache
  dnf:
    name: httpd
    state: present
  when: ansible_os_family == "RedHat"
```

Install Nginx on Ubuntu

```yaml
- name: Install Nginx
  apt:
    name: nginx
    state: present
  when: ansible_os_family == "Debian"
```

This makes one Playbook work across multiple Linux distributions.

---

# Custom Facts

You can create your own Facts.

Create a directory

```bash
mkdir -p /etc/ansible/facts.d
```

Create a file

```bash
vim /etc/ansible/facts.d/company.fact
```

Example

```ini
[company]

department=DevOps

location=Pune
```

Run Setup Again

```bash
ansible all -m setup
```

Use the Custom Fact

```yaml
{{ ansible_local.company.department }}
```

Output

```text
DevOps
```

---

# Local Facts Structure

```
/etc/ansible/

└── facts.d/

      ├── company.fact

      ├── app.fact

      └── server.fact
```

---

# Fact Caching

Normally, Facts are collected every time a Playbook runs.

Fact Caching stores Facts so Ansible can reuse them instead of collecting them repeatedly.

Benefits:

- Faster Playbook execution
- Reduced network traffic
- Better performance
- Useful in large environments

---

# Enable Fact Caching

Example `ansible.cfg`

```ini
[defaults]

fact_caching=jsonfile

fact_caching_connection=/tmp/ansible_cache

fact_caching_timeout=86400
```

---

# Supported Cache Plugins

- jsonfile
- memory
- redis
- memcached

Redis is commonly used in enterprise environments.

---

# Refresh Facts

Collect Facts again.

```yaml
- setup:
```

---

# Disable Facts for Faster Execution

```yaml
- hosts: all

  gather_facts: false
```

Useful when the Playbook does not need any system information.

---

# Best Practices

- Disable `gather_facts` if Facts are not needed.
- Use Fact Caching in large environments.
- Use Facts instead of hardcoded values.
- Keep Custom Facts simple and meaningful.
- Use `setup` filters to retrieve only the required information.
