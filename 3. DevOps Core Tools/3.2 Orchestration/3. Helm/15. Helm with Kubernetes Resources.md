# Helm with Kubernetes Resources

Helm does not replace Kubernetes. Helm generates and manages Kubernetes resources from chart templates and values.

---

# 1. Common Kubernetes Resources ⭐⭐⭐⭐⭐

A typical Helm application chart may contain:

```text
Deployment
Service
ConfigMap
Secret
Ingress
ServiceAccount
HPA
PVC
Job / CronJob
Role / RoleBinding
Namespace
```

### Quick Overview

| Resource           | Purpose                         |
| ------------------ | ------------------------------- |
| Deployment         | Run and manage application Pods |
| Service            | Expose Pods through networking  |
| ConfigMap          | Non-sensitive configuration     |
| Secret             | Sensitive configuration         |
| Ingress            | HTTP/HTTPS routing              |
| ServiceAccount     | Pod identity                    |
| Role / RoleBinding | RBAC permissions                |
| PVC                | Persistent storage              |
| Job                | One-time task                   |
| CronJob            | Scheduled task                  |
| HPA                | Autoscaling                     |
| Namespace          | Resource isolation              |

---

# 2. Deployment ⭐⭐⭐⭐⭐

A Deployment usually controls:

- Replica count
- Container image
- Ports
- Resources
- Probes
- Environment configuration

Example Helm template:

```yaml
spec:
  replicas: { { .Values.replicaCount } }
```

The value can come from:

```yaml
replicaCount: 3
```

Helm renders:

```yaml
spec:
  replicas: 3
```

---

# 3. Service ⭐⭐⭐⭐⭐

A Service exposes application Pods through Kubernetes networking.

Example:

```yaml
spec:
  selector:
    app.kubernetes.io/name: { { include "myapp.name" . } }
```

The Service selector should match the labels on the Pods.

### Important

```text
Deployment
    ↓
Pods
    ↓
Service
    ↓
Application Network Access
```

---

# 4. ConfigMap and Secret ⭐⭐⭐⭐⭐

Helm can template both ConfigMaps and Secrets.

### ConfigMap

Used for **non-sensitive configuration**.

```text
ConfigMap
    ↓
Application Configuration
```

### Secret

Used for **sensitive configuration** such as credentials.

```text
Secret
    ↓
Sensitive Configuration
```

### Typical flow

```text
values.yaml
     ↓
ConfigMap / Secret
     ↓
Deployment
     ↓
Application
```

**Important:** Do not store sensitive source data directly in Git.

---

# 5. Ingress ⭐⭐⭐⭐⭐

Ingress is commonly used for HTTP/HTTPS routing.

Helm can make an Ingress resource conditional.

Example:

```yaml
{ { - if .Values.ingress.enabled } }
...
{ { - end } }
```

Values:

```yaml
ingress:
  enabled: true
```

This allows Ingress to be enabled or disabled through configuration.

---

# 6. Resource Requests and Limits ⭐⭐⭐⭐

Helm can template Kubernetes resource requests and limits.

Example:

```yaml
resources:
{{- toYaml .Values.resources | nindent 2 }}
```

Values can define:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

This allows different environments to use different resource configurations.

---

# 7. HPA — Horizontal Pod Autoscaler ⭐⭐⭐⭐⭐

Helm can template HPA configuration.

However:

> **Helm does not perform autoscaling. Kubernetes HPA performs the actual autoscaling.**

Flow:

```text
HPA
 ↓
Deployment
 ↓
Pods
```

For example:

```text
Minimum replicas → 2
Maximum replicas → 5
```

Kubernetes adjusts the number of Pods based on the configured scaling metrics.

---

# 8. Labels and Selectors ⭐⭐⭐⭐

Labels and selectors are important when managing Kubernetes resources.

For example:

```text
Deployment
   ↓
Pod Labels
   ↓
Service Selector
```

The labels and selectors must be consistent.

Helm's `_helpers.tpl` is useful for generating common names and labels centrally.

Example:

```yaml
metadata:
  labels:
    app.kubernetes.io/name: { { include "myapp.name" . } }
```

---

# 9. ServiceAccount and RBAC ⭐⭐⭐⭐

Helm can also manage Kubernetes identity and permissions.

### ServiceAccount

Provides an identity for Pods.

```text
Pod
 ↓
ServiceAccount
```

### Role / RoleBinding

Used for Kubernetes RBAC permissions.

```text
ServiceAccount
      ↓
RoleBinding
      ↓
Role
      ↓
Permissions
```

These resources are commonly included when an application needs access to Kubernetes APIs.

---

# 10. PVC — Persistent Storage ⭐⭐⭐⭐

A PersistentVolumeClaim can be managed through a Helm template.

Typical flow:

```text
PVC
 ↓
Persistent Storage
 ↓
Application
```

PVCs are useful when application data needs to persist beyond the lifecycle of individual Pods.

---

# 11. Job and CronJob ⭐⭐⭐⭐

Helm can also create batch workloads.

### Job

Used for a one-time task.

```text
Job
 ↓
Task
```

### CronJob

Used for scheduled tasks.

```text
CronJob
 ↓
Scheduled Job
 ↓
Task
```

Typical use cases include migrations, maintenance and scheduled processing.

---

# 12. Complete Helm → Kubernetes Flow ⭐⭐⭐⭐⭐

The overall process is:

```text
                    Helm Chart
                         │
              ┌──────────┴──────────┐
              │                     │
         values.yaml           templates/
              │                     │
              └──────────┬──────────┘
                         ↓
                  Helm Rendering
                         ↓
              Kubernetes Manifests
                         ↓
                 Kubernetes API
                         ↓
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
   Deployment         Service         ConfigMap
        ↓                                 ↓
      Pods                             Config
        │
        ├── Secret
        ├── PVC
        ├── HPA
        ├── ServiceAccount
        └── RBAC
                         ↓
                    Application
```

### Important Concept

Helm generates the Kubernetes manifests, while Kubernetes is responsible for running and reconciling the resources.


# 14. Debugging Helm + Kubernetes Resources ⭐⭐⭐⭐⭐

When a Helm deployment has problems, debug from the chart first and then check Kubernetes.

### Step 1 — Validate Chart

```bash
helm lint ./mychart
```

### Step 2 — Render Templates

```bash
helm template myapp ./mychart
```

### Step 3 — Dry Run

```bash
helm install myapp ./mychart \
  --dry-run --debug
```

### Step 4 — Deploy / Upgrade

```bash
helm upgrade --install myapp ./mychart
```

### Step 5 — Check Helm Release

```bash
helm status myapp
```

### Step 6 — Check Kubernetes Resources

```bash
kubectl get all
```

### Step 7 — Check Pods

```bash
kubectl get pods
```

### Step 8 — Describe Pod

```bash
kubectl describe pod <pod-name>
```

### Step 9 — Check Logs

```bash
kubectl logs <pod-name>
```

### Debugging Flow

```text
Helm Chart
    ↓
helm lint
    ↓
helm template
    ↓
--dry-run --debug
    ↓
Helm Release
    ↓
kubectl get
    ↓
kubectl describe
    ↓
kubectl logs
```

# 16. Quick Interview Revision ⭐⭐⭐⭐⭐

### Q: What does Helm deploy?

> Helm generates and manages Kubernetes resources from Chart templates and values.

### Q: Can Helm create a Deployment?

Yes.

```yaml
kind: Deployment
```

### Q: Can Helm create Services, ConfigMaps and Secrets?

Yes. Helm can template and deploy these Kubernetes resources.

### Q: How do you make a resource optional?

Use a condition:

```yaml
{ { - if .Values.ingress.enabled } }
...
{ { - end } }
```

### Q: How do you configure resources for different environments?

Use separate values files:

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

### Q: How does Helm handle application configuration?

Typically:

```text
values.yaml
    ↓
ConfigMap / Secret
    ↓
Deployment
    ↓
Application
```

### Q: Does Helm perform autoscaling?

No.

> Helm creates/configures the HPA; **Kubernetes HPA performs the actual autoscaling**.

### Q: Does Helm manage Kubernetes resources after deployment?

Yes.

> Helm tracks resources as part of a release, while Kubernetes is responsible for running and reconciling the resources.

### Q: What is the relationship between Deployment and Service?

> Deployment manages the Pods, while Service provides stable network access to those Pods using selectors.

### Q: What is the difference between ConfigMap and Secret?

> ConfigMap is generally used for non-sensitive configuration, while Secret is intended for sensitive configuration.

### Q: What is the purpose of HPA?

> HPA automatically adjusts the number of Pod replicas based on configured metrics.
