# Helm Hooks

## What are Hooks?

Hooks let a chart run Kubernetes resources at specific points in the Helm lifecycle.

Common hooks:

- `pre-install`
- `post-install`
- `pre-upgrade`
- `post-upgrade`
- `pre-delete`
- `post-delete`
- `pre-rollback`
- `post-rollback`

## Annotation

```yaml
metadata:
  annotations:
    "helm.sh/hook": pre-install
```

## Example Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    "helm.sh/hook": pre-upgrade
    "helm.sh/hook-delete-policy": hook-succeeded
```

## Hook Weight

Weights control ordering when multiple hooks run.

```yaml
"helm.sh/hook-weight": "0"
```

Lower weights run before higher weights for the same hook event.

## Delete Policy

Common values:

```text
before-hook-creation
hook-succeeded
hook-failed
```

## Typical Use Cases

- Database migrations
- Pre-deployment validation
- Post-deployment checks
- Cleanup tasks

## Important Warning

Hooks are powerful but should not be used for normal application resources. Keep hook jobs idempotent and make their cleanup behavior explicit.

## Debugging

```bash
helm get hooks <release>
kubectl get jobs
kubectl describe job <job>
kubectl logs job/<job>
```

# 1. What are Helm Hooks? ⭐⭐⭐⭐⭐

**Helm Hooks** allow you to run specific Kubernetes resources at particular points during a Helm operation.

For example:

```text id="h1"
helm install
     ↓
pre-install hook
     ↓
Install resources
     ↓
post-install hook
```

Hooks are useful when you need to perform an additional action **before or after** a Helm operation.

---

# 2. Why Helm Hooks are Used

Common use cases:

- Database migration
- Initialization tasks
- Pre-deployment validation
- Post-deployment testing
- Cleanup tasks
- Backup operations
- Initialization Jobs

Example:

```text id="h2"
Helm Upgrade
     ↓
Run DB migration
     ↓
Deploy new application
```

---

# 3. Hook Annotation ⭐⭐⭐⭐⭐

Helm identifies a Hook using an annotation:

```yaml id="h3"
metadata:
  annotations:
    "helm.sh/hook": pre-install
```

Example:

```yaml id="h4"
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    "helm.sh/hook": pre-install
```

This tells Helm:

> Run this Job as a `pre-install` hook.

---

# 4. `pre-install` ⭐⭐⭐⭐⭐

Runs **before the main application resources are installed**.

Example:

```yaml id="h5"
metadata:
  annotations:
    "helm.sh/hook": pre-install
```

Flow:

```text id="h6"
helm install
     ↓
pre-install Hook
     ↓
Deployment
Service
ConfigMap
...
```

### Example use

Database initialization:

```text id="h7"
pre-install
    ↓
Create database schema
    ↓
Deploy application
```

---

# 5. `post-install` ⭐⭐⭐⭐⭐

Runs **after the application resources are installed**.

```yaml id="h8"
metadata:
  annotations:
    "helm.sh/hook": post-install
```

Flow:

```text id="h9"
helm install
     ↓
Deploy application
     ↓
post-install Hook
```

Possible use:

- Run smoke tests
- Initialize additional configuration
- Perform post-deployment tasks

---

# 6. `pre-upgrade` ⭐⭐⭐⭐

Runs before Helm performs an upgrade.

```yaml id="h10"
metadata:
  annotations:
    "helm.sh/hook": pre-upgrade
```

Flow:

```text id="h11"
helm upgrade
     ↓
pre-upgrade Hook
     ↓
Upgrade application
```

Example:

```text id="h12"
Run database migration
        ↓
Upgrade application
```

---

# 7. `post-upgrade` ⭐⭐⭐⭐

Runs after the upgrade.

```yaml id="h13"
metadata:
  annotations:
    "helm.sh/hook": post-upgrade
```

Flow:

```text id="h14"
helm upgrade
     ↓
Upgrade resources
     ↓
post-upgrade Hook
     ↓
Smoke test
```

---

# 8. `pre-delete`

Runs before a release is deleted.

```yaml id="h15"
metadata:
  annotations:
    "helm.sh/hook": pre-delete
```

Flow:

```text id="h16"

     ↓
pre-delete Hook
     ↓

```

Possible use:

- Backup
- Cleanup
- External resource handling

# 13. Complete Hook Example ⭐⭐⭐⭐⭐

A database migration Job can be created as a `pre-upgrade` hook.

```yaml id="h27"
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    "helm.sh/hook": pre-upgrade
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migration
          image: myapp:1.0
          command:
            - /bin/sh
            - -c
            - ./migrate.sh
```

When:

```bash id="h28"
helm upgrade myapp ./mychart
```

Helm runs the migration Job before completing the upgrade.

---

# 14. Multiple Hook Events

A resource can be associated with multiple hook events.

Example:

```yaml id="h29"
metadata:
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade
```

This means the hook can run during:

```text id="h30"
helm install
    OR
helm upgrade
```

---

# 15. Hook Weight ⭐⭐⭐⭐

If multiple hooks exist for the same event, you can control their execution order using:

```yaml id="h31"
"helm.sh/hook-weight": "1"
```

Example:

```yaml id="h32"
annotations:
  "helm.sh/hook": pre-install
  "helm.sh/hook-weight": "1"
```

Another hook:

```yaml id="h33"
annotations:
  "helm.sh/hook": pre-install
  "helm.sh/hook-weight": "2"
```

The lower weight is processed before the higher weight.

Conceptually:

```text id="h34"
Weight -1
   ↓
Weight 0
   ↓
Weight 1
```

This is useful when hooks have dependencies on each other.

---

# 16. Hook Delete Policy ⭐⭐⭐⭐⭐

Helm provides:

```text id="h35"
helm.sh/hook-delete-policy
```

This controls when Helm deletes hook resources.

Example:

```yaml id="h36"
metadata:
  annotations:
    "helm.sh/hook": post-install
    "helm.sh/hook-delete-policy": hook-succeeded
```

This means:

> Delete the hook resource after it succeeds.

---

# 17. Common Hook Delete Policies

### `hook-succeeded`

Delete after successful execution.

```yaml id="h37"
"helm.sh/hook-delete-policy": hook-succeeded
```

### `hook-failed`

Delete after failure.

```yaml id="h38"
"helm.sh/hook-delete-policy": hook-failed
```

### `before-hook-creation`

Delete an existing hook resource before creating a new one.

```yaml id="h39"
"helm.sh/hook-delete-policy": before-hook-creation
```

Multiple policies can be specified:

```yaml id="h40"
"helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
```

# 18. Hook Jobs ⭐⭐⭐⭐⭐

Most practical Helm Hooks use Kubernetes **Jobs**.

Example:

```text id="h41"
Helm Hook
    ↓
Kubernetes Job
    ↓
Run task
    ↓
Job completes
    ↓
Helm continues
```

Common tasks:

- Database migration
- Data initialization
- Validation
- Smoke testing

---

# 19. Hook Failure ⭐⭐⭐⭐

Suppose a `pre-install` Job fails:

```text id="h42"
helm install
     ↓
pre-install Job
     ↓
FAILED
```

Helm may stop the operation because the required hook did not complete successfully.

Therefore, hook Jobs should be designed carefully.

A failed migration hook can prevent an application deployment.

---

# 20. Hook vs Normal Kubernetes Resource ⭐⭐⭐⭐⭐

### Normal resource

```yaml id="h43"
apiVersion: apps/v1
kind: Deployment
```

It is managed as part of the normal Helm release.

### Hook resource

```yaml id="h44"
annotations:
  "helm.sh/hook": pre-install
```

It participates in a specific Helm lifecycle event.

Easy way to remember:

```text id="h45"
Normal Resource
    ↓
Part of Release

Hook Resource
    ↓
Runs at specific Helm lifecycle event
```

---

# 21. Important Hook Behavior

A Hook is **not simply an ordinary resource that Helm creates at the normal point in the release lifecycle**.

Hooks are executed according to their lifecycle event and ordering rules.

For example:

```text id="h46"
pre-install Hook
      ↓
Main resources
      ↓
post-install Hook
```

# 22. Real-World Database Migration Example ⭐⭐⭐⭐⭐

Suppose version 1 of your application uses:

```text id="h47"
users
```

Version 2 requires:

```text id="h48"
users
orders
```

Before deploying version 2, you need to create the `orders` table.

You can use:

```text id="h49"
pre-upgrade Hook
       ↓
Database Migration
       ↓
Application Upgrade
```

This is a common reason for using Helm Hooks.

A CI/CD deployment could look like:

```text id="h50"

   ↓
CI Pipeline
   ↓
Helm Upgrade
   ↓
pre-upgrade Hook
   ↓
Database Migration
   ↓
Application Upgrade
   ↓
post-upgrade Hook
   ↓
Smoke Test
```

This allows deployment-related tasks to be included in the Helm Chart.

---

# 24. Helm Hooks + Argo CD ⭐⭐⭐⭐

Since you are learning Argo CD, know this concept.

When Argo CD deploys a Helm application, Helm hooks can have corresponding GitOps/Argo CD lifecycle behavior depending on the hook and configuration.

However, in an Argo CD environment, it is important to understand **Argo CD resource hooks** separately from **Helm hooks**.

Do not assume that every Helm hook behaves exactly like a native Argo CD hook.

For interviews, remember:

```text id="h51"
Helm Hook
    ↓
Helm lifecycle

Argo CD Hook
    ↓
Argo CD sync lifecycle
```

# 25. When Should You Use Helm Hooks? ⭐⭐⭐⭐⭐

Good use cases:

```text id="h52"
Database migration
Initialization Job
Pre-deployment validation
Post-deployment smoke test
Cleanup operation
```

Avoid using Hooks for everything.

For normal Kubernetes resources, use normal templates.

# 26. Common Hook Problems

### Problem 1 — Hook Job remains

The Job may remain after execution.

Use:

```yaml id="h53"
"helm.sh/hook-delete-policy": hook-succeeded
```

---

### Problem 2 — Hook runs in wrong order

Use:

```yaml id="h54"
"helm.sh/hook-weight": "-1"
```

and appropriate weights for other hooks.

---

# 29. Complete Hook Workflow ⭐⭐⭐⭐⭐

```text id="h64"
helm upgrade
      │
      ↓
pre-upgrade Hook
      │
      ├── Success → Continue
      │
      └── Failure → Deployment may fail/stop
      │
      ↓
Upgrade Kubernetes Resources
      │
      ↓
post-upgrade Hook
      │
      ↓
Hook Cleanup
```

---

# 30. Important Best Practices ⭐⭐⭐⭐⭐

### 1. Keep hooks small

A Hook should perform a specific task.

### 2. Use Jobs for one-time operations

Good for:

```text id="h65"
Migration
Initialization
Validation
```

### 3. Use delete policies

For temporary Jobs:

```yaml id="h66"
"helm.sh/hook-delete-policy": hook-succeeded
```

### 4. Make migrations safe

Database migrations should ideally be designed to handle retries/failures safely.

### 5. Don't overuse hooks

Normal application resources should remain normal Helm templates.
