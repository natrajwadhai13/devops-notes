# Validation and Debugging

## Recommended Workflow

```text
helm lint
   ↓
helm template
   ↓
helm install --dry-run --debug
   ↓
helm install / upgrade
   ↓
helm status
   ↓
kubectl get pods
   ↓
kubectl describe / logs / events
```

## helm lint

```bash
helm lint ./mychart
```

Checks chart structure and common chart problems.

## helm template

Render templates locally:

```bash
helm template myapp ./mychart
helm template myapp ./mychart -f values-prod.yaml
```

Useful when the problem is in Helm rendering.

## Dry Run

```bash
helm install myapp ./mychart --dry-run --debug
```

Previews an installation without actually creating the resources.

## Check Release

```bash
helm status myapp
helm history myapp
helm get manifest myapp
helm get all myapp
```

## Kubernetes Debugging

```bash
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
kubectl get events --sort-by=.lastTimestamp
kubectl get svc
kubectl get ingress
```

## Common Problems

### YAML Parse Error
Usually caused by bad indentation or invalid rendered YAML.

### nil pointer
Usually means a referenced value does not exist or the template path is wrong.

### ImagePullBackOff
Check image repository/tag and registry access.

### CrashLoopBackOff
Check pod logs, configuration, environment variables, and events.

### Service Not Working
Check service selector, endpoints, target port, and pod labels.

## Key Difference

`helm template` = render locally.

`helm install --dry-run --debug` = simulate an install and inspect the rendered output/context.

# 1. Why Helm Validation is Important ⭐⭐⭐⭐⭐

Before deploying a Helm Chart to Kubernetes, you should verify that:

* Chart structure is correct
* Templates are valid
* Values are correct
* YAML is properly generated
* Kubernetes resources are valid
* No configuration is missing

A good workflow is:

```text id="0j7b9g"
Write Chart
    ↓
helm lint
    ↓
helm template
    ↓
helm install --dry-run --debug
    ↓
Deploy
    ↓
Check Kubernetes resources
```

# 2. `helm lint` ⭐⭐⭐⭐⭐

`helm lint` checks a Helm Chart for possible problems.

```bash id="v3d2r7"
helm lint ./mychart
```

Example:

```text id="3c8p9h"
==> Linting ./mychart
[INFO] Chart.yaml: icon is recommended
1 chart(s) linted, 0 chart(s) failed
```

### What does it check?

It can detect issues such as:

* Invalid Chart structure
* Template problems
* Incorrect Chart metadata
* Some YAML/template errors
* Missing required information

### Important

`helm lint` is a **static validation** step.

It does not actually deploy the application.

---

# 3. `helm template` ⭐⭐⭐⭐⭐

`helm template` renders the Helm templates locally.

```bash id="t2l9g4"
helm template myapp ./mychart
```

It generates the Kubernetes YAML that Helm would produce.

Example:

```text id="hj4t5c"
values.yaml
    +
templates/deployment.yaml
    +
templates/service.yaml
    ↓
helm template
    ↓
Rendered Kubernetes YAML
```

This is one of the **most important debugging commands**.

---

# 4. Template with Custom Values

If you use a production values file:

```bash id="q0g3za"
helm template myapp ./mychart \
  -f values-prod.yaml
```

You can check exactly what will be generated for production.

---

# 5. `helm install --dry-run` ⭐⭐⭐⭐⭐

`--dry-run` simulates an installation without actually deploying resources.

```bash id="6y8f9s"
helm install myapp ./mychart --dry-run
```

This is useful before a real deployment.

---

# 6. `--debug` ⭐⭐⭐⭐⭐

Use `--debug` to get additional information.

```bash id="h5qz7v"
helm install myapp ./mychart \
  --dry-run \
  --debug
```

Very useful when troubleshooting:

* Template errors
* Values problems
* Rendering problems
* Release installation issues

---

# 7. `helm template` vs `--dry-run`

This is an important interview question.

### `helm template`

```bash id="hjh9sc"
helm template myapp ./mychart
```

Main purpose:

```text id="c3jv5m"
Render templates locally
```

### `helm install --dry-run`

```bash id="2r3k83"
helm install myapp ./mychart --dry-run
```

Main purpose:

```text id="5c7s6e"
Simulate a Helm installation
```

### Easy way to remember

```text id="u4e0ya"
helm template
     ↓
"What YAML will Helm generate?"

helm install --dry-run
     ↓
"What would happen if I installed this?"
```

# 8. Validate Rendered Kubernetes YAML ⭐⭐⭐⭐⭐

After rendering:

```bash id="gl4i9j"
helm template myapp ./mychart
```

Check:

* `apiVersion`
* `kind`
* `metadata`
* `spec`
* indentation
* names
* labels
* selectors
* container image
* ports
* resources

Example:

```yaml id="m9x7hp"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
```

The generated output should be valid Kubernetes YAML.

# 9. Check Release Status ⭐⭐⭐⭐⭐

After deployment:

```bash id="qk1nyn"

```

Example:

```text id="yb8b3k"

NAMESPACE: default
STATUS: deployed
REVISION: 1
```

If status is:

```text id="jpkx7q"

```

you need to investigate further.

Use:

```bash id="8gyh8k"

```

Example:

```text id="b8g8mx"

1          superseded
2          deployed

```

# 11. Check Deployed Manifest ⭐⭐⭐⭐⭐

```bash id="s4jtx0"

```

This shows the Kubernetes manifests generated for the installed release.

Compare:

```text id="yqg5kn"
Expected Template
       ↓

       ↓
```

This can help identify configuration differences.

Start with:

```bash id="2z8d6q"

```

Then:

```bash id="h88l4d"
kubectl get deployment
```

```bash id="5z1e2v"
kubectl get service
```

```bash id="qpjfcm"
kubectl get ingress
```

For all resources:

```bash id="0p2h5v"
kubectl get all
```

# 14. Check Pod Status

```bash id="c7yn2b"
kubectl get pods
```

Possible statuses:

```text id="v4b8qg"
Running
Pending
CrashLoopBackOff
ImagePullBackOff
ErrImagePull
Completed
```

These statuses give the first clue about the problem.

# 15. Describe a Pod ⭐⭐⭐⭐⭐

If a Pod is failing:

```bash id="s7i2zq"
kubectl describe pod <pod-name>
```

Look especially at:

```text id="t2b5jh"
Events
```

Events can reveal:

* Image pull errors
* Scheduling problems
* Resource issues
* Mount errors
* Configuration errors
* Probe failures

---

# 16. Check Pod Logs ⭐⭐⭐⭐⭐

For application errors:

```bash id="x8f5d1"
kubectl logs <pod-name>
```

For a specific container:

```bash id="n6b6ak"
kubectl logs <pod-name> -c <container-name>
```

For previous crashed container:

```bash id="7wy3j0"
kubectl logs <pod-name> --previous
```

This is very useful for:

```text id="x1l2ep"
CrashLoopBackOff
```

---

# 17. Check Events ⭐⭐⭐⭐⭐


```bash id="kn2zcn"
kubectl get events --sort-by=.lastTimestamp
```

Events can show:

```text id="k8p3d0"

FailedMount
```

# 18. Common Helm Error: YAML Parse Error

Example:

```text id="g5j9nd"
YAML parse error
```

Common causes:

* Incorrect indentation
* Missing `:`
* Incorrect template syntax
* Wrong `if/end`
* Wrong `range/end`

Debug with:

```bash id="2w6d4x"
helm template myapp ./mychart
```

---

# 19. Common Error: Wrong Values

Suppose `values.yaml` contains:

```yaml id="x8c7z7"
replicaCount: 3
```

But template uses:

```yaml id="j9m2o8"
replicas: {{ .Values.replicas }}
```

The names don't match.

Correct:

```yaml id="2xj9mg"
replicas: {{ .Values.replicaCount }}
```

Check your values with:

```bash id="1j8j5p"
helm get values myapp
```

---

# 20. Common Error: Template Not Found

Example:

```text id="eq6d0c"
no template "myapp.labels" associated with template
```

Check `_helpers.tpl`:

```yaml id="x1cyx5"
{{- define "myapp.labels" -}}
...
{{- end }}
```

And the usage:

```yaml id="t3j5oj"
{{ include "myapp.labels" . }}
```

Make sure the names match exactly.

---

# 21. Common Error: `nil pointer`

Example:

```text id="b3q5hr"
nil pointer evaluating interface
```

Usually caused by accessing a value that doesn't exist.

Example:

```yaml id="6j1bpy"
{{ .Values.image.repository }}
```

but `image` isn't defined.

Possible solutions:

```yaml id="t1p6tq"
image:
  repository: nginx
```

or use appropriate defaults/validation.

---

# 22. Common Error: `ImagePullBackOff`

Helm may successfully install the release, but Kubernetes may fail to start the Pod.

Check:

```bash id="5bqf5j"
kubectl get pods
```

Then:

```bash id="qv3y0w"
kubectl describe pod <pod-name>
```

Common causes:

* Wrong image name
* Wrong image tag
* Private registry authentication problem
* Image doesn't exist

Check the generated image:

```bash id="9m0h6q"
helm get manifest myapp
```

---

# 23. Common Error: `CrashLoopBackOff`

The container starts but repeatedly crashes.

Check:

```bash id="ql9s4h"
kubectl logs <pod-name>
```

If it restarted:

```bash id="x4y4pi"
kubectl logs <pod-name> --previous
```

Also:

```bash id="2p0cvv"
kubectl describe pod <pod-name>
```

Common causes:

* Application configuration problem
* Missing environment variable
* Database connection failure
* Incorrect command/entrypoint
* Application startup failure

---

# 24. Common Error: Service Not Working

Check:

```bash id="9w3h6e"
kubectl get service
```

Then:

```bash id="n1i7h9"
kubectl describe service <service-name>
```

Check Endpoints:

```bash id="c4p1d9"
kubectl get endpoints
```

Also verify Pod labels:

```bash id="4p3k5d"
kubectl get pods --show-labels
```

A common problem is:

```text id="kzq5h1"
Service selector
       ≠
Pod labels
```

Then the Service has no endpoints.

---

# 25. Common Error: Ingress Not Working

Check:

```bash id="6i3u2w"
kubectl get ingress
```

Then:

```bash id="m7g1w8"
kubectl describe ingress <ingress-name>
```

Verify:

* Host
* Path
* Service name
* Service port
* Ingress Controller
* DNS

Also inspect the rendered Helm configuration:

```bash id="9z8t5w"
helm get manifest myapp
```

# 27. Complete Helm Debugging Workflow ⭐⭐⭐⭐⭐

Use this sequence in real projects:

```text id="5k3m1p"
1. helm lint
       ↓
2. helm template
       ↓
3. helm install --dry-run --debug
       ↓
4. helm install / helm upgrade
       ↓
5. helm status
       ↓
6. helm get values
       ↓
7. helm get manifest
       ↓
8. kubectl get pods
       ↓
9. kubectl describe pod
       ↓
10. kubectl logs
       ↓
11. kubectl get events
       ↓
12. Fix Chart / Values
       ↓
13. helm upgrade
```

# 28. Production Troubleshooting Example ⭐⭐⭐⭐⭐

Suppose you deploy:

```bash id="q6q5gh"
helm upgrade --install myapp ./mychart \
  -n production \
  -f values-prod.yaml
```

But the application doesn't work.

### Step 1 — Check Helm

```bash id="4f50eq"
helm status myapp -n production
```

### Step 2 — Check Pods

```bash id="4n3wzv"
kubectl get pods -n production
```

### Step 3 — Describe failing Pod

```bash id="7c7sh2"
kubectl describe pod <pod-name> -n production
```

### Step 4 — Check Logs

```bash id="hj5b99"
kubectl logs <pod-name> -n production
```

### Step 5 — Check Events

```bash id="f9z1w5"
kubectl get events -n production --sort-by=.lastTimestamp
```

### Step 6 — Check Helm values

```bash id="m8k7x4"
helm get values myapp -n production
```

### Step 7 — Check deployed manifest

```bash id="3z5x7v"
helm get manifest myapp -n production
```

### Step 8 — Fix and upgrade

```bash id="3m9x2w"
helm upgrade myapp ./mychart \
  -n production \
  -f values-prod.yaml
```

# 29. Validation vs Debugging

### Validation

Before deployment:

```text id="b2d5f7"
helm lint
helm template
helm install --dry-run --debug
```

Purpose:

```text id="7p7z1x"
Find problems before deployment
```

### Debugging

After deployment:

```text id="m4q7j6"
helm status
helm get values
helm get manifest
kubectl get pods
kubectl describe
kubectl logs
kubectl get events
```

Purpose:

```text id="6f9s5k"
Find problems in the running application
```

### ⭐ Must Remember

```text id="v5h8y4"
BEFORE DEPLOYMENT
─────────────────
helm lint
     ↓
helm template
     ↓
helm install --dry-run --debug


AFTER DEPLOYMENT
────────────────
helm status
     ↓
helm get values
     ↓
helm get manifest
     ↓
kubectl get pods
     ↓
kubectl describe
     ↓
kubectl logs
     ↓
kubectl get events
```

**Golden rule:** If Helm deployment succeeds but the application fails, **don't assume Helm is the problem**. Check the Kubernetes resources, Pod events, and application logs.
