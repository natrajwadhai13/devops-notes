# values.yaml and Configuration

## Why values.yaml?

It separates **configuration** from **template logic**.

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  port: 80
```

Use values inside templates:

```yaml
replicas: {{ .Values.replicaCount }}
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

## Override with a Values File

```bash
helm install myapp ./mychart -f values-dev.yaml
helm upgrade myapp ./mychart -f values-prod.yaml
```

## Override with --set

```bash
helm install myapp ./mychart --set replicaCount=3
```

## Multiple Values Files

```bash
helm upgrade myapp ./mychart   -f values.yaml   -f values-prod.yaml
```

Later values override earlier values.

## Practical Precedence

A useful simplified rule is:

```text
chart defaults
   ↓
values files
   ↓
--set / command-line overrides
```

## Best Practices

- Keep sensible defaults in `values.yaml`
- Use environment-specific values files
- Avoid hardcoding environment configuration in templates
- Use meaningful value names
- Do not put production secrets in plain text

## Useful Commands

```bash
helm show values <chart>
helm get values <release>
helm get values <release> --all
```

## 1. What is `values.yaml`?

`values.yaml` is the **default configuration file of a Helm Chart**.

It stores configurable values that are used by templates.

Example:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80
```

The template can access these values using:

```yaml
{{ .Values.replicaCount }}
```

---

## 2. Why `values.yaml` is Used ⭐⭐⭐⭐⭐

The main purpose is to **separate configuration from Kubernetes templates**.

Without values:

```yaml
replicas: 2
image: nginx
port: 80
```

These values are hardcoded inside templates.

With Helm:

```text
values.yaml
     ↓
Configuration

templates/
     ↓
Kubernetes resources
```

This makes the Chart:

* Reusable
* Configurable
* Environment-independent
* Easier to maintain
* Suitable for CI/CD

---

## 3. Default Values

`values.yaml` contains default values.

Example:

```yaml
replicaCount: 2
```

Template:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
```

Generated Kubernetes YAML:

```yaml
spec:
  replicas: 2
```

If no custom value is provided, Helm uses the value from `values.yaml`.

---

# 4. The `.Values` Object ⭐⭐⭐⭐⭐

Helm provides a special object called:

```text
.Values
```

It is used to access values defined in `values.yaml`.

Example:

```yaml
replicaCount: 3
```

Access it:

```yaml
{{ .Values.replicaCount }}
```

---

## 5. Nested Values

Values can be organized into nested structures.

Example:

```yaml
image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent
```

Access them:

```yaml
{{ .Values.image.repository }}
```

```yaml
{{ .Values.image.tag }}
```

```yaml
{{ .Values.image.pullPolicy }}
```

This makes large configuration files easier to manage.

---

# 6. Using Values in Deployment

`values.yaml`:

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: "1.27"
```

`templates/deployment.yaml`:

```yaml
spec:
  replicas: {{ .Values.replicaCount }}

  containers:
    - name: nginx
      image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Helm generates:

```yaml
spec:
  replicas: 3

  containers:
    - name: nginx
      image: "nginx:1.27"
```

# 7. Custom Values File ⭐⭐⭐⭐⭐

You don't have to modify the main `values.yaml` for every environment.

Create:

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

Example:

### `values-dev.yaml`

```yaml
replicaCount: 1

image:
  tag: "1.27"
```

### `values-prod.yaml`

```yaml
replicaCount: 5

image:
  tag: "1.28"
```

Deploy Dev:

```bash
helm install myapp ./mychart -f values-dev.yaml
```

Deploy Production:

```bash
helm install myapp ./mychart -f values-prod.yaml
```

---

# 8. `-f` / `--values` ⭐⭐⭐⭐⭐

Both commands are equivalent:

```bash
helm install myapp ./mychart -f values-prod.yaml
```

and:

```bash
helm install myapp ./mychart --values values-prod.yaml
```

`-f` is simply the shorter form.

---

# 9. `--set` ⭐⭐⭐⭐⭐

You can override values directly from the command line.

Example:

```bash
helm install myapp ./mychart --set replicaCount=5
```

For nested values:

```bash
helm install myapp ./mychart \
  --set image.tag=1.28
```

Multiple values:

```bash
helm install myapp ./mychart \
  --set replicaCount=5 \
  --set image.tag=1.28
```

---

# 10. `--set` vs `-f`

### Using values file

```bash
helm install myapp ./mychart -f values-prod.yaml
```

Better when you have **many configuration values**.

### Using `--set`

```bash
helm install myapp ./mychart --set replicaCount=5
```

Useful for **small or dynamic overrides**.

---

# 11. Multiple Values Files ⭐⭐⭐⭐

You can provide multiple values files.

```bash
helm install myapp ./mychart \
  -f values.yaml \
  -f values-prod.yaml
```

The later file can override values from the earlier file.

Example:

`values.yaml`:

```yaml
replicaCount: 2
image:
  tag: "1.27"
```

`values-prod.yaml`:

```yaml
replicaCount: 5
```

Final configuration:

```yaml
replicaCount: 5
image:
  tag: "1.27"
```

---

# 12. Value Precedence ⭐⭐⭐⭐⭐

This is very important for interviews.

In general, when values come from multiple sources, **more specific overrides win**.

A practical order to remember is:

```text
Chart's values.yaml
       ↓
Custom values file (-f)
       ↓
Additional values files
       ↓
--set
```

So:

```bash
helm install myapp ./mychart \
  -f values-prod.yaml \
  --set replicaCount=10
```

If `values-prod.yaml` says:

```yaml
replicaCount: 5
```

but `--set` says:

```text
replicaCount=10
```

The final value is:

```text
10
```

# 13. Environment-Specific Configuration ⭐⭐⭐⭐⭐

A common DevOps structure is:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── values-dev.yaml
├── values-test.yaml
├── values-prod.yaml
└── templates/
```

Example:

```text
Development
replicas = 1

Testing
replicas = 2

Production
replicas = 5
```

Same Helm Chart:

```text
myapp
```

Different configuration:

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

This is one of the major advantages of Helm.

# 15. `helm show values`

When using an existing Chart, you can see its default values:

```bash
helm show values bitnami/nginx
```

This is very useful before installing a third-party Chart.

You can understand:

* Available configuration
* Image settings
* Service configuration
* Resource configuration
* Ingress configuration
* Replicas
* Other options

---

# 16. `helm get values`

After a release is installed, you can see the values used by that release:

```bash
helm get values myapp
```

To see all values, including default values:

```bash
helm get values myapp -a
```

Important difference:

```text
helm show values
       ↓
Chart's available/default values

helm get values
       ↓
Values used by an installed Release
```

---

# 17. `values.yaml` and Secrets ⚠️

Do **not** treat `values.yaml` as a secure password store.

Avoid putting sensitive information directly into Git:

```yaml
password: MySecretPassword123
```

For production, consider solutions such as:

* Kubernetes Secrets
* External Secrets
* Cloud secret managers
* Vault
* Sealed Secrets

The exact solution depends on your organization's security architecture.

# 18. Best Practices ⭐⭐⭐⭐⭐

### 1. Keep defaults in `values.yaml`

```yaml
replicaCount: 2
```

### 2. Use environment-specific files

```text
values-dev.yaml
values-prod.yaml
```

### 3. Avoid hardcoding configuration in templates

Prefer:

```yaml
replicas: {{ .Values.replicaCount }}
```

Instead of:

```yaml
replicas: 3
```

### 4. Use meaningful names

Good:

```yaml
image:
  repository: nginx
  tag: "1.27"
```

Avoid confusing names.

### 5. Don't commit plain-text production secrets

Use an appropriate secret-management solution.

# 19. Complete Flow ⭐⭐⭐⭐⭐

```text
values.yaml
     ↓
Default Configuration
     ↓
values-prod.yaml
     ↓
Environment Override
     ↓
--set
     ↓
Final Values
     ↓
Helm Templates
     ↓
Kubernetes YAML
     ↓
Kubernetes Cluster
```

Example:

```bash
helm upgrade --install myapp ./mychart \
  -f values-prod.yaml \
  --set image.tag=2.0.0
```

**Q: What is `values.yaml`?**
→ It contains the default configuration values for a Helm Chart.

```yaml
{{ .Values.replicaCount }}
```

**Q: How do you provide a custom values file?**

```bash
helm install myapp ./mychart -f values-prod.yaml
```

```bash

```

→ Yes.

```bash
helm install myapp ./mychart \
  -f values.yaml \
  -f values-prod.yaml
```

→ `--set` generally overrides values supplied through values files.

```text
helm show values
→ Inspect a Chart's values

helm get values
→ Inspect values of an installed Release
```
