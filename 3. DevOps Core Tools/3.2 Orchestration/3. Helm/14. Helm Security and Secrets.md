# Helm Security and Secrets

## 1. Helm Security Fundamentals ⭐⭐⭐⭐⭐

Helm itself is a **package manager and templating tool**. It does not replace Kubernetes security.

Helm security depends mainly on:

```text
Helm
  ↓
Kubernetes API
  ↓
RBAC
  ↓
Service Account / User Permissions
  ↓
Kubernetes Resources
```

Important security areas:

* Authentication
* Authorization
* RBAC
* Secrets
* Repository security
* OCI registry security
* Git security
* CI/CD security

### Main Security Principles

* Least privilege
* Secure registry authentication
* Do not commit plaintext production secrets
* Protect CI/CD credentials
* Use Kubernetes RBAC correctly
* Rotate secrets
* Audit access
* Validate and scan charts before deployment

---

# 2. Helm and Kubernetes RBAC ⭐⭐⭐⭐⭐

Helm communicates with the Kubernetes API server.

Therefore, the identity running Helm needs sufficient Kubernetes permissions.

For example:

```bash
helm install myapp ./mychart
```

Helm may need permission to create resources such as:

```text
Deployment
Service
ConfigMap
Secret
Ingress
Job
```

If the user or ServiceAccount does not have the required permission, installation can fail.

Example:

```text
Error: forbidden
```

---

# 3. Principle of Least Privilege ⭐⭐⭐⭐⭐

Helm should not automatically be given unrestricted `cluster-admin` access.

Prefer:

```text
Only required permissions
        ↓
Specific namespace
        ↓
Specific resources
```

Instead of:

```text
cluster-admin
     ↓
Everything
```

This follows the **Principle of Least Privilege**.

### Example

Suppose Helm only needs to deploy into:

```text
production
```

Use appropriate namespace-scoped permissions instead of unrestricted cluster access.

Conceptually:

```text
Helm ServiceAccount
       ↓
     Role
       ↓
 RoleBinding
       ↓
production namespace
```

This limits the blast radius if credentials are compromised.

---

# 4. Kubernetes Secrets ⭐⭐⭐⭐⭐

Helm can create Kubernetes Secret resources.

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secret
type: Opaque
stringData:
  username: admin
  password: mypassword
```

However, putting sensitive values directly into Helm templates or Git is generally unsafe.

Applications can consume Secrets as:

* Environment variables
* Mounted files

---

# 5. `values.yaml` and Secrets ⭐⭐⭐⭐⭐

Do **not** treat `values.yaml` as a secure secret store.

Avoid:

```yaml
database:
  username: admin
  password: MyPassword123
```

Especially when `values.yaml` is stored in Git.

The problem is:

```text
values.yaml
     ↓
Git
     ↓
Anyone with repository access
     ↓
Can potentially see credentials
```

Even private repositories should not be treated as a secure secret vault.

### Remember

```text
values.yaml → Configuration
Secret      → Sensitive Kubernetes configuration
```

A Kubernetes Secret is also **not automatically equivalent to strong encryption at rest or a complete secret-management system**.

Its security depends on:

* Kubernetes configuration
* RBAC
* Encryption settings
* Access controls

---

# 6. Using Kubernetes Secrets in Pods ⭐⭐⭐⭐

A Secret can be consumed as an environment variable.

Example:

```yaml
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: myapp-secret
        key: password
```

It can also be mounted as a volume.

Typical flow:

```text
Kubernetes Secret
       ↓
Deployment / Pod
       ↓
Application
```

This avoids putting the password directly into the Deployment configuration.

---

# 7. `--set` and Secrets ⚠️ ⭐⭐⭐⭐⭐

A common mistake is:

```bash
helm install myapp ./mychart \
  --set database.password=MyPassword123
```

This is **not a good secret-management strategy**.

Command-line arguments can potentially be exposed through:

* Shell history
* CI/CD logs
* Process inspection
* Debug output

Therefore, avoid passing sensitive credentials directly through `--set` where possible.

---

# 8. Helm Release Data and Secret Exposure ⭐⭐⭐⭐⭐

Helm stores release information in the Kubernetes cluster.

Depending on Helm configuration/version and storage, release information can include rendered release data.

Therefore, do not assume:

```text
Secret was passed to Helm
        ↓
Secret is invisible
```

You should carefully consider who has permission to access:

* Helm release information
* Kubernetes Secrets

Use:

* RBAC
* Appropriate encryption controls
* Least-privilege access

---

# 9. Secrets in Git ⭐⭐⭐⭐⭐

Avoid committing secrets such as:

```yaml
password: SuperSecret123
```

to Git.

Even if the secret is deleted later, it may remain in:

```text
Git history
```

A better approach is:

```text
Git
 ↓
Non-sensitive configuration
 ↓
Secret Manager
 ↓
Deployment
```

The actual production secret should remain outside Git.

---

# 10. External Secret Management ⭐⭐⭐⭐⭐

Common enterprise approaches include:

### Option 1 — Kubernetes Secrets

```text
Helm
 ↓
Kubernetes Secret
 ↓
Application
```

Suitable for simpler environments when Kubernetes Secret management is properly secured.

### Option 2 — External Secrets

```text
Cloud Secret Manager
       ↓
External Secrets Operator
       ↓
Kubernetes Secret
       ↓
Application
```

### Option 3 — HashiCorp Vault

```text
Vault
 ↓
Secret
 ↓
Application / Kubernetes integration
```

### Option 4 — Cloud Secret Managers

Examples:

```text
AWS Secrets Manager
Azure Key Vault
Google Secret Manager
```

These are commonly used in production environments.

---

# 11. Helm + External Secret Management ⭐⭐⭐⭐⭐

A modern architecture can look like:

```text
Developer
    ↓
Git
    ↓
Helm Chart
    ↓
Argo CD
    ↓
Kubernetes
    ↓
External Secrets Operator
    ↓
AWS Secrets Manager / Azure Key Vault / Vault
```

The Helm Chart contains **references/configuration**, not the actual production password.

---

# 12. ExternalSecret Concept ⭐⭐⭐⭐

Instead of:

```yaml
password: mypassword
```

you might define an `ExternalSecret` that references an external secret store.

Conceptually:

```text
ExternalSecret
      ↓
Secret Manager
      ↓
DB_PASSWORD
      ↓
Kubernetes Secret
      ↓
Application
```

This keeps the actual secret outside Git.

---

# 13. Secret Encryption ⭐⭐⭐⭐

Kubernetes Secrets can be stored in etcd.

Depending on cluster configuration, you can enable **encryption at rest** for sensitive Kubernetes data.

Conceptually:

```text
Application
    ↓
Kubernetes API
    ↓
Secret
    ↓
etcd
    ↓
Encrypted at rest
```

Encryption at rest should be combined with:

* RBAC
* Network security
* Strong authentication
* Audit logging

---

# 14. Helm Repository Security ⭐⭐⭐⭐

When using Helm repositories:

```bash
helm repo add ...
```

ensure you trust the repository.

Security concerns include:

* Malicious Charts
* Compromised repositories
* Vulnerable dependencies
* Untrusted third-party code

A Helm Chart contains templates that can create Kubernetes resources.

Therefore:

> **Never blindly install an untrusted Helm Chart into production.**

Review the Chart before deployment.

---

# 15. OCI Registry Security ⭐⭐⭐⭐⭐

For private OCI registries:

```text
helm registry login
        ↓
Authentication
        ↓
OCI Registry
        ↓
Helm Chart
```

Use:

* Strong authentication
* Least privilege
* Access controls
* Secure CI/CD credentials
* Private registries where appropriate

Avoid putting registry passwords directly into scripts.

---

# 16. CI/CD Security ⭐⭐⭐⭐⭐

A typical pipeline:

```text
Git
 ↓
CI/CD
 ↓
Helm
 ↓
Kubernetes
```

Avoid:

```bash
helm upgrade ... --set password=secret123
```

Instead, use:

* CI/CD secret stores
* External secret-management solutions
* Protected CI variables

Also ensure secrets are not printed in CI logs.

---

# 17. Helm Chart Security Scanning ⭐⭐⭐⭐

Helm Charts should be reviewed and scanned before production.

Look for:

* Hardcoded credentials
* Privileged containers
* Host networking
* HostPath mounts
* Excessive RBAC permissions
* Insecure images
* Untrusted dependencies
* Unsafe Kubernetes configurations

Tools such as:

* Trivy
* Kubesec
* Checkov
* Kube-score

can be part of a broader Kubernetes security workflow.

Recommended flow:

```text
Helm Chart
    ↓
Security Scan
    ↓
Review
    ↓
CI/CD
    ↓
Deployment
```

---

# 18. Secret Rotation ⭐⭐⭐⭐

Production secrets should be rotated periodically.

Example:

```text
Old DB Password
      ↓
    Rotate
      ↓
New DB Password
      ↓
Update Secret Manager
      ↓
Application picks up new secret
```

Helm should not become the permanent storage location for long-lived credentials.

---

# 19. Common Security Mistakes ❌

### Mistake 1 — Hardcoded secrets

```yaml
password: admin123
```

inside Git.

### Mistake 2 — Secrets through `--set`

```bash
--set password=secret
```

in CI/CD.

### Mistake 3 — Excessive permissions

Giving Helm:

```text
cluster-admin
```

without need.

### Mistake 4 — Untrusted Charts

Installing an untrusted third-party Chart without review.

### Mistake 5 — Secrets in CI logs

Printing credentials during pipeline execution.

### Mistake 6 — Long-lived cloud credentials

Using long-lived cloud credentials unnecessarily in pipelines.

This architecture separates:



# 22. Quick Interview Revision ⭐⭐⭐⭐⭐

### Q: Is Helm a security tool?

→ No. Helm is a package manager/template engine. Kubernetes RBAC and external security controls provide authorization and security.

### Q: Should you store passwords in `values.yaml`?

→ Generally no, especially if the file is committed to Git.

### Q: Is `--set password=xxx` recommended?

→ No. It can expose secrets through shell history, logs, process information, or debug output.

### Q: How can you manage production secrets?

→ Common approaches include Kubernetes Secrets, External Secrets Operator, Vault, AWS Secrets Manager, Azure Key Vault, and Google Secret Manager.

### Q: What controls Helm's Kubernetes permissions?

→ Kubernetes RBAC.

### Q: What is the least-privilege principle?

→ Give the Helm user or ServiceAccount only the permissions required for its task.

### Q: Can Helm Charts contain security risks?

→ Yes. A Chart contains templates that can create powerful Kubernetes resources, so review and scan untrusted Charts.

### Q: How do you secure a private OCI registry?

→ Use authentication, authorization, least privilege, secure credentials, and appropriate registry access controls.

### Q: Why should secrets not be stored in Git?

→ Git history can retain sensitive values even after they are deleted from the current version.

### Q: How do you protect secrets in CI/CD?

→ Use protected CI/CD secret variables or an external secret-management system and prevent secrets from appearing in logs.

### Q: How do you secure Helm deployments?

→ Use RBAC, least privilege, secure registries, chart scanning, secret management, encryption at rest, protected CI/CD credentials, and secret rotation.
