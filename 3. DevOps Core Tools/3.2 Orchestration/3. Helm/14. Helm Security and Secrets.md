# Helm Security and Secrets

## Main Principles

- Least privilege
- Secure registry authentication
- Do not commit plaintext production secrets
- Protect CI/CD credentials
- Use Kubernetes RBAC correctly
- Rotate secrets

## values.yaml and Secrets

Do not treat `values.yaml` as a secure secret store.

Avoid:

```yaml
databasePassword: "mypassword"
```

Prefer a secret-management approach appropriate for the environment.

## Kubernetes Secret

A template can create a Kubernetes Secret, but the source value still needs to be protected.

Applications can consume Secrets as environment variables or mounted files.

## External Secret Management

Common production approaches include:

- External Secrets
- HashiCorp Vault
- Cloud secret managers
- Sealed/encrypted secret workflows

The important principle is:

```text
Git / Helm configuration
        ↓
reference secret
        ↓
secure secret system
        ↓
Kubernetes Secret / application
```

## `--set` Warning

Avoid passing sensitive values directly on the command line when this could expose them through shell history, process information, or CI logs.

## RBAC

The identity running Helm should have only the Kubernetes permissions it needs.

## Security Checklist

- No plaintext production credentials in Git
- Secure registry credentials
- Least-privilege RBAC
- Protected CI variables
- Secret rotation
- Audit access
- Validate charts before deployment
