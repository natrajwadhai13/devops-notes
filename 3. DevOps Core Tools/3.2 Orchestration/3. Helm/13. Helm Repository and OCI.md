# 13. Helm Repository and OCI

# 1. What is a Helm Repository? ⭐⭐⭐⭐⭐

A **Helm Repository** is a location where Helm Charts are stored and distributed.

For example:

```text id="x1"
Helm Repository
      ↓
 ┌─────────────┐
 │ nginx Chart │
 │ redis Chart │
 │ mysql Chart │
 └─────────────┘
```

You can add a repository:

```bash id="x2"
helm repo add bitnami https://charts.bitnami.com/bitnami
```

Then search for Charts:

```bash id="x3"
helm search repo nginx
```

---

# 2. Traditional Helm Repository Workflow ⭐⭐⭐⭐⭐

The typical workflow is:

```text id="x4"
Helm Repository
      ↓
helm repo add
      ↓
helm repo update
      ↓
helm search repo
      ↓
helm install
```

Example:

```bash id="x5"
helm repo add bitnami https://charts.bitnami.com/bitnami
```

```bash id="x6"
helm repo update
```

```bash id="x7"
helm search repo nginx
```

```bash id="x8"
helm install my-nginx bitnami/nginx
```

---

# 3. `helm repo add` ⭐⭐⭐⭐⭐

Adds a Helm repository.

Syntax:

```bash id="x9"
helm repo add <name> <url>
```

Example:

```bash id="x10"
helm repo add bitnami https://charts.bitnami.com/bitnami
```

Verify:

```bash
helm repo list
```

---

# 4. `helm repo list`

Lists configured repositories.

```bash id="x11"
helm repo list
```

Example:

```text id="x12"
NAME      URL
bitnami   https://charts.bitnami.com/bitnami
```

---

# 5. `helm repo update` ⭐⭐⭐⭐

Updates local repository information.

```bash id="x13"
helm repo update
```

This downloads the latest repository index information so Helm knows about available Chart versions.

---

# 6. `helm search repo`

Searches Charts from configured repositories.

```bash id="x14"
helm search repo nginx
```

Example:

```text id="x15"
NAME            CHART VERSION
bitnami/nginx   ...
```

You can search for a specific Chart:

```bash
helm search repo bitnami/nginx
```

---

# 7. `helm pull`

Downloads a Chart without installing it.

```bash id="x16"
helm pull bitnami/nginx
```

This downloads a packaged Chart such as:

```text id="x17"
nginx-x.x.x.tgz
```

To download and extract:

```bash
helm pull bitnami/nginx --untar
```

Useful when you want to inspect an existing Chart.

---

# 8. Traditional Helm Repository Structure

A traditional Helm repository commonly contains:

```text id="x18"
index.yaml
chart-1.0.0.tgz
chart-1.1.0.tgz
chart-2.0.0.tgz
```

The important file is:

```text id="x19"
index.yaml
```

It contains metadata about available Charts and versions.

Conceptually:

```text id="x20"
Helm Repository
     │
     ├── index.yaml
     ├── myapp-1.0.0.tgz
     ├── myapp-1.1.0.tgz
     └── myapp-2.0.0.tgz
```

---

# 9. What is OCI? ⭐⭐⭐⭐⭐

**OCI** stands for:

**Open Container Initiative**

OCI defines standards for storing and distributing container-related artifacts.

Modern Helm supports storing Helm Charts as **OCI artifacts** in OCI-compatible registries.

Examples of registries include:

* Amazon ECR
* Azure Container Registry
* Google Artifact Registry
* GitHub Container Registry
* Harbor

---

# 10. Helm Charts with OCI

Instead of storing Charts in a traditional Helm repository:

```text id="x21"
Helm Repository
      ↓
index.yaml
      ↓
Chart packages
```

You can store Charts in an OCI registry:

```text id="x22"
OCI Registry
      ↓
Helm Chart OCI Artifact
```

Example:

```text id="x23"
oci://registry.example.com/helm/myapp
```

---

# 11. Traditional Repository vs OCI ⭐⭐⭐⭐⭐

| Feature       | Traditional Helm Repo     | OCI Registry                   |
| ------------- | ------------------------- | ------------------------------ |
| Storage       | Chart repository          | OCI registry                   |
| Metadata      | `index.yaml`              | Registry metadata              |
| URL           | `https://...`             | `oci://...`                    |
| Login         | Repository-specific       | Registry authentication        |
| Chart package | `.tgz`                    | OCI artifact                   |
| Versioning    | Chart versions            | OCI artifact tags/versions     |
| Common use    | Public/private Helm repos | Enterprise artifact management |

---

# 12. OCI Login ⭐⭐⭐⭐⭐

For a private OCI registry, you generally authenticate first.

Helm provides:

```bash id="x24"
helm registry login <registry>
```

Example:

```bash
helm registry login registry.example.com
```

You may be prompted for:

```text id="x25"
Username
Password
```

After authentication, Helm can access private OCI Charts according to the registry's permissions.

---

# 13. OCI Pull ⭐⭐⭐⭐⭐

You can pull a Chart from an OCI registry.

Example:

```bash id="x26"
helm pull oci://registry.example.com/helm/myapp --version 1.0.0
```

This downloads the Chart package locally.

To extract:

```bash
helm pull oci://registry.example.com/helm/myapp \
  --version 1.0.0 \
  --untar
```

---

# 14. OCI Push ⭐⭐⭐⭐⭐

First package your Chart:

```bash id="x27"
helm package myapp
```

This creates:

```text id="x28"
myapp-1.0.0.tgz
```

Login:

```bash
helm registry login registry.example.com
```

Then push:

```bash id="x29"
helm push myapp-1.0.0.tgz oci://registry.example.com/helm
```

Conceptually:

```text id="x30"
Helm Chart
    ↓
helm package
    ↓
.tgz
    ↓
helm push
    ↓
OCI Registry
```

---

# 15. OCI Installation

You can install directly from an OCI registry.

Example:

```bash id="x31"
helm install myapp \
  oci://registry.example.com/helm/myapp \
  --version 1.0.0
```

Flow:

```text id="x32"
OCI Registry
     ↓
Helm Chart
     ↓
helm install
     ↓
Release
     ↓
Kubernetes
```

---

# 16. OCI Versioning ⭐⭐⭐⭐

Charts stored in OCI registries have versions.

Example:

```text id="x33"
myapp:1.0.0
myapp:1.1.0
myapp:2.0.0
```

You can specify a version:

```bash id="x34"
helm pull oci://registry.example.com/helm/myapp \
  --version 1.1.0
```

This is useful for reproducible deployments.

# 18. Example: Helm + Amazon ECR

Amazon ECR can be used as an OCI registry for Helm Charts.

Conceptually:

```text id="x38"
Developer
    ↓
helm package
    ↓
ECR
    ↓
Helm Chart
    ↓
Kubernetes / Argo CD
```

Typical workflow:

```bash
helm package myapp
```

Authenticate with the registry using the appropriate AWS/ECR authentication mechanism.

Then:

```bash
helm push myapp-1.0.0.tgz oci://<ecr-registry>/helm
```

The exact authentication command depends on your AWS setup.

---

# 19. Example: Helm + Azure Container Registry

Azure Container Registry can also store Helm Charts as OCI artifacts.

Conceptually:

```text id="x39"
Helm Chart
    ↓
Azure Container Registry
    ↓
OCI Artifact
    ↓
AKS / Kubernetes
```

This is useful in Azure DevOps environments.

---

# 20. Example: Helm + Harbor

Harbor can act as a private registry for:

```text id="x40"
Docker Images
+
Helm Charts
```

Typical architecture:

```text id="x41"
CI/CD
  ↓
Harbor
  ├── Container Images
  └── Helm OCI Charts
          ↓
      Kubernetes
```

This is common in private/on-premises environments.

# 22. OCI Workflow ⭐⭐⭐⭐⭐

```text id="x43"
helm package
      ↓
helm registry login
      ↓
helm push
      ↓
OCI Registry
      ↓
helm pull / install
```

Example:

```bash
helm package myapp
```

```bash
helm registry login registry.example.com
```

```bash

  oci://registry.example.com/helm
```

Then:

```bash
helm install myapp \
  oci://registry.example.com/helm/myapp \
  --version 1.0.0
```

# 23. Helm Repository vs OCI — Easy Understanding ⭐⭐⭐⭐⭐

Think of it like this:

### Traditional Helm Repository

```text
Chart
  ↓
.tgz
  ↓
Helm Repository
  ↓
index.yaml
  ↓
Helm
```

### OCI

```text
Chart
  ↓
OCI Artifact
  ↓
OCI Registry
  ↓
Helm
```

The key difference is **how the Chart is stored and distributed**.

# 26. Security Considerations ⭐⭐⭐⭐

For private repositories/registries:

* Use authentication
* Use least-privilege access
* Avoid hardcoding credentials
* Use CI/CD secret management
* Control who can push Charts
* Control who can pull Charts
* Use versioned Charts
* Prefer immutable/reproducible artifact versions where supported
