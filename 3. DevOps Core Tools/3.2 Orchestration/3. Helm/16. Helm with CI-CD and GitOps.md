# Helm with CI/CD and GitOps

## 1. Helm in CI/CD ⭐⭐⭐⭐⭐

Helm is commonly used in CI/CD pipelines to deploy applications to Kubernetes.

### Traditional CI/CD Flow

```text
Developer
    ↓
Git Push
    ↓
CI Pipeline
    ↓
Build Application
    ↓
Run Tests
    ↓
Build Docker Image
    ↓
Push Image
    ↓
Validate Helm Chart
    ↓
helm upgrade --install
    ↓
Kubernetes
```

### Example

```bash
helm upgrade --install myapp ./helm/myapp \
  -n production \
  --create-namespace \
  -f ./helm/myapp/values-prod.yaml \
  --set image.tag=$IMAGE_TAG
```

---

# 2. Build → Push → Deploy Workflow ⭐⭐⭐⭐⭐

This is one of the most important DevOps concepts.

```text
1. Developer pushes code
          ↓
2. CI starts
          ↓
3. Run tests
          ↓
4. Build Docker image
          ↓
5. Push image to registry
          ↓
6. Update image tag
          ↓
7. Helm deployment
          ↓
8. Kubernetes
```

Example image:

```text
myapp:abc123
```

Helm configuration:

```yaml
image:
  repository: registry.example.com/myapp
  tag: abc123
```

The important idea is:

```text
Application Code
      ↓
Docker Image
      ↓
Container Registry
      ↓
Helm Configuration
      ↓
Kubernetes
```

# 3. Automated Helm Validation ⭐⭐⭐⭐⭐

Before deployment, CI should validate the Helm Chart.

### Helm Lint

```bash
helm lint ./helm/myapp
```

Checks the chart for common problems.

### Render Templates

```bash
helm template myapp ./helm/myapp
```

With environment-specific values:

```bash
helm template myapp ./helm/myapp \
  -f ./helm/myapp/values-prod.yaml
```

### Recommended validation flow

```text
Helm Chart
    ↓
helm lint
    ↓
helm template
    ↓
Security Checks / Scans
    ↓
Deployment
```

# 4. Environment-Specific Values ⭐⭐⭐⭐⭐

A common structure:

```text
helm/
└── myapp/
    ├── Chart.yaml
    ├── values.yaml
    ├── values-dev.yaml
    ├── values-test.yaml
    ├── values-prod.yaml
    └── templates/
```

### Dev

```yaml
replicaCount: 1

image:
  tag: dev
```

### Production

```yaml
replicaCount: 5

image:
  tag: stable
```

Deploy:

```bash
helm upgrade --install myapp ./helm/myapp \
  -f values-prod.yaml
```

Keep environment differences in configuration rather than copying the whole chart.

---

# 5. `helm upgrade --install` ⭐⭐⭐⭐⭐

This command is extremely common in CI/CD.

```bash
helm upgrade --install myapp ./helm/myapp
```

Logic:

```text
Release exists?
       │
   ┌───┴───┐
   ↓       ↓
  Yes      No
   ↓       ↓
Upgrade  Install
```

It prevents the pipeline from needing separate logic for the first deployment and subsequent deployments.

## GitLab CI/CD ⭐⭐⭐⭐⭐

Typical pipeline:

```text
GitLab
   ↓
Build
   ↓
Test
   ↓

   ↓

   ↓
```

Example:

```yaml

  stage: deploy
  script:
```

The exact pipeline depends on how Kubernetes credentials and runners are configured.

# 7. Helm Package + OCI Registry ⭐⭐⭐⭐⭐

Helm Charts can be packaged and stored in an OCI registry.

### Package Chart

```bash
helm package ./helm/myapp
```

Output:

```text
myapp-1.0.0.tgz
```

### Login

```bash
helm registry login registry.example.com
```

### Push

```bash
helm push myapp-1.0.0.tgz \
  oci://registry.example.com/helm
```

Architecture:

```text
CI Pipeline
    ↓
helm package
    ↓
OCI Registry
    ↓
Helm Chart
```

# 8. Helm in GitOps ⭐⭐⭐⭐⭐

In GitOps, **Git is the source of truth**.

### Traditional CI/CD

```text
Git
 ↓
CI
 ↓
Helm
 ↓
Kubernetes
```

### GitOps

```text
Git
 ↓
Argo CD
 ↓
Helm
 ↓
Kubernetes
```

Argo CD continuously compares the desired state in Git with the actual state in Kubernetes.

---

# 9. Helm + Argo CD ⭐⭐⭐⭐⭐

Argo CD can use a Helm Chart as the application source.

Architecture:

```text
Git Repository
      ↓
  Helm Chart
      ↓
    Argo CD
      ↓
  Kubernetes
```

Argo CD can use:

```text
Chart.yaml
values.yaml
templates/
```

and use Helm to render Kubernetes manifests.

---

# 10. Argo CD Does Not Normally Need `helm install` ⭐⭐⭐⭐⭐

In a GitOps model, you generally do not manually run:

```bash
helm install
```

from CI for an Argo CD-managed application.

Instead:

```text
Git
 ↓
Argo CD
 ↓
Helm Rendering
 ↓
Kubernetes
```

Argo CD manages synchronization.

### Interview Point

> In traditional CI/CD, the pipeline can run Helm commands directly. In a GitOps model, Argo CD normally manages the deployment and synchronization.

# 13. GitOps Deployment Model ⭐⭐⭐⭐⭐

Suppose you want to deploy:

```text

```

```yaml

  tag: "1.2.0"
```

```text

    ↓

    ↓
Argo CD syncs
    ↓

```

Git remains the desired-state source.

# 14. GitOps Rollback vs Helm Rollback ⭐⭐⭐⭐⭐

## Traditional Helm

Check history:

```bash
helm history myapp
```

Rollback:

```bash
helm rollback myapp 2
```

## GitOps

Normally revert the Git change:

```text
Git
 ↓
Revert Commit
 ↓
Argo CD
 ↓
Kubernetes
```

### Why?

Suppose Git defines:

```text
Version 3
```

but you manually rollback Kubernetes to:

```text
Version 2
```

Argo CD may detect the cluster as **OutOfSync** and reconcile it back to the state defined in Git.

Therefore:

> In GitOps, rollback is normally performed by reverting the Git change rather than manually running `helm rollback`.

# 15. Traditional Helm vs GitOps ⭐⭐⭐⭐⭐

| Area            | Traditional Helm CI/CD | GitOps + Argo CD   |
| --------------- | ---------------------- | ------------------ |
| Source of truth | CI/CD + Git            | Git                |
| Deployment      | CI runs Helm           | Argo CD            |
| Helm command    | `helm upgrade`         | Argo CD manages it |
| Drift detection | Usually manual         | Automatic          |
| Rollback        | Helm rollback          | Git revert         |
| Desired state   | Pipeline configuration | Git                |
| Kubernetes sync | Pipeline-driven        | Argo CD-driven     |

### Easy Interview Answer

> Traditional Helm deployment is usually pipeline-driven, where CI executes Helm commands directly. In GitOps, Git is the source of truth and Argo CD continuously reconciles Kubernetes with the desired state.

# 18. Helm + Argo CD Interview Scenario ⭐⭐⭐⭐⭐

### Question

> Your CI pipeline builds a Docker image. How will you deploy it using Helm and Argo CD?

### Answer

```text
1. Developer pushes code.
2. CI builds and tests the application.
3. CI builds the Docker image.
4. Image is pushed to the container registry.
5. CI updates the image tag in the GitOps repository.
6. Argo CD detects the Git change.
7. Argo CD renders the Helm Chart.
8. Argo CD synchronizes Kubernetes resources.
9. Kubernetes deploys the new image.
```

### Short Interview Answer

> CI is responsible for building, testing and publishing the image. The image tag is updated in the GitOps repository. Argo CD detects the change, uses Helm to render the desired Kubernetes manifests, and synchronizes them to the cluster.

# 20. Production Best Practices ⭐⭐⭐⭐⭐

### 1. Validate Helm Charts

```bash
helm lint ./mychart
helm template myapp ./mychart
```

### 2. Use Environment-Specific Values

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

### 3. Use Immutable Image Tags

Prefer:

```text
myapp:abc123
```

over:

```text
myapp:latest
```

Avoid relying on mutable tags such as `latest` for production deployments.

### 4. Don't Store Secrets in Git

Use an appropriate secret-management solution.

### 5. Use Git as the Source of Truth for GitOps

Avoid manual changes directly in the cluster.

### 6. Use `helm upgrade --install` for Traditional CI/CD

```bash
helm upgrade --install myapp ./mychart
```

### 7. For Argo CD, Prefer Git-Based Rollback

```text
Revert Git
    ↓
Argo CD
    ↓
Kubernetes
```

# 22. Quick Interview Revision ⭐⭐⭐⭐⭐

### Q: How is Helm used in CI/CD?

> CI validates the Helm Chart and can use Helm to deploy applications to Kubernetes.

```text
CI → Helm → Kubernetes
```

### Q: How is Helm used with GitOps?

> Helm provides the packaging and template mechanism, while Argo CD manages synchronization from Git to Kubernetes.

```text
Git → Argo CD → Helm → Kubernetes
```

### Q: Traditional Helm vs GitOps?

```text
Traditional:

CI → helm upgrade → Kubernetes

GitOps:

Git → Argo CD → Helm → Kubernetes
```

### Q: What does CI usually do in a GitOps model?

> Build, test, scan, create/push the Docker image and update the GitOps configuration.

### Q: How is an image tag updated?

```yaml
image:
  tag: abc123
```

CI updates the GitOps configuration and Argo CD deploys the new desired state.

### Q: How do you rollback in GitOps?

> Revert the Git change rather than manually changing the cluster with `helm rollback`.

### Q: Why can manual `helm rollback` be problematic with Argo CD?

> Argo CD may detect the cluster as OutOfSync and restore the state defined in Git.
