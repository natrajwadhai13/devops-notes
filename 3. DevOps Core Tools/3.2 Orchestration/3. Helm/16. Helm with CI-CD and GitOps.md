# Helm with CI/CD and GitOps

## Traditional CI/CD

A common deployment flow:

```text
Developer
   ↓
Git
   ↓
CI pipeline
   ↓
Build image
   ↓
Push image
   ↓
Validate Helm chart
   ↓
helm upgrade --install
   ↓
Kubernetes
```

## Recommended Validation

```bash
helm lint ./mychart
helm template myapp ./mychart -f values-prod.yaml
helm upgrade --install myapp ./mychart -f values-prod.yaml
```

## Environment Values

```text
values.yaml
values-dev.yaml
values-test.yaml
values-prod.yaml
```

Keep environment differences in configuration rather than copying the whole chart.

## GitOps with Argo CD

GitOps commonly uses Git as the desired-state source.

```text
Developer
   ↓
Git repository
   ↓
Argo CD
   ↓
Helm rendering
   ↓
Kubernetes
```

Argo CD can use a Helm chart as a source and render it. In this model, you normally do **not** need to run `helm install` manually for the Argo-managed application.

## CI vs GitOps

**CI:** build/test image and update the desired deployment configuration.

**GitOps controller:** continuously reconciles Kubernetes with Git.

## Image Tags

Prefer immutable image tags or digests where practical. Avoid relying on mutable tags such as `latest` for production deployments.

## Rollback

Traditional Helm:

```bash
helm history myapp
helm rollback myapp <revision>
```

GitOps:

```text
Revert desired configuration in Git
        ↓
Argo CD reconciles
        ↓
Kubernetes returns to desired state
```

## Production Best Practices

- Validate charts in CI
- Use environment-specific values
- Keep Git as the GitOps source of truth
- Protect secrets
- Use immutable image versions
- Separate application build from deployment reconciliation
