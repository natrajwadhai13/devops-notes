# Release Management

## Chart vs Release

**Chart:** reusable package.

**Release:** installed instance of that chart.

One chart can create many releases:

```text
myapp chart
 ├── dev release
 ├── test release
 └── prod release
```

## Install

```bash
helm install myapp ./mychart
```

## Upgrade

```bash
helm upgrade myapp ./mychart
```

Recommended for automation:

```bash
helm upgrade --install myapp ./mychart
```

## History

```bash
helm history myapp
```

Each upgrade can create a new revision.

## Rollback

```bash
helm rollback myapp 2
```

Rollback returns the release to a previous revision.

## Inspect

```bash
helm status myapp
helm get values myapp
helm get manifest myapp
helm get all myapp
```

## Uninstall

```bash
helm uninstall myapp
```

## Release Lifecycle

```text
install
  ↓
revision 1
  ↓
upgrade
  ↓
revision 2
  ↓
upgrade
  ↓
revision 3
  ↓
rollback
  ↓
previous revision
```

# 1. What is a Helm Release? ⭐⭐⭐⭐⭐

A **Release** is an installed instance of a Helm Chart in a Kubernetes cluster.

For example:

```bash
helm install myapp ./mychart
```

Here:

```text
myapp
   ↓
Release name

./mychart
   ↓
Helm Chart
```

So:

```text
Chart + Configuration + Kubernetes Cluster
                ↓
             Release
```

---

# 2. Chart vs Release ⭐⭐⭐⭐⭐

This is very important.

### Chart

A **Chart** is a package/template.

```text
mychart/
├── Chart.yaml
├── values.yaml
└── templates/
```

### Release

A **Release** is an installed instance of that Chart.

```bash
helm install dev-app ./mychart
```

```bash
helm install prod-app ./mychart
```

Both releases can use the same Chart.

```text
             mychart
             /     \
            ↓       ↓
       dev-app    prod-app
       Release    Release
```

---

# 3. Install a Release ⭐⭐⭐⭐⭐

Basic command:

```bash
helm install myapp ./mychart
```

Helm:

1. Reads the Chart
2. Loads values
3. Processes templates
4. Generates Kubernetes manifests
5. Sends resources to Kubernetes
6. Creates a Helm Release

Check:

```bash
helm list
```

---

# 4. Release Lifecycle ⭐⭐⭐⭐⭐

A typical lifecycle:

```text
helm install
      ↓
   Release
      ↓
helm upgrade
      ↓
 New Revision
      ↓
helm upgrade
      ↓
 New Revision
      ↓
Problem?
      ↓
helm rollback
      ↓
Previous Revision
```

Eventually:

```bash
helm uninstall myapp
```

removes the release.

# 5. `helm list` ⭐⭐⭐⭐⭐

Lists Helm releases.

```bash
helm list
```

Example:

```text
NAME       NAMESPACE   REVISION   STATUS
myapp      default     1          deployed
```

All namespaces:

```bash
helm list -A
```

Specific namespace:

```bash
helm list -n production
```

# 6. `helm status` ⭐⭐⭐⭐⭐

Shows the current status of a release.

```bash
helm status myapp
```

Example:

```text
NAME: myapp
NAMESPACE: default
STATUS: deployed
REVISION: 3
```

Useful when troubleshooting a deployment.

---

# 7. Release Revision ⭐⭐⭐⭐⭐

Every time you install or upgrade a release, Helm maintains a **revision number**.

Example:

```text
Revision 1 → Initial installation
Revision 2 → First upgrade
Revision 3 → Second upgrade
Revision 4 → Third upgrade
```

Example:

```text
REVISION   STATUS
1          superseded
2          superseded
3          deployed
```

The latest successful revision is normally the current release revision.

---

# 8. `helm history` ⭐⭐⭐⭐⭐

Shows the revision history.

```bash
helm history myapp
```

Example:

```text
REVISION   STATUS       DESCRIPTION
1          superseded   Install complete
2          superseded   Upgrade complete
3          deployed     Upgrade complete
```

This is extremely important before performing a rollback.

---

# 9. `helm upgrade` ⭐⭐⭐⭐⭐

Updates an existing release.

```bash
helm upgrade myapp ./mychart
```

For example, you change:

```yaml
replicaCount: 3
```

to:

```yaml
replicaCount: 5
```

Then:

```bash
helm upgrade myapp ./mychart
```

Helm creates a new revision.

```text
Revision 1
    ↓
Revision 2
```

---

# 10. Upgrade with Values

Using a values file:

```bash
helm upgrade myapp ./mychart \
  -f values-prod.yaml
```

Using `--set`:

```bash
helm upgrade myapp ./mychart \
  --set image.tag=2.0.0
```

---

# 11. `helm upgrade --install` ⭐⭐⭐⭐⭐

This is one of the most useful commands in **CI/CD**.

```bash
helm upgrade --install myapp ./mychart
```

Logic:

```text
Does release exist?
       │
   ┌───┴───┐
   │       │
  Yes      No
   │       │
Upgrade   Install
```

This allows pipelines to use one command regardless of whether the release already exists.

Example:

```bash
helm upgrade --install myapp ./mychart \
  -n production \
  --create-namespace \
  -f values-prod.yaml
```

---

# 12. Rollback ⭐⭐⭐⭐⭐

Rollback means returning a release to an earlier revision.

First check history:

```bash
helm history myapp
```

Example:

```text
REVISION   STATUS
1          superseded
2          superseded
3          deployed
```

Rollback to revision 2:

```bash
helm rollback myapp 2
```

Helm restores the release to the configuration represented by that revision.

---

# 13. Important Rollback Concept ⭐⭐⭐⭐⭐

Suppose:

```text
Revision 1 → Application v1
Revision 2 → Application v2
Revision 3 → Application v3
```

You deploy v3 and it causes a problem.

Rollback:

```bash
helm rollback myapp 2
```

Conceptually:

```text
v3 ❌
 ↓
Rollback
 ↓
v2 ✅
```

### Important

A rollback itself creates a **new revision**.

For example:

```text
1 → Install
2 → Upgrade
3 → Upgrade
4 → Rollback to revision 2
```

So after rollback, you may see:

```text
REVISION   STATUS
1          superseded
2          superseded
3          superseded
4          deployed
```

This is an important interview point.

```bash

```

---

# 18. Release Statuses ⭐⭐⭐⭐

You may see statuses such as:

```text
deployed
failed
pending-install
pending-upgrade
pending-rollback
uninstalling
uninstalled
superseded
```

The most important ones to recognize:

```text
deployed   → Successfully deployed
failed     → Operation failed
superseded → Older revision replaced by newer revision
pending-*  → Operation is in progress/pending
```

---

# 19. Uninstall a Release ⭐⭐⭐⭐⭐

Remove a release:

```bash
helm uninstall myapp
```

Specific namespace:

```bash
helm uninstall myapp -n production
```

Check:

```bash
helm list
```

### Important

```text
Helm Chart
    ≠
Helm Release
```

Uninstalling a release does not delete the Chart files from your local machine or repository.

---

# 20. Release in a Namespace ⭐⭐⭐⭐⭐

You can install a release into a specific namespace.

```bash
helm install myapp ./mychart \
  -n production
```

If the namespace doesn't exist:

```bash
helm install myapp ./mychart \
  -n production \
  --create-namespace
```

Check:

```bash
helm list -n production
```

---

# 21. Multiple Releases from One Chart

One Chart can have multiple releases.

Example:

```bash
helm install dev-app ./mychart -n dev
```

```bash
helm install test-app ./mychart -n test
```

```bash
helm install prod-app ./mychart -n production
```

Architecture:

```text
                 mychart
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
     dev-app     test-app    prod-app
        │           │           │
       dev         test      production
```

This is one of Helm's major advantages.

---

# 22. Production Release Workflow ⭐⭐⭐⭐⭐

A practical production deployment might look like:

```bash
helm lint ./mychart
```

Then:

```bash
helm template prod-app ./mychart \
  -f values-prod.yaml
```

Then:

```bash
helm upgrade --install prod-app ./mychart \
  -n production \
  --create-namespace \
  -f values-prod.yaml
```

Check:

```bash
helm status prod-app -n production
```

Check:

```bash
helm history prod-app -n production
```

If something goes wrong:

```bash
helm rollback prod-app <revision> -n production
```

# 23. Helm Release with CI/CD ⭐⭐⭐⭐⭐

A typical pipeline:

```text
Developer
    ↓
Git Push
    ↓
CI Pipeline
    ↓
Build Docker Image
    ↓
Push Image
    ↓
Update Helm Values
    ↓
helm upgrade --install
    ↓
Kubernetes
```

Example CI command:

```bash
helm upgrade --install myapp ./helm/myapp \
  -n production \
  --create-namespace \
  -f ./helm/myapp/values-prod.yaml \
  --set image.tag=$IMAGE_TAG
```

This is a very common DevOps pattern.

---

# 24. Helm + Argo CD ⭐⭐⭐⭐⭐

Since you are also learning **Argo CD/GitOps**, understand this relationship.

With traditional CI/CD:

```text
Git
 ↓
CI Pipeline
 ↓
helm upgrade
 ↓
Kubernetes
```

With GitOps:

```text
Git
 ↓
Helm Chart / Values
 ↓
Argo CD
 ↓
Kubernetes
```

Argo CD can use the Helm Chart to generate manifests and then synchronize them to Kubernetes.

In this model, Argo CD generally manages the application lifecycle rather than your CI pipeline directly running `helm install`/`helm upgrade`.
