# Helm Interview Cheat Sheet — Clean & Rearranged

## 1. Helm Basics — Must Know

### Q1. What is Helm?

**Interview Answer:**

> Helm is a package manager for Kubernetes. It uses reusable **Charts, Templates and Values** to package and deploy applications, and provides release management such as install, upgrade, rollback and history.

### Q2. Why do we use Helm?

Helm helps to:

* Reduce repetitive Kubernetes YAML
* Create reusable templates
* Manage different environments — Dev/QA/Prod
* Manage application versions
* Easily install and upgrade applications
* Roll back failed deployments
* Standardize Kubernetes deployments
* Integrate with CI/CD and GitOps

### Q3. What is a Helm Chart?

A **Chart** is a reusable package containing:

* `Chart.yaml` → metadata
* `values.yaml` → default configuration
* `templates/` → Kubernetes manifest templates
* `charts/` → dependencies/subcharts
* Optional files such as `README`, `NOTES.txt`, tests, etc.

**Remember:**

```text
Chart = Package / Blueprint
```

### Q4. What is a Helm Release?

A **Release** is a deployed/installed instance of a Helm Chart.

Example:

```text
Chart   → apache-helm
Release → dev-apache
```

If the same chart is installed in different environments:

```text
apache-helm
   ├── dev-apache
   ├── stage-apache
   └── prod-apache
```

**Remember:**

```text
Chart   = Package
Release = Installed instance
```

# 2. Helm Architecture & How It Works

### Q5. What are the main components of Helm?

For interview purposes:

```text
Helm CLI
   ↓
Helm Chart
   ├── Chart.yaml
   ├── values.yaml
   └── templates/
```

Helm 3+ communicates directly with the Kubernetes API; there is no Tiller server. 

### Q6. How does Helm work?

Simple flow:

```text
Chart
  ↓
values.yaml
  ↓
Templates
  ↓
Helm renders templates
  ↓
Kubernetes YAML
  ↓
Kubernetes API
  ↓
Resources created
  ↓
Helm Release
```

**Interview answer:**

> Helm takes the chart templates, combines them with the configured values, renders the final Kubernetes manifests, and sends them to the Kubernetes API to create or update resources.

# 3. Helm Chart Structure

### Q7. Explain Helm Chart directory structure.

Typical chart:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── charts/
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    ├── hpa.yaml
    ├── serviceaccount.yaml
    ├── _helpers.tpl
    └── tests/
```

### Q8. What is `Chart.yaml`?

Contains **chart metadata**, for example:

```yaml
name: myapp
version: 0.1.0
appVersion: "1.0"
description: My application
```

**Remember:**

```text
Chart.yaml → Metadata
```

### Q9. What is `values.yaml`?

Contains default/configurable values.

Example:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: "latest"

service:
  type: ClusterIP
  port: 80
```

**Remember:**

```text
values.yaml → Configuration
```

### Q10. What is the `templates/` directory?

It contains Kubernetes manifest templates.

Example:

```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

The actual values are taken from `values.yaml` or other value sources.

**Remember:**

```text
templates/ → Kubernetes YAML + Helm variables
```

# 4. Values & Environment Management

### Q11. How do you override `values.yaml`?

Two common ways:

### Using `--set`

```bash
helm install myapp ./mychart \
  --set replicaCount=5
```

### Using custom values file

```bash
helm install myapp ./mychart \
  -f values-prod.yaml
```

### Q12. How do you manage Dev/Stage/Prod?

Example:

```text
values.yaml
values-dev.yaml
values-stage.yaml
values-prod.yaml
```

Production:

```bash
helm install myapp ./mychart \
  -f values-prod.yaml \
  -n prod \
  --create-namespace
```

**Interview answer:**

> `values.yaml` contains default values, while environment-specific values files override those defaults for Dev, Stage and Prod.

# 6. Install → Upgrade → Rollback Lifecycle

This is **very important for interviews**.

```text
helm create
     ↓
helm lint
     ↓
helm template / --dry-run
     ↓
helm install
     ↓
helm upgrade
     ↓
helm history
     ↓
helm rollback
     ↓
helm uninstall
```

### Q13. How do you upgrade a Helm release?

```bash
helm upgrade myapp ./mychart -n dev
```

### Q14. How do you rollback?

First check history:

```bash
helm history myapp -n dev
```

Then:

```bash
helm rollback myapp 1 -n dev
```

**Important:** `1` is the revision number to which you want to roll back.

# 7. Helm Debugging — Very Important

### Q15. How do you debug a Helm chart?

Use:

```bash
helm lint ./mychart
```

Then:

```bash
helm template myapp ./mychart
```

Then:

```bash
helm install myapp ./mychart \
  --dry-run --debug
```

For an already-installed release:

```bash
helm get manifest myapp
helm get values myapp
helm history myapp
helm get all myapp
```

And use Kubernetes commands:

```bash
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod>
kubectl get all
```

### Easy difference to remember

```text
helm lint
    ↓
Check chart problems

helm template
    ↓
See generated Kubernetes YAML

helm install --dry-run --debug
    ↓
Preview installation without actually installing
```

This distinction is explicitly covered in the source notes.

# 8. Helm 2 vs Helm 3

### Q16. What happened to Tiller?

**Helm 2:**

```text
Helm CLI
   ↓
Tiller
   ↓
Kubernetes
```

**Helm 3:**

```text
Helm CLI
   ↓
Kubernetes API
```

Tiller was removed in Helm 3.

### Interview answer

> Tiller was the server-side component used by Helm 2. Helm 3 removed Tiller and the Helm client communicates directly with the Kubernetes API.

**Remember:**

```text
Helm 2 → Tiller
Helm 3 → No Tiller
```

# 9. Helm Repository & OCI

### Q17. What is a Helm Repository?

A traditional Helm repository is used to distribute Helm charts and chart metadata.

Useful commands:

```bash
helm repo list
```

```bash
helm repo add <name> <url>
```

```bash
helm repo update
```

Search:

```bash
helm search repo nginx
```

Search chart versions:

```bash
helm search repo nginx --versions
```

### Q18. What is OCI in Helm?

Helm also supports storing charts as **OCI artifacts** in container registries.

Example from the notes:

```bash
helm install nginx-helm \
  oci://registry-1.docker.io/bitnamicharts/nginx
```

**Interview difference:**

```text
Helm Repository
       ↓
Traditional chart repository

OCI Registry
       ↓
Charts stored as OCI artifacts
```

# 10. Helm Dependencies

### Q19. What are Helm dependencies?

A chart can depend on another chart.

Example:

```yaml
dependencies:
  - name: redis
    version: 17.3.0
    repository: "https://charts.bitnami.com/bitnami"
```

Update dependencies:

```bash
helm dependency update
```

Example:

```text
My Application
     │
     ├── Redis
     └── PostgreSQL
```

Typical use case:

> An application chart may use supporting services such as Redis or PostgreSQL.

# 11. Helm Hooks

### Q20. What are Helm Hooks?

Hooks allow Kubernetes resources to run at specific points in the Helm release lifecycle.

Examples:

```text
pre-install
post-install
pre-upgrade
post-upgrade
pre-delete
post-delete
```

Common use cases:

* Database migrations
* Pre/post deployment jobs
* Backup jobs
* Cleanup tasks

**Interview answer:**

> Helm Hooks are special resources that execute at specific lifecycle events of a Helm release, such as before installation or after an upgrade.

# 12. Helm + GitOps

### Q21. Can Helm work with Argo CD?

**Yes.**

Common tools:

* Argo CD
* Flux

Typical architecture:

```text
Developer
    ↓
Git Repository
    ↓
Argo CD
    ↓
Helm Chart
    ↓
Kubernetes Cluster
```

Helm charts and configuration can be stored/versioned in Git, while Argo CD continuously reconciles the desired state. 

### Interview answer

> Yes, Helm works with GitOps tools such as Argo CD and Flux. Argo CD can use Helm charts to generate Kubernetes manifests and continuously synchronize the desired state with the Kubernetes cluster.

# 13. Helm vs Kubernetes YAML

| Kubernetes YAML         | Helm                       |
| ----------------------- | -------------------------- |
| Static manifests        | Templates                  |
| More repetition         | Reusable charts            |
| Manual configuration    | Values-based configuration |
| Harder to reuse         | Easy to reuse              |
| No Helm release history | Release revisions          |
| Applied using `kubectl` | Managed using Helm         |

### Interview answer

> Kubernetes manifests define resources directly. Helm packages those manifests into reusable charts and adds templating, configuration management, release history, upgrades and rollbacks.



---

# 14. Helm vs Kustomize

| Feature            | Helm             | Kustomize                      |
| ------------------ | ---------------- | ------------------------------ |
| Main purpose       | Package & deploy | Customize YAML                 |
| Templating         | Yes              | No traditional templating      |
| Configuration      | `values.yaml`    | `kustomization.yaml`           |
| Packaging          | Yes              | No                             |
| Release management | Yes              | No Helm-style releases         |
| Rollback           | Helm revisions   | Usually Git/deployment tooling |

### Easy interview answer

> Helm is mainly used for packaging, templating and release management, whereas Kustomize is mainly used for customizing Kubernetes YAML without traditional templates.

# 17. Dev vs Prod Values

### `values-dev.yaml`

```yaml
replicaCount: 1

resources:
  limits:
    cpu: "200m"
    memory: "256Mi"
  requests:
    cpu: "100m"
    memory: "128Mi"

image:
  tag: "dev"
```

### `values-prod.yaml`

```yaml
replicaCount: 4

resources:
  limits:
    cpu: "500m"
    memory: "512Mi"
  requests:
    cpu: "300m"
    memory: "256Mi"

image:
  tag: "stable"

autoscaling:
  enabled: true
  minReplicas: 4
  maxReplicas: 10
  targetCPUUtilizationPercentage: 60
```

Deploy:

```bash
helm install prod-apache apache-helm \
  -f values-prod.yaml \
  -n prod --create-namespace
```
