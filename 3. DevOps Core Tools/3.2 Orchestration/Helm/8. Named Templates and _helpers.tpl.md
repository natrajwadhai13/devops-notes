# 1. What is `_helpers.tpl`? ⭐⭐⭐⭐⭐

`_helpers.tpl` is a special Helm template file used to store **reusable named templates and helper functions**.

It is normally located inside:

```text id="3x6d2x"
myapp/
└── templates/
    └── _helpers.tpl
```

Example:

```text id="b8i9ae"
templates/
├── deployment.yaml
├── service.yaml
├── ingress.yaml
└── _helpers.tpl
```

The main purpose is to **avoid repeating the same template code**.

---

# 2. What are Named Templates?

A **Named Template** is a reusable block of Helm template code.

It is created using:

```text id="y3w6f2"
{{- define "template-name" -}}
...
{{- end }}
```

Example:

```yaml id="8c0w9e"
{{- define "myapp.name" -}}
{{- .Chart.Name -}}
{{- end }}
```

Here:

```text id="2z2zj7"
myapp.name
```

is the name of the reusable template.

---

# 3. `define` ⭐⭐⭐⭐⭐

`define` creates a named template.

Example in `_helpers.tpl`:

```yaml id="n3h7tq"
{{- define "myapp.name" -}}
{{- .Chart.Name -}}
{{- end -}}
```

This doesn't directly create a Kubernetes resource.

It only defines reusable logic.

You can then call it from another template.

---

# 4. `include` ⭐⭐⭐⭐⭐

`include` is used to call a named template.

Example:

```yaml id="04v2fc"
name: {{ include "myapp.name" . }}
```

Here:

```text id="3yr4x7"
myapp.name
```

is the named template.

And:

```text id="izg8ov"
.
```

passes the current context.

---

# 5. Understanding `.` ⭐⭐⭐⭐⭐

The dot:

```text id="4gy1di"
.
```

represents the **current context**.

For example:

```yaml id="j0t8b9"
{{ include "myapp.name" . }}
```

passes the complete Helm context to the named template.

This allows the helper to access:

```text id="4q6zz8"
.Chart
.Values
.Release
.Capabilities
```

For example:

```yaml id="0kvp4g"
{{- define "myapp.name" -}}
{{- .Chart.Name -}}
{{- end -}}
```

Because `.` was passed, the helper can access:

```text id="x5lh45"
.Chart.Name
```

---

# 6. Basic `_helpers.tpl` Example ⭐⭐⭐⭐⭐

### `_helpers.tpl`

```yaml id="h2i6c5"
{{- define "myapp.name" -}}
{{- .Chart.Name -}}
{{- end -}}
```

### `deployment.yaml`

```yaml id="a2pj2j"
metadata:
  name: {{ include "myapp.name" . }}
```

If the Chart name is:

```text id="g2jyja"
myapp
```

The generated YAML becomes:

```yaml id="pf1i7f"
metadata:
  name: myapp
```

---

# 7. Why Use `_helpers.tpl`? ⭐⭐⭐⭐⭐

Without helpers:

```yaml id="t0v3pl"
metadata:
  name: {{ .Release.Name }}-{{ .Chart.Name }}
```

You may repeat this logic in:

* Deployment
* Service
* ConfigMap
* Ingress
* Secret

This creates duplication.

With `_helpers.tpl`:

```yaml id="05j0h7"
{{ include "myapp.fullname" . }}
```

You define the logic once and reuse it everywhere.

### Benefits

* Less duplicate code
* Consistent naming
* Easier maintenance
* Cleaner templates
* Reusable logic
* Production-friendly Chart structure

# 8. `name` Helper ⭐⭐⭐⭐

A common Helm helper is:

```yaml id="0sp0gi"
{{- define "myapp.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}
```

This creates a reusable application name.

It can support:

```yaml
nameOverride: custom-name
```

from `values.yaml`.

---

# 9. `fullname` Helper ⭐⭐⭐⭐⭐

Another common helper is:

```yaml id="l6z3yv"
{{- define "myapp.fullname" -}}
{{- if .Values.fullnameOverride }}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" }}
{{- else }}
{{- printf "%s-%s" .Release.Name (include "myapp.name" .) | trunc 63 | trimSuffix "-" }}
{{- end }}
{{- end }}
```

This creates a consistent resource name.

For example:

```text id="t5g7dy"
Release Name = production
Chart Name   = myapp
```

Could produce:

```text id="5r8i1q"
production-myapp
```

Then:

```yaml id="z09z7h"
metadata:
  name: {{ include "myapp.fullname" . }}
```

---

# 10. Common Labels ⭐⭐⭐⭐⭐

`_helpers.tpl` is commonly used to create standard Kubernetes labels.

Example:

```yaml id="lq3ax5"
{{- define "myapp.labels" -}}
helm.sh/chart: {{ include "myapp.chart" . }}
{{ include "myapp.selectorLabels" . }}
{{- end }}
```

Then:

```yaml id="fppz0q"
metadata:
  labels:
    {{- include "myapp.labels" . | nindent 4 }}
```

This keeps labels consistent across resources.

---

# 11. Selector Labels

A common helper:

```yaml id="u9n2bb"
{{- define "myapp.selectorLabels" -}}
app.kubernetes.io/name: {{ include "myapp.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}
```

Use it:

```yaml id="m2nqcs"
selector:
  matchLabels:
    {{- include "myapp.selectorLabels" . | nindent 4 }}
```

This is very common in Helm-generated Deployments.

---

# 12. `include` with Pipelines ⭐⭐⭐⭐⭐

One of the most important real-world patterns:

```yaml id="h2okx5"
{{ include "myapp.labels" . | nindent 4 }}
```

Flow:

```text id="i4c0uc"
include
  ↓
Generate labels
  ↓
nindent 4
  ↓
Correct YAML indentation
```

This pattern is extremely common.

---

# 13. Named Template + `dict`

You can pass a custom dictionary to a named template.

Example:

```yaml id="t7g2lq"
{{ include "myapp.example" (dict "name" "test" "env" "prod") }}
```

The named template can access:

```yaml id="o7v6cz"
{{ .name }}
```

and:

```yaml id="4h4fnp"
{{ .env }}
```

This is an advanced technique.

For now, understand the concept:

```text id="6o8e5n"
dict
 ↓
Create custom context
 ↓
Pass context to named template
```

---

# 14. `include` vs `template` ⭐⭐⭐⭐

Both can execute named templates, but there is an important practical difference.

### `template`

```yaml id="4haxg5"
{{ template "myapp.labels" . }}
```

### `include`

```yaml id="g8p8sa"
{{ include "myapp.labels" . }}
```

`include` returns the rendered output as a string, so it can be passed through pipelines.

Example:

```yaml id="h3jq3x"
{{ include "myapp.labels" . | nindent 4 }}
```

This is why **`include` is commonly preferred in Helm Charts**.

---

# 15. Why `_helpers.tpl` Starts with `_`

Files beginning with `_` inside the `templates/` directory are treated as **helper/template files**, not Kubernetes manifests to be directly rendered as resources.

For example:

```text id="6j5j8b"
_helpers.tpl
```

is used for reusable template definitions.

It doesn't produce:

```yaml
kind: Deployment
```

or another Kubernetes resource by itself.

# 16. Complete Practical Example ⭐⭐⭐⭐⭐

### `_helpers.tpl`

```yaml id="q9gjrw"
{{/*
Create a default fully qualified app name.
*/}}
{{- define "myapp.fullname" -}}
{{- printf "%s-%s" .Release.Name .Chart.Name | trunc 63 | trimSuffix "-" }}
{{- end }}

{{/*
Common labels.
*/}}
{{- define "myapp.labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end }}
```

### `deployment.yaml`

```yaml id="6b7x7u"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "myapp.fullname" . }}
  labels:
    {{- include "myapp.labels" . | nindent 4 }}
```

### `service.yaml`

```yaml id="jy1xj7"
apiVersion: v1
kind: Service
metadata:
  name: {{ include "myapp.fullname" . }}
  labels:
    {{- include "myapp.labels" . | nindent 4 }}
```

Now both resources use the same:

```text id="e7v8av"
name
labels
```

logic.

# 18. Debugging Named Templates

Render the entire Chart:

```bash id="o1i8bb"
helm template myapp ./mychart
```

Debug:

```bash id="d0qj11"
helm install myapp ./mychart --dry-run --debug
```

Validate:

```bash id="v8u8f8"
helm lint ./mychart
```

If you get an error such as:

```text
template: myapp/templates/deployment.yaml:
executing "myapp.fullname" at <...>
```

check:

* Template name
* `define`
* `include`
* Context `.`
* Indentation
* Values being passed

# 19. Best Practices ⭐⭐⭐⭐⭐

### Use descriptive names

Good:

```text id="0ivw1f"
myapp.fullname
myapp.labels
myapp.selectorLabels
```

### Keep helpers reusable

Don't put application-specific complex logic everywhere.

### Use `include`

Especially when output needs to be piped:

```yaml id="mt9c0y"
{{ include "myapp.labels" . | nindent 4 }}
```

### Keep naming consistent

Use the same helpers for:

```text id="0g0h6p"
Deployment
Service
Ingress
ConfigMap
Secret
```

### Avoid duplicate template logic

If the same logic appears multiple times, consider moving it into `_helpers.tpl`.
