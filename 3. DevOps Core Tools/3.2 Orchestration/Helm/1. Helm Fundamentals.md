## 1. What is Helm?

**Helm** is a **package manager for Kubernetes**.

It helps you define, install, upgrade, and manage Kubernetes applications using reusable packages called **Helm Charts**.

Instead of maintaining many Kubernetes YAML files manually, Helm allows you to create a reusable template and provide different configuration values.

Example:

Without Helm:

```text
deployment.yaml
service.yaml
configmap.yaml
secret.yaml
ingress.yaml
```

With Helm:

```text
myapp/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    └── ingress.yaml
```

---

## 2. Why Helm is Used

Helm is mainly used to make Kubernetes application deployment **easier, reusable, configurable, and version-controlled**.

### Key benefits

* Simplifies Kubernetes deployments
* Reduces duplicate YAML
* Supports reusable templates
* Supports environment-specific configuration
* Makes application upgrades easier
* Provides rollback capability
* Manages application versions
* Supports dependencies
* Works well with CI/CD
* Works with GitOps tools such as Argo CD

---

## 3. Helm vs Kubernetes YAML

### Traditional Kubernetes YAML

You may need separate YAML files for different environments:

```text
dev-deployment.yaml
test-deployment.yaml
prod-deployment.yaml
```

This can create duplication.

### Helm

You can use one template:

```text
templates/deployment.yaml
```

And different values:

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

For example:

```bash
helm install myapp ./mychart -f values-prod.yaml
```

So, **Helm separates the Kubernetes template from configuration values**.

---

## 4. What is a Helm Chart?

A **Helm Chart** is a collection of files that describes a Kubernetes application.

A basic chart looks like:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── templates/
└── charts/
```

The chart contains:

* Application metadata
* Default configuration
* Kubernetes templates
* Dependencies

Think of a **Chart as a Kubernetes application package**.

---

## 5. What is a Helm Release?

When you install a Helm Chart into a Kubernetes cluster, Helm creates a **Release**.

Example:

```bash
helm install myapp ./mychart
```

Here:

* `mychart` → Chart
* `myapp` → Release name

You can install the same chart multiple times with different release names:

```bash
helm install dev-app ./mychart
helm install prod-app ./mychart
```

Both use the same Chart but create separate Releases.

---

## 6. What is a Helm Repository?

A **Helm Repository** stores and distributes Helm Charts.

You can add a repository:

```bash
helm repo add bitnami https://charts.bitnami.com/bitnami
```

Update repository information:

```bash
helm repo update
```

Search for charts:

```bash
helm search repo nginx
```

---

## 7. What are Helm Values?

**Values** are configuration parameters used by Helm templates.

They are normally stored in:

```text
values.yaml
```

Example:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80
```

The template can use these values:

```yaml
replicas: {{ .Values.replicaCount }}
```

This allows the same chart to be used for different environments.

---

## 8. What are Helm Templates?

Helm uses **Go template syntax** to dynamically generate Kubernetes YAML.

Example:

```yaml
replicas: {{ .Values.replicaCount }}
```

If:

```yaml
replicaCount: 3
```

Helm generates:

```yaml
replicas: 3
```

This is one of the **most important Helm concepts** to understand.

---

## 9. Helm 3 Architecture

Helm 3 uses a **client-only architecture**.

There is no separate **Tiller** component.

### Helm 2

```text
Helm Client
     ↓
  Tiller
     ↓
Kubernetes
```

### Helm 3

```text
Helm CLI
    ↓
Kubernetes API Server
    ↓
Kubernetes Cluster
```

Helm 3 removed Tiller, improving security and simplifying the architecture.

## 10. Helm in DevOps / CI-CD / GitOps

Helm is commonly used to package and deploy Kubernetes applications.

A typical CI/CD flow:

```text
Developer
    ↓
Git
    ↓
CI Pipeline
    ↓
Build Docker Image
    ↓
Push Image
    ↓
Update Helm Values
    ↓
Deploy to Kubernetes
```

With GitOps:

```text
Git Repository
      ↓
Helm Chart
      ↓
Argo CD
      ↓
Kubernetes
```

This is especially important because **Helm + Argo CD** is a common combination in modern DevOps environments.
