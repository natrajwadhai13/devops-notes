# 1. GitOps

**GitOps** is a deployment approach where **Git is treated as the single source of truth for the desired state of the Kubernetes environment**.

In simple words:

> **Whatever configuration is stored in Git should be the desired state of Kubernetes.**

### Traditional Deployment

```text
Developer
   ↓
Git
   ↓
CI Pipeline
   ↓
kubectl / Helm
   ↓
Kubernetes
```

The CI pipeline directly changes the Kubernetes cluster.

### GitOps

```text
Developer
   ↓
Git Repository
   ↓
Argo CD
   ↓
Kubernetes
```

Argo CD continuously checks Git and makes the cluster match the desired state.

---

# 2. GitOps Architecture ⭐⭐⭐

A typical Kubernetes GitOps setup:

```text
                Developer
                    ↓
                Git Push
                    ↓
             ┌─────────────┐
             │ Git Repo    │
             │ Manifests   │
             │ Helm Charts │
             └──────┬──────┘
                    ↓
                 Argo CD
                    ↓
              Kubernetes API
                    ↓
               K8s Cluster
                    ↓
                  Pods
```

Example Git repository:

```text
k8s-manifests/
├── deployment.yaml
├── service.yaml
├── ingress.yaml
└── configmap.yaml
```

Or with Helm:

```text
helm-chart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml
```

# 3. Argo CD ⭐⭐⭐

**Argo CD** is a **GitOps continuous delivery tool for Kubernetes**.

In simple words:

> **Argo CD continuously compares the Kubernetes cluster with the configuration stored in Git and synchronizes the cluster when they differ.**

### Flow

```text
Git
 ↓
Desired State
 ↓
Argo CD
 ↓
Compare
 ↓
Kubernetes Cluster
```

---

## Desired State vs Actual State

Suppose Git says:

```yaml
replicas: 3
```

But the Kubernetes cluster currently has:

```text
Running Pods = 2
```

Argo CD detects:

```text
Git Desired State = 3
Cluster Actual State = 2

        ↓

Difference detected
        ↓

Argo CD Sync
        ↓

Cluster = 3 Pods
```

This is called **reconciliation**.

---

# 4. Argo CD Sync

Argo CD can synchronize Git configuration to Kubernetes.

### Automatic Sync

```text
Git change
    ↓
Argo CD detects change
    ↓
Sync
    ↓
Kubernetes updated
```

### Manual Sync

You can also configure Argo CD so that changes require an explicit sync.

```text
Git change
    ↓
Argo CD detects OutOfSync
    ↓
Engineer approves/syncs
    ↓
Kubernetes updated
```

---

# 5. Argo CD Application

In Argo CD, an **Application** represents the relationship between:

```text
Git Repository
      +
Kubernetes Cluster
      +
Namespace
```

Conceptually:

```text
Argo CD Application
│
├── Source
│    └── Git repository
│
├── Destination
│    ├── Cluster
│    └── Namespace
│
└── Sync Policy
```

---

# 6. Argo CD Application States

Common states:

### Synced

```text
Git = Kubernetes
```

Everything matches.

### OutOfSync ⭐

```text
Git ≠ Kubernetes
```

There is a difference between the desired and actual state.

### Healthy

Application resources are working correctly.

### Degraded

Something is unhealthy.

For example:

```text
Deployment
   ↓
Pods failing
   ↓
Argo CD
   ↓
Degraded
```

# 7. CI/CD with Kubernetes ⭐⭐⭐

A Kubernetes CI/CD pipeline commonly separates **CI** and **CD**.

### CI — Continuous Integration

CI handles:

```text
Code
 ↓
Build
 ↓
Test
 ↓
Docker Image
 ↓
Container Registry
```

Example:

```text
Developer
   ↓
Git Push
   ↓
Jenkins / GitHub Actions / GitLab CI
   ↓
Build Application
   ↓
Run Tests
   ↓
Build Docker Image
   ↓
Push Image
   ↓
ECR / ACR / GCR
```

---

# 8. CD — Continuous Delivery

With GitOps, CD can look like:

```text
New Docker Image
      ↓
Update image tag in Git
      ↓
Git Repository
      ↓
Argo CD
      ↓
Kubernetes
      ↓
New Pods
```

This is a very common modern Kubernetes architecture.

# 9. Complete GitOps CI/CD Flow ⭐⭐⭐

This is the flow you should remember for interviews:

```text
Developer
    ↓
Git Push
    ↓
CI Pipeline
    ↓
Build + Test
    ↓
Docker Image
    ↓
Container Registry
    ↓
Update Kubernetes Manifest
    ↓
GitOps Repository
    ↓
Argo CD
    ↓
Kubernetes Cluster
    ↓
Deployment
```

### Example

Suppose application version changes:

```text
v1.0 → v1.1
```

CI builds:

```text
my-app:1.1
```

Pushes it to:

```text
Amazon ECR
```

Then GitOps repository is updated:

```yaml
image:
  repository: <registry>/my-app
  tag: "1.1"
```

Argo CD detects the Git change:

```text
Git
 ↓
Argo CD
 ↓
Kubernetes
 ↓
Deployment updated
 ↓
Rolling update
 ↓
Pods running v1.1
```

# 10. Why GitOps? ⭐

Main benefits:

### Version Control

All Kubernetes configuration is stored in Git.

```text
Who changed?
When?
What changed?
```

Git provides the history.

### Rollback

If a deployment is bad:

```text
Current
  ↓
v1.1 ❌
  ↓
Git revert
  ↓
v1.0
  ↓
Argo CD
  ↓
Kubernetes
```

### Auditability

You can see:

```text
Developer
   ↓
Git Commit
   ↓
Configuration Change
```

### Self-Healing / Reconciliation

If someone manually changes the cluster:

```text
Git = 3 replicas
Kubernetes = 5 replicas
```

Argo CD can detect the drift and, depending on the configured sync policy, restore the desired Git state.

---

# 11. GitOps vs Traditional CI/CD ⭐

### Traditional

```text
CI/CD
  ↓
kubectl apply
  ↓
Kubernetes
```

The CI system directly modifies the cluster.

### GitOps

```text
CI
 ↓
Build Image
 ↓
Git
 ↓
Argo CD
 ↓
Kubernetes
```

The deployment configuration is stored in Git and Argo CD handles reconciliation.

---

# 12. Important Interview Question

### "Does Argo CD build Docker images?"

**No.**

Argo CD is primarily a **continuous delivery/GitOps tool**.

```text
CI Tool
 ↓
Build + Test + Docker Image
```

```text
Argo CD
 ↓
Deploy/Synchronize Kubernetes desired state
```

So:

> **CI builds the application. Argo CD deploys the desired Kubernetes state.**

---

# ⭐ Interview Answer — GitOps

> **GitOps is a deployment methodology where Git acts as the single source of truth for the desired Kubernetes state. Kubernetes manifests or Helm charts are maintained in Git, and Argo CD continuously monitors the repository and reconciles the Kubernetes cluster with the desired state. This provides version control, auditability, consistent deployments, and easy rollback.**

# ⭐ Interview Answer — Argo CD

> **Argo CD is a GitOps continuous delivery tool for Kubernetes. It monitors the Kubernetes configuration stored in Git, compares it with the actual cluster state, and synchronizes the cluster when there is a difference. It helps automate deployments and maintain the desired state.**

# ⭐ Interview Answer — Kubernetes CI/CD

> **In a Kubernetes CI/CD pipeline, CI is responsible for building the application, running tests, creating the Docker image, and pushing it to a container registry. For CD, we can use GitOps with Argo CD. The Kubernetes manifests or Helm values are updated in Git, and Argo CD detects the change and deploys the desired state to the Kubernetes cluster.**

### 🔥 One-line memory

```text
CI → Build & Test → Docker Image → Registry

GitOps → Git = Desired State

Argo CD → Git → Kubernetes

Kubernetes → Runs the Application
```
