## ClusterIP

**ClusterIP** is the **default Kubernetes Service type**. It provides a **stable internal IP address** to access Pods **inside the Kubernetes cluster**.

### Simple Example

Suppose you have 3 backend Pods:

```text
             Backend Pods
          ┌─────┬─────┬─────┐
          │Pod 1│Pod 2│Pod 3│
          └──┬──┴──┬──┴──┬──┘
             │     │     │
             └─────┼─────┘
                   ↓
              ClusterIP
             10.96.10.100
                   ↓
             Frontend Pod
```

The Frontend doesn't need to know the individual Pod IPs. It connects to the **Service**, and the Service forwards traffic to the backend Pods.

### Example YAML

```yaml
apiVersion: v1
kind: Service

metadata:
  name: backend-service

spec:
  type: ClusterIP

  selector:
    app: backend

  ports:
    - port: 80
      targetPort: 8080
```

Here:

* `type: ClusterIP` → Internal-only Service
* `selector: app: backend` → Finds backend Pods using their label
* `port: 80` → Service port
* `targetPort: 8080` → Pod/container port

### How it works

```text
Frontend Pod
     │
     │ backend-service:80
     ↓
ClusterIP
     │
     ├──→ Backend Pod 1 :8080
     ├──→ Backend Pod 2 :8080
     └──→ Backend Pod 3 :8080
```

The Service provides **stable networking** even when Pods are recreated and their IP addresses change.

### Important Point ⭐

ClusterIP is **not directly accessible from the public internet** by default.

It is mainly used for **internal communication between applications inside the cluster**.

Example:

```text
Frontend → Backend
Backend → Database
Microservice A → Microservice B
```

### Common Command

```bash
kubectl get services
```

Example:

```text
NAME              TYPE        CLUSTER-IP      PORT
backend-service   ClusterIP   10.96.10.100    80
```

### ClusterIP vs NodePort vs LoadBalancer

| Service Type     | Access                                      |
| ---------------- | ------------------------------------------- |
| **ClusterIP**    | Inside cluster                              |
| **NodePort**     | Outside cluster through Node IP + port      |
| **LoadBalancer** | External access through cloud load balancer |

### ⭐ Interview Answer

> **ClusterIP is the default Kubernetes Service type. It provides a stable virtual IP and DNS name for accessing Pods internally within the Kubernetes cluster. It is mainly used for communication between services or applications inside the cluster.**

**Easy to remember:**

> **ClusterIP = Internal communication**
> **NodePort = External access through Node**
> **LoadBalancer = External access through Load Balancer**

## NodePort

**NodePort** is a Kubernetes Service type that exposes an application **outside the Kubernetes cluster** using a specific port on every eligible Node.

### Simple Example

Suppose your application is running on Pods:

```text
              Kubernetes Cluster
                     │
              ┌──────┴──────┐
              │   Service    │
              │  NodePort    │
              │   :30080     │
              └──────┬──────┘
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
       Node 1      Node 2     Node 3
          │
       Pod 1       Pod 2      Pod 3
```

You can access the application using:

```text
http://<Node-IP>:30080
```

### Example YAML

```yaml
apiVersion: v1
kind: Service

metadata:
  name: my-app

spec:
  type: NodePort

  selector:
    app: my-app

  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
```

Here:

* **`port: 80`** → Service port
* **`targetPort: 8080`** → Application/Pod port
* **`nodePort: 30080`** → Port exposed on the Node

Traffic flow:

```text
Client
  ↓
Node-IP:30080
  ↓
NodePort Service
  ↓
Pod :8080
```

### NodePort Range

By default, Kubernetes NodePort uses:

```text
30000–32767
```

So `30080` is a valid NodePort.

### Important Point ⭐

You don't have to access the specific Node where the Pod is running. Kubernetes networking can route the request to an appropriate backend Pod.

### ClusterIP vs NodePort

| ClusterIP                               | NodePort                                  |
| --------------------------------------- | ----------------------------------------- |
| Internal access                         | External access                           |
| Default Service type                    | Explicitly configured                     |
| Uses ClusterIP                          | Uses Node IP + NodePort                   |
| Mainly service-to-service communication | Useful for simple external access/testing |

```text
ClusterIP:
Pod → Service → Pod

NodePort:
External Client → NodeIP:NodePort → Service → Pod
```

### When to use NodePort?

Good for:

* **Testing**
* **Development**
* Simple external access
* Learning Kubernetes networking

For production cloud environments, **LoadBalancer or Ingress** is generally preferred.

### ⭐ Interview Answer

> **NodePort is a Kubernetes Service type that exposes an application externally through a static port on each Node. Clients can access the application using the Node IP and NodePort, and Kubernetes forwards the traffic to the backend Pods.**

**Easy to remember:**

> **ClusterIP = Inside cluster**
> **NodePort = Node IP + Port**
> **LoadBalancer = Cloud Load Balancer**

## LoadBalancer

**LoadBalancer** is a Kubernetes Service type used to **expose an application outside the Kubernetes cluster through an external load balancer**.

In cloud environments like **AWS, Azure, and GCP**, Kubernetes can request the cloud provider to create a load balancer.

### Simple Example

```text id="q6g8xj"
              Internet
                  │
                  ↓
        Cloud Load Balancer
          (AWS / Azure / GCP)
                  │
                  ↓
          LoadBalancer Service
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Pod 1     Pod 2     Pod 3
```

### Example YAML

```yaml id="p8n1st"
apiVersion: v1
kind: Service

metadata:
  name: my-app

spec:
  type: LoadBalancer

  selector:
    app: my-app

  ports:
    - port: 80
      targetPort: 8080
```

After creating the Service:

```bash id="8x6f1n"
kubectl get service my-app
```

You may see:

```text
NAME     TYPE           CLUSTER-IP     EXTERNAL-IP
my-app   LoadBalancer   10.96.10.20    20.x.x.x
```

The **EXTERNAL-IP** is provided by the cloud load-balancing infrastructure.

### Traffic Flow

```text id="x7o1eq"
User
  ↓
External Load Balancer
  ↓
LoadBalancer Service
  ↓
Kubernetes Service
  ↓
Pods
```

### In AWS EKS

For example:

```text id="h9y1xy"
Internet
   ↓
AWS Load Balancer
   ↓
EKS Service
   ↓
Pods
```

Depending on the configuration and AWS integration, Kubernetes can provision an AWS load-balancing resource.

### ClusterIP vs NodePort vs LoadBalancer ⭐

| Type             | Access                 | Common Use                     |
| ---------------- | ---------------------- | ------------------------------ |
| **ClusterIP**    | Internal               | Service-to-service             |
| **NodePort**     | Node IP + Port         | Testing/simple external access |
| **LoadBalancer** | External Load Balancer | Cloud-based external access    |

```text id="e5u5gc"
ClusterIP
   ↓
Internal


NodePort
   ↓
Node-IP:30080
   ↓
External


LoadBalancer
   ↓
Cloud Load Balancer
   ↓
External
```

### Important Interview Point

`LoadBalancer` is generally used to expose a **Service externally**. In cloud Kubernetes, the cloud provider integrates with Kubernetes to provision/configure the external load-balancing infrastructure.

### ⭐ Interview Answer

> **LoadBalancer is a Kubernetes Service type used to expose an application externally through a cloud load balancer. In managed Kubernetes services such as EKS, AKS, and GKE, it can provision or configure the appropriate cloud load-balancing resource and route traffic to the application Pods.**

**Easy to remember:**

> **ClusterIP → Internal**
> **NodePort → Node IP + Port**
> **LoadBalancer → External Cloud Load Balancer**

## Ingress

**Ingress** is a Kubernetes API object used to **manage external HTTP/HTTPS traffic to services inside the cluster**.

In simple words:

> **Ingress acts as an entry point for web traffic and routes requests to different Kubernetes Services based on the hostname or URL path.**

### Simple Example

Suppose you have three applications:

```text
Internet
   │
   ↓
Ingress
   │
   ├── example.com/        → Frontend Service
   ├── example.com/api     → Backend Service
   └── example.com/admin   → Admin Service
```

Instead of creating a separate `LoadBalancer` Service for every application, you can use **one Ingress entry point** and route traffic to multiple Services.

### Traffic Flow

```text
User
  ↓
External Load Balancer
  ↓
Ingress Controller
  ↓
Ingress Rules
  ├── /       → Frontend Service
  ├── /api    → Backend Service
  └── /admin  → Admin Service
                  ↓
                Pods
```

### Ingress vs Ingress Controller ⭐

These two are different:

**Ingress**

> Defines the **routing rules**.

**Ingress Controller**

> Actually **implements those rules and handles the traffic**.

Examples of Ingress Controllers:

* NGINX Ingress Controller
* AWS Load Balancer Controller
* Traefik
* HAProxy

```text
Ingress
   ↓
Routing Rules
   ↓
Ingress Controller
   ↓
Kubernetes Services
   ↓
Pods
```

### Example YAML

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: app-ingress

spec:
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 80
```

Here:

```text
example.com/      → frontend-service
example.com/api   → backend-service
```

### Ingress vs LoadBalancer

| LoadBalancer                              | Ingress                            |
| ----------------------------------------- | ---------------------------------- |
| Exposes a Service externally              | Routes external HTTP/HTTPS traffic |
| Usually one external endpoint per Service | Can route to multiple Services     |
| L4/load-balancing focus                   | L7 HTTP/HTTPS routing              |
| Simple external exposure                  | Host/path-based routing            |
| Cloud load balancer commonly used         | Requires an Ingress Controller     |

### Important Point

Ingress is mainly for **HTTP and HTTPS** traffic. For TCP/UDP or other non-HTTP traffic, other Kubernetes/networking mechanisms are generally used.

### ⭐ Interview Answer

> **Ingress is a Kubernetes API object that defines rules for routing external HTTP/HTTPS traffic to Services inside the cluster. An Ingress Controller implements these rules and forwards requests to the appropriate backend Services.**

**Easy to remember:**

> **Service → Exposes application**
> **Ingress → Routes web traffic to Services**
> **Ingress Controller → Implements the routing**

<a id="Ingress Controller"></a>

## Ingress Controller

An **Ingress Controller** is the component that **actually implements and processes the routing rules defined in an Ingress resource**.

In simple words:

> **Ingress = Rules**
> **Ingress Controller = Executes those rules**

### Simple Architecture

```text
                    Internet
                       │
                       ↓
              Ingress Controller
                       │
                Reads Ingress Rules
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
     Frontend       Backend       Admin
      Service       Service       Service
          ↓            ↓            ↓
        Pods         Pods         Pods
```

### Example

Ingress rules:

```yaml
spec:
  rules:
    - host: example.com
      http:
        paths:
          - path: /
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

          - path: /api
            backend:
              service:
                name: backend-service
                port:
                  number: 80
```

The **Ingress Controller** receives the request and routes it:

```text
https://example.com/
       ↓
Frontend Service


https://example.com/api
       ↓
Backend Service
```

### Common Ingress Controllers

Examples include:

* **NGINX Ingress Controller**
* **AWS Load Balancer Controller**
* **Traefik**
* **HAProxy**

### What does an Ingress Controller do?

It can handle:

* HTTP/HTTPS routing
* Host-based routing
* Path-based routing
* TLS/SSL termination
* Load balancing
* Redirects and rewrites

### In EKS Example

A common AWS setup can look like:

```text
Internet
   ↓
AWS Load Balancer
   ↓
AWS Load Balancer Controller
   ↓
Kubernetes Service
   ↓
Pods
```

The exact architecture depends on which AWS load-balancing approach and configuration you use.

### Ingress vs Ingress Controller ⭐

| Ingress                            | Ingress Controller                               |
| ---------------------------------- | ------------------------------------------------ |
| Kubernetes API resource            | Running controller/software                      |
| Defines routing rules              | Implements routing rules                         |
| YAML configuration                 | Watches Kubernetes resources and handles traffic |
| Does not process traffic by itself | Actually processes/routes traffic                |

### ⭐ Interview Answer

> **An Ingress Controller is a Kubernetes component that implements the rules defined in an Ingress resource. It receives external HTTP/HTTPS traffic and routes it to the appropriate Kubernetes Services based on host or path rules.**

**Easy to remember:**

> **Ingress = What should happen?**
> **Ingress Controller = Actually makes it happen.**

## AKS Example — Ingress Controller

In **AKS**, a common setup is to use an **NGINX Ingress Controller** to route external HTTP/HTTPS traffic to multiple applications inside the cluster.

### Architecture

```text
                    Internet
                       │
                       ↓
              Azure Load Balancer
                       │
                       ↓
             NGINX Ingress Controller
                       │
                Ingress Rules
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
      Frontend       Backend       Admin
      Service        Service       Service
          ↓            ↓            ↓
        Pods          Pods         Pods
```

### Example

Suppose your AKS cluster has:

```text
frontend-service
backend-service
admin-service
```

You want:

```text
https://myapp.com/        → Frontend
https://myapp.com/api     → Backend
https://myapp.com/admin   → Admin
```

The **Ingress** defines these routing rules:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: myapp.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 80

          - path: /admin
            pathType: Prefix
            backend:
              service:
                name: admin-service
                port:
                  number: 80
```

### How the request flows

```text
User
 │
 │ https://myapp.com/api
 ↓
Azure Load Balancer
 │
 ↓
NGINX Ingress Controller
 │
 │ Reads Ingress rule
 ↓
backend-service
 │
 ↓
Backend Pod
```

### What does each component do?

**Azure Load Balancer**

> Provides the external entry point/IP.

**NGINX Ingress Controller**

> Receives HTTP/HTTPS requests and processes the routing rules.

**Ingress**

> Defines where `/`, `/api`, `/admin` requests should go.

**Service**

> Provides stable access to the backend Pods.

**Pod**

> Runs the actual application.

### ⭐ Interview Answer

> **In AKS, I can use an NGINX Ingress Controller to expose multiple applications through a single external entry point. Azure Load Balancer receives the external traffic and forwards it to the NGINX Ingress Controller. The Ingress Controller reads the Ingress rules and routes requests based on hostname or path to the appropriate Kubernetes Services and Pods.**

### One important interview distinction

Don't say:

> ❌ "Ingress Controller is the Azure Load Balancer."

Say:

> ✅ **"Azure Load Balancer provides the external entry point, while the NGINX Ingress Controller handles HTTP/HTTPS routing based on Ingress rules."**

For **modern AKS**, there are also Azure-native ingress/load-balancing options, so the exact architecture depends on which AKS ingress solution you choose.

## DNS in Kubernetes

**DNS (Domain Name System)** converts a **name into an IP address**. In Kubernetes, DNS provides **service discovery**, allowing Pods to communicate with Services using names instead of IP addresses.

### Simple Example

Instead of using a Service IP:

```text
10.96.20.10
```

A Pod can communicate using the Service name:

```text
backend-service
```

```text
Frontend Pod
     │
     │ backend-service
     ↓
Kubernetes DNS
     ↓
backend-service → Service IP
     ↓
Backend Pods
```

### Kubernetes DNS

Kubernetes normally uses **CoreDNS** for cluster DNS.

```text
Pod
 ↓
CoreDNS
 ↓
Service DNS name
 ↓
Service
 ↓
Pod
```

### Service DNS Name

A Service can be accessed using:

```text
<service-name>.<namespace>.svc.cluster.local
```

Example:

```text
backend-service.dev.svc.cluster.local
```

Where:

```text
backend-service → Service name
dev             → Namespace
svc             → Kubernetes Service
cluster.local   → Cluster DNS domain
```

### Example

Suppose:

```text
Service: backend-service
Namespace: production
```

Another Pod can access it using:

```text
backend-service.production.svc.cluster.local
```

Usually, within the same namespace, you can simply use:

```text
backend-service
```

### Why is Kubernetes DNS important?

* **Service discovery**
* Pods can communicate using **Service names**
* Avoids depending on changing Pod IPs
* Enables communication between applications
* Provides DNS names for Services and Pods

### Pod vs Service DNS ⭐

**Pod IP:**

```text
10.244.1.15
```

Can change when the Pod is recreated.

**Service DNS:**

```text
backend-service
```

Remains stable even when backend Pods change.

```text
Frontend
   ↓
backend-service
   ↓
Service
   ↓
Pod 1 / Pod 2 / Pod 3
```

### ⭐ Interview Answer

> **Kubernetes DNS provides service discovery inside the cluster. CoreDNS resolves Kubernetes Service names to their corresponding Service IPs, allowing Pods to communicate using stable DNS names instead of changing Pod IP addresses.**

**Easy to remember:**

> **DNS = Name → IP**
> **CoreDNS = Kubernetes DNS**
> **Service DNS = Stable service discovery**

## NetworkPolicy

**NetworkPolicy** is a Kubernetes security mechanism used to **control network traffic between Pods and from external sources to Pods**.

In simple words:

> **NetworkPolicy defines which Pods are allowed to communicate with which other Pods.**

### Simple Example

Suppose you have:

```text
Frontend Pod
     │
     │ ✅ Allowed
     ↓
Backend Pod
     │
     │ ❌ Not Allowed
     ↓
Database Pod
```

You can create a policy that allows only the **Backend Pod** to communicate with the Database.

```text
Frontend → Backend     ✅
Backend  → Database    ✅
Frontend → Database    ❌
```

### Example YAML

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: allow-backend-to-db

spec:
  podSelector:
    matchLabels:
      app: database

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: backend
```

This means:

> Only Pods with `app=backend` are allowed to send traffic to Pods with `app=database`.

### How it works

```text
                 NetworkPolicy
                      │
             ┌────────┴────────┐
             ↓                 ↓
        Allowed Traffic    Blocked Traffic
             │                 │
        Backend → DB       Frontend → DB
             ✅                 ❌
```

### Common Uses

NetworkPolicy can be used to:

* Restrict **Pod-to-Pod communication**
* Allow only required application traffic
* Isolate databases
* Improve application security
* Implement **network segmentation**
* Control **Ingress and Egress** traffic

### Ingress vs Egress

**Ingress** → Incoming traffic to a Pod

```text
Backend → Database
           ↓
        Ingress
```

**Egress** → Outgoing traffic from a Pod

```text
Database → External Service
    ↓
 Egress
```

### Important Point ⭐

NetworkPolicy works only if the Kubernetes **network plugin/CNI supports NetworkPolicy**.

Also, once a Pod is selected by a policy for a particular traffic direction, the allowed traffic for that direction becomes restricted according to the applicable policies.

### NetworkPolicy vs Service

| Service                         | NetworkPolicy                     |
| ------------------------------- | --------------------------------- |
| Provides network access to Pods | Controls network access           |
| Service discovery               | Security/traffic restriction      |
| Routes traffic                  | Allows/denies traffic             |
| Example: `backend-service`      | Example: allow backend → database |

### ⭐ Interview Answer

> **NetworkPolicy is used to control and restrict network communication between Kubernetes Pods and other network endpoints. It can define which traffic is allowed for ingress and egress, helping implement network-level security and isolation.**

**Easy to remember:**

> **Service = How to reach the Pod**
> **NetworkPolicy = Who is allowed to reach the Pod**
