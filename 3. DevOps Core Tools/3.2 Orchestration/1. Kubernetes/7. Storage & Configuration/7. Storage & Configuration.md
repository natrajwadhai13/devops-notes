## Volume

A **Volume** in Kubernetes provides **storage to containers inside a Pod**. It is used when an application needs to store or share data beyond the normal container filesystem.

### Why do we need Volume?

Container filesystem is generally **ephemeral**. If a container is deleted and recreated, data stored only inside that container may be lost.

```text id="l1g5r2"
Without Volume:

Container
   ↓
Application Data
   ↓
Container deleted ❌
   ↓
Data lost
```

With a Volume:

```text id="b4qk7m"
Container
    ↓
   Volume
    ↓
Persistent/Shared Storage
    ↓
Container recreated
    ↓
Data available
```

### Volume inside a Pod

A Volume can also be **shared between multiple containers in the same Pod**.

```text id="w7e4p1"
                 Pod
        ┌──────────────────┐
        │ App Container    │
        │       ↓          │
        │    Shared Volume │
        │       ↑          │
        │ Sidecar Container│
        └──────────────────┘
```

### Example

```yaml id="7v4jqp"
apiVersion: v1
kind: Pod

metadata:
  name: volume-demo

spec:
  containers:
    - name: app
      image: nginx
      volumeMounts:
        - name: app-data
          mountPath: /data

  volumes:
    - name: app-data
      emptyDir: {}
```

Here:

```text id="0oy8e7"
Volume name  → app-data
Mount path   → /data
Volume type  → emptyDir
```

### Common Kubernetes Volume Types

Some common storage types are:

- **emptyDir** → Temporary storage shared by containers in a Pod
- **hostPath** → Mounts a directory from the Node
- **PersistentVolume (PV)** → Cluster storage resource
- **PersistentVolumeClaim (PVC)** → Request for storage
- **CSI volumes** → Storage provided through CSI drivers, such as cloud disks/filesystems

### Volume vs PV vs PVC ⭐

This is important for interviews:

```text id="e3y9pl"
Pod
 ↓
Volume
 ↓
Storage

For persistent storage:

Pod
 ↓
PVC
 ↓
PV
 ↓
Actual Storage
```

**Volume** → Makes storage available to a Pod.

**PVC** → Application's request for storage.

**PV** → Storage resource available to Kubernetes.

### Volume vs Container Storage

| Container Filesystem                           | Volume                                    |
| ---------------------------------------------- | ----------------------------------------- |
| Usually ephemeral                              | Can provide longer-lived storage          |
| Data can disappear when container is recreated | Data can persist depending on volume type |
| Belongs to container                           | Can be shared between containers          |
| Limited to container lifecycle                 | Can have a separate storage lifecycle     |

### ⭐ Interview Answer

> **A Kubernetes Volume provides storage to containers running inside a Pod. Volumes can be used to share data between containers and, depending on the volume type, preserve data beyond the lifecycle of a container. For persistent application storage, Kubernetes commonly uses PVCs, PVs, and storage backends.**

**Easy to remember:**

> **Volume = Storage attached to Pod**
> **PVC = Request for storage**
> **PV = Storage resource**

## PV — PersistentVolume

A **PersistentVolume (PV)** is a **storage resource in a Kubernetes cluster** that provides persistent storage for applications.

In simple words:

> **PV is the actual storage resource that Kubernetes makes available to Pods.**

### Simple Flow

```text
Pod
 ↓
PVC (Storage Request)
 ↓
PV (Storage Resource)
 ↓
Actual Storage
```

For example:

```text
Application
    ↓
   PVC
    ↓
   PV
    ↓
Azure Disk / AWS EBS / NFS / etc.
```

### Why do we need PV?

Pod/container storage can be temporary. For applications like databases, we need data to **survive Pod/container recreation**.

```text
Pod
 ↓
Database Data
 ↓
Pod deleted ❌
 ↓
New Pod
 ↓
Same persistent data ✅
```

### Example PV

```yaml
apiVersion: v1
kind: PersistentVolume

metadata:
  name: mysql-pv

spec:
  capacity:
    storage: 10Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  hostPath:
    path: /data/mysql
```

Here:

- `storage: 10Gi` → PV provides 10 GB
- `ReadWriteOnce` → Can be mounted read/write by one node at a time
- `Retain` → Keep the storage/data when the PVC is deleted
- `hostPath` → Uses storage from the Kubernetes node

### PV Access Modes

Common access modes:

| Access Mode             | Meaning                        |
| ----------------------- | ------------------------------ |
| **ReadWriteOnce (RWO)** | Read/write from one node       |
| **ReadOnlyMany (ROX)**  | Read-only from multiple nodes  |
| **ReadWriteMany (RWX)** | Read/write from multiple nodes |

### PV vs PVC ⭐

**PV:**

> Provides storage.

**PVC:**

> Requests storage.

```text
Administrator
     ↓
    PV
     ↑
    PVC
     ↑
Application / Pod
```

Example:

```yaml
# PVC requests 10Gi
spec:
  resources:
    requests:
      storage: 10Gi
```

Kubernetes then finds a suitable PV for that request.

### Static vs Dynamic Provisioning

**Static provisioning:**

```text
Admin creates PV
      ↓
PVC
      ↓
PV
```

**Dynamic provisioning:**

```text
PVC
 ↓
StorageClass
 ↓
Automatically creates PV
 ↓
Cloud Storage
```

Dynamic provisioning is very common in **EKS, AKS, and GKE**.

### ⭐ Interview Answer

> **PersistentVolume is a Kubernetes storage resource that provides persistent storage to applications. A PV can be backed by storage such as cloud disks, file systems, or other storage systems. Applications normally request this storage through a PersistentVolumeClaim.**

**Easy to remember:**

> **PV = Storage available**
> **PVC = Storage requested**
> **StorageClass = Automatically provision storage**

## PVC — PersistentVolumeClaim

A **PersistentVolumeClaim (PVC)** is a **request for storage made by an application/user** in Kubernetes.

In simple words:

> **PVC asks Kubernetes for the storage that a Pod needs.**

### Simple Flow

```text
Pod
 ↓
PVC → "I need 10 GB storage"
 ↓
PV → Provides 10 GB storage
 ↓
Actual Storage
```

### Example

A PVC can request:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: mysql-pvc

spec:
  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 10Gi
```

Here:

```text
PVC name     → mysql-pvc
Storage      → 10Gi
Access Mode  → ReadWriteOnce
```

Kubernetes looks for a suitable **PV**. With dynamic provisioning, it can use a **StorageClass** to create the required storage automatically.

### Using PVC in a Pod

```yaml
volumes:
  - name: mysql-data
    persistentVolumeClaim:
      claimName: mysql-pvc
```

Then mount it:

```yaml
volumeMounts:
  - name: mysql-data
    mountPath: /var/lib/mysql
```

Flow:

```text
MySQL Pod
    ↓
mysql-pvc
    ↓
PersistentVolume
    ↓
AWS EBS / Azure Disk / GCP Disk
```

### PV vs PVC vs StorageClass ⭐

| Resource         | Meaning                                               |
| ---------------- | ----------------------------------------------------- |
| **PV**           | Storage resource available to Kubernetes              |
| **PVC**          | Request for storage                                   |
| **StorageClass** | Defines how storage should be dynamically provisioned |

Easy example:

> **PV = House** 🏠
> **PVC = Request to rent a house** 📝
> **StorageClass = Rules for providing the house** ⚙️

### Static Provisioning

```text
Admin
 ↓
Creates PV
 ↓
PVC
 ↓
PV gets bound to PVC
 ↓
Pod uses PVC
```

### Dynamic Provisioning

```text
Pod
 ↓
PVC
 ↓
StorageClass
 ↓
Automatically creates PV
 ↓
Cloud Storage
```

### Important Point

A Pod normally **uses the PVC**, not the PV directly.

```text
Pod → PVC → PV → Storage
```

### ⭐ Interview Answer

> **A PersistentVolumeClaim is a request for persistent storage in Kubernetes. The application creates a PVC specifying requirements such as storage size and access mode, and Kubernetes binds it to a suitable PersistentVolume. With dynamic provisioning, a StorageClass can automatically create the required PV.**

**Easy to remember:**

> **PV = Provides storage**
> **PVC = Requests storage**
> **StorageClass = Dynamically provisions storage**

</details>

## StorageClass

A **StorageClass** in Kubernetes defines **how persistent storage should be dynamically created/provisioned**.

In simple words:

> **StorageClass tells Kubernetes what type of storage to create when an application requests storage through a PVC.**

### Simple Flow

```text
Pod
 ↓
PVC
 ↓
StorageClass
 ↓
Dynamic Provisioning
 ↓
PV
 ↓
Cloud Storage
```

For example, in **AKS**:

```text
Application
    ↓
PVC: "I need 10 GB"
    ↓
StorageClass
    ↓
Azure Disk is dynamically created
    ↓
PV
    ↓
Pod uses storage
```

### Why do we need StorageClass?

Without dynamic provisioning, an administrator may need to manually create PVs.

With StorageClass:

```text
Without StorageClass:
Admin → Create PV → PVC → Pod

With StorageClass:
PVC → StorageClass → Automatically create PV → Pod
```

This makes storage management **automated and scalable**.

### Example

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass

metadata:
  name: fast-storage

provisioner: disk.csi.azure.com

parameters:
  skuName: Premium_LRS

reclaimPolicy: Delete

volumeBindingMode: WaitForFirstConsumer
```

This example tells Kubernetes to use the **Azure Disk CSI driver** to dynamically provision storage.

### PVC using StorageClass

```yaml
apiVersion: v1
kind: PersistentVolumeClaim

metadata:
  name: app-pvc

spec:
  storageClassName: fast-storage

  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 10Gi
```

Flow:

```text
PVC
 │
 │ storageClassName: fast-storage
 ↓
StorageClass
 │
 ↓
Azure Disk
 │
 ↓
PV
 │
 ↓
Pod
```

### Important Fields

**`provisioner`**
Defines which storage plugin/CSI driver creates the storage.

**`parameters`**
Defines storage-specific options such as disk type.

**`reclaimPolicy`**
Controls what happens to the underlying storage when the PVC is deleted.

Common values:

- `Delete`
- `Retain`

**`volumeBindingMode`**
Controls when the PV is provisioned/bound.

Common values:

- `Immediate`
- `WaitForFirstConsumer`

### PV vs PVC vs StorageClass ⭐

| Component        | Meaning                                         |
| ---------------- | ----------------------------------------------- |
| **StorageClass** | Defines **how** storage should be provisioned   |
| **PVC**          | Requests **how much/type of** storage is needed |
| **PV**           | Represents the **provisioned storage resource** |
| **Pod**          | Uses the storage through the PVC                |

### ⭐ Interview Answer

> **StorageClass is a Kubernetes resource used for dynamic storage provisioning. It defines the storage provisioner and parameters, allowing Kubernetes to automatically create a PersistentVolume when an application creates a PersistentVolumeClaim.**

**Easy to remember:**

> **StorageClass = How to create storage**
> **PVC = Request storage**
> **PV = Storage provided**
> **Pod = Uses storage**

</details>

## ConfigMap

A **ConfigMap** is a Kubernetes object used to store **non-sensitive configuration data** separately from the application container image.

In simple words:

> **ConfigMap keeps application configuration outside the Docker image, so the same image can be used in different environments.**

### Example

Instead of hardcoding:

```text
DATABASE_HOST=dev-db
APP_ENV=dev
```

inside the application image, store it in a ConfigMap:

```text
ConfigMap
├── DATABASE_HOST = dev-db
└── APP_ENV       = dev
```

### Example YAML

```yaml
apiVersion: v1
kind: ConfigMap

metadata:
  name: app-config

data:
  APP_ENV: "production"
  DATABASE_HOST: "mysql-service"
  LOG_LEVEL: "info"
```

### Using ConfigMap as Environment Variables

```yaml
containers:
  - name: app
    image: myapp:1.0
    envFrom:
      - configMapRef:
          name: app-config
```

The container receives:

```text
APP_ENV=production
DATABASE_HOST=mysql-service
LOG_LEVEL=info
```

### Using ConfigMap as a Volume

ConfigMap data can also be mounted as files:

```yaml
volumes:
  - name: config-volume
    configMap:
      name: app-config
```

```yaml
volumeMounts:
  - name: config-volume
    mountPath: /etc/config
```

The application can then read configuration files from:

```text
/etc/config/
```

### Why use ConfigMap?

- Keep configuration separate from application code
- Avoid rebuilding Docker images for configuration changes
- Use different configuration for `dev`, `staging`, and `production`
- Provide configuration as environment variables or files

```text
Same Docker Image
       │
       ├── Dev ConfigMap → Development
       ├── Stage ConfigMap → Staging
       └── Prod ConfigMap → Production
```

### ConfigMap vs Secret ⭐

| ConfigMap                          | Secret                               |
| ---------------------------------- | ------------------------------------ |
| Non-sensitive configuration        | Sensitive data                       |
| URLs, environment names, settings  | Passwords, tokens, keys              |
| `DATABASE_HOST`                    | `DATABASE_PASSWORD`                  |
| Not intended for confidential data | Designed for sensitive configuration |

⚠️ **Do not store passwords, API keys, or other sensitive credentials in a ConfigMap.**

### Common Commands

```bash
kubectl get configmaps
kubectl describe configmap app-config
kubectl create configmap app-config --from-literal=APP_ENV=production
```

### ⭐ Interview Answer

> **ConfigMap is a Kubernetes object used to store non-sensitive application configuration separately from the container image. It can provide configuration to Pods through environment variables or mounted files.**

**Easy to remember:**

> **ConfigMap = Non-sensitive configuration**
> **Secret = Sensitive configuration**

</details>

## Secret

A **Secret** is a Kubernetes object used to store **sensitive information**, such as passwords, API keys, tokens, certificates, and credentials.

In simple words:

> **Secret = Sensitive configuration that should not be stored in plain application configuration.**

### Common Examples

```text
Secret
├── DB_USERNAME
├── DB_PASSWORD
├── API_TOKEN
├── TLS_CERTIFICATE
└── SSH_KEY
```

### Example YAML

```yaml
apiVersion: v1
kind: Secret

metadata:
  name: db-secret

type: Opaque

stringData:
  username: admin
  password: MyPassword123
```

For learning/demo purposes, `stringData` is convenient because Kubernetes handles the encoding.

### Using Secret as Environment Variables

```yaml
containers:
  - name: app
    image: myapp:1.0
    env:
      - name: DB_USERNAME
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: username

      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: password
```

The application receives:

```text
DB_USERNAME=admin
DB_PASSWORD=MyPassword123
```

### Using Secret as a Volume

Secrets can also be mounted as files inside a Pod:

```yaml
volumes:
  - name: secret-volume
    secret:
      secretName: db-secret
```

Then:

```yaml
volumeMounts:
  - name: secret-volume
    mountPath: /etc/secrets
```

### Important Security Point ⭐

Kubernetes Secrets are **not automatically equivalent to strong encryption at rest**. By default, Secret values are commonly represented using **base64 encoding**, which is **not encryption**.

For production, use appropriate protections such as:

- Encryption at rest
- RBAC
- Least-privilege access
- External secret management when appropriate
- Cloud secret services such as **Azure Key Vault**, **AWS Secrets Manager**, or **Google Secret Manager**

### ConfigMap vs Secret

| ConfigMap                   | Secret                   |
| --------------------------- | ------------------------ |
| Non-sensitive configuration | Sensitive configuration  |
| App settings                | Passwords, tokens, keys  |
| `DATABASE_HOST`             | `DATABASE_PASSWORD`      |
| URLs/configuration          | Credentials/certificates |

```text
ConfigMap → Non-sensitive
Secret    → Sensitive
```

### ⭐ Interview Answer

> **A Kubernetes Secret is an object used to store sensitive information such as passwords, tokens, API keys, and certificates. Secrets can be provided to Pods as environment variables or mounted as files. In production, we should also protect Secrets using RBAC and encryption or an external secret-management solution.**

**Easy to remember:**

> **ConfigMap = Configuration**
> **Secret = Sensitive Configuration**

</details>
