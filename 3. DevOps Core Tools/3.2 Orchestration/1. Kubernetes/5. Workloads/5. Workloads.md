## ReplicaSet

A **ReplicaSet** is a Kubernetes workload object that ensures a **specified number of identical Pod replicas are running at all times**.

### Simple Example

If you define:

```yaml
spec:
  replicas: 3
```

ReplicaSet tries to maintain:

```text
ReplicaSet
    │
    ├── Pod 1
    ├── Pod 2
    └── Pod 3
```

If **one Pod fails or is deleted**:

```text
Pod 1 ❌
Pod 2 ✅
Pod 3 ✅
```

ReplicaSet automatically creates a **new Pod**:

```text
Pod 1 → New Pod ✅
Pod 2 → Running
Pod 3 → Running
```

So the desired count remains **3**.

### Why use ReplicaSet?

- Maintains the desired number of Pods
- Provides basic **self-healing**
- Supports **scaling** by changing replica count
- Uses **Labels and Selectors** to identify Pods

### Example YAML

```yaml
apiVersion: apps/v1
kind: ReplicaSet

metadata:
  name: nginx-rs

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
        - name: nginx
          image: nginx
```

### ReplicaSet and Labels/Selectors

This is important:

```text
ReplicaSet
     │
     │ selector: app=nginx
     ↓
┌───────────────┐
│ Pod           │
│ app=nginx     │
└───────────────┘
```

The ReplicaSet uses the **selector** to identify the Pods it manages.

### ReplicaSet vs Deployment ⭐

| ReplicaSet                                     | Deployment                             |
| ---------------------------------------------- | -------------------------------------- |
| Maintains Pod replicas                         | Manages ReplicaSets and Pods           |
| Basic self-healing                             | Self-healing + rolling updates         |
| Can scale Pods                                 | Can scale Pods                         |
| Less commonly managed directly                 | **Commonly used in production**        |
| Does not provide deployment strategy by itself | Supports rolling updates and rollbacks |

Typical relationship:

```text
Deployment
     ↓
ReplicaSet
     ↓
Pods
     ↓
Containers
```

### ⭐ Interview Answer

> **A ReplicaSet ensures that the desired number of identical Pods are running at all times. If a Pod fails or gets deleted, the ReplicaSet creates a replacement Pod. In production, we usually use a Deployment, which manages ReplicaSets for us.**

**Easy to remember:**

> **ReplicaSet = Maintain the required number of Pods.**

## Deployment

A **Deployment** is a Kubernetes workload object used to **deploy and manage stateless applications**. It manages **ReplicaSets**, which in turn manage the Pods.

### Simple Flow

```text
Deployment
     ↓
ReplicaSet
     ↓
Pods
     ↓
Containers
```

### What does Deployment provide?

A Deployment helps with:

- **Creating Pods**
- **Maintaining replicas**
- **Scaling**
- **Rolling updates**
- **Rollback**
- **Self-healing**
- Managing the desired state of the application

### Example

If you configure:

```yaml
spec:
  replicas: 3
```

The Deployment maintains:

```text
Deployment
    │
    ↓
ReplicaSet
    │
    ├── Pod 1
    ├── Pod 2
    └── Pod 3
```

If one Pod fails:

```text
Pod 2 ❌
```

The ReplicaSet creates a replacement:

```text
Pod 1 ✅
Pod 2 → New Pod ✅
Pod 3 ✅
```

---

### Rolling Update

Suppose your application is running:

```text
nginx:1.25
```

You update it to:

```text
nginx:1.26
```

Deployment can perform a **rolling update**, gradually replacing old Pods with new Pods.

```text
Old Pods
nginx:1.25
   ↓
Rolling Update
   ↓
New Pods
nginx:1.26
```

This helps reduce application downtime.

### Rollback

If the new version has a problem, you can roll back:

```bash
kubectl rollout undo deployment nginx
```

Check rollout status:

```bash
kubectl rollout status deployment nginx
```

View rollout history:

```bash
kubectl rollout history deployment nginx
```

### Example YAML

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx-deployment

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:
    metadata:
      labels:
        app: nginx

    spec:
      containers:
        - name: nginx
          image: nginx:1.26
          ports:
            - containerPort: 80
```

### Common Commands

```bash
kubectl get deployments
kubectl get rs
kubectl get pods

kubectl scale deployment nginx-deployment --replicas=5

kubectl set image deployment/nginx-deployment nginx=nginx:1.27

kubectl rollout status deployment nginx-deployment
kubectl rollout history deployment nginx-deployment
kubectl rollout undo deployment nginx-deployment
```

### ReplicaSet vs Deployment ⭐

| ReplicaSet                       | Deployment                      |
| -------------------------------- | ------------------------------- |
| Maintains desired number of Pods | Manages ReplicaSets and Pods    |
| Provides basic self-healing      | Provides self-healing + updates |
| Can scale Pods                   | Can scale Pods                  |
| No built-in rollout management   | Supports rolling updates        |
| No direct rollback mechanism     | Supports rollback               |
| Usually not managed directly     | **Commonly used in production** |

### ⭐ Interview Answer

> **A Deployment is a Kubernetes workload object used to manage stateless applications. It manages ReplicaSets and provides features such as replica management, self-healing, scaling, rolling updates, and rollback. In production, we generally use Deployments instead of creating ReplicaSets directly.**

**Easy to remember:**

> **Deployment → manages ReplicaSet → manages Pods → runs Containers.**

## StatefulSet

A **StatefulSet** is a Kubernetes workload object used to manage **stateful applications** that need **stable identity, stable network names, and persistent storage**.

### Simple Example

```text
StatefulSet
     │
     ├── Pod 0 → mysql-0
     ├── Pod 1 → mysql-1
     └── Pod 2 → mysql-2
```

Unlike normal Deployment Pods, StatefulSet Pods have **stable and predictable names**.

If `mysql-1` is deleted, Kubernetes recreates it as:

```text
mysql-1
```

—not as a random Pod name.

### Key Features

**1. Stable Pod Identity**

```text
mysql-0
mysql-1
mysql-2
```

Pod names remain predictable.

**2. Stable Network Identity**

Each Pod can have a stable DNS name, typically through a **Headless Service**.

```text
mysql-0
mysql-1
mysql-2
```

**3. Persistent Storage**

Each Pod can have its own persistent volume.

```text
mysql-0 → PVC-0
mysql-1 → PVC-1
mysql-2 → PVC-2
```

If a Pod is recreated, its storage can be reattached.

**4. Ordered Deployment and Scaling**

StatefulSet can create Pods in an ordered manner:

```text
mysql-0
   ↓
mysql-1
   ↓
mysql-2
```

### Common Use Cases

StatefulSet is commonly used for applications such as:

- **MySQL**
- **PostgreSQL**
- **MongoDB**
- **Kafka**
- **ZooKeeper**
- Other distributed/stateful systems

### StatefulSet vs Deployment ⭐

| Deployment                                     | StatefulSet                                |
| ---------------------------------------------- | ------------------------------------------ |
| Mainly for stateless applications              | Mainly for stateful applications           |
| Pod identity is not stable                     | Stable Pod identity                        |
| Random/generated Pod names                     | Predictable names                          |
| Storage is not inherently tied to Pod identity | Persistent storage can be tied to each Pod |
| Pods are generally interchangeable             | Pods can have individual identity          |
| Example: Web server                            | Example: Database                          |

### Simple Comparison

```text
Deployment:

nginx-7d8f9-x1a2
nginx-7d8f9-y3b4
nginx-7d8f9-z5c6

→ Pods are interchangeable


StatefulSet:

mysql-0
mysql-1
mysql-2

→ Pods have stable identities
```

### ⭐ Interview Answer

> **StatefulSet is a Kubernetes workload object used for stateful applications that require stable network identity, predictable Pod names, and persistent storage. It is commonly used for databases and distributed systems where each Pod may have its own identity and storage.**

**Easy to remember:**

> **Deployment = Stateless + interchangeable Pods**
> **StatefulSet = Stable identity + persistent storage**

<a id="DaemonSet"></a>

## DaemonSet

A **DaemonSet** is a Kubernetes workload object that ensures a **copy of a Pod runs on every eligible Node** in the cluster.

### Simple Example

Suppose you have 3 worker nodes:

```text
Kubernetes Cluster
│
├── Node 1 → DaemonSet Pod
├── Node 2 → DaemonSet Pod
└── Node 3 → DaemonSet Pod
```

If a new Node is added:

```text
Node 4 → DaemonSet Pod automatically created
```

If a Node is removed, its DaemonSet Pod is also removed.

### Why use DaemonSet?

DaemonSet is useful when you need to run a service **on every node** or on a specific group of nodes.

Common examples:

- **Log collectors** — Fluent Bit, Fluentd
- **Monitoring agents** — Node Exporter
- **Security agents**
- **Network plugins**
- **Storage agents**

Example:

```text
              DaemonSet
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓
    Node 1      Node 2      Node 3
      │           │           │
   Agent Pod   Agent Pod   Agent Pod
```

### Important Point

DaemonSet does **not necessarily mean every node**.

You can use **nodeSelector, node affinity, or taints/tolerations** to control which nodes should run the Pod.

### Example YAML

```yaml
apiVersion: apps/v1
kind: DaemonSet

metadata:
  name: log-agent

spec:
  selector:
    matchLabels:
      app: log-agent

  template:
    metadata:
      labels:
        app: log-agent

    spec:
      containers:
        - name: log-agent
          image: fluent-bit
```

### Common Commands

```bash
kubectl get daemonsets
kubectl get ds
kubectl describe daemonset log-agent
kubectl get pods -o wide
```

### Deployment vs StatefulSet vs DaemonSet ⭐

| Deployment               | StatefulSet               | DaemonSet                  |
| ------------------------ | ------------------------- | -------------------------- |
| Stateless applications   | Stateful applications     | Node-level agents/services |
| Pods are interchangeable | Pods have stable identity | One Pod per eligible Node  |
| Example: Web application | Example: Database         | Example: Log collector     |
| `replicas: 3`            | `replicas: 3`             | Based on eligible Nodes    |

### ⭐ Interview Answer

> **A DaemonSet is a Kubernetes workload object that ensures a copy of a Pod runs on every eligible node. It is commonly used for node-level services such as log collection, monitoring agents, security agents, and networking components.**

**Easy to remember:**

> **Deployment → Required number of Pods**
> **StatefulSet → Stable identity and storage**
> **DaemonSet → Pod on every eligible Node**

## Job

A **Job** is a Kubernetes workload object used to run a **task or batch process until it completes successfully**.

Unlike a Deployment, which keeps Pods running continuously, a Job is designed for **one-time or finite tasks**.

### Simple Example

```text
Job
 │
 └── Pod
      │
      ├── Start
      ├── Perform Task
      └── Complete Successfully
```

Example:

```text
Database Backup
      ↓
    Job
      ↓
Run backup script
      ↓
Backup completed ✅
      ↓
Job completed
```

### Common Use Cases

Jobs are commonly used for:

- Database backup
- Data migration
- Batch processing
- One-time scripts
- Report generation
- Data processing tasks

### Example YAML

```yaml
apiVersion: batch/v1
kind: Job

metadata:
  name: backup-job

spec:
  template:
    spec:
      containers:
        - name: backup
          image: busybox
          command:
            - sh
            - -c
            - echo "Backup completed"

      restartPolicy: Never
```

### Job with Multiple Completions

You can configure a Job to complete multiple successful tasks:

```yaml
spec:
  completions: 3
  parallelism: 2
```

Meaning:

- **`completions: 3`** → Need 3 successful completions
- **`parallelism: 2`** → Run up to 2 Pods at the same time

```text
Job
│
├── Pod 1 → Completed ✅
├── Pod 2 → Completed ✅
└── Pod 3 → Completed ✅
```

### Job vs Deployment ⭐

| Job                              | Deployment                         |
| -------------------------------- | ---------------------------------- |
| Runs a finite task               | Runs an application continuously   |
| Ends after successful completion | Keeps Pods running                 |
| Used for batch processing        | Used for web applications/services |
| `batch/v1` API                   | `apps/v1` API                      |
| Example: Database backup         | Example: Nginx application         |

### Job vs CronJob

**Job:**

> Run the task **once**.

**CronJob:**

> Run the task **on a schedule**.

```text
Job
 ↓
Run once
 ↓
Complete


CronJob
 ↓
Schedule
 ↓
Job
 ↓
Complete
 ↓
Next Schedule
 ↓
Job
```

### ⭐ Interview Answer

> **A Job is a Kubernetes workload object used to run a finite task until it successfully completes. It is commonly used for batch processing, database backups, data migration, and one-time scripts.**

**Easy to remember:**

> **Deployment = Keep application running**
> **Job = Run task and finish**
> **CronJob = Run task on schedule**

## CronJob

A **CronJob** is a Kubernetes workload object used to **run Jobs automatically on a scheduled basis**.

It is similar to the **Linux `cron`** command.

### Simple Flow

```text
CronJob
   ↓
Schedule
   ↓
Job
   ↓
Pod
   ↓
Task
   ↓
Complete
```

For example, if you want a database backup **every day at 2 AM**:

```text
CronJob
   ↓
Every day at 2 AM
   ↓
Create Job
   ↓
Run Backup Pod
   ↓
Backup completed
```

### Common Use Cases

- Database backups
- Log cleanup
- Report generation
- Data synchronization
- Batch processing
- Temporary/maintenance tasks

### Example YAML

```yaml
apiVersion: batch/v1
kind: CronJob

metadata:
  name: backup-cronjob

spec:
  schedule: "0 2 * * *"

  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: backup
              image: busybox
              command:
                - sh
                - -c
                - echo "Database backup completed"

          restartPolicy: Never
```

### Cron Schedule

```text
┌──────── minute (0-59)
│ ┌────── hour (0-23)
│ │ ┌──── day of month (1-31)
│ │ │ ┌── month (1-12)
│ │ │ │ ┌ day of week (0-6)
│ │ │ │ │
0 2 * * *
```

`0 2 * * *` means:

> **Run every day at 2:00 AM.**

### Job vs CronJob ⭐

| Job                         | CronJob               |
| --------------------------- | --------------------- |
| Runs a task                 | Schedules a task      |
| Usually runs once           | Runs repeatedly       |
| No schedule required        | Uses cron schedule    |
| Example: one-time migration | Example: daily backup |

```text
Job
 ↓
Run once
 ↓
Complete


CronJob
 ↓
Schedule
 ↓
Job
 ↓
Complete
 ↓
Next Schedule
 ↓
Job
```

### ⭐ Interview Answer

> **A CronJob is a Kubernetes object used to schedule Jobs at specific times or intervals. It is commonly used for recurring tasks such as database backups, log cleanup, and report generation.**

**Easy to remember:**

> **Job = Run a task**
> **CronJob = Schedule a Job**
