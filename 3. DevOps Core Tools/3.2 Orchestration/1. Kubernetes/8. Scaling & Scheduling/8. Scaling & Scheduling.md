# 8. Scaling & Scheduling

## Requests & Limits

**Requests and Limits** are used in Kubernetes to control how much **CPU and Memory** a container can request and use.

### Simple Definition

> **Request = Minimum resources required by a container.**
> **Limit = Maximum resources a container is allowed to use.**

### Example

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "512Mi"
```

Here:

```text
Request:
CPU    → 250m
Memory → 256Mi

Limit:
CPU    → 500m
Memory → 512Mi
```

### 1. Requests

**Requests tell the Kubernetes Scheduler how much resource the Pod needs.**

For example:

```text
Pod requests:
CPU    = 250m
Memory = 256Mi
```

Kubernetes looks for a Node that has enough **available requested resources**.

```text
Node 1 → Not enough CPU ❌
Node 2 → Enough CPU & Memory ✅
                 ↓
              Pod scheduled
```

So:

> **Request mainly affects scheduling.**

---

### 2. Limits

**Limits define the maximum amount of CPU or Memory a container can use.**

Example:

```text
CPU Limit    = 500m
Memory Limit = 512Mi
```

The container should not be allowed to exceed these configured limits under normal Kubernetes resource enforcement.

### CPU vs Memory behavior ⭐

If a container reaches its **CPU limit**, CPU usage is generally **throttled**.

```text
CPU Limit = 500m
       ↓
Application wants 700m
       ↓
CPU is throttled
```

If a container exceeds its **memory limit**, it can be **OOMKilled**.

```text
Memory Limit = 512Mi
       ↓
Application exceeds memory
       ↓
OOMKilled ❌
```

### Requests vs Limits

| Requests                      | Limits                                  |
| ----------------------------- | --------------------------------------- |
| Minimum resource requirement  | Maximum resource usage                  |
| Mainly used for scheduling    | Used for resource enforcement           |
| Helps Scheduler select a Node | Prevents excessive resource consumption |
| CPU/Memory                    | CPU/Memory                              |

### Example in Real Project

Suppose your backend application normally needs:

```text
CPU    → 250m
Memory → 256Mi
```

but during high traffic it can use:

```text
CPU    → 500m
Memory → 512Mi
```

You can configure:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "512Mi"
```

### Important Interview Point ⭐

**Requests do not mean the container always consumes that amount.**

They are primarily used by the scheduler when deciding where to place the Pod.

```text
Request = "I need this much capacity reserved for scheduling."
Limit   = "Don't allow me to use beyond this configured maximum."
```

### Units

CPU:

```text
1 CPU  = 1000m
500m   = 0.5 CPU
250m   = 0.25 CPU
100m   = 0.1 CPU
```

Memory:

```text
Mi = Mebibytes
Gi = Gibibytes
```

### ⭐ Interview Answer

> **Requests define the CPU and memory resources a container needs and are primarily used by the Kubernetes Scheduler to place the Pod on a suitable Node. Limits define the maximum resources the container can consume. If a container reaches its CPU limit, it can be throttled, while exceeding its memory limit can result in an OOMKilled container.**

**Easy to remember:**

> 🟢 **Request → Scheduling**
> 🔴 **Limit → Maximum Usage**
> ⚠️ **CPU limit → Throttling**
> ⚠️ **Memory limit → OOMKilled**

# HPA — Horizontal Pod Autoscaler

**HPA (Horizontal Pod Autoscaler)** is a Kubernetes feature that **automatically increases or decreases the number of Pods** based on resource utilization or other metrics.

In simple words:

> **HPA automatically scales the number of Pods according to application load.**

### Simple Example

```text
                Traffic / Load
                     ↓
                    HPA
              ┌──────┴──────┐
              ↓             ↓
        High CPU        Low CPU
              ↓             ↓
        Scale Up        Scale Down
              ↓             ↓
          3 → 5 Pods    5 → 3 Pods
```

### Example

Suppose your Deployment has:

```yaml
replicas: 2
```

And HPA is configured:

```text
Minimum Pods = 2
Maximum Pods = 10
Target CPU    = 70%
```

During high traffic:

```text
CPU = 90%
   ↓
HPA detects high utilization
   ↓
2 Pods → 5 Pods
```

When traffic decreases:

```text
CPU = 30%
   ↓
HPA detects low utilization
   ↓
5 Pods → 2 Pods
```

### Example YAML

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: nginx-hpa

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx

  minReplicas: 2
  maxReplicas: 10

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

This means:

> Keep the Deployment between **2 and 10 Pods** and try to maintain average CPU utilization around **70%**.

### HPA and Requests ⭐

For CPU utilization-based HPA, **CPU requests are important**.

For example:

```yaml
resources:
  requests:
    cpu: "250m"
```

If the container is using `200m` CPU:

```text
200m / 250m × 100 = 80%
```

So HPA sees approximately **80% CPU utilization relative to the request**.

### HPA vs VPA vs Cluster Autoscaler

| Autoscaler             | What it scales               |
| ---------------------- | ---------------------------- |
| **HPA**                | Number of Pods               |
| **VPA**                | CPU/Memory resources of Pods |
| **Cluster Autoscaler** | Number of Nodes              |

```text
HPA
 ↓
2 Pods → 5 Pods

VPA
 ↓
Pod CPU/Memory request changes

Cluster Autoscaler
 ↓
3 Nodes → 5 Nodes
```

### Important Interview Point

**HPA does not directly increase the number of Nodes.**

If HPA wants to create more Pods but the existing Nodes don't have enough capacity, the **Cluster Autoscaler** can add Nodes, if configured.

```text
High Traffic
    ↓
HPA
    ↓
More Pods required
    ↓
Not enough Node capacity
    ↓
Cluster Autoscaler
    ↓
More Nodes
```

### ⭐ Interview Answer

> **HPA, or Horizontal Pod Autoscaler, automatically adjusts the number of Pod replicas based on metrics such as CPU, memory, or custom metrics. It scales Pods up when demand increases and scales them down when demand decreases. HPA commonly works together with resource requests and the Metrics Server.**

**Easy to remember:**

> **HPA → Scale Pods horizontally**
> **VPA → Scale Pod resources vertically**
> **Cluster Autoscaler → Scale Nodes**

# VPA — Vertical Pod Autoscaler

**VPA (Vertical Pod Autoscaler)** automatically adjusts the **CPU and Memory requests/limits of Pods** based on their resource usage.

In simple words:

> **HPA increases/decreases the number of Pods, while VPA increases/decreases the resources assigned to a Pod.**

### Simple Example

Suppose a Pod currently has:

```text
CPU Request    = 250m
Memory Request = 256Mi
```

But the application regularly needs more resources.

VPA can recommend or adjust it to:

```text
CPU Request    = 500m
Memory Request = 512Mi
```

```text
        VPA
         ↓
   ┌─────────────┐
   │    Pod      │
   │             │
   │ CPU: 250m   │ → 500m
   │ RAM: 256Mi  │ → 512Mi
   └─────────────┘
```

### How VPA works

```text
Pod
 ↓
Resource Usage
 ↓
VPA observes usage
 ↓
Calculates recommended resources
 ↓
Adjusts CPU/Memory
```

VPA has three important modes:

| Mode         | Meaning                                                |
| ------------ | ------------------------------------------------------ |
| **Off**      | Only provides recommendations                          |
| **Auto**     | Can automatically apply recommendations                |
| **Recreate** | Applies recommendations by recreating Pods when needed |

### Example VPA YAML

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler

metadata:
  name: nginx-vpa

spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx

  updatePolicy:
    updateMode: "Auto"

  resourcePolicy:
    containerPolicies:
      - containerName: nginx
        minAllowed:
          cpu: "100m"
          memory: "128Mi"
        maxAllowed:
          cpu: "1"
          memory: "1Gi"
```

### HPA vs VPA ⭐

| HPA                        | VPA                                          |
| -------------------------- | -------------------------------------------- |
| Horizontal scaling         | Vertical scaling                             |
| Changes **number of Pods** | Changes **CPU/Memory resources**             |
| 2 Pods → 5 Pods            | 250m → 500m CPU                              |
| Useful for varying traffic | Useful when Pod resource requirements change |

```text
HPA:
2 Pods → 5 Pods
     ↕
More / fewer Pods


VPA:
Pod
CPU: 250m → 500m
RAM: 256Mi → 512Mi
     ↕
Bigger / smaller Pod resources
```

### VPA vs Cluster Autoscaler

```text
VPA
 ↓
Changes Pod CPU/Memory
 ↓
Pod needs more capacity
 ↓
Cluster Autoscaler
 ↓
May add Nodes
```

### Important Interview Point

VPA can **recreate Pods** when applying new resource recommendations, depending on its configuration. Therefore, you need to consider application availability when using it.

Also, **HPA and VPA should be designed carefully together**, especially if both are trying to scale based on the same CPU/memory metrics.

### ⭐ Interview Answer

> **VPA, or Vertical Pod Autoscaler, automatically adjusts the CPU and memory resources of Pods based on their actual usage. Unlike HPA, which changes the number of Pods, VPA changes the resources allocated to existing workloads.**

**Easy to remember:**

> **HPA → More/Fewer Pods**
> **VPA → More/Less CPU & Memory**
> **Cluster Autoscaler → More/Fewer Nodes**

# KEDA — Kubernetes Event-driven Autoscaling

**KEDA (Kubernetes Event-driven Autoscaling)** is an autoscaling component that automatically **scales Kubernetes workloads based on external events or metrics**.

In simple words:

> **KEDA scales Pods based on events such as messages in a queue, Kafka lag, HTTP requests, or cloud-service metrics.**

### Simple Example

Suppose your application processes messages from a queue:

```text
Message Queue
     │
     │ 1000 messages
     ↓
    KEDA
     ↓
Deployment
     ↓
2 Pods → 10 Pods
```

When the queue becomes empty:

```text
Queue = 0 messages
       ↓
      KEDA
       ↓
10 Pods → 0 Pods
```

This can be useful for **event-driven applications**, including workloads that may need to **scale to zero**.

### KEDA vs HPA ⭐

| HPA                                                  | KEDA                                        |
| ---------------------------------------------------- | ------------------------------------------- |
| Commonly scales based on CPU/Memory and metrics      | Scales based on event sources/metrics       |
| Usually needs resource metrics or configured metrics | Supports many event sources through scalers |
| Typically keeps at least `minReplicas`               | Can scale workloads to **zero**             |
| Example: CPU > 70%                                   | Example: Queue messages > 100               |

KEDA commonly works **with HPA** rather than replacing it.

```text
             Event Source
                  ↓
                KEDA
                  ↓
                 HPA
                  ↓
             Deployment
                  ↓
              Pods
```

### Common KEDA Scalers

KEDA supports many event sources, for example:

* **Azure Service Bus**
* **Azure Storage Queue**
* **AWS SQS**
* **Kafka**
* **RabbitMQ**
* **Redis**
* **Prometheus**
* **Cron**
* Many other external systems

### Example — Azure Service Bus

Imagine:

```text
Azure Service Bus
       ↓
  500 messages
       ↓
      KEDA
       ↓
   HPA scaling
       ↓
2 Pods → 8 Pods
```

After the queue is processed:

```text
500 messages → 0 messages
       ↓
2 Pods → 0 Pods
```

### Important Terms

**ScaledObject**

Defines **what workload KEDA should scale and what trigger should be used**.

Example:

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject

metadata:
  name: worker-scaler

spec:
  scaleTargetRef:
    name: worker

  minReplicaCount: 0
  maxReplicaCount: 10

  triggers:
    - type: kafka
      metadata:
        topic: orders
```

The exact trigger configuration depends on the event source.

### HPA vs VPA vs KEDA

```text
HPA
 ↓
Number of Pods
 ↓
CPU / Memory / Metrics


VPA
 ↓
CPU / Memory of Pods


KEDA
 ↓
Event-driven scaling
 ↓
Queue / Kafka / Service Bus / etc.
```

### ⭐ Interview Answer

> **KEDA is a Kubernetes event-driven autoscaling solution. It scales workloads based on external event sources such as message queues, Kafka, Azure Service Bus, or Prometheus metrics. KEDA integrates with Kubernetes HPA and can scale workloads down to zero when there is no work to process.**

**Easy to remember:**

> **HPA → Resource/metric-based Pod scaling**
> **VPA → Pod CPU/Memory scaling**
> **KEDA → Event-based Pod scaling**
> **Cluster Autoscaler → Node scaling**

# Scheduling

**Kubernetes Scheduling** is the process of deciding **which Node should run a Pod**.

In simple words:

> **Scheduler decides where a Pod should run in the Kubernetes cluster.**

### Basic Flow

```text
Pod Created
    ↓
Kubernetes API Server
    ↓
Scheduler
    ↓
Checks available Nodes
    ↓
Selects suitable Node
    ↓
Pod assigned to Node
    ↓
Kubelet starts Pod
```

### Example

Suppose you have:

```text
Node 1 → 2 CPU available
Node 2 → 8 CPU available
Node 3 → 1 CPU available
```

Your Pod requests:

```yaml
resources:
  requests:
    cpu: "4"
```

Scheduler checks the Nodes:

```text
Node 1 → 2 CPU ❌
Node 2 → 8 CPU ✅
Node 3 → 1 CPU ❌
```

So:

```text
Pod → Node 2
```

---

## Factors Used by Scheduler

Kubernetes Scheduler considers several things when selecting a Node:

### 1. Resource Requests

```text
Pod requests:
CPU    = 2 CPU
Memory = 4Gi
```

The Node must have sufficient allocatable resources.

> **Requests are important for scheduling.**

---

### 2. nodeSelector

You can tell Kubernetes to schedule a Pod on Nodes having a specific label.

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

```text
Node 1 → disktype=hdd ❌
Node 2 → disktype=ssd ✅
```

Pod goes to **Node 2**.

---

### 3. Node Affinity

Node affinity provides more flexible rules for selecting Nodes.

```text
Pod
 ↓
Node Affinity
 ↓
Select Nodes based on labels
```

It can express preferences and more complex matching rules than a simple `nodeSelector`.

---

### 4. Taints and Tolerations

**Taint** is applied to a Node to **repel Pods**.

**Toleration** allows a Pod to be scheduled onto a tainted Node.

```text
Node
 ↓
Taint
 ↓
Pod without toleration ❌

Pod with matching toleration ✅
```

---

### 5. Pod Affinity / Anti-Affinity

Controls whether Pods should be placed **together or apart**.

**Pod Affinity:**

> Place Pods close to specific Pods.

**Pod Anti-Affinity:**

> Avoid placing Pods together.

Example:

```text
Node 1 → Application Pod
Node 2 → Application Pod
Node 3 → Application Pod
```

Anti-affinity can help distribute replicas across Nodes.

---

## Important Scheduling Concepts

```text
Kubernetes Scheduling
│
├── Resource Requests
├── nodeSelector
├── Node Affinity
├── Taints & Tolerations
├── Pod Affinity
└── Pod Anti-Affinity
```

### ⭐ Interview Answer

> **Kubernetes scheduling is the process of assigning newly created Pods to suitable Nodes. The Kubernetes Scheduler evaluates factors such as resource requests, node labels, affinity and anti-affinity rules, and taints and tolerations before selecting a suitable Node.**

**Easy to remember:**

> **Scheduler = Decides WHERE the Pod should run.**
> **Kubelet = Runs the Pod on the selected Node.**

<a id="Taints & Tolerations"></a>

# Taints & Tolerations

**Taints and Tolerations** are Kubernetes scheduling mechanisms used to **control which Pods can run on a Node**.

In simple words:

> **Taint → Node says: "Don't schedule Pods here."**
> **Toleration → Pod says: "I am allowed to run here."**

### Simple Example

Suppose you have a Node dedicated to database workloads:

```text
Database Node
     │
     └── Taint: dedicated=database
```

Normal Pods:

```text
Normal Pod
    ↓
No matching toleration
    ↓
❌ Cannot be scheduled
```

Database Pod:

```text
Database Pod
    ↓
Has matching toleration
    ↓
✅ Can be scheduled
```

### Flow

```text
                 Node
                  │
             Taint applied
                  │
        ┌─────────┴─────────┐
        ↓                   ↓
 Pod without            Pod with
 toleration             toleration
        ↓                   ↓
       ❌                  ✅
```

## 1. Taint

A taint is applied to a Node.

Example:

```bash
kubectl taint nodes node1 dedicated=database:NoSchedule
```

Now Kubernetes will not schedule Pods without a matching toleration onto `node1`.

```text
node1
  │
  └── dedicated=database:NoSchedule
```

## 2. Toleration

A Pod can have a matching toleration:

```yaml
spec:
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "database"
      effect: "NoSchedule"
```

Now this Pod **can be scheduled** on the tainted Node.

### Important ⭐

A **toleration does not force a Pod onto a Node**.

It only means:

> **"This Pod is allowed to be scheduled here."**

If you want to specifically place the Pod on that Node, you can combine toleration with **nodeSelector or node affinity**.

---

## Taint Effects

There are three main effects:

### `NoSchedule`

New Pods without a matching toleration **will not be scheduled**.

```text
Tainted Node
     ↓
New Pod without toleration
     ↓
❌ Not scheduled
```

### `PreferNoSchedule`

Kubernetes **tries to avoid** scheduling the Pod on that Node, but it is a softer preference.

```text
Prefer another Node
        ↓
If necessary → may use tainted Node
```

### `NoExecute`

Affects both **new and already-running Pods**.

Pods without the appropriate toleration can be **evicted** from the Node.

```text
Node gets NoExecute taint
        ↓
Pod without toleration
        ↓
❌ Evicted
```

---

## Taint vs Toleration ⭐

| Taint                 | Toleration                       |
| --------------------- | -------------------------------- |
| Applied to Node       | Applied to Pod                   |
| Repels Pods           | Allows Pod to tolerate the taint |
| Controls Node access  | Gives Pod permission             |
| `kubectl taint nodes` | Defined in Pod YAML              |

### Real-World Example

Suppose an AKS cluster has:

```text
Node Pool 1 → General applications
Node Pool 2 → GPU workloads
```

You don't want normal applications running on GPU Nodes.

```text
GPU Node
   │
   └── Taint: workload=gpu:NoSchedule
```

GPU application:

```yaml
tolerations:
  - key: "workload"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
```

Now:

```text
Normal Pod
   ↓
❌ GPU Node

GPU Pod
   ↓
✅ GPU Node
```

### ⭐ Interview Answer

> **Taints are applied to Nodes to prevent unwanted Pods from being scheduled there, while tolerations are applied to Pods to allow them to run on tainted Nodes. Taints repel Pods, and tolerations allow Pods to tolerate those taints.**

**Easy to remember:**

> **Taint = Node says NO 🚫**
> **Toleration = Pod says I can handle it ✅**
> **Taint + Toleration = Pod is allowed, not necessarily required, to run there.**

# NodeSelector

**NodeSelector** is a simple Kubernetes scheduling mechanism used to **schedule a Pod on Nodes that have specific labels**.

In simple words:

> **NodeSelector tells Kubernetes: "Run this Pod only on a Node with this label."**

### Simple Example

Suppose your Nodes have these labels:

```text
Node 1 → disktype=ssd
Node 2 → disktype=hdd
Node 3 → disktype=ssd
```

Your Pod requires SSD:

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

Kubernetes will schedule the Pod only on:

```text
Node 1 → ✅
Node 2 → ❌
Node 3 → ✅
```

### Step 1 — Add Label to Node

```bash
kubectl label nodes node1 disktype=ssd
```

Check labels:

```bash
kubectl get nodes --show-labels
```

### Step 2 — Use NodeSelector in Pod

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: app-pod

spec:
  nodeSelector:
    disktype: ssd

  containers:
    - name: app
      image: nginx
```

### How it works

```text
                 Pod
                  │
           nodeSelector
        disktype = ssd
                  │
          Kubernetes Scheduler
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
    Node 1      Node 2     Node 3
      SSD         HDD        SSD
       ✅          ❌         ✅
```

### NodeSelector vs Taints & Tolerations ⭐

These are often confused.

| NodeSelector                       | Taints & Tolerations                |
| ---------------------------------- | ----------------------------------- |
| Pod selects a Node based on labels | Node repels unwanted Pods           |
| Applied in Pod spec                | Taint applied to Node               |
| `nodeSelector`                     | `taint` + `toleration`              |
| Controls **where Pod can run**     | Controls **which Pods are allowed** |

For example:

```text
NodeSelector:
Pod → "I want an SSD Node."

Taint/Toleration:
Node → "Only Pods that tolerate me can come here."
```

### NodeSelector vs Node Affinity

**NodeSelector** is simple:

```yaml
nodeSelector:
  disktype: ssd
```

**Node Affinity** is more flexible and supports more complex rules and preferences.

```text
NodeSelector
    ↓
Simple label matching

Node Affinity
    ↓
Advanced label matching + preferences
```

### ⭐ Interview Answer

> **NodeSelector is a Kubernetes scheduling mechanism that uses Node labels to restrict a Pod to Nodes with matching labels. It is useful when we want to run a specific workload on a particular type of Node, such as SSD, GPU, or a dedicated Node pool.**

**Easy to remember:**

> **Node Label = Node's property**
> **NodeSelector = Pod selects that property**

# Affinity

**Affinity** is a Kubernetes scheduling feature used to control **which Nodes a Pod should run on** or **which Pods should run together/apart**.

In simple words:

> **Affinity = Tell Kubernetes where a Pod prefers or needs to run.**

There are two main types:

```text
Affinity
│
├── Node Affinity
│     └── Pod → Select Nodes
│
└── Pod Affinity
      └── Pod → Select/Stay close to other Pods
```

---

## 1. Node Affinity

**Node Affinity** allows you to schedule a Pod based on **Node labels**.

Example Nodes:

```text
Node 1 → zone=az1
Node 2 → zone=az2
Node 3 → zone=az3
```

Pod:

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: zone
                operator: In
                values:
                  - az1
```

The Pod will be scheduled only on a Node with:

```text
zone=az1
```

### Two important types

**`requiredDuringSchedulingIgnoredDuringExecution`**

> This is a **hard requirement**. The Pod must find a matching Node.

**`preferredDuringSchedulingIgnoredDuringExecution`**

> This is a **preference**. Kubernetes tries to satisfy it, but can choose another suitable Node if necessary.

```text
required  → Must match ✅
preferred → Prefer match 👍
```

---

# 2. Pod Affinity

**Pod Affinity** is used when you want a Pod to be scheduled **near other Pods**.

Example:

```text
Application Pod
      ↓
Should run in the same zone
      ↓
as Backend Pod
```

This can be useful when two applications frequently communicate and you want them placed close together.

```text
Node 1
├── Backend Pod
└── Frontend Pod
```

---

# 3. Pod Anti-Affinity ⭐

**Pod Anti-Affinity** is used to **avoid placing certain Pods together**.

For example, you have 3 replicas:

```text
Node 1 → App Pod 1
Node 2 → App Pod 2
Node 3 → App Pod 3
```

This improves availability because if one Node fails, the other replicas are still running.

```text
Pod 1 → Node 1
Pod 2 → Node 2
Pod 3 → Node 3
```

---

## Node Affinity vs Pod Affinity

| Node Affinity         | Pod Affinity                  |
| --------------------- | ----------------------------- |
| Based on Node labels  | Based on other Pods           |
| Pod selects Nodes     | Pod is placed near other Pods |
| `zone=az1`            | `app=backend`                 |
| Node-based scheduling | Pod-based scheduling          |

### Node Affinity vs NodeSelector

```text
NodeSelector
    ↓
Simple Node selection

Node Affinity
    ↓
Advanced Node selection
    ↓
Required / Preferred rules
```

**NodeSelector:**

```yaml
nodeSelector:
  disktype: ssd
```

**Node Affinity:**

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      ...
```

---

## ⭐ Interview Answer

> **Affinity is a Kubernetes scheduling feature used to control Pod placement. Node Affinity allows Pods to be scheduled based on Node labels, while Pod Affinity and Pod Anti-Affinity control whether Pods should be placed near or away from other Pods.**

### Easy to remember

> **Node Affinity → Pod with specific Node**
