<a id="Namespace"></a>

## ⭐ Namespace

A **Namespace** is a logical way to **separate and organize Kubernetes resources** within the same Kubernetes cluster.

### Why use Namespace?

- Separate environments: `dev`, `staging`, `prod`
- Separate teams or applications
- Apply **RBAC** permissions
- Apply **ResourceQuota** and resource limits
- Make resource management easier

### Example

```text
Kubernetes Cluster
│
├── dev
│   ├── Pod
│   ├── Service
│   └── Deployment
│
├── staging
│   ├── Pod
│   └── Service
│
└── production
    ├── Pod
    ├── Service
    └── Deployment
```

### Common Commands

```bash
kubectl get namespaces
kubectl create namespace dev
kubectl get pods -n dev
kubectl delete namespace dev
```

Create a resource in a specific namespace:

```yaml
metadata:
  name: nginx
  namespace: dev
```

### Important Point ⭐

**Namespace does NOT create a separate Kubernetes cluster.**

It provides **logical isolation inside the same cluster**.

### Interview Answer

> **A Namespace is a logical isolation mechanism in Kubernetes used to organize and separate resources such as Pods, Services, and Deployments within the same cluster.**

**Keywords:** `Logical Isolation` → `Resource Organization` → `dev/staging/prod` → `RBAC` → `ResourceQuota`

<a id="Labels"></a>

## ⭐ Labels

**Labels** are **key-value pairs** attached to Kubernetes resources such as Pods, Deployments, and Services. They are used to **identify, organize, and select resources**.

### Example

```yaml
metadata:
  name: nginx
  labels:
    app: nginx
    environment: production
    tier: frontend
```

Here:

```text
app         = nginx
environment = production
tier        = frontend
```

### Why use Labels?

- Identify resources
- Group resources
- Select specific Pods
- Connect **Services to Pods**
- Help with deployments and management

### Example: Service selecting Pods

Pod:

```yaml
labels:
  app: nginx
```

Service:

```yaml
selector:
  app: nginx
```

The Service will send traffic to Pods having:

```text
app=nginx
```

### Common Commands

```bash
kubectl get pods --show-labels
kubectl get pods -l app=nginx
kubectl label pod nginx environment=prod
```

### Labels vs Namespace

**Namespace** → separates resources logically.

**Label** → identifies/groups resources within a namespace.

### ⭐ Interview Answer

> **Labels are key-value pairs attached to Kubernetes objects that help identify, organize, group, and select resources. Services and other Kubernetes components commonly use labels and selectors to identify Pods.**

**Keywords:** `key-value` → `identify` → `group` → `selector` → `Service → Pod`

<a id="Selectors"></a>

## ⭐ Selectors

A **Selector** is used in Kubernetes to **find and select specific resources, usually Pods, based on their Labels**.

Think:

> **Label = identification**
> **Selector = searching/selecting by that identification**

### Example

Pod has labels:

```yaml
metadata:
  labels:
    app: nginx
    environment: production
```

A Service can use a selector:

```yaml
selector:
  app: nginx
```

The Service finds all Pods with:

```text
app=nginx
```

and sends traffic to them.

### Simple Flow

```text
Pod 1 → app=nginx
Pod 2 → app=nginx
Pod 3 → app=apache

          ↓
     Service Selector
       app=nginx
          ↓
     Pod 1 + Pod 2
```

### Common Commands

```bash
kubectl get pods -l app=nginx
```

Select Pods with multiple labels:

```bash
kubectl get pods -l app=nginx,environment=production
```

### Types of Selectors

**1. Equality-based**

```yaml
selector:
  app: nginx
```

Means:

> Select resources where `app` equals `nginx`.

**2. Set-based**

```yaml
selector:
  matchExpressions:
    - key: environment
      operator: In
      values:
        - dev
        - staging
```

Means:

> Select resources where `environment` is either `dev` or `staging`.

### Labels vs Selectors ⭐

| Labels              | Selectors                           |
| ------------------- | ----------------------------------- |
| Identify resources  | Find/select resources               |
| Key-value pairs     | Matching rules                      |
| `app: nginx`        | `app: nginx`                        |
| Attached to objects | Used by Services, Deployments, etc. |

### Interview Answer

> **A Selector is a mechanism used by Kubernetes to identify and select resources based on their labels. For example, a Service uses a selector to find the Pods to which it should send traffic.**

**Easy to remember:**
**Label = Tag** 🏷️
**Selector = Find by Tag** 🔍

<a id="Annotations"></a>

## ⭐ Annotations

**Annotations** are **key-value pairs** attached to Kubernetes resources that store **additional information or metadata** about the resource.

Unlike **Labels**, annotations are **not normally used to select or group resources**.

### Example

```yaml
metadata:
  name: nginx
  annotations:
    description: "Frontend application"
    owner: "devops-team"
    contact: "devops@example.com"
```

Here:

```text
description = Frontend application
owner       = devops-team
contact     = devops@example.com
```

### Why use Annotations?

Annotations are commonly used to store:

* Application information
* Owner/team information
* Configuration for Kubernetes tools
* Ingress configuration
* Monitoring configuration
* Build/version information
* Tool-specific metadata

### Real-world Example

With an **Ingress**, annotations can provide additional configuration:

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
```

Here, the annotation gives configuration information to the **NGINX Ingress Controller**.

### Labels vs Annotations ⭐

| Labels                            | Annotations                                |
| --------------------------------- | ------------------------------------------ |
| Used to identify resources        | Used to store extra information            |
| Used for selection                | Not normally used for selection            |
| Should be relatively small/simple | Can contain more detailed metadata         |
| Service selectors use labels      | Tools/controllers commonly use annotations |

### Easy way to remember

> **Label = Identify & Select** 🏷️
> **Annotation = Additional Information/Configuration** 📝

### Interview Answer

> **Annotations are key-value metadata attached to Kubernetes objects. They are mainly used to store additional information or configuration for tools and controllers, rather than selecting resources.**

**Keywords:** `Metadata` → `Key-Value` → `Extra Information` → `Tool Configuration` → `Ingress` → `Controllers`

<a id="Kubernetes Objects"></a>

## ⭐ Kubernetes Objects

**Kubernetes Objects** are the **resources/entities used to represent the desired state of applications and infrastructure inside a Kubernetes cluster**.

In simple words:

> **Kubernetes Objects tell Kubernetes what you want to run and how you want it to behave.**

### Common Kubernetes Objects

```text
Kubernetes Objects
│
├── Namespace
├── Pod
├── Deployment
├── ReplicaSet
├── StatefulSet
├── DaemonSet
├── Service
├── Ingress
├── ConfigMap
├── Secret
├── PersistentVolume (PV)
├── PersistentVolumeClaim (PVC)
├── ServiceAccount
├── Job
└── CronJob
```

### Example

A Deployment object can tell Kubernetes:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx

spec:
  replicas: 3
```

This means:

> **I want 3 replicas of the nginx application.**

Kubernetes continuously works to maintain this desired state.

### Important fields

Most Kubernetes YAML objects contain:

```yaml
apiVersion:
kind:
metadata:
spec:
```

**`apiVersion`** → API version of the object

**`kind`** → Type of object, such as `Pod`, `Deployment`, or `Service`

**`metadata`** → Name, namespace, labels, annotations, etc.

**`spec`** → Desired configuration/state of the object

### Desired State

```text
YAML Manifest
     ↓
Desired State
     ↓
Kubernetes API Server
     ↓
Controllers
     ↓
Actual State
     ↓
Kubernetes continuously reconciles
```

For example, if you specify:

```yaml
replicas: 3
```

and one Pod crashes, the Deployment controller creates another Pod to bring the actual state back to **3 replicas**.

### ⭐ Interview Answer

> **Kubernetes Objects are persistent entities in the Kubernetes API that represent the desired state of resources in a cluster. Examples include Pods, Deployments, Services, ConfigMaps, Secrets, and StatefulSets.**

**Keywords:** `Resource` → `Desired State` → `API Server` → `kind` → `metadata` → `spec` → `Controller`
