## Pod

A **Pod** is the **smallest deployable unit in Kubernetes**. It runs **one or more containers** that share the same network and storage.

### Simple Example

```text
Kubernetes Cluster
       │
      Node
       │
      Pod
   ┌─────────┐
   │  Nginx  │
   │Container│
   └─────────┘
```

A Pod normally contains **one container**.

### Why does Kubernetes use Pods?

Kubernetes does not directly manage containers. It manages **Pods**, and containers run inside Pods.

```text
Kubernetes
    ↓
   Pod
    ↓
Container
    ↓
Application
```

### Multiple Containers in a Pod

A Pod can have multiple containers when they are **tightly coupled** and need to work together.

```text
             Pod
      ┌───────────────┐
      │               │
      │ App Container │
      │               │
      │ Sidecar       │
      │ Container     │
      │               │
      └───────────────┘
```

Containers in the same Pod share:

* **Same IP address**
* **Network namespace**
* **localhost**
* Can share **volumes**

For example:

```text
App Container  → localhost:8080
Sidecar        → localhost:8080
```

### Pod IP

Each Pod gets its own **IP address**.

```text
Pod 1 → 10.0.0.10
Pod 2 → 10.0.0.11
Pod 3 → 10.0.0.12
```

⚠️ Pod IPs are generally **ephemeral**. If a Pod is deleted and recreated, it can get a different IP.

That's why applications normally communicate through a **Kubernetes Service**, rather than directly using Pod IPs.

### Common Pod Commands

```bash
kubectl get pods
kubectl get pods -A
kubectl describe pod nginx
kubectl logs nginx
kubectl delete pod nginx
```

Create a simple Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
    - name: nginx
      image: nginx
```

Apply it:

```bash
kubectl apply -f pod.yaml
```

### Pod vs Container ⭐

| Pod                                | Container                |
| ---------------------------------- | ------------------------ |
| Kubernetes deployment unit         | Application runtime unit |
| Can contain one or more containers | Runs the application     |
| Gets a Pod IP                      | Uses the Pod's network   |
| Managed by Kubernetes              | Runs inside Pod          |

### Important Interview Point

**Pod is not normally used directly in production.** Usually, a **Deployment** manages Pods so Kubernetes can provide replicas, rolling updates, and self-healing.

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
    ↓
Containers
```

### ⭐ Interview Answer

> **A Pod is the smallest deployable unit in Kubernetes. It encapsulates one or more containers that share the same network namespace, IP address, and optionally storage volumes. In production, Pods are usually managed by controllers such as Deployments or StatefulSets.**

**Keywords:** `Smallest Deployable Unit` → `Container` → `Pod IP` → `Shared Network` → `Shared Storage` → `Deployment` → `Self-Healing`

<a id="Multi-container Pod"></a>

## Multi-Container Pod

A **Multi-Container Pod** is a Kubernetes Pod that contains **two or more containers** running together.

The containers are usually **tightly coupled** and need to work together to provide a single application or functionality.

### Simple Example

```text
                Pod
        ┌─────────────────┐
        │                 │
        │  App Container  │
        │                 │
        │  Sidecar        │
        │  Container      │
        │                 │
        └─────────────────┘
              │
        Shared Network
        Shared Storage
```

### What do containers share?

Containers inside the same Pod share:

* **Same Pod IP**
* **Network namespace**
* **`localhost`**
* **Volumes**, if configured

Example:

```text
App Container
     │
     │ localhost:8080
     ▼
Sidecar Container
```

They can communicate using `localhost` because they share the same network namespace.

### Common Use Case — Sidecar

For example, an application generates logs and another container collects those logs.

```text
             Pod
    ┌─────────────────────┐
    │                     │
    │  Application        │
    │  Container           │
    │       │             │
    │       ↓             │
    │   Shared Volume     │
    │       ↓             │
    │  Log Collector      │
    │  (Sidecar)          │
    │                     │
    └─────────────────────┘
```

The application writes logs to a shared volume, and the sidecar reads and processes them.

### YAML Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: multi-container-pod

spec:
  containers:
    - name: app
      image: nginx

    - name: sidecar
      image: busybox
      command: ["sh", "-c", "while true; do echo Sidecar running; sleep 10; done"]
```

Here the Pod has **two containers**:

```text
Pod
├── app container
└── sidecar container
```

### Important Point ⭐

Multi-container Pods should be used when containers have a **strong relationship** and need to share resources.

Don't put unrelated applications into the same Pod just because Kubernetes allows multiple containers.

### Interview Answer

> **A multi-container Pod is a Pod containing two or more tightly coupled containers. These containers share the same network namespace and can share storage volumes. A common example is the sidecar pattern, where one container runs the main application and another provides supporting functionality such as logging or proxying.**

**Keywords:** `Same Pod` → `Multiple Containers` → `Shared Network` → `localhost` → `Shared Volume` → `Sidecar Pattern`

<a id="Init Container"></a>

## Init Container

An **Init Container** is a special container in a Kubernetes Pod that **runs before the main application containers start**.

Its job is to perform **initialization or setup tasks** required by the application.

### Simple Flow

```text
Pod
 │
 ├── Init Container
 │       ↓
 │   Setup / Check
 │       ↓
 │   Completes
 │
 └── Main Application Container
         ↓
      Application
```

### Important Points

* Init containers run **before** application containers.
* They run **sequentially** if there are multiple init containers.
* The next init container starts only after the previous one completes successfully.
* The application containers start only after **all init containers complete successfully**.
* If an init container fails, Kubernetes **restarts it** according to the Pod's restart policy.
* Init containers are useful for **initial setup, dependency checks, configuration preparation, and waiting for another service**.

### Example

Suppose your application needs a database to be available before starting.

```text
Init Container
     ↓
Check Database
     ↓
Database Available ✅
     ↓
Main Application
     ↓
Start Application
```

### YAML Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: init-demo

spec:
  initContainers:
    - name: init-check
      image: busybox
      command:
        - sh
        - -c
        - echo "Initialization completed"

  containers:
    - name: app
      image: nginx
```

Execution order:

```text
init-check
    ↓
Completed successfully
    ↓
nginx container starts
```

### Init Container vs Sidecar ⭐

| Init Container                 | Sidecar Container                   |
| ------------------------------ | ----------------------------------- |
| Runs **before** main container | Runs **alongside** main container   |
| Usually completes and exits    | Usually keeps running               |
| Used for initialization/setup  | Used for supporting the application |
| Example: dependency check      | Example: log collector              |

### Interview Answer

> **An Init Container is a container that runs before the main application containers in a Pod. It is used to perform initialization tasks such as dependency checks, configuration setup, or preparing files. The application containers start only after all Init Containers complete successfully.**

**Keywords:** `Runs First` → `Initialization` → `Sequential` → `Dependency Check` → `Setup` → `Main Container`

<a id="Sidecar"></a>

## Sidecar Container

A **Sidecar Container** is an additional container that runs **alongside the main application container in the same Pod**.

Its purpose is to provide **supporting functionality** to the main application.

### Simple Flow

```text
                 Pod
        ┌─────────────────────┐
        │                     │
        │  Main App Container │
        │         │           │
        │         │           │
        │  Sidecar Container  │
        │                     │
        └─────────────────────┘
                 │
          Shared Network
          Shared Volume
```

### Common Use Cases

A sidecar can be used for:

* **Log collection**
* **Monitoring**
* **Proxy**
* **Configuration synchronization**
* **Security**
* **Data processing**

### Example — Log Collector

```text
                 Pod
    ┌──────────────────────────┐
    │                          │
    │  Application Container   │
    │          │               │
    │          ↓               │
    │     Shared Volume        │
    │          ↓               │
    │  Log Collector           │
    │  (Sidecar)               │
    │                          │
    └──────────────────────────┘
```

The application writes logs to a shared volume, and the sidecar reads those logs and sends them to a logging system.

### Sidecar vs Init Container ⭐

| Init Container                      | Sidecar Container                 |
| ----------------------------------- | --------------------------------- |
| Runs **before** main container      | Runs **alongside** main container |
| Performs initialization             | Provides supporting functionality |
| Usually exits after completing task | Usually keeps running             |
| Example: DB/dependency check        | Example: log collector            |

### Important Point

Both containers are inside the **same Pod**, so they share:

* **Pod IP**
* **Network namespace**
* **`localhost`**
* **Volumes**, when configured

### ⭐ Interview Answer

> **A sidecar container is a supporting container that runs alongside the main application container in the same Pod. It is used for additional functionality such as log collection, monitoring, proxying, or security without modifying the main application.**

**Easy to remember:**

> **Init Container = Prepare first**
> **Main Container = Run application**
> **Sidecar = Support application while it runs**

<a id="Pod Lifecycle"></a>

## Pod Lifecycle

**Pod Lifecycle** describes the different **phases a Pod goes through from creation until it finishes or is deleted**.

### Pod Lifecycle Flow

```text
        Pod Created
             ↓
          Pending
             ↓
          Running
          ↙     ↘
     Succeeded   Failed
             \
            Unknown
```

### 1. Pending

The Pod has been created, but **one or more containers have not started yet**.

Possible reasons:

* Waiting for a node to be scheduled
* Image is being pulled
* Required resources are unavailable

```bash
kubectl get pods
```

Example:

```text
NAME    STATUS
nginx   Pending
```

---

### 2. Running

The Pod has been **scheduled to a node** and at least one container is running or starting.

```text
Pod
 └── Container → Running
```

Example:

```text
NAME    STATUS
nginx   Running
```

---

### 3. Succeeded

All containers in the Pod **completed successfully** and will not restart.

Common for:

* Jobs
* One-time tasks
* Batch processing

```text
Container
    ↓
Task completed successfully
    ↓
Succeeded
```

---

### 4. Failed

All containers in the Pod have **terminated**, and at least one container failed.

For example:

```text
Application
    ↓
Error
    ↓
Container exits
    ↓
Failed
```

---

### 5. Unknown

Kubernetes **cannot determine the current state** of the Pod, usually because it cannot communicate with the node where the Pod is running.

---

### Pod Conditions

Apart from the main **Pod phase**, Kubernetes also tracks conditions such as:

* `PodScheduled`
* `Initialized`
* `ContainersReady`
* `Ready`

Example:

```bash
kubectl describe pod nginx
```

### ⭐ Important Interview Point

**Pod Phase ≠ Container State**

Pod phases are:

```text
Pending
Running
Succeeded
Failed
Unknown
```

Container states are:

```text
Waiting
Running
Terminated
```

For example, a Pod can be **Running** while one of its containers is restarting or another container is not ready.

### Interview Answer

> **Pod lifecycle represents the different phases of a Pod from creation to completion. The main Pod phases are Pending, Running, Succeeded, Failed, and Unknown. Kubernetes uses these states to track the overall status of the Pod.**

**Keywords:** `Pending` → `Running` → `Succeeded` → `Failed` → `Unknown` → `Pod Conditions` → `Container States`

## Probes

**Probes** are health checks used by Kubernetes to determine the **health and availability of containers**.

Kubernetes mainly provides **three types of probes**:

```text
Probes
│
├── Liveness Probe
├── Readiness Probe
└── Startup Probe
```

### 1. Liveness Probe

Checks whether the application is **alive**.

If the liveness check fails repeatedly, Kubernetes **restarts the container**.

```text
Application
    ↓
Liveness Check ❌
    ↓
Container Restart
```

**Example:** Application is stuck/hung but the process is still running.

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
```

**Remember:**

> **Liveness = Should I restart the container?**

---

### 2. Readiness Probe

Checks whether the application is **ready to receive traffic**.

If the readiness check fails, Kubernetes **removes the Pod from Service endpoints**, so traffic is not sent to it. The container is **not necessarily restarted**.

```text
Application
    ↓
Readiness Check ❌
    ↓
No Traffic to Pod
```

**Example:** Application is running but still connecting to a database or loading configuration.

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
```

**Remember:**

> **Readiness = Should I send traffic to this Pod?**

---

### 3. Startup Probe

Checks whether the application has **finished starting**.

It is useful for applications that take a long time to start.

```text
Container Starts
      ↓
Startup Probe
      ↓
Application Ready
      ↓
Liveness / Readiness Checks
```

If the startup probe keeps failing, Kubernetes can restart the container.

```yaml
startupProbe:
  httpGet:
    path: /health
    port: 8080
  failureThreshold: 30
  periodSeconds: 10
```

**Remember:**

> **Startup = Has the application started successfully?**

---

### Liveness vs Readiness vs Startup ⭐

| Probe         | Main Question                  | Failure Result       |
| ------------- | ------------------------------ | -------------------- |
| **Liveness**  | Is the app alive?              | Restart container    |
| **Readiness** | Can the app receive traffic?   | Stop sending traffic |
| **Startup**   | Has the app finished starting? | Allow slow startup   |

### Probe Methods

Probes can check applications using:

**HTTP**

```yaml
httpGet:
  path: /health
  port: 8080
```

**TCP**

```yaml
tcpSocket:
  port: 8080
```

**Command**

```yaml
exec:
  command:
    - cat
    - /tmp/healthy
```

### ⭐ Interview Answer

> **Kubernetes probes are health checks used to monitor containers. Liveness checks whether a container should be restarted, readiness checks whether it should receive traffic, and startup checks whether a slow-starting application has successfully started.**

**Easy formula:**

> 🟢 **Startup → Liveness → Readiness**
> **Startup:** Start? → **Liveness:** Alive? → **Readiness:** Ready for traffic?
