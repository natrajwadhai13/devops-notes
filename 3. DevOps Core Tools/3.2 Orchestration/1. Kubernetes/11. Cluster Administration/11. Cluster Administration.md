# kubeconfig

**kubeconfig** is a configuration file used by **kubectl** to connect to and authenticate with a Kubernetes cluster.

In simple words:

> **kubeconfig tells `kubectl` which Kubernetes cluster to connect to, who you are, and which context to use.**

---

## What does kubeconfig contain?

A kubeconfig file mainly contains:

```text
kubeconfig
│
├── Clusters
│     └── Kubernetes API Server details
│
├── Users
│     └── Authentication details
│
├── Contexts
│     └── Cluster + User + Namespace
│
└── Current Context
      └── Currently selected context
```

### Simple Flow

```text
kubectl
   ↓
kubeconfig
   ↓
Context
   ↓
User + Cluster + Namespace
   ↓
Kubernetes API Server
```

---

## Example kubeconfig

Simplified example:

```yaml
apiVersion: v1

clusters:
  - name: dev-cluster
    cluster:
      server: https://api.example.com
      certificate-authority-data: ...

users:
  - name: dev-user
    user:
      client-certificate-data: ...
      client-key-data: ...

contexts:
  - name: dev-context
    context:
      cluster: dev-cluster
      user: dev-user
      namespace: dev

current-context: dev-context
```

So when you run:

```bash
kubectl get pods
```

`kubectl` checks the current context and knows:

```text
Which cluster?
     ↓
dev-cluster

Which identity?
     ↓
dev-user

Which namespace?
     ↓
dev
```

---

# Context ⭐

A **Context** is a combination of:

```text
Context
 ├── Cluster
 ├── User
 └── Namespace
```

For example:

```text
dev-context
   ├── dev-cluster
   ├── dev-user
   └── dev namespace
```

You can have multiple clusters configured:

```text
Contexts
│
├── dev-context
├── staging-context
└── prod-context
```

---

## Useful Commands

### Check current context

```bash
kubectl config current-context
```

### List all contexts

```bash
kubectl config get-contexts
```

### Switch context

```bash
kubectl config use-context dev-context
```

Then:

```bash
kubectl get pods
```

will operate against the cluster defined by that context.

---

## View kubeconfig

```bash
kubectl config view
```

Check the default kubeconfig location:

```text
~/.kube/config
```

On Linux:

```bash
cat ~/.kube/config
```

On Windows, commonly:

```text
C:\Users\<username>\.kube\config
```

---

# Multiple Kubernetes Clusters ⭐

Suppose you manage:

```text
EKS
AKS
GKE
```

You can have contexts such as:

```text
eks-prod
aks-dev
gke-test
```

Then switch between them:

```bash
kubectl config use-context eks-prod
```

```bash
kubectl config use-context aks-dev
```

```bash
kubectl config use-context gke-test
```

This is very useful for DevOps engineers managing multiple environments.

---

# EKS Example

For AWS EKS, you commonly generate/update kubeconfig using:

```bash
aws eks update-kubeconfig --region ap-south-1 --name my-eks-cluster
```

This configures `kubectl` to communicate with the EKS cluster using AWS authentication.

Then:

```bash
kubectl get nodes
```

---

# Important Security Point ⚠️

The kubeconfig file can contain **authentication information or credentials**, depending on how the cluster is configured.

Therefore:

> **Never commit your kubeconfig file or sensitive credentials to GitHub.**

For example, don't do:

```text
git add ~/.kube/config
```

or upload it publicly.

---

# ⭐ Interview Answer

> **kubeconfig is a configuration file used by kubectl to connect to Kubernetes clusters. It contains cluster information, user authentication information, contexts, and the current context. A context combines a cluster, user, and namespace, allowing us to easily switch between different Kubernetes environments such as dev, staging, and production.**

### Easy to remember

```text
kubeconfig
    ↓
Cluster + User + Context
    ↓
kubectl
    ↓
Kubernetes API Server
```

> **kubeconfig = Connection & authentication configuration for kubectl.**

# Nodes

A **Node** is a **worker machine in a Kubernetes cluster** where Kubernetes runs Pods.

In simple words:

> **Node = Machine where your application Pods actually run.**

The machine can be a **virtual machine (VM)** or a physical server.

### Basic Architecture

```text
Kubernetes Cluster
│
├── Control Plane
│     └── Manages the cluster
│
└── Worker Nodes
      │
      ├── Node 1
      │     ├── Pod
      │     └── Pod
      │
      ├── Node 2
      │     ├── Pod
      │     └── Pod
      │
      └── Node 3
            └── Pod
```

---

## What runs on a Node?

A worker Node typically has:

```text
Node
│
├── kubelet
├── Container Runtime
├── kube-proxy
└── Pods
```

### 1. kubelet ⭐

**kubelet** is the agent running on each Node.

It communicates with the Kubernetes Control Plane and makes sure the assigned Pods are running.

```text
Control Plane
      ↓
   kubelet
      ↓
    Pods
```

---

### 2. Container Runtime

The container runtime is responsible for actually running containers.

Common example:

> **containerd**

```text
kubelet
   ↓
containerd
   ↓
Container
```

---

### 3. kube-proxy

`kube-proxy` helps implement Kubernetes Service networking on Nodes.

```text
Client
  ↓
Service
  ↓
kube-proxy / networking
  ↓
Pod
```

Modern Kubernetes networking can also use CNI implementations that handle much of the networking functionality.

---

# How does a Pod get to a Node?

The **Scheduler** decides which suitable Node should run a newly created Pod.

```text
User
 ↓
Deployment
 ↓
Pod
 ↓
Scheduler
 ↓
Selects suitable Node
 ↓
kubelet
 ↓
Container starts
```

For example:

```text
Pod requires:
CPU = 500m
Memory = 1Gi

Node 1 → Not enough resources ❌
Node 2 → Enough resources ✅
Node 3 → Taint not tolerated ❌

Scheduler
   ↓
Node 2
```

---

# Node Resources

A Node has resources such as:

```text
CPU
Memory
Storage
Network
```

Example:

```text
Node-1

CPU:     4 vCPU
Memory:  16 GB
Storage: 100 GB
```

Pods consume these resources.

---

# Node Status

Check Nodes:

```bash
kubectl get nodes
```

Example:

```text
NAME      STATUS   ROLES    AGE
node-1    Ready    <none>   20d
node-2    Ready    <none>   20d
node-3    Ready    <none>   20d
```

More details:

```bash
kubectl describe node node-1
```

You can see:

* CPU
* Memory
* Conditions
* Pods running on the Node
* Taints
* Allocatable resources
* Node information

---

# Node Conditions

Kubernetes tracks the health of Nodes.

Common conditions include:

```text
Ready
MemoryPressure
DiskPressure
PIDPressure
NetworkUnavailable
```

For example:

```text
Ready = True
```

means the Node is available to run Pods.

---

# Node Maintenance ⭐

Suppose you need to perform maintenance on a Node.

You can first prevent new Pods from being scheduled:

```bash
kubectl cordon node-1
```

Then safely move eligible workloads away:

```bash
kubectl drain node-1
```

After maintenance:

```bash
kubectl uncordon node-1
```

Flow:

```text
Node
 ↓
cordon
 ↓
No new Pods scheduled
 ↓
drain
 ↓
Existing workloads moved/evicted where possible
 ↓
Maintenance
 ↓
uncordon
 ↓
Node available again
```

---

# Node vs Pod ⭐

| Node                     | Pod                                 |
| ------------------------ | ----------------------------------- |
| Worker machine           | Smallest deployable Kubernetes unit |
| Runs Pods                | Runs one or more containers         |
| Has CPU/Memory/Storage   | Consumes Node resources             |
| Managed by Control Plane | Scheduled onto Nodes                |

Think:

> **Node = House 🏠**
> **Pod = Room inside the house 🛏️**

Multiple Pods can run on one Node.

```text
Node
│
├── Pod A
├── Pod B
└── Pod C
```

---

# Node in EKS / AKS / GKE

In managed Kubernetes:

```text
EKS / AKS / GKE
       ↓
Control Plane
       ↓
Worker Nodes
       ↓
Pods
```

For example, in **Amazon EKS**, worker Nodes are commonly EC2 instances or other supported compute options.

The cloud provider manages much of the control plane, while your worker compute runs the workloads.

---

## ⭐ Interview Answer

> **A Node is a worker machine in a Kubernetes cluster where Pods are scheduled and run. Each Node typically runs kubelet, a container runtime such as containerd, and networking components. The Kubernetes Scheduler selects suitable Nodes for Pods based on resource availability and scheduling rules.**

### Easy to remember

```text
Control Plane
      ↓
  Scheduler
      ↓
    Node
      ↓
    kubelet
      ↓
    Pod
      ↓
 Container
```

> **Node = Worker machine that runs Pods.**

# Certificates in Kubernetes

Kubernetes uses **TLS certificates** mainly to provide **secure communication and authentication** between Kubernetes components.

In simple words:

> **Certificates = Secure identity + encrypted communication between Kubernetes components.**

### Basic Architecture

```text
                Kubernetes Cluster
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   API Server       Scheduler      Controller
        ↕
      kubelet
        ↕
   Kubernetes Nodes
```

Certificates help these components **verify each other's identity** and communicate securely.

---

## 1. Why are certificates needed?

Without TLS:

```text
Client ──────── Plain HTTP ────────> API Server
```

With TLS:

```text
Client
   │
   │ Encrypted + authenticated
   ↓
API Server
```

This protects communication from:

* Eavesdropping
* Man-in-the-middle attacks
* Unauthorized identities

---

# 2. Kubernetes Certificate Authority — CA ⭐

Kubernetes normally has a **Certificate Authority (CA)** that signs certificates for trusted components.

Think of CA as:

> **CA = Trusted authority that issues/signs certificates.**

```text
                 Kubernetes CA
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
      API Server   kubelet     Client
     Certificate  Certificate  Certificate
```

If a certificate is signed by the trusted CA, the receiving component can verify its identity.

---

# 3. API Server Certificate

The **Kubernetes API Server** uses a TLS certificate.

```text
kubectl
   ↓
HTTPS
   ↓
API Server
```

`kubectl` verifies that it is communicating with the correct API Server using the CA information from kubeconfig.

---

# 4. kubelet Certificate

Each Node's **kubelet** communicates securely with the Kubernetes API Server.

```text
API Server
     ↕
   HTTPS/TLS
     ↕
  kubelet
```

The kubelet can use certificates to authenticate itself to the API Server.

---

# 5. Client Certificates

A Kubernetes client can authenticate using a client certificate.

For example:

```text
User
 ↓
kubectl
 ↓
Client Certificate
 ↓
API Server
```

The API Server verifies the certificate and identifies the user.

Then **RBAC** determines what that user is allowed to do.

```text
Certificate
    ↓
Authentication
    ↓
"Who are you?"
    ↓
RBAC
    ↓
"What can you do?"
```

This distinction is very important in interviews.

---

# 6. Certificate vs RBAC ⭐⭐⭐

These are different.

### Certificate

Answers:

> **Who are you?**

### RBAC

Answers:

> **What are you allowed to do?**

```text
Certificate
     ↓
Authentication
     ↓
User Identity
     ↓
RBAC
     ↓
Authorization
     ↓
Permissions
```

Example:

```text
Certificate → identifies user as "dev-user"

RBAC → allows dev-user to:
        get Pods
        list Pods

RBAC → does not allow:
        delete Pods
```

---

# 7. Certificates in kubeconfig

A kubeconfig can contain certificate-related information:

```yaml
users:
  - name: dev-user
    user:
      client-certificate-data: ...
      client-key-data: ...

clusters:
  - name: dev-cluster
    cluster:
      server: https://api.example.com
      certificate-authority-data: ...
```

Here:

```text
client-certificate
      ↓
Client identity

client-key
      ↓
Private key

certificate-authority
      ↓
Trusts the Kubernetes API Server
```

---

# 8. Certificate Expiration ⭐

Kubernetes certificates have an expiration date.

If important certificates expire, Kubernetes components may stop communicating correctly.

For example:

```text
Certificate
    ↓
Expires
    ↓
API Server ↔ kubelet communication fails
```

In a kubeadm-managed cluster, you can check certificate expiration with:

```bash
kubeadm certs check-expiration
```

You may see:

```text
CERTIFICATE        EXPIRES
apiserver          ...
apiserver-kubelet  ...
front-proxy        ...
```

Certificate renewal can be performed using appropriate kubeadm certificate commands, depending on the cluster setup.

---

# 9. EKS / AKS / GKE

In managed Kubernetes such as:

```text
EKS
AKS
GKE
```

the cloud provider manages significant portions of the control-plane infrastructure and certificate lifecycle.

As a DevOps engineer, you still need to understand:

* TLS
* kubeconfig
* Cluster CA
* Client authentication
* Certificate expiration
* Workload certificates
* mTLS

---

# 10. Certificate vs Secret

A certificate and a Kubernetes Secret are not the same thing.

A TLS certificate and private key are often **stored in a Kubernetes Secret**.

Example:

```yaml
apiVersion: v1
kind: Secret
type: kubernetes.io/tls
```

It typically contains:

```text
tls.crt → Certificate
tls.key → Private key
```

Then an Ingress or application can use that Secret for HTTPS.

```text
Internet
   ↓ HTTPS
Ingress
   ↓
TLS Secret
   ├── tls.crt
   └── tls.key
```

---

# 11. Kubernetes Certificate Architecture

A simplified view:

```text
                     CA
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
     API Server    kubelet    Client
          │          │          │
          └──────────┼──────────┘
                     ↓
                TLS / HTTPS
```

---

## ⭐ Interview Answer

> **Kubernetes uses TLS certificates for secure communication and authentication between components such as the API Server, kubelet, and clients. A Certificate Authority signs and validates these certificates. Certificates provide authentication and encryption, while RBAC provides authorization. In kubeadm clusters, certificate expiration can be checked using `kubeadm certs check-expiration`.**

### Easy to remember

```text
CA
 ↓
Signs Certificates
 ↓
Authentication + Encryption
 ↓
Kubernetes Components
```

> **Certificate → Who are you?**
> **RBAC → What can you do?**
> **TLS → How do we communicate securely?**

# etcd

**etcd** is a **distributed key-value database** used by Kubernetes to store the **cluster's state and configuration**.

In simple words:

> **etcd = Kubernetes cluster's database / source of truth.**

It stores information about things such as:

* Pods
* Deployments
* Services
* ConfigMaps
* Secrets
* Nodes
* Namespaces
* RBAC objects
* Cluster configuration and desired state

---

## Kubernetes Architecture

```text
                    kubectl
                       ↓
                Kubernetes API
                   Server
                       ↓
                     etcd
                       │
              Cluster State
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
   Scheduler     Controller       Other Components
```

The **API Server is the main component that communicates with etcd**.

---

## Example

Suppose you create a Deployment:

```bash
kubectl create deployment nginx --image=nginx
```

Simplified flow:

```text
kubectl
   ↓
API Server
   ↓
etcd
   ↓
Stores desired state
   ↓
Controllers/Scheduler
   ↓
Pod gets created
```

etcd stores the Kubernetes object's state so the control plane knows what the cluster should look like.

---

# Desired State vs Actual State ⭐

This is an important concept.

Suppose you create:

```yaml
replicas: 3
```

Kubernetes stores the desired configuration in its cluster state.

```text
Desired State
     ↓
  3 Pods
```

If one Pod crashes:

```text
Desired: 3 Pods
Actual:  2 Pods
```

The Kubernetes controllers detect the difference and create another Pod.

```text
etcd / API state
       ↓
Desired = 3
       ↓
Controller
       ↓
Creates missing Pod
       ↓
Actual = 3
```

So etcd is an important part of maintaining the **cluster state**.

---

# etcd is NOT where container images are stored

This is an important distinction.

```text
etcd
 ↓
Kubernetes cluster state
```

It does **not** store:

```text
❌ Container images
❌ Application files
❌ Pod filesystem data
❌ Persistent application data
```

Container images normally come from a **container registry**:

```text
ECR / ACR / GCR / Docker Hub
        ↓
Container Runtime
        ↓
Node
        ↓
Container
```

Persistent application data should be stored using Kubernetes storage mechanisms such as:

```text
PV
PVC
StorageClass
Cloud Storage
```

---

# etcd Backup ⭐⭐⭐

Because etcd contains the Kubernetes cluster state, **backing up etcd is extremely important in self-managed Kubernetes clusters**.

If etcd data is lost:

```text
etcd data lost
     ↓
Cluster state may be lost
     ↓
Major cluster recovery problem
```

A typical etcd backup uses:

```bash
etcdctl snapshot save backup.db
```

The exact command/options depend on the etcd version and cluster configuration.

---

# etcd and High Availability

In a production Kubernetes control plane, etcd is commonly deployed as a **cluster of multiple members** rather than a single instance.

```text
             etcd Cluster
        ┌────────┼────────┐
        ↓        ↓        ↓
     etcd-1   etcd-2   etcd-3
```

This provides redundancy.

etcd uses the **Raft consensus algorithm** to maintain consistency between members.

For example:

```text
3 etcd members
     ↓
2 members available
     ↓
Majority exists
     ↓
Cluster can continue
```

This majority is called a **quorum**.

---

# etcd in EKS / AKS / GKE

In managed Kubernetes:

```text
EKS
AKS
GKE
```

the cloud provider manages the Kubernetes control plane, including the etcd infrastructure.

As a DevOps engineer, you generally don't directly administer the provider-managed etcd cluster.

But you should understand its role:

> **etcd stores the Kubernetes control-plane state.**

---

# etcd vs Kubernetes API Server ⭐

| API Server                     | etcd                                      |
| ------------------------------ | ----------------------------------------- |
| Entry point to Kubernetes API  | Database for cluster state                |
| Handles API requests           | Stores state                              |
| Authentication & authorization | Persistent state storage                  |
| Communicates with etcd         | Receives state operations from API Server |

Think:

```text
kubectl
   ↓
API Server
   ↓
etcd
```

> **API Server = Gateway**
> **etcd = Database**

---

# ⭐ Interview Answer

> **etcd is a distributed, consistent key-value store used by Kubernetes to store the cluster's state and configuration. The Kubernetes API Server communicates with etcd, and other control-plane components use the API Server to work with that state. etcd is critical because it contains the cluster's source of truth, so backups and high availability are important.**

### Easy to remember

> **etcd = Kubernetes Database**
> **API Server = Gateway to the database**
> **etcd stores = Cluster state, not application data**

# Cluster Upgrade

A **Kubernetes Cluster Upgrade** means upgrading the Kubernetes version of the cluster and its components to a newer supported version.

In simple words:

> **Cluster Upgrade = Safely moving Kubernetes from an older version to a newer version without disrupting applications.**

Example:

```text
Kubernetes 1.31
      ↓
Kubernetes 1.32
      ↓
Kubernetes 1.33
```

---

## Why do we upgrade?

Main reasons:

* Security patches
* Bug fixes
* New Kubernetes features
* Performance improvements
* Vendor/cloud-provider support
* Avoid running an unsupported Kubernetes version

---

# Cluster Upgrade Process ⭐

A typical production upgrade looks like:

```text
1. Check compatibility
        ↓
2. Check deprecated APIs
        ↓
3. Backup etcd / cluster state
        ↓
4. Test in Dev/Staging
        ↓
5. Upgrade Control Plane
        ↓
6. Upgrade Worker Nodes
        ↓
7. Validate applications
        ↓
8. Monitor cluster
```

---

## 1. Check Current Version

```bash
kubectl version
```

Also check Nodes:

```bash
kubectl get nodes
```

Example:

```text
NAME     VERSION
node-1   v1.31
node-2   v1.31
node-3   v1.31
```

---

## 2. Check Deprecated APIs ⭐

Before upgrading, check whether applications use APIs that will be removed in the target Kubernetes version.

For example:

```text
Old API
apps/v1beta1
      ↓
Deprecated / removed
      ↓
Use supported API
apps/v1
```

This is important because an upgrade can succeed while an application later fails to deploy due to an unsupported API version.

---

# 3. Backup

For a **self-managed cluster**, etcd backup is very important because etcd contains the Kubernetes cluster state.

```text
etcd
 ↓
Backup
 ↓
Upgrade
```

If something goes wrong, the backup can help with disaster recovery.

For managed Kubernetes such as **EKS, AKS, and GKE**, the cloud provider manages the control plane and its underlying etcd infrastructure, so the upgrade and backup responsibilities are different.

---

# 4. Upgrade Control Plane

The **Control Plane** should generally be upgraded before worker Nodes.

```text
Old Version
     ↓
Control Plane Upgrade
     ↓
New Version
```

Then worker Nodes are upgraded.

```text
Control Plane
      ↓
Worker Nodes
```

---

# 5. Upgrade Worker Nodes ⭐

Worker Nodes run your applications.

You generally don't want to suddenly terminate all Nodes.

A common production approach is:

```text
Cordon
   ↓
Drain
   ↓
Replace / Upgrade Node
   ↓
Uncordon
```

### Cordon

```bash
kubectl cordon node-1
```

Prevents new Pods from being scheduled onto that Node.

### Drain

```bash
kubectl drain node-1
```

Evicts eligible workloads from the Node so it can be safely maintained/upgraded.

### Uncordon

```bash
kubectl uncordon node-1
```

Allows new Pods to be scheduled again.

---

# 6. Rolling Node Upgrade

For production, worker Nodes are commonly upgraded **one at a time or in controlled batches**.

```text
Node 1 → Upgrade
Node 2 → Continue serving
Node 3 → Continue serving

        ↓

Node 1 Ready

        ↓

Node 2 → Upgrade
```

This reduces application downtime.

---

# 7. Application Availability ⭐

Before draining Nodes, make sure applications have sufficient replicas.

Example:

```text
Deployment
replicas: 3

Pod 1 → Node 1
Pod 2 → Node 2
Pod 3 → Node 3
```

During upgrade:

```text
Node 1 → Drained

Pod 1
 ↓
Rescheduled
 ↓
Node 2/3 or another available Node
```

**PodDisruptionBudget (PDB)** can help limit how many replicas are voluntarily disrupted at once.

---

# Managed Kubernetes Upgrade

For **EKS / AKS / GKE**, the cloud provider provides managed upgrade mechanisms.

Conceptually:

```text
Cloud Provider
      ↓
Control Plane Upgrade
      ↓
Node Group Upgrade
      ↓
Application Validation
```

For example, with EKS you typically upgrade the cluster/control plane version and then update the worker node groups.

The exact process depends on the provider and cluster configuration.

---

# Upgrade vs Rollback ⭐

A good production strategy is to have a recovery plan.

```text
Upgrade
   ↓
Validation
   ↓
Problem?
 ├── No → Continue
 └── Yes → Recovery / Rollback Plan
```

Important point:

> **Kubernetes version upgrades are not always simply "rollback the cluster version."** Recovery may involve restoring workloads, reverting manifests, replacing Nodes, or using the cloud provider's supported recovery procedures.

So you should always test the upgrade process in **staging** before production.

---

# Important Checks After Upgrade

Run:

```bash
kubectl get nodes
```

Check:

```text
Node status = Ready
```

Then:

```bash
kubectl get pods -A
```

Check for:

```text
CrashLoopBackOff
Pending
ImagePullBackOff
Error
```

Also verify:

```text
Deployments
Services
Ingress
Storage
NetworkPolicy
Monitoring
Application health
```

---

# ⭐ Interview Example

If interviewer asks:

**"How do you perform a Kubernetes cluster upgrade?"**

You can answer:

> **First, I check the current and target Kubernetes versions and verify version compatibility. Then I check for deprecated APIs and application compatibility. For self-managed clusters, I take an etcd backup. I test the upgrade in a lower environment first. In production, I upgrade the control plane first and then upgrade worker Nodes in a controlled manner. Before upgrading a Node, I cordon and drain it so workloads can be rescheduled. After upgrading, I validate Node health, Pods, Services, Ingress, storage, and application functionality, and monitor the cluster for issues.**

### Easy Interview Flow

```text
Check Version
     ↓
Compatibility / Deprecated APIs
     ↓
Backup
     ↓
Test in Staging
     ↓
Control Plane Upgrade
     ↓
Cordon + Drain Nodes
     ↓
Upgrade Worker Nodes
     ↓
Uncordon
     ↓
Validate
     ↓
Monitor
```

> **Golden rule: Control Plane → Worker Nodes → Validate → Monitor.**
