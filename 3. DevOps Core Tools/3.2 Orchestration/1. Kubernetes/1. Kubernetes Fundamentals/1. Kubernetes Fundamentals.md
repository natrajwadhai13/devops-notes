## What is Kubernetes?

**Kubernetes (K8s)** is an **open-source container orchestration platform** used to **deploy, manage, scale, and monitor containerized applications**.

In simple words:

> **Kubernetes automatically manages containers across multiple servers (nodes).**

<a id="Why Kubernetes?"></a>

### Why do we need Kubernetes?

Suppose you have 20 Docker containers running an application. Managing them manually becomes difficult.

Kubernetes can automatically handle:

- **Deployment** – deploy applications/containers
- **Scaling** – increase or decrease replicas
- **Self-healing** – restart failed containers
- **Load balancing** – distribute traffic
- **Rolling updates** – update applications without major downtime
- **Service discovery** – allow applications to find each other
- **Storage management** – provide persistent storage
- **Configuration & secrets** – manage application configuration securely

# **5. Kubernetes Architecture**

Kubernetes architecture is divided into: **A) Control Plane (Master Node)** and **B) Data Plane (Worker Node)**

Below is the high-level Kubernetes Cluster Architecture:

![Kubernetes Architecture](https://raw.githubusercontent.com/natrajwadhai13/devops-playbook/main/images/kubernetes-cluster-architecture.svg)

| **Section**                        | **Component**                      | **Description / Responsibilities**                                                                                                                          |
| ---------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A) Control Plane (Master Node)** | **API Server**                     | • Main entry point for all Kubernetes requests<br>• Handles kubectl commands<br>• Validates and processes API requests                                      |
|                                    | **Scheduler**                      | • Assigns pods to nodes<br>• Decides _which node_ runs a Pod<br>• Scheduling based on CPU, memory, affinity, taints/tolerations                             |
|                                    | **etcd**                           | • Distributed key-value store<br>• Stores entire cluster state (desired + actual)                                                                           |
|                                    | **Controller Manager**             | • Runs background controllers<br>• Ensures correct number of replicas<br>• Controllers: Deployment, ReplicaSet, Node Controller                             |
|                                    | **Cloud Controller Manager (CCM)** | • Integrates Kubernetes with cloud providers (AWS, Azure, GCP)<br>• Manages load balancers, node lifecycle, cloud networking                                |
| **B) Data Plane (Worker Node)**    | **Kubelet**                        | • Ensures containers are running in Pods<br>• Communicates with API Server<br>• Reports node and pod status                                                 |
|                                    | **Kube-Proxy**                     | • Handles networking and load balancing<br>• Manages cluster networking rules<br>• Implements iptables/ipvs rules<br>• Handles service-level load balancing |
|                                    | **Container Runtime**              | • Runs containers on the node<br>• Examples: containerd, CRI-O, Docker (via containerd)                                                                     |

## Containerization

**Containerization** is a technology/process of packaging an application together with its **code, dependencies, libraries, and configuration** into a **container** so it can run consistently across different environments.

### Simple example

Without containerization:

```text
Developer Machine
Application
 ├── Code
 ├── Node.js version
 ├── Libraries
 └── Configuration

Works on Developer Machine ❌
May fail on Server
```

With containerization:

```text
Container
 ┌─────────────────────┐
 │ Application         │
 │ Code                │
 │ Dependencies        │
 │ Libraries           │
 │ Configuration       │
 └─────────────────────┘
          │
          ▼
   Runs consistently
 Dev → Test → Production
```

### Why use containerization?

- **Consistency** – same application environment everywhere
- **Portability** – run on laptop, server, AWS, Azure, etc.
- **Isolation** – applications run in isolated environments
- **Fast startup** – containers start much faster than VMs
- **Efficient** – multiple containers can share the host OS kernel
- **Easy deployment** – package once and deploy anywhere

### Docker and Kubernetes

**Docker** is commonly used to **build and run containers**.

**Kubernetes** is used to **manage containers at scale**.

```text
Application
     ↓
Dockerfile
     ↓
Docker Image
     ↓
Container
     ↓
Kubernetes
     ↓
Deploy / Scale / Self-Heal / Manage
```

### ⭐ Interview Answer

> **Containerization is the process of packaging an application along with its dependencies and configuration into a lightweight, isolated container so that it can run consistently across different environments.**

**Keywords:** `Isolation` → `Portability` → `Consistency` → `Docker` → `Container` → `Image` → `Kubernetes`

## Monolithic vs Microservices

### 1. Monolithic Architecture

In **Monolithic architecture**, the entire application is built and deployed as **one single application/unit**.

Example: An e-commerce application:

```text
                E-Commerce Application
                       │
       ┌───────────────┼────────────────┐
       │               │                │
     Login           Payment          Orders
       │               │                │
       └───────────────┼────────────────┘
                       │
                  One Application
                       │
                    Deploy
```

If you make a small change in the **Payment** module, you generally need to **build and deploy the complete application**.

**Advantages:**

- Simple to develop initially
- Easy to deploy
- Easy to test for small applications
- Simple architecture

**Disadvantages:**

- Large application becomes difficult to maintain
- One small change may require full deployment
- Scaling is less flexible
- Failure in one area can affect the whole application
- Technology choices are usually tightly coupled

---

### 2. Microservices Architecture

In **Microservices architecture**, the application is divided into **small, independent services**, and each service performs a specific business function.

```text
                 E-Commerce Application
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
   User Service     Payment Service   Order Service
       │                 │                 │
      Pod               Pod               Pod
       │                 │                 │
       └────────── Independent ────────────┘
```

For example:

- **User Service** → login/user management
- **Payment Service** → payment processing
- **Order Service** → order management

If you change the Payment Service, you can **build and deploy only the Payment Service**.

**Advantages:**

- Independent deployment
- Independent scaling
- Easier to maintain large applications
- Failure can be isolated
- Different technologies can be used for different services

**Disadvantages:**

- More complex architecture
- Network communication between services
- Monitoring and troubleshooting are harder
- Requires proper DevOps, networking, security, and observability

---

### ⭐ Interview Difference

| Monolithic                           | Microservices                        |
| ------------------------------------ | ------------------------------------ |
| One large application                | Multiple small services              |
| Single deployment                    | Independent deployments              |
| Usually tightly coupled              | Loosely coupled                      |
| Scaling is usually whole application | Scale individual services            |
| Simple initially                     | More complex                         |
| Easier to manage for small apps      | Better suited for large/complex apps |

### 🎯 Interview Answer — Simple English

> **Monolithic architecture means the complete application is developed and deployed as one unit. Microservices architecture divides the application into multiple small, independent services. Each service can be developed, deployed, scaled, and maintained independently.**

### DevOps perspective

This is especially important for Kubernetes:

```text
Microservices
     ↓
Docker Containers
     ↓
Kubernetes
     ↓
Deploy / Scale / Self-Heal
     ↓
CI/CD
```

**Remember this line for interview:**

- **Monolithic = one application, one deployment.**

- **Microservices = multiple services, independent deployments.**
