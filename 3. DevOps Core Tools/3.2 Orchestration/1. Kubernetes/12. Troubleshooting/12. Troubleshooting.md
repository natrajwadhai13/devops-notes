# 12. Troubleshooting

**Kubernetes Troubleshooting** means identifying the **root cause of a problem** in the cluster or application and fixing it.

In simple words:

> **Troubleshooting = Check → Identify → Fix → Verify**

---

## Basic Troubleshooting Flow ⭐

```text
Problem
   ↓
kubectl get
   ↓
kubectl describe
   ↓
kubectl logs
   ↓
kubectl get events
   ↓
Check Service / Network / Storage
   ↓
Identify Root Cause
   ↓
Fix
   ↓
Verify
```

### Most important commands

```bash
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl get events
kubectl get nodes
kubectl describe node <node-name>
```

# 1. Pod Troubleshooting ⭐

First check:

```bash
kubectl get pods
```

You may see:

```text
STATUS
Running
Pending
CrashLoopBackOff
ImagePullBackOff
ErrImagePull
Error
Completed
```

### Example

```text
my-app   0/1   CrashLoopBackOff
```

Check details:

```bash
kubectl describe pod my-app
```

Then check application logs:

```bash
kubectl logs my-app
```

If the container restarted:

```bash
kubectl logs my-app --previous
```

---

# 2. Pending Pod

If:

```text
Pod → Pending
```

Common reasons:

* Insufficient CPU/Memory
* Node selector mismatch
* Taints/Tolerations problem
* Affinity rules
* PVC not available

Check:

```bash
kubectl describe pod <pod-name>
```

Look at the **Events** section.

Example:

```text
0/3 nodes are available:
Insufficient cpu
```

Then the problem is likely Node capacity.

---

# 3. CrashLoopBackOff ⭐

```text
Pod
 ↓
Container starts
 ↓
Application crashes
 ↓
Container restarts
 ↓
Crashes again
 ↓
CrashLoopBackOff
```

Check:

```bash
kubectl logs <pod-name>
```

and:

```bash
kubectl logs <pod-name> --previous
```

Also:

```bash
kubectl describe pod <pod-name>
```

Common causes:

* Application error
* Wrong configuration
* Missing Secret/ConfigMap
* Wrong command/entrypoint
* Dependency unavailable
* Failed health probe

---

# 4. ImagePullBackOff / ErrImagePull

Example:

```text
my-app   ImagePullBackOff
```

Check:

```bash
kubectl describe pod <pod-name>
```

Common causes:

```text
Wrong image name       ❌
Wrong image tag        ❌
Private registry       ❌
Missing imagePullSecret ❌
Registry unavailable   ❌
```

Example:

```yaml
image: nginx:wrong-tag
```

The image may not exist.

# 5. Service Troubleshooting

Suppose:

```text
Pod → Running ✅
Service → Not working ❌
```

Check:

```bash
kubectl get svc
```

Then:

```bash
kubectl describe svc <service-name>
```

Check Endpoints:

```bash
kubectl get endpoints <service-name>
```

Or EndpointSlices:

```bash
kubectl get endpointslice
```

A common problem is a **Service selector that doesn't match Pod labels**.

```text
Service selector:
app: backend

Pod label:
app: frontend
```

Result:

```text
Service → No matching Pods ❌
```

---

# 6. DNS Troubleshooting

If one Pod cannot reach another using the Service name:

```text
backend-service
```

check DNS.

You can test from inside a Pod:

```bash
kubectl exec -it <pod-name> -- nslookup <service-name>
```

or, depending on the image:

```bash
kubectl exec -it <pod-name> -- getent hosts <service-name>
```

Check CoreDNS:

```bash
kubectl get pods -n kube-system
```

Look for CoreDNS Pods.

---

# 7. NetworkPolicy Troubleshooting

Suppose:

```text
Frontend → Backend ❌
```

but both Pods are Running.

Check:

```bash
kubectl get networkpolicy
```

Then inspect:

```bash
kubectl describe networkpolicy <policy-name>
```

Possible cause:

```text
NetworkPolicy
     ↓
Traffic blocked
```

Check:

* Ingress rules
* Egress rules
* Pod selectors
* Namespace selectors
* Ports

---

# 8. Node Troubleshooting ⭐

Check:

```bash
kubectl get nodes
```

If:

```text
node-1   NotReady
```

check:

```bash
kubectl describe node node-1
```

Look at:

```text
Conditions
Events
Taints
CPU
Memory
Disk
```

You can also check resource usage:

```bash
kubectl top node
```

Common causes:

* kubelet problem
* Disk pressure
* Memory pressure
* Network issue
* Container runtime problem
* Node connectivity problem

---

# 9. Storage Troubleshooting

If a Pod is stuck because of storage:

```text
Pod → Pending
```

Check:

```bash
kubectl get pvc
```

Then:

```bash
kubectl describe pvc <pvc-name>
```

Check:

```bash
kubectl get pv
kubectl get storageclass
```

Common problems:

```text
PVC Pending
PV unavailable
Wrong StorageClass
Mount failure
Insufficient storage
Access mode mismatch
```

# 10. Ingress Troubleshooting

If:

```text
Internet
   ↓
Ingress ❌
   ↓
Service
   ↓
Pod
```

Check:

```bash
kubectl get ingress
```

Then:

```bash
kubectl describe ingress <ingress-name>
```

Check:

```text
Ingress Controller
Service
Endpoints
DNS
TLS certificate
Ingress rules
```

# 11. Resource Troubleshooting

Sometimes the application is slow because of CPU or memory limits.

Check:

```bash
kubectl top pods
kubectl top nodes
```

Example:

```text
CPU: 95%
Memory: 90%
```

Then check Pod resources:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi

  limits:
    cpu: 1
    memory: 1Gi
```

Possible problems:

```text
Insufficient resources
OOMKilled
CPU throttling
```

For `OOMKilled`, check:

```bash
kubectl describe pod <pod-name>
```

---

# 12. Kubernetes Events ⭐

Events are very useful for finding the reason behind failures.

```bash
kubectl get events
```

For a specific Pod:

```bash
kubectl describe pod <pod-name>
```

At the bottom:

```text
Events:
  Warning  Failed
  Warning  BackOff
  Warning  FailedMount
  Warning  Unhealthy
```

# Golden Troubleshooting Method ⭐⭐⭐

For an interview, remember this sequence:

```text
1. kubectl get
       ↓
2. kubectl describe
       ↓
3. kubectl logs
       ↓
4. kubectl get events
       ↓
5. Check Service / DNS / Network
       ↓
6. Check Storage
       ↓
7. Check CPU / Memory
       ↓
8. Fix
       ↓
9. Verify
```

### Example Interview Answer

> **When troubleshooting a Kubernetes issue, I first check the resource status using `kubectl get`. Then I use `kubectl describe` to understand events, conditions, and configuration. For application-level issues, I check container logs using `kubectl logs`. If the issue is networking, I check Services, Endpoints, DNS, and NetworkPolicies. For storage issues, I check PVC, PV, and StorageClass. I also check Node health and CPU/memory usage. After identifying the root cause, I fix it and verify that the workload is healthy.**

### Quick Memory Trick

> **GET → DESCRIBE → LOGS → EVENTS → NETWORK/STORAGE → RESOURCES → FIX → VERIFY**
