# 🚀 Kubernetes (kubectl) Cheat Sheet

## 🔹 1. Cluster & Context

```bash
kubectl cluster-info                # Cluster details
kubectl config view                # View config
kubectl config current-context     # Current context
kubectl config use-context <name>  # Switch context
```

---

## 🔹 2. Nodes

```bash
kubectl get nodes
kubectl describe node <node-name>
kubectl top nodes                  # CPU/memory usage
```

---

## 🔹 3. Pods

```bash
kubectl get pods
kubectl get pods -o wide           # More details
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl logs -f <pod-name>         # Live logs
kubectl exec -it <pod-name> -- bash
kubectl delete pod <pod-name>
```

---

## 🔹 4. Namespaces

```bash
kubectl get namespaces
kubectl create namespace <name>
kubectl delete namespace <name>

kubectl get pods -n <namespace>
```

---

## 🔹 5. Deployments

```bash
kubectl get deployments
kubectl create deployment <name> --image=<image>
kubectl describe deployment <name>

kubectl scale deployment <name> --replicas=3
kubectl rollout status deployment <name>
kubectl rollout undo deployment <name>

kubectl delete deployment <name>
```

---

## 🔹 6. Services

```bash
kubectl get svc
kubectl expose deployment <name> --type=NodePort --port=80
kubectl describe svc <service-name>
kubectl delete svc <service-name>
```

---

## 🔹 7. ConfigMaps & Secrets

```bash
kubectl create configmap <name> --from-literal=key=value
kubectl get configmaps

kubectl create secret generic <name> --from-literal=key=value
kubectl get secrets
```

---

## 🔹 8. Files (YAML Apply)

```bash
kubectl apply -f file.yaml
kubectl create -f file.yaml
kubectl delete -f file.yaml
kubectl get all -f file.yaml
```

---

## 🔹 9. Describe & Debug

```bash
kubectl describe <resource> <name>
kubectl get events
kubectl top pods
```

---

## 🔹 10. Port Forwarding

```bash
kubectl port-forward pod/<pod-name> 8080:80
kubectl port-forward svc/<service-name> 8080:80
```

---

## 🔹 11. Labels & Selectors

```bash
kubectl get pods --show-labels
kubectl label pod <pod-name> env=prod
kubectl get pods -l env=prod
```

---

## 🔹 12. Quick Shortcuts (Very Useful 🔥)

```bash
kubectl get po      # pods
kubectl get svc     # services
kubectl get deploy  # deployments
kubectl get ns      # namespaces
kubectl get all
```

---

## 🔹 13. Dry Run & Output

```bash
kubectl run nginx --image=nginx --dry-run=client -o yaml
kubectl get pod <name> -o yaml
kubectl get pod <name> -o json
```

---

## 🔹 14. Delete Everything (Careful ⚠️)

```bash
kubectl delete all --all
```

# 1. Kubernetes Basics

| Keyword                     | Simple Interview Explanation                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **Kubernetes (K8s)** ⭐⭐⭐ | Kubernetes is a container orchestration platform used to deploy, scale, manage, and self-heal containerized applications. |
| **Cluster** ⭐⭐⭐          | A Kubernetes cluster is a group of machines containing the **Control Plane and Worker Nodes**.                            |
| **Control Plane** ⭐⭐⭐    | The Control Plane is the brain of Kubernetes; it manages the cluster and maintains the desired state.                     |
| **Worker Node** ⭐⭐⭐      | A Worker Node is a machine where application Pods actually run.                                                           |
| **Namespace** ⭐⭐⭐        | A Namespace logically separates and organizes resources inside a Kubernetes cluster, such as `dev`, `test`, and `prod`.   |
| **Manifest** ⭐⭐           | A Manifest is a YAML file that defines the desired configuration of a Kubernetes resource.                                |
| **Desired State** ⭐⭐⭐    | Desired state means what we want Kubernetes to run, for example, 3 replicas of an application.                            |
| **Actual State** ⭐⭐⭐     | Actual state is what is currently running in the cluster.                                                                 |
| **Reconciliation** ⭐⭐⭐⭐ | Kubernetes continuously compares desired and actual state and takes corrective action to make them match.                 |
| **Label** ⭐⭐⭐            | Labels are key-value pairs used to identify and group Kubernetes resources.                                               |
| **Selector** ⭐⭐⭐         | Selectors find resources based on their labels; Services and Deployments commonly use selectors.                          |
| **Annotation** ⭐⭐         | Annotations store additional metadata or information that is not used for selecting resources.                            |

## Control Plane Components

| Keyword                                | Interview Explanation                                                                                                                  |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **kube-apiserver** ⭐⭐⭐⭐⭐          | It is the main entry point to the Kubernetes cluster; `kubectl`, controllers, and other components communicate through the API Server. |
| **etcd** ⭐⭐⭐⭐⭐                    | etcd is a distributed key-value database that stores the Kubernetes cluster's configuration and state.                                 |
| **kube-scheduler** ⭐⭐⭐⭐⭐          | The scheduler decides which Worker Node should run a newly created Pod based on resources and scheduling rules.                        |
| **kube-controller-manager** ⭐⭐⭐⭐⭐ | It runs controllers that continuously monitor the cluster and make the actual state match the desired state.                           |
| **cloud-controller-manager** ⭐⭐⭐    | It integrates Kubernetes with cloud-provider resources such as Load Balancers, routes, and cloud nodes.                                |

## Worker Node Components

| Keyword                        | Interview Explanation                                                                                                                  |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| **kubelet** ⭐⭐⭐⭐⭐         | kubelet is the agent running on every Worker Node; it receives Pod specifications and ensures the required containers are running.     |
| **kube-proxy** ⭐⭐⭐⭐        | kube-proxy traditionally implements Kubernetes Service networking rules on nodes; modern CNIs may replace parts of this functionality. |
| **Container Runtime** ⭐⭐⭐⭐ | The container runtime actually runs containers; common runtimes include `containerd` and `CRI-O`.                                      |
| **CRI** ⭐⭐⭐                 | Container Runtime Interface is the interface between Kubernetes and the container runtime.                                             |
| **CNI** ⭐⭐⭐⭐⭐             | Container Network Interface provides networking for Kubernetes Pods.                                                                   |
| **CSI** ⭐⭐⭐⭐⭐             | Container Storage Interface allows Kubernetes to integrate with external storage systems.                                              |

### Remember the Architecture

```text
                 Kubernetes Cluster
                        |
              +---------+---------+
              |                   |
        Control Plane        Worker Nodes
              |                   |
       +------+------+       +----+------+
       |      |      |       |           |
   API Server etcd Scheduler kubelet   Container
       |             |          |
       +------+------+\         |
              |       \         |
         Controllers   \       Pod
                         \       |
                          \  Container
```

# 3. Pod ⭐⭐⭐⭐⭐

| Keyword                        | Interview Explanation                                                                                                       |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **Pod** ⭐⭐⭐⭐⭐             | A Pod is the smallest deployable unit in Kubernetes and contains one or more containers that share networking and storage.  |
| **Pod IP** ⭐⭐⭐              | Each Pod normally gets its own IP, but the IP is temporary and can change when the Pod is recreated.                        |
| **Multi-container Pod** ⭐⭐⭐ | Multiple containers can run in the same Pod when they need to closely share networking, storage, or lifecycle.              |
| **Sidecar Container** ⭐⭐⭐⭐ | A sidecar is a helper container running with the main application container, such as a logging or proxy container.          |
| **Init Container** ⭐⭐⭐⭐    | An init container runs before the main application containers and is commonly used for initialization or dependency checks. |

### Important

```text
Deployment
    ↓
ReplicaSet
    ↓
Pod
    ↓
Container
```

**Do not normally manage production Pods directly.** Use controllers such as Deployment or StatefulSet.

# 4. Workload Controllers ⭐⭐⭐⭐⭐

## Deployment

**Deployment** is mainly used for **stateless applications** and provides replica management, rolling updates, scaling, and rollback.

```text
Deployment
     ↓
ReplicaSet
     ↓
Pods
```

### Important commands

```bash
kubectl get deployment
kubectl scale deployment app --replicas=5
kubectl rollout status deployment app
kubectl rollout history deployment app
kubectl rollout undo deployment app
```

---

## ReplicaSet

**ReplicaSet ensures that the required number of identical Pods are always running.**

Example:

```text
Desired Pods = 3
Running Pods = 2

ReplicaSet creates 1 new Pod
```

**Interview point:** Deployment creates and manages ReplicaSets.

---

## StatefulSet ⭐⭐⭐⭐⭐

**StatefulSet is used for stateful applications that need stable identity, ordering, and persistent storage.**

Examples:

```text
MySQL
MongoDB
Kafka
Elasticsearch
```

Pod names:

```text
mysql-0
mysql-1
mysql-2
```

### Deployment vs StatefulSet

```text
Deployment  → Stateless application
StatefulSet → Stateful application
```

---

## DaemonSet ⭐⭐⭐⭐

**DaemonSet ensures that a Pod runs on every eligible Worker Node.**

Common use cases:

```text
Logging Agent
Monitoring Agent
Security Agent
Node Exporter
Fluent Bit
```

New node added → DaemonSet automatically creates the required Pod.

---

## Job ⭐⭐⭐

**Job runs a task until it successfully completes.**

Examples:

```text
Database migration
Backup
Batch processing
Data processing
```

---

## CronJob ⭐⭐⭐

**CronJob creates Jobs on a scheduled basis**, similar to Linux cron.

Example:

```text
Every day at 2 AM
       ↓
CronJob
       ↓
Job
       ↓
Pod
```

# 5. Kubernetes Networking ⭐⭐⭐⭐⭐

This is another **very important senior interview area**.

## Service ⭐⭐⭐⭐⭐

**A Service provides a stable network endpoint for accessing Pods, because Pod IPs can change.**

### Service Types

| Type                      | Explanation                                                              |
| ------------------------- | ------------------------------------------------------------------------ |
| **ClusterIP** ⭐⭐⭐⭐    | Default Service type; provides internal access inside the cluster.       |
| **NodePort** ⭐⭐⭐       | Exposes a Service through a port on each Worker Node.                    |
| **LoadBalancer** ⭐⭐⭐⭐ | Creates/uses a cloud Load Balancer to expose the application externally. |
| **ExternalName** ⭐⭐     | Maps a Kubernetes Service name to an external DNS name.                  |

---

# 6. Service Discovery ⭐⭐⭐⭐

**Kubernetes provides DNS-based service discovery so applications can communicate using Service names instead of Pod IPs.**

Example:

```text
backend-service
```

Full DNS:

```text
backend-service.default.svc.cluster.local
```

---

# 7. CoreDNS ⭐⭐⭐⭐

**CoreDNS provides DNS resolution inside the Kubernetes cluster and allows Pods to resolve Service names.**

Example:

```text
frontend → backend-service
```

CoreDNS resolves the Service name to the appropriate Service IP.

---

# 8. Ingress ⭐⭐⭐⭐⭐

**Ingress defines HTTP/HTTPS routing rules that forward external traffic to Kubernetes Services.**

Example:

```text
https://example.com/api
          ↓
       Ingress
          ↓
    backend-service
          ↓
        Pods
```

Ingress supports:

- Host-based routing
- Path-based routing
- TLS/HTTPS
- HTTP routing

### Very Important Interview Point

**Ingress is only the routing configuration; Ingress Controller actually implements the routing.**

Examples:

```text
NGINX Ingress Controller
Traefik
HAProxy
```

---

# 9. Gateway API ⭐⭐⭐⭐

**Gateway API is the newer and more flexible Kubernetes networking API model for traffic routing and application exposure.**

Important resources:

```text
GatewayClass
Gateway
HTTPRoute
```

For a modern interview, know **Ingress + Gateway API**.

---

# 10. CNI ⭐⭐⭐⭐⭐

**CNI provides networking between Kubernetes Pods and connects Pods to the cluster/network environment.**

Popular examples:

```text
Calico
Cilium
Flannel
Cloud-specific CNI
```

---

# 11. NetworkPolicy ⭐⭐⭐⭐⭐

**NetworkPolicy controls which Pods are allowed to communicate with other Pods or network endpoints.**

Example:

```text
Frontend → Backend     ALLOW
Frontend → Database    DENY
Backend  → Database    ALLOW
```

**Important:** NetworkPolicy requires a compatible network implementation/CNI.

# 12. eBPF & Cilium ⭐⭐⭐⭐

**eBPF allows programs to run efficiently inside the Linux kernel without modifying the kernel itself.**

Cilium uses eBPF for:

```text
Networking
Security
Observability
```

For 20+ LPA interviews, know the basic relationship:

```text
Cilium → CNI
Cilium → eBPF
eBPF → Networking + Security + Observability
```

# 15. Secret ⭐⭐⭐⭐⭐

**Secret stores sensitive configuration such as passwords, tokens, API keys, and certificates.**

```text
Azure Key Vault

External Secrets Operator

# 16. Azure Key Vault ⭐⭐⭐⭐

Kubernetes can integrate with it using mechanisms such as:

Azure Key Vault provider

```

# 17. Resource Management ⭐⭐⭐⭐⭐

## Requests

**Request defines the minimum CPU/memory that Kubernetes should reserve for a container and is mainly used by the scheduler.**

## Limits

**Limit defines the maximum CPU/memory a container is allowed to consume.**

Example:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

### Important interview point

```text
CPU limit exceeded
→ CPU throttling can occur

Memory limit exceeded
→ Container may be OOMKilled
```

---

# 18. QoS Classes ⭐⭐⭐

Kubernetes has three main Pod Quality of Service classes:

```text
Guaranteed
Burstable
BestEffort
```

They are determined based on CPU/memory requests and limits.

---

# 19. Health Probes ⭐⭐⭐⭐⭐

## Liveness Probe

**Checks whether the application is still alive; repeated failure can cause Kubernetes to restart the container.**

## Readiness Probe

**Checks whether the application is ready to receive traffic; failure removes the Pod from Service endpoints.**

## Startup Probe

**Checks whether a slow-starting application has successfully started before regular liveness/readiness checks become effective.**

### Easy way to remember

```text
Startup   → Has application started?
Readiness → Can application receive traffic?
Liveness  → Is application still alive?
```

---

# 20. Scaling ⭐⭐⭐⭐⭐

## HPA

**Horizontal Pod Autoscaler increases or decreases the number of Pods based on metrics such as CPU, memory, or custom metrics.**

```text
CPU ↑
 ↓
HPA
 ↓
Pods 3 → 6
```

---

## VPA

**Vertical Pod Autoscaler adjusts or recommends CPU and memory requests for Pods.**

```text
CPU request
250m → 500m
```

---

## Cluster Autoscaler

**Cluster Autoscaler increases or decreases the number of Worker Nodes when Pods cannot be scheduled or nodes are underutilized.**

```text
Pods Pending
    ↓
Cluster Autoscaler
    ↓
New Node
    ↓
Pod scheduled
```

### Remember

```text
HPA → Scale Pods
VPA → Scale Pod resources
CA  → Scale Nodes
```

---

# 21. KEDA ⭐⭐⭐⭐

**KEDA is an event-driven autoscaling solution that can scale Kubernetes workloads based on external events such as Kafka messages or queue length.**

Example:

```text
Kafka messages ↑
       ↓
     KEDA
       ↓
Pods 2 → 10
```

---

# 22. Kubernetes Scheduling ⭐⭐⭐⭐⭐

## Scheduler

**The scheduler selects a suitable Worker Node for a Pod based on resources, affinity, taints, topology, and other constraints.**

---

## nodeSelector

**nodeSelector schedules a Pod only on nodes having the specified label.**

```text
Pod
 ↓
nodeSelector
 ↓
Matching Node
```

---

## Node Affinity ⭐⭐⭐⭐

**Node Affinity provides more flexible rules for selecting which nodes a Pod should run on.**

Types:

```text
requiredDuringScheduling...
preferredDuringScheduling...
```

Remember:

```text
required  → Must match
preferred → Prefer to match
```

---

## Pod Affinity

**Pod Affinity allows Pods to be scheduled close to other selected Pods based on topology rules.**

---

## Pod Anti-Affinity ⭐⭐⭐⭐

**Pod Anti-Affinity helps distribute Pods away from each other to improve availability.**

Example:

```text
Node 1 → app-1
Node 2 → app-2
Node 3 → app-3
```

---

## Taint ⭐⭐⭐⭐

**A Taint is applied to a Node to prevent Pods from being scheduled there unless they have a matching toleration.**

---

## Toleration ⭐⭐⭐⭐

**A Toleration is applied to a Pod to allow it to be scheduled on a node with a matching taint.**

### Easy interview line

> **Taint is applied to a Node, while Toleration is applied to a Pod.**

---

## Topology Spread Constraints ⭐⭐⭐⭐

**Topology Spread Constraints distribute Pods across nodes or availability zones to improve high availability and fault tolerance.**

---

# 31. Deployment Strategies ⭐⭐⭐⭐⭐

## Rolling Update

**Gradually replaces old Pods with new Pods while keeping the application available.**

```text
v1: 5 Pods

v1: 4
v2: 1

v1: 3
v2: 2

...

v2: 5
```

---

## Recreate

**All old Pods are stopped before new Pods are started, which can cause downtime.**

```text
v1 → Stop
     ↓
v2 → Start
```

---

## Blue-Green ⭐⭐⭐⭐

**Two complete environments are maintained: Blue is current and Green is the new version; traffic is switched when Green is ready.**

```text
Blue  → Current
Green → New

Traffic
   ↓
Green
```

---

## Canary ⭐⭐⭐⭐⭐

**A small percentage of traffic is sent to the new version first, and traffic is gradually increased after validation.**

```text
95% → v1
5%  → v2
```

Common tools:

```text
Argo Rollouts
Istio
Gateway/API routing
```

---

# 32. PodDisruptionBudget — PDB ⭐⭐⭐⭐

**PDB protects application availability during voluntary disruptions such as node maintenance or upgrades.**

Example:

```text
5 replicas
minAvailable = 4
```

It helps ensure that too many replicas are not voluntarily disrupted at once.

---

# 33. Node Management ⭐⭐⭐⭐

## Cordon

**Cordon prevents new Pods from being scheduled on a node but does not remove existing Pods.**

```bash
kubectl cordon node1
```

---

## Drain

**Drain safely evicts eligible workloads from a node so it can be maintained or upgraded.**

```bash
kubectl drain node1
```

---

## Uncordon

**Uncordon makes a node available for new Pod scheduling again.**

```bash
kubectl uncordon node1
```

### Easy difference

```text
Cordon  → Stop new scheduling
Drain   → Evict workloads + prepare node
Uncordon → Allow scheduling again
```

---

# 34. Graceful Shutdown ⭐⭐⭐⭐

**Graceful shutdown allows an application to finish existing work before the container is terminated.**

Important concepts:

```text
SIGTERM
preStop
terminationGracePeriodSeconds
```

This is especially important for production APIs and long-running requests.

# 35. Troubleshooting ⭐⭐⭐⭐⭐

This is **extremely important for your experience level**.

## CrashLoopBackOff

**Container starts, crashes, and Kubernetes repeatedly restarts it.**

Common reasons:

```text
Application error
Wrong command
Wrong environment variable
Missing Secret
Configuration issue
Dependency unavailable
```

Check:

```bash
kubectl logs <pod>
kubectl logs <pod> --previous
kubectl describe pod <pod>
```

---

## ImagePullBackOff

**Kubernetes cannot pull the required container image from the registry.**

Common reasons:

```text
Wrong image
Wrong tag
Private registry authentication
Registry issue
imagePullSecret issue
```

---

## Pending Pod

**Pod is waiting because Kubernetes cannot currently schedule it onto a suitable node.**

Common reasons:

```text
Insufficient CPU
Insufficient Memory
Taints
Affinity
NodeSelector
PVC problem
Topology constraints
```

Check:

```bash
kubectl describe pod <pod>
```

---

## OOMKilled

**Container consumed more memory than allowed and the operating system/Kubernetes killed it because of memory exhaustion.**

```text
Memory ↑
   ↓
Limit exceeded
   ↓
OOMKilled
```

# 48. Drift ⭐⭐⭐⭐
