# Security & RBAC

**RBAC — Role-Based Access Control** is a Kubernetes security mechanism used to **control who or what can access Kubernetes resources and what actions they are allowed to perform**.

In simple words:

> **RBAC decides: Who can do What on Which Kubernetes resource.**

### Basic Flow

```text
User / ServiceAccount
        ↓
Role / ClusterRole
        ↓
RoleBinding / ClusterRoleBinding
        ↓
Kubernetes Resources
        ↓
Allowed Actions
```

### Example

Suppose an application Pod should only be allowed to **read Pods**.

```text
Application Pod
      ↓
ServiceAccount: app-sa
      ↓
Role
      ↓
get / list Pods
      ↓
Kubernetes API
```

It should **not** be allowed to delete Pods.

```text
get Pods      → ✅
```


<a id="ServiceAccount"></a>

# ServiceAccount

A **ServiceAccount** in Kubernetes provides an **identity to a Pod or application running inside the cluster**.

In simple words:

> **ServiceAccount = Identity used by a Pod to access Kubernetes resources or other systems.**

### Simple Example

```text
Pod
 │
 │ uses
 ↓
ServiceAccount
 │
 ↓
Identity / Permissions
 │
 ↓
Kubernetes API
```

For example, a Pod may need permission to:

```text
Get Pods
Read ConfigMaps
List Services
```

Instead of using a human user's identity, the Pod uses a **ServiceAccount**.

---

## Example

Create a ServiceAccount:

```yaml
apiVersion: v1
kind: ServiceAccount

metadata:
  name: app-sa
```

Use it in a Pod:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: app-pod

spec:
  serviceAccountName: app-sa

  containers:
    - name: app
      image: nginx
```

Now the Pod runs using:

```text
app-pod
   ↓
app-sa
```

### ServiceAccount + RBAC ⭐

A ServiceAccount by itself does **not automatically give broad permissions**.

Permissions are normally provided using **RBAC**.

```text
ServiceAccount
      ↓
Role / ClusterRole
      ↓
RoleBinding / ClusterRoleBinding
      ↓
Permissions
```

Example:

```text
app-sa
  ↓
Role
  ↓
Allow: get/list Pods
```

So the Pod can access only the resources allowed by its RBAC permissions.

---

## Real-World Example

Suppose an application needs to check the status of Pods.

```text
Application Pod
      ↓
ServiceAccount
      ↓
Role
      ↓
RoleBinding
      ↓
Kubernetes API
      ↓
Get Pods
```

Without the required permission:

```text
Application → Kubernetes API → Forbidden ❌
```

---

## ServiceAccount vs User Account

| User Account            | ServiceAccount                     |
| ----------------------- | ---------------------------------- |
| Represents a human/user | Represents an application/workload |
| Used by people          | Used by Pods                       |
| Example: Developer      | Example: backend Pod               |
| Human authentication    | Workload identity                  |

---

## Important Interview Point

Modern Kubernetes setups generally use **short-lived projected service-account tokens** rather than relying on old-style long-lived Secret-based tokens. This is more secure.

Also, in cloud environments such as **AKS/EKS/GKE**, a Pod's identity can be integrated with the cloud provider so that the workload can access cloud resources without storing long-lived cloud credentials inside the Pod.

### ⭐ Interview Answer

> **A ServiceAccount provides an identity for applications or Pods running inside Kubernetes. It is commonly used with RBAC to control what Kubernetes API resources a workload can access. In cloud environments, ServiceAccounts can also be integrated with cloud workload identity mechanisms to securely access cloud resources.**

**Easy to remember:**

> **ServiceAccount = Pod Identity**
> **RBAC = Permissions**
> **RoleBinding = Connects identity with permissions**

# Role

A **Role** in Kubernetes defines **what actions are allowed on which resources within a specific Namespace**.

In simple words:

> **Role = Permissions inside one Namespace.**

### Simple Example

Suppose you have a `dev` Namespace and you want an application to:

```text
Get Pods
List Pods
Watch Pods
```

But it should **not delete Pods**.

You can create a Role:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role

metadata:
  name: pod-reader
  namespace: dev

rules:
  - apiGroups: [""]
    resources:
      - pods
    verbs:
      - get
      - list
      - watch
```

This means:

```text
Namespace: dev

Pod Reader Role
      │
      ├── get    Pods ✅
      ├── list   Pods ✅
      ├── watch  Pods ✅
      └── delete Pods ❌
```

### Role alone doesn't give permissions to a User/Pod

You need a **RoleBinding** to connect the Role with a User or ServiceAccount.

```text
ServiceAccount
      ↓
RoleBinding
      ↓
Role
      ↓
Permissions
```

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding

metadata:
  name: pod-reader-binding
  namespace: dev

subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: dev

roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

Now:

```text
app-sa
  ↓
RoleBinding
  ↓
pod-reader Role
  ↓
Can get/list/watch Pods in dev namespace
```

### Role vs ClusterRole ⭐

| Role                             | ClusterRole                               |
| -------------------------------- | ----------------------------------------- |
| Namespace-scoped                 | Cluster-scoped                            |
| Permissions within one Namespace | Can apply across the cluster              |
| Used with RoleBinding            | Can use RoleBinding or ClusterRoleBinding |
| Example: Pods in `dev`           | Nodes across the cluster                  |

### Important Interview Point

A **Role does not directly assign permissions**. It only **defines the permissions**. A **RoleBinding** grants those permissions to a user, group, or ServiceAccount.

### ⭐ Interview Answer

> **A Role is a Kubernetes RBAC object that defines permissions for resources within a specific Namespace. It specifies which resources can be accessed and which actions, such as get, list, create, or delete, are allowed. A RoleBinding is used to assign that Role to a User, Group, or ServiceAccount.**

**Easy to remember:**

> **Role = What permissions?**
> **RoleBinding = Who gets those permissions?**
> **ClusterRole = Cluster-wide or reusable permissions**

<a id="RoleBinding"></a>

# RoleBinding

A **RoleBinding** in Kubernetes is used to **assign the permissions defined in a Role to a User, Group, or ServiceAccount**.

In simple words:

> **Role = What permissions?**
> **RoleBinding = Who gets those permissions?**

### Simple Flow

```text
Role
 │
 │ Defines permissions
 ↓
RoleBinding
 │
 │ Assigns permissions to
 ↓
User / Group / ServiceAccount
```

### Example

Suppose we already have a Role:

```text
Role: pod-reader

Permissions:
- get Pods
- list Pods
- watch Pods
```

Now we want to give these permissions to `app-sa`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding

metadata:
  name: pod-reader-binding
  namespace: dev

subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: dev

roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### What happens?

```text
Namespace: dev

app-sa
  │
  ↓
RoleBinding
  │
  ↓
pod-reader Role
  │
  ├── get Pods   ✅
  ├── list Pods  ✅
  ├── watch Pods ✅
  └── delete Pods ❌
```

So `app-sa` gets only the permissions defined in the Role.

---

## Role vs RoleBinding ⭐

| Role                          | RoleBinding                   |
| ----------------------------- | ----------------------------- |
| Defines permissions           | Assigns permissions           |
| Specifies resources           | Specifies who gets access     |
| `get`, `list`, `create`, etc. | User / Group / ServiceAccount |
| Namespace-scoped              | Namespace-scoped              |

Think:

> **Role = Permission book 📖**
> **RoleBinding = Gives that book to someone 👤**

---

## RoleBinding with ClusterRole

A **RoleBinding can also reference a ClusterRole**.

For example:

```text
ClusterRole
    ↓
RoleBinding
    ↓
User
    ↓
Permissions within one Namespace
```

This is useful when you have a reusable ClusterRole but want to grant its permissions only within a particular Namespace.

### RoleBinding vs ClusterRoleBinding

| RoleBinding                       | ClusterRoleBinding         |
| --------------------------------- | -------------------------- |
| Grants access within a Namespace  | Grants cluster-wide access |
| Can reference Role or ClusterRole | References ClusterRole     |
| Namespace-scoped binding          | Cluster-scoped binding     |

### ⭐ Interview Answer

> **RoleBinding is a Kubernetes RBAC object that grants the permissions defined in a Role to a User, Group, or ServiceAccount within a specific Namespace. It can also bind a ClusterRole to a subject while limiting the permissions to the RoleBinding's Namespace.**

**Easy to remember:**

```text
Role
  ↓
"What can they do?"

RoleBinding
  ↓
"Who can do it?"
```

<a id="ClusterRole"></a>

# ClusterRole

A **ClusterRole** is a Kubernetes RBAC object that defines **permissions at the cluster level**.

In simple words:

> **ClusterRole = Defines permissions that can be used across the cluster or for cluster-scoped resources.**

### Example

Suppose you want a user or application to:

```text
Get Nodes
List Nodes
Get Pods
List Pods
```

You can define a ClusterRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole

metadata:
  name: cluster-reader

rules:
  - apiGroups: [""]
    resources:
      - nodes
      - pods
    verbs:
      - get
      - list
      - watch
```

### ClusterRole + ClusterRoleBinding

To give these permissions **across the cluster**:

```text
User / ServiceAccount
        ↓
ClusterRoleBinding
        ↓
ClusterRole
        ↓
Cluster-wide permissions
```

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding

metadata:
  name: cluster-reader-binding

subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: dev

roleRef:
  kind: ClusterRole
  name: cluster-reader
  apiGroup: rbac.authorization.k8s.io
```

Now `app-sa` can use the permissions defined by `cluster-reader` across the cluster.

---

## ClusterRole vs Role ⭐

| Role                                  | ClusterRole                              |
| ------------------------------------- | ---------------------------------------- |
| Namespace-scoped permissions          | Can define cluster-wide permissions      |
| Used for resources within a Namespace | Can be used for cluster-scoped resources |
| Example: Pods in `dev`                | Example: Nodes                           |
| Usually used with RoleBinding         | Often used with ClusterRoleBinding       |

### Important Point

A **ClusterRole doesn't automatically mean cluster-wide access**.

A ClusterRole can also be used with a **RoleBinding** to grant its permissions **only within one Namespace**.

```text
ClusterRole
     │
     ├── ClusterRoleBinding
     │       ↓
     │   Cluster-wide access
     │
     └── RoleBinding
             ↓
       Access limited to
       one Namespace
```

### ⭐ Interview Answer

> **A ClusterRole is a Kubernetes RBAC object used to define permissions for cluster-scoped resources or permissions that can be applied across multiple Namespaces. A ClusterRole is typically assigned using ClusterRoleBinding for cluster-wide access, or RoleBinding when the same permissions should be limited to a particular Namespace.**

**Easy to remember:**

> **Role → Namespace permissions**
> **ClusterRole → Cluster-level/reusable permissions**
> **RoleBinding → Grants access in a Namespace**
> **ClusterRoleBinding → Grants ClusterRole access cluster-wide**

<a id="ClusterRoleBinding"></a>

# ClusterRoleBinding

**ClusterRoleBinding** is a Kubernetes RBAC object used to **assign a ClusterRole to a User, Group, or ServiceAccount across the entire cluster**.

In simple words:

> **ClusterRole = What permissions?**
> **ClusterRoleBinding = Who gets those cluster-wide permissions?**

### Basic Flow

```text
User / ServiceAccount
        ↓
ClusterRoleBinding
        ↓
ClusterRole
        ↓
Cluster-wide permissions
```

### Example

Suppose we have a ClusterRole:

```text
ClusterRole: cluster-reader

Permissions:
- get Nodes
- list Nodes
- get Pods
- list Pods
```

We want to give these permissions to `app-sa`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding

metadata:
  name: cluster-reader-binding

subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: dev

roleRef:
  kind: ClusterRole
  name: cluster-reader
  apiGroup: rbac.authorization.k8s.io
```

Now:

```text
app-sa
  ↓
ClusterRoleBinding
  ↓
cluster-reader
  ↓
Can use permitted resources cluster-wide
```

### RoleBinding vs ClusterRoleBinding ⭐

| RoleBinding                       | ClusterRoleBinding            |
| --------------------------------- | ----------------------------- |
| Grants access within a Namespace  | Grants access cluster-wide    |
| Can reference Role or ClusterRole | References ClusterRole        |
| Example: Pods in `dev`            | Example: Nodes across cluster |
| Namespace-scoped binding          | Cluster-scoped binding        |

### Important Example

```text
Role
 ↓
RoleBinding
 ↓
User
 ↓
Only dev Namespace
```

Whereas:

```text
ClusterRole
 ↓
ClusterRoleBinding
 ↓
User
 ↓
Cluster-wide access
```

### ⚠️ Security Point

ClusterRoleBinding can provide **very broad permissions**, so in production we should follow **least privilege**.

For example, avoid giving:

```text
cluster-admin
```

unless it is genuinely required.

### ⭐ Interview Answer

> **ClusterRoleBinding is a Kubernetes RBAC object that binds a ClusterRole to a User, Group, or ServiceAccount and grants the defined permissions across the Kubernetes cluster. It is commonly used when a workload or user needs access to cluster-scoped resources such as Nodes, or needs the same permissions across multiple Namespaces.**

**Easy to remember:**

> **ClusterRole → Defines permissions**
> **ClusterRoleBinding → Assigns those permissions cluster-wide**

# SecurityContext

**SecurityContext** is a Kubernetes configuration used to define **security settings for a Pod or container**.

In simple words:

> **SecurityContext controls how a Pod/container runs from a security perspective.**

It can control things like:

* Which **Linux user** runs the container
* Which **group** it belongs to
* Whether it can run as **root**
* Linux capabilities
* File-system permissions
* Privilege escalation

---

## Example

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: secure-pod

spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000

  containers:
    - name: app
      image: nginx
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
```

### What this means

```text
Pod
│
├── runAsUser: 1000
│      → Container runs as Linux user 1000
│
├── runAsGroup: 3000
│      → Primary group is 3000
│
├── fsGroup: 2000
│      → Group ownership for supported mounted volumes
│
└── Container SecurityContext
       ├── No privilege escalation
       └── Root filesystem is read-only
```

---

## Pod-level vs Container-level

SecurityContext can be defined at **Pod level** or **Container level**.

### Pod-level

```yaml
spec:
  securityContext:
    runAsUser: 1000
```

Applies to containers in the Pod unless overridden.

### Container-level

```yaml
containers:
  - name: app
    securityContext:
      runAsUser: 2000
```

Applies specifically to that container.

> **Container-level settings can override applicable Pod-level settings.**

---

## Important SecurityContext Settings ⭐

### `runAsUser`

Specifies the Linux user ID.

```yaml
runAsUser: 1000
```

Instead of running as root (`UID 0`), the application runs as user `1000`.

---

### `runAsNonRoot`

Ensures the container is expected to run as a non-root user.

```yaml
runAsNonRoot: true
```

This is a common security best practice.

---

### `runAsGroup`

Specifies the primary Linux group.

```yaml
runAsGroup: 3000
```

---

### `fsGroup`

Defines a group ID used for permissions on supported mounted volumes.

```yaml
fsGroup: 2000
```

Useful when an application needs appropriate group access to mounted storage.

---

### `allowPrivilegeEscalation`

Controls whether a process can gain more privileges than its parent process.

```yaml
allowPrivilegeEscalation: false
```

Generally recommended when the application does not need privilege escalation.

---

### `privileged`

Runs a container with elevated privileges.

```yaml
privileged: false
```

For normal applications, you generally want this disabled.

---

### `readOnlyRootFilesystem`

Makes the container's root filesystem read-only.

```yaml
readOnlyRootFilesystem: true
```

This reduces the ability of an attacker or compromised application to modify the container filesystem.

---

## SecurityContext vs RBAC ⭐

These are different concepts and are often confused.

### SecurityContext

Controls:

> **How the container runs**

```text
User
Group
Root / Non-root
Privileges
Filesystem
Capabilities
```

### RBAC

Controls:

> **What Kubernetes API resources the identity can access**

```text
User / ServiceAccount
        ↓
Role / ClusterRole
        ↓
Permissions
```

### Easy Difference

```text
SecurityContext
     ↓
"How does my container run?"

RBAC
     ↓
"What can my identity access?"
```

---

## SecurityContext vs ServiceAccount

Another important distinction:

```text
ServiceAccount
     ↓
Kubernetes identity
     ↓
RBAC permissions
```

Whereas:

```text
SecurityContext
     ↓
Linux/container security settings
     ↓
User / Group / Privileges
```

A Pod can use both:

```text
                 Pod
              /       \
             ↓         ↓
     ServiceAccount   SecurityContext
             ↓         ↓
           RBAC     Container Security
```

---

## ⭐ Interview Answer

> **SecurityContext is used to define security settings for Pods and containers, such as the Linux user and group they run as, whether they can run as root, privilege escalation, filesystem permissions, and Linux capabilities. It helps enforce the principle of least privilege at the container level.**

### Easy to remember

> **SecurityContext → Container security**
> **ServiceAccount → Pod identity**
> **RBAC → Kubernetes API permissions**

# NetworkPolicy

**NetworkPolicy** is a Kubernetes object used to **control network traffic between Pods and other network endpoints**.

In simple words:

> **NetworkPolicy defines which traffic is allowed and which traffic is blocked.**

It works like a **firewall for Pod network communication**.

### Simple Example

Suppose you have:

```text
Frontend Pod
     ↓
Backend Pod
     ↓
Database Pod
```

You want:

```text
Frontend → Backend  ✅
Backend  → Database ✅
Frontend → Database ❌
```

NetworkPolicy can enforce this communication pattern.

---

## Basic Flow

```text
                 NetworkPolicy
                      ↓
              ┌───────┴───────┐
              ↓               ↓
           Ingress          Egress
              ↓               ↓
        Incoming traffic   Outgoing traffic
```

### Ingress

**Ingress = incoming traffic to a Pod**

```text
Frontend Pod
     ↓
     ↓ incoming
Backend Pod
```

The policy can say:

> Backend Pod accepts traffic only from Frontend Pods.

### Egress

**Egress = outgoing traffic from a Pod**

```text
Backend Pod
     ↓ outgoing
Database Pod
```

The policy can say:

> Backend Pod can communicate only with the Database Pod.

---

# Example NetworkPolicy

Suppose the backend Pods have this label:

```yaml
app: backend
```

And frontend Pods have:

```yaml
app: frontend
```

We can allow only frontend → backend traffic:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: backend-policy
  namespace: default

spec:
  podSelector:
    matchLabels:
      app: backend

  policyTypes:
    - Ingress

  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
```

### Meaning

```text
Backend Pods
     ↑
     │
     │ Allowed
     │
Frontend Pods
```

Other Pods trying to access the backend can be blocked once the applicable ingress policy selects the backend Pods.

---

# Namespace Example ⭐

You can also allow traffic from a specific Namespace.

```yaml
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            environment: production
```

Meaning:

> Allow incoming traffic from Pods in Namespaces labeled `environment=production`.

You can combine Namespace and Pod selectors for more precise rules.

---

# Port Restriction

You can also restrict traffic to specific ports.

Example:

```yaml
ingress:
  - from:
      - podSelector:
          matchLabels:
            app: frontend

    ports:
      - protocol: TCP
        port: 8080
```

Meaning:

```text
Frontend → Backend:8080  ✅
Frontend → Backend:3306  ❌
```

assuming no other applicable policy allows the latter.

---

# Default Deny ⭐

A common security practice is to start with **default deny** and then explicitly allow required traffic.

### Deny all ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: deny-all-ingress

spec:
  podSelector: {}

  policyTypes:
    - Ingress
```

Now incoming traffic to selected Pods is denied unless another applicable policy allows it.

Similarly, you can create:

```text
Default Deny Ingress
Default Deny Egress
```

and then create specific allow policies.

---

# Real-World Example

Suppose you have an application:

```text
Internet
   ↓
Ingress
   ↓
Frontend
   ↓
Backend
   ↓
Database
```

You can design policies like:

```text
Frontend → Backend       ✅
Backend → Database:5432  ✅
Frontend → Database      ❌
Database → Frontend      ❌
Unknown Pod → Backend    ❌
```

This follows the **least-privilege networking** principle.

---

# NetworkPolicy vs SecurityContext ⭐

These are different:

| NetworkPolicy                 | SecurityContext             |
| ----------------------------- | --------------------------- |
| Controls network traffic      | Controls container security |
| Pod-to-Pod communication      | User/group/privileges       |
| Ingress/Egress                | Root/non-root               |
| Network firewall-like control | Linux/container security    |

```text
NetworkPolicy
     ↓
"Who can communicate with my Pod?"

SecurityContext
     ↓
"How does my container run?"
```

### Important Point

NetworkPolicy enforcement depends on the **Kubernetes networking implementation/CNI**. A NetworkPolicy object by itself does not magically enforce traffic rules unless the cluster's network provider supports NetworkPolicy.

---

## ⭐ Interview Answer

> **NetworkPolicy is a Kubernetes security mechanism used to control network communication to and from Pods. It can define ingress and egress rules based on Pods, Namespaces, IP ranges, and ports. We can use it to implement least-privilege networking, for example allowing only frontend Pods to access backend Pods and only backend Pods to access the database.**

### Easy to remember

> **Ingress → Incoming traffic**
> **Egress → Outgoing traffic**
> **NetworkPolicy → Controls Pod network communication**
> **Default Deny → Block first, allow only required traffic**
