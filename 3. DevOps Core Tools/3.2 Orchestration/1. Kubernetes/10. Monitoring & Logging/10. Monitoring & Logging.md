# Metrics

**Metrics in Kubernetes** are numerical measurements used to understand the **health, performance, and resource usage** of the cluster and applications.

In simple words:

> **Metrics tell us how much CPU, Memory, traffic, and other resources are being used.**

### Common Kubernetes Metrics

```text
Metrics
│
├── CPU Usage
├── Memory Usage
├── Pod Count
├── Node Usage
├── Request Rate
├── Error Rate
└── Request Latency
```

### 1. CPU & Memory Metrics

For example:

```text
Node
CPU Usage    = 65%
Memory Usage = 70%
```

Pod:

```text
Pod-1
CPU    = 200m
Memory = 300Mi
```

These metrics help identify resource consumption and capacity problems.

---

## Metrics Server ⭐

**Metrics Server** collects basic resource metrics from Kubernetes Nodes and Pods.

```text
Kubelet
   ↓
Metrics Server
   ↓
Kubernetes API
   ↓
kubectl / HPA
```

You can check resource usage with:

```bash
kubectl top nodes
kubectl top pods
```

Example:

```text
NAME      CPU(cores)   MEMORY(bytes)
node-1    850m         3.2Gi
node-2    450m         2.1Gi
```

### Metrics Server and HPA

HPA can use resource metrics such as CPU and memory to decide whether to scale Pods.

```text
Pod CPU Usage
      ↓
Metrics Server
      ↓
HPA
      ↓
More / Fewer Pods
```

For example:

```text
CPU > 70%
   ↓
HPA
   ↓
2 Pods → 5 Pods
```

---

# Monitoring Metrics

Metrics Server is mainly for **basic resource metrics**. For full monitoring, platforms commonly use **Prometheus + Grafana**.

```text
Application / Kubernetes
          ↓
      Prometheus
          ↓
       Metrics
          ↓
       Grafana
          ↓
      Dashboards
```

### Prometheus

Prometheus collects and stores time-series metrics.

Examples:

```text
CPU usage
Memory usage
Request count
Error count
Request latency
```

### Grafana

Grafana displays metrics through dashboards and graphs.

```text
Prometheus
    ↓
Grafana
    ↓
Dashboard
```

---

# Metrics vs Logs vs Traces ⭐

These three are important in DevOps interviews.

| Type        | Tells you                      |
| ----------- | ------------------------------ |
| **Metrics** | What is happening numerically? |
| **Logs**    | What happened?                 |
| **Traces**  | Where did the request travel?  |

Example:

```text
Metrics → CPU = 90%
Logs    → "Database connection failed"
Trace   → Frontend → Backend → Database
```

### ⭐ Interview Answer

> **Metrics are numerical measurements used to monitor the health and performance of Kubernetes resources and applications. Metrics Server provides basic CPU and memory metrics for Pods and Nodes and is commonly used by HPA. For advanced monitoring, tools such as Prometheus and Grafana are commonly used.**

**Easy to remember:**

> **Metrics → Numbers**
> **Metrics Server → Basic CPU/Memory**
> **Prometheus → Collects/stores metrics**
> **Grafana → Visualizes metrics**

# Prometheus

**Prometheus** is an open-source **monitoring and metrics collection system** used to collect, store, query, and alert on time-series metrics.

In simple words:

> **Prometheus collects metrics from Kubernetes and applications and stores them so we can monitor performance and create alerts.**

### Basic Flow

```text
Kubernetes / Applications
          ↓
       Metrics
          ↓
     Prometheus
          ↓
   ┌──────┴──────┐
   ↓             ↓
Grafana       Alertmanager
   ↓             ↓
Dashboard      Alerts
```

## What does Prometheus collect?

Examples:

```text
CPU Usage
Memory Usage
Pod Count
Request Count
Error Rate
Request Latency
Network Traffic
```

For example:

```text
Pod CPU Usage = 75%
Memory Usage  = 60%
HTTP Requests = 10,000
Error Rate    = 2%
```

---

## How Prometheus works ⭐

Prometheus commonly uses a **pull/scrape model**.

It periodically **scrapes metrics from configured targets**.

```text
Application
     ↑
     │ /metrics
     │
Prometheus
     │
     ↓
Stores time-series data
```

For Kubernetes:

```text
Kubernetes
    ↓
Metrics endpoints
    ↓
Prometheus
    ↓
Time-series database
```

Prometheus can discover Kubernetes targets using **Kubernetes service discovery**.

---

## `/metrics`

Applications can expose metrics through an endpoint such as:

```text
/metrics
```

Example:

```text
http_requests_total 15000
http_request_errors_total 120
```

Prometheus periodically collects these values.

---

## Prometheus Query Language — PromQL

Prometheus provides **PromQL (Prometheus Query Language)** to query metrics.

Example:

```promql
up
```

Shows whether targets are up.

Another example:

```promql
rate(http_requests_total[5m])
```

This can be used to calculate the request rate over the last 5 minutes.

---

# Prometheus + Grafana ⭐

Prometheus and Grafana are often used together.

```text
Kubernetes
     ↓
Prometheus
     ↓
Collect & Store Metrics
     ↓
Grafana
     ↓
Dashboard
```

Example Grafana dashboard:

```text
┌─────────────────────────────┐
│ Kubernetes Monitoring       │
├─────────────────────────────┤
│ CPU Usage       72%         │
│ Memory Usage    65%         │
│ Pods            25          │
│ Requests/sec    1,250       │
│ Error Rate      1.2%        │
└─────────────────────────────┘
```

---

# Prometheus + Alertmanager

Prometheus can evaluate alerting rules.

Example:

```text
CPU > 80%
for 5 minutes
      ↓
Prometheus Alert
      ↓
Alertmanager
      ↓
Notification
```

Alertmanager can handle things such as:

* Grouping alerts
* Deduplicating alerts
* Routing alerts
* Sending notifications

---

# Prometheus vs Metrics Server ⭐

| Metrics Server           | Prometheus                                       |
| ------------------------ | ------------------------------------------------ |
| Basic resource metrics   | Full monitoring/metrics platform                 |
| CPU & Memory primarily   | Many types of application/infrastructure metrics |
| Commonly used by HPA     | Monitoring, dashboards, alerting                 |
| Short-term/basic metrics | Stores time-series data                          |
| `kubectl top`            | PromQL queries                                   |

```text
Metrics Server
     ↓
Basic CPU/Memory
     ↓
HPA


Prometheus
     ↓
Detailed metrics
     ↓
Grafana / Alertmanager
```

---

# Real DevOps Example

Suppose your Kubernetes application suddenly becomes slow.

Prometheus can show:

```text
CPU Usage       → 95%
Memory Usage    → 90%
Request Rate    → High
Error Rate      → 8%
Latency         → 2 seconds
```

You can use Grafana to visualize these metrics and Alertmanager to notify the team.

```text
High Traffic
     ↓
CPU increases
     ↓
Prometheus collects metrics
     ↓
Grafana shows the problem
     ↓
Alertmanager sends alert
```

---

## ⭐ Interview Answer

> **Prometheus is an open-source monitoring and time-series metrics platform. In Kubernetes, it collects metrics from Nodes, Pods, applications, and other components, stores them as time-series data, and allows us to query them using PromQL. Prometheus is commonly integrated with Grafana for visualization and Alertmanager for alerting.**

### Easy to remember

> **Prometheus → Collect + Store + Query metrics**
> **PromQL → Query metrics**
> **Grafana → Visualize metrics**
> **Alertmanager → Send/manage alerts**
> **Metrics Server → Basic CPU/Memory metrics**

# Grafana

**Grafana** is an open-source **observability and visualization platform** used to create dashboards and visualize metrics collected from systems such as Kubernetes and Prometheus.

In simple words:

> **Grafana takes metrics from Prometheus and converts them into easy-to-understand dashboards, graphs, and alerts.**

### Basic Flow

```text
Kubernetes / Application
          ↓
      Prometheus
          ↓
    Collects Metrics
          ↓
       Grafana
          ↓
   Dashboards / Graphs
```

### Example

Prometheus stores metrics like:

```text
CPU Usage      = 75%
Memory Usage   = 65%
Pod Count      = 10
Request Rate   = 1,200/sec
Error Rate     = 2%
```

Grafana displays them visually:

```text
┌──────────────────────────────────┐
│       Kubernetes Dashboard       │
├──────────────────────────────────┤
│ CPU Usage       ███████ 75%      │
│ Memory Usage    ██████  65%      │
│ Pods                    10       │
│ Requests/sec           1200      │
│ Error Rate             2%        │
└──────────────────────────────────┘
```

---

## Grafana Dashboard

A Grafana **Dashboard** contains multiple panels.

```text
Dashboard
│
├── CPU Usage
├── Memory Usage
├── Pod Count
├── Network Traffic
├── Request Rate
├── Error Rate
└── Latency
```

Each panel can display data as:

* Graph
* Time series
* Gauge
* Table
* Stat
* Bar chart

---

## Grafana + Prometheus ⭐

They are commonly used together, but they have different responsibilities.

| Prometheus               | Grafana                         |
| ------------------------ | ------------------------------- |
| Collects metrics         | Visualizes metrics              |
| Stores time-series data  | Creates dashboards              |
| Uses PromQL              | Uses data-source queries        |
| Can evaluate alert rules | Can visualize and manage alerts |
| Monitoring backend       | Visualization/observability UI  |

```text
Prometheus
    │
    │ Metrics
    ↓
Grafana
    │
    ↓
Dashboard
```

### Example

Prometheus:

```promql
rate(http_requests_total[5m])
```

Grafana uses the query/data source to show the result as a graph.

---

## Grafana Data Sources

Grafana can connect to many data sources, not only Prometheus.

Examples:

```text
Prometheus
Loki
Elasticsearch
InfluxDB
MySQL
PostgreSQL
Cloud monitoring systems
```

For Kubernetes monitoring, a common stack is:

```text
Prometheus → Metrics
Loki       → Logs
Grafana    → Visualization
```

---

## Grafana Alerting

Grafana can also create alerts based on metrics.

Example:

```text
CPU > 80%
for 5 minutes
       ↓
Grafana Alert
       ↓
Notification
```

Depending on the monitoring architecture, alerting may instead be handled by **Prometheus + Alertmanager**.

          ┌─────────┴─────────┐

## ⭐ Interview Answer

# Logs

**Logs** are records of events generated by applications, containers, Pods, and Kubernetes components.

In simple words:

> **Logs tell us what happened inside an application or system.**

Logs are mainly used for **troubleshooting, debugging, monitoring, and auditing**.

### Simple Example

Suppose an application is not working:

```text
Application
     ↓
Error occurs
     ↓
Log
     ↓
"Database connection failed"
```

This helps the DevOps engineer understand the problem.

---

## Kubernetes Logs

Kubernetes provides logs from containers running inside Pods.

```bash
kubectl logs <pod-name>
```

Example:

```bash
kubectl logs my-app-pod
```

For a specific container in a multi-container Pod:

```bash
kubectl logs my-app-pod -c app
```

To follow logs continuously:

```bash
kubectl logs -f my-app-pod
```

### Previous Container Logs

If a container restarted and you want the logs from its previous instance:

```bash
kubectl logs my-app-pod --previous
```

This is very useful for troubleshooting **CrashLoopBackOff**.

---

# Types of Logs

### 1. Application Logs

Generated by the application itself.

```text
INFO  User login successful
ERROR Database connection failed
WARN  Request took too long
```

### 2. Container Logs

Container runtime captures the application's standard output/error.

```text
stdout
stderr
```

Kubernetes can expose these through:

```bash
kubectl logs
```

### 3. Kubernetes Component Logs

Kubernetes components such as:

```text
API Server
Scheduler
Controller Manager
Kubelet
```

also generate logs that help troubleshoot cluster-level problems.

---

# Centralized Logging ⭐

In a production Kubernetes environment, we usually don't depend only on:

```bash
kubectl logs
```

because Pods are often temporary and logs need to be collected centrally.

A common architecture is:

```text
Pod / Container
      ↓
Container Logs
      ↓
Log Collector
      ↓
Central Log Storage
      ↓
Search / Dashboard
```

Common technologies include:

* **Fluent Bit**
* **Fluentd**
* **Logstash**
* **Loki**
* **Elasticsearch**
* **OpenSearch**

---

# Loki + Grafana ⭐

A common lightweight Kubernetes logging stack is:

```text
Kubernetes
    ↓
Fluent Bit
    ↓
Loki
    ↓
Grafana
```

### Loki

**Loki** stores and indexes logs in a way designed to work well with Grafana.

### Grafana

Grafana allows engineers to search and visualize those logs.

```text
Application
     ↓
Logs
     ↓
Fluent Bit
     ↓
Loki
     ↓
Grafana
     ↓
Search / Dashboard
```

---

# Logs vs Metrics vs Traces ⭐⭐⭐

This is a very common interview question.

| Observability Type | Purpose                   |
| ------------------ | ------------------------- |
| **Logs**           | What happened?            |
| **Metrics**        | How much / how often?     |
| **Traces**         | Where did the request go? |

Example:

```text
Logs:
"Database connection failed"

Metrics:
Error rate = 8%

Trace:
Frontend → Backend → Payment → Database
                         ↓
                       Slow
```

Together they provide **observability**.

---

# Real DevOps Example

Suppose users report that your application is slow.

### Metrics

```text
CPU = 85%
Memory = 75%
Latency = 2 seconds
```

### Logs

```text
ERROR Database connection timeout
```

### Trace

```text
Frontend
   ↓
Backend
   ↓
Database
   ↓
2-second delay
```

Now you can identify that the database connection is likely causing the problem.

---

## ⭐ Interview Answer

> **Logs are records generated by applications, containers, and Kubernetes components that describe events and errors. In Kubernetes, we can use `kubectl logs` to view container logs. In production, we commonly use centralized logging solutions such as Fluent Bit with Loki or Elasticsearch, and Grafana can be used to search and visualize logs.**

### Easy to remember

> **Logs → What happened?**
> **Metrics → How much/how often?**
> **Traces → Where did it happen?**
> **Grafana → Visualize**
> **Loki/Elasticsearch → Store & search logs**

# Kubernetes Events

**Kubernetes Events** are records generated by Kubernetes when something important happens to a resource such as a **Pod, Node, Deployment, or Service**.

In simple words:

> **Events tell us what Kubernetes is doing or why something happened.**

They are especially useful for **troubleshooting**.

### Example

Suppose a Pod is not starting:

```text id="z2e0o3"
Pod
 ↓
Pending
 ↓
Scheduler cannot find a suitable Node
 ↓
Event:
"0/3 nodes are available"
```

You can investigate the reason using Events.

---

## Common Kubernetes Events

```text id="1d3z0d"
Events
│
├── Scheduled
├── Pulling
├── Pulled
├── Created
├── Started
├── Failed
├── BackOff
├── Unhealthy
└── Evicted
```

### Example Pod Lifecycle

```text id="2m4v7c"
Pod Created
    ↓
Scheduled
    ↓
Pulling image
    ↓
Pulled image
    ↓
Created container
    ↓
Started container
```

Kubernetes generates Events for these actions.

---

## Important Commands ⭐

### View all Events

```bash
kubectl get events
```

### Events in all Namespaces

```bash
kubectl get events -A
```

### Events sorted by time

```bash
kubectl get events --sort-by=.lastTimestamp
```

### Events for a specific Pod

```bash
kubectl describe pod <pod-name>
```

At the bottom of the output, you commonly see:

```text
Events:
  Type     Reason     Message
  ----     ------     -------
  Normal   Scheduled  Successfully assigned...
  Normal   Pulling    Pulling image...
  Normal   Started    Started container...
```

---

# Event Types

### Normal

Indicates a normal/expected operation.

```text
Normal  Scheduled
Normal  Pulled
Normal  Created
Normal  Started
```

### Warning

Indicates a problem or abnormal condition.

```text
Warning  Failed
Warning  BackOff
Warning  Unhealthy
Warning  FailedMount
```

---

# Real Troubleshooting Example

Suppose:

```bash
kubectl get pods
```

shows:

```text
NAME       READY   STATUS             RESTARTS
my-app     0/1     CrashLoopBackOff   5
```

First:

```bash
kubectl describe pod my-app
```

Look at **Events**:

```text
Warning  BackOff
Back-off restarting failed container
```

Then check the container logs:

```bash
kubectl logs my-app
```

So:

```text id="s4f2v8"
Events
  ↓
Why is Kubernetes having a problem?
  ↓
Logs
  ↓
What did the application report?
```

---

# Events vs Logs vs Metrics ⭐

| Events                                  | Logs                             | Metrics                    |
| --------------------------------------- | -------------------------------- | -------------------------- |
| Kubernetes actions/state changes        | Application/system messages      | Numerical measurements     |
| Short-lived troubleshooting information | Detailed application information | Performance/resource data  |
| `kubectl get events`                    | `kubectl logs`                   | `kubectl top` / Prometheus |
| "Pod failed to mount volume"            | "Database connection failed"     | CPU = 90%                  |

### Easy Example

```text id="v4g1rm"
Event:
Pod was unable to mount volume.

Log:
Application cannot access /data.

Metric:
Disk usage = 95%.
```

Together, they help identify the root cause.

---

## Important Interview Point

Kubernetes Events are **not a replacement for centralized logging or monitoring**. They are mainly useful for understanding Kubernetes resource lifecycle and troubleshooting recent cluster/resource problems.

Events are also generally **short-lived/retained for a limited period**, depending on cluster configuration.

---

## ⭐ Interview Answer

> **Kubernetes Events are records generated by Kubernetes when important actions or state changes occur, such as Pod scheduling, image pulling, container failures, volume mount failures, or Pod eviction. We commonly use `kubectl get events` and `kubectl describe` to troubleshoot Kubernetes resources.**

**Easy to remember:**

> **Events → What did Kubernetes do or why did it fail?**
> **Logs → What did the application say?**
> **Metrics → How is the system performing?**
