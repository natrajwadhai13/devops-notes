# 1. Helm in CI/CD ⭐⭐⭐⭐⭐

Helm is commonly used in CI/CD pipelines to deploy applications to Kubernetes.

Typical pipeline:

```text
Developer
    ↓
Git Push
    ↓
CI Pipeline
    ↓
Build Application
    ↓
Build Docker Image
    ↓
Push Image
    ↓
Helm Deploy
    ↓
Kubernetes
```

Example:

```bash
helm upgrade --install myapp ./helm/myapp \
  -n production \
  --create-namespace \
  -f ./helm/myapp/values-prod.yaml \
  --set image.tag=$IMAGE_TAG
```

# 2. Helm in GitOps ⭐⭐⭐⭐⭐

In GitOps, Git is the **source of truth**.

Instead of CI directly deploying to Kubernetes:

```text
Traditional CI/CD:

Git
 ↓
CI
 ↓
Helm
 ↓
Kubernetes
```

GitOps:

```text
Git
 ↓
Argo CD
 ↓
Helm
 ↓
Kubernetes
```

Argo CD continuously compares the desired state in Git with the actual state in Kubernetes.

# 4. Helm + GitLab CI/CD ⭐⭐⭐⭐⭐

A typical GitLab pipeline:

```text
GitLab
   ↓
Build
   ↓
Test
   ↓
Docker Build
   ↓
Docker Push
   ↓
Helm Deploy
```

Example `.gitlab-ci.yml` concept:

```yaml
deploy:
  stage: deploy
  script:
    - helm lint ./helm/myapp
    - helm upgrade --install myapp ./helm/myapp
      -n production
      -f ./helm/myapp/values-prod.yaml
      --set image.tag=$CI_COMMIT_SHA
```

The exact pipeline depends on how your Kubernetes credentials and runners are configured.

# 7. Helm Package + OCI Registry ⭐⭐⭐⭐⭐

Helm Charts can be packaged and stored in an OCI registry.

```bash
helm package ./helm/myapp
```

Output:

```text
myapp-1.0.0.tgz
```

Login:

```bash
helm registry login registry.example.com
```

Push:

```bash
helm push myapp-1.0.0.tgz \
  oci://registry.example.com/helm
```

Architecture:

```text
CI Pipeline
    ↓
helm package
    ↓
OCI Registry
    ↓
Helm Chart
```

# 8. `helm upgrade --install` ⭐⭐⭐⭐⭐

This is extremely common in CI/CD.

```bash
helm upgrade --install myapp ./helm/myapp
```

Logic:

```text
Release exists?
     │
 ┌───┴───┐
Yes      No
 ↓        ↓
Upgrade  Install
```

It prevents the pipeline from needing separate logic for first deployment vs subsequent deployment.

# 10. Helm + Argo CD ⭐⭐⭐⭐⭐

This is especially important because you're learning **Argo CD and GitOps**.

Argo CD can use a Helm Chart as the application source.

Architecture:

```text
             Git Repository
                   │
                   ↓
             Helm Chart
                   │
                   ↓
                Argo CD
                   │
                   ↓
             Kubernetes
```

Argo CD reads:

```text
Chart.yaml
values.yaml
templates/
```

and uses Helm to render Kubernetes manifests.

---

# 11. Important: Argo CD Does Not Normally Need `helm install` ⭐⭐⭐⭐⭐

In a GitOps model, you generally don't manually run:

```bash
helm install
```

from CI for the Argo CD-managed application.

Instead:

```text
Git
 ↓
Argo CD
 ↓
Helm rendering
 ↓
Kubernetes
```

Argo CD manages synchronization.

This is an important interview point.

# 12. GitOps Deployment Model ⭐⭐⭐⭐⭐

Suppose you want to deploy version:

```text
1.2.0
```

You update the Git configuration:

```yaml
image:
  tag: "1.2.0"
```

Then:

```text
Git Commit
    ↓
Argo CD detects change
    ↓
Helm renders Chart
    ↓
Argo CD syncs
    ↓
Kubernetes
```

Git becomes the desired-state source.



```text
                CI
                 │
     ┌───────────┼───────────┐
     ↓           ↓           ↓
   Build       Test       Push Image
                              │
                              ↓
                         Image Registry

      ↓

      ↓
```

# 15. Automated Validation ⭐⭐⭐⭐⭐

Before deployment, CI should validate the Helm Chart.

Typical steps:

```bash
helm lint ./helm/myapp
```

Then:

```bash
helm template myapp ./helm/myapp
```

Optionally:

```bash
helm template myapp ./helm/myapp \
  -f ./helm/myapp/values-prod.yaml
```

Then security checks/scans can be performed.

# 17. Helm Rollback in CI/CD ⭐⭐⭐⭐⭐

If a deployment fails:

```bash
helm history myapp
```

Then:

```bash
helm rollback myapp 2
```

But in a GitOps setup, be careful.

If Git says:

```text
Version 3
```

and you manually rollback the cluster to:

```text
Version 2
```

Argo CD may detect the cluster as **OutOfSync** and reconcile it back to the Git-defined state.

Therefore, in GitOps, rollback is usually performed by **reverting the Git change**.

```text
GitOps Rollback:

Git
 ↓
Revert commit
 ↓
Argo CD
 ↓
Kubernetes
```

This is a very important distinction.

# 18. Traditional Helm vs GitOps ⭐⭐⭐⭐⭐

| Area            | Traditional Helm CI/CD | GitOps + Argo CD |
| --------------- | ---------------------- | ---------------- |
| Source of truth | CI/CD + Git            | Git              |
| Deployment      | CI runs Helm           | Argo CD          |
| Helm command    | `helm upgrade`         | Argo CD manages  |
| Drift detection | Usually manual         | Automatic        |
| Rollback        | Helm rollback          | Git revert       |
| Desired state   | Pipeline configuration | Git              |
| Kubernetes sync | Pipeline-driven        | Argo CD-driven   |

# 21. Helm + Argo CD Interview Scenario ⭐⭐⭐⭐⭐

### Question:

**"Your CI pipeline builds a Docker image. How will you deploy it using Helm and Argo CD?"**

Good answer:

```text
1. Developer pushes code.
2. CI builds and tests the application.
3. CI builds the Docker image.
4. Image is pushed to the container registry.
5. CI updates the image tag in the GitOps repository.
6. Argo CD detects the Git change.
7. Argo CD renders the Helm Chart.
8. Argo CD synchronizes the Kubernetes resources.
9. Kubernetes deploys the new image.
```

This demonstrates both **CI/CD and GitOps understanding**.

# 23. Best Practices ⭐⭐⭐⭐⭐

### 1. Validate Helm Charts

```bash
helm lint
helm template
```

### 2. Use environment-specific values

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

### 3. Use immutable image tags

Prefer:

```text
myapp:abc123
```

over:

```text
myapp:latest
```

### 4. Don't store secrets in Git

Use an appropriate secret-management solution.

### 5. Use Git as the source of truth for GitOps

Avoid manual changes directly in the cluster.

### 6. Use `helm upgrade --install` for traditional CI/CD

```bash
helm upgrade --install
```

### 7. For Argo CD, prefer Git-based rollback

```text
Revert Git
   ↓
Argo CD
   ↓
Kubernetes
```

# Quick Interview Revision

**Q: How is Helm used in CI/CD?**

→ CI validates the Chart and can use Helm to deploy applications to Kubernetes.

```text
CI → Helm → Kubernetes
```

**Q: How is Helm used with GitOps?**

→ Helm provides the packaging/template mechanism while Argo CD manages synchronization from Git to Kubernetes.

```text
Git → Argo CD → Helm → Kubernetes
```

**Q: What is the difference between traditional Helm deployment and Argo CD?**

```text
Traditional:
CI → helm upgrade → Kubernetes

GitOps:
Git → Argo CD → Kubernetes
```

**Q: What does CI usually do in a GitOps model?**

→ Build, test, scan, create/push the Docker image, and update the GitOps configuration.

**Q: How is an image tag updated?**

Example:

```yaml
image:
  tag: abc123
```

CI updates the GitOps configuration, and Argo CD deploys the new desired state.

**Q: How do you rollback in GitOps?**

→ Revert the Git change rather than manually changing the cluster with `helm rollback`.

**Q: Why can manual `helm rollback` be problematic with Argo CD?**

→ Argo CD may detect the cluster as OutOfSync and restore the state defined in Git.
