# 1. Helm and Kubernetes Resources ⭐⭐⭐⭐⭐

Helm does **not replace Kubernetes**.

Helm is used to package, configure, template, and deploy Kubernetes resources.

```text
Helm Chart
    ↓
Templates + values.yaml
    ↓
Rendered Kubernetes YAML
    ↓
Kubernetes API
    ↓
Kubernetes Resources
```

Common resources managed by Helm:

```text
Deployment
Service
ConfigMap
Secret
Ingress
ServiceAccount
Role
RoleBinding
PVC
Job
CronJob
HPA
```

---

# 2. Helm Chart → Kubernetes Manifest ⭐⭐⭐⭐⭐

Example:

`values.yaml`

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: "1.27"
```

Template:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
```

Helm renders:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
```

Then Kubernetes creates the Deployment.

---

# 3. Deployment ⭐⭐⭐⭐⭐

Deployment manages application Pods.

Helm template:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}

  selector:
    matchLabels:
      app: {{ include "myapp.name" . }}

  template:
    metadata:
      labels:
        app: {{ include "myapp.name" . }}

    spec:
      containers:
        - name: myapp
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```

Values:

```yaml
replicaCount: 3

image:
  repository: nginx
  tag: "1.27"
```

---

# 4. Service ⭐⭐⭐⭐⭐

Service exposes Pods inside or outside the cluster.

`values.yaml`:

```yaml
service:
  type: ClusterIP
  port: 80
```

Template:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  type: {{ .Values.service.type }}
  ports:
    - port: {{ .Values.service.port }}
  selector:
    app: {{ include "myapp.name" . }}
```

Common Service types:

```text
ClusterIP
NodePort
LoadBalancer
```

---

# 5. ConfigMap ⭐⭐⭐⭐⭐

ConfigMap stores non-sensitive configuration.

`values.yaml`:

```yaml
config:
  APP_ENV: production
  LOG_LEVEL: info
```

Template:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ include "myapp.fullname" . }}
data:
{{- toYaml .Values.config | nindent 2 }}
```

Applications can consume ConfigMaps as:

* Environment variables
* Files

---

# 6. Secret ⭐⭐⭐⭐⭐

Secrets store sensitive Kubernetes configuration.

Example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: {{ include "myapp.fullname" . }}
type: Opaque
stringData:
  username: {{ .Values.database.username | quote }}
```

However, avoid putting actual production passwords directly in:

```text
values.yaml
```

or Git.

Use an appropriate secret-management solution.

# 7. Ingress ⭐⭐⭐⭐⭐

Ingress manages HTTP/HTTPS routing into the cluster.

Example values:

```yaml
ingress:
  enabled: true
  host: myapp.example.com
```

Template:

```yaml
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  rules:
    - host: {{ .Values.ingress.host }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: {{ include "myapp.fullname" . }}
                port:
                  number: 80
{{- end }}
```

Here Helm conditionally creates the Ingress.

# 8. Namespace ⭐⭐⭐⭐

Helm releases can be installed into a specific namespace.

```bash
helm install myapp ./mychart \
  -n production \
  --create-namespace
```

Check:

```bash
helm list -n production
```

Usually, the namespace is managed separately from the application Chart unless there is a specific reason to include it in the Chart.

Template:

```yaml
{{- if .Values.serviceAccount.create }}
apiVersion: v1
kind: ServiceAccount
metadata:
  name: {{ include "myapp.fullname" . }}
{{- end }}
```

# 10. RBAC Resources ⭐⭐⭐⭐⭐

Helm can create:

```text
Role
RoleBinding
ClusterRole
ClusterRoleBinding
```

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: {{ include "myapp.fullname" . }}
rules:
  - apiGroups: [""]
    resources:
      - configmaps
    verbs:
      - get
      - list
```

Then bind it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: {{ include "myapp.fullname" . }}
subjects:
  - kind: ServiceAccount
    name: {{ include "myapp.fullname" . }}
roleRef:
  kind: Role
  name: {{ include "myapp.fullname" . }}
  apiGroup: rbac.authorization.k8s.io
```

This allows the application to access only the required Kubernetes resources.

# 11. ConfigMap and Secret from Values ⭐⭐⭐⭐⭐

A common Helm pattern is:

```text
values.yaml
    ↓
ConfigMap / Secret template
    ↓
Deployment
    ↓
Application
```

Example:

```yaml
env:
  APP_ENV: production
  LOG_LEVEL: info
```

Deployment:

```yaml
envFrom:
  - configMapRef:
      name: {{ include "myapp.fullname" . }}
```

This keeps configuration separate from the Deployment template.

# 12. PersistentVolumeClaim ⭐⭐⭐⭐⭐

Helm can create a PVC.

Values:

```yaml
persistence:
  enabled: true
  size: 10Gi
  storageClass: gp3
```

Template:

```yaml
{{- if .Values.persistence.enabled }}
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: {{ .Values.persistence.storageClass }}
  resources:
    requests:
      storage: {{ .Values.persistence.size }}
{{- end }}
```

This is useful for:

* Databases
* Stateful applications
* Persistent application data

# 13. Job ⭐⭐⭐⭐

Helm can deploy Kubernetes Jobs.

Example:

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "myapp.fullname" . }}-job
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: task
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          command:
            - /bin/sh
            - -c
            - echo "Running task"
```

Jobs are useful for one-time tasks.

They can also be combined with **Helm Hooks**.

# 14. CronJob ⭐⭐⭐⭐

Helm can create scheduled Kubernetes jobs.

Values:

```yaml
cronjob:
  enabled: true
  schedule: "0 2 * * *"
```

Template:

```yaml
{{- if .Values.cronjob.enabled }}
apiVersion: batch/v1
kind: CronJob
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  schedule: {{ .Values.cronjob.schedule | quote }}
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: myapp
              image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
{{- end }}
```

# 15. HPA ⭐⭐⭐⭐⭐

Helm can configure a Horizontal Pod Autoscaler.

Values:

```yaml
autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 70
```

Template:

```yaml
{{- if .Values.autoscaling.enabled }}
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  minReplicas: {{ .Values.autoscaling.minReplicas }}
  maxReplicas: {{ .Values.autoscaling.maxReplicas }}
{{- end }}
```

Helm controls the configuration; Kubernetes performs the actual autoscaling.

# 16. Resource Requests and Limits ⭐⭐⭐⭐⭐

Helm commonly exposes resource configuration through `values.yaml`.

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

Template:

```yaml
resources:
{{- toYaml .Values.resources | nindent 12 }}
```

This allows different environments to have different resource configurations.

Example:

```text
Development
CPU: 100m
Memory: 128Mi

Production
CPU: 500m
Memory: 512Mi
```

# 17. Labels and Selectors ⭐⭐⭐⭐⭐

Helm should use consistent labels.

Example helper:

```yaml
{{- define "myapp.selectorLabels" -}}
app.kubernetes.io/name: {{ include "myapp.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end }}
```

Deployment:

```yaml
selector:
  matchLabels:
    {{- include "myapp.selectorLabels" . | nindent 4 }}
```

Pod:

```yaml
labels:
  {{- include "myapp.selectorLabels" . | nindent 6 }}
```

The labels used by:

```text
Deployment selector
        ↓
Pod labels
```

must match correctly.

---

# 18. Resource Naming ⭐⭐⭐⭐⭐

Use reusable helpers from `_helpers.tpl`.

Example:

```yaml
metadata:
  name: {{ include "myapp.fullname" . }}
```

Instead of hardcoding:

```yaml
metadata:
  name: myapp
```

This allows multiple releases:

```text
dev-myapp
test-myapp
prod-myapp
```

without resource-name conflicts.

---

# 19. Resource Dependencies ⭐⭐⭐⭐

Some Kubernetes resources logically depend on others.

Example:

```text
Secret
   ↓
Deployment
   ↓
Service
   ↓
Ingress
```

Helm renders resources from templates, but Kubernetes ultimately manages resource readiness and relationships.

Don't rely on simple template file ordering as a general mechanism for application readiness.

For operations that truly need lifecycle ordering, Helm Hooks or Kubernetes-native readiness mechanisms may be appropriate.

# 20. Helm with a Complete Application ⭐⭐⭐⭐⭐

A realistic Helm Chart may contain:

```text
myapp/
├── Chart.yaml
├── values.yaml
├── values-dev.yaml
├── values-prod.yaml
│
├── charts/
│
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── configmap.yaml
    ├── secret.yaml
    ├── ingress.yaml
    ├── serviceaccount.yaml
    ├── role.yaml
    ├── rolebinding.yaml
    ├── pvc.yaml
    ├── hpa.yaml
    └── _helpers.tpl
```

This is a typical application-oriented Helm structure.

# 23. Debugging Helm + Kubernetes Resources

```bash

```

```bash
helm lint ./mychart
```

Dry run:

```bash
helm install myapp ./mychart --dry-run --debug
```

Deploy:

```bash
helm upgrade --install myapp ./mychart
```

```bash
helm status myapp
```

```bash
kubectl get all
```

```bash
kubectl get pods
```



# Quick Interview Revision

**Q: What does Helm deploy?**
→ Helm deploys Kubernetes resources generated from Chart templates.

**Q: Can Helm create a Deployment?**

Yes:

```yaml
kind: Deployment
```

**Q: Can Helm create Services, ConfigMaps and Secrets?**

Yes.

**Q: How do you make a resource optional?**

Use a condition:

```yaml
{{- if .Values.ingress.enabled }}
...
{{- end }}
```

**Q: How do you configure resources for different environments?**

Use separate values files:

```text
values-dev.yaml
values-test.yaml
values-prod.yaml
```

**Q: How does Helm handle application configuration?**

Typically:

```text
values.yaml
    ↓
ConfigMap / Secret
    ↓
Deployment
    ↓
Application
```

**Q: Does Helm perform autoscaling?**

No. Helm creates/configures the HPA; **Kubernetes HPA performs the actual autoscaling**.

**Q: Does Helm manage Kubernetes resources after deployment?**

Yes, Helm tracks resources as part of a release, while Kubernetes is responsible for running and reconciling the resources.
